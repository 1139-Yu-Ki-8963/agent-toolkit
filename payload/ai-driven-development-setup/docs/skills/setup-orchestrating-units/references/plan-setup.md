# plan-setup.sh の判定方法

`scripts/plan-setup.sh` が実行順を導く2つの根拠と、その近似の粗さを記す。

## 2つの辺

1. `requires`: 機能 X の `requires` に機能 Y があれば、Y を X より先に置く
2. 入出力の重なり: 機能 Y の `outputs` のいずれかと、機能 X の `inputs` のいずれかが「重なる」なら、Y を X より先に置く

## 重なりの判定（近似）

入力・出力はいずれもパターン文字列（例: `docs/rules/*/parent.yml`）で宣言する。重なりの判定は、パターンを `/` で区切った要素列に分ける。要素数が同じで全要素が一致するときだけ「重なる」とみなす。要素どうしの一致は、どちらかが `*` を含む場合と含まない場合で分かれる。含む場合はその要素を相手側に対する近似一致とする（`*` を `.*` に置き換えた正規表現、または相手も `*` を含むなら無条件で一致）。どちらも `*` を含まなければ、文字列として等しいときだけ一致とする。

例えば `docs/rules/*/parent.yml` と `docs/rules/*/*/rule.md` は要素数が4と5で異なるため重ならない。

一方 `docs/design/*/*/基本設計書.md` と `docs/design/screens/a/基本設計書.md` は要素数がどちらも5である。ワイルドカードの位置の要素どうしも近似一致するため、この2つは重なる。

この判定は近似である。要素ごとの一致を取っても、実際には無関係なパターン同士を重なると判定してしまう場合や、書き方が異なるが同じファイル集合を指すパターン（要素数が異なる書き方等）を重ならないと判定してしまう場合がある。宣言する側が、意図しない実行順を避けたい場合は、パターンの要素構成を意図的に分ける、または `requires` で明示するとよい。

## 機能の定義の置き場

機能の定義は既定で `<リポジトリのルート>/docs/skills` から読む。この置き場が存在しない場合は `<リポジトリのルート>/.claude/skills` を読む。納品先のリポジトリは、支援ツールの定義そのもの（`docs/skills`）を持たず、派生済みの `.claude/skills` だけを持つ。この fallback が無いと、納品先で計画を組み立てられない。

## 外部入力

どの機能の `outputs` とも重ならない `inputs` は「外部入力」として計画の表に載せる。統括はこれを依存関係の欠落としては扱わず、読む側の判断に委ねる。`--target` を渡した場合は、そのパスの下に該当パターンに一致するファイルが実在するかどうかを添えるが、実在しなくても計画自体は終了コード0で返す。

## 既知の限界

- 要素数が異なるパターンは常に重ならないと判定する。同じ場所を異なる階層数の書き方で指すパターンは重なりを見逃す
- `*` を含む要素どうしの一致は、両方が `*` を含む場合に判定を単純化し無条件で一致とみなす。厳密な正規表現としての交差判定は行わない
- 同一の機能内で `inputs` と `outputs` が重なっていても自己辺は作らない（i != j の対だけを見る）
- 循環が検出された場合、報告する循環は残存ノードの中から名前の辞書順で最小のものを起点に1つ見つけた例であり、複数の循環がある場合にすべてを列挙しない

## --until による打ち切り

`--until <機能名>` を渡すと、トポロジカル順に並べた計画のうち、その機能名のSTEPまでを残し、以降のSTEPを出力しない。table形式の表・外部入力の表も打ち切り後のSTEP集合だけを反映する。指定した機能名が計画のSTEPに無い場合は終了コード2で止まる。統括の手順1は、出力の範囲（全部・基本設計まで・一覧まで）から`--until`へ渡す機能名を選ぶ対応づけを持つ。
