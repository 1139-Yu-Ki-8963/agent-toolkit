# リバースの流れの設計

既存コードから設計書を起こすリバース工程（reverse 単位）の流れを定める。流れを第一フェーズと第二フェーズに分け、各工程を同じ 17 の観点で書く。要件は `docs/design/requirements/AI駆動開発の導入支援の要件.md`、体系の決定は `docs/design/common/体系の設計.md` にある。置き場は `docs/design/common/作業ディレクトリと出力の配置.md` にある。

この文書は基本設計の粒度で書く。引数の名前・ファイルの名前・検査の判定式・様式の節と列の細部は詳細設計の段で決める。

## 決まっていること

- 流れは第一フェーズと第二フェーズに分ける
- 第一フェーズでは、コードの調査と分析を AI が読んで行う。知らないリポジトリに既製の検索パターンを当てる形は取らない
- 第一フェーズの出力は、道標・承認用の要約・要件定義書・共通設計文書である。承認用の要約は 1 枚に収める
- 第二フェーズは、道標を地図にして、第一フェーズが見つけた言語・フォルダ構造・検出条件を前提に一覧化し、詳細設計・テスト設計・確認事項一覧まで行う
- 人に聞くのは 3 回（範囲の承認・確認事項の提示・完了の受け入れ）である。中間で人を待たない
- 詳細設計へ進む判定は人に聞かない。機械検査と自己レビューの繰り返しで判定し、hook で止める

## 流れに求める条件

流れの良し悪しはこの条件で測る。出典の無い 2 件は提案である。

| キー | 条件 | 出典 |
|---|---|---|
| 件数の一致 | 種別ごとの件数が実測と一致する | 要件の柱 1 |
| 対象外の理由 | 対象外とした全件に理由がある | 要件の柱 1 |
| 試作と本番の同一手順 | 範囲を絞った試作も本番と同じ工程で作れる | 要件の柱 1 |
| 再生成の照合 | 詳細設計書だけからコードを再生成し、元と照合できる形になっている | 要件の柱 2 |
| 確認事項の一元化 | 未回答の確認事項が 1 か所に集まり、回答を設計書へ反映できる | 要件の柱 2 |
| 環境の外へ出さない | 対象システムの環境の中で動き、外部への参照を持たない | 要件の制約 |
| ツール非依存 | 設計書・規約は 1 つで、特定の AI ツールに依存しない | 要件の制約 |
| 機械の完了条件 | 全工程が機械で確かめられる完了条件と tests を持つ | 要件の制約 |
| 統括を直さない | 工程を足すとき統括の手順を直さない | 要件の制約 |
| ポータル任意 | 流れの出力に HTML を含めない | 要件の制約 |
| 大規模で動く | 数百万行規模の対象で成り立つ | 要件の対象 |
| 単位の独立 | 他の単位の名前を本文に書かず、受け渡しは出力ファイル経由 | 体系の決定 |
| 人に聞く 3 回 | 範囲の承認・確認事項の提示・完了の受け入れの 3 回だけ | 作業の計画 |
| 判定を人に頼らない | 詳細設計へ進む判定は機械検査と自己レビューで行う | 作業の計画 |
| 同じ入力で同じ出力 | 機械で読む部分は、同じ入力から同じ出力が出る | 体系の決定 |
| 置き場の遵守 | 出力の置き場は配置の設計文書に従う | 配置の設計文書 |
| 実測の裏付け | 言語や構成への依存は実測で裏付ける | 作業の計画 |
| 要件が先 | 要件定義を基本設計より先に置く | スライドの決まり |
| 基本設計を閉じる | 全単位の基本設計を閉じてから詳細設計へ進む | スライドの決まり |
| 単体テストは基本設計で | 単体テスト設計書は基本設計の段で作る | スライドの決まり |
| 共通の詳細が先 | 共通処理の詳細設計を単位ごとの詳細設計より先に書く | スライドの決まり |
| 再開できる | 途中で止まっても、終わった工程をやり直さずに続きから再開できる | 提案 |
| 差し戻しの発散判定 | 同じ不合格が 2 回続いたら方法を変え、人に戻さない | 提案 |

## 用語

| 語 | 意味 |
|---|---|
| 種別 | 単位の種類。画面・接続窓口・表・バッチ・帳票・外部連携・機能の 7 つ。メッセージは単位にせず、共通外部仕様書の節にする。数え方の定義は次のとおり。画面: 経路（ルーティング）に対応するページを 1 つと数える。再利用される部品は単位にせず、道標の節 1「UI 共通部品」と共通外部仕様書で扱う。1 ファイルが複数の経路から共有される場合は経路ごとに数え、専用ファイルを持たない経路も数える。接続窓口: 経路と HTTP メソッドの組を 1 つと数える。データベースの関数・トリガーは接続窓口にせず、表の事実（制約・関係）に属させる。表: 現在存在する表を 1 つと数える（削除された表は数えない）。定義元はマイグレーションかスキーマの写しのどちらか 1 つに決め、アプリ側のモデル定義は属するファイルとする。バッチ: 業務のデータを処理する定期処理・取り込み処理を 1 つと数える。CI・lint・ビルド・品質確認の道具は含めず、除外の種類「開発の道具」にする。帳票: 帳票の様式 1 つを 1 つと数える。外部連携: 他システムとの通信の実装（呼び出し 1 か所）を 1 つと数える。取り込むデータファイルは外部連携にせず、節 5「動的な定義」か資産として扱う。機能: 業務の単位。道標の 4.8「機能のまとめ方」に従う。まとめ方が無ければ、経路と接続窓口の束を業務の言葉で括る |
| 単位 | 設計書を 1 つ持つまとまり。種別ごとの数え方の定義は「種別」の行にある |
| 領域 | 第一フェーズで AI が読む単位。フォルダ構成から切り出すまとまり（サブシステム・モジュール・層など） |
| 道標 | 第一フェーズが書く、対象の調査結果と第二フェーズの地図。1 枚に限らない |
| 承認用の要約 | 範囲の承認のために人が読む 1 枚 |
| 検出条件 | 第二フェーズが単位を見つけるために実行する条件。AI が読んで見つけた目印を、実行できる形で書いたもの |
| 到達範囲 | 種別 × 工程ごとに、機械で回す・AI の読み取りで回す・対象外のどれかを決めた表 |
| 差し戻し表 | どの工程のどの検査が、どこへ、何を持って戻るかを定めた表 |
| 保留 | 差し戻しで同じ不合格が 2 回続き、方法を変えても解決しない単位や領域を、既定を置いて先へ進めずに置く扱い |

## 流れの全体

```text
第一フェーズ（AI が読む。領域ごとの段階読み）
  1-1 領域の切り出しと除外
  1-2 領域ごとの調査（全領域が終わるまで繰り返す）   ─▶ 道標
  1-3 要件定義書                                       ─▶ 要件定義書
  1-4 共通設計文書                                     ─▶ 共通設計文書
  1-5 第一フェーズの検査と出し直し
  1-6 範囲の承認【人】                                 ─▶ 承認用の要約・承認の記録
第二フェーズ（道標を地図にする。検出条件を実行する）
  2-1  一覧化（実測）                 ─▶ 一覧と元データ
  2-2  要件定義書の裏付け
  2-3  基盤文書                       ─▶ 技術スタック・環境構築手順書
  2-4  単位の事実の取り出し           ─▶ 単位ごとの事実
  2-5  単位の基本設計と単体テスト設計 ─▶ 基本設計書・単体テスト設計書
  2-6  基本設計の完了判定             ─▶ 合格の記録（共通設計文書を含む）
        ║ 保留を除く全単位と共通設計文書の合格の記録が揃うまで下へ進まない
  2-7  共通処理の詳細設計             ─▶ 共通処理の詳細設計書
  2-8  単位の詳細設計                 ─▶ 詳細設計書
  2-9  テスト設計                     ─▶ テスト観点表・テストケース一覧・結合テスト仕様書
  2-10 規約提案                       ─▶ 規約提案（用語の追加候補を含む）
  2-11 確認事項一覧                   ─▶ 確認事項一覧
  2-12 確認事項の提示【人】
  2-13 完了報告と受け入れ【人】
```

第一フェーズは柱 1（調査を支える）と柱 2（基盤一式の作成を支える）の両方の起点である。柱 1 の試作は、範囲を 1 領域に絞って第一・第二フェーズを同じ工程で回すことで行う。

## 大規模な対象の読み方（段階読み）

数百万行の対象を AI が一度に読むことはできない。第一フェーズは次の形で読む。

1. 工程 1-1 で、フォルダ構成・依存の定義・ビルドの定義から領域を切り出す。1 領域は AI が一度に読める量に収める。収まらない領域はフォルダで再分割する
2. 工程 1-2 を領域ごとに回し、道標へ追記する。読んだ範囲は「読みの記録」に、領域・フォルダ・ファイル数・読み方（全文を読んだ・要約だけ読んだ・読んでいない）・根拠を書く
3. 全領域の読みが終わったら道標を閉じる。読んでいない範囲は到達範囲で「未読」とし、対象外にするか確認事項に登録する
4. 途中で止まったときは、読みの記録にある未完の領域から再開する。終わった領域は読み直さない

承認用の要約は 1 枚に収める。道標の本体は領域の数に応じて長くなってよい。

## 読む対象の既定

- 既存の設計文書: 手順 3 の参考資料とし、単位の検出はしない
- 補助のポータルや管理画面: 対象外（補助の資産）
- reverse の工程は先方に規約を置かない。設計書の決まりの検査は支援ツール側の写しで行う

## 出力の型

### 道標

先方リポジトリの `docs/design/common/道標.md`。節は次の 11 である。旧のアーキテクチャ調査書はこの道標に置き換わる。

| 節 | 内容 |
|---|---|
| 0 対象と時点 | 対象の名前、ブランチ、コミット（第一フェーズはこのコミットに固定して読む。稼働中の変更は対象外）、作成日、文字コード（非 UTF-8 は変換して読む）、構成の形（単一・モノレポ・複数サイト。複数の独立したアプリや配布物を 1 リポジトリで管理する場合だけ「モノレポ」とし、1 つのアプリを backend と frontend に分けて置く形は「単一」とする） |
| 1 調査 | 言語と版、フレームワークと版（世代が混在する場合は全部）、実行環境の前提、フォルダ構造、層構造、入口、外部接続、データの保存先、ミドルウェア、依存の定義の場所、ビルド・起動・テストの定義の場所、環境の値の定義の場所、テストの枠組みと場所、UI 共通部品の場所、共通と単位固有の境界。各項目に場所（パス）を持つ。場所は複数のパスを `;` 区切りで書ける。検査は各パスの実在を見る |
| 2 領域 | 領域、対応するフォルダ、役割、規模（ファイル数）、読みの順。フォルダに加えて、どのフォルダにも属さない直下のファイル（App.tsx など）の帰属も書く。完了条件は「全フォルダと全ファイルが領域か除外に属する」 |
| 3 除外 | 除外するフォルダ、種類（生成コード・廃止コード・ベンダー・試験用・開発の道具・資産（画像・データ）・既存文書・その他）、理由。フォルダ内の一部だけを除く場合は「フォルダ内のパターン」列に glob を書く。要件「対象外の全件に理由がある」の置き場 |
| 4 単位の見つけ方 | 7 種別ごとに、単位の定義、走査の範囲、検出条件（対象フォルダ・拡張子・照合する文字列または記法・除外。第二フェーズが実行できる形。1 種別につき囲みは 1 つとし、補完の囲みを置く場合は `"補完": true` を付け、実行器は候補数に合算しない。検出条件の形の制約は「検出条件の形の制約」節に従う）、分割の規則、識別子の付け方、名前の取り方、説明の取り方、属するファイル、分類軸の取り方、例（実在するパス）。言語や世代ごとに見つけ方が違う種別は行を足す。検出条件で表せない種別は、単位の定義・まとめ方の規則・例は書き、走査・目印・分割は「AI の読み取り」と書く（その種別は節 9 の一覧化と事実の取り出しも「AI の読み取り」になる）。横断で、機能のまとめ方。加えて種別ごとに、事実の取り出しの規則（事実の形の各項目を、この対象のどの構文・どの記述から取るかを、第二フェーズの実行器が解釈できる形で書いたもの） |
| 5 動的な定義 | 設定ファイル・データベースの表・外部の定義ファイルで動的に決まる単位について、定義の場所、種別、見つけ方、環境の制約（データベースを読めない場合は定義の写しを先方に求める旨）。コード内の登録表（registry など）も含める |
| 6 候補数 | 種別 × 領域の概数。現在の実在数を、節 4 の分割の規則と同じ数え方で数える。AI の読み取りの種別は範囲（12〜20 のように）で書き、数え方に判断の根拠を書く。同じ単位を複数の領域で数えない（定義元の領域だけに数を置き、他の領域は 0 とし「定義元は…」と書く） |
| 7 共通方式の場所 | 認証・権限・エラー・ログ・データアクセス・設定・入力検証・メッセージ・トランザクション・排他の各方式の実装の場所。場所は複数のパスを `;` 区切りで書ける。検査は各パスの実在を見る |
| 8 用語の候補 | コードの名前、業務の言葉、出典。定義は規約「業務の言葉の決まり」であり、この節はそこへの提案である |
| 9 到達範囲 | 種別 × 4 工程（一覧化・事実の取り出し・基本設計・詳細設計）ごとに、機械・AI の読み取り・対象外のどれかと理由 |
| 10 読みの記録 | 領域ごとの読み方と根拠 |

確認事項は道標に持たない。各工程が `ai-output` の確認事項の記録へ直接書く（定義を 1 つにするため）。

### 承認用の要約

`ai-output` の `confirmations/承認用の要約.md`。1 枚。範囲（対象・対象外）、除外と理由の一覧、種別ごとの候補数、到達範囲の要点、確認事項の件数と重要な事項、読み残し、要件定義書の要点（3 行）、共通設計文書の要点（3 行）。人はこの要約と確認事項で判断し、全文を読むことを求めない。

### 要件定義書

先方リポジトリの `docs/design/requirements/要件定義書.md`。規約「設計書の書き方の決まり」の要件定義書の 6 内容に節を 1 対 1 で対応させる。旧の 5 文書の様式は使わない。

| 節 | 内容 |
|---|---|
| §1 適用の範囲 | 対象範囲、対象外、前提条件、関係者の責務、変更管理の方針。見出し「対象範囲」を持つ |
| §2 業務要件 | 目的、業務プロセス、業務仕様（取引・会計・勘定・外部接続）。業務の言葉は規約「業務の言葉の決まり」を参照する |
| §3 機能要件 | 機能（業務の単位）ごとに、目的、利用者、入力と出力、例外時の要求、権限の要求、優先度と根拠、対応する種別と単位の候補。見出し「優先度」を持つ |
| §4 非機能要件 | 性能、可用性、拡張性、セキュリティ、監査、運用、バックアップ、災害対策、保守性 |
| §5 制約条件 | 法令と規制、社内標準、既存資産、移行条件、稼働時間、ネットワークの制約 |
| §6 受入条件 | 完了の定義、受入テストの観点、検収条件、品質基準。見出し「受入条件」を持つ |

リバースでは、現状のコードが実現している振る舞いを現状の要件として確定して書く。望ましい姿との差は本文に書かず確認事項へ登録する。機能要件は AI が読んで業務の単位で起こし、第二フェーズの一覧で裏付ける。裏付けで差が出ても要件定義書は第二フェーズで変更しない。変更が要る場合は工程 1-3 へ差し戻し、再承認を経る。

### 共通設計文書

先方リポジトリの `docs/design/common/`。規約の基本設計書の内容のうち共通の部分を、次の 6 文書に分ける。文書名に「基本設計書」を含めない（規約の静的検査は「基本設計書」を含む文書に単位ごとの 6 見出しを要求するため）。共通設計文書用の見出しの検査を規約に足す。

| 文書 | 内容（規約の基本設計書の項目との対応） |
|---|---|
| 業務仕様書 | 業務フロー、状態遷移、業務ルール（判定表と計算式）、例外条件、取消と再実行と二重送信の取り扱い |
| 方式設計書 | 性能、可用性、セキュリティ、監査ログ、運用、バックアップ、災害対策の各方式 |
| データ設計書 | エンティティの論理名・キー・整合性、データフロー、更新責任、保存期間、マスキング、トランザクション境界、排他 |
| エラー設計書 | エラー分類、コード体系、利用者通知、ログ出力、リトライ可否、復旧手順 |
| 共通外部仕様書 | 画面の共通状態、共通操作、共通レイアウト、メッセージ一覧 |
| 基盤設計書 | フレームワーク構成、ビルド、デプロイ、ディレクトリ構成、環境の値の管理、認証とセッション、共通関数の契約 |

各節の位置づけ（仕様・現行実装）と要確認事項一覧は、設計書の様式の決まりに従う。

### 「不明点が存在しない」の扱い

規約の完了状態「詳細設計を書き始める上での不明点が存在しない」は、次のとおり扱う。未確定の事項に既定（決まるまでの扱い）を置き、既定のもとで詳細設計を書き始められるなら、その事項は不明点ではなく確認事項である。既定を置けない事項は不明点であり、その単位または文書は保留にして詳細設計へ進めない。完了状態の定義は変えず、既定の有無で判定する。

## 検出条件の形の制約

第二フェーズの実行器に渡す検出条件は、次の形の制約に従う。実行器の実装もこれに一致させる。

- 正規表現は行単位の拡張正規表現（ERE）。先読み・後読み・複数行の一致は使えない
- `一致` の複数の要素は「すべて満たすファイル」の絞り込みを表す。1 行に複数の単位がある切り方は `分割: 一致` と `単位: true` の要素で表す
- `識別子` の `元` は `ファイルパス` か `一致の捕捉`（正規表現の 1 番目の捕捉）。`名前` の `元` は `内容`・`ファイル名`・`識別子`
- 表の削除を辿るために `除外の一致` を足す。形は `{"対象": "内容", "正規表現": "DROP TABLE[[:space:]]+(IF EXISTS[[:space:]]+)?([a-z_]+)", "捕捉": 2}` である。捕捉した名前と同じ識別子の単位を、結果から除く。実行器はこれを解釈する
- 例は、走査で実際に拾われるファイルのパスを書く（変更だけを持つファイルは例にしない）

## 取り出しの規則の形

道標の節4の「取り出しの規則」列は、次のいずれかの形で書く。

- `正規表現: <ERE> ／ 捕捉: <N> ／ 範囲: <場所|属するファイル|両方|単位>`
- `AI の読み取り: <説明>`

区切りは全角スラッシュ「 ／ 」。捕捉の既定は1、範囲の既定は両方。セル内で `|` を書く場合は `\|` と書き、実行器が読むときに戻す。範囲の値は前方一致で読む（例えば「場所（画面ファイル）」は「場所」として扱う）。

範囲の「場所」と「単位」は、一覧の根拠（`<場所>:<行>`）が指す単位の区間だけを走査する。区間は根拠の行から、同じ場所（ファイル）内で次に大きい行を持つ別の単位の直前の行まで（同じ場所を持つ他の単位が無ければファイル末尾）。1ファイルに1単位しか無い場合は区間がファイル全体に一致する。「単位」は「属するファイルを読まない」ことを強調した「場所」の別名である。「属するファイル」の各要素は検出条件の規則の文字列であり、対象ルートからのglobとして展開して実在するファイルだけを走査する。展開結果が0件の要素は警告に留め、不合格にはしない。

実行器はこの形だけを解釈し、言語別の分岐を持たない。

## 事実の形

種別ごとの事実の項目は次のとおり。

| 種別 | 事実の項目 |
|---|---|
| screen | 入力項目・表示項目・操作・遷移・呼ぶ接続窓口 |
| api | 経路・入力・出力・検証・呼ぶ処理・触る表 |
| table | 列・型・制約・関係 |
| batch | 起動条件・入力・出力・処理の流れ |
| report | 出力条件・項目・レイアウトの元 |
| external | 相手先・形式・項目・応答・再試行 |
| feature | 含む単位 |

事実ファイルは `<出力の置き場>/facts/<種別>/<単位のフォルダ名>.json` に置く。

内容は 種別・識別子・名前・場所・属するファイル（配列）と、項目ごとの事実を持つ。

各項目の事実は 値（配列）・出所（機械かAI）・根拠（相対パスの配列）を持つ。

値は常に配列で、機械で0件だった項目は 値 が空のまま 未 に載る。

未の項目はAIが埋める。同じ手順で2回読み、一致した値を採る。決まらなければ確認事項に登録する。

## 単位の進行の記録

`<実行フォルダ>/logs/units-status.json` は、種別と識別子ごとに4工程の状態を持つ。

4工程は 事実・基本設計・完了判定・詳細設計。事実・基本設計・詳細設計の値は 済・未・保留 のいずれか。完了判定の値は 合格・不合格・保留・未 のいずれか。値の無い工程は 未 とする。

後続の機能は、工程が 済 または 合格 の単位を飛ばす。保留の単位は詳細設計を書かない。

## 合格の記録の形

合格の記録は `ai-work/records/basic-design-acceptance/<種別>-<単位のフォルダ名>.json` に置く。共通設計文書は `common-<文書名>.json` とする。

項目は 種別・識別子・文書ごとのsha256・コミット・判定・観点・理由・判定した実行 を持つ。

工程2-7と工程2-8の入口は、この記録の判定と、文書のsha256が現在と一致することを確かめる。記録が無いか不一致なら止まる。

書き込みを機械で阻止する仕組みは今回の公開では持たない。入口の検査で代える。
