# 体系の設計

このリポジトリの skill・要件・設計の体系を定める設計資料。決めたこと、その理由、退けた案、まだ決めていないことを持つ。要件の定義は `docs/design/requirements/AI駆動開発の導入支援の要件.md` である。経緯・改善事項・実践で見つかった欠点と不具合は記録として `ai-work/records/2026-09-04-体系の再設計の経緯と不具合.md` にある。

## 決定事項

| 決定 | 内容 | 採用した理由 | 退けた案 |
|---|---|---|---|
| 業務の柱 | 業務は調査・基盤一式の作成・引き渡しの3段階で進める。調査は人の手作業であり、このリポジトリは担わない | 参照スライドの3区分のうち、調査は見積もり前の判断であり支援ツール化の対象ではないため | 調査を支援ツールの柱に含める案 |
| 納品物 | 設計書・規約、各AIツールの設定、開発フローの3つ。用語は規約（業務の言葉の決まり）に含める | 用語が無いと開発が回らない根拠が無く、配る規約の1件として既に存在するため | 用語を独立した納品物にする案 |
| AIツール名 | 要件・納品物にツール名を書かない | 未対応のツール（GitHub Copilot）を約束することになるため。現場の環境の事実としてだけ制約に残す | 納品物にツール名を列挙する案 |
| リポジトリの担当 | セットアップと運用。セットアップの中に納品物セットアップ・リバースと、任意のポータル・反復リバース検証を置く | 業務の柱と支援ツールの単位は粒度が違う。単独で使いたい単位（リバースだけ等）を独立させる必要があるため | 業務の柱をそのままフォルダにする案 |
| 独立単位 | setup / reverse / verify / portal / operate の5つ。skill 名の接頭辞で表し、大分類（セットアップ／運用）は宣言に持つ | Claude Code が skill を見つけるのは `.claude/skills/` の1階層だけで、その下に柱のフォルダを作れないため | 最上位フォルダで柱を切る案 |
| 独立の条件 | 他の単位の skill 名を本文に書かない。受け渡しは出力ファイル経由だけ。共有部品は単位ごとに持つ。例外として実行フォルダを作る処理と実行順を組み立てる処理はsetup単位とreverse単位の両方の統括が使うため`reverse-shared`に1本化し、各単位の統括は`--units`を固定した入口だけを持つ | 単位を単独で取り出して動かすため | 共有部品を1か所に置き全単位が参照する案 |
| 機能の単位 | 1 skill = 1 機能。フォルダの中に SKILL.md・scripts・templates・tests・samples をすべて持つ | 追加が1フォルダで完結する。今は1納品物で8か所を直す必要があり、どこを直すか分からない | 種別（画面・API…）をフォルダの階層にする案 |
| 機能の宣言 | SKILL.md の先頭に unit・category・kind・inputs・outputs・requires を書く。統括は宣言を読んで inputs と outputs の依存で順序を決め、skill 名を直書きしない。requires には同じ単位の機能名だけを書ける | 機能を足したとき統括を編集しなくてよいため。現在の統括は43本の skill 名を直書きしている | 統括の Step 本文で呼ぶ現行方式 |
| 統括の実装 | `reverse-shared` の `plan-units.sh` が機能の宣言（requires と inputs・outputs の重なり）から実行順を導き、`STEP <n> <機能名>` として返す。`setup-orchestrating-units` の `plan-setup.sh` と `reverse-orchestrating-flow` の `plan-reverse.sh` は、それぞれ `--units` を固定して呼ぶ入口。統括の手順書は計画の出力から名前を読み、機能名を直書きしない。入出力の重なりはパターンの固定部分の接頭辞一致で判定する近似であり、外部入力は表に載せて判断を読む側に委ねる | 機能を足したとき統括を編集しなくてよいため。旧の統括は 43 本の名前を直書きしていた | 統括の Step 本文で名前を呼ぶ旧の形 |
| 合格の集計 | 機能は tests が全部通ること。単位は配下の機能がすべて合格。要件は受入基準を担う単位が合格 | 何をクリアすればよいかが各階層で機械的に決まる。テスト設計を機能ごとの表として書ける | 階層ごとに別の基準を持つ案 |
| tests の位置づけ | `tests/` は支援ツール自身の検収であり、機能を対象に実行したときの完了条件ではない。各機能の完了条件から tests の行を外し、検収の集計は統括の完了時の処理だけが担う（2026-09-04） | 自身の検収と実行時の完了条件を機械的に分けるため | 完了条件に tests を含める案 |
| 欠落の検査 | テストを持たない機能・どの機能にも属さないテスト・2単位に属する機能・統括が直書きする機能名・他の単位の名前を持つ機能・portal 以外の機能の宣言 outputs にある .html の6つを0件で要求する | 追跡の鎖が切れた箇所と、定義に混ざった人が見る物を機械で見つけるため | 目視レビューだけに頼る案 |
| 共有の定義 | output-layout・portal-catalog などの定義は `docs/` に1つだけ置き、各単位へ配布時に複製する。一致は検査で見張る | 4単位から読まれる定義を手で5か所同期する形を避けるため。定義と生成物の分け方の決まりに沿う | 各単位に手で写す案 |
| ポータル | 任意。第一段階（AIが読む定義）だけで開発フローが回る。ポータルは第一段階の出力だけを入力にする。portal 以外の4単位の SKILL.md・scripts・tests に portal の語が現れないことを欠落の検査で見張る | 業務の3段階のどこにもポータルは必須として現れないため | ポータルを納品物に含める案 |
| 確認事項一覧 | 1行1事項。単位（画面・API等）はキー列。確認事項・用語の承認の 2 種類を 1 枚に載せる（規約提案の採否は 2026-09-07 の廃止で外した）。Markdown を定義とし、各行に反映先を持つ | 顧客が確認する資産を1つにする。1単位に複数の事項があるため1行1単位にはしない。単位ごとの台帳とポータルの質問票に定義が散っている状態を解消する | 1行1単位の案、単位ごとの台帳を定義にする案、ポータルの質問票を定義にする案 |
| ユーザーへの提示 | スライドを見せる前に観点表と判定役を通し、タイトル・副題・読み手と結論の3行だけで提示する | 長文の提示が読まれずに差し戻された実例による。規約 `generating-explanation-html-slides` の「ユーザー提示」節に定めた | 構成の解説や検査結果を添える提示 |
| ルート構成 | ルート直下は `docs/`・`.claude/`・`delivery-payload/`・`ai-work/` の4つ。定義・機能・配布の3層と運用の記録に対応する。`generation-engine/` は解体し、scripts と samples は各機能フォルダへ、単位共有の部品は `delivery-payload/<単位>/shared/` へ移す。`ai-work/` はこの体系を作り直す作業の計画・作業指示書・完了記録を置き、対象プロジェクトのフォルダの `ai-work/` と同じ形にする | 層とフォルダを1対1にし、置き場に迷わないため。作業の計画を旧リポジトリの指示書に置いたままでは、旧は不具合修正だけを行う決定と矛盾するため | `generation-engine/` を残して中を単位で切る案、作業の計画を旧リポジトリの `docs/tasks/` に置き続ける案 |
| skill の定義と派生 | `docs/skills/<単位>-<機能>/` を定義とし、`.claude/skills/` へ機械で派生させる。派生の仕組みは新リポジトリの最初の機能とする | 納品先に求める「定義は docs、派生は生成物」の仕組みを自分自身にも持つため。持たなければ納品先に同じ運用を求める根拠が無い | `.claude/skills/` を定義にする案（編集のたびの派生は不要だが、納品先と仕組みが食い違う） |
| 規約の定義の形 | front matter に `docType: rule \| context` と任意の `derivedPath` を持つ。`context` は説明文書（project-context 等）で、規則の表の検査を飛ばし本文だけを派生する。`derivedPath` は共通の hook が固定の場所で読む派生物のために派生先を上書きする。生成器はリポジトリのルート・分類定義・checker の置き場をすべて引数と規約フォルダから解決し、自分の位置に依存しない | 旧の生成器を新しい置き場で動かしたところ、置き場依存のパス解決と規則表前提の検査で止まったため | 説明文書を規約の外に置く案（共通 hook の固定パスへ派生できない） |
| project-context の置き場 | 配置先でも自分のリポジトリでも `docs/rules/agent-operations/project-context/rule.md` を定義とし、`docType: context` と `derivedPath` で共通の hook が読む固定の場所へ派生させる。`flow-values.yml` は規約ではないため配置が直接書く | 配置が派生物を直接書くと、定義から派生する形と矛盾し、ずれ検査が常に「余分」を報告するため。親は分類定義にある `agent-operations` に揃え、自分専用の親を作らない | 配置が `.claude/rules` を直接書く旧の形、自分専用の親 `repository-operations` を持つ案 |
| category の値 | 宣言の category は支援ツールの3本柱に対応する `survey`・`setup`・`operate` の3値。unit が operate なら category は operate。それ以外の unit は3値のどれでもよい（例: 納品先で回すポータル保守は unit=portal・category=operate） | 要件の合格を柱ごとに集計するには、機能が柱のどれを担うかを宣言に持つ必要があるため。2値では調査を支える柱を表せなかった | category を setup／operate の2値にする当初の案 |
| 合格の集計の実装 | `setup-orchestrating-units`の完了時の処理が機能（tests全通過）→単位（配下すべて合格）→要件（柱ごとにcategory一致の機能がすべて合格し、必須単位に機能がある）を1コマンドで判定し、欠落5つを0件で要求する。柱と単位の対応は `docs/design/requirements/requirement-pillars.json` に置く。tests1本の上限は300秒で、超過は不合格ではなく未確認として扱う | 何をクリアすればよいかを各階層で機械的に決めるため。上限超過を不合格に数えると、実行環境の都合を成果物の欠陥と読み違える | 階層ごとに別の基準を持つ案、上限超過を不合格に数える案 |
| skill の派生の形 | `docs/skills/<名前>/` から `tests/` と `samples/` を除く全ファイルを `.claude/skills/<名前>/` へ複製する。SKILL.md は front matter の直後に生成物の印を入れる。派生の前に定義の形（宣言の鍵・名前と接頭辞と unit の一致・requires の同一単位・tests の実在・他の単位の名前の不在）を検査する | 実行時に要るのは手順とスクリプトだけで、検査と見本は定義側にあればよいため。欠落の検査を派生の入口に置けば、検査を通らない機能は Claude Code に読まれない | 派生せず `.claude/skills` を定義にする案 |
| 新リポジトリ | `ai-driven-development-setup` を新設し、そこへ新構造を作る。旧リポジトリ（reverse-docs-skills）は配布済みの納品物の不具合修正だけを行い、新しい機能を足さない | 旧の規約・hook・公開の受け口が現構造に結び付いており、その場で組み替えると作業のたびに止まるため。移行の期間に `generation-engine/` が残ることも、ルート直下の許可リストと両立しない | 同じリポジトリの中で横に作る案 |
| 移行の進め方 | 単位ごとに新リポジトリへ作る。合格条件に「旧リポジトリの見本と同じ入力から同じ出力が出る」を含める。旧の検査は写さず、機能ごとの tests へ振り直す。単位が合格するごとに旧の対応する skill を廃止する | 一気に移すと合格を判定できない期間が長くなるため | 全部書いてから一気に移す案 |
| このリポジトリ自身の定義と生成物 | 規約は `docs/rules/` を定義とし `.claude/rules/` へ派生させる。skill も同じ仕組みで派生させる | 納品先と同じ仕組みを自分自身が持つため | `.claude/` を定義にする案 |
| 公開 | リポジトリ自体は GitHub に置かない（remote を持たない）。必要な内容だけを agent-toolkit の `payload/ai-driven-development-setup` へ同期して公開する。公開対象は `.claude/skills`（派生）・`delivery-payload`・`README.md` とし、`docs/` は配らない。受け口 `.claude/rules/always/publish/publish-values.txt` は hook が固定の場所で読むため `.claude/` に直接置く。同期定義への登録は最初の配布物ができた時に行う | 旧リポジトリと同じ運用にし、定義と設計資料を外へ出さないため | GitHub に非公開リポジトリを作る案 |
| skill の名前 | 名前は `<単位>-<作業>-<対象>` の 3 語だけで組む。種別は `kind`、文脈は `unit`・`category` が表し、名前に入れない。共有部品は `<単位>-shared`。規約 `docs/rules/agent-operations/skill-naming/` が定義し、検査は機能の派生の入口から呼ぶ | 名前で単位をグループ分けしているため、形が崩れると欠落の検査と統括の計画が崩れる。旧の名前は文脈と種別の語を重ねており、束ねる粒度と合わない | 名前の形を validate の実装だけに持ち規約を書かない案 |
| 規約と検査の 1 対 1 | 配る規約の定義は `templates/rules/tool-defined/<親>/<子>/` に rule.md・checker・checker の test を同じフォルダで持つ。横断の検査 5 本は規約に起こし（27 → 32 件）、横断の枠は無くす。検査は宣言と実在の 1 対 1（宣言の無い checker・1 つの checker を 2 規約が宣言・test の欠落）を不合格にする | 共通の決まり「規約のフォルダに、その規約を守らせる hook を 1 対 1 で置く」を定義側にも適用するため。定義と配置先で置き場が違うと、どの検査がどの規約のものかを追えない | checker を 1 フォルダにまとめる旧の置き場、1 規約に複数の checker を許す案 |
| リバースの流れ | 第一フェーズ（AI が読む: 領域の切り出し → 領域ごとの調査 → 要件定義書 → 共通設計文書 → 検査と出し直し → 範囲の承認）と第二フェーズ（調査と検出条件の定義書の検出条件を実行: 一覧化 → 要件定義書の裏付け → 基盤文書 → 読み取り結果の取り出し → 基本設計 → 完了判定 → 共通処理の詳細設計 → 詳細設計 → 確認事項一覧 → 提示 → 完了報告）の 17 工程（2-10 は欠番）（テスト設計は出力するときだけ）。定義は `docs/design/common/リバースの流れの設計.md` | 知らないリポジトリに既製の検索パターンを当てられないため、AI が読んで対象に合った検出条件を組み、それを機械で実行して件数で確かめる 2 段にした。実案件のコードで第一フェーズを通し、4 種別で実測が候補数と一致した | 一覧を先に機械で作り、その後に要件を書く旧の順序（言語ごとの走査スクリプトを前提にする） |
| 要件定義書の組み込み | 含める。第一フェーズで AI が現状の要件として書き、第二フェーズの一覧で裏付ける。様式は規約「設計書の書き方の決まり」の 6 内容に節を 1 対 1 で対応させた新しいもの | 基本設計書は要件定義書で確定した要求を実現する文書であり、要件なしに書き始めない。旧の 5 文書の様式は規約の内容を持っていなかった | 含めない（当初の既定）。一覧と基本設計書と現場の回答から起こす 4 段の順序 |
| 機能の粒度 | 作業ごとに 1 機能。種別は `kind` の引数で受ける | 種別ごとに機能を分けると同じ作業が 7 つに割れ、統括と検査が増える | 種別ごとに機能を分ける |
| 単位共有の部品の置き場 | `docs/skills/<単位>-shared/` に置き、配布時に `delivery-payload/<単位>/shared/` へ複製する | 単位を単独で取り出して動かすため、共有は単位の中に閉じる | 全単位が 1 か所を参照する |
| 人に聞く場面 | 範囲の承認・確認事項の提示・完了の受け入れの 3 回。中間で人を待たず、既定を置いて進む | 無人で走らせるため。判定を人に頼ると基準がぶれる | 基本設計の完了時に人へ確認する |
| python 専用の読み取り結果抽出の経路 | 持ち込まない。言語ごとの走査や抽出の規則は支援ツール側に持たず、第一フェーズが対象を読んで検出条件と取り出しの規則を組む | 言語ごとの経路を支援ツールが持つと、知らない対象で合わない | 言語ごとの経路を機能に持つ |
| 検証の出力先 | 対象リポジトリの外（`ai-output/<対象プロジェクト名>/<実行の識別子>/`）。確認事項・承認の記録・読み取り結果・記録を置く | 対象プロジェクトのフォルダには AI が読む定義だけを置き、回答の途中の状態を混ぜない | 対象リポジトリの中に置く |
| 確認事項一覧のキー | 内容を要約した意味語のキー。連番は使わない | 規約が連番を禁じている | 連番の番号 |
| 公開の段階 | 納品物の段階で切る。公開1〜3 | 機能の途中で止めると完了の判定ができないため | 機能の途中で止める案 |
| 出力の範囲 | 統括の前提の確認で3値（全部・基本設計まで・一覧まで）を選ぶ | 一覧までや基本設計までの試作を、人に聞かずに打ち切れるようにするため | 常に全部を実行する案 |
