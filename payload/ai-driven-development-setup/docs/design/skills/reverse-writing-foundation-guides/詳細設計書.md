# 基盤文書を書く（reverse-writing-foundation-guides）の詳細設計書

## §2 処理の定義

**この節の位置づけ: 現行実装**

1. `check-entry.sh` で範囲の承認（可否・調査と検出条件の定義書の同一性）を確かめる。
2. `templates/技術スタック.md` を対象へ複製する。
3. `templates/環境構築手順書.md` を対象へ複製する。
4. 調査と検出条件の定義書の節1と基盤設計書、依存の定義ファイルを読み2文書を埋める。技術スタックの「名前」は依存の定義ファイルに実在する名前をそのまま書く。
5. 環境の値（接続先・秘密の値）は書かず、要確認事項一覧と確認事項の記録へ登録する。
6. `check-foundation-guides.sh` を実行する。
7. 終了コードを見て、1なら不合格の内容（依存-不在・節-欠落・位置づけ-欠落・未記入-残存・位置-禁止・秘密-混入）を読み文書を直し手順6からやり直す。

## §3 ロジック

**この節の位置づけ: 現行実装**

### check-foundation-guides.sh

技術スタックに書いた依存の名前が実際の依存の定義に実在するか、環境構築手順書に環境の値そのものが紛れ込んでいないかは、目視では見落としやすい。依存の定義ファイルとの文字列一致・節構成・秘密の値らしき記述の検出は機械で確実に行える。

AIの自己レビューだけに任せる案は、秘密の値の混入は見落とすと影響が大きく機械検査を欠かせないため採らない。依存の定義ファイルを構文解析して版まで突き合わせる案は、依存の定義ファイルの形式が言語ごとに異なり名前の文字列一致で十分な精度が得られる範囲を超えるため採らない。

保守責任者は人手（ユーザー）。様式（templates/技術スタック.md・templates/環境構築手順書.md）の節構成を変えるときは、本スクリプトと自己テストを同時に直す。

廃棄条件は基盤文書の機械で読む部分を構造化データとして別に出す形に変えた時。
