# リバースの統括（reverse-orchestrating-flow）の基本設計書

reverse単位の機能の宣言を読んで実行順を組み立て、実行フォルダを作ってから各機能を順に実行し、出力の範囲で打ち切る。

## §1 外部仕様

### 要件との対応

| 要件の柱 | 要件の項目 | この機能が満たす内容 |
|---|---|---|
| 支援ツール全体の制約 | 柱ごとに取り出して動く。機能を1つ足すとき、統括の手順を直さない | reverse単位だけを単独で動かす入口を持ち、setupの統括の手順を直さずに新設する |
| 支援ツール全体の制約 | 全機能がテストと合格基準を持つ | `scripts/plan-reverse.sh --self-test`と`tests/`で完了条件を確認する |
| 柱2 基盤一式の作成を支える | 完了条件: 未回答の確認事項が無い | 共通設計文書6つの合格の記録が現在の文書と一致することを門として確かめてから次工程へ進める |

### 入力

| 入力 | 形 | 出所 |
|---|---|---|
| docs/skills/reverse-\*/SKILL.md | Markdown（front matter） | reverse単位の各機能の宣言 |
| 対象範囲・対象プロジェクト名・展開先・出力の範囲 | AskUserQuestionの回答 | 利用者 |

### 出力

| 出力 | 形 | 置き場 |
|---|---|---|
| 実行フォルダとrun.json | JSON | `ai-output/*/*/run.json`（`../reverse-shared/scripts/start-run.sh`が作る） |
| 実行計画の報告 | Markdown | `ai-output/*/*/reports/reverse-plan.md` |
| 納品物一覧 | Markdown | `docs/design/lists/納品物一覧.md`（写しを`ai-output/*/*/reports/納品物一覧.md`） |
| 完了報告 | Markdown | `ai-output/*/*/reports/完了報告.md` |

### 実行の口

Skill("reverse-orchestrating-flow")として呼ぶ。内部で`scripts/plan-reverse.sh`・`scripts/build-completion-report.sh`を呼ぶ。あわせて`../reverse-shared/scripts/start-run.sh`・`check-acceptance-record.sh`も呼ぶ。

## §2 業務仕様

### 手順

0. 前提の確認（作業場所・対象プロジェクト名・設計書の展開先・出力の範囲）をAskUserQuestionで確かめ、`start-run.sh`へ渡す
1. `scripts/plan-reverse.sh`で実行順の計画を得る（出力の範囲に応じて`--until`を足す）
2. 計画の各STEPを上から順にSkillで実行する
3. 各機能の完了条件を確かめてから次へ進む
4. 共通処理の詳細設計書を書く機能の前に、`check-acceptance-record.sh --common`で共通設計文書6つの合格の記録を確かめる門を置く
5. 全STEPが終わったら計画の表と各機能の結果を`reports/reverse-plan.md`へ書く
6. 工程2-13（完了報告と受け入れ）として納品物一覧を`docs/design/lists/`へ書く。単位は表示名で列挙し識別子を併記する
7. 工程2-13の完了報告を`reports/完了報告.md`へ書く。持つのは到達範囲・納品物の件数・確認事項の件数と未回答の件数・実行した機能とその結果・受け入れの欄の5つである。受け入れの欄は人が書くため空で出す

### 判定の規則

| 検査 | スクリプト | 検査キー |
|---|---|---|
| 実行順の組み立て | scripts/plan-reverse.sh（実体は../reverse-shared/scripts/plan-units.sh） | 循環検知・units絞り込み・until打ち切り |
| 実行フォルダの作成 | ../reverse-shared/scripts/start-run.sh | 既存フォルダ検知・gitリポジトリ判定 |
| 共通設計文書の合格記録の門 | ../reverse-shared/scripts/check-acceptance-record.sh --common | 同一性-不一致・記録-不在 |
| 完了報告と納品物一覧の集計 | scripts/build-completion-report.sh | 納品物-不在 |

## §3 方式設計

機械とAIの分担は、実行順の組み立て・実行フォルダの作成・合格記録の確認を機械（共有部品のスクリプト）が担い、AIが各STEPのSkill呼び出しと完了条件の確認を担う二段構成である。

実行方式はシェルスクリプトによる計画の組み立てと、Skill呼び出しの列挙であり、対象コードの言語に依存しない。

### 設計判断: scripts/plan-reverse.sh・scripts/start-run.shの委譲先

**必要性**: 実行フォルダを作る処理（`start-run.sh`）と実行順を組み立てる処理（`plan-units.sh`）は、セットアップの統括（setup単位の統括）と全く同じ実装で足りる。reverseを単独で動かす統括を新設するにあたり、同じ計算を2か所に持つと、片方だけを直して整合が崩れる事故が起きる。両者から呼べる共有部品（`reverse-shared/scripts/`）へ実体を1本化し、各単位の統括は`--units`を固定して渡す入口だけを持つ。

**代替案を採用しなかった理由**:
- setup側の実装をコピーしてreverse専用に持つ: 修正のたびに2か所を同時に直す必要があり、片方の直し忘れで実行順の計算がずれる
- reverseの統括からセットアップの統括のスクリプトを直接パスで参照する: setup単位のフォルダにreverse単位が依存する形になり、単位分離の前提に反する

**保守責任者**: 人手（ユーザー）。実行フォルダの作り方・実行順の計算のロジックを直す場合は`reverse-shared/scripts/`の該当スクリプトを直す。

**廃棄条件**: reverse単位・setup単位のいずれかが統括の仕組み自体を廃止した時。

| 出力 | 形 | 置き場 |

| 完了報告 | Markdown | `ai-output/*/*/reports/完了報告.md` |

### 納品物一覧の形

納品物一覧の表の列は 種別・単位・文書・所在 の4列である。単位の欄は`<表示名>（<識別子>）`の形にする。表示名と識別子は`docs/design/lists/業務名.json`から読む。業務名.jsonは表示名の列を持たないため、一覧を作る機能と同じ規則で組む。区別が無ければ表示名は業務名とし、区別があれば`業務名（区別）`とする。単位を持たない共通設計文書の行は単位の欄を`全体`にする。

## §5 エラーと例外

### 終了コード・差し戻しの一覧

| 検査 | スクリプト | 検査キー |
|---|---|---|
| 循環検知 | scripts/plan-reverse.sh | 終了コード1 |
| untilの対象不在 | scripts/plan-reverse.sh | 終了コード2 |
| 共通設計文書の合格記録の不一致 | ../reverse-shared/scripts/check-acceptance-record.sh --common | 基本設計書を書く機能へ差し戻す |
| 納品物一覧の行の文書が不在 | scripts/build-completion-report.sh | 終了コード1（名指しされた文書を作る工程へ差し戻す） |
| 業務名.jsonが無いか読めない | scripts/build-completion-report.sh | 終了コード3（一覧を作る工程へ差し戻す） |
| 単位のフォルダ名が空か空白だけ | scripts/build-completion-report.sh | 終了コード3（一覧を作る工程へ差し戻す） |

### 完了条件

- `../reverse-shared/scripts/start-run.sh` が終了コード0で実行フォルダを作る
- `scripts/plan-reverse.sh` が終了コード0で計画を返す
- 全STEPの機能がそれぞれの完了条件を満たす
- 工程2-13で書く納品物一覧は、単位を表示名で列挙し識別子を併記する
- `scripts/build-completion-report.sh` が終了コード0で納品物一覧と完了報告を書く
- `tests/` の全件が通る
