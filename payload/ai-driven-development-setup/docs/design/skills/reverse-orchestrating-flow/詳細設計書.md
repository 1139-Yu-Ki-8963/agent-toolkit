# リバースの統括（reverse-orchestrating-flow）の詳細設計書

## §1 構成要素

| スクリプト | 役割 |
|---|---|
| scripts/plan-reverse.sh | `--units reverse`を固定して../reverse-shared/scripts/plan-units.shへ委譲する入口 |
| scripts/build-completion-report.sh | 工程2-13（完了報告と受け入れ）の集計。納品物一覧を業務名.jsonから組み立て実在を確かめ、完了報告を書く |

## §2 処理の定義

0. 前提の確認（作業場所・対象プロジェクト名・設計書の展開先・出力の範囲）をAskUserQuestionで確かめ、`start-run.sh`へ渡す
1. `scripts/plan-reverse.sh`で実行順の計画を得る
2. 計画の各STEPを上から順にSkillで実行する
3. 各機能の完了条件を確かめてから次へ進む
4. 共通処理の詳細設計書を書く機能の前に、合格記録の門を確かめる
5. 全STEPが終わったら報告を書く
6. `scripts/build-completion-report.sh <実行フォルダ> --design-root <設計書の置き場>`で納品物一覧と完了報告を組み立てる。納品物一覧は`<設計書の置き場>/docs/design/lists/納品物一覧.md`へ書き、写しを`<実行フォルダ>/reports/納品物一覧.md`へ置く
7. 納品物一覧の各行の所在の文書が実在するかを確かめる。1件でも無ければ`[FAIL] 納品物-不在`を出して終了コード1で止める。すべて実在すれば完了報告を`<実行フォルダ>/reports/完了報告.md`へ書き、終了コード0で終わる。
8. 業務名.jsonが無いか読めないときは`[FAIL] 業務名-読めない`を出して終了コード3で止める。単位のフォルダ名が空、または前後の空白を落とすと空になるときは`[FAIL] フォルダ名-未確定: <識別子>`を出して終了コード3で止める。フォルダ名は工程2-1の業務名の確定が決めるものであり、識別子で代用しない
9. フォルダ名の前後の空白を落とすとき、空白として扱うのは半角の空白・タブ・全角の空白（U+3000）の3つである。これ以外の文字は落とさない。ノーブレークスペースなど3つ以外の空白類だけのフォルダ名は未確定として扱わず、そのままフォルダ名として使う

## §3 ロジック

`plan-reverse.sh`は自身では計画を組み立てない。共有部品が存在しなければ終了コード2を返す。存在すれば`--units reverse`を固定して引数をそのまま委譲する。ロジックの実体は共有部品側に1本化されており、本機能は入口の分岐だけを持つ。

`build-completion-report.sh`は、単位を持つ行と単位を持たない行を集めて納品物一覧を組み立てる。単位を持つ行は業務名.jsonの各種別の要素から作る。単位を持たない行は既存のMarkdownファイルから作る。対象はdocs/design/common・docs/design/requirements・docs/design/lists・種別ごとのフォルダ直下である。

単位を持つ行の所在は、種別→フォルダ名の対応（record-acceptance.shのspecies_folderと同じ対応の複製）から導く。文書名は`design-doc-name.sh`が返す基本設計書の名前を使う。run.jsonの「テスト設計書の出力」が「出力する」のときは単体テスト設計書の名前も使う。これらの所在を実在の確認対象にする。単位を持たない行は既存のファイルを走査するため、走査した時点で実在が保証されている。

単位を持つ行の対象は基本設計書・単体テスト設計書に限る。`design-doc-name.sh`は基本設計書・単体テスト設計書の名前しか持たない。詳細設計書・テーブル定義書の名前は返さない。このため詳細設計書・テーブル定義書は本スクリプトの集計対象に含めない。

対象と出力の一覧.mdと`record-acceptance.sh`の間には既知の食い違いがある。前者の「種別ごとの出力」の表は、画面（screen）種別の基本設計書の置き場を`docs/design/screens/<単位のフォルダ名>/画面/基本設計/`とする。後者のunit_pathの組み立ては`docs/design/${folder}/${dirname}/${basic_name}`であり、`画面/基本設計/`の階層を持たない。本スクリプトはrecord-acceptance.shの組み立てに合わせる。合格の記録が実際に参照する経路であり、既に機械強制されているためである。この食い違いの解消は本機能の対象外であり、対象と出力の一覧.md側の見直しが必要である。

### 受け入れの欄を空で出す理由

受け入れは人（開発チーム）が行う。スクリプトが受け入れの値を埋めると、人が見ていないのに受け入れられたように読める。完了報告は集計した事実だけを持ち、受け入れの欄は空のまま出す。工程2-13の完了条件が求める受け入れの記録は、人がこの欄へ書いた時点で成立する。

## §4 入出力の値

| 入力 | 形 | 出所 |
|---|---|---|
| docs/skills/reverse-\*/SKILL.md | Markdown（front matter） | reverse単位の各機能の宣言 |
| docs/design/lists/業務名.json | JSON | reverse-listing-unitsが書く単位の業務名の記録 |
| confirmations/確認事項の記録.md | Markdown | reverse-writing-survey-definitionが書く確認事項の記録 |

| 出力 | 形 | 置き場 |
|---|---|---|
| 実行フォルダとrun.json | JSON | `ai-output/*/*/run.json` |
| 実行計画の報告 | Markdown | `ai-output/*/*/reports/reverse-plan.md` |
| 納品物一覧 | Markdown | `docs/design/lists/納品物一覧.md`（写しを`ai-output/*/*/reports/納品物一覧.md`） |
| 完了報告 | Markdown | `ai-output/*/*/reports/完了報告.md` |

## §5 エラー処理

| 検査 | スクリプト | 検査キー |
|---|---|---|
| 共有部品不在 | scripts/plan-reverse.sh | 終了コード2 |
| 循環検知 | ../reverse-shared/scripts/plan-units.sh | 終了コード1 |
| untilの対象不在 | ../reverse-shared/scripts/plan-units.sh | 終了コード2 |
| run.json不在・読めない | scripts/build-completion-report.sh | 終了コード2 |
| 使い方の誤り（引数不足・--design-root無し） | scripts/build-completion-report.sh | 終了コード2 |
| 納品物一覧の行の文書が不在 | scripts/build-completion-report.sh | 終了コード1（`[FAIL] 納品物-不在`） |
| 業務名.jsonが無いか読めない | scripts/build-completion-report.sh | 終了コード3（`[FAIL] 業務名-読めない`） |
| 単位のフォルダ名が空か空白だけ | scripts/build-completion-report.sh | 終了コード3（`[FAIL] フォルダ名-未確定`） |

### 失敗したときの出力の扱い

終了コード1（納品物の不在）と終了コード3（設定の不備）のどちらで止まったときも、完了報告と納品物一覧は書かない。前回の実行が書いた両ファイルはそのまま残るため、終了コード0以外で終わったときの`reports/`と`docs/design/lists/`の中身は最新の入力を表さない。名指しされた不足を直して実行し直すまで、両ファイルの値を当てにしない。
