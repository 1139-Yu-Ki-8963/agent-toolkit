# 基本設計書を書く（reverse-writing-basic-design）の基本設計書

読み取り結果の取り出しと要件定義書の裏付けが終わった後、読み取り結果を業務の言葉へ写し、種別ごとの様式で基本設計書を書く。テスト設計書の出力が「出力する」のときは単体テスト設計書も対で書く（2026-09-05 オプション化）。

### 実行の口

Skill("reverse-writing-basic-design")として呼ぶ、または`scripts/`配下の各スクリプトを直接実行する。

### ひな形の様式

ひな形の冒頭案内は、本書にファイルパス・コード識別子等を含めない禁止事項を定める。api種別のひな形（API基本設計書.mdの§6.1・API単体テスト設計書.mdの§9.1）に限り、観測の出どころの表の内側を禁止事項の例外とする。この表には読み取った実装箇所のファイルと行だけを記録する。他の6種別のひな形はこの節を持たない（第1回改善指示書1-13）。

生成する文書の文体はである調である。記入規則の定義はSKILL.mdの「記入規則（文体）」節の1か所である。14件のひな形はそこを指す（第1回改善指示書1-16。議題は§6を参照）。

種別ごとの様式は、自分の種別以外の種別の名前を定型文の中に書かない。単位をまたぐ概念は「設計単位」の語で書く。同じ概念の言い方は1つの様式の中で1通りにする（第1回改善指示書1-20）。

他の単位の名前そのものを指す正当な参照（例: 画面固有の操作シナリオ仕様書という文書名への言及）は対象外とする。複数の単位から構成される機能の様式が構成要素の実例を挙げる記述も、定型文の複製ではないため対象外とする。

基本設計書・詳細設計書の見出し（h1）は表示名とする。識別子は基本設計書§1の表に併記し、見出しには書かない。

自己テストでの走査は、地の文全体ではなく複数の様式に複製された定型文（外部結合の行・本書が扱わない範囲の文・論理データモデルの§1）だけに絞る。「表」は表示・観測可能な値・状態・表示等の一般語と衝突するため、種別名としての用法（表の単位・表の種別という複合語）だけを判定対象とする（実測で「表示」の誤検出を確認済み）。

## §2 業務仕様

**この節の位置づけ: 現行実装**

### 手順

1. `check-entry.sh` で範囲の承認を確かめる
2. 種別ごとに `list-units-of.sh` で単位を列挙する
3. 単位ごとに読み取り結果・共通設計文書・要件定義書・対応表・調査と検出条件の定義書の用語候補を読み、種別に対応する様式を埋める。読み取り結果の各項目名をそのまま `### <項目名>` の見出しにする
4. テスト設計書の出力が「出力する」のときだけ、同じ単位の単体テスト設計書の様式を埋める
5. 実装用語の混入検査を種別ごとの検出パターンで grep し、検出0件まで書き直す
6. `check-basic-design.sh` を実行する
7. 終了コードが1なら不合格の理由を読み直す。差し戻し表『基本設計-不合格』の定めに従い、指摘された項目だけを直す。上限は設けない
8. 合格した単位を `units-status.sh` で記録する
9. 単位数・合格数・要確認事項の件数を報告する

### 完了判定の状態

完了判定は流れの設計「完了判定の状態」に従う。基本設計は6観点を合・否・要確認の3値で判定し、record-acceptance.shで記録する。

### 規約の完了状態と観点の対応

規約「設計書の書き方の決まり」の基本設計書の完了状態6項目と、`references/basic-phase-viewpoints.md`の6観点は1対1で対応する。

| 規約の完了状態 | 対応する観点のキー |
|---|---|
| 外部仕様が曖昧さなく確定している | 外部仕様の確定 |
| 業務ルールと例外系が矛盾なく確定している | 業務ルールと例外系の確定 |
| 非機能要件を満たす方式が確定している | 非機能の方式の確定 |
| データの整合性・トランザクション境界・排他の方針が確定している | データの整合性・トランザクション境界・排他の確定 |
| 詳細設計書を書き始める上での不明点が存在しない | 不明点の不在 |
| 単体テスト設計書が作成されている | 単体テスト設計書の実在 |

### 判定の規則

| 検査 | スクリプト | 検査キー |
|---|---|---|
| 文書の実在 | check-basic-design.sh | 文書-不在 |
| 読み取り結果の転記 | check-basic-design.sh | 読み取り結果-未転記 |
| 確認事項の登録 | check-basic-design.sh | 確認事項-未登録 |
| 節の実在 | check-basic-design.sh | 節-欠落 |
| 見出しの一致 | check-basic-design.sh | 見出し-表示名不一致 |
| 規約・一覧の実在 | check-basic-design.sh | 規約-不在・一覧-不在 |

## §3 方式設計

**この節の位置づけ: 現行実装**

機械とAIの分担は、機械検査（`検査`節の各スクリプト）が形式・実在・網羅を確かめ、AIが業務の言葉への翻訳・判断を担う二段構成である。

実行方式はシェルスクリプトと`grep`・正規表現による走査であり、対象コードの言語に依存しない。

### 判定の手順（機械検査 → 観点 → 記録）

完了時の判定は、機械検査・観点の判定・記録の3段で進む。パスはいずれも本機能のフォルダ（`docs/skills/reverse-writing-basic-design/`）からの相対である。`references/basic-phase-viewpoints.md`自身の置き場（`references/`）からの相対ではない。

| 段 | 対象 | 使う道具 |
|---|---|---|
| 機械検査 | 単位 | `scripts/check-basic-design.sh` |
| 機械検査 | 共通設計文書 | `../reverse-shared/scripts/check-basic-phase.sh --common` |
| 観点の判定 | 単位・共通設計文書共通 | `references/basic-phase-viewpoints.md`の6観点 |
| 記録 | 単位・共通設計文書共通 | `../reverse-shared/scripts/record-acceptance.sh` |

### 判定のループ

```
機械検査 --> AIが6観点を判定 --> 否があるか
                                   |はい
                                   v
                 名指しされた項目を読み取り結果とコードから書き直す
                                   |
                                   v
                              再度6観点を判定 ---> 否が無い --> 合格（要確認を含んでよい）
```

否が出た観点は差し戻し表『基本設計-不合格』の定めに従う。名指しされた項目だけを直し、上限は設けない。停止条件は否が無くなることだけであり、人には戻さない。要確認は確認事項のキーを添えて合格へ進める。

### check-basic-design.sh

**必要性**: 基本設計書は AI が読み取り結果を写して書くため文面は毎回変わる。完了条件（節の順序・位置づけの行・未記入の不在・読み取り結果の転記・確認事項の登録）は機械で確かめられる形を持つ。文面を問わず形と実在だけを検査することで、詳細設計へ進んでよいかを判定できる。

**代替案を採用しなかった理由**:
- 自己レビューだけにする: 節の欠落や転記漏れを毎回人手で数えることになる
- 対象の規約検査だけに任せる: 読み取り結果の転記や確認事項の登録までは規約検査が知らない

**保守責任者**: 人手（ユーザー）。読み取り結果の項目や様式を変えるときは、`docs/design/common/code-reading-items.json`・`templates/`・本スクリプトを同時に直す。

**廃棄条件**: 基本設計書の様式を構造化データから生成する仕組みに置き換えた時。

### 実装用語の混入検査

種別ごとの検出の型は`check-basic-design.sh`が1か所で持つ。検査キーは`実装用語-混入`である。検査の対象は本文であり、次の3か所は対象外とする。

1. 「観測の出どころ」を含む見出しの内側（見出しから次の見出しまで）
2. 「構成要素一覧」を含む見出しの内側（見出しから次の見出しまで。feature様式が識別子欄に相対パスを求めるため）
3. 文書冒頭の前付け（1行目が`---`で始まり閉じの`---`まで。閉じが無ければ前付けとみなさない）

除外に使う見出しの文字列（観測の出どころ・構成要素一覧）は、`templates/`配下の実見出しに実在することを自己テストで固定する（第1回改善指示書1-13・1-14・1-15）。

## §5 エラーと例外

**この節の位置づけ: 現行実装**

### 終了コード・差し戻しの一覧

| 検査 | スクリプト | 検査キー | 保留のとき |
|---|---|---|---|
| 文書の実在 | check-basic-design.sh | 文書-不在 | 対象外 |
| 読み取り結果の転記 | check-basic-design.sh | 読み取り結果-未転記 | 対象外 |
| 確認事項の登録 | check-basic-design.sh | 確認事項-未登録 | 対象外 |
| 節の実在 | check-basic-design.sh | 節-欠落 | 対象外 |
| 見出しの一致 | check-basic-design.sh | 見出し-表示名不一致 | 対象外 |
| 規約・一覧の実在 | check-basic-design.sh | 規約-不在・一覧-不在 | 対象外 |
| 実装用語の混入 | check-basic-design.sh | 実装用語-混入 | 対象外 |

### 完了条件

- 全単位に基本設計書がある（テスト設計書の出力が「出力する」のときは単体テスト設計書も）
- 必須節が順に埋まっており、実装位置（file:line）と未記入のプレースホルダーが無い
- 要確認事項一覧の各キーが確認事項の記録に登録されている
- 読み取り結果の各項目が基本設計書に転記されている
- 様式に他の種別の名前が残っていない。`setup-scaffolding-rules` が配る様式の写しも同じ定めに従い、自己テストで両方を走査する。他の種別の名前の検出は、種別名（画面・機能・API・テーブル・バッチ・帳票・外部連携）を`・`・`と`・`/`で2つ以上並べた列挙を定型文と見なして行う。原本の全様式と写しの全ファイルを走査し、自分の種別以外の名前を含む列挙があれば不合格とする。種別横断の文書（`プロジェクト共通/`配下）は複数の種別に触れる文書であり、列挙が正当であるため走査の対象から外す。種別ごとの様式では列挙を避け、「複数の設計単位」と書く。アンカー行の突合は補助として残す（第1回改善指示書1-20・再検証）
- 見出し（h1）が元データの表示名と一致する
- `tests/` の全件が通る
- 不合格の理由は規約が求める項目を名指しする。項目の欠けを要確認や保留で逃げない
