# テスト設計書を書く（reverse-writing-test-designs）の詳細設計書

## §1 構成要素

**この節の位置づけ: 現行実装**

| スクリプト | 役割 |
|---|---|
| check-test-designs.sh | 自己テストと機械検査を持つスクリプト |

## §2 処理の定義

**この節の位置づけ: 現行実装**

1. テスト設計書の出力を読む。「出力しない」なら何も作らず終える
2. 設計書の置き場を読む
3. 種別ごとに単位を列挙し、単位が1つ以上ある種別だけ`templates/種別内結合テスト設計書.md`を複製して埋める
4. `templates/種別横断結合テスト設計書.md`を複製して埋める。§1は要件定義書の受入条件から観点を起こし、§4に受入条件との対応を書く
5. `check-test-designs.sh`を実行する
6. 不合格の項目を手順3または4からやり直す。不合格の理由が名指しする項目を、基本設計書・詳細設計書・要件定義書の受入条件を再度読んで書き出す。理由に無い箇所は変えない。欠けが無くなるまで回数の上限なく戻る

## §3 ロジック

**この節の位置づけ: 現行実装**

### check-test-designs.sh

**必要性**: 種別内結合テスト設計書は単位が1つ以上ある種別すべてに要り、種別横断結合テスト設計書は観点とケースと受入条件の対応が要る。対象ごとに単位の有無・種別の数・受入条件の件数が違うため、機械で節の欠落・観点キーの不整合・未記入・file:lineを一括で確かめる必要がある。

**代替案を採用しなかった理由**:
- 手順書の注意書きだけにする: 種別の数が対象ごとに違うため、種別内結合テスト設計書の作り忘れが後工程まで見つからない
- 単体テスト設計書の検査を流用する: あちらは単位ごとの様式の専用であり、種別をまたぐ流れ・受入条件との対応という別の様式を検査する責務を持たない

**保守責任者**: 人手（ユーザー）。7種別の一覧・節の名前を変えるときは、`templates/`配下の2様式と本スクリプトと自己テストを同時に直す。

**廃棄条件**: テスト設計書の様式を構造化データに変えた時。

### 種別ごとの判定

種別のフォルダ名・種別名・種別内結合テスト設計書の置き場は`kind_folder`・`kind_label`の2関数が唯一の定義を持つ。単位一覧は`list-units-of.sh`を呼び、対応する一覧の元データが無い種別は単位0件として扱い、種別内結合テスト設計書を要求しない。
