## §2 処理の定義

**この節の位置づけ: 現行実装**

1. 領域の切り出しと除外（節0・節2・節3を埋める）。あわせて共有部品の参照の置き場の unit-kinds.json を設計書の置き場の docs/design/common/unit-kinds.json へ複製する。複製元が無いときは判定不能として止める
2. 領域ごとの調査（全領域が終わるまで繰り返す。節1・4・5・6・7・8・9・10と確認事項を埋める）
3. 要件定義書（現状のコードが実現している振る舞いを現状の要件として確定して書く）
4. 共通設計文書（調査と検出条件の定義書・要件定義書・共通方式の実装を読み、各文書の節を埋める）
5. 検査と出し直し（check-doc-heading-addendum.sh・check-survey-definition.sh・check-design-docs.shに掛け、不合格を直す）
6. 範囲の承認（承認用の要約を提示し、AskUserQuestionで承認を求める）

## §3 ロジック

**この節の位置づけ: 現行実装**

### check-survey-definition.sh

**必要性**: 調査と検出条件の定義書はAIが読んで書くため文面は毎回変わる。第二フェーズが機械で読む部分（節の構成・検出条件のJSONの形・例と場所の実在・候補数・到達範囲の網羅）は毎回同じ形でなければならない。形と実在を機械で確かめ、文面は問わない。

**代替案を採用しなかった理由**:
- 手順書の注意書きだけにする: 書き漏れが第二フェーズで初めて見つかる
- 調査と検出条件の定義書をスクリプトで生成する: 知らないリポジトリに既製の見つけ方を当てることになる

種別の定義（unit-kinds.json）の一致は、jq -S -c . で正規化した後の文字列の一致で判定する（キー順・空白・改行・BOM・Unicodeエスケープの差は無視する。数値の表記の差（1.0と1等）はjqの版に依存し、一致を保証しない）。共有部品の参照自体が実在しないときは前提-複製元不在として判定不能（終了コード2）で止める。

複製元・複製先のいずれかが種別の定義の形（unit-kinds.jsonの最上位は配列）でないときは、正規化後の文字列が両方とも空文字になり一致と誤判定する恐れがあるため、比較の前にjq -e 'type == "array"'で種別の定義の形かどうかを確かめる。構文が壊れている場合（jq自体が読めない）と、構文は正しいが最上位がnull・falseなど配列でない場合の両方を、この1つの判定でまとめて扱う。「JSONとして読めるか」だけを見ると、最上位がnullやfalseの構文として正しいJSONを誤って合格の候補として扱ってしまうため、判定は構文ではなく種別の定義の形そのもので行う。複製元が種別の定義の形でなければ前提-複製元不正として判定不能（終了コード2）、複製先が種別の定義の形でなければ種別-不正として不合格（終了コード1）にする。複製先は手で直せるため不合格、複製元（共有部品の参照）は本スクリプトの外側の問題のため判定不能、と区別する。種別-不一致（内容の相違）とはさらに別の理由として扱う。

jqは種別の定義の一致だけでなく、節4の検出条件（json 検出条件の囲み）の形式検査でも使う。jqが使えないと、いずれの検査も判定できない。このため前提-jq不在は--design-root指定時の種別の定義の比較だけの前提ではなく、全検査の前提として扱う。スクリプトの入口（引数解析・ファイル実在の確認の直後、検査本体を呼ぶ前）でjqの実在を確かめ、使えなければ判定不能（終了コード2）でスクリプト全体を止める。

**保守責任者**: 人手（ユーザー）。様式の節・検出条件の形を変えるときは、templates/調査と検出条件の定義書.md・本スクリプト・自己テストを同時に直す。

**廃棄条件**: 調査と検出条件の定義書の機械で読む部分を構造化データとして別に出す形に変えた時。

**設計判断（2026-09-07）**: 改善指示書1-33の反証の過程で、節4の検出条件の形式検査（検出条件-形式・検出条件-例不在・検出条件-識別子の正規表現なし）がjq不在のとき個別のhas_jqガードでスキップされ、不合格ケースをexit 0で通す（fail-open）既存の不具合を見つけた。--design-root指定時のunit-kinds.jsonの一致検査だけを前提-jq不在（判定不能）とし、節4の検査はjq不在時に無検査のまま合格にしていたためである。jq不在時のfail-openを判定不能に統一した。1-33の反証で見つかった既存の不具合であり、起票の範囲外だが同じスクリプトの前提の不整合のため同じ枝で直した。

**設計判断（2026-09-07・第4版への反証）**: 第4版に対する反証で、最上位がnull・falseの複製先（構文としては正しいJSON）を`jq -e .`が非0で返し、種別-不正として不合格にしていることが、設計の定義「構文が壊れている」と一致しない不一致が見つかった。構文としては正しいJSONだが種別の定義の形（配列）ではないため、そもそも比較の対象にならない。判定を「JSONとして読めるか」から「種別の定義の形（unit-kinds.jsonの最上位が配列）か」に改めた。`jq -e 'type == "array"'`は構文が壊れている場合（jq自体がパースできず非0を返す）と、構文は正しいが最上位が配列でない場合（true/falseの判定結果が偽になり非0を返す）の両方を1つの判定で扱える。複製元・複製先のどちらについても同じ判定を使う。

### check-design-docs.sh

**必要性**: 要件定義書と共通設計文書は規約「設計書の書き方の決まり」の内容を節に1対1で持つ。見出しの欠落・追記章・省略記載・位置づけの行の欠落は機械で見つかる。文書名に「基本設計書」を含まない共通設計文書は規約の既存の検査の対象外のため、この機能が同等の検査を持つ。

**代替案を採用しなかった理由**:
- 規約の既存の検査に任せる: 共通設計文書の見出しを知らない
- 自己レビューだけにする: 見出しの欠落を毎回人手で数えることになる

**保守責任者**: 人手（ユーザー）。見出しの構成を変えるときはreferences/design-doc-sections.jsonと様式を同時に直す。

**廃棄条件**: 規約の検査が共通設計文書の見出しを持つようになった時。
