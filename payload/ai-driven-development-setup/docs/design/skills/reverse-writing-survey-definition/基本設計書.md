# 調査と検出条件の定義書を書く（reverse-writing-survey-definition）の基本設計書

既存コードから設計書を起こす作業の最初に使う。対象リポジトリをAIが読み、第二フェーズが実行する検出条件を含む調査と検出条件の定義書と、要件定義書と共通設計文書を書き、範囲の承認を得るまでを担う。

## §1 外部仕様

**この節の位置づけ: 現行実装**

### 要件との対応

| 要件の柱 | 要件の項目 | この機能が満たす内容 |
|---|---|---|
| 柱1 調査を支える | 出力: 規模・構成と、画面・API・テーブルなど種別ごとの件数。支援範囲と、対象外とする理由。設計書の試作 | 調査と検出条件の定義書に領域・除外・単位の見つけ方・候補数・到達範囲を書く |
| 柱1 調査を支える | 完了条件: 対象外の全件に理由がある | 除外と到達範囲の各節で、対象外にした理由を書く |
| 柱2 基盤一式の作成を支える | 出力: 種別ごとの設計書と、業務の言葉の決まりを含む規約 | 要件定義書と共通設計文書6つ（業務仕様書・方式設計書・データ設計書・エラー設計書・共通外部仕様書・基盤設計書）を書く |
| 柱2 基盤一式の作成を支える | 出力: 確認事項と規約提案 | 確認事項の記録を出力の置き場に書く |
| 柱2 基盤一式の作成を支える | 完了条件: 未回答の確認事項が無い | 範囲の承認の手順で確認事項への回答を確かめる |

| 出力の置き場 | フォルダパス | 実行フォルダのrun.json（read-run.shで読む） |
| README・依存の定義・既存の設計文書 | ファイル | 対象リポジトリ |

### 出力

| 出力 | 形 | 置き場 |
|---|---|---|

| 承認用の要約・承認の記録・確認事項の記録 | Markdown | 出力の置き場の confirmations/ |

### 実行の口

Skill("reverse-writing-survey-definition")として呼ぶ、または`scripts/`配下の各スクリプトを直接実行する。

## §2 業務仕様

**この節の位置づけ: 現行実装**

### 手順

1. 領域の切り出しと除外（節0・節2・節3を埋める）
2. 領域ごとの調査（全領域が終わるまで繰り返す。節1・4・5・6・7・8・9・10と確認事項を埋める）
3. 要件定義書（現状のコードが実現している振る舞いを現状の要件として確定して書く）
4. 共通設計文書（調査と検出条件の定義書・要件定義書・共通方式の実装を読み、各文書の節を埋める）
5. 検査と出し直し（check-doc-heading-addendum.sh・check-survey-definition.sh・check-design-docs.shに掛け、不合格を直す）
6. 範囲の承認（承認用の要約を提示し、AskUserQuestionで承認を求める）

### 判定の規則

| 検査 | スクリプト | 検査キー |
|---|---|---|
| 調査と検出条件の定義書の形の検査 | scripts/check-survey-definition.sh | 節構成・検出条件の形式・例の実在・到達範囲の値 |
| 要件定義書・共通設計文書の形の検査 | scripts/check-design-docs.sh | 様式のまま・節の欠落・追記章・省略・位置づけ・文書名 |
| 設計書の書き方の決まりの検査 | ../reverse-shared/scripts/check-doc-heading-addendum.sh | 追記章と補足章を作らない・任意記載と省略記載をしない・要件定義書は合意した範囲を確定させる |

## §3 方式設計

**この節の位置づけ: 現行実装**

機械とAIの分担は、機械検査（`検査`節の各スクリプト）が形式・実在・網羅を確かめ、AIが業務の言葉への翻訳・判断を担う二段構成である。

実行方式はシェルスクリプトと`grep`・正規表現による走査であり、対象コードの言語に依存しない。

### check-survey-definition.sh

**必要性**: 調査と検出条件の定義書はAIが読んで書くため文面は毎回変わる。第二フェーズが機械で読む部分（節の構成・検出条件のJSONの形・例と場所の実在・候補数・到達範囲の網羅）は毎回同じ形でなければならない。形と実在を機械で確かめ、文面は問わない。

**代替案を採用しなかった理由**:
- 手順書の注意書きだけにする: 書き漏れが第二フェーズで初めて見つかる
- 調査と検出条件の定義書をスクリプトで生成する: 知らないリポジトリに既製の見つけ方を当てることになる

**保守責任者**: 人手（ユーザー）。様式の節・検出条件の形を変えるときは、templates/調査と検出条件の定義書.md・本スクリプト・自己テストを同時に直す。

**廃棄条件**: 調査と検出条件の定義書の機械で読む部分を構造化データとして別に出す形に変えた時。

### check-design-docs.sh

**必要性**: 要件定義書と共通設計文書は規約「設計書の書き方の決まり」の内容を節に1対1で持つ。見出しの欠落・追記章・省略記載・位置づけの行の欠落は機械で見つかる。文書名に「基本設計書」を含まない共通設計文書は規約の既存の検査の対象外のため、この機能が同等の検査を持つ。

**代替案を採用しなかった理由**:
- 規約の既存の検査に任せる: 共通設計文書の見出しを知らない
- 自己レビューだけにする: 見出しの欠落を毎回人手で数えることになる

**保守責任者**: 人手（ユーザー）。見出しの構成を変えるときはreferences/design-doc-sections.jsonと様式を同時に直す。

**廃棄条件**: 規約の検査が共通設計文書の見出しを持つようになった時。
