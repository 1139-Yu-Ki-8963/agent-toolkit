# 確認事項一覧を作る（reverse-building-confirmation-items）の基本設計書

確認事項の記録と、各設計書の「要確認事項一覧」節を読み、8列1枚の確認事項一覧を決定的なスクリプトで作る。

## §1 外部仕様

**この節の位置づけ: 現行実装**

### 要件との対応

| 要件の柱 | 要件の項目 | この機能が満たす内容 |
|---|---|---|
| 柱2 基盤一式の作成を支える | 完了条件: 未回答の確認事項が無い | 確認事項の記録と設計書の要確認事項一覧を突き合わせ、記録に登録されていないキーを検知して1枚にまとめる |
| 柱2 基盤一式の作成を支える | 入力: 確認事項への回答と、規約提案の採否 | 規約提案（工程2-10）が確認事項の記録へ足した提案の行を、確認事項一覧へ引き継ぐ |

### 入力

| 入力 | 形 | 出所 |
|---|---|---|
| 確認事項の記録 | Markdown（8列） | `confirmations/確認事項の記録.md` |
| 各設計書の要確認事項一覧 | Markdown（節） | `docs/design/` 配下の各設計書の「## 要確認事項一覧」節 |

### 出力

| 出力 | 形 | 置き場 |
|---|---|---|
| 確認事項一覧 | Markdown（8列＋記録に無いキー節） | `confirmations/確認事項一覧.md` |

### 実行の口

Skill("reverse-building-confirmation-items")として呼ぶ、または`scripts/`配下のスクリプトを直接実行する。

## §2 業務仕様

**この節の位置づけ: 現行実装**

### 手順

1. `../reverse-shared/scripts/design-root.sh <実行フォルダ>` で設計書の置き場を読む
2. `confirmations/確認事項の記録.md`（8列）を読む。無ければ0行として扱う
3. 設計書の置き場配下の全Markdownを走査し、「## 要確認事項一覧」節の表を集める。見出しは前方一致（末尾の空白・付記を許す）で判定し、表の列見出しは設計書ごとに異なる3通りがあるため列見出しの文字列（「キー」「確認事項」または「事項」「確認先」または「既定」）で値を読み分ける。セル内のエスケープ済みパイプ（`\|`）は列区切りと誤認せず元の文字へ戻す
4. 記録に無いキーを、埋め方の規則（後述）で8列に埋めて追加する
5. `scripts/build-confirmation-items.sh`を実行し、`confirmations/確認事項一覧.md`を書く
6. 不合格（既定・反映先の空欄、設計書のキーが出力に無い）なら、名指しされた項目を確認事項の記録または設計書へ書き足してから3へ戻る

### 要確認事項一覧の列見出しの3通り

| 列見出しの組 | 使う設計書の例 |
|---|---|
| キー・確認事項・確認先 | 要件定義書、業務仕様書等の共通設計文書 |
| キー・事項・既定 | 共通処理の詳細設計書 |
| キー・事項・既定・状態 | 基本設計書 |

### 埋め方の規則

| 欄 | 埋め方 |
|---|---|
| 単位 | 設計書の置き場から取る。`docs/design/common/`・`docs/design/requirements/`配下は「全体」。`docs/design/<種別>/<単位>/`配下は`<単位>`。同じキーが複数の単位に現れる場合は先頭の単位と「ほかN件」を書く |
| 種類 | 「確認先」列の値から当てる。非機能要件定義書は非機能、事業部門は業務ルール、運用部門は運用、設計担当は制約とする。「確認先」列が無い、または値が対応表に無い場合は制約とする |
| 事項 | 「確認事項」または「事項」列の値を写す。同じキーが複数ある場合は先頭を写す |
| 既定 | 「既定」列があればその値。無ければ「設計書の現行の記述のまま扱う」を置く |
| 反映先 | 「設計書のファイル名 単位」の形で書く |
| 回答 | 空欄のまま |
| 状態 | 「未回答」を置く |

### 判定の規則

| 検査 | スクリプト | 検査キー |
|---|---|---|
| 既定・反映先の空欄 | build-confirmation-items.sh | 行-空欄 |
| 設計書のキーの出力欠落 | build-confirmation-items.sh --verify | キー-出力欠落 |

## §3 方式設計

**この節の位置づけ: 現行実装**

機械とAIの分担は、本機能を全面的に機械（`build-confirmation-items.sh`）が担う。設計書の要確認事項一覧の列を読み分ける処理、確認事項の記録との突き合わせ、8列の表の組み立てまでを決定的に行う。AIは不合格時に名指しされた項目を確認事項の記録または設計書へ書き足す作業だけを担う。

macOS標準awkはUTF-8ロケールで多バイト文字列の`==`比較を誤るため`LC_ALL=C`で実行する。bash 3.2は空配列の`"${arr[@]}"`展開を`set -u`下でunbound variableとするため、配列の展開前に要素数を確認してから連結・反復する。表のセル分割は共通のawk関数（エスケープ済みパイプの退避と復元を含む）に一本化し、確認事項の記録・要確認事項一覧の抽出のすべてが同じ規則で列を読む。

### build-confirmation-items.sh

**必要性**: 確認事項の記録と、7種別・共通設計文書に散らばる「要確認事項一覧」節を、開発チームが読める1枚の8列表へ統合する必要がある。列見出しが設計書によって3通りに分かれるため、列名を動的に読み分ける必要がある。設計書のキーが記録に登録されないまま進む（工程2-5・2-8の完了条件の破れ）事故を機械で検知する必要もある。

**代替案を採用しなかった理由**:
- 確認事項の記録をそのまま確認事項一覧として使う: 設計書側で新たに見つかったキー（記録への登録漏れ）を拾えない
- AIが手で1枚にまとめる: 219件規模のキーを人手で突き合わせると漏れが生じる（実測で94件の登録漏れが見つかった実績がある）

**保守責任者**: 人手（ユーザー）。要確認事項一覧の列見出しの組み合わせを増やすときは、本スクリプトと自己テストを同時に直す。

**廃棄条件**: 確認事項の記録・要確認事項一覧の様式を構造化データに変えた時。
