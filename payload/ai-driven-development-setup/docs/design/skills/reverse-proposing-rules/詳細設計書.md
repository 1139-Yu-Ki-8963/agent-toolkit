# 規約提案を出す（reverse-proposing-rules）の詳細設計書

## §1 構成要素

**この節の位置づけ: 現行実装**

| スクリプト | 役割 |
|---|---|
| check-rule-proposals.sh | 規約提案.mdの出典・提案先・観測なしの理由を検査する。自己テストを持つ |

## §2 処理の定義

**この節の位置づけ: 現行実装**

1. 設計書の置き場を読む
2. 設計文書とコードから規約提案の候補を集める（AIが行う）
3. `templates/規約提案.md`を`confirmations/規約提案.md`へ複製し、「## 観測」「## 判断」「## 観測なし」を埋める（AIが行う）
4. `check-rule-proposals.sh <実行フォルダ>`を実行する
   1. `confirmations/規約提案.md`を読む。無ければ`[FAIL] 規約提案-不在`で終了コード2
   2. 「## 観測」「## 判断」「## 観測なし」の3節の見出しが揃っているかを確かめる。1つでも無ければ（空ファイルを含む）`[FAIL] 節-欠落`で終了コード1
   3. `../reverse-shared/references/rule-taxonomy.json`から`parent`/`key`の組の一覧を作る。読めなければ`[FAIL] 規約定義-不在`で終了コード2
   4. 「## 判断」の各行について、キーに対応する「## 観測」の行があり出典の文書が空でないかを確かめる。無ければ`[FAIL] 出典-不在`
   5. 「## 判断」の各行の「提案先の規約」が空でないか、`parent`/`key`の一覧に実在するかを確かめる。満たさなければ`[FAIL] 提案先-不在`
   6. 「## 観測なし」の各行の理由が空でないかを確かめる。空なら`[FAIL] 観測なし-理由欠落`
   7. 不合格が1件も無ければ終了コード0
5. 不合格の行を名指しされた理由に沿って直し、手順3へ戻る

## §3 ロジック

**この節の位置づけ: 現行実装**

### check-rule-proposals.sh

**必要性**: 基本設計書§3を参照。

**代替案を採用しなかった理由**: 基本設計書§3を参照。

**保守責任者**: 人手（ユーザー）。様式の節構成を変えるときは、本スクリプトと`templates/規約提案.md`と自己テストを同時に直す。

**廃棄条件**: 基本設計書§3を参照。

### 節の抽出

「## 観測」「## 判断」「## 観測なし」の各節は見出し文字列の完全一致で区切る。見出し直後の最初の表の行を列見出しとして読み飛ばし、以降の行をデータ行として扱う。区切り行（`|---|`等）とプレースホルダー行（`<...>`を含む1列目）は除く。

### 提案先の実在確認

`../reverse-shared/references/rule-taxonomy.json`（写し）を読む。`parents[].key`と`parents[].children[].key`の組を`<parent>/<key>`の形で全件並べる。「## 判断」の「提案先の規約」列の値と完全一致するかを見る。原本ではなく写しを参照するのは、reverse単位がsetup単位へ直接依存しない設計（skill-naming規約の単位分離）を保つためである。
