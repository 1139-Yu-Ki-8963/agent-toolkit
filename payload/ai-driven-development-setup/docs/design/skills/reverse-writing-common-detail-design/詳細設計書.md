# 共通処理の詳細設計書を書く（reverse-writing-common-detail-design）の詳細設計書

## §2 処理の定義

**この節の位置づけ: 現行実装**

1. `check-acceptance-record.sh --common` の終了コードが0であることを確かめる
2. `templates/共通処理の詳細設計書.md` を複製する
3. 調査と検出条件の定義書の節7のうち、実装の場所が「なし」でない方式だけを残す
4. 各節を、調査と検出条件の定義書の節7が指す実装を読んで6つの小節（クラス設計・メソッド設計・ロジック設計・戻り値と引数・エラー処理・データ定義）で埋め、位置づけの行を実測に応じて改める
5. 本文にfile:lineを書かない。決められない節は要確認事項一覧へ書く
6. `check-common-detail-design.sh` を実行する
7. 不合格の項目を手順4からやり直す。同じ不合格が2回続いたら方法を変える

## §3 ロジック

**この節の位置づけ: 現行実装**

### check-common-detail-design.sh

**必要性**: 共通処理の詳細設計書は調査と検出条件の定義書の節7に対応する節をすべて持たなければならない。方式の数と場所は対象ごとに違うため、機械で調査と検出条件の定義書を読み、節の欠落・位置づけの欠落・小節の欠落・未記入・file:lineを一括で確かめる必要がある。判定方法の入口（合格の記録の有無）は`reverse-checking-basic-phase`の`check-acceptance-record.sh`に委ねる。

**代替案を採用しなかった理由**:
- 手順書の注意書きだけにする: 方式の数が対象ごとに違うため、節の書き漏れが後工程で初めて見つかる
- 合格の記録の判定を本スクリプトが再実装する: 判定方法が2箇所に分散し、記録の形を変えるたびに2箇所を直すことになる

**保守責任者**: 人手（ユーザー）。10方式の一覧・6小節の名前を変えるときは、`templates/共通処理の詳細設計書.md`と本スクリプトと自己テストを同時に直す。

**廃棄条件**: 共通処理の詳細設計書の様式を構造化データに変えた時。
