# 共通処理の詳細設計書を書く（reverse-writing-common-detail-design）の基本設計書

道標の共通方式の場所とその実装を読み、共通処理の詳細設計書を方式ごとに書き、位置づけ・未記入・file:lineを機械検査する。

## §1 外部仕様

**この節の位置づけ: 現行実装**

### 要件との対応

| 要件の柱 | 要件の項目 | この機能が満たす内容 |
|---|---|---|
| 柱2 基盤一式の作成を支える | 出力: 種別ごとの設計書と、業務の言葉の決まりを含む規約 | 道標が指す共通方式ごとに詳細設計書の節を書く |
| 柱2 基盤一式の作成を支える | 完了条件: 設計書だけからコードを再生成し、元のコードとの照合が通る | クラス設計・メソッド設計・ロジック設計・戻り値と引数・エラー処理・データ定義を実測から埋める |
| 柱2 基盤一式の作成を支える | 完了条件: 未回答の確認事項が無い | 仕様か現行実装かを決められない節を要確認事項一覧へ書く |

### 入力

| 入力 | 形 | 出所 |
|---|---|---|
| 道標 | Markdown | `docs/design/common/道標.md` |
| 共通設計文書の合格の記録 | JSON | `ai-work/records/basic-design-acceptance/common-*.json` |

### 出力

| 出力 | 形 | 置き場 |
|---|---|---|
| 共通処理の詳細設計書 | Markdown | `docs/design/common/共通処理の詳細設計書.md` |

### 実行の口

Skill("reverse-writing-common-detail-design")として呼ぶ、または`scripts/`配下の各スクリプトを直接実行する。

## §2 業務仕様

**この節の位置づけ: 現行実装**

### 手順

1. `check-acceptance-record.sh --common` の終了コードが0であることを確かめる
2. `templates/共通処理の詳細設計書.md` を複製する
3. 道標の節7のうち、実装の場所が「なし」でない方式だけを残す
4. 各節を、道標の節7が指す実装を読んで6つの小節（クラス設計・メソッド設計・ロジック設計・戻り値と引数・エラー処理・データ定義）で埋め、位置づけの行を実測に応じて改める
5. 本文にfile:lineを書かない。決められない節は要確認事項一覧へ書く
6. `check-common-detail-design.sh` を実行する
7. 不合格の項目を手順4からやり直す。同じ不合格が2回続いたら方法を変える

### 判定の規則

| 検査 | スクリプト | 検査キー |
|---|---|---|
| 合格記録の入口 | check-common-detail-design.sh | 合格記録-不在 |
| 節の実在 | check-common-detail-design.sh | 節-欠落 |
| 位置づけの実在 | check-common-detail-design.sh | 位置づけ-欠落 |
| 小節の実在 | check-common-detail-design.sh | 小節-欠落 |
| 未記入の不在 | check-common-detail-design.sh | 未記入-残存 |
| file:lineの不在 | check-common-detail-design.sh | 位置-禁止 |
| 追記見出しの不在 | check-common-detail-design.sh | 追記章-禁止 |

## §3 方式設計

**この節の位置づけ: 現行実装**

機械とAIの分担は、機械検査（`検査`節の各スクリプト）が形式・実在・網羅を確かめ、AIが業務の言葉への翻訳・判断を担う二段構成である。

実行方式はシェルスクリプトと`grep`・正規表現による走査であり、対象コードの言語に依存しない。

### check-common-detail-design.sh

**必要性**: 共通処理の詳細設計書は道標の節7に対応する節をすべて持たなければならない。方式の数と場所は対象ごとに違うため、機械で道標を読み、節の欠落・位置づけの欠落・小節の欠落・未記入・file:lineを一括で確かめる必要がある。判定方法の入口（合格の記録の有無）は`reverse-checking-basic-phase`の`check-acceptance-record.sh`に委ねる。

**代替案を採用しなかった理由**:
- 手順書の注意書きだけにする: 方式の数が対象ごとに違うため、節の書き漏れが後工程で初めて見つかる
- 合格の記録の判定を本スクリプトが再実装する: 判定方法が2箇所に分散し、記録の形を変えるたびに2箇所を直すことになる

**保守責任者**: 人手（ユーザー）。10方式の一覧・6小節の名前を変えるときは、`templates/共通処理の詳細設計書.md`と本スクリプトと自己テストを同時に直す。

**廃棄条件**: 共通処理の詳細設計書の様式を構造化データに変えた時。
