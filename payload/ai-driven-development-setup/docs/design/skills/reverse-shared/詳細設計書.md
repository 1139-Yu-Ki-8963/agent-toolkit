## §2 処理の定義

**この節の位置づけ: 現行実装**

共有部品のため単一の手順は持たない。各スクリプトの使い方は先頭コメントに置く。

- read-run.sh: `read-run.sh <実行フォルダ> <キー>` で実行フォルダのrun.jsonから値を1行読む
- check-entry.sh: `check-entry.sh <実行フォルダ> <対象リポジトリのルート>` で対象範囲の承認.mdの可否と調査と検出条件の定義書の同一性を確かめる
- unit-dir-name.sh: `unit-dir-name.sh <識別子>` で識別子をフォルダ名に使える形へ置換する
- design-doc-name.sh: `design-doc-name.sh <種別> <basic|test>` で種別ごとの基本設計書・単体テスト設計書のファイル名（実名）を返す
- units-status.sh: `units-status.sh <実行フォルダ> set|get|list <残りの引数>` で工程の状態を読み書きする
- list-units-of.sh: `list-units-of.sh <対象リポジトリのルート> <種別> [--lists <場所>]` で一覧の元データをタブ区切りで返す
- check-doc-heading-addendum.sh: PreToolUse(Write|Edit)で設計書の書き方の決まりを検査する
- check-unit-test-design-doc-sections.sh: PreToolUse(Write)で単体テスト設計書の決まりを検査する

## §3 ロジック

**この節の位置づけ: 現行実装**

### list-units.sh（一覧を作る機能が使う検出条件の実行）に対する共有部品としての位置づけ

reverse-sharedは検出条件の実行そのものは持たず、実行後の元データの読み取り（list-units-of.sh）とフォルダ名の作成（unit-dir-name.sh）を共有する。検出条件の実行はreverse-listing-unitsのlist-units.shが担い、責務を分離している。

### check-doc-heading-addendum.sh / check-unit-test-design-doc-sections.sh の写し方式

**必要性**: 設計書の書き方の決まり・単体テスト設計書の決まりはsetup単位の規約が持つ原本であり、reverse単位のPreToolUse(Write|Edit)から同じ検査を使うために写しを置く。原本を直接requireする依存を持たず、テスト（test-self-tests.sh）で写しと原本の一致（改行・通知行を除く）を確かめることで、ずれを検出可能にする。

**代替案を採用しなかった理由**:
- setup側の原本を直接読み込む: reverse単位とsetup単位の間に実行時依存が生まれ、「柱ごとに取り出して動く」という制約に反する
- 写しを持たずreverse独自に再実装する: 同じ検査を2箇所で保守することになり、ずれが機械で検出できない

**保守責任者**: 人手（ユーザー）。原本（setup-scaffolding-rulesのtemplates配下）を変えるときは写しも同時に直し、test-self-tests.shで一致を確かめる。

**廃棄条件**: 写し方式を別の共有機構（symlink等）に置き換えた時。

### design-doc-name.sh の共有部品化

**必要性**: 種別ごとの基本設計書・単体テスト設計書のファイル名（旧様式の実名）は、check-basic-design.sh（様式の検査）とrecord-acceptance.sh（合格の記録）の双方が使う。かつては両スクリプトがそれぞれ独自にこの名前を決め打ちしており、二重定義がずれて合格の記録の文書名が種別ごとの実名と揃わず、記録の同一性の値が空になる不具合（第1回改善指示書1-12）を起こした。名前の決め方を1箇所へ集め、unit-dir-name.shと同じ形の共有部品として持つ必要がある。

**代替案を採用しなかった理由**:
- 現状維持（各スクリプトが個別に決め打ちする）: 名前を変えるときに一方だけ直す事故が再発する。実際に起きた不具合の直接原因である
- check-basic-design.shの関数をrecord-acceptance.shが直接requireする: reverse-writing-basic-designとreverse-sharedの間に実行時依存が生まれ、「柱ごとに取り出して動く」という制約に反する

**保守責任者**: 人手（ユーザー）。文書名を変えるときは、本スクリプトと自己テストと、本スクリプトを使う各機能（check-basic-design.sh・record-acceptance.sh）を同時に確かめる。

**廃棄条件**: 種別ごとの文書名の決め方を構造化データから生成する仕組みに置き換えた時。

## §4 入出力の値

**この節の位置づけ: 現行実装**

| 入力 | 形 | 出所 |
|---|---|---|
| 実行フォルダのrun.json | JSON | 統括の実行の開始スクリプト |
| 対象範囲の承認.md・調査と検出条件の定義書.md | Markdown | reverse-writing-survey-definitionの出力 |
| 一覧の元データ（<種別>.json） | JSON | reverse-listing-unitsの出力 |
| 書き込み対象の文書本文 | Markdown | Write/Editのtool_input |

| 出力 | 形 | 置き場 |
|---|---|---|
| 実行フォルダの値（対象リポジトリ等） | 標準出力（1行） | 呼び出し元へ返す |
| 範囲の承認の判定 | 終了コード | 呼び出し元へ返す |
| 一覧の元データの1行1件（タブ区切り） | 標準出力 | 呼び出し元へ返す |
| 単位のフォルダ名 | 標準出力（1行） | 呼び出し元へ返す |
| 単位ごとの工程の状態 | JSON | <実行フォルダ>/logs/units-status.json |
| linterの許可・拒否・通知・対象外の判定 | 終了コード・メッセージ | 呼び出し元（PreToolUse）へ返す |

## §5 エラー処理

**この節の位置づけ: 現行実装**

| 検査 | スクリプト | 検査キー |
|---|---|---|
| 範囲の承認の可否と同一性 | scripts/check-entry.sh | 合格・不合格-否・不合格-同一性不一致・判定不能-承認ファイル不在・判定不能-調査と検出条件の定義書ファイル不在 |
| 実行フォルダの値の読み取り | scripts/read-run.sh | 対象リポジトリ・対象プロジェクト名・出力の置き場・実行の識別子・対象のコミット・キー不在・run.json不在・引数不足 |
| 単位のフォルダ名の作成 | scripts/unit-dir-name.sh | スラッシュ等の置換・空白置換・先頭アンダースコア除去・引数無し |
| 種別ごとの文書名の作成 | scripts/design-doc-name.sh | 種別×basic/testの14通りの実名・不正な種別/区分・引数不足 |
| 工程の状態の読み書き | scripts/units-status.sh | 未設定は未・set後にget一致・別工程は未のまま・list・不正な工程・引数不足 |
| 一覧の元データの読み取り | scripts/list-units-of.sh | タブ区切り出力・一覧不在・不正なJSON・--listsオプション |
| 追記章と補足章を作らない | scripts/check-doc-heading-addendum.sh | 追記・補足・その他で始まる見出しの検出 |
| 任意記載と省略記載をしない | scripts/check-doc-heading-addendum.sh | 列挙を打ち切る省略記号の検出 |
| 要件定義書は合意した範囲を確定させる | scripts/check-doc-heading-addendum.sh | 対象範囲・優先度・受入条件の3見出しの実在 |
| 基本設計書は詳細設計を書ける状態を作る | scripts/check-doc-heading-addendum.sh | 様式の見出しと単体テスト設計書の同居フォルダの実在 |
| 記載項目を省かない | scripts/check-unit-test-design-doc-sections.sh | 12節または13節の名前・順序・件数の一致 |
| 単体テスト設計書は基本設計フェーズで作る | scripts/check-unit-test-design-doc-sections.sh | 基本設計フォルダの宣言と単体テスト設計書の実在 |
| 規約が求めるテストを観点へ取り込む | scripts/check-unit-test-design-doc-sections.sh | 検査列に「テスト:」を含む規則名の本文への出現 |
| テスト設計書の節の役割 | scripts/check-unit-test-design-doc-sections.sh | §1・§2・§5・§6のキー集合の整合 |
