# 機能設計書・詳細設計書・単体テスト設計書の決まり

## 概要

`docs/skills/` のうち reverse の単位（`reverse-*`・`reverse-shared`）の各機能を対象にする。
各機能に、納品物と同じ章構成の3文書（基本設計書・詳細設計書・単体テスト設計書）を
`docs/design/skills/<機能名>/` に置くことを定める。SKILL.mdは機能の宣言と手順を持つ。
要件との対応・方式設計・テスト観点は3文書として残す。setup の単位はこの規約の対象外。

## 規則

| 規則 | 内容 | 検査 |
|---|---|---|
| reverse単位の全機能に3文書がある | `docs/skills/reverse-*`（SKILL.mdを持つフォルダと`-shared`フォルダ）の全件について、`docs/design/skills/<機能名>/基本設計書.md`・`詳細設計書.md`・`単体テスト設計書.md`がある | 静的解析: `docs/skills/`のreverse単位の一覧と`docs/design/skills/`の一覧を突き合わせ、欠落を走査する |
| 基本設計書は6節を持つ | 節は `## §1 外部仕様`／`## §2 業務仕様`／`## §3 方式設計`／`## §4 データ仕様`／`## §5 エラーと例外`／`## §6 関連資料`の6つで固定する。各§の直後に「この節の位置づけ: 現行実装」の行を置く | 静的解析: 見出しの実在を走査する |
| §1外部仕様は要件との対応を表で持つ | `## §1 外部仕様`は要件との対応の表（要件の柱 \| 要件の項目 \| この機能が満たす内容）を持つ | 静的解析: 表の実在と見出し行を走査する |
| 詳細設計書は6節を持つ | 節は `## §1 構成要素`／`## §2 処理の定義`／`## §3 ロジック`／`## §4 入出力の値`／`## §5 エラー処理`／`## §6 関連資料`の6つで固定する | 静的解析: 見出しの実在を走査する |
| 単体テスト設計書は旧の様式（12節）に合わせる | `docs/skills/reverse-shared/scripts/check-unit-test-design-doc-sections.sh --check-file`で節の名前・順序・件数、§1・§2・§5・§6の観点キーの整合を検査する | 静的解析: 同スクリプトの終了コードを走査する |
| §2は現場コードの期待値のケースを持つ | 「§2 テストケース一覧」の列は キー・番号・機能・ケースの名前・対応する観点のキー・区分・前提・操作・期待結果 の9列で、各行の前提・操作・期待結果の3列が空でない | 静的解析: 表の列見出しと各行の該当3列の空欄を走査する |
| §2の観点キーは§1にある | 「§2 テストケース一覧」の各行の「対応する観点のキー」列の値が、「§1 テスト観点」の観点キー列のいずれかと一致する | 静的解析: §1の観点キーの一覧と§2の値を突き合わせる |
| §2に検査スクリプトの分岐を並べない | 「§2 テストケース一覧」の行が、検査スクリプト自身の内部分岐（引数解析・`--self-test`の分岐等）を並べたものでない | 判定不能: 目視で確かめる |
| 自己テストの件数が実物と一致する | 「自己テスト」の表（§7の末尾に置いてもよい）の各スクリプトの件数列が、そのスクリプトへ`--self-test`を渡した実行結果の件数（出力の「実行 N 件」のN。無ければPASS行の数）と一致する | テスト: 各スクリプトへ`--self-test`を渡して実行し件数を比較する（`--self-test`が無い、または実行できないスクリプトは判定不能として警告に留め、不合格にはしない） |
| 対応表がreverse単位の全機能を逆引きに持つ | `docs/design/requirements/要件と機能の対応表.md`の「機能から要件への逆引き」表が、`docs/skills/reverse-*`の全機能を1行ずつ持つ | 静的解析: 逆引き表の機能列と`docs/skills/`のreverse単位の一覧を突き合わせる |
| 全体の制約に満たす機能がある | 対応表の柱1・柱2・支援ツール全体の制約の各行のうち、状態が「対応済み」の行について、「満たす機能」列が空でない。「未対応（公開3以降）」「対象外」の行は空でもよい | 静的解析: 該当する行の「満たす機能」列が「（なし）」でないかを走査する |

## このプロジェクトの規則

| 規則 | 内容 | 検査 |
|---|---|---|
| 観測なし | この規約はこのリポジトリ自身の機能の設計文書を定めるもので、対象リポジトリの観測から起こす規則は無い | 観測なし |

## 違反時の手順

文書が欠落している場合、`docs/design/skills/<機能名>/`に基本設計書.md・詳細設計書.md・単体テスト設計書.mdを、規則が定める節と表の形で作る。単体テスト設計書は`check-unit-test-design-doc-sections.sh --check-file`が許可を返すまで直す。§2の行に前提・操作・期待結果が無い場合、現場コードを走らせたときの値で埋める。§2の観点キーが§1に無い場合、§1へ観点を足すか§2の値を直す。自己テストの件数が実物とずれる場合、「自己テスト」の表の件数列を`--self-test`の実測に合わせて直す。対応表に機能が無い場合、`docs/design/requirements/要件と機能の対応表.md`の逆引き表へ追記する。

## 設計判断

### check-skill-design-docs.sh

**必要性**: `docs/skills/`のreverse単位の機能は増え続ける。機能ごとに3文書の実在・節構成・対応表との整合・テストケース数の実物一致という複数段の判定を要する。人が目視で確かめるのは非現実的であり、CIから繰り返し呼ばれる検査として固定する必要がある。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 機能を追加するたびに節見出し・表のヘッダ・ケース数の一致を手で確認すると、確認の省略・見落としを繰り返す
- 既存 `validate-skill-definitions.sh` への直接実装: あちらは SKILL.md 自体の宣言（鍵・requires・tests の実在）を検査する。設計文書という別の成果物の形を検査する判定を混ぜると責務が肥大化するため、規約自身のフォルダに置く checker として分離した
- setupの単位も対象に含める: setupは対象システムの環境構築を担い、reverseとは要件・完了条件の性質が異なる。1つの検査に混ぜると、setup側の変更でreverse側の検査が誤って揺れる
- 既存 Makefile ターゲット拡張・package.json scripts 追加: このリポジトリはどちらも持たず、新規導入は本検査専用の依存を増やすだけになる

**保守責任者**: 人手（ユーザー）。節の構成や単体テスト設計書の表の形を変更する場合は、本ファイルの規則の表と`check-skill-design-docs.sh`を同時に更新する。setupの単位を対象に含める場合は、規約名・対象範囲の記述も同時に見直す。

**廃棄条件**: `docs/skills/`によるreverse単位の機能定義の運用を廃止した時、または3文書の検査を構造化データから機械的に導出できるようになった時。
