## いつ使うか

既存コードから設計書を起こす作業の最初に使う。対象リポジトリを AI が読み、第二フェーズが実行する検出条件を含む道標と、要件定義書と共通設計文書を書き、範囲の承認を得るまでを担う。

## いつ使わないか

道標が承認済みのとき（第二フェーズの機能を使う）。個々の単位の設計書を書くとき。

## 前提

- 対象リポジトリがコミット済みであること。読むコミットを固定し、稼働中の変更は対象外にする
- 実行フォルダ（統括の実行の開始スクリプトが作る）を受け取る。対象リポジトリのルートは `bash ../reverse-shared/scripts/read-run.sh <実行フォルダ> 対象リポジトリ` で読む。設計書の置き場（道標・要件定義書・共通設計文書を書く先）は `bash ../reverse-shared/scripts/design-root.sh <実行フォルダ>` で読む。この置き場は、先方リポジトリへ展開する使い方と作業場所だけに置く使い方の両方に対応する。確認事項・承認等の置き場（先方リポジトリに含めない出力の置き場のルート）は `bash ../reverse-shared/scripts/read-run.sh <実行フォルダ> 出力の置き場` で読む
- 出力先は次のとおりである
  - 道標: 設計書の置き場の `docs/design/common/道標.md`
  - 要件定義書: 設計書の置き場の `docs/design/requirements/要件定義書.md`
  - 共通設計文書 6 つ: 設計書の置き場の `docs/design/common/`
  - 承認用の要約・承認の記録・確認事項の記録: 出力の置き場の `confirmations/`
- コードの調査と分析は AI が読んで行う。既製の検索パターンを対象に当てない。スクリプトを使うのは手順 5 の検査だけである
- 確認事項は道標に持たない。各手順で見つけた確認事項は、出力の置き場の `confirmations/確認事項の記録.md` に 1 行 1 事項（キー・単位・種類・事項・既定・反映先・回答・状態の 8 列）で追記する
- 種別の定義（画面・接続窓口・表・バッチ・外部連携・機能の 6 種別。帳票は各手順の様式に従う）
  - 画面: 経路（ルーティング）に対応するページを 1 つと数える。再利用される部品は単位にせず、道標の節 1「UI 共通部品」と共通外部仕様書で扱う。1 ファイルが複数の経路から共有される場合は経路ごとに数える。専用ファイルを持たない経路も数える
  - 接続窓口: 経路と HTTP メソッドの組を 1 つと数える。データベースの関数・トリガーは接続窓口にせず、表の事実（制約・関係）に属させる
  - 表: 現在存在する表を 1 つと数える（削除された表は数えない）。定義元はマイグレーションかスキーマの写しのどちらか 1 つに決め、アプリ側のモデル定義は属するファイルとする
  - バッチ: 業務のデータを処理する定期処理・取り込み処理を 1 つと数える。CI・lint・ビルド・品質確認の道具は含めず、除外の種類「開発の道具」にする
  - 外部連携: 他システムとの通信の実装（呼び出し 1 か所）を 1 つと数える。取り込むデータファイルは外部連携にせず、節 5「動的な定義」か資産として扱う
  - 機能: 業務の単位。道標の 4.8「機能のまとめ方」に従う。まとめ方が無ければ、経路と接続窓口の束を業務の言葉で括る
- 読む対象の既定: 既存の設計文書は手順 3 の参考資料とし、単位の検出はしない。補助のポータルや管理画面は対象外（補助の資産）とする
- 第一フェーズは AI が読む工程であり、言語・フレームワーク・記法を理由に対象外にしない。読めない原因になり得るのは文字コードだけで、それは変換して読む。到達範囲の「対象外」は、その種別が対象に存在しない場合にだけ使う。検出条件や取り出しの規則を実行できる形で書けない種別は「AI の読み取り」にする

## 手順

### 手順 1: 領域の切り出しと除外

1. `templates/道標.md` を `docs/design/common/道標.md` へ複製し、節 0「対象と時点」を埋める。コミットは `git rev-parse --short HEAD`。文字コードは主要なソースファイルを数本読んで判定する。構成の形は単一・モノレポ・複数サイトのいずれか
2. フォルダ構成とビルドの定義と README を読む。依存の定義（package.json・pom.xml・Gemfile・requirements.txt・go.mod・composer.json・Makefile など）も読む
3. 節 2「領域」に、読む領域を切り出す。1 領域は一度に読める量（目安はファイル 200 本まで）に収め、収まらない領域はフォルダで再分割する。領域は対象の全フォルダを覆い、除外と重ならない。ファイル数は `find <フォルダ> -type f -not -path '*/.git/*' | wc -l` のように一括で数える。完了条件: 全フォルダと直下のファイルが領域か除外に属する
4. 節 3「除外」に、生成コード・廃止コード・ベンダー・試験用・開発の道具・資産（画像・データ）・既存文書・その他の除外フォルダを、種類と理由付きで書く。迷うフォルダは確認事項に登録する

### 手順 2: 領域ごとの調査（全領域が終わるまで繰り返す）

段階読みの実際の形: 領域ごとに別の担当者（別の文脈）で読み、断片（節ごとの追記分。節 1・4・5・6・7・8・9・10 と確認事項）を書き、統括が統合する。担当者には検出条件の制約（節 4 冒頭の案内）を渡す。

1. 節 2 の順に 1 領域を読む。コード・設定ファイル・テストコード・画面の文言・コメントを読む。節 0 の文字コードが UTF-8 でないファイルは `iconv -f <文字コード> -t UTF-8 <ファイル>` で変換して読む
2. 節 1「調査」の項目を、その領域で分かったことで埋める。各項目に場所（パス）を書く。既に埋まっている項目は領域の分を足す
3. 節 4「単位の見つけ方」を種別ごとに書く。表の項目は、単位の定義・走査の範囲・目印・分割の規則・識別子の付け方・名前の取り方・説明の取り方・属するファイル・分類軸の取り方・動的な定義の扱いの 10 個である。これらを埋め、`json 検出条件` の囲みを様式の形のとおりに書く。検出条件は、この領域を読んで見つけた目印を、第二フェーズの実行器が実行できる形で書く。書く要素は、含むフォルダ・除くフォルダ・拡張子・ファイル名と内容の正規表現・分割・識別子・名前・例である。例は実在するファイルのパスを書く。言語や世代が混在して見つけ方が違う種別は囲みを足す。検出条件で表せない種別は表に `AI の読み取り` と書き、囲みを書かない。対象に存在しない種別は、見つけ方の表の各欄と事実の取り出しの表の各欄に `対象外` と書き、囲みを書かない。到達範囲の節にも `対象外` と書き、理由を添える
4. 節 4 の種別ごとに「取り出しの規則」の表を埋める。事実の各項目を、この対象のどの構文・どの記述から取るかを書く。事実の項目は種別ごとに次のとおりである
   - 画面: 入力項目・表示項目・操作・遷移・呼ぶ接続窓口
   - 接続窓口: 経路・入力・出力・検証・呼ぶ処理・触る表
   - 表: 列・型・制約・関係
   - 列と型など対応を保つ必要がある項目は、1つの捕捉で1行を丸ごと取り、値に並びを残す
   - バッチ: 起動条件・入力・出力・処理の流れ
   - 帳票: 出力条件・項目・レイアウトの元
   - 外部連携: 相手先・形式・項目・応答・再試行
   - 機能: 含む単位
5. 節 5「動的な定義」に、設定ファイル・データベースの表・外部の定義ファイルで動的に決まる単位の定義の場所と見つけ方を書く。データベースの中身を読めない場合は、定義の写しを先方に求める事項を確認事項に登録する
6. 節 6「候補数」に、この領域の種別ごとの概数を、節 4 の単位の定義と同じ数え方で書く。AI の読み取りの種別の表の埋め方: 検出条件を持つ種別の候補数は現在の実在数を書き、AI の読み取りの種別は範囲（例: 12〜20）で書く
7. 節 7「共通方式の場所」に、この領域で見つけた共通方式の実装の場所を書く
8. 節 8「用語の候補」に、コードの名前と業務の言葉と出典を書く
9. 節 9「到達範囲」を種別ごと工程ごとに書く。検出条件と取り出しの規則を実行できる形で書けた種別と工程は「機械」とする。書けなかったが AI が読めば一覧化や取り出しができるものは「AI の読み取り」とする。対象に無いか読めないものは「対象外」とし、理由を書く
10. 節 10「読みの記録」に、領域・フォルダ・ファイル数・読み方（全文・要約・未読）・根拠を書く
11. 次の領域へ進む。全領域が終わったら手順 3 へ。途中で止まったときは、節 10 で未完の領域から再開する

### 手順 3: 要件定義書

1. `templates/要件定義書.md` を `docs/design/requirements/要件定義書.md` へ複製する
2. 道標、README、仕様に類する文書、テストコード、画面の文言、各領域の入口（経路・メニュー）を読み、6 節を埋める。現状のコードが実現している振る舞いを現状の要件として確定して書く。望ましい姿との差は本文に書かず確認事項に登録する。定義はあるが実装が無いものは本文に事実として書き、確認事項にも登録する
3. §3 機能要件は、機能（業務の単位）ごとに 1 行とし、対応する種別と単位の候補を書く。機能要件の粒度は道標の 4.8「機能のまとめ方」に従う。§1 に「対象範囲」、§3 に「優先度」、§6 に「受入条件」の見出しを残す
4. 用語は本文で定義せず、道標の節 8（用語の候補）を参照する

### 手順 4: 共通設計文書

前提: 手順 3 が完了していること。手順 3 と並行して進めない。

1. `templates/common/` の 6 様式を `docs/design/common/` へ複製する
2. 道標の節 1・5・7、要件定義書、共通方式の実装（場所は節 7）を読み、各文書の節を埋める。各節の位置づけ（仕様・現行実装・仕様／現行実装）の行を実測に応じて改める
3. 本文に実装の位置（file:line）を書かない。未確定の事項は各文書の要確認事項一覧に書き、既定を付けて確認事項に登録する。既定を置けない事項は保留の候補として登録する

### 手順 5: 検査と出し直し

1. 共有部品の写しの検査スクリプトを要件定義書と共通設計文書 6 つに掛け、終了コード 0 を確かめる。ファイルは次の場所にある
   ```
   ../reverse-shared/scripts/check-doc-heading-addendum.sh
   ```
2. 道標を検査する
   ```bash
   bash scripts/check-map.sh docs/design/common/道標.md --target <対象リポジトリのルート>
   ```
3. 要件定義書と共通設計文書 6 つを検査する
   ```bash
   bash scripts/check-design-docs.sh \
     docs/design/requirements/要件定義書.md \
     docs/design/common/業務仕様書.md \
     docs/design/common/方式設計書.md \
     docs/design/common/データ設計書.md \
     docs/design/common/エラー設計書.md \
     docs/design/common/共通外部仕様書.md \
     docs/design/common/基盤設計書.md
   ```
4. 不合格の項目を直す。道標の不合格は当該領域の手順 2 を、要件定義書の不合格は手順 3 を、共通設計文書の不合格は手順 4 をやり直す。共通設計文書の不合格の原因が要件定義書にあれば手順 3 へ、道標の場所の誤りなら手順 2 へ戻る。やり直しの回数に上限は設けない。同じ不合格が 2 回続いたら、同じ方法を繰り返さずに方法を変える。変えられる方法が尽きた場合だけ止め、人に戻さず、既定を置いて確認事項に登録し、保留にする
5. 検査がすべて通ったら、`references/completion-states.md` の要件定義書と基本設計書の完了状態を観点として自己レビューし、指摘を直す
6. `templates/承認用の要約.md` を出力の置き場の `confirmations/承認用の要約.md` へ複製して埋める。本文 100 行以内に収める
7. 承認の前に、一覧化の実行器（`reverse-listing-units` の `list-units.sh`）を統括が走らせて候補数と実測を突き合わせ、差があれば検出条件を統括が直す。実測まで済ませてから承認を求める
8. 完了時の処理として、共通設計文書6つを次で機械検査する
    ```bash
    bash ../reverse-shared/scripts/check-basic-phase.sh <対象リポジトリのルート> --common --run <実行フォルダ> --design-root <設計書の置き場>
    ```
    通った文書ごとに、文書のレビュー担当（AI）が `references/completion-states.md` の基本設計書の完了状態の観点で読む。合否を判定し、合格・不合格・保留のいずれかを次で記録する
    ```bash
    bash ../reverse-shared/scripts/record-acceptance.sh <対象> --run <実行フォルダ> --common <文書名> --verdict <合格|不合格|保留> --viewpoints "<観点=合|否;...>" [--reason "<理由>"] --design-root <設計書の置き場>
    ```
    不合格は 4 へ戻る。保留は既定を置けない不明点を持つ文書だけにし、理由を確認事項に登録する

### 手順 6: 範囲の承認

1. 承認用の要約をユーザーに提示し、範囲・除外・到達範囲・要件定義書・共通設計文書の承認を AskUserQuestion で求める。データベースの定義の写しなど先方に求める物も併せて伝える
2. 出力の置き場の `confirmations/対象範囲の承認.md` に、`可否: 可`（否のときは `可否: 否`）の行、否の理由、日時、対象のコミットを書く。道標・要件定義書・共通設計文書 6 つの同一性の値（`shasum -a 256`）は文書名ごとに `<文書名>: <値>` の行（例: `道標: <値>`）で書く。`reverse-shared` の `check-entry.sh` はこの `可否:` 行と `道標:` 行を読む
3. 否の場合は、理由を確認事項に登録し、理由の指す手順をやり直してから再提示する

- 保留を除く共通設計文書6つに合格の記録がある
- 次が0を返す: `check-acceptance-record.sh <対象> --common --design-root <設計書の置き場>`
- `confirmations/承認用の要約.md` が 100 行以内で実在する
- `confirmations/対象範囲の承認.md` の可否が `可` で、同一性の値が現在の各文書と一致する

## 設計判断

### check-map.sh

**必要性**: 道標は AI が読んで書くため文面は毎回変わる。第二フェーズが機械で読む部分（節の構成・検出条件の JSON の形・例と場所の実在・候補数・到達範囲の網羅）は毎回同じ形でなければならない。形と実在を機械で確かめ、文面は問わない。

**代替案を採用しなかった理由**:
- 手順書の注意書きだけにする: 書き漏れが第二フェーズで初めて見つかる
- 道標をスクリプトで生成する: 知らないリポジトリに既製の見つけ方を当てることになる

**保守責任者**: 人手（ユーザー）。様式の節・検出条件の形を変えるときは、`templates/道標.md`・本スクリプト・自己テストを同時に直す。

**廃棄条件**: 道標の機械で読む部分を構造化データとして別に出す形に変えた時。

### check-design-docs.sh

**必要性**: 要件定義書と共通設計文書は規約「設計書の書き方の決まり」の内容を節に 1 対 1 で持つ。見出しの欠落・追記章・省略記載・位置づけの行の欠落は機械で見つかる。文書名に「基本設計書」を含まない共通設計文書は規約の既存の検査の対象外のため、この機能が同等の検査を持つ。

**代替案を採用しなかった理由**:
- 規約の既存の検査に任せる: 共通設計文書の見出しを知らない
- 自己レビューだけにする: 見出しの欠落を毎回人手で数えることになる

**保守責任者**: 人手（ユーザー）。見出しの構成を変えるときは `references/design-doc-sections.json` と様式を同時に直す。

**廃棄条件**: 規約の検査が共通設計文書の見出しを持つようになった時。

### check-basic-phase.sh・record-acceptance.sh

**必要性**: 共通設計文書6つの完了判定は、単位の完了判定と同じ記録の形（文書の同一性・コミット・観点・判定）を持つ必要がある。基本設計を書く機能が単位の合格を記録する仕組みと同じ共有部品（`reverse-shared/scripts/`）を使うことで、共通処理の詳細設計を書く機能が読み方を1つに保てる。完了の検査を独立した機能に分けず、この機能自体の手順の最後に置く。
