# 人とAIの分担の決まり

## 概要

AI エージェントへ作業を任せるときの役割分担と、任せてよい範囲の取り決め。

任せる側が何を決め、任される側が何を決めてよいかの境界を先に固定する。この境界が曖昧なまま任せると、出来上がったものが意図と違っていても、どこで食い違ったのかを追えない。

## このプロジェクトの規則

使用する AI ツールの種類と、担当の呼び名・呼び出し方は対象リポジトリの構成に依存する。本書の規則を前提としたうえで、実際に使うツール名と担当の対応をこの節へ起こす。

この節へ書き足す対象は次の 3 つである。

- 使う AI のツールの名前と、上の分担との対応
- 上で定めた境界のうち、このプロジェクトで変える部分があれば、その内容と理由
- 人が不在のときに AI がどこまで進めてよいか

## 違反時の手順

委任が止められた場合、指示へ完了条件を書き足す。何をもって終わりとするかを、受け手が機械的に確かめられる形で書く。確かめる手段が無い作業であれば、その作業を委任せず自分で行う。

外への公開の操作が止められた場合、履歴を書き換えずに済む形（新しい記録を重ねる）に直してから送る。強制の送信に緊急口は無い。

パスの語（`docs/skills`・`docs/design`・`docs/rules`・`scripts/`・`templates/`）を含む委任が止められた場合、prompt に見出し「## 設計の引用」を足す。その直下へ所在を書く。所在は `<パス>#<節>` の形とし、`docs/design/` または `docs/rules/` 配下に限る。続けて引用文を書く。引用文は `引用: <定めの本文をそのまま写した1文以上>` の形とし、40字以上・句点を含み・見出し行や表の区切り行は不可とする。引用文は所在のファイルに実在する文言をそのまま写す。読み取り専用の担当者（investigator等。定義は本規則の内容欄）への委任は対象外。緊急口は無い。この検査は設計先行が守られなかった実例を機械で止めるためのものであり、他規則の緊急口を流用しない。

提示前の応答が止められた場合、提示する内容を `docs/design/` 配下かscratchpadのファイルへ書く。その所在を prompt に含めて `document-reviewer`・`adversarial-verifier`・`code-reviewer` のいずれかへ委任し、改めて応答する。自動解除は、transcript内にhook自身の出力（`"decision":"block"`）と自タグが同じ行に3回以上あるときだけ働く。単なるタグ名の言及では解除されない。

## 既知の限界

- 「実装の委任は設計の引用を渡す」は判定役への委任が実在することだけを見る。委任の**結果**（合格・不合格の別）までは読まない。判定役が不合格を返したのにそのまま進む行動は、本規約の検査だけでは止められない（合格の記録をtranscriptから読む検査は次段の課題）。
- 「提示前に判定役を通す」に自動解除は無い（2026-09-06第4版で撤去。下記設計判断参照）。livelockの緩和は、同じblockが5回続いたらsystemMessageで人に知らせるだけであり、block自体は解除しない。
- 「原稿」「案」「文面」等の提示語は短い一般語のため、無関係な文脈（「提案」「事案」等の一部）でも一致しうる。過検知は許容し、提示物をファイルに書いて委任すれば解消する運用で吸収する。
- 「判定役への委任はレビュー対象を明記する」は、promptが`docs/design/`・`docs/rules/`への言及を含む委任にだけ課す。それ以外の一般的なコードレビュー委任には課さない。
- mainの参照が実際に動くかどうかの検査（設計書・単体テスト設計書§2の意味のある追加・check-skill-design-docs.shの合格）は本規約の対象外である。`docs/rules/agent-operations/work-records/rule.md`のgitの参照更新フック（`reference-transaction`）が担う。本規約は委任の見出し・結果・提示前レビューという行動面だけを見る
- 「外への公開まで AI が行う」は、引数をパイプで流し込む形（`printf … | xargs git`）で強制の送信を組み立てる経路は防げない

## 設計判断

### 規則「外への公開は人がする」の廃止

2026-09-06、規則「外への公開は人がする」を廃止した。この規則は旧リポジトリの様式から持ち込まれた AI の記述であり、人の指示に無かった。グローバル規約 toolkit-payload-cycle の手順 4（統合先へ送るまで完遂する）とも矛盾していた。人の指摘で廃止し、強制の送信だけを拒否する「外への公開まで AI が行う」規則へ改めた。理由付きの緊急口も、通常の送信を止めなくなったため外した。強制の判定には、通常のgit push検出と同じ前置の剥がしとgitオプションの読み飛ばしを引き続き適用する。

### check-delegation-completion-criteria.sh への「実装の委任は設計の引用を渡す」「提示前に判定役を通す」の追加

**必要性**: 改善指示書の対応で、設計書に振る舞いを書かないまま実装だけを進める作業が繰り返された（2026-09-05に9件中8件で発覚）。既存の「受け入れの手順」は設計先行を求めていたが、行動を機械で止める仕組みが無く、AIの自己申告に依存していた。委任 prompt に設計の引用（所在＋実在する引用文）を強制すること、および提示前に判定役への委任を強制することで、行動そのものを止める必要があった。

**代替案を採用しなかった理由**:
- 新規スクリプトとして分離する: 本ファイルの front matter `checker` は単一の値しか持てない（`build-derived-rules.sh` の登録ロジックを確認済み）。同じ規約に2本目の検査スクリプトを置いても settings.json には登録されない。既存の check-delegation-completion-criteria.sh は既に PreToolUse(Agent) を扱っている。`# timing:` 宣言を複数持たせる形（check-work-records.sh が Stop と PreToolUse を1本で扱う既存パターン）に合わせ、同一ファイルへ追記した
- Bash ツール直叩き: PreToolUse(Agent)・Stop の発火点に接続できず、機械強制が成立しない
- 既存の緊急口（[DELEGATION-EXEMPT]・SKIP_REASON・孫委任の免除）を新しい2規則にも適用する: 本作業が解こうとした問題（設計先行が守られなかった実例）に対する検査である。既存の緊急口を流用すると同じ抜け道を再現するため、「実装の委任は設計の引用を渡す」は免除を持たない

**保守責任者**: 人手（ユーザー）。規則を増減する場合は本ファイルの規則の表と `check-delegation-completion-criteria.sh` を同時に更新する。

**廃棄条件**: 改善指示書の受け入れの手順（work-records/rule.md）が別の仕組みで設計先行を保証するようになった時。または、本チェックが対象とする委任経路（Agent への prompt・Stop 時点の最終応答）自体が Claude Code 側で構造的に変わった時。

2026-09-06、提出前の自己検査を判定役の観点に揃える定めを足した（作業の記録の決まりと同じ経緯）。

### 2026-09-06改訂: 字面の検査は補助、順序と判定役の記録が本体

**必要性**: 上記の初版（変更語の判定・「設計」＋「以下」の組）は字面の一致による門であった。adversarial-verifierの反証（高5・中3）とcode-reviewerの指摘により、迂回できると実証された。1文字の引用（句点のみ）が通ってしまう。否定文「変更はしない」を誤検知する。活用形「直して」を見逃す。「docs/design」のようなスラッシュ無しを見逃す。「設計」＋「以下」が通常の報告文を過検知し、逆に「原稿…ご確認ください」を見逃す。字面のパターンを積み増す修正は同種の迂回を再生産する。そこで本体をwork-records側の「設計を先に書いてから実装する」へ移した。これは同じ枝の先行commitに設計書の変更があり、判定役への委任がtranscriptにあることを求める規則である。本ファイルの2規則（実装の委任は設計の引用を渡す・提示前に判定役を通す）は**字面の粗さを埋める補助**に位置づけを改めた。judge_design_quoteは変更語の判定を廃止しパスの語のみで対象を決め、読み取り専用の担当者を免除する。judge_presentation_reviewは「設計」＋「以下」の組を外し、原稿・案・文面等の直接的な語とフェンス内の「設計」に絞った。判定役への委任は、提示する内容の所在（`docs/design/`かscratchpad）をpromptに含むものだけを数える。これは提示物をファイルに書いてから委任する運用と対応づけたものである。

**代替案を採用しなかった理由**:
- 字面のパターンをさらに追加する: 反証のたびに新しいパターンを追加する対症療法であり、次の迂回を防げない。順序（commitの前後関係）と判定役への委任という改ざんが難しい記録を本体に据える方が迂回されにくい。
- 変更語の判定を残しつつ活用形を追加する: 否定文（「変更はしない」）の誤検知は活用形の追加では解決しない。語彙判定そのものを廃止しパスの語だけで対象を決める方が単純で迂回されにくい。

**保守責任者**: 人手（ユーザー）。字面の検査（40字下限・句点・見出し/区切り行除外・提示語彙）を変更する場合は本ファイルと `check-delegation-completion-criteria.sh` を同時に更新する。本体（順序の強制）は `docs/rules/agent-operations/work-records/rule.md` と `check-work-records.sh` 側で保守する。

**廃棄条件**: 字面の検査（本節の対象）が不要になるほど本体（順序の強制）の網羅性が高まった時。

### 2026-09-06第4版: PASS判定の厳密化・レビュー対象の明記・自動解除の撤去

**必要性**: 3回目の反証で実装上の不具合が複数見つかった。

(1) tool_resultの判定が「PASS」の部分文字列一致だった。そのため「PASS条件を満たさない」のようなFAIL宣言の一部まで合格と誤判定していた。判定の行（「判定:」「総合判定:」「Verdict」）に限定した。同じ行群にFAIL・不合格・修正必須があれば不合格を優先するよう改めた。あわせて、adversarial-verifierは合否を宣言しない担当者である。そのため「code-reviewerまたはdocument-reviewerの合格」と「adversarial-verifierの委任」を別条件に分けた。

(2) promptにパスの文字列が含まれるだけでは判定できないことがあった。そのパスを本当にレビュー対象として渡したかは字面では分からない。委任の時点で見出し「## レビュー対象」を強制した。これにより後段の判定に使える確実な手がかりを作った。

(3) `stop_hook_active=true`で無条件return 0していた。そのため1回blockされたセッションは、その後の`stop_hook_active`が立つStopを素通りする抜け道になっていた。同じ判定をそのまま行うよう改めた。livelockの緩和は5回連続block時のsystemMessage通知のみに限定した（解除はしない）。

(4) 提示語彙に「見ていただけますか」「ご覧ください」「たたき台」を追加した。10行以上のコードフェンスの判定も変更した。単一ブロックの行数ではなく全フェンスの合計行数で見る。複数の短いフェンスへの分割による回避を防ぐためである。

**代替案を採用しなかった理由**:
- PASS判定を「PASS」の単純な部分一致のまま維持する: 「PASS条件を満たさない」のようなFAIL文中の語まで拾う誤判定が実測で確認されており、判定の行に限定しないと解消しない
- レビュー対象の明記を求めず、Stop側のcontains判定の精度を上げる: 委任の時点で構造化されていない情報から後段だけで確実性を作ることはできない。委任の入口で強制する方が確実
- 自動解除の基準を推測で決める: Stop hookのblock時のreasonが実transcriptへどう記録されるかを`~/.claude/projects/`配下で確認できなかった。確認できない基準に基づく自動解除は、根拠のない安全装置になる

**保守責任者**: 人手（ユーザー）。変更対象は判定の行の語彙（「判定:」「総合判定:」「Verdict」）・提示語彙・livelock緩和のしきい値（5回）である。変更する場合は本ファイルと `check-delegation-completion-criteria.sh` を同時に更新する。

**廃棄条件**: 判定役の合否表明の形式が統一され、部分一致でも誤判定が起きなくなった時。またはStop hookのblock記録形式が確認でき、確実な自動解除条件を設計できるようになった時。

2026-09-06 の 5 回目のレビューで、外部公開の判定が `git` と `push` が文字列のどこかにあるだけで拒否することが実測された。レビュー担当自身の無関係なコマンド（ヒアドキュメント内の正規表現と Perl の `push`）を止めていた。判定を「`git` で始まる区切りの中に副命令 `push` がある」形へ改めた。

6 回目の反証で、`command git push`・`exec git push`・`/usr/bin/git push`・`\git push` が区切りの先頭の `git` の判定を逃れることが実測された。前置を剥がしてから命令を見る形へ改めた。

7 回目の反証で `./tools/git`・`~/bin/git`・`{ git push; }`・`then git push`・`busybox git` が前置の判定を逃れることが実測され、前置の一覧を広げた。引数をパイプで流し込む形（`printf … | xargs git`）は既知の限界とする。

8 回目の反証で `./git push` と `git -C . push` の形が実測されたため、前置のパスの範囲と git のオプションの読み飛ばしを定めた。実行時の展開（`$(which git)`・変数・`${IFS}`・`parallel`・`ssh`）は既知の限界とする。
