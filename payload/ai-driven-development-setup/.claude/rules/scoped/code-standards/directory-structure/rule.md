# どこに何を置くかの決まり

## 概要

リポジトリの中で、どこに何を置くかの取り決め。

置き場が決まっていないと、探す人は全体を見るまで無いことを確認できない。新しいファイルを作る人が、迷わず置き場を決められる状態を保つ。

## 規則

| 規則 | 内容 | 検査 |
|---|---|---|
| 直下を許可の一覧で管理する | リポジトリの直下に置くディレクトリを一覧で定め、一覧に無いものを増やさない | 静的解析: リポジトリ直下のディレクトリが許可の一覧に含まれているかを走査する |
| 置き場を役割で分ける | 実装・テスト・文書・設定・生成物を、役割ごとに別のディレクトリへ置く | 静的解析: 実装とテストと文書が別のディレクトリへ分かれているかを走査する |
| 一時ファイルをリポジトリ内へ置かない | 調査のための書き置きと途中の生成物を、版管理の対象になる場所へ作らない | 静的解析: 版管理の追跡の対象に一時ファイルらしい名前が無いかを走査する |
| 依存の向きを一方向に保つ | 層をまたぐ参照の向きを一方向に決め、逆向きの参照を作らない | 静的解析: 層をまたぐ取り込みの向きが規定と逆になっていないかを走査する |
| 深い入れ子を作らない | ディレクトリの入れ子を浅く保ち、階層を増やす前に分け方そのものを見直す。既定の上限は5階層とする | 静的解析: 5 階層を超えていないかを走査する。値はこのプロジェクトの規則の表で上書きできる |
| 名前の付け方を階層内で揃える | 同じ階層に並ぶディレクトリの名前の付け方を揃え、単数と複数を混ぜない | 静的解析: 同じ階層のディレクトリ名の表記の形式が揃っているかを走査する ／ レビュー: 単数と複数の混在が無いかを確認する |
| 運営文書の置き場を固定する | `ai-work/todo/` に計画と作業指示書、`ai-work/records/` に完了の記録・検査と検証の記録・台帳・設計判断の記録を置く。`docs/` には AI が読む定義だけを置き、運営文書を置かない | 静的解析: ファイル名から種類を確定できる運営文書が定めた 2 つの置き場にあるかを走査する |
| 設計文書の置き場を固定する | 要件定義書は `docs/design/requirements/` に置く。調査と検出条件の定義書・共通設計文書 6 つ・共通処理の詳細設計書・種別横断結合テスト設計書・技術スタック・環境構築手順書は `docs/design/common/` に置く。種別ごとの一覧・納品物一覧・テスト観点表・テストケース一覧は `docs/design/lists/` に md と json を同じ場所に置く。基本設計書・単体テスト設計書・詳細設計書・テーブル定義書・集約設計書は `docs/design/<種別>/<単位>/` に置く。操作シナリオ仕様書は繰り返し再検証を選んだ場合だけ `docs/design/screens/<単位>/` に md と YAML の対で置く | 静的解析: `docs/design/` 配下の書き込み先について、ファイル名から種類を確定できる設計文書が定めた置き場にあるかを走査する |

## このプロジェクトの規則

上限と形式の具体的な値は、リバース解析が対象リポジトリを観測してこの表の行として起こす。

| 規則 | 内容 | 検査 |
|---|---|---|
| 未解析 | この規約に対応する実装の慣行は、まだ観測していない。リバース解析を実行して対象コードを分析すると、その結果からこの節へ規則が起こされる。解析を待たずに規則を決めたい場合は、この節へ直接書き足してよい | 未解析: リバース解析が未実行であり、対象コードの観測結果がない | 不可: 観測の有無は解析の実行結果に依存し、静的解析で判定できない |

## 違反時の手順

書き込みが止められた場合、書き込み先を `.gitignore` の対象になる一時作業ディレクトリへ変更する。版管理へ残す必要があるファイルだった場合は、ファイル名を一時ファイルらしいパターン（`.tmp` 等の拡張子・`scratch-` 等の接頭辞）から外す。
