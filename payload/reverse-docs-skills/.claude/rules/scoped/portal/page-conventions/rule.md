# ポータル HTML 規約（PORTAL-PAGE-CONVENTIONS）

リバース設計ポータルの生成 HTML に適用する合格基準。テンプレートから生成された全ページが統一されたデザインシステムと構造規約に準拠していることを検証する。portal-reviewer が本ファイルを Read して照合する。

## 適用対象

`shared/templates/` 配下のテンプレートから生成された HTML ファイル、および `shared/samples/` 配下のサンプル HTML。ポータルトップも共通シェルを使うため、他のページと同じ観点で検査する。

文書ビューア型も共通シェルを使うため、他のページと同じ観点で検査する。文書の本文は共通シェルのメインペイン内でスクロールする。

`shared/samples/規約提案/` と `shared/templates/rule-proposal/` 配下は適用対象から外す。規約提案 HTML（サンプルとその生成元テンプレート）はポータルのページではなく、リポジトリ外へ出力して現場のエンジニアが判定するための独立した成果物である。ポータル共通シェルを使わず、意匠は `shared/references/規約定義と派生生成の設計.md` が参照する別の定義に従う。同じ検査を当てると、意匠の違いをすべて不合格として数えることになる。

スキルガイド HTML（`.claude/skills/*/references/*-guide.html`）は現状すべてが本規約の観点で不合格である。ポータル共通シェルを使わず、独自の意匠を持つためである。スキルを 1 本追加するたびに不合格の件数が増える。件数を着手前と比べる運用では、この増加分を新規ガイドの枚数から見込む必要がある。ガイド HTML を共通シェルへ寄せるか、本規約の適用対象から外すかは、別の判断として残っている。

## カラーシステム

| 観点キー | 検査内容 |
|---|---|
| 色トークン-旧値禁止 | 刷新前のトークン値がファイル内に存在しないこと。ライト系は `#F6F8FA`・`#D1D9E0`・`#AFB8C1`・`#0969DA`・`#218BFF`・`#DDF4FF`・`#54AEFF`・`#BC4C00`・`#FFF1E5`・`#1A7F37`・`#DAFBE1`・`#CF222E`、ダーク系は `#15171C`・`#1C1F26`・`#21262D`・`#30363D`・`#484F58`・`#E8E5DC`・`#B6B3AB`・`#888784`・`#58A6FF`・`#79C0FF`・`#132D4B`・`#1F6FEB` |
| 色トークン-新値存在 | `#0F1217`（ダークの背景）・`#4CC2FE`（ダークのアクセント）・`#FF6E4F`（差し色）が CSS 変数定義に存在すること |
| テーマ-定義 | `prefers-color-scheme` のメディアクエリと、`data-theme="dark"`・`data-theme="light"` の両方の属性セレクタが存在すること |

## 全画面フィットレイアウト

| 観点キー | 検査内容 |
|---|---|
| 全画面-高さ固定 | ページコンテナに `height: 100vh` が指定されていること。`min-height: 100vh` は違反 |
| 全画面-overflow制御 | ページコンテナに `overflow: hidden` が指定されていること |
| 全画面-スクロール領域 | メインコンテンツ領域（`.table-area`・`.dp-main`・`.pt-main`・`.pt-tablewrap` のいずれか）に `overflow-y: auto` または `overflow: auto` が指定されていること |
| sticky-thead | テーブルを持つページで `thead` に `position: sticky` が指定されていること |
| 共通シェル-サイドバー | `class="pt-sidebar"` が存在すること |
| 共通シェル-方眼紙 | 方眼紙背景の `background-size` 指定が存在すること |

## デザインの基本形

| 観点キー | 検査内容 |
|---|---|
| 角丸-ゼロ | `border-radius` の値が `0` 以外にならないこと。刷新後のデザインは角丸を使わない |
| 影-オフセットのみ | `box-shadow` にぼかし半径を持つ影が無いこと。3 つ目の長さが `0` 以外の指定を禁止する。`inset` 指定は対象外 |

## 一覧ページ固有（id="unit-manifest" または id="screen-manifest" を持つページ）

| 観点キー | 検査内容 |
|---|---|
| 一覧-列数上限 | `<thead>` 内の `<th>` が 6 個以下であること（シェブロン列含む。JS による任意列追加は対象外）。静的な `<thead>` は画面名・ルート・区分の 3 列を持ち、画面区分・必要権限・関連API・設計書は値が 1 件でもある場合のみ JS が実行時に任意列として末尾へ追加する。画面 ID は列ではなく展開行の詳細に表示する |
| 一覧-展開グループ分離 | JS 内に `detail-group-label` と `evidence` の両キーワードが存在すること |
| 一覧-details禁止 | `<details class="module-group">` が存在しないこと。ただし、分割軸を宣言するページは除外する。分割軸の宣言は `data-split-axis="<軸キー>"` の有無で判定する |
| 一覧-common-files禁止 | `class="common-files"` が存在しないこと |
| unresolved-条件付き | unresolved セクションが `empty` または `has-items` のクラスで条件分岐していること |
| 一覧-分割軸マーカー | `<details class="module-group">` を使うページは、その群を包む要素に `data-split-axis="<軸キー>"` を持つこと。分割を宣言していないページで `details` を使うことを禁止する |

## ポータルトップの画面なし縮退

`portal-catalog.json` の blueprint が `disabledWhenEmpty: true` を持つ種別は、対象リポジトリに実ファイルが 0 件でもカードを消さず、選べない状態で残す。

| 観点キー | 検査内容 |
|---|---|
| 縮退-無効カード表示 | `disabledWhenEmpty: true` の種別が 0 件のとき、カードが消えずに `data-disabled="true"` を持って残ること |
| 縮退-リンク無効化 | 無効カードがリンクとして機能しないこと（`href` を持たないか `aria-disabled="true"` を持つ） |

## 重要度コールアウト

通常表へ埋没させてはいけない注意喚起は、共通シェルの `.pt-callout` と重要度修飾クラスを組み合わせて表示する。
見出しをコールアウトの先頭要素に置き、色帯とアイコンの両方で重要度を区別する。

| 重要度 | CSSクラス | Material Symbols名 | 適用対象 |
|---|---|---|---|
| 注意 | `.pt-callout.pt-callout--caution` | `info` | 補足確認が必要だが、作業を継続できる事項 |
| 警告 | `.pt-callout.pt-callout--warning` | `warning` | 未解決リスク、要確認事項一覧、判断前に解消すべき事項 |
| 重要 | `.pt-callout.pt-callout--important` | `priority_high` | 承認済み決定、変更禁止条件、見落とすと成果物の意味が変わる事項 |

要確認事項一覧・未解決一覧は1件以上ある場合だけ「警告」を適用する。
0件を示す空状態へ警告色を付けない。
アイコンはGoogle Fonts CDNから読み込むMaterial Symbols Outlinedを、`material-symbols-outlined pt-callout__icon`の専用`span`で表示する。
共通CSSには`info`・`warning`・`priority_high`だけの公式フォントサブセットを埋め込み、CDN遮断時も同じアイコン表示を保つ。
本文の強調だけを目的にコールアウトを乱用せず、通常の説明は従来のパネル・表・注記を使う。

## 設計判断

### shell-injection.sh

**必要性**: 共通シェル（サイドバー・フッター・方眼紙背景）を22本のテンプレートへ入れる。
実体を1箇所で保守しながら、共通資産をインライン注入した単一HTMLとして出力する必要がある。
Material Symbols OutlinedのGoogle Fonts CDNだけは、アイコン表示に必要な外部依存として許可する。
同じ3アイコンの公式フォントサブセットを共通CSSへ埋め込み、オフライン表示を維持する。
既存の`tokens.css`注入と同じマーカー置換を使い、サイドバーのナビ項目はカタログから組み立てる。
組み立てとプレースホルダ解決を6本のビルドスクリプトへ複製すると、保守点が6倍になる。
共通関数を1本のスクリプトに閉じ、各ビルドスクリプトが`source`して呼ぶ。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: ビルドスクリプトから呼ぶ共通関数であり、対話セッションのツール呼び出しでは代替できない
- 既存 Makefile ターゲット拡張: このリポジトリに Makefile は存在せず、新規導入は本スクリプト専用の依存を増やすだけになる
- package.json scripts 追加: 同様に、このリポジトリはビルド設定を持たない
- `render-template.sh` への統合: あちらは汎用の文字列置換エンジンであり、カタログの構造やサイドバーの仕様を知るべきでない。関心が異なる

**保守責任者**: 人手（ユーザー）。`partials/` のファイル構成やマーカー名を変える場合は、本スクリプトと `page-conventions/rule.md` を同時に更新する。

**廃棄条件**: 共通シェルを廃止した時、またはテンプレートの部分結合をビルド基盤が標準で提供するようになった時。

### unit-axes.sh

**必要性**: 分類軸と任意列の宣言（`shared/references/unit-axes.json`）は、リポジトリ既定・プロジェクト全種別上書き・種別別上書きの 3 階層を持つ。これらをキー単位で deep merge して解決する必要がある。この解決規則を `build-unit-list.sh` だけに実装すると問題が生じる。manifest パスだけを引数に単独実行される `validate-manifest.sh` と、`--self-test` で直接叩かれる `build-feature-list.sh` がある。この両者が、同じ規則を再実装することになる。結果として、build と validate が別の宣言を見る二重基準が生まれる。`render-template.sh` / `shell-injection.sh` と同じ共通関数として実装する。複数ビルダーが source する形で 1 本に閉じるのが唯一の現実的な手段である。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: ビルドスクリプトと検証スクリプトの双方から呼ぶ共通関数であり、対話セッションのツール呼び出しでは代替できない
- 既存 Makefile ターゲット拡張: このリポジトリに Makefile は存在せず、新規導入は本スクリプト専用の依存を増やすだけになる
- package.json scripts 追加: 同様に、このリポジトリはビルド設定を持たない
- `render-template.sh` への統合: あちらは汎用の文字列置換エンジンであり、宣言のスキーマやマージ規則を知るべきでない。関心が異なる
- `portal-catalog.mjs` と同じ Node.js 実装: 消費者が全て bash スクリプトである。`jq` は既に全ビルダーと `validate-manifest.sh` の必須依存として導入済みのため、新たに Node.js 依存を足す理由がない

**保守責任者**: 人手（ユーザー）。宣言のスキーマ（`valuePolicy` の値・`column.show` の値・`split` の構造）を変える場合は、本スクリプトの `unit_axes_validate` を更新する。あわせて `shared/references/unit-axes.json` と本 rule.md も同時に更新する。

**廃棄条件**: 分類軸の宣言化を廃止した時、または列定義の宣言解決をビルド基盤が標準で提供するようになった時。

### check-manifest-persistence.sh

**必要性**: 一覧生成スキルごとにマニフェストの永続化先が非対称だった問題（改善課題 1-136）に対し、生成後の実在を機械判定するため。定義文書の記述だけでは実際に永続化されたかを確認できない。7 種別（画面・API・テーブル・バッチ・帳票・外部連携・機能）の一覧フォルダを横断して検査する必要があり、共通関数として 1 本に閉じるのが妥当である。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 7 種別分の存在確認を毎回手動実行するとトークンを浪費し、往復検証セッションのたびに同じ確認作業を繰り返すことになる
- `validate-manifest.sh` への統合: あちらは manifest の中身（スキーマ・重複・summary 整合性）の検証を担っており、ファイルの配置場所（永続化されたかどうか）の検査は関心が異なる
- 各一覧生成スキルへの個別実装: 7 種別で同じ「HTML が実在するならマニフェストも実在するはず」という検査ロジックが重複する

**保守責任者**: 人手（ユーザー）。一覧種別を追加した場合は本スクリプトの `manifest_name_for_folder` 対応表に行を追加する。

**廃棄条件**: 一覧フォルダとマニフェスト名の対応が宣言ファイル（`shared/references/unit-axes.json` 等）から解決できるようになった時。

### check-derived-drift.sh

**必要性**: 定義から生成した派生物（ポータル HTML 等）が手作業で編集されると、定義との対応が壊れたまま気付けない。生成時にハッシュを台帳（derived-fingerprints.json）へ記録し、以後の突合で MODIFIED と DELETED と ADDED を検知する。同じ突合をコミット時 hook と CI と手動実行の 3 経路から呼ぶため、判定を 1 本のスクリプトへ集約する。判定はハッシュだけで行い、更新時刻は使わない（git checkout や別ツールでも時刻は動くため）。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 3 経路から同じ判定を呼ぶ必要があり、都度組み立てると経路ごとに判定がずれる
- 既存 test-portal-conventions.sh への同居: あちらは HTML の規約適合（色やレイアウト）の検査であり、定義と派生の一致という関心が異なる
- Makefile / package.json scripts 追加: このリポジトリはどちらも持たない

**保守責任者**: 人手（ユーザー）。検知対象を値のレベル（画面名や表示コミットの突合）へ広げる際も本スクリプトへ集約する。

**廃棄条件**: 派生アダプターと保守の仕組み（AI駆動開発セットアップ構想の Phase C と Phase D）自体を廃止した時。

### output-layout.sh

**必要性**: 生成スクリプト 26 ファイルが出力先の日本語パスを直書きしており、物理配置の変更（`docs/` への移行）が全ファイル書き換えになる。パスの定義を `shared/references/output-layout.json` へ集約し、リポジトリ既定と対象側上書きの 2 階層をキー単位で合成して解決する共通関数が必要である。解決規則を各スクリプトへ個別実装すると、生成と検証が別の宣言を見る二重基準が生まれる（`unit-axes.sh` と同じ判断）。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 生成と検証の双方から呼ぶ共通関数であり、対話セッションのツール呼び出しでは代替できない
- `unit-axes.sh` への同居: あちらは分類軸と列定義の宣言解決であり、出力配置という関心が異なる
- `render-template.sh` への統合: あちらは汎用の文字列置換エンジンであり、配置の宣言を知るべきでない

**保守責任者**: 人手（ユーザー）。配置キーを増減する場合は `output-layout.json` と本節と self-test を同時に更新する。

`layout.screenUnitRoot` は対象リポジトリ内の画面単位文書（`screen-*`）だけの物理rootを表す。既定値は `画面`。表示用の `kindLabels.screen` は物理pathへ流用しない。値は非空の安全な単一相対segmentに限定し、JSON null・空文字・`.`・`..`・`/`・backslash・find globメタ文字（`* ? [ ]`）を解決時に拒否する。このキーは一覧root、画面遷移、matrix、テンプレート原本、samples、リポジトリ外の `verification/` へ連動させない。

**廃棄条件**: 出力配置の宣言化を廃止した時、または配置解決をビルド基盤が標準で提供するようになった時。

### build-confirmation-survey-data.sh

**必要性**: 推定名称（`nameConfidence=="inferred"`）・要手動確認（`kind=="unresolved"`）・権限未設定（`permissions==null`）・要確認事項（画面詳細設計書の要確認事項一覧）の4系統は、それぞれ別々のページ・別々の判定式で分散記録されており、人間が確認すべき事項を横断で発見する経路が無かった（改善課題1-169）。4系統の判定式を1箇所に集約し、`build-matrix-pages.sh` の決定的生成パイプラインへ載せる導出エンジンが必要で、self-testを含み再生成のたびに繰り返し呼ばれる。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: `build-matrix-pages.sh` から決定的に呼ばれる前段処理であり、対話セッションのツール呼び出しでは代替できない
- 既存 `build-matrix-data.sh` への機能追加: あちらは画面・API・テーブルの交差関係（マトリクス）の導出が関心であり、4系統の「人間確認待ち」集約とは検査対象・判定式が異なる
- Makefile / package.json scripts 追加: このリポジトリはどちらも持たない

**保守責任者**: 人手（ユーザー）。4系統の判定式（`nameConfidence`・`kind`・`permissions`・要確認事項の入力形式）を変更する場合は本スクリプトの導出ロジックと self-test を同時に更新する。

**廃棄条件**: 確認事項質問票ページ自体を廃止した時、または4系統の集約を別基盤が標準で提供するようになった時。

### check-glossary-sync.sh

**必要性**: `docs/AI駆動開発セットアップ構想.md` は「`docs/用語集.md` を説明HTML群の用語の単一情報源とする。ガイドのパネルとの同期はずれ検知の対象」と定義済みだが、同期を機械検知する手段が無かった（同構想の実装進捗記録は「情報源は新設済み、同期機構は未着手」と明記）。用語集を直してもガイドが古いまま残り、逆にガイドで用語を書き換えても用語集に反映されないまま気付けない状態だった。22本のガイドHTML（`.claude/skills/*/references/*-guide.html`）が用語パネルを持ち、`docs/用語集.md` 1本と突き合わせる必要があるため、手動突合ではなく機械的な差分検知が要る。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: ガイド追加・用語追加のたびに同じ突合作業（22本のHTMLパースと用語集の対照）を繰り返すことになり、都度トークンを浪費する
- 既存 `check-derived-drift.sh` への機能追加: あちらは生成済み派生物（ポータルHTML等）のハッシュ台帳突合が関心であり、用語集とガイド用語パネルという手書き文書同士の内容比較とは検査対象・判定式が異なる
- Makefile / package.json scripts 追加: このリポジトリはどちらも持たない

**保守責任者**: 人手（ユーザー）。ガイドHTMLの用語パネル形式（`<dt>`/`<dd>` 対・`<table>` 行以外の新形式）を新設する場合は本スクリプトの `parse_guide` 抽出ロジックを同時に更新する。

**廃棄条件**: `docs/用語集.md` とガイドの用語パネルが単一の生成元から自動生成される仕組みに統合され、手動記述の二重管理自体が解消された時。

### check-derived-values.sh

**必要性**: check-derived-drift.sh はファイル単位のハッシュ突合で「派生物が変わったか」を検知するが、「表示されている値が定義と一致するか」までは判定しない。AI駆動開発セットアップ構想 Phase D「保守-派生値ずれ検知」は、画面名（screen-manifest.json の値と一覧・詳細ページの表示値の一致）と表示コミット（画面詳細設計書 frontmatter の source_ref とポータル・画面ページの表示値の一致）という2種類の値レベルの一致を検査対象と定める。値は台帳を持たず、定義（manifest.json / frontmatter）から毎回決定的に導出して現在の表示値と突合する。shared/scripts/tests/ の自己テスト群（test-e2e-portal.sh）から呼ばれる形で、生成物全体に対する回帰検知として機能する。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: test-e2e-portal.sh・保守フロー双方から同じ判定を呼ぶ必要があり、都度手動実行すると経路ごとに判定がずれる
- check-derived-drift.sh への機能追加: 同スクリプトの設計判断（本節直上）は将来の値レベル検知の集約先として自身を挙げているが、判定方式が異なる（ハッシュ突合による record/status の台帳前提 vs. 定義からの毎回再導出による値比較）ため、同居させると台帳ありきの体系と台帳なしの体系が1本のスクリプト内で混在し複雑度が増す。値レベル検知を独立スクリプトとする判断は本スクリプトを新設した作業指示による明示選択であり、集約するかどうかは改めて判断が必要な既知の未決事項として残す
- test-portal-conventions.sh への同居: あちらは単一HTMLファイルの規約適合（色・レイアウト）を検査するリンタであり、複数種の定義ファイルとHTMLを横断する値突合とは検査対象が異なる
- validate-manifest.sh への機能追加: あちらは manifest 単体のスキーマ・重複・summary整合性の検証が関心であり、HTML表示値との突合という別ファイル間の一致検査とは関心が異なる
- Makefile / package.json scripts 追加: このリポジトリはどちらも持たない

**保守責任者**: 人手（ユーザー）。画面名・表示コミット以外の値検知を追加する場合、または check-derived-drift.sh との統合を判断する場合は本スクリプトと本節を同時に更新する。

**廃棄条件**: 派生アダプターと保守の仕組み（AI駆動開発セットアップ構想の Phase C と Phase D）自体を廃止した時、または check-derived-drift.sh へ統合され本スクリプトが不要になった時。

### scaffold-design-unit.sh

**必要性**: テンプレートの複製と配置と検証を機械で保証する層を持つのは画面だけだった。API・テーブル・バッチ・帳票・外部連携の 10 スキルは、スキル定義の手順（Read → Write）で配置しており、未置換のプレースホルダ・章の欠落・配置先の誤りを検出できない。`scaffold-screen.sh` は 3 サブフォルダ 8 ファイルの束・相対パス補正・共通文書の複製という画面固有の構造を持ち、種別引数で分岐させると複雑度が増して既存の画面経路を壊す。非画面の 5 種別は互いに同形（フラットな束・基本設計と詳細設計の 2 相・名前 1 トークンの置換）であり、1 本で覆える。10 スキルから同じ配置処理を呼ぶため、共通スクリプトへ閉じる。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 10 スキルの Phase 3 から呼ばれる配置処理であり、対話セッションのツール呼び出しでは代替できない
- `scaffold-screen.sh` の拡張: 画面の 3 サブフォルダ構造と非画面のフラット構造を 1 本で分岐させると、既存の画面経路に触れる。画面は実績があり壊せない
- 各スキルへの個別実装: 10 スキルで同じ複製・置換・検証が重複する
- Makefile / package.json scripts 追加: このリポジトリはどちらも持たない

**保守責任者**: 人手（ユーザー）。種別を追加する場合は `shared/references/design-unit-layout.json` の `kinds` へ 1 件足し、テンプレートを配置する。スクリプト本体の変更は不要である。

**廃棄条件**: 非画面種別の設計書生成を廃止した時、または配置と検証をビルド基盤が標準で提供するようになった時。

### test-design-unit-scaffold.sh

**必要性**: `scaffold-design-unit.sh` は 5 種別 × 2 相の展開と 4 種類の検査を持ち、種別の追加やテンプレートの変更で退行しうる。素通り条件（正常な展開）と拒否条件（symlink・重複実行・未置換・章の欠落）を 8 ケースで回帰検証する。手動で 8 ケースを毎回確認するとトークンを浪費する。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 8 ケースを毎回手動実行すると、スクリプト修正のたびに同じ確認を繰り返す
- `test-screen-unit-root-layout.sh` への同居: あちらは画面の配置検査であり、対象と判定式が異なる
- Makefile / package.json scripts 追加: このリポジトリはどちらも持たない

**保守責任者**: 人手（ユーザー）。`scaffold-design-unit.sh` の検査条件を変えるたびに本テストのケースを追従させる。

**廃棄条件**: `scaffold-design-unit.sh` が廃止された時。

3. サンプルを再生成して再検証する
