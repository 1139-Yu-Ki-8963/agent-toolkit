§1概要

そのバッチがどう動くか（処理の流れ・コミットの単位・排他の制御）は、バッチ詳細設計書が書く。しかし、そのバッチが何のために存在し、いつ起動され、どんな業務上の目的を担うかという問いには、実装の手順とは別に答える必要がある。

本スキルは業務語彙だけで基本設計書を書く。コード識別子・フレームワーク用語・型構文・原本の拡張子・内部の成果物名は使わない。読み手は業務担当者である。

本スキルがやること
バッチ 1 本ごとの業務的な意味（起動の契機・実行の周期・入力と出力・業務上の目的・異常時の復旧の方針）を業務語彙のみで記入したバッチ基本設計書の生成
本スキルがやらないこと
処理の流れ・コミットの単位・排他の制御の記述（バッチ詳細設計書の担当）／バッチ一覧の生成（generating-batch-list-for-reverse-docsの担当）

起動引数

引数 必須 内容
batch_manifest_path 必須 バッチ一覧の拡張マニフェストの絶対パス
source_dir 必須 原本コードのルート
output_dir 必須 出力先のルート
template_root 必須 テンプレート群のルート
unit_keys 任意 対象を絞るキーの配列
common_docs_root 任意 共通文書のルート。業務語彙とメッセージの突合に使う

unit_kind は batch 固定であり、引数には取らない。

§2出力

バッチ 1 本につき、次の 2 点が生まれる。

バッチ基本設計書.md（<output_dir>/<batchUnitRoot>/batch-<バッチ識別子>/基本設計/バッチ基本設計書.md）
そのバッチの起動の契機・実行の周期・入力と出力・業務上の目的・異常時の復旧の方針を、業務語彙のみで記入した文書。コードから確定できなかった事項は要確認事項一覧へまとめて記載される。
バッチテスト設計書.md（テスト設計/）
基本設計書の外部仕様・業務仕様・エラーと例外の各章から起こしたテストの観点を記入した文書。各観点に、由来する基本設計書の章が記録される。原本コードもマニフェストも情報源にしない。

§3用語

業務語彙
コード識別子・フレームワーク用語・型構文・パス・ライブラリ名を使わず、業務担当者が読める言葉だけで書く記述の方針。
要確認事項
コードから確定できない事項を推測で埋めず、確認事項として記録したもの。キーは連番を禁じ、内容を要約した意味語で付ける。

§4動作フロー

Phase やること 完了条件
Phase 1
起動引数の確認と対象の確定		 必須4引数の実在確認、マニフェストの確認（unitKind が batch・units が1件以上）、対象ユニットの確定を行う 4引数が実在し、マニフェストが確認済みで、対象ユニットが確定している
Phase 2
業務的な意味の抽出		 マニフェストの記載事項（schedule・targetTables・downstreamJobs・execMethod 等）を把握し、原本コードから起動の契機・実行の周期・入力と出力・業務上の目的・異常時の復旧の方針を読み取る。処理の流れ・コミットの単位・排他の制御は読み取らない。確定できない事項は推測で埋めず要確認事項として記録する 対象ユニット全件について、業務的な意味の記入材料が揃っている
Phase 3
執筆		 テンプレートを展開・配置し、業務語彙のみで各章へ記入する。空欄のまま残った項目を要確認事項一覧へ列挙し、frontmatter の status を draft から authored へ更新する 全対象ユニットの設計書が業務語彙のみで記入済みである
Phase 4
バッチテスト設計書の執筆		 Phase 3 で書き上げた基本設計書だけを情報源にテストの観点を作る。原本コードもマニフェストも読まない。基本設計書で確定していない事項からは観点を作らない バッチテスト設計書が出力され、全ての観点に由来する章が記録されている
Phase 5
機械検査		 業務語彙の検査・注記の残存検査・frontmatter の検査・章の完備検査・由来の記録検査・情報源の検査・配置の検査の7検査を実行する。不合格が1件でもあれば Phase 3 または Phase 4 へ戻る（上限3回） 6検査すべてが合格している

§5守り（禁止事項と機械検証）

禁止事項

  • コード識別子・フレームワーク用語・型構文・ファイルパス・ライブラリ名を本文に書かない
  • 処理の流れ・コミットの単位・排他の制御を書かない（バッチ詳細設計書の担当）
  • コードから確定できない事項を推測で埋めない
  • 根拠を本文に file:line の形で書かない。業務語彙の検査がファイルパス形式の文字列そのものを不合格の対象とするため
  • 子スキルへ委任しない。原本読解と執筆（Phase 1〜3）は業務語彙の一貫性を保つため単一のメインエージェントが通しで担う
  • バッチテスト設計書（Phase 4）は原本コードもマニフェストも情報源にしない。情報源は基本設計書だけ

機械検証

Phase 5 で次の7検査を実行する。検査1は生成した本文に実装用語（フレームワーク用語・型構文・interface の宣言・型注釈・原本の拡張子・内部の成果物名等）が含まれないことを grep で確認する。検査2はテンプレートの記入規則を書いた HTML コメントが残っていないことを確認する。検査3は frontmatter の status が authored になっていることを確認する。検査4はテンプレートが持つ全ての章見出しが出力に存在することを確認する。由来の記録検査はバッチテスト設計書の全観点に由来する章が記録されていることを確認する。情報源の検査はバッチテスト設計書の本文に基本設計書に現れない語が含まれていないことを確認する。配置の検査は基本設計とテスト設計の両phaseを確認する。1つでも不合格なら該当 Phase へ戻り、上限3回で収束しなければ status=ERROR とする。
