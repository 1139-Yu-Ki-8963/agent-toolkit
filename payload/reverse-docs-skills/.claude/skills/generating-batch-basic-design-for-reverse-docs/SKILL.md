## いつ使うか

バッチの基本設計書を作りたいとき、ジョブ単位の業務向け設計書を作りたいとき。

## いつ使わないか

バッチの詳細設計書を作るとき（→generating-batch-detail-design-for-reverse-docs が担当）、バッチの一覧を作るとき（→generating-batch-list-for-reverse-docs が担当）。

# 正本: reverse-docs-skills

本スキルが生成する納品物は顧客提示の文書である。自由記述の本文（要約・説明文）は敬体（です・ます）で書く。記入規則・検証記録・作業記録は常体でもよい（`delivery-payload/references/設計書様式.md` §8）。

# バッチ基本設計書の生成スキル

工程全体は orchestrating-ai-development-setup が案内する。本スキルはバッチ 1 本ごとの基本設計書の執筆のみを担い、単独起動できる。起動引数は batch_manifest_path・source_dir・output_dir・template_root の 4 つが必須で、これらを渡せば動く。`unit_kind` は **batch 固定** であり、引数では受け取らない。

## 情報源

情報源は次の 2 つに限る。

1. バッチ一覧の拡張マニフェスト（`batch-manifest.ext.json`。`schedule`・`targetTables`・`downstreamJobs`・`execMethod` を含む）
2. マニフェストの `sourceFile` が指す原本コード

抽出するのは、起動の契機、実行の周期、入力と出力、業務上の目的、異常時の復旧の方針である。処理の流れ・コミットの単位・排他の制御といった実装の詳細は抽出しない。それはバッチ詳細設計書（generating-batch-detail-design-for-reverse-docs）の担当である。

## 使用タイミング

- バッチ一覧が生成済みで、ジョブ単位の業務設計書を作りたいとき
- 前提: `<output_dir>/<manifestsRoot>/batch-manifest.ext.json` が生成済みであること（`manifestsRoot` は output-layout の物理配置キー。既定値 `docs/manifests`）

## 起動引数

| 引数 | 必須 | 内容 |
|---|---|---|
| `batch_manifest_path` | 必須 | バッチ一覧の拡張マニフェストの絶対パス |
| `source_dir` | 必須 | 原本コードのルート |
| `output_dir` | 必須 | 出力先のルート |
| `template_root` | 必須 | テンプレート群のルート |
| `unit_keys` | 任意 | 対象を絞るキーの配列 |
| `common_docs_root` | 任意 | 共通文書のルート。業務語彙とメッセージの突合に使う |

`unit_kind` は `batch` 固定であり引数に取らない。

## 成果物

| 項目 | 基本設計書 | バッチ結合テスト設計書 | バッチ単体テスト設計書 |
|---|---|---|---|
| 出力フォルダ | `<output_dir>/<batchUnitRoot>/batch-<バッチ識別子>/<unitPhaseDirNames.basic>/` | `<output_dir>/<batchUnitRoot>/batch-<バッチ識別子>/<unitTestDesignDir>/` | `<output_dir>/<batchUnitRoot>/batch-<バッチ識別子>/<unitTestDesignDir>/` |
| 出力ファイル | `バッチ基本設計書.md` | `バッチ結合テスト設計書.md` | `バッチ単体テスト設計書.md` |
| テンプレート | `<template_root>/リバース検証/バッチ/バッチ基本設計書.md` | `<template_root>/リバース検証/バッチ/バッチ結合テスト設計書.md` | `<template_root>/リバース検証/バッチ/バッチ単体テスト設計書.md` |

`batchUnitRoot` は output-layout の物理配置キー（既定値 `docs/design/batches`）。表示用 `kindLabels.batch` は path に使わない。`unitPhaseDirNames.basic` は output-layout の `unitPhaseDirNames.basic` の値（既定値 `basic-design`）であり、scaffold-design-unit.sh が実際に展開する配置フォルダ名と一致させる（1-210）。

テスト成果物は全種別共通で、<unitTestDesignDir>/バッチ結合テスト設計書.md（設計単位1つの外部の振る舞い）とバッチ単体テスト設計書.md（関数・メソッド単位）の2文書とする。観点とケースは各文書の共通13節へ統合し、単位配下へ結合テスト文書を生成しない。

2文書とも本スキルの成果物である。バッチ結合テスト設計書は基本設計で確定した外部の振る舞いから、バッチ単体テスト設計書は詳細設計または入力資料で確定した関数・メソッドから観点とケースを記入する。対象関数が無い場合も雛形のまま完了せず、§1と§2に根拠付きで「該当なし」を記入する。完了時は両文書に未置換プレースホルダがなく、12見出し検査に合格していなければならない。

`<バッチ識別子>` はマニフェストの `unitId` を使う。`unitId` が空（`null` または空文字）の場合は `unitKey` を使う。両方が空の場合だけ当該ユニットを生成せず、`status=ERROR` で中断して hint に「出力先の識別子が確定しない」と当該ユニットの `identifier` を記録する。

`unitKey` をディレクトリ名に使う場合、パス区切り（`/`）と制御文字をそのまま使わない。含む場合はハイフンへ置き換えて使い、置換した事実を当該単位について要確認事項一覧へ記録する。

## 進捗管理（必須手順）

スキル開始時に `TaskCreate` で Phase 1〜5 のタスクを登録する。各 Phase 開始時に該当タスクを `in_progress` に、完了時に `completed` へ `TaskUpdate` で更新する。Phase 5 から Phase 3 または Phase 4 へ差し戻す場合は該当タスクを `in_progress` に戻す。実行環境に TaskCreate/TaskUpdate が存在しない場合は、出力先ディレクトリ内のタスク台帳ファイル（`task-ledger.md`）で同等の Phase 遷移記録を代替する。

## Phase 1: 起動引数の確認と対象の確定

## Step 1-1: 起動引数の確認と対象の確定

- **Step 1**: 必須 4 引数の実在を確認する（`test -f` / `test -d`）。いずれかが欠ける場合は `status=ERROR` で停止する。完了条件: 4 引数すべてが実在する
- **Step 2**: `batch_manifest_path` を Read し、`unitKind` が `batch` であること、`units` が 1 件以上あることを確認する。完了条件: マニフェストが確認済み
- **Step 3**: 対象ユニットを確定する。`unit_keys` が渡されていればその集合、無ければマニフェストの全ユニットを対象とする。完了条件: 対象ユニットの一覧が確定済み

**完了**: 4 引数が実在し、マニフェストが確認済みで、対象ユニットが確定している

## Phase 2: 業務的な意味の抽出

## Step 2-1: ユニットごとの業務的な意味の抽出

対象ユニット 1 件につき次を行う。

- **Step 1**: マニフェストの当該ユニットのエントリ（`schedule`・`targetTables`・`downstreamJobs`・`execMethod` 等）を読む。完了条件: マニフェストの記載事項を把握済み
- **Step 2**: マニフェストの `sourceFile` が指す原本コードを Read し、起動の契機、実行の周期、入力と出力、業務上の目的、異常時の復旧の方針を読み取る。処理の流れ・コミットの単位・排他の制御は読み取らない。完了条件: 業務的な意味の記入材料が揃っている
- **Step 3**: コードから確定できない事項は推測で埋めず、要確認事項一覧へ記録する。完了条件: 未確定事項が当該資料へ整理済み

**完了**: 対象ユニット全件について、業務的な意味の記入材料が揃っている

## Phase 3: 執筆

### テンプレートの配置

執筆の前に、テンプレートを出力先へ配置する。手作業で Read と Write を行わず、次のスクリプトを呼ぶ。

```bash
bash generation-engine/scripts/scaffold-design-unit.sh batch basic <output_dir> <識別子> <表示名> <template_root>
```

`<kind>` と `<phase>` は本スキルの担当に固定する。配置済みのファイルへ記入する形で執筆する。

配置に失敗した場合は執筆へ進まず、`status=ERROR` を返す。

### 表題の形式と前付けとの関係

本文冒頭の `# ` 見出し（表題）は「<対象名> <役割名>」の形式とする。役割名はファイル名から拡張子を除いた文字列と完全に一致させ、記入時に書き換えない。対象名（表示名）トークンは雛形の展開時に自動置換済みであり、記入時に対象名部分を書き換えない。対象名の末尾が役割名の先頭と同じ語で終わる場合は、対象名側から重複する語を落とし、同じ語が2回続けて現れないようにする（例: 対象名「注文API」＋ 役割名「API詳細設計書」→ 表題「注文API詳細設計書」）。

前付け（frontmatter）の識別名（`<種別>KEY`・`<種別>ID` 等）と本文の表題は、一致を求めない。前付けはマニフェストの識別子をそのまま使う機械可読の値であり、表題は対象の表示名を使う人が読む見出しである。両者が異なる文字列になっても構わない。

## Step 3-1: テンプレートの展開と記入

- **Step 1**: `<template_root>/リバース検証/バッチ/バッチ基本設計書.md` を Read する。読み込んだ内容を `<output_dir>/<batchUnitRoot>/batch-<バッチ識別子>/<unitPhaseDirNames.basic>/バッチ基本設計書.md` へ書き出す。`<バッチ識別子>` の決め方は「成果物」節の規約に従う。中間ディレクトリが無ければ作成する。完了条件: 全対象ユニットのファイルが配置済み
- **Step 2**: Phase 2 で得た材料を業務語彙のみで各章へ記入する。原本に無い値を書かない。推測で埋めない。完了条件: 各章の記入が完了している
- **Step 3**: 空欄のまま残った項目を要確認事項一覧へ列挙する。対象コードの位置は記録しない。完了条件: 要確認事項一覧へ記録済み
- **Step 4**: frontmatter の `status` を `draft` から `authored` へ更新する。完了条件: `status: authored` になっている

**完了**: 全対象ユニットの設計書が業務語彙のみで記入済みである

## Phase 4: バッチ結合テスト設計書・バッチ単体テスト設計書の執筆

## Step 4-1: 2つのテスト設計書を執筆する

**使用ツール**: Read / Write

テスト設計書では、§1を正常・異常・境界を含む全観点の一覧とする。
§5と§6には、§1のうち異常・境界の観点を§1と同じ観点キーで詳述する。
§5と§6では新しいケースを定義せず、§1の全観点に対応する実行ケースを§2だけへ記載する。
実行するテストの件数は、§2のデータ行数だけで数える。

バッチ結合テスト設計書（外部振る舞い用）の情報源は **Phase 3 で書き上げた基本設計書だけ**とする。原本コードもマニフェストも読まない。バッチ単体テスト設計書（単体用）の情報源は、対応する詳細設計書または入力資料で確定した関数・メソッドだけとする。対象関数が無い場合は、§1と§2に根拠付きで「該当なし」を記入する。どちらの文書も雛形のまま完了としてはならない。

```bash
bash generation-engine/scripts/scaffold-design-unit.sh batch test <output_dir> <識別子> <表示名> <template_root>
```

1. バッチ結合テスト設計書とバッチ単体テスト設計書のテンプレートを Read し、それぞれの12見出しを保持して記入する
2. バッチ結合テスト設計書は、基本設計書の外部仕様・業務仕様・エラーと例外の各章からテストの観点を作り、各観点に由来する基本設計書の章を記録する。基本設計書で確定していない事項からは観点を作らず、要確認事項一覧へ移す
3. バッチ単体テスト設計書は、詳細設計書または入力資料で確定した関数・メソッドから観点とケースを作り、各観点に由来する資料と関数・メソッドを記録する。対象関数が無い場合は、§1と§2に根拠付きで「該当なし」を記入する
4. 2文書とも12見出しを保持したまま出力先へ Write する

**完了**: バッチ結合テスト設計書・バッチ単体テスト設計書がテスト設計/へ出力され、前者の全観点に由来する基本設計書の章、後者の全観点に由来する詳細設計書または入力資料の関数・メソッドが記録されている。対象関数が無い場合は、後者の§1と§2に根拠付きの「該当なし」が記入されている。

## Phase 5: 機械検査

## Step 5-1: 機械検査

**使用ツール**: Bash

次の 7 つを実行する。1 つでも不合格なら Phase 3 または Phase 4 へ戻る。上限 3 回で収束しなければ `status=ERROR` とする。

- **検査1 業務語彙の検査**: 生成した本文に実装用語が含まれないことを grep で確認する。検出対象はフレームワーク用語・型構文・`interface` の宣言・型注釈・原本の拡張子・内部の成果物名（`batch-manifest`・`unitId`・`unitKey`・`detectionMethod`）。検出 0 件で合格

  ```bash
  grep -nE 'interface [A-Z]|: *(string|number|boolean)\b|\bstyled-components\b|\bFastAPI\b|\bExpress\b|@app\.(get|post|put|delete)|\.(py|pl|pm|cgi|rb|go|java)\b|batch-manifest|unitId|unitKey|detectionMethod' <バッチ基本設計書.md>
  ```

- **検査2 注記の残存検査**: テンプレートの記入規則を書いた HTML コメント（`<!-- -->`）が残っていないことを確認する。残存 0 件で合格
- **検査3 frontmatter の検査**: `status` が `authored` になっていることを確認する
- **検査4 章の完備検査**: テンプレートが持つ全ての章見出しが出力に存在することを確認する
- **検査5 由来の記録検査**: バッチ結合テスト設計書の §1 テスト観点と §5 異常系の全行に由来する基本設計書の章が、バッチ単体テスト設計書の同じ行に由来する詳細設計書または入力資料の関数・メソッドが記録されていることを確認する。対象関数が無い場合は、後者の§1と§2に根拠付きの「該当なし」があることを確認する
- **検査6 情報源の検査**: バッチ結合テスト設計書の本文に基本設計書に現れない語が、バッチ単体テスト設計書の本文に詳細設計書または入力資料に現れない関数名・変数名が含まれていないことを確認する
- **検査7 配置の検査**: `bash generation-engine/scripts/scaffold-design-unit.sh --verify batch basic <output_dir> <識別子>` と `bash generation-engine/scripts/scaffold-design-unit.sh --verify batch test <output_dir> <識別子>` を実行し、設計書・バッチ結合テスト設計書・バッチ単体テスト設計書の必須ファイル・トークン・章・配置を確認する。続けて `bash <template_root>/rules/checkers/check-unit-test-design-doc-sections.sh --check-file <バッチ結合テスト設計書.md>` と `bash <template_root>/rules/checkers/check-unit-test-design-doc-sections.sh --check-file <バッチ単体テスト設計書.md>` を実行し、両文書の12見出しの名前・順序・件数がテンプレートと一致することを確認する

**完了**: 7 検査すべてが合格している

## 根拠の書き方

兄弟の詳細設計スキル（generating-batch-detail-design-for-reverse-docs）は本文に `file:line` の形で根拠を書くよう求めるが、本スキルではこれを禁止する。業務語彙の検査がファイルパスを検出するためである。根拠は本文に書かず、実行結果の報告へ記録する。この方針は generating-reverse-basic-design の「紐づけの確認は執筆者の自己点検で行い、本文に注記を書かない」という記述に従う。

## サブエージェント委任仕様

本スキルは子スキルを起動しない。原本読解と執筆（Phase 1〜3）は業務語彙の一貫性を保つため単一のメインエージェントが通しで担う。

## ループ設計

Phase 5（機械検査）で不合格が検出された場合、テスト設計書2点に関する検査の不合格は Phase 4 で書き直し、それ以外の検査の不合格は Phase 3 で書き直して Phase 5 を再実行する。

| 要素 | 内容 |
|---|---|
| 反復条件 | 7 検査のいずれかが 1 件でも不合格なら、該当箇所を書き直して Phase 5 を再実行する |
| 上限回数 | 3回 |
| 停止条件 | 収束停止: 7 検査すべて合格 ／ リソース上限: 3回到達（未収束の場合は `status=ERROR` として呼び出し元へ差し戻す） |

## 停止条件

| status | 意味 |
|---|---|
| `DONE` | 全対象ユニットのバッチ基本設計書・バッチ結合テスト設計書・バッチ単体テスト設計書が記入済みで、外部振る舞い用は基本設計書、単体用は詳細設計書または入力資料の関数・メソッドを根拠とし、対象関数が無い場合は根拠付きの「該当なし」を記入済み、かつ Phase 5 の 7 検査すべてに合格した |
| `ERROR` | 必須引数の欠落・マニフェスト不整合・出力先の識別子が確定しない・Phase 5 が上限 3 回で収束しない、のいずれかで著述不能 |

## 予想を裏切る挙動

- 実マニフェストでは `unitId` が全件空のことがある。その場合の出力先は `unitKey` 由来になるため、合成フィクスチャで確認した出力先と実データでの出力先が一致しないことがある
- 本スキルの業務語彙の検査は、詳細設計書と同様にファイルパス形式の文字列そのものを不合格の対象とする。対象コードの位置を本文へ書くと検査1で必ず差し戻される
- 本スキルの成果物は往復検証の対象外である。基本設計書だけからコードを再生成して原本と突き合わせる検証は行わない
