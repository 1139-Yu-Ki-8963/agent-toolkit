改善課題の登録と優先順位付けスキル
prioritizing-improvement-tasks-from-images

改善課題を写した画像を書き起こして台帳へ登録し、台帳に残る未解決の項目を全件調査して優先順位を振るスキルの確定仕様。

対応 OSWindows WSL2 環境
検証状況台帳突合の 3 コマンド（要確認リストの行番号の特定・履歴の検索・削除前本文の取得）を実データで確認済み。スキル全体の通し実行は未実施
依存transcribing-images スキル、git、grep
関連資料リポジトリルートの 改善課題タスク一覧.md（台帳）、.claude/rules/always/skill-guide/html/rule.md

§1概要

本スキルは、改善課題を写した画像を書き起こし、それが改善課題であれば台帳 改善課題タスク一覧.md へ登録する。登録後は台帳に残る未解決の項目を全件調査し、反映先の資産ごとにまとめて優先順位を振る。書き起こし自体は既存の transcribing-images スキルへ委任し、本スキルでは実装しない。

台帳の構造には手作業で踏み外しやすい点が 3 つある。第 1 に、末尾は ## 要確認リスト 以降が別セクションのため、末尾へ追記すると構造が崩れる。第 2 に、解消した項目は台帳から削除されるため採番が連続せず、次の番号を計算して振ると原本の採番と食い違う。第 3 に、キーが台帳に無いことは未登録を意味せず、削除された可能性を版管理の履歴で確かめる必要がある。本スキルはこの 3 点を手順として固定する。

── 処理の全体像 ──────────────────────────────

  改善課題を写した画像
       │  Phase 1  書き起こし（transcribing-images へ委任）
       ▼
  書き起こしテキスト
       │  Phase 2  分類と突合（改善課題か → キー確定 → 台帳の状態）
       ▼
       │  Phase 3  台帳への反映（要確認リストの直前へ挿入 / 再検証追記）
       ▼
  改善課題タスク一覧.md（更新）
       │  Phase 4  事実調査（未解決の項目を全件・証拠付き）
       │  Phase 5  グループ化（反映先資産の同一性で束ねる）
       │  Phase 6  優先順位（依存を制約とし処理量の小さい順）
       ▼
  改善課題優先順位.md（Phase 7・毎回上書き再生成）

§2出力

スキルを実行すると、以下の 2 点が生まれる。

改善課題タスク一覧.md への追記（リポジトリルート）
画像に写っていた改善課題が、台帳の既存項目と同じ 5 要素（題名・現象（実測事実）・修正内容・検収方法・完了条件）で記録される。挿入位置は最終項目の直後・要確認リストの直前で、原本の採番がそのまま見出しキーになる。画像から読み取れなかった要素は [画像に写っていないため未取得] と明示されるため、読んだ人は「まだ原本を確認する必要がある箇所」と「確定した記録」を区別できる。既に解消して削除された項目に再検証の記載があった場合は、履歴から削除前の本文が復元され、末尾に 再検証時の追加実測 が加わる。
改善課題優先順位.md（リポジトリルート・毎回上書き）
台帳に残る未解決の項目が、反映先の資産ごとのグループ節と、順位表の 2 部で並ぶ。順位表は順位・キー・題名・5 基準それぞれの判定値・依存関係を列に持つ。読んだ人は「どれから着手すれば手戻りが少ないか」と「その順位になった根拠」を同時に得られる。あわせて Phase 4 で得た実測値（反映先が実在するか、変更が必要なファイル数、検収を追加できる自己テスト分岐があるか）が記録されるため、順位を疑ったときに数え直せる。

§3用語

台帳
リポジトリルートの 改善課題タスク一覧.md。往復検証の実走で見つかった不具合を、画像からの原文ママの書き起こしとして記録した文書。解消して公開した項目は削除される。
見出しキー
台帳の各項目を識別する採番。1-156 のような形をとる。原本由来のため連続しない。本スキルは画像に写っている採番をそのまま使い、新たな採番を発明しない。
反映先
項目を直すために手を入れる対象。ファイル名・関数名・スクリプト名・スキル名のいずれかで台帳に記載される。グループ化と優先順位の判定はこの反映先を軸に行う。
自己テスト分岐
スクリプトが --self-test を受け取って処理を分ける実装。検収を安く追加できるかの判定に使う。文字列を含むだけで分岐を持たないスクリプトが実在するため、文字列検索では判定しない。

§5台帳突合の判定

キーごとに台帳の状態を 2 段で判定する。まず grep -n "^## <キー>\." <台帳> で本文を検索し、該当があれば「未対応で残存」とする。該当がなければ git log -S "## <キー>." -- <台帳> で履歴を検索し、登場があれば「解消済みで削除」、なければ「未登録」とする。

台帳の状態画像の記載処理
未登録—新規項目として挿入する
未対応で残存—何もしない。重複して追記しない
解消済みで削除再検証の記載あり履歴から削除前の本文を復元し、末尾に再検証の内容を追記する
解消済みで削除再検証の記載なし実在確認による調査だけを実施する。欠陥が残っていなければ削除した状態を維持し、残っていれば証拠を添えて復活の可否をユーザーに確認する

最後の行は、修正後の再検証が別の経路で完了しているとは判断しないという方針に基づく。この分岐で項目を自動では復活させない。

採番が読み取れない場合: 見出しの先頭に「数字-数字.」の形が写っていれば読み取れるとする。数字の一部が判読できない場合、この形が無い場合、候補が複数ある場合はいずれも読み取れないとし、推測で振らずユーザーに確認する。

§6優先順位の決定規則

依存の順序を制約とし、その中で処理量の小さい順に並べる。処理量だけを唯一の基準にすると、先行して直すべき項目が後ろへ落ちるためである。

基準内容役割
1他項目への依存がないこと。依存されている項目を先に置く順序の制約
2反映先のファイル数が少ない制約内での比較（第 1 キー）
3反映先に自己テスト分岐があり、そこへ検収を追加できる制約内での比較（第 2 キー）
4新規スクリプトの作成が不要制約内での比較（第 3 キー）
5反映先のスキル数が少ない制約内での比較（第 4 キー）

基準 2 から 5 は辞書式に比較する。すべて同値なら見出しキーの昇順で決める。基準の重み付けや合計点は使わない。

依存の判定

台帳には依存を明示するマークが存在しない。よって依存は 2 つの読み取りで判定する。第 1 に反映先の重複で、2 項目が同一のファイル・関数を反映先に挙げていれば同一グループとして扱う。第 2 に完了条件の前提で、完了条件または反映先の記述に他項目の反映先が名指しされていれば、その他項目を先行と判定する。名指しがなく、内容から関連しそうだという読み取りだけで依存を作らない。

循環依存を検出した場合: 2 項目以上が互いを先行と判定する状態を検出したら、順序を決めない。循環に含まれる項目のキーと判定根拠を添えてユーザーへ提示し、順序の指定を求める。循環を機械的に切って並べることはしない。
