# 改善課題の登録と優先順位付け

改善課題を写した画像を書き起こし、改善課題であれば台帳へ登録する。登録後は台帳に残る未解決の項目を全件調査し、反映先ごとにまとめて優先順位を振る。

## 起動引数

| 引数 | 必須 | 内容 | 既定値 |
|---|---|---|---|
| image_paths | 任意 | 書き起こす画像のパス | 未指定ならユーザー添付とアップロード配下を全件 |
| task_list_path | 任意 | 台帳のパス | リポジトリルートの `改善課題タスク一覧.md` |
| priority_output_path | 任意 | 優先順位の出力先 | リポジトリルートの `改善課題優先順位.md` |
| survey_depth | 任意 | `existence`（反映先の実在を確認）／ `reproduce`（該当スクリプトを走らせて再現） | `existence` |

## 台帳の構造

反映の前に、台帳が次の構造を持つことを前提とする。

- 冒頭に採番の方針を述べた注記がある
- 各項目は `## <キー>. <題名>` の見出しで始まる
- 続く 4 要素はいずれも `**<要素名>**: <本文>` の太字ラベル付き段落
- 4 要素の順序は 現象（実測事実）・修正内容・検収方法・完了条件 で固定
- 再検証を経た項目は 4 要素の後ろに `**再検証時の追加実測**` を持つ
- 項目と項目の間は `---` の区切り線で隔てる
- 最終項目の後ろは `## 要確認リスト` 以降の別セクション
- 解消して公開した項目は台帳から削除する。よって採番は連続しない

## Phase 1: 書き起こし

`transcribing-images` スキルへ委任する。原文ママの転記、数値と固有名詞の再照合、要確認リストの作成はそちらの責務であり、本スキルでは実装しない。

`image_paths` を渡し、書き起こし結果を画像 1 枚ごとに保持する。

**完了**: 対象画像の全件について書き起こし結果が得られている。

## Phase 2: 分類と突合

### Step 2-1: 改善課題かどうかの判定

書き起こし 1 件ごとに、次の 2 条件をどちらも満たすかを見る。

1. このリポジトリの資産の欠陥または欠落を述べている。資産とはスキル定義・スクリプト・テンプレート・規約を指す
2. 反映先の候補をファイル名・スキル名・関数名のいずれかで特定できる

この判定は書き起こしテキストを読んだ上での判断である。正規表現やコマンドによる機械判定の手順は定めない。

どちらかを満たさない場合、および判定に迷う場合は改善課題として扱わない。書き起こし結果をユーザーへ報告し、台帳には触れずに停止する。

**完了**: 書き起こし 1 件ごとに改善課題か否かが判定されている。

### Step 2-2: 見出しキーの確定

見出しキーは画像に写っている採番をそのまま使う。台帳の採番は原本由来のため、新たな採番を発明しない。次の番号を計算して振ってはならない。

読み取れるかどうかは次で判定する。見出しの先頭に `<数字>-<数字>.` の形が写っていれば読み取れるとする。数字の一部が判読できない場合、この形が無い場合、候補が複数ある場合はいずれも読み取れないとする。

読み取れない場合は推測で振らない。書き起こし結果と、採番が読み取れない旨を提示し、`AskUserQuestion` でキーをユーザーに確認する。

**完了**: 改善課題と判定した全件について見出しキーが確定している。

### Step 2-3: 台帳との突合

キーごとに台帳の状態を判定する。手順は 2 段である。

1. `grep -n "^## <キー>\." <task_list_path>` で台帳の本文を検索する。該当があれば「未対応で残存」とする
2. 該当がなければ `git log -S "## <キー>." -- <task_list_path>` で履歴を検索する。登場があれば「解消済みで削除」、なければ「未登録」とする

判定結果と画像の記載内容から処理を決める。

| 台帳の状態 | 画像の記載 | 処理 |
|---|---|---|
| 未登録 | — | 新規項目として挿入する |
| 未対応で残存 | — | 何もしない。重複して追記しない |
| 解消済みで削除 | 再検証の記載あり | 項目を復活させ、再検証の内容を追記する |
| 解消済みで削除 | 再検証の記載なし | 実在確認による調査だけを実施する。詳細は Step 2-4 |

**完了**: 全キーについて台帳の状態と処理が確定している。

### Step 2-4: 解消済み項目の再調査

「解消済みで削除」かつ画像に再検証の記載がない場合、既定の `existence` のまま判定する。この分岐で再現実行へ切り替えない。判定は 2 段である。

1. 画像が述べる現象の記述と、現在の実装を突合する
2. 記述どおりの欠陥が現在の実装に残っていなければ削除した状態を維持する

欠陥が残っていた場合は、突合した箇所を証拠として添えてユーザーへ復活の可否を確認する。この分岐で項目を自動では復活させない。修正後の再検証が別の経路で完了しているとは判断しない。

**完了**: 当該分岐の全キーについて、削除の維持か復活の確認かが決まっている。

## Phase 3: 台帳への反映

### Step 3-1: 新規項目の挿入

挿入位置は末尾ではない。台帳の末尾は要確認リストと原本捜索の記録という別セクションのため、末尾へ足すと構造が崩れる。

1. `grep -n "^## 要確認リスト" <task_list_path>` で境界の行番号を得る
2. その直前にある最終項目の後ろへ、区切り線とともに挿入する
3. 台帳に項目が 1 件も無い場合は、境界の直前にある区切り線の前へ挿入する
4. 形式は台帳の既存項目と同じ 5 要素を守る
5. 画像から取得できなかった要素は `[画像に写っていないため未取得]` と明示する。推測で補わない

未取得の要素が残った項目も、有効な改善課題として扱う。未取得を理由に項目を保留しない。原本または撮影範囲の広い画像が入手できた時点で、当該箇所を原文で置き換える。

### Step 3-2: 再検証の追記と復活

「解消済みで削除」かつ画像に再検証の記載がある場合は、項目を復活させる。

1. `git log -S "## <キー>." -- <task_list_path>` で削除コミットを特定する
2. `git show <削除コミット>^:<task_list_path>` で削除前の全文を取得する
3. 5 要素をそのまま復元し、Step 3-1 と同じ位置へ挿入する
4. 末尾に `**再検証時の追加実測**` を追記し、画像の再検証内容を原文ママで書く

履歴に本文が残っていない場合は復元しない。その旨を添えて、画像の内容だけで新規項目として挿入する。

台帳に残存する項目へ再検証を追記する場合も、同じ見出し名で当該項目の末尾へ足す。

**完了**: 処理対象の全キーが台帳へ反映され、項目群と要確認リストの順序が保たれている。

## Phase 4: 事実調査

対象は今回の追記分だけではない。台帳に残る未解決の項目を全件とする。一部だけを並べても順序付けの意味がないためである。

未解決の項目が 0 件の場合は Phase 4 から Phase 6 を実行しない。台帳の変更内容だけを報告し、未解決が 0 件である旨を添えて完了とする。この場合 `priority_output_path` は生成しない。

調査は読み取り専用の調査担当へ委任する。項目ごとに次を収集する。

| 収集項目 | 内容 |
|---|---|
| 反映先の実在 | 項目が名指しするファイル・関数・スクリプトが実在するか |
| 現象との突合 | 現象の記述と実装が一致するか。既に解消していないか |
| 依存関係 | 他項目と同じ反映先を触るか。前提となる項目があるか |
| 反映先の数 | 変更が必要なファイルの数 |
| 検収の受け皿 | 反映先のスクリプトに自己テスト分岐があるか |
| 新規作成の要否 | 新しいスクリプトの作成が必要か |

`survey_depth` が `reproduce` の場合のみ、該当スクリプトを実行して現象の再現まで確認する。実行はリポジトリルートを作業ディレクトリとして行う。実行が失敗した場合は、失敗した事実と終了コードを記録し、当該項目の調査結果は `existence` の内容で代替する。失敗を現象の再現とみなさない。

委任の前に `subagent-investigation-checklist` スキルで調査チェックリストを作り、その全文を prompt へ埋め込む。調査担当の報告は、報告判定へ渡して事実性を検証してから採用する。証拠のない記述は採用しない。

**完了**: 台帳に残る未解決の項目の全件について、上表 6 項目が証拠付きで揃っている。

## Phase 5: グループ化

反映先資産の同一性で束ねる。同じスクリプト、同じテンプレート、同じスキル定義を触る項目を 1 グループとする。

- グループ名は反映先の資産名とする。連番を振らない
- 1 項目だけのグループも作る。無理に他へ寄せない
- 複数の資産にまたがる項目は、変更量が最も大きい資産のグループへ入れ、他の資産名を併記する
- 同じ項目を複数のグループへ重複して載せない

**完了**: 未解決の全項目がいずれか 1 グループに属し、グループ名が反映先の資産名になっている。

## Phase 6: 優先順位

依存の順序を制約とし、その中で処理量の小さい順に並べる。処理量だけを唯一の基準にすると、先行して直すべき項目が後ろへ落ちるためである。

1. 他項目への依存がないこと。依存されている項目を先に置く
2. 反映先のファイル数が少ない
3. 反映先のスクリプトに自己テスト分岐があり、そこへ検収を追加できる
4. 新規スクリプトの作成が不要
5. 反映先のスキル数が少ない

1 が順序の制約である。2 から 5 は同じ制約内での並べ替えに使い、辞書式に比較する。まず 2 で比較し、同値なら 3、さらに同値なら 4、さらに同値なら 5 で比較する。すべて同値なら見出しキーの昇順で決める。基準の重み付けや合計点は使わない。判定の根拠は項目ごとに記録する。

### 依存の判定基準

台帳には依存を明示するマークが存在しない。よって依存は次の 2 つの読み取りで判定する。

1. 反映先の重複。2 項目が同一のファイル・関数を反映先に挙げている場合、同一グループとして扱い、変更が競合しうる旨を記録する
2. 完了条件の前提。項目の完了条件または反映先の記述に、他項目の反映先が名指しされている場合、その他項目を先行と判定する

名指しがなく、内容から関連しそうだという読み取りだけで依存を作らない。いずれにも当たらなければ依存なしとする。

### 循環依存を検出した場合

2 項目以上が互いを先行と判定する状態を検出した場合、順序を決めない。循環に含まれる項目のキーと、循環と判定した根拠を添えてユーザーへ提示し、順序の指定を求める。循環を機械的に切って並べることはしない。

### 自己テスト分岐の判定

基準 3 は `--self-test` という文字列の有無では判定しない。文字列を含みながら分岐を持たないスクリプトが実在する。

この事実は台帳の履歴に記録がある。解消済みの項目 1-156 は `render-template.sh` と `shell-injection.sh` について、いずれも自己テスト分岐を持たず引数が無視されると述べていた。台帳から削除済みの項目のため、現在の本文には無い。

判定は反映先のスクリプトそれぞれについて、`--self-test` を受け取って処理を分岐する実装があるかを本文で確認して行う。分岐を持つものが 1 つ以上あれば受け皿ありとする。1 つも無ければ受け皿なしとし、新しいテストの土台が必要な項目として順位を下げる。

**完了**: 未解決の全項目に順位が付き、各順位に上記 5 基準での判定根拠が添えられている。

## Phase 7: 成果物の提示

`priority_output_path` へ優先順位の一覧を書き出す。形式は Markdown とする。JSON や HTML では出力しない。既存ファイルがある場合は追記せず、毎回上書きして再生成する。

構成は次の 2 部とする。

1. グループ節。反映先資産の名前を見出しとし、属する項目のキーと題名を列挙する
2. 順位表。順位・キー・題名・5 基準それぞれの判定値・依存関係を列に持つ表

あわせて Phase 4 で得た実測値を記録する。反映先の実在、反映先のファイル数、検収の受け皿がその対象である。

台帳は原文ママの記録として保つ。分析で得た記述を台帳へ混ぜない。

**完了**: 優先順位の一覧が出力され、台帳の変更内容とあわせてユーザーへ提示済み。

## サブエージェント委任仕様

Claude Code は `Claude agent` 列を `Agent(subagent_type: ...)` に渡す。Codex は `Codex agent` 列の定義を全文読み、定義の `model`・`reasoning_effort`・本文と共通 prompt を `spawn_agent` に渡す。prompt 骨格と期待返却値は両ランタイムで共通とし、モデル値をこの定義へ重複記載しない。

| 呼び出し箇所 | 役割 | Claude agent | Codex agent | prompt 骨格 | 期待返却値 |
|---|---|---|---|---|---|
| Phase 4 調査 | 事実確認 | investigator | investigator-terra | 台帳のパス・対象キーの一覧・収集 6 項目・調査チェックリスト全文・変更禁止・出力形式と行数上限 | キーごとの収集 6 項目と、各項目の根拠パス |
| Phase 4 検証 | 報告判定 | report-reviewer | report-reviewer-sol | 調査チェックリスト全文・調査担当の報告全文・事実性の検証観点 | PASS / FAIL と、根拠が欠けた項目の指摘 |
| Phase 3・7 反映 | ファイル反映 | worker-sonnet | worker-terra | 確定済みの挿入位置と本文・対象ファイルのパス・範囲外変更の禁止・完了条件 | 変更結果と、変更した行番号 |

## ループ設計

| 要素 | 内容 |
|---|---|
| 反復条件 | Phase 4 の報告判定が FAIL を返したら、指摘された項目の証拠を集め直して再検証する |
| 上限回数 | 5 回 |
| 停止条件 | 下記 3 パターンのうち 2 つ以上で停止する |

- 収束停止: 報告判定が 2 回連続で PASS
- リソース上限: 反復が 5 回に到達
- 発散検知: 同じ指摘が 2 回連続で再発

調査担当と報告判定は別のエージェントに分ける。調査担当に自身の報告を検証させない。

## 予想を裏切る挙動

- 台帳への反映は末尾追記ではない。末尾は要確認リストと原本捜索の記録であり、そこへ足すと構造が崩れる
- 見出しキーは画像に写っている採番をそのまま使う。台帳の採番は連続しないため、次の番号を計算して振ってはならない
- キーが台帳に見つからないことは未登録を意味しない。解消して削除された可能性があるため、必ず版管理の履歴を引く
- 台帳に残存する項目と同一内容の画像は追記しない。重複した項目が並ぶ状態を作らない
- 優先順位の対象は今回の追記分ではなく、台帳に残る未解決の全項目である
- 自己テスト分岐の有無は文字列検索では判定できない。`--self-test` を含みながら分岐を持たないスクリプトが実在する
- 優先順位の出力先はリポジトリのルート直下である。ルート直下への新規ファイル作成はグローバルの配置規約に触れるが、本スキルではユーザーの指示に従いルート直下へ置く

## 完了報告

共通骨格（作業報告型）に従う。骨格の定義は次のファイルである。

- `~/agent-home/skills/managing-agent-configs/references/skills/completion-report-format.md`

固有の検証行は 6 点である。

書き起こした画像の枚数、改善課題と判定した件数、台帳への新規挿入・再検証追記・処理なしの各件数。調査した未解決の項目数、グループ数、報告判定の収束回数。
