規約提案の書き出し
generating-rule-proposals-for-reverse-docs

対象リポジトリのコードを調査し、観測した実装慣行を規約提案HTMLとしてリポジトリ外へ出力するスキルの確定仕様。

こんな人向け
対象リポジトリに規約が整備されていない、または実態と規約の乖離を疑っている人 ／ 実装慣行から規約の叩き台を起こし、現場の判定に委ねたい人
こんな場面で使う
アーキテクチャ調査書が確定済みで、次に規約整備の材料を集めたい時 ／ 規約提案の観測範囲と根拠を機械検証付きの成果物として残したい時

検証状況 エンジンスクリプト（build-rule-proposal.sh）はself-testと手動スモークテストでの動作確認済み。スキル単体の実機検証は未実施

§1概要

対象リポジトリに規約が無い、または規約と実態が食い違っている状態は珍しくない。本スキルは対象コードを調査し、観測できた実装慣行を規約提案HTMLとして作る係である。規約そのものを確定させる工程ではない。提案を読んだ現場のエンジニアが、カテゴリごとに採用・保留・却下を判定するための叩き台を作る。

出力先はリポジトリ外に固定する。提案は観測であって規範ではないため、リポジトリの中に置くと確定済みの規約と見分けがつかなくなる。output_path がリポジトリ内を指す場合、本スキルは生成せず停止する。

── 処理の全体像 ──────────────────────────────

  アーキテクチャ調査書.md（調査範囲の前提）
       │  Phase 1  target_repo_path・survey_doc_path の実在確認 + output_pathの範囲確認
       ▼
  対象リポジトリのコード
       │  Phase 2  親7・子27の構成を当て、カテゴリごとにstateを判定
       ▼
  state=proposal / proposal-limited のカテゴリ
       │  Phase 3  実測値を伴う観測の収集（件数・パス・行番号）
       ▼
  観測済みカテゴリ
       │  Phase 4  proposedRule・検査条件（scope/paths/enforcement/checkable/checkMethod）の起草
       ▼
  入力JSON
       │  Phase 5  build-rule-proposal.sh による決定的生成 + 静的検査
       ▼
  <output_path>/規約提案HTML（リポジトリ外）

本スキルは規約の採否を判定しない。判定は現場のエンジニアが提案HTML上の採用・保留・却下ボタンで行う。

§2出力

スキルを実行すると、以下の2点が生まれる。

規約提案HTML（<output_path>）
親7・子27カテゴリごとに、観測・根拠・提案文・検査条件を並べ、採用・保留・却下の判定ボタンと進捗表示を備えたページ。材料が無いカテゴリは判定ボタンを出さず、対象外の理由だけを示す。読んだ人はカテゴリを1つずつ判定しながら、判定結果をJSONとして書き出せる。
カテゴリ別の状態内訳
27カテゴリが proposal・proposal-limited・na・common のどれに分類されたかの内訳。材料の有無を隠さずに示すため、提案できたカテゴリだけでなく「観測できなかった」事実も成果物に残る。

output_path が対象リポジトリ内を指す場合、本スキルは生成を行わず停止する。この場合、規約提案HTMLは生まれない。

§3用語

state
カテゴリごとの判定状態。値域は proposal（提案あり）・proposal-limited（提案あり・範囲限定）・na（対象外）・common（共通規約を参照）の4つ。
proposedRule
観測を規範の文へ変えた規約提案文。state が proposal か proposal-limited のカテゴリだけが持つ。
checkable / checkMethod
checkable は静的解析で判定できるかの真偽値。true のとき checkMethod に検査方法を自然文で書く。判定できないものを true にすると、取り込みスキルが動かない検査を作ることになる。

§4動作フロー

起動引数は target_repo_path・output_path・survey_doc_path（必須）と proposal_id（任意）の4つ。

Phase 内容 完了条件
Phase 1
前提の確認		 対象リポジトリ・調査書の実在確認、output_path がリポジトリ外を指すことの確認 3項目すべて確認済み、または不備を報告して停止
Phase 2
章とカテゴリの決定		 親7・子27の構成を対象へ当て、カテゴリごとに材料の有無から state を判定 27カテゴリ全件に state が確定済み
Phase 3
観測の収集		 proposal・proposal-limited のカテゴリについて、件数・パス・行番号付きの観測を収集 対象カテゴリ全件に根拠付きの観測が付与済み
Phase 4
提案文と検査方法の起草		 proposedRule と scope・paths・enforcement・checkable・checkMethod を確定 対象カテゴリ全件に6項目が確定済み
Phase 5
生成と検査		 入力JSONを組み立て build-rule-proposal.sh を実行。生成後の静的検査を通過 提案HTMLが生成され静的検査を通過（不在時は警告を確認）

エンジンスクリプトはスキルフォルダ相対 ../../../generation-engine/scripts/rule-proposal/ で参照する。

返却（呼び出し元との契約）

キー 内容
status DONE | STOPPED（前提不備・出力先違反）| ERROR
output_path 生成した提案HTMLのパス（STOPPED/ERROR 時は空）
total 判定対象の件数（state が proposal または proposal-limited のカテゴリ数）
proposalCounts state 別の内訳（4値それぞれの件数）

§5制約と禁止事項

手作業でのプレースホルダ置換は禁止。 規約提案HTMLは必ず build-rule-proposal.sh 経由の決定的処理で生成する。
出力先はリポジトリ外に固定。 output_path が対象リポジトリ内を指す場合、生成せず停止する。既定値は持たない。
規約の確定は対象外。 本スキルの仕事は観測と提案文の起草までであり、採否の判定は現場のエンジニアが行う。

起草時の落とし穴

落とし穴 対処
材料が薄いカテゴリを proposal にしてしまう na として理由を書く。材料の不在を書けることが工程の質である
判定できない検査方法に checkable: true を付ける 静的解析で判定できる場合だけ true にする。判定できないものを true にすると取り込み側が動かない検査を作ることになる
enforcement に block を選んでしまう 値域は advisory と none の2つのみ。block は選べない
observations[] へ任意のHTMLを混入させる observations[] と crossFindings[].body は生HTMLとしてそのまま出力される（proposedRule・reason・checkMethod はエスケープされる）。この非対称を踏まえ、観測文は事実の記述に留める
