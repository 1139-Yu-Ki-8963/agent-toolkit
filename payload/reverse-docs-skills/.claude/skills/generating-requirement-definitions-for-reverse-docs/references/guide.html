§1概要

要件定義の5文書（機能要件一覧・帳票要件・バッチ要件・外部連携要件・ビジネス概要）は、業務の目的や利用者像を扱う文書でありながら、対象コードそのものには現れない。本スキルは対象コードを一切読まず、既に生成済みの一覧マニフェストと個別基本設計書、つまり他スキルの成果物だけを情報源として、観測できる事実と業務の意図を分離しながら5文書を組み立てる。

本スキルは orchestrating-ai-development-setup の統括フローへは結線されておらず、単独起動でのみ動く。起動引数を渡せば動く。

本スキルがやること
一覧マニフェストと個別基本設計書からの観測事実の記入、業務の意図の要確認事項一覧への分離、要件定義5文書の生成と機械検査
本スキルがやらないこと
個別ユニットの基本設計書・詳細設計書の生成（各 generating-*-basic-design-for-reverse-docs / generating-*-detail-design-for-reverse-docs の担当） ／ 一覧マニフェスト自体の生成（各 generating-*-list-for-reverse-docs の担当） ／ 対象コード・原本ファイルパス・関数名・変数名の参照 ／ 業務の意図の推測や一般的な内容での補完

起動引数

引数 内容
output_dir 納品物ルートの絶対パス。一覧マニフェスト・個別基本設計書・出力先は、それぞれ output-layout.json の物理配置キーから解決する
template_root <template_root>/リバース検証/プロジェクト共通/ の要件定義5文書を雛形に使う
target_docs 任意。既定は5件すべて。functional-requirements／report-requirements／batch-requirements／external-requirements／business-overview の doc_id で絞り込む

本スキルはユーザーに直接確認しない（AskUserQuestion 不使用）。単独起動時は起動引数をユーザーから直接取得する。

§2出力

対象リポジトリ1つにつき、次の最大5点が生まれる。target_docs で絞り込める。個別基本設計書が未生成のユニットがある場合、該当する観測列は空欄のまま残る。

機能要件一覧.md
機能一覧マニフェストの各ユニットについて、キー・機能名・大分類・構成要素数（関連画面・API・テーブルの合計）・個別設計書の参照を記す。満たすべき要件という業務の意図は §3 要確認事項一覧へ回す
帳票要件.md
帳票一覧マニフェストと、実在する個別基本設計書の該当章（出力の条件と契機・レイアウトの要件）から、観測できる事実だけを記す
バッチ要件.md
バッチ一覧マニフェストと、実在する個別基本設計書の該当章（起動の契機と実行の周期・異常時の復旧の方針）から、観測できる事実だけを記す
外部連携要件.md
外部連携一覧マニフェストと、実在する個別基本設計書の該当章（連携先と方式・正常応答と異常応答・タイムアウトとリトライと冪等性）から、観測できる事実だけを記す
ビジネス概要.md
機能・画面・API・テーブル・バッチ・帳票・外部連携の7種別それぞれの件数、またはマニフェストも該当なし記録も無い種別は「対象外（入力なし）」を記す

生成された文書は <output_dir>/<commonRoot>/<ファイル名>（既定値 docs/design/common）に置かれる。「入力なし」と判定された文書は生成されない。

§3用語

マニフェスト
一覧生成エンジンが読む JSON。定義書や画面等の記述を機械が扱える形へ写したもの。種別ごとに <kind>-manifest.json または <kind>-manifest.ext.json として置かれる

§4動作フロー（Phase 1〜4）

Phase 内容
Phase 1 起動引数の確認と対象文書の確定 output_dir・template_root の実在を確認する。要件定義5文書のテンプレートの実在を確認する。target_docs から対象文書の doc_id 集合を確定する
Phase 2 入力の特定 機能・帳票・バッチ・外部連携要件は一覧マニフェストの入力状態（マニフェスト有／該当なし／入力なし）を判定する。帳票・バッチ・外部連携要件は個別基本設計書の有無を確認し、実在すれば該当章を読む。ビジネス概要は7種別の件数または「対象外（入力なし）」を確定する
Phase 3 執筆 テンプレートを出力先へ配置する。§2 の観測事実を記入する。§3 要確認事項一覧へ業務の意図と空欄理由を記入する。§2 に空欄が無ければ frontmatter の status を draft から traced へ更新する
Phase 4 機械検査（機械実行） 6つの検査を実行する。1つでも不合格なら Phase 3 へ差し戻す。上限3回で収束しなければ status=ERROR とする

§5守り（禁止事項と機械検証）

禁止事項

  • 対象コード・原本ファイルパス・関数名・変数名を読まない
  • 業務の意図を推測や一般的な内容で補完しない。埋まらない欄は常に §3 要確認事項一覧へ回す
  • 個別ユニットの基本設計書・詳細設計書そのものを生成しない（各設計書生成スキルの担当）
  • 一覧マニフェスト自体を生成しない（各一覧生成スキルの担当）

機械検証

Phase 4 で次の6検査を実行する。1つでも不合格なら Phase 3 へ戻り、上限3回で収束しなければ status=ERROR とする。

検査 内容
検査1 業務語彙 本文に実装用語・内部成果物名（型構文・フレームワーク用語・原本の拡張子・unitId・unitKey・detectionMethod・sourceFile・unitNameGuess・manifest.ext.json 等）が無いことを grep で確認する
検査2 注記の残存 テンプレートの記入規則を書いた HTML コメント（<!-- -->）が残っていないことを確認する
検査3 frontmatter status が draft または traced のいずれかであり、Step 3-4 の判定結果と一致していることを確認する
検査4 章の完備 テンプレートが持つ全ての章見出し（§1〜§3）が出力に存在することを確認する
検査5 §3行数 機能・帳票・バッチ・外部連携要件は §3 の行数が対象ユニット数以上であることを確認する。ビジネス概要は事業概要・システム役割・対象利用者の3キーの残存を確認する
検査6 配置 対象文書が <output_dir>/<commonRoot>/<ファイル名> に実在することを確認する
