§1概要

画面・API・機能の設計単位ごとに、確定済みfactsまたは設計文書の順序表をシーケンス図へ変換する。画面はfactsのcall_order、APIはAPI詳細設計書§4.1、機能は機能設計書§3.1を順序の定義元とする。

テーブル・バッチ・帳票・外部連携・メッセージは順序表を持たないため生成しない。一覧マニフェストからsequencePathを省き、空欄や未作成表示も出さない。

§2出力

本スキルを実行すると、順序を導ける対象単位ごとに以下の成果物が生まれる。

シーケンス図.html
screenはscreenViewRoot/screen-<ID>へ生成する。 api・featureは各UnitRootの<unit-dir>へ生成する。 unit-dirは安全なunitIdを優先し、不正値なら停止する。 unitIdが空なら、検証済みのunitKeyを無変換で種別prefixへ連結する。 HTMLの実在確認後だけ一覧マニフェストへsequencePathを設定する。

§3使用タイミング

区分 内容
前提 screenのfacts.yml、API詳細設計書§4.1、機能設計書§3.1、または手書きpage-dataのいずれかに順序が明示されていること
起動引数 output_dir・対象種別（screen/api/feature）・対象ユニットID（複数可）
対象外 table・batch・report・external・message。references/sequence-kind-policy.jsonを本スキル内の生成可否定義とする

§4用語・page-data の形状

各設計単位のpage-dataはunitKind・unitId・unitLabelを共通キーに持つ。既存画面のscreenId・screenLabelも後方互換で受け入れる。

── シーケンス図-data.json の形状 ─────────────────────────
{
  "unitKind": "screen",
  "unitId": "screen-order-list",
  "unitKey": "order-list",
  "unitLabel": "注文一覧",
  "screenId": "screen-order-list",
  "screenLabel": "注文一覧",
  "generatedAt": "ISO8601",
  "lanes": [
    {"key": "user", "label": "利用者"},
    {"key": "screen", "label": "画面"},
    {"key": "api", "label": "API"},
    {"key": "table", "label": "テーブル"}
  ],
  "operations": [
    {
      "key": "save-click",
      "label": "保存ボタン押下",
      "handler": "handler-onSave-保存",
      "lanes": [
        {"key": "user", "label": "利用者"},
        {"key": "screen", "label": "画面"},
        {"key": "api", "label": "API"},
        {"key": "table", "label": "テーブル"}
      ],
      "steps": [
        {"seq": 1, "from": "user", "to": "screen", "label": "操作開始", "kind": "trigger"},
        {"seq": 2, "from": "screen", "to": "api", "label": "注文登録", "sourceRef": "src/screens/Order.tsx:42"},
        {"seq": 3, "from": "api", "to": "table", "label": "注文レコード登録", "sourceRef": "server/orders.ts:10"},
        {"seq": 4, "from": "api", "to": "screen", "label": "登録完了 → 一覧再取得", "kind": "return", "sourceRef": "src/screens/Order.tsx:42"}
      ]
    }
  ]
}
用語 内容
レーン（ライフライン） operation.lanes、page-data直下のlanes、固定4本（user=利用者 / screen=画面 / api=API / table=テーブル）の順で採用する。page-data直下の定義は後方互換fallback
kind: "trigger" 各operationの開始step。screenは利用者→画面の「操作開始」、apiはcaller→apiの合成stepで、どちらもsourceRefを持たない。featureはuser→最初の構成要素とし、§3.1の表行をsourceRefに持つ
ステップ表示文言 呼び出し先の業務名（原本の日本語コメント、または関数名・BL 名から導出）。代入式・引数・分類タグは含めない。導出できない場合は識別子のみを使い、根拠のない機能名は作らない
kind: "return" 破線で描画されるステップ。省略時は実線
sourceRef screenの合成triggerを除くfacts由来step、apiの合成triggerを除く設計書由来step、およびfeatureの全stepで省略しない。設計書由来は相対pathと節・表行を記録する。手書きpage-dataで根拠が無い場合のみ省略可
sourceRef境界 「操作開始」を除くstepに存在するsourceRefを行番号除去して正規化する。一意パス数が1ならAPI endpointをinternalへ機械置換し「内部処理」レーンを使う。複数ならAPI endpointとレーンを維持する。0なら単一判定を適用せず、手書きpage-data等の既存endpointを変換しない
call_order facts.yml の⑤handler item が持つ任意フィールド。形式 "<連番>:<api分類のkey>@<file:line>; ..."。delivery-payload/references/facts-schema.md が定義元
1 operation あたりの分割上限 1 handler の call_order が 15 ステップを超える場合、機能単位・コメント区切り・15 ステップ機械区切りの優先順で複数 operations[] へ分割する。分割後のキーは連番禁止で内容要約語とする

§5Phase 手順

スキル開始時に TaskCreate で Phase 1〜3 のタスクを登録する。各 Phase 開始時に該当タスクを in_progress に、完了時に completed へ TaskUpdate で更新する。

Phase 内容 完了条件
1. page-data の確保 policyで対象種別を判定し、screenはcall_order、apiは§4.1、featureは§3.1を順番どおり変換する 順序を導ける単位のjq検証が通過し、導けない単位は生成省略済み
2. DOC_NAV の組み立て 各種別の一覧への戻るリンクと、実在する設計書項目だけを組み立てる 対象単位ごとにdoc_navが確定済み
3. HTML・一覧反映 api・featureは各UnitRootのunit-dir直下へ生成する。unit-dirはunitIdをそのまま使い、空なら種別prefix＋unitKeyとする。一覧HTMLの親からの相対pathをrawマニフェストへ設定し、派生マニフェストと一覧を再生成する。非対象種別はキーを削除する 生成対象のリンクが現れ、非対象種別にはシーケンス図欄がない

手作業でのプレースホルダ置換（sed・perl 直書き等）は禁止する。render_template は最短前方一致で置換するため、値の中に他プレースホルダ文字列が偶然含まれても誤爆しない。新規 .sh スクリプトファイルは作らない。

§6重要な注意事項・予想を裏切る挙動

順序を推測しない。APIは§4.1、機能は§3.1以外の節から順序を補わない。表が空・プレースホルダのみ・順番号不正なら生成しない。非対象種別へ空の図や「未作成」欄を作らない。
予想を裏切る挙動 内容
出力先の階層 screenはscreenViewRoot、api・featureは各UnitRootの設計単位ディレクトリへ出す。pageKind体系は適用しない
DOC_NAV の担当分担 build-portal.sh は画面設計書（基本設計・詳細設計）側の DOC_NAV にのみシーケンス図項目を追加する。シーケンス図.html 自体の DOC_NAV は本スキルの Phase 2/3 が組み立てる（build-portal.sh の担当範囲外）
