§1概要

画面ごとの操作（ボタン押下・フォーム送信等）を選ぶと、利用者→画面→API／内部処理→テーブル の呼び出し順序を表示するシーケンス図を生成する。物理配置は output-layout の layout.screenUnitRoot から解決し、表示用 kindLabels.screen はpathに使わない。本スキルは pageKind 体系（用語辞書・技術スタック・画面遷移図・ER図・環境構築手順・状態遷移図）には属さない。1 pageKind = 1 固定ファイル名という pageKind 契約に対し、シーケンス図は画面ごとに複数生成される画面別ページであり、出力先も <screenUnitRoot>/screen-<ID>/ 配下に画面ごとに存在するため、shared/scripts/detail-pages/ の共通エンジン（validate-page-data.sh / build-detail-page.sh）は使わない。

判定・評価はしない。呼び出し順序や処理内容の良否には踏み込まず、facts（call_order）または手書き page-data に記録された事実のみを転記する。

§2出力

本スキルを実行すると、対象画面 1 つにつき以下の 1 点が生まれる。

シーケンス図.html
<output_dir>/<screenUnitRoot>/screen-<ID>/ 直下に固定生成される、当該画面の操作単位（ボタン押下・フォーム送信等）を階層サイドバーから切り替えられるシーケンス図ページ。操作ごとのoperation.lanesを優先し、利用者起点とfactsの呼び出し順序を表示する。全根拠が同一ファイルならAPIレーンを内部処理へ機械置換し、画面基本設計書・詳細設計書と同じ体裁の左サイドバーを持つ。

§3使用タイミング

区分内容
前提対象画面の facts.yml（extracting-unit-facts-from-code が確定済み）または手書きの page-data がある画面について、シーケンス図を生成・更新したいとき
起動引数output_dir（<screenUnitRoot>/screen-<ID>/ の所在）・対象画面 ID（複数可）
出力先各画面ディレクトリ直下の <output_dir>/<screenUnitRoot>/screen-<ID>/シーケンス図.html に固定（build-portal.sh の DOC_NAV 判定と同値。基本設計・詳細設計フォルダの 1 階層上）

§4用語・page-data の形状

各画面の page-data（<output_dir>/<screenUnitRoot>/screen-<ID>/シーケンス図-data.json）は以下の形状を持つ。

── シーケンス図-data.json の形状 ─────────────────────────
{
  "screenId": "screen-order-list",
  "screenLabel": "注文一覧",
  "generatedAt": "ISO8601",
  "lanes": [
    {"key": "user", "label": "利用者"},
    {"key": "screen", "label": "画面"},
    {"key": "api", "label": "API"},
    {"key": "table", "label": "テーブル"}
  ],
  "operations": [
    {
      "key": "save-click",
      "label": "保存ボタン押下",
      "handler": "handler-onSave-保存",
      "lanes": [
        {"key": "user", "label": "利用者"},
        {"key": "screen", "label": "画面"},
        {"key": "api", "label": "API"},
        {"key": "table", "label": "テーブル"}
      ],
      "steps": [
        {"seq": 1, "from": "user", "to": "screen", "label": "操作開始", "kind": "trigger"},
        {"seq": 2, "from": "screen", "to": "api", "label": "注文登録", "sourceRef": "src/screens/Order.tsx:42"},
        {"seq": 3, "from": "api", "to": "table", "label": "注文レコード登録", "sourceRef": "server/orders.ts:10"},
        {"seq": 4, "from": "api", "to": "screen", "label": "登録完了 → 一覧再取得", "kind": "return", "sourceRef": "src/screens/Order.tsx:42"}
      ]
    }
  ]
}
用語内容
レーン（ライフライン）operation.lanes、page-data直下のlanes、固定4本（user=利用者 / screen=画面 / api=API / table=テーブル）の順で採用する。page-data直下の定義は後方互換fallback
kind: "trigger"各operation先頭の利用者→画面「操作開始」。call_orderの業務内容を捏造しない合成stepなのでsourceRefは付けない。分割operationにもそれぞれ追加する
ステップ表示文言呼び出し先の業務名（原本の日本語コメント、または関数名・BL 名から導出）。代入式・引数・分類タグは含めない。導出できない場合は識別子のみを使い、根拠のない機能名は作らない
kind: "return"破線で描画されるステップ。省略時は実線
sourceReffacts 由来のステップでは省略しない（call_order の file:line を転記）。手書き page-data で根拠が無い場合のみ省略可で、無いステップはテンプレート側で根拠列を空表示する
sourceRef境界「操作開始」を除くstepに存在するsourceRefを行番号除去して正規化する。一意パス数が1ならAPI endpointをinternalへ機械置換し「内部処理」レーンを使う。複数ならAPI endpointとレーンを維持する。0なら単一判定を適用せず、手書きpage-data等の既存endpointを変換しない
call_orderfacts.yml の⑤handler item が持つ任意フィールド。形式 "<連番>:<api分類のkey>@<file:line>; ..."。shared/references/facts-schema.md が定義元
1 operation あたりの分割上限1 handler の call_order が 15 ステップを超える場合、機能単位・コメント区切り・15 ステップ機械区切りの優先順で複数 operations[] へ分割する。分割後のキーは連番禁止で内容要約語とする

§5Phase 手順

スキル開始時に TaskCreate で Phase 1〜3 のタスクを登録する。各 Phase 開始時に該当タスクを in_progress に、完了時に completed へ TaskUpdate で更新する。

Phase内容完了条件
1. page-data の確保Step 1: シーケンス図-data.json の実在確認。Step 2: factsのcall_orderを機械変換し、各operation先頭へ利用者→画面の合成triggerを追加。全sourceRefが同一ファイルならAPIを内部処理へ置換し、15ステップ超は分割operationごとにtriggerを付与。Step 3: jqでレーン、seq、利用者起点、単一sourceRef境界を検証facts がある対象画面は操作 0 件を含め jq 検証通過済み。facts 不在画面は変換不能を報告済み
2. DOC_NAV の組み立て戻るリンク・基本設計項目・詳細設計項目・シーケンス図項目（自ページ）を、実在する項目だけで組み立てる（build-portal.sh セクション 3.5 と同一判定）対象画面ごとに doc_nav 文字列が確定済み
3. HTML 生成render-template.sh の render_template 関数を Bash から source して シーケンス図.html を生成。portal_output_dir 指定時は build-portal.sh を再実行対象画面すべてで シーケンス図.html が生成済み

手作業でのプレースホルダ置換（sed・perl 直書き等）は禁止する。render_template は最短前方一致で置換するため、値の中に他プレースホルダ文字列が偶然含まれても誤爆しない。新規 .sh スクリプトファイルは作らない。

§6重要な注意事項・予想を裏切る挙動

判定・評価はしない。呼び出し順序や処理内容の良否には踏み込まず、facts（call_order）または手書き page-data に記録された事実のみを転記する。「操作開始」は非ドメインの合成triggerであり、対応する原本行がないためsourceRefを付けない。call_order を持つ handler が 0 件の画面では、AskUserQuestion でステップを聞き出さず operations: [] の空状態を生成する。shared/scripts/detail-pages/ 配下・extracting-unit-facts-from-code 配下・seal-facts.sh は変更しない（別スキルの管轄）。
予想を裏切る挙動内容
出力先の階層テンプレート名（シーケンス図.html）が pageKind の FUTURE_FILES と同名でも、output_dir 直下ではなく画面ごとのフォルダ（<screenUnitRoot>/screen-<ID>/）直下になる。pageKind 体系の「1 pageKind = 1 固定ファイル名」契約はここでは適用されない
DOC_NAV の担当分担build-portal.sh は画面設計書（基本設計・詳細設計）側の DOC_NAV にのみシーケンス図項目を追加する。シーケンス図.html 自体の DOC_NAV は本スキルの Phase 2/3 が組み立てる（build-portal.sh の担当範囲外）
