画面一覧生成スキル
generating-screen-list-for-reverse-docs

既存コードベースを調査して画面単位にファイルをグルーピングし、raw画面正本・raw由来ext・画面一覧HTMLを生成するスキルの確定仕様。画面種別（unit_kind=screen）専用。

対応 OS Windows WSL2 環境
検証状況 統合スキル generating-unit-list-for-reverse-docs の画面（unit_kind=screen）経路として実プロジェクトで動作実績あり。種別分割後の単独起動は分割時点では未検証
依存 jq / bash（generation-engine/scripts/unit-list/ 配下の validate-manifest.sh・build-unit-list.sh・detect-screens.sh が使用）

§1概要

リバース設計で最初に決めるべきは「設計書を何冊に分けるか」＝画面の境界である。本スキルは既存コードベースを、スタック調査 → 検出戦略の宣言 → 戦略に基づく抽出・分類 → raw正本確定 → 整合検証 の順で調査する。画面詳細設計書の単位と全派生物の入力正本はscreen-manifest.jsonである。

仕事はraw・raw由来ext・画面一覧HTMLの生成までで、設計書の雛形展開・生成・記入は一切行わない。工程全体の案内は orchestrating-ai-development-setup が担い、本スキルは単独でも起動できる。

── リバース設計工程における位置づけ ─────────────────────────

  既存コードベース
  │
  ▼
  ┌───────────────────────────┐
  │ 本スキル                   │  Phase 1  スタック・画面規約の特定
  │ generating-screen-list-   │  Phase 2  戦略に基づく抽出
  │ for-reverse-docs          │  Phase 3  整合検証（機械実行）
  │                           │  Phase 4  画面一覧.html 生成
  └─────────────┬─────────────┘
  ▼
  一覧/画面一覧/screen-manifest.json ＝ raw正本
  │
  ▼
  画面詳細設計書の執筆工程（別スキルが担当）
設計原則: 固定と可変の分離。 マニフェストの形式・整合検証・HTML 生成は決定的スクリプトに固定し、プロジェクトごとに異なる「画面境界の検出」だけを可変にする。どの経路で抽出しても、同じ検証（validate-manifest.sh）を通らなければ HTML は生成できない。

§2出力

スキルを完走すると、以下の成果物が生まれる。

画面一覧.html（<output_dir>/一覧/画面一覧/画面一覧.html）
対象コードベースに存在する画面の全数を、画面キー・推定画面名・入口ファイル・構成ファイル群・検出根拠とともに一覧化した文書。読んだ人は「このシステムには画面が何枚あり、それぞれどのファイル群でできているか」を根拠付きで把握でき、画面詳細設計書を何冊書くべきかを迷わず決められる。共有部品・埋め込みビュー・未解決候補・診断警告も可視化される。
検証済みマニフェスト（<output_dir>/一覧/画面一覧/）
screen-manifest.jsonを人が編集できる唯一のraw正本、screen-manifest.ext.jsonをraw由来の派生物として原子的に保存する。検出情報・既存テスト件数・階層分類をrawへ確定してからSHA-256を算出し、extのmanifestContentHashへ伝播する。通常の後続工程と再開実行はrawまたはraw由来extを直接読み、HTML埋込JSONを逆抽出しない。

§3用語

マニフェスト
抽出結果を保持する JSON。画面ごとに screenKey（意味キー）・entryFile・files・confidence 等を持つ。スキーマの全体は references/screen-detection.md を参照。
検出の方針の宣言
Phase 1 の調査結果を JSON（unitKind/extractionMethod/screenIdRegex/viewSwitchPattern/excludePatterns 等）にまとめ、ユーザー承認（approvedByUser: true）を得た宣言。抽出と検証の両方がこの宣言を参照する。
個別に組み立てる抽出
組み込み検出器が適合しないプロジェクトで、Claude 自身が戦略宣言に沿って専用の抽出手順を設計・実行し、スキーマ準拠のマニフェストを出力する経路。

§4使い方（起動引数と返却）

起動引数（2 つのみ）

引数 内容
source_dir 探索対象のソースコードディレクトリ。対象プロジェクトの実コードルート（例: frontend/src）を指定する。モノレポの場合はアーキテクチャ調査書 §10 のサイト一覧で確定した当該サイトのルートディレクトリを渡す
output_dir 納品物ルート。この配下の一覧/画面一覧/へraw・ext・画面一覧HTMLを書き出す

旧統合スキルにあった unit_kind 引数は存在しない。本スキルは screen 固定であり、他種別（API・テーブル・バッチ・帳票・外部連携）は対応する種別別一覧スキルを使う。

返却（orchestrating-ai-development-setup の契約準拠）

返却キー 内容
status DONE または ERROR
artifacts 生成した画面一覧.html のパス。artifacts[0] を汎用名 unit_list_html としても返す
screen_list_html 従来互換のエイリアス（unit_list_html と同値）
embedded_json_ref HTML 内に埋め込んだマニフェスト JSON への参照
screen_manifest_path 画面一覧フォルダへ永続保存した生マニフェストJSON
screen_manifest_ext_path 設計書メタデータを付与した永続拡張マニフェストJSON
unit_kind 固定値 screen

§5動作フロー（Phase 1〜4）

開始時に TaskCreate で Phase 1〜4 のタスクを登録し、Phase の開始・完了ごとに TaskUpdate で進捗を更新する。

Phase やること 完了条件
Phase 1
スタック・画面規約の特定		 package.json・lock ファイルからフレームワーク・ルーターライブラリを確定 → ルーティング定義の所在を追跡 → 画面 ID 命名パターン・View 切替関数を調査 → 除外パターンを確定 → 検出の方針の宣言を作成しユーザー承認を取る 戦略 JSON（approvedByUser: true を含む）が保存済み
Phase 2
戦略に基づく抽出		 組み込みパスか個別に組み立てる抽出かを分岐判定 → raw作業コピーを生成 → diagnostics確認 → 既存テスト件数と階層分類をrawへ付与 → rawを原子的に保存 → hash付きextを生成・原子的に保存 canonical raw・raw由来extのschemaとhashが一致。0件検出はハード停止（画面を捏造しない）
Phase 3
整合検証（機械実行）		 validate-manifest.shをraw/extへ実行し、rawの正規化SHA-256とextのhash一致も検査する。FAIL時はrawを修正してextを再生成する（3回失敗でPhase 2へ差し戻し） exit 0（全項目 PASS）
Phase 4
画面一覧.html 生成		 build-unit-list.sh <screen-manifest.ext.json> <output_dir>/一覧/画面一覧/画面一覧.html --unit-kind screenを実行する（内部でbuild-screen-list.shに委譲）。build側がvalidateを再実行するため、未検証マニフェストからは生成できない HTML 生成済み・埋め込み JSON がマニフェストと一致

エンジンスクリプトはいずれもスキルフォルダ相対の ../../../generation-engine/scripts/unit-list/ 配下にある。正本リポジトリと公開先はフォルダ配置が同一のため、どちらの環境でも同じ相対参照で動く。

§6検出の 2 経路

経路 使える条件 担い手
組み込み検出器（高速パス） Next.js App/Pages Router（next.config.* の実在必須）・React Router（useRoutes 含む）・慣習ディレクトリのいずれかが Phase 1 の調査結果と適合する場合 detect-screens.sh（決定的スクリプト）
個別に組み立てる抽出 組み込み検出器が適合しない場合（カスタムルート配列・element 属性解決・動的ルート構築・深い階層の View 切替等） Claude 自身が戦略宣言に沿って Bash/Grep/Read で抽出し、スキーマ準拠 JSON を Write する
どちらの経路でも検証は同一基準。 validate-manifest.sh は抽出者非依存で動き、Phase 1 で承認した戦略宣言の存在確認も担う。カスタム抽出だからといって検証を省略する経路は存在しない。

組み込み検出器の既知の限界（個別に組み立てる抽出への切替の目安）

  • 動的に構築されるルート文字列（変数結合等）は検出できない。静的リテラルの path のみが対象
  • import Foo, { Bar } from ...（default+named 混合 import）の解決は不完全
  • import 追跡は 2 段階まで。埋め込みビューのスキャンは 1 階層のみで、子コンポーネント内のさらなる View 切替は検出できない
  • diagnostics で entryFile 集中警告が出たら、組み込みパスの継続ではなく個別に組み立てる抽出への切替を検討する

§7禁止事項と注意点

禁止・注意 理由
手作業でのプレースホルダ置換の禁止。HTML 生成は必ず build-unit-list.sh 経由で行う 過去に手動置換で entryFile=None が 10 件混入した実害がある。決定的スクリプトに固定して手作業経路を根絶する
0 件検出時のハード停止。AskUserQuestion で手動リストを聞き出さない 誤った画面境界を即興で確定させないため。0 件は戦略の不適合を示す信号であり、Phase 1 へ戻って調査し直す
設計書の雛形展開・生成・記入はスコープ外 本スキルの成果物はraw・raw由来ext・画面一覧HTML。設計書は後続工程の別スキルが担当する
Phase 1 の調査を省略して汎用の screen-id-regex を当てない 命名規約・ナビゲーション方式はプロジェクトごとに異なり、汎用正規表現は境界の取り違えを生む
カスタム抽出時はコメントアウトされた定義を除去してから抽出する コメント内のルート定義・import 文を実在として誤検出した実害がある
jq 未インストール環境では事前に導入する 検証・生成スクリプトが jq に依存する
