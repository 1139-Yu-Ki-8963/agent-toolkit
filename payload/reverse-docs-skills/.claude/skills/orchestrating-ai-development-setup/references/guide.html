§1概要

orchestrating-ai-development-setup はリバース設計書往復検証フローの進行係（管理者）。 自分では検証・比較・実装を一切行わず、状態判定 → 子スキルを args 全量指定で Skill 起動 → 返却ブロックの status で確認 → 次工程決定、というループで工程全体を統括する。

子スキル14（surveying-architecture-for-reverse-docs、種別別一覧生成スキル6種 〈generating-screen-list-for-reverse-docs / generating-api-list-for-reverse-docs / generating-table-list-for-reverse-docs / generating-batch-list-for-reverse-docs / generating-report-list-for-reverse-docs / generating-external-list-for-reverse-docs〉、 generating-reverse-common-docs、syncing-reverse-env、 unlocking-reverse-target-screens、extracting-unit-facts-from-code、 generating-reverse-detailed-design、rebuilding-screen-unit-from-docs、 rebuilding-code-from-docs）は互いを知らず、 工程間の受け渡しはすべて本スキルが仲介する（完全仲介方式）。契約の正本は references/contract.md。

使用タイミング / スキップ条件
使用する: リバース検証を工程統括したいとき（画面一覧生成から基準タグ確立までの一連の流れ）。
スキップする: 個別工程だけを動かしたい場合。各子スキルは同じ args を手渡せば単独でも動く契約のため、単体実行なら子スキルを直接起動する。

§2出力

統括スキル自体はファイルを生成しない。以下の最終状態を、事前ヒアリングと Phase 1〜7 / global Step 1〜41 の工程を依存順に制御して達成する。

全画面の設計書一式
対象アプリケーションのすべての画面について、コードの事実に基づいた詳細設計書が揃い、「設計書だけからコードを再構築→元と一致」の往復検証に合格した状態。新規参画者がコードを読まなくても画面仕様を把握できるドキュメント群が最終成果物になる。
全6種別の到達状態レポート
最終報告に、画面・API・テーブル・バッチ・帳票・外部連携の6種別それぞれの到達状態が「生成済み / 対象外 / 後続未対応」の3値で記載される。screen 以外の種別は facts抽出以降の工程が現時点で未対応のため、一覧確立をもって「後続未対応」として終端記録される。

§3状態判定表と判定フロー（15状態）

成果物の実在から現在の状態を15状態で判定し、次に起動する子スキルを機械的に決定する。 判定はアーキテクチャ調査・一覧・共通の書き起こし・ポータル・任意ページを先に確認し、その後に facts確定、基本設計・詳細設計、画面開通、ファイル単位検証、基準確立、judge の順に降りる。画面未開通でも静的リバースは止めない。 成果物の実在から毎回評価するので中断後も再開できる。

§4Phase 1〜7 / global Step 1〜41

Phase 内容 実行条件
Phase 1 / Step 1〜2 対象・出力先・スコープ・実行モード・状態を確定する。facts_profile=python を明示した場合は画面範囲を求めず、target_file_paths・facts_unit_id・verification_dir を確定して明示Python facts-only経路で終端する 常時
Phase 2 / Step 3〜8 アーキテクチャ調査と明示的なrevise 戻り方向の依存 アーキ未調査または検出手がかり不足時
Phase 3 / Step 9〜11 種別別一覧、対象外記録、機能一覧、マトリクス・対応表を確定する 一覧・派生成果物が未生成時
Phase 4 / Step 12〜16 共通文書、ポータル、任意基盤ページを確定する 共通未書き起こしまたはポータル未生成時
Phase 5 / Step 17〜39 facts確定、基本設計・詳細設計の静的リバース（29〜39は非画面ユニットの静的著述） screen種別。docs-onlyはStep 28で終端。api種別はStep 31、機能はStep 30で終端
Phase 6 / Step 40 unlock→setup→file verify→baseline sync→implement→compare single-pass / iterativeのみ
Phase 7 / Step 41 judge、基準更新、必要時teardown、明示戻り方向の依存 比較結果取得後
facts profileの境界
起動引数が空でも対話による確認は行わず、不足値を推測せず中断する。facts_profile=pythonではtarget_repo_path・output_dir・target_file_paths・facts_unit_id・verification_dir・実行モードを起動引数として要求する。target_file_pathsは対象リポジトリ内に実在する相対.pyパスだけを許可し、外部絶対パスは要求しない。フル実行は global Step 3 以降へ進まず、global Step 2 の明示Python facts-only経路へ分岐する。通常の画面ループは対象ファイルの拡張子にかかわらず常に profile=screen を使う。profile=python は明示した経路だけで使う。この経路は survey_doc_path を既存調査書から解決し、不在なら surveying-architecture-for-reverse-docs(mode=survey)、不合格なら mode=revise で確定してからfacts抽出へ進み、facts確定後に終端する。拡張子だけから画面フローをPython facts-onlyへ切り替えない。
静的完了前の画面一覧更新
基本設計・詳細設計の著述が合流したら、永続 screen-manifest.json を直接解決する。通常再開で不在なら停止する。rawが無い旧成果物を明示的に移行・復元する場合だけ、既存画面一覧HTMLの #screen-manifest から restore-screen-manifest.sh で復元・検証する。その後、設計書メタデータ抽出と画面一覧生成を再実行し、実在する4成果物のリンク・確定画面名・登録件数と表行数を確認してから、画面レジストリを authored へ更新する。
global Step 40〜41 の関係
rebuilding-code-from-docs は mode で2分割される（implement=比較要求を返して停止 / judge=比較結果を受け取り判定）。 管理者がこの2回を別々に起動し、global Step 40内で sync dry-run を挟む。
種別ループ
管理者は excluded-kinds.json の presentKinds に記載された各種別についてループする。screen のみユニット反復〜基準確立〜往復検証へ進む。 screen 以外（api / table / batch / report / external）は facts抽出以降の工程が現時点で未対応のため、一覧確立をもって「後続未対応」の終端状態として記録する。 最終報告には全6種別の到達状態（生成済み / 対象外 / 後続未対応 の3値）を必ず含める（正本は references/contract.md の「種別ループ」）。

§6返却ブロック契約

正本は references/contract.md。管理者は各子スキルの返却ブロックを共通サブセットで確認し、状態判定表に従って次工程を機械的に決定する。 これにより管理者と子スキルの間には契約書という単一の仲介点だけが存在し、子スキル同士が互いの内部仕様を知る必要がない完全仲介方式が成立する。

返却ブロック共通サブセット

キー 型 意味
status enum 各スキル固有の enum。管理者はこれで go / 差し戻しを判定する
scope string <system>-<画面ID>。工程を跨いだ同一性キー
artifacts path[] 生成物のパス（画面一覧HTML / 修正指示書.md / 最終報告.md / 証跡ディレクトリ 等）
hint string 次工程への申し送り（差し戻し理由・不足引数・後続工程への申し送り 等）

注記: next_request という語は使わない。syncing-reverse-env の実返却ブロックに存在しないフィールドのため。次工程への依頼内容は hint または各スキル固有の拡張フィールドで表す。

各スキル固有の status enum と拡張フィールド

子スキル status enum 拡張フィールド

generating-reverse-detailed-design（設計書著述） AUTHORED | BLOCKED fact_table_path（事実表 fact-table.md のパス）、measurement_pending（実測委譲項目一覧）

§7args 仕様

管理者と各子スキルが受け取る引数の全量。単独起動時はユーザーが同じ args を手渡しすれば動く。

子スキル args
管理者 verification_mode（docs-only | single-pass | iterative、既定 single-pass）。docs-only は facts・基本設計・詳細設計まで、single-pass は動的検証を1回、iterative は FAIL 後の改善反復も行う
各一覧生成スキル（6スキル共通） source_dir, output_dir（unit_kind は各スキルの固定値のため args に含めない）
syncing-reverse-env design-doc, mode（setup|sync|teardown）, dry-run, reset-first, user-approved, scenarios, max-loop（既存契約のまま）
generating-reverse-detailed-design screen_dir, output_dir, template_root, chapter_map_path, audit_script_path, target_repo_path, target_branch, source_ref, mode, target_file_path（mode=file時）, screenshot_dir（任意）, registry値（任意）
rebuilding-screen-unit-from-docs screen_dir, target_file_path, output_dir, template_root, audit_script_path, chapter_map_path, env_block, user-approved
rebuilding-code-from-docs (mode=implement) screen_dir, scope, reverse_worktree, ports, baseline_tag_status, output_dir, template_root, audit_script_path, chapter_map_path, user-approved
rebuilding-code-from-docs (mode=judge) screen_dir, compare_result, reverse_worktree, freeze_commit

注記: user-approved（白紙化承認）と output_dir は管理者が事前に解決して args で渡す（完全仲介方式のため子スキルはユーザーに直接聞かない）。

§8ループ設計

要素 内容
反復条件 verification_mode=iterative かつglobal Step 40または41がFAILした場合だけ、back_edge_idで明示したStepへ戻す
上限回数 max_loop（既定3。②の max_loop とは別軸の工程ループ）
停止条件 ① 収束停止: 全対象画面が PASS（2連続で確定）
② リソース上限: max_loop 到達で FAIL 確定
③ 発散検知: judge が2連続同一差分（compare_result の static_diff 署名一致）で上限前に打切り
④ single-pass はFAILの結果と改善候補を報告して停止、docs-only は外側ループを適用しない
検証役の分離 各工程の判定は子スキルの返却ブロック（status）のみで行い、管理者は自然文で判定しない

この外側ループ（発散判定2連続・上限）はiterativeにだけ適用する。single-passは1回のjudge結果を記録して停止し、docs-onlyはglobal Step 28の静的リバース完了で終端する。

静的著述とファイル単位検証の戻り方向の依存

要素 内容
反復条件 verification_mode=iterative かつ rebuilding-screen-unit-from-docs（S1b）が status=差し戻し を返した場合だけ generating-reverse-detailed-design（S1a）へ戻し、再著述後に S1b を再実行する
上限回数 5回目安（rebuilding-screen-unit-from-docs 自身の内側ループ上限と揃える）
停止条件 ① 収束停止: rebuilding-screen-unit-from-docs が status=再現一致 を返す
② リソース上限: 5回到達しても差し戻しが続く場合はユーザーに報告する
検証役の分離 S1a（著述）と S1b（原本を見ない検証）は別スキル・別セッションで実行され、S1b の判定は自身の完全性ゲート・6計測の決定的出力のみで行う

予想を裏切る挙動

状態判定はアーキテクチャ調査、一覧、共通の書き起こし、facts確定、基本設計・詳細設計、画面開通、ファイル単位検証、基準確立、judge の順に成果物実在から毎回評価する。したがって静的リバースは画面開通より先に完了できる。
docs-only はPhase 6の静的リバース完了で終端する。動的検証では implement → sync dry-run → judge を別々に起動し、judge FAIL後に反復するのは iterative だけである。single-pass は結果を報告して停止する。
