§1概要

テーブル定義書はカラムの名前・型・長さ・必須の別・既定値・制約・索引・外部キーの参照先を書く。しかし、そのテーブルが業務上の何を表すか、どの業務で使われるか、どのエンティティと関係するかという問いには、実装の定義とは別に答える必要がある。

本スキルは業務語彙だけで論理データモデルを書く。カラムの型・制約・索引・物理名は使わない。読み手は業務担当者である。

本スキルがやること
テーブル 1 件ごとの業務的な意味（業務上の何を表すか・どの業務で使われるか・どのエンティティと関係するか・保持する期間と廃棄の条件）を業務語彙のみで記入した論理データモデルの生成
本スキルがやらないこと
カラムの名前・型・長さ・必須の別・既定値・制約・索引・外部キーの参照先の記述（テーブル定義書の担当）／テーブル一覧の生成（generating-table-list-for-reverse-docsの担当）

起動引数

引数 必須 内容
table_manifest_path 必須 テーブル一覧の拡張マニフェストの絶対パス
source_dir 必須 原本コードのルート
output_dir 必須 出力先のルート
template_root 必須 テンプレート群のルート
unit_keys 任意 対象を絞るキーの配列
common_docs_root 任意 共通文書のルート。業務語彙の突合に使う

unit_kind は table 固定であり、引数には取らない。

§2出力

テーブル 1 件につき、次の 2 点が生まれる。

論理データモデル.md（<output_dir>/<tableUnitRoot>/table-<テーブル識別子>/基本設計/論理データモデル.md）
そのテーブルが業務上の何を表すか・どの業務で使われるか・どのエンティティと関係するか・保持する期間と廃棄の条件を、業務語彙のみで記入した文書。コードから確定できなかった事項は要確認事項一覧へまとめて記載される。
テーブルテスト設計書.md（テスト設計/）
論理データモデルの外部仕様・業務仕様・エラーと例外の各章から起こしたテストの観点を記入した文書。各観点に、由来する論理データモデルの章が記録される。原本コードもマニフェストも情報源にしない。

§3用語

業務語彙
コード識別子・フレームワーク用語・型構文・パス・ライブラリ名を使わず、業務担当者が読める言葉だけで書く記述の方針。
要確認事項
コードから確定できない事項を推測で埋めず、確認事項として記録したもの。キーは連番を禁じ、内容を要約した意味語で付ける。

§4動作フロー

Phase やること 完了条件
Phase 1
起動引数の確認と対象の確定		 必須4引数の実在確認、マニフェストの確認（unitKind が table・units が1件以上）、対象ユニットの確定を行う 4引数が実在し、マニフェストが確認済みで、対象ユニットが確定している
Phase 2
業務的な意味の抽出		 マニフェストの記載事項を把握し、原本コードから業務的な意味（業務上の何を表すか・どの業務で使われるか・どのエンティティと関係するか・保持する期間と廃棄の条件）を読み取る。カラムの型・制約・索引・物理名は読み取らない。確定できない事項は推測で埋めず要確認事項として記録する 対象ユニット全件について、業務的な意味の記入材料が揃っている
Phase 3
執筆		 テンプレートを展開・配置し、業務語彙のみで各章へ記入する。空欄のまま残った項目を要確認事項一覧へ列挙し、frontmatter の status を draft から authored へ更新する 全対象ユニットの設計書が業務語彙のみで記入済みである
Phase 4
テーブルテスト設計書の執筆		 Phase 3 で書き上げた基本設計書だけを情報源にテストの観点を作る。原本コードもマニフェストも読まない。基本設計書で確定していない事項からは観点を作らない テーブルテスト設計書が出力され、全ての観点に由来する章が記録されている
Phase 5
機械検査		 業務語彙の検査・注記の残存検査・frontmatter の検査・章の完備検査・根拠の追跡検査・由来の記録検査・情報源の検査・配置の検査の8検査を実行する。不合格が1件でもあれば Phase 3 または Phase 4 へ戻る（上限3回） 7検査すべてが合格している

§5守り（禁止事項と機械検証）

禁止事項

  • コード識別子・フレームワーク用語・型構文・ファイルパス・ライブラリ名を本文に書かない
  • カラムの型・制約・索引・物理名を書かない（テーブル定義書の担当）
  • コードから確定できない事項を推測で埋めない
  • 根拠を本文に file:line の形で書かない。業務語彙の検査がファイルパス形式の文字列そのものを不合格の対象とするため
  • 子スキルへ委任しない。原本読解と執筆（Phase 1〜3）は業務語彙の一貫性を保つため単一のメインエージェントが通しで担う
  • テーブルテスト設計書（Phase 4）は原本コードもマニフェストも情報源にしない。情報源は基本設計書だけ

機械検証

Phase 5 で次の8検査を実行する。検査1は生成した本文に実装用語（型構文・interface の宣言・ORM/DDL の構文語・原本の拡張子・内部の成果物名等）が含まれないことを grep で確認する。検査2はテンプレートの記入規則を書いた HTML コメントが残っていないことを確認する。検査3は frontmatter の status が authored になっていることを確認する。検査4はテンプレートが持つ全ての章見出しが出力に存在することを確認する。根拠の追跡検査は本文の各記述の導出元をマニフェスト項目または原本コードの箇所として検証記録へ列挙し、導出元を示せない記述が残っていないことを確認する。由来の記録検査はテーブルテスト設計書の全観点に由来する章が記録されていることを確認する。情報源の検査はテーブルテスト設計書の本文に基本設計書に現れない語が含まれていないことを確認する。配置の検査は基本設計とテスト設計の両phaseを確認する。1つでも不合格なら該当 Phase へ戻り、上限3回で収束しなければ status=ERROR とする。
