# generating-batch-detail-design-for-reverse-docs テストケース

観点キーは連番禁止。内容を要約した意味語で付ける（番号からは情報を得られないため）。

| 観点キー | 前提 | 操作 | 期待結果 | 機械検証の方法 |
|---|---|---|---|---|
| マニフェスト記載事項-一致 | バッチ詳細設計書が生成済みである | Phase 4 検査1を実行する | マニフェストの`schedule`・`targetTables`・`downstreamJobs`・`execMethod`のうち値を持つフィールドが本文に反映されていること | 検査1（不一致0件） |
| 注記-記入規則コメント残存なし | テンプレートを展開した設計書がある | Phase 4 検査2を実行する | テンプレートの記入規則を書いたHTMLコメント（`<!-- -->`）が本文に残っていないこと | 検査2 |
| frontmatter-status-authored | Phase 3 Step4が完了している | Phase 4 検査3を実行する | frontmatterの`status`が`authored`になっていること | 検査3 |
| 章-完備 | テンプレートが章見出しを持つ | Phase 4 検査4を実行する | テンプレートが持つ全ての章見出しが出力に存在すること | 検査4 |
| 実装位置-非記録 | 処理定義に根拠が必要である | Phase 2 Step2を実行する | 対象コードのファイルパス・行番号がなく、確定できない項目は要確認事項一覧へ回されること | 手動（対象コードベースを要する） |
| マニフェスト-整合確認 | マニフェストの`schedule`・`targetTables`・`downstreamJobs`・`execMethod`がある | Phase 2 Step3を実行する | 原本から読み取った内容との食い違いが要確認事項一覧へ記録されること | 手動（対象コードベースを要する） |
| 業務意味-記述なし | バッチ詳細設計書が生成済みである | 本文の起動の契機・業務上の目的等の記載有無を確認する | 起動の契機・実行の周期・入力と出力・業務上の目的・異常時の復旧の方針が書かれていないこと（バッチ基本設計書の担当範囲であるため） | 手動（章立て確定前のため機械検査項目化は未実施） |
| 識別子-空でERROR中断 | `unitId`と`unitKey`の双方が空のユニットがある | Phase 3 Step1で出力先を決定する | `status=ERROR`となり、hintに「出力先の識別子が確定しない」が入る | 手動（合成フィクスチャを要する） |
| 実装用語-検査対象外 | 本文に実装用語が含まれる | Phase 4 の4検査を実行する | 実装用語の混入を理由に不合格としないこと（兄弟の基本設計スキルと逆の方針） | 検査1〜4の対象外であることを確認（grepパターンに実装用語検出が含まれない） |
| 未確定事項-要確認事項への回送 | コードから確定できない事項がある | Phase 2 Step2およびPhase 3 Step3を実行する | 推測で埋めず、要確認事項一覧へ記録される | 手動（対象コードベースを要する） |

## 機械検証との対応

- 機械検証が「手動」の行は、guide.html の検証状況へ手動確認を記録する
- self-test に対応ケースを追加したら、この表の機械検証列を同じコミットで更新する
