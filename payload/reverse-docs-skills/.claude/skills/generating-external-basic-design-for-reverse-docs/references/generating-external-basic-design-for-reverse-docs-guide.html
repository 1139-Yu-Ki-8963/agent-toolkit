§1概要

その外部連携がどんな電文をどう変換して送るかは、外部連携詳細設計書が書く。しかし、その連携が何のために存在し、誰と連携し、正常時と異常時にどう応答するかという問いには、実装の詳細とは別に答える必要がある。

本スキルは業務語彙だけで基本設計書を書く。電文の項目の定義・変換の処理・タイムアウトといった実装の詳細は抽出しない。読み手は業務担当者である。

本スキルがやること
外部連携 1 本ごとの業務的な意味（連携の方式・連携の契機・責任の分界点・正常時と異常時の応答・再送の可否）を業務語彙のみで記入した外部連携基本設計書の生成、およびその基本設計書だけを情報源とした外部連携単体テスト設計書の生成
本スキルがやらないこと
電文の項目の定義・変換の処理・タイムアウトの記述（外部連携詳細設計書の担当）／ 外部連携一覧の生成（generating-external-list-for-reverse-docsの担当）

起動引数

引数必須内容
external_manifest_path必須外部連携一覧の拡張マニフェストの絶対パス
source_dir必須原本コードのルート
output_dir必須出力先のルート
template_root必須テンプレート群のルート
unit_keys任意対象を絞るキーの配列
common_docs_root任意共通文書のルート。業務語彙とメッセージの突合に使う

unit_kind は external 固定であり、引数には取らない。

§2出力

外部連携 1 本につき、次の 2 点が生まれる。

外部連携基本設計書.md（<output_dir>/外部連携/external-<外部連携識別子>/基本設計/外部連携基本設計書.md）
その外部連携の連携の方式・連携の契機・責任の分界点・正常時と異常時の応答・再送の可否を、業務語彙のみで記入した文書。コードから確定できなかった事項は要確認事項一覧へまとめて記載される。
外部連携単体テスト設計書.md（<output_dir>/外部連携/external-<外部連携識別子>/基本設計/外部連携単体テスト設計書.md）
外部連携基本設計書だけを情報源として起こしたテストの観点をまとめた文書。原本コードもマニフェストも参照しない。各観点には由来する基本設計書の章が記録される。

§3用語

業務語彙
コード識別子・フレームワーク用語・型構文・パス・ライブラリ名を使わず、業務担当者が読める言葉だけで書く記述の方針。
責任の分界点
その外部連携が業務上どこまでを担い、どこから先を連携先に委ねるかという境界。連携の方式・連携の契機・正常時と異常時の応答とあわせて、原本コードから抽出する対象の一つ。
要確認事項
コードから確定できない事項を推測で埋めず、確認事項として記録したもの。キーは連番を禁じ、内容を要約した意味語で付ける。

§4動作フロー

Phaseやること完了条件
Phase 1
起動引数の検収と対象の確定		 必須4引数の実在確認、マニフェストの検収（unitKind が external・units が1件以上）、対象ユニットの確定を行う 4引数が実在し、マニフェストが検収済みで、対象ユニットが確定している
Phase 2
業務的な意味の抽出		 マニフェストの記載事項（direction・protocol・authMethod等）を把握し、原本コードから連携の方式・連携の契機・責任の分界点・正常時と異常時の応答・再送の可否を読み取る。確定できない事項は推測で埋めず要確認事項として記録する 対象ユニット全件について、業務的な意味の記入材料が揃っている
Phase 3
執筆		 テンプレートを展開・配置し、業務語彙のみで各章へ記入する。空欄のまま残った項目を要確認事項一覧へ列挙し、frontmatter の status を draft から authored へ更新する 全対象ユニットの設計書が業務語彙のみで記入済みである
Phase 4
単体テスト設計書の執筆		 Phase 3 で書き上げた基本設計書だけを情報源として、外部仕様・業務仕様・エラーと例外の各章からテストの観点を起こす。各観点に由来する基本設計書の章を記録し、確定していない事項は要確認事項一覧へ移す 単体テスト設計書が出力され、全ての観点に由来する章が記録されている
Phase 5
機械検査		 業務語彙の検査・注記の残存検査・frontmatter の検査・章の完備検査・由来の記録検査・情報源の検査の6検査を実行する。不合格が1件でもあれば Phase 3 または Phase 4 へ戻る（上限3回） 6検査すべてが合格している

§5守り（禁止事項と機械検証）

禁止事項

  • コード識別子・フレームワーク用語・型構文・ファイルパス・ライブラリ名を本文に書かない
  • 電文の項目の定義・変換の処理・タイムアウトを書かない（外部連携詳細設計書の担当）
  • コードから確定できない事項を推測で埋めない
  • 根拠を本文に file:line の形で書かない。業務語彙の検査がファイルパス形式の文字列そのものを不合格の対象とするため
  • 外部連携単体テスト設計書の情報源を基本設計書だけに限る。原本コードもマニフェストも読まない
  • 子スキルへ委任しない。原本読解と執筆（Phase 1〜3）は業務語彙の一貫性を保つため単一のメインエージェントが通しで担う

機械検証

Phase 5 で次の6検査を実行する。検査1は生成した本文に実装用語（フレームワーク用語・型構文・原本の拡張子・内部の成果物名等）が含まれないことを grep で確認する。検査2はテンプレートの記入規則を書いた HTML コメントが残っていないことを確認する。検査3は frontmatter の status が authored になっていることを確認する。検査4はテンプレートが持つ全ての章見出しが出力に存在することを確認する。由来の記録検査は単体テスト設計書の全行に由来する基本設計書の章が記録されていることを確認する。情報源の検査は単体テスト設計書の本文に基本設計書に現れない語（原本のファイル名・関数名・変数名）が含まれていないことを確認する。1つでも不合格なら該当する Phase へ戻り、上限3回で収束しなければ status=ERROR とする。
