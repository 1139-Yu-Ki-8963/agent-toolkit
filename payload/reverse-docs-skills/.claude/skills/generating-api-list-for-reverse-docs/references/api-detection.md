# API 検出戦略ガイダンス

Phase 1（スタック・API規約の特定）で調査すべき対象と検出手法を示す。本スキルの `unit_kind` は api 固定であり、組み込み検出器はない。抽出は常にカスタム抽出パス（Claude 自身が戦略宣言に沿って抽出し、スキーマ準拠のマニフェスト JSON を出力する）を使う。

## 調査項目

| 調査対象 | 検出手法 |
|---|---|
| エンドポイント定義の所在 | OpenAPI/Swagger 定義ファイル、Express/Fastify/Hono のルート定義、FastAPI/Django REST のビュー定義、コントローラファイル |
| HTTPメソッドとパス | `app.get()`/`app.post()` 等のメソッド呼び出し、デコレータ（`@Get()`/`@Post()`）、ルートテーブル |
| ミドルウェア | 認証・バリデーション等の共通処理 |
| 除外パターン | テスト用エンドポイント、ヘルスチェック |

## 対象形態の判定（調査の最初の分岐）

調査は形態の判定から始める。Web フレームワークを前提とした調査項目は、HTTP でエンドポイントを公開しないコードベースには当たらない。

| 判定 | 条件 | 使う調査項目 |
|---|---|---|
| HTTP 系 | 依存定義（`package.json`・`requirements.txt`・`pyproject.toml`・`go.mod` 等）に Web フレームワークが実在する、または OpenAPI/Swagger 定義が実在する | 「調査項目」の表 |
| 非 HTTP 系 | 上記のいずれも実在しない。ビルド定義（Makefile・CMakeLists.txt 等）から実行ファイルを生成する構成を含む | 「非 HTTP 系の調査項目」の表 |
| 併存 | 両方が実在する | 両方の表を使い、単位ごとに `detectionMethod` へどちらで検出したかを記録する |

判定できない場合は推測で片方に倒さない。両方の表を走らせ、検出件数を比較してから確定する。

## 非 HTTP 系の調査項目

レガシー C 等、HTTP でエンドポイントを公開しないコードベースで呼び出し境界を特定する手がかり。強い順に並べる。①が境界決定の主手段であり、HTTP 系におけるルート定義に相当する。

| 優先 | 手がかり | 抽出元 | 用途 |
|---|---|---|---|
| ① | ビルド定義の生成ターゲット | Makefile・CMakeLists.txt・ビルドスクリプトの実行ファイル生成規則 | 単位境界の決定。実行可能単位が物理的に確定するため最も強い |
| ② | プロセスのエントリポイント | `main()` を持つソースファイル | ①の裏取り。1 実行ファイルが 1 単位であることの確認 |
| ③ | ディスパッチ表 | 取引コード・サービス番号から処理関数を引く `switch` 文・関数ポインタ配列 | 1 実行ファイル内に複数の業務単位が同居する場合の内部分割 |
| ④ | 公開ヘッダの外部宣言 | `include/`・`public/` 等に置かれ他モジュールから取り込まれるヘッダの `extern` 関数宣言 | ライブラリ形態の場合の単位 |
| ⑤ | ゲートウェイ境界 | `REQUEST_METHOD`・`QUERY_STRING` 等の環境変数参照、RPC のインターフェース定義ファイル、メッセージキュー名の定数 | 外部から呼ばれる入口の識別 |
| ⑥ | ジョブ制御からの起動単位 | シェルスクリプト・ジョブ定義から起動される実行ファイル | ②の裏取りと、業務としての起動契機の把握 |
| ⑦ | 埋め込み SQL のプリコンパイル単位 | `EXEC SQL` を含むソース | 境界の決定ではなくデータ操作の関連付けに使う |

競合の解決手順は次のとおり。

1. 単位境界は常に①で引く。①が引けない場合のみ②で仮置きし、`confidence` を low とする
2. ③で内部分割した場合、親の実行ファイルを `entrypoint`、分割した各行を `dispatch-entry` として両方を記録する。件数の重複計上を避けるため、`dispatch-entry` が存在する実行ファイルは単位数のカウント対象から外す
3. ⑤が①と異なる境界を示す場合は①を採用し、`confidence` を 1 段下げ、当該ユニットの `notes` に競合内容を記録する
4. ⑦は境界の決定に使わない
5. ①から⑥のいずれでも境界が引けない場合は捏造せず `kind` を `unresolved` とし、`notes` に試した手がかりを記録して人間へ引き継ぐ。①が「引ける」とは、ビルド定義に実行ファイルを生成する規則が実在し、その生成物名を確定できることを指す。ライブラリだけを生成する構成や、生成規則が外部の共通ファイルへ委ねられていて追跡できない構成は「引けない」と扱う

## 調査の進め方

1. **対象形態の判定**: 「対象形態の判定」の表に従い、HTTP 系・非 HTTP 系・併存のいずれかを確定する
2. **フレームワークまたはビルド系の確定**: HTTP 系は `package.json`・lockファイル、またはバックエンド相当（`requirements.txt`/`pyproject.toml`/`go.mod` 等）から Web フレームワークを特定する。非 HTTP 系はビルド定義（Makefile・CMakeLists.txt 等）から、生成される実行ファイルの一覧を確定する
3. **定義所在の追跡**: ルーターの分割マウント（`app.use('/prefix', router)` 等）がある場合、マウント元からルート定義ファイルまで追跡し、最終的なパス（prefix 結合後）を確定する。非 HTTP 系はビルド定義の生成ターゲットから、リンク対象のソースファイル一覧を確定する
4. **一次情報の選定**: OpenAPI/Swagger 定義が存在する場合はそれを一次情報とし、実装コードと突合する。食い違いは実装側を正とし、`notes` に記録する。非 HTTP 系はビルド定義を一次情報とする
5. **除外の実地確認**: テスト用エンドポイント・ヘルスチェック・モックの実在を `ls`/Grep で確認してから `excludePatterns` に載せる。非 HTTP 系ではテスト用の実行ファイル・デバッグ用ツールを同様に確認する

## マニフェストスキーマ

```json
{
  "generatedAt": "ISO8601",
  "sourceDir": "探索対象ルート",
  "unitKind": "api",
  "strategy": {
    "extractionMethod": "custom",
    "approvedByUser": true,
    "unitIdRegex": "string|null",
    "excludePatterns": []
  },
  "detectionSummary": {
    "method": "custom",
    "unitCount": 0,
    "unresolvedCount": 0
  },
  "units": [
    {
      "unitKey": "意味キー",
      "unitId": "業務ID（任意）",
      "unitNameGuess": "推定名",
      "kind": "endpoint|entrypoint|dispatch-entry|exported-function|middleware|unresolved",
      "identifier": "主識別子（例: GET /users/:id）",
      "sourceFile": "主ファイルパス",
      "confidence": "high|medium|low",
      "fileCount": 0,
      "files": [],
      "detectionMethod": "検出手法"
    }
  ]
}
```

## `kind` 値の使い分け

| kind | 用途 |
|---|---|
| `endpoint` | HTTP メソッド + パスが確定した API エンドポイント。HTTP 系における単位数のカウント対象はこの行のみ |
| `entrypoint` | 実行ファイル 1 本に対応する呼び出し単位。非 HTTP 系の既定。同じ実行ファイルに `dispatch-entry` が存在する場合はカウント対象から外す |
| `dispatch-entry` | ディスパッチ表の 1 行に対応する業務単位。取引コード等で分岐する実行ファイルを内部分割する場合に使う |
| `exported-function` | 公開ヘッダで外部宣言された関数。ライブラリ形態の呼び出し単位 |
| `middleware` | 認証・バリデーション等の共通処理。単位として数えない |
| `unresolved` | 定義の存在は確認できたが、識別子・実装ファイルのいずれかを確定できなかったもの |

## 記録の指針

- `identifier` の形式は対象形態で分ける。HTTP 系は「HTTP メソッド + パス」とし、パスは prefix 結合後の最終形で記録する（例: `GET /users/:id`）。非 HTTP 系は実行ファイルの相対パス（例: `bin/order_entry`）、ディスパッチ表の行は「実行ファイル名 + コード値」（例: `order_entry#TX0421`）、公開関数は「ヘッダ名 + 関数名」（例: `order_api.h:submit_order`）とする。いずれも実装に実在する識別子だけを使い、独自に採番しない
- `unitKey` は連番禁止。内容を要約した意味語キーを付ける（例: `ユーザー-詳細取得`）
- 動的に構築されるルート（変数結合・ループ登録）は、展開ロジックを追跡して最終パスを確定できた場合のみ `endpoint` とし、できなければ `unresolved` に降格する
