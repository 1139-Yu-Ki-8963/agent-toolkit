# generating-table-definition-for-reverse-docs テストケース

観点キーは連番禁止。内容を要約した意味語で付ける（番号からは情報を得られないため）。

| 観点キー | 前提 | 操作 | 期待結果 | 機械検証の方法 |
|---|---|---|---|---|
| カラム件数-一致 | テーブル定義書が生成済みである | Phase 4 検査1を実行する | マニフェストの`columnCount`と、本文に書き出したカラムの件数が一致していること | 検査1（不一致0件） |
| 注記-記入規則コメント残存なし | テンプレートを展開した設計書がある | Phase 4 検査2を実行する | テンプレートの記入規則を書いたHTMLコメント（`<!-- -->`）が本文に残っていないこと | 検査2 |
| frontmatter-status-authored | Phase 3 Step4が完了している | Phase 4 検査3を実行する | frontmatterの`status`が`authored`になっていること | 検査3 |
| 章-完備 | テンプレートが章見出しを持つ | Phase 4 検査4を実行する | テンプレートが持つ全ての章見出しが出力に存在すること | 検査4 |
| 根拠-file:line記載 | カラム定義に根拠が必要である | Phase 2 Step2を実行する | 各項目に`file:line`形式の根拠が付いていること。根拠を付けられない項目は空欄のまま要確認事項一覧へ回されること | 手動（対象コードベースを要する） |
| マニフェスト-整合確認 | マニフェストの`foreignKeys`・`columnCount`・`mainColumns`がある | Phase 2 Step3を実行する | 原本から読み取った内容との食い違いが要確認事項一覧へ記録されること | 手動（対象コードベースを要する） |
| 業務意味-記述なし | テーブル定義書が生成済みである | 本文の業務上の何を表すか等の記載有無を確認する | 業務上の何を表すか・どの業務で使われるか・どのエンティティと関係するかが書かれていないこと（論理データモデルの担当範囲であるため） | 手動（章立て確定前のため機械検査項目化は未実施） |
| 識別子-空でERROR中断 | `unitId`と`unitKey`の双方が空のユニットがある | Phase 3 Step1で出力先を決定する | `status=ERROR`となり、hintに「出力先の識別子が確定しない」が入る | 手動（合成フィクスチャを要する） |
| 実装用語-検査対象外 | 本文に実装用語（型構文・DDL構文語等）が含まれる | Phase 4 の4検査を実行する | 実装用語の混入を理由に不合格としないこと（兄弟の基本設計スキルと逆の方針） | 検査1〜4の対象外であることを確認（grepパターンに実装用語検出が含まれない） |
| 未確定事項-要確認事項への回送 | コードから確定できない事項がある | Phase 2 Step2およびPhase 3 Step3を実行する | 推測で埋めず、要確認事項一覧へ記録される | 手動（対象コードベースを要する） |

## 機械検証との対応

- 機械検証が「手動」の行は、guide.html の検証状況へ手動確認を記録する
- self-test に対応ケースを追加したら、この表の機械検証列を同じコミットで更新する
