## いつ使うか

接続窓口の基本設計書を作りたいとき、呼び出し口ごとの業務向け設計書を作りたいとき。

## いつ使わないか

接続窓口の詳細設計書を作るとき（→generating-api-detail-design-for-reverse-docs が担当）、接続窓口の一覧を作るとき（→generating-api-list-for-reverse-docs が担当）。

# 正本: reverse-docs-skills

本スキルが生成する納品物は顧客提示の文書である。自由記述の本文（要約・説明文）は敬体（です・ます）で書く。記入規則・検証記録・作業記録は常体でもよい（`delivery-payload/references/設計書様式.md` §8）。

# API基本設計書の生成スキル

工程全体は orchestrating-ai-development-setup が案内する。本スキルは API 1 本ごとの基本設計書の執筆のみを担い、単独起動できる。起動引数は api_manifest_path・source_dir・output_dir・template_root の 4 つが必須で、これらを渡せば動く。`unit_kind` は **api 固定** であり、引数では受け取らない。

## 情報源

情報源は次の 2 つに限る。

1. API 一覧の拡張マニフェスト（`api-manifest.ext.json`。`method`・`authRequired`・`ioSummary` を含む）
2. マニフェストの `files` が指す原本コード

抽出するのは、その API が何のために存在するか、誰が呼ぶか、業務上どの処理を担うか、認証と権限の要否、責任の分界点、および外部から見える入力と出力の契約である。入力はリクエストの形式・入力項目・ヘッダと認証情報、出力は応答の包み・正常時の出力項目・異常時の出力の構造・空と境界の扱いを対象とする。内部の処理手順、実装固有のデータ構造、関数間の引数と戻り値は抽出しない。

## 基本設計書と詳細設計書の役割分担

- API基本設計書は、利用者と外部システムから見える契約を定義する。外部から指定または観測できる入力と出力は、項目名・型・必須性・有効な範囲・既定値・NULL許容・桁と精度を含めて本書へ記録する
- API詳細設計書の §2 リクエストと §3 レスポンスは、基本設計書で定義した契約を実装と1対1に対応する内部仕様へ具体化する。内部の変数、変換、データ構造、処理手順は詳細設計書だけへ記録する
- 同じ項目を両方へ記録する場合、基本設計書では外部契約としての意味と制約を、詳細設計書ではコード上の対応先と処理方法を記録する

## 言語プロファイル

対象言語ごとに、呼び出し境界の読み取り方を定めたプロファイルを持つ。Phase 1 はプロファイルを選択し、どのプロファイルにも該当しない言語だけを中断する。「未対応なら中断」という判定は採らない。

実装済みのプロファイルは次の 2 つである。

| プロファイル | 対象 | 拡張子 | エンドポイントの所在 |
|---|---|---|---|
| `python` | FastAPI 等の HTTP フレームワーク | `.py` | デコレータ（`@app.get` 等）とルーター登録 |
| `perl` | HTTP エンドポイントを持つ Perl 実装 | `.pl`・`.pm`・`.cgi` | ルーティング定義表（ディスパッチ表・ルートのハッシュ等）とサブルーチン名の対応 |

### プロファイルの選択

`api-manifest.ext.json` の `units[].files` の拡張子を集計し、最多の拡張子が属するプロファイルを選ぶ。同数の場合は、対象ユニット数の多い側のプロファイルを選ぶ。それでも決まらない場合は AskUserQuestion で確認する。

どのプロファイルの拡張子にも該当しない場合だけ `status=ERROR` を返して中断し、hint に「該当する言語プロファイルなし」と、集計した拡張子の内訳を記録する。

選んだプロファイルは返却ブロックの `language_profile` に記録する。

## 使用タイミング

- API 一覧が生成済みで、エンドポイント単位の業務設計書を作りたいとき
- 前提: `<output_dir>/<manifestsRoot>/api-manifest.ext.json` が生成済みであること（`manifestsRoot` は output-layout の物理配置キー。既定値 `docs/manifests`）

## 起動引数

| 引数 | 必須 | 内容 |
|---|---|---|
| `api_manifest_path` | 必須 | API一覧の拡張マニフェストの絶対パス |
| `source_dir` | 必須 | 原本コードのルート |
| `output_dir` | 必須 | 出力先のルート |
| `template_root` | 必須 | テンプレート群のルート |
| `unit_keys` | 任意 | 対象を絞るキーの配列 |

## 成果物

| 項目 | 基本設計書 | APIテスト設計書 |
|---|---|---|
| 出力フォルダ | `<output_dir>/<apiUnitRoot>/api-<API 識別子>/<unitPhaseDirNames.basic>/` | `<output_dir>/<apiUnitRoot>/api-<API 識別子>/<unitTestDesignDir>/` |
| 出力ファイル | `API基本設計書.md` | `APIテスト設計書.md` |
| テンプレート | `<template_root>/リバース検証/API/API基本設計書.md` | `<template_root>/リバース検証/API/APIテスト設計書.md` |

`apiUnitRoot` は output-layout の物理配置キーである。既定値は `docs/design/apis` とする。`unitPhaseDirNames.basic` は output-layout の `unitPhaseDirNames.basic` の値である。既定値は `basic-design` とする（scaffold-design-unit.sh が実際に展開する配置フォルダ名と一致させる。1-210）。

表示用 `kindLabels.api` は path に使わない。APIテスト設計書はAPI基本設計書だけを情報源とし、対象コードの位置を成果物へ記録しない。

`<API 識別子>` はマニフェストの `unitId` を使う。`unitId` が空（`null` または空文字）の場合は `unitKey` を使う。両方が空の場合だけ当該ユニットを生成せず、`status=ERROR` で中断して hint に「出力先の識別子が確定しない」と当該ユニットの `identifier` を記録する。

`unitKey` をディレクトリ名に使う場合、パス区切り（`/`）と制御文字をそのまま使わない。含む場合はハイフンへ置き換えて使い、置換した事実を実行結果へ記録する。

### 記述の3区分

本文へ書く前に、記述を次の3区分へ分ける。

| 区分 | 内容 | 扱い |
|---|---|---|
| 観測できる事実 | 拡張マニフェストの項目に直接現れる値・原本コードの観測で直接確認できる呼び出し先 | 本文へ書く。導出元のマニフェスト項目または原本コードの箇所を検証記録へ残す |
| 観測から一意に導ける存在理由 | エンドポイントの定義箇所・呼び出し関係から一意に定まる、そのAPIが担う処理 | 本文へ書く。導出元のマニフェスト項目または原本コードの箇所を検証記録へ残す |
| 判断基準と業務背景 | なぜその制約か・誰が呼ぶか・業務上の位置づけ・例外の適用条件 | 本文へ書かず、要確認事項一覧へ移す |

3区分のどれか迷う記述は、3番目として扱う。断定より要確認を優先する。

## Phase 3: 執筆

### テンプレートの配置

執筆の前に、テンプレートを出力先へ配置する。手作業で Read と Write を行わず、次のスクリプトを呼ぶ。

```bash
bash generation-engine/scripts/scaffold-design-unit.sh api basic <output_dir> <識別子> <表示名> <template_root>
```

`<kind>` と `<phase>` は本スキルの担当に固定する。配置済みのファイルへ記入する形で執筆する。

配置に失敗した場合は執筆へ進まず、`status=ERROR` を返す。

### 表題の形式と前付けとの関係

本文冒頭の `# ` 見出し（表題）は「<対象名> <役割名>」の形式とする。役割名はファイル名から拡張子を除いた文字列と完全に一致させ、記入時に書き換えない。対象名（表示名）トークンは雛形の展開時に自動置換済みであり、記入時に対象名部分を書き換えない。対象名の末尾が役割名の先頭と同じ語で終わる場合は、対象名側から重複する語を落とし、同じ語が2回続けて現れないようにする（例: 対象名「注文API」＋ 役割名「API詳細設計書」→ 表題「注文API詳細設計書」）。

前付け（frontmatter）の識別名（`<種別>KEY`・`<種別>ID` 等）と本文の表題は、一致を求めない。前付けはマニフェストの識別子をそのまま使う機械可読の値であり、表題は対象の表示名を使う人が読む見出しである。両者が異なる文字列になっても構わない。

**使用ツール**: Bash / Read / Write

- **Step 2**: Phase 2 で得た材料を業務語彙のみで各章へ記入する。§1.3 入力仕様の3表と §1.4 出力仕様の4表は、行が0件の場合も見出しと列を削除せず、外部から見える項目を1項目1行で記入する。原本に無い値を書かず、推測で埋めない。設計書本文にも別資料にも、対象コードへの参照、対象コードのパスまたは行番号を書かない。完了条件: 入力項目と出力項目の表を含む各章の記入が完了している

**完了**: 全対象ユニットの設計書が業務語彙のみで記入済みである

### 要確認事項一覧の記入規則

要確認事項一覧には、確認する人が業務上の未確定事項を判断できる表現だけを書く。検査1に列挙した内部の成果物名・内部キーを、人が読む列へ転記しない。原本のファイル名や拡張子も転記しない。

| 書かない表現 | 言い換え |
|---|---|
| `authRequired` が未設定 | 利用時に本人確認が必要か確定できない |
| `ioSummary` から入出力を確定できない | 利用者が渡す情報と受け取る結果を確定できない |
| `dispatch-entry` の対応が不明 | 受付後にどの業務処理へ引き渡すか確定できない |
| `api-manifest` と `unitKey` の対応が不明 | 一覧上の接続窓口と設計対象の対応を確定できない |

正確な原本のファイル名・行番号は、設計書本文・要確認事項一覧・別資料のいずれにも記録しない。必要な参照は、設計書内の節番号または関数単位の契約で表す。

根拠の所在を示す場合も、検査1を免除したり検出行を合格扱いしたりしない。

## Phase 4: APIテスト設計書の執筆

## Step 4-1: APIテスト設計書を執筆する

**使用ツール**: Read / Write

テスト設計書では、§1を正常・異常・境界を含む全観点の一覧とする。
§5と§6には、§1のうち異常・境界の観点を§1と同じ観点キーで詳述する。
§5と§6では新しいケースを定義せず、§1の全観点に対応する実行ケースを§2だけへ記載する。
実行するテストの件数は、§2のデータ行数だけで数える。

情報源は **Phase 3 で書き上げたAPI基本設計書だけ**とする。原本コードもマニフェストも読まない。APIテスト設計書は1つのAPIの外部契約を検証し、関数単位と結合テストは扱わない。

```bash
bash generation-engine/scripts/scaffold-design-unit.sh api test <output_dir> <識別子> <表示名> <template_root>
```

1. APIテスト設計書のテンプレートを Read し、12個の`##`見出しを名前と順序を含めて記入対象として固定する。本文を白紙から組み立てず、`<unitTestDesignDir>` へ配置したテンプレートへ記入する
2. 冒頭3節を次の規則で記入する。見出しは削除・改名・並べ替えをしない
   - **テスト対象**: APIの表示名・業務上の入出力境界・対応するAPI基本設計書を記す
   - **テストの粒度と自動化の方針**: 1エンドポイントを1単位とし、基本設計書で確定した要求・応答・例外のうち自動化する範囲と、自動化しない範囲および理由を記す
   - **本書が扱わない範囲**: 他のAPI・内部実装の処理手順・基本設計書で未確定の事項を記す。該当が無い場合も見出しを残し「なし」と記す
3. 基本設計書の外部仕様・業務仕様・エラーと例外の各章から、§1から§7を記入する。各観点に、由来する基本設計書の章を記録する
4. §8にはテスト開始前に満たす条件と終了判定を記入する。入力から確定できない場合も節を削らず、未確定事項を記す
5. 基本設計書で確定していない事項は観点にせず、確定できなかった事項が0件でも節を残し「なし」と記す
6. 12節を保持したまま出力先へ Write する

**完了**: APIテスト設計書が `<unitTestDesignDir>` へ出力され、全ての観点に由来する基本設計書の章が記録されている。

## Phase 5: 機械検査

## Step 5-1: 機械検査

**使用ツール**: Bash

Phase 5の開始時に永続化した試行回数を1増やし、次の9つを実行する。不合格ならPhase 3へ戻る。3回目も収束しない場合だけ`status=ERROR`とする。

- **検査1 業務語彙の検査**: Phase 3で生成した全API基本設計書を入力にする。コード構文・原本拡張子・referenceに列挙した内部名を検出し、全ファイル0件だけを合格とする。`interface`、Pythonの`class`・`def`・Markdown内の型注釈、Perlの`sub`、`app`と`router`のメソッドデコレータも対象とする。

Phase 5の実行直前に `references/phase5-business-vocabulary-check.md` を必ず Read する。そこにある関数を同じBashセッション内で定義し、検査1から検査9まで順番に実行する。検査ごとに別のBashを起動しない。

検査1の前に期待対象を再導出し、保存済み期待TSVと照合する。同件数でも対象集合が違えば不合格にする。TSVは2列・空値なし・各列重複なし・絶対パスであることも検査する。

試行回数ファイルは、`0`・`1`・`2`のいずれかを持つ1行だけを受け付ける。`phase5_attempt` と `report_phase5_failure` は検査9まで同じ範囲で使う。不合格出力は一時ログへ捕捉し、検出ファイル・件数・行、または構造エラー詳細をhintへ含める。

1回目と2回目は `phase5_result=RETRY` とhintを返す。`status=ERROR` と `status=DONE` は返さず、Phase 3を `in_progress` に戻す。3回目は `status=ERROR` とhintを返す。

検査2から検査9は既存仕様を保つcallbackとして定義する。単一のゲートが9つを順に呼び、すべてが0を返した後だけPhase 5を `completed` にして `status=DONE` を返す。

- **検査2 注記の残存検査**: テンプレートの記入規則を書いた HTML コメント（`<!-- -->`）が残っていないことを確認する。残存 0 件で合格
- **検査3 frontmatter の検査**: `status` が `authored` になっており、未記入プレースホルダーが残っていないことを確認する
- **検査4 章の完備検査**: テンプレートが持つ全ての章見出しが出力に存在することを確認する
- **検査5 実装位置の非記録検査**: 基本設計書とAPIテスト設計書に、対象コードのファイルパス・行番号・`file:line` が無く、参照先が文書内の節または関数単位の契約に限定されていることを確認する
- **検査6 由来の記録検査**: APIテスト設計書の §1 テスト観点と §5 異常系の全行に、由来する基本設計書の章が記録されていることを確認する

### 検査1の合成フィクスチャ確認

検査規則を変更した場合は、referenceの合成フィクスチャ36項目を実走する。

1. 1回目と2回目の不合格は `phase5_result=RETRY` とhintを返し、ERRORとDONEを返さない
2. 3回目の不合格は `status=ERROR` とhintを返し、DONEを返さない
3. 大小の型名を持つinterface、Python構文、Perlのsub、app/routerのメソッドデコレータを検出する
4. 行頭・箇条書き・表・inline codeの型注釈を検出し、`status: authored` は検出しない
5. 全件選択の欠落、複数top-level JSON、符号化キー、試行回数、DONEの正方向を含む36項目すべてに合格する

合成フィクスチャには、少なくとも「利用時に本人確認が必要か確定できない」と「接続窓口を定義する原本」を含める。これらの言い換えが検出0件であることをもって、要確認事項一覧と原本名の記入規則が検査1と整合していることを確認する。

## 根拠の書き方

本スキルが生成するAPI基本設計書とAPIテスト設計書に、`file:line`、対象コードのファイルパス、行番号を記録することは禁止する。コード変更への継続追従が必要な位置情報を納品物へ持たせない。参照先は文書内の節または関数単位の契約に限定する。

## サブエージェント委任仕様

本スキルは子スキルを起動しない。原本読解と執筆（Phase 1〜3）は業務語彙の一貫性を保つため単一のメインエージェントが通しで担う。

## ループ設計

Phase 5で不合格が検出された場合は、Phase 3へ戻してPhase 5を再実行する。APIテスト設計書の修正が必要な場合は、Phase 3から続けてPhase 4も再実行する。

| 要素 | 内容 |
|---|---|
| 反復条件 | 1回目と2回目にいずれかが不合格なら、`phase5_result=RETRY` でPhase 3へ戻る |
| 上限回数 | 3回 |
| 停止条件 | 9検査すべて合格、または3回目の不合格で`status=ERROR`を返す |

## 停止条件

| status | 意味 |
|---|---|
| `DONE` | 全対象ユニットのAPI基本設計書・APIテスト設計書が業務語彙のみで記入済み、かつPhase 5の9検査すべてに合格した |
| `ERROR` | 必須引数の欠落・マニフェスト不整合・該当する言語プロファイルなし・出力先の識別子が確定しない・Phase 5 が上限 3 回で収束しない、のいずれかで著述不能 |

## 予想を裏切る挙動

- 実装済みのプロファイルは python と perl の 2 つ。判定は `files` の拡張子の最多で行うため、多言語混在のリポジトリでは意図しないプロファイルが選ばれうる。その場合は `unit_keys` で同一言語のユニットだけに絞って起動する
- 本スキルの業務語彙の検査はファイルパス形式の文字列そのものを不合格の対象とする。対象コードの位置は本文にも別資料にも記録しない
- 実マニフェストでは `unitId` が全件空のことがある。その場合の出力先は `unitKey` 由来になるため、合成フィクスチャで確認した出力先と実データでの出力先が一致しないことがある
- 本スキルの成果物は往復検証の対象外である。基本設計書だけからコードを再生成して原本と突き合わせる検証は行わない
