# API詳細設計書の生成スキル

工程全体は orchestrating-ai-development-setup が案内する。本スキルは API 1 本ごとの詳細設計書の執筆のみを担い、単独起動できる。起動引数は api_manifest_path・source_dir・output_dir・template_root の 4 つで、これらを渡せば動く。`unit_kind` は **api 固定** であり、引数では受け取らない。

## 情報源と原本を見ない検証の扱い

画面詳細設計書（generating-reverse-detailed-design）は確定済み facts だけを情報源とし、原本コードの読解を禁じる。本スキルはこの制約を採らない。API 単位の facts を供給する経路が存在しないためである。

したがって本スキルは **原本だけを読み取る種類** である。情報源は次の 2 つに限る。

1. API 一覧の拡張マニフェスト（`api-manifest.ext.json`。`method`・`authRequired`・`ioSummary` を含む。`authRequired` が欠落している場合、それはルーター登録時に一括付与される認証依存（`include_router` の `dependencies` 引数等）を抽出器が検出できないことによる欠落であり「認証不要」を意味しない。原本のルーター登録箇所を確認してから記述する）
2. マニフェストの `files` が指す原本コード

この帰結として、本スキルが生成した設計書は往復検証（設計書だけからコードを再生成して原本と突き合わせる検証）の対象にならない。設計書と原本が同じ情報源を共有しており、突合が独立した検証にならないためである。品質は §検証 の 5 つの機械検査で担保する。

原本から確定できない型・制約・既定値を推測で埋めない原則は維持する。ただし、テンプレートの 12.5「設計判断とその理由」に限り、実装構造から導いた選択理由を `推定（実装構造）` と明示して記録できる。推定を観測事実として扱わない。

原本コードの位置は、各API単位の直下にある `設計単位根拠台帳.md` へだけ記録する。API基本設計で作成済みの台帳があれば同じファイルを使い、無ければ `<template_root>/リバース検証/設計単位共通/設計単位根拠台帳.md` から生成する。API詳細設計書の本文には根拠列や対象コードのファイル名を書かない。行番号、`file:line`、ファイル名を省いた括弧書き、文中の行番号も、表・疑似コード・説明文のいずれにも書かない。疑似コードの行末へ対象コードの位置を注記することも禁止する。

API単体テスト設計書と機能設計書はコードを直接情報源にしないため、設計単位根拠台帳の対象外とする。バッチ詳細設計書、帳票詳細設計書、外部連携の詳細設計書など、コードを直接読んで作る詳細設計書には同じ本文・根拠台帳の分離原則を適用する。各スキルへの具体的な反映はそれぞれの変更課題で行う。

## 言語プロファイル

対象言語ごとに、呼び出し境界の読み取り方を定めたプロファイルを持つ。Phase 1 はプロファイルを選択し、どのプロファイルにも該当しない言語だけを中断する。「未対応なら中断」という判定は採らない。

実装済みのプロファイルは次の 2 つである。

| プロファイル | 対象 | 拡張子 | エンドポイントの所在 | 引数の所在 | 応答の所在 |
|---|---|---|---|---|---|
| `python` | FastAPI 等の HTTP フレームワーク | `.py` | デコレータ（`@app.get` 等）とルーター登録 | 関数シグネチャの型注釈と `Query`・`Path`・`Body` の宣言 | 戻り値の型注釈と `response_model` |
| `perl` | HTTP エンドポイントを持つ Perl 実装 | `.pl`・`.pm`・`.cgi` | ルーティング定義表（ディスパッチ表・ルートのハッシュ等）とサブルーチン名の対応 | `param` による読み出し箇所と、引数ハッシュの展開箇所 | 応答を組み立てる箇所（描画呼び出し・標準出力・ハッシュの返却） |

### プロファイルの選択

`api-manifest.ext.json` の `units[].files` の拡張子を集計し、最多の拡張子が属するプロファイルを選ぶ。同数の場合は、対象ユニット数の多い側のプロファイルを選ぶ。それでも決まらない場合は AskUserQuestion で確認する。

どのプロファイルの拡張子にも該当しない場合だけ `status=ERROR` を返して中断し、hint に「該当する言語プロファイルなし」と、集計した拡張子の内訳を記録する。

選んだプロファイルは返却ブロックの `language_profile` に記録する。

### perl プロファイルの読み取り規約

- エンドポイントとサブルーチンの対応は、ルーティング定義表を正とする。サブルーチン名からの推測で対応を決めない
- 1 つのモジュールに複数のエンドポイントが同居する構成を前提とする。ファイル単位ではなくサブルーチン単位で §9 実装契約を書く
- 引数は宣言的な型を持たないため、読み出し箇所から名前を採る。型は原本から確定できる場合のみ書き、確定できない型は設計単位根拠台帳へ回す
- 共通処理を担う内部ヘルパーが複数のエンドポイントから呼ばれる場合、§4.2 内部呼び出しへ記録する。ヘルパー自体を独立したエンドポイントとして数えない
- `files` が入口モジュール 1 本のみを指し、その中にディスパッチ表がある場合は、表から当該エンドポイントのハンドラを引き、ハンドラの実装モジュールまで読む。入口モジュールの記述だけで §2 から §9 を埋めない
- ハンドラの実装モジュールが `files` に含まれていない場合も読解対象にする。あわせて `files` の不足を設計単位根拠台帳へ記録し、一覧生成側の再実行が要ることを残す

### 設計判断の読み取り規約

- コードコメントを `観測（コードコメント）` に分類できるのは、コメントが現在の実装上の選択と理由を因果関係で直接結び付け、そのコメントが説明する処理を特定できる場合だけとする
- TODO、過去の経緯だけを述べるコメント、却下済み案の説明、別処理を説明する近接コメントは観測から除外する
- 観測として記録するのは「原本コメントがその理由を述べている」という事実である。コメントの主張が現在も妥当であるとは断定しない
- コメントに理由が無く、実装構造から理由を導ける場合は `推定（実装構造）` とする。確からしさは `medium` または `low` に限り、推定に `high` を使わない
- 選ばなかった選択肢と不採用理由を原本から読めない場合は、両欄を `不明（原本に記述なし）` とする。もっともらしい代替案を補わない
- 設計判断または選択理由を観測も推定もできない場合は 12.5 に行を作らず、設計単位根拠台帳へ移す
- 原本コードの位置は設計書本文へ書かない。設計単位根拠台帳に判断キーと原本位置の対応を残す

## 使用タイミング

- API 一覧が生成済みで、エンドポイント単位の詳細設計書を作りたいとき
- 前提: `<output_dir>/<manifestsRoot>/api-manifest.ext.json` が生成済みであること（`manifestsRoot` は output-layout の物理配置キー。既定値 `docs/manifests`）
- 起動引数:
  - `api_manifest_path`（必須。API 一覧の拡張マニフェストの絶対パス）
  - `source_dir`（必須。原本コードのルート）
  - `output_dir`（必須。設計書の出力先ルート）
  - `template_root`（必須。テンプレート群のルート。実体は `delivery-payload/templates/`）
  - `unit_keys`（任意。対象を絞る場合のマニフェスト上のキー配列。省略時は全件）
  - `common_docs_root`（任意。プロジェクト共通文書のルート。メッセージ定義との突合に使う）

`apiUnitRoot` は output-layout の物理配置キー（既定値 `docs/design/apis`）。表示用 `kindLabels.api` は path に使わない。

API単位のテスト文書は `<unitTestDesignDir>/APIテスト設計書.md`（外部契約）と `API単体テスト設計書.md`（関数・メソッド単位）の2件である。本スキルが執筆するのは後者だけとし、前者はAPI基本設計スキルが基本設計書を根拠に執筆する。単位配下に結合テスト文書は生成しない。

`<API 識別子>` はマニフェストの `unitId` を使う。`unitId` が空（`null` または空文字）の場合は `unitKey` を使う。両方が空の場合だけ当該ユニットを生成せず、`status=ERROR` で中断して hint に「出力先の識別子が確定しない」と当該ユニットの `identifier` を記録する。

実マニフェストでは `unitId` が全件空のことがある。一覧生成側が `unitId` を非必須フィールドとして扱い、実装にも `null` を入れる分岐があるためである。合成フィクスチャでは埋まっていることが多く、この状態は実データでしか現れない。

`unitKey` をディレクトリ名に使う場合、パス区切り（`/`）と制御文字をそのまま使わない。含む場合はハイフンへ置き換えて使い、置換した事実を当該APIの設計単位根拠台帳へ記録する。

## 進捗管理（必須手順）

スキル開始時に `TaskCreate` で Phase 1〜4 のタスクを登録する。各 Phase 開始時に該当タスクを `in_progress` に、完了時に `completed` へ `TaskUpdate` で更新する。Phase 4 から Phase 3 へ差し戻す場合は該当タスクを `in_progress` に戻す。実行環境に TaskCreate/TaskUpdate が存在しない場合は、出力先ディレクトリ内のタスク台帳ファイル（`task-ledger.md`）で同等の Phase 遷移記録を代替する。

## Phase 1: 起動引数の確認と対象確定

## Step 1-1: 起動引数の確認と対象確定

- **Step 1**: 必須 4 引数の実在を確認する（`test -f` / `test -d`）。いずれかが欠ける場合は `status=ERROR` で停止する。完了条件: 4 引数すべてが実在する
- **Step 2**: `api_manifest_path` を Read し、`unitKind` が `api` であること、`units` が 1 件以上あることを確認する。完了条件: マニフェストが確認済み
- **Step 3**: 言語プロファイルを選択する。「言語プロファイル」節の選択規則に従い `python` または `perl` を確定する。どちらの拡張子にも該当しない場合だけ `status=ERROR` で停止し、hint に「該当する言語プロファイルなし」と拡張子の内訳を記録する。完了条件: プロファイルが 1 つ確定している、または該当なしとして停止している
- **Step 4**: 対象ユニットを確定する。`unit_keys` が渡されていればその集合、無ければ次の規則で選ぶ。`kind` が `endpoint` または `dispatch-entry` のユニットを対象に含める。`entrypoint` は、同じ実行ファイルに `dispatch-entry` が 1 件でも存在する場合は対象外とし、存在しない場合だけ対象に含める。`middleware` と `unresolved` は常に対象外とする。完了条件: 対象ユニットの一覧が確定済み

**完了**: 4 引数が実在し、マニフェストが確認済みで、言語プロファイルが確定し、対象ユニットが確定している

## Phase 2: 原本読解

## Step 2-1: ユニットごとの原本読解

対象ユニット 1 件につき次を行う。

- **Step 1**: マニフェストの `files` が指すファイルを Read する。`sourceFile` を起点に、そこから呼ばれる関数の定義元まで追う。追跡は 2 段までとし、それ以上は設計単位根拠台帳へ記録する。`files` と `sourceFile` が入口モジュール 1 本へ集約されている場合は、そのモジュール内のディスパッチ表から当該エンドポイントのハンドラを引く。引いたハンドラの実装モジュールを読解対象へ加える。この解決は追跡の 2 段とは別枠で数え、ハンドラへ到達した地点を 1 段目とする。完了条件: 読解対象のファイル一覧が確定済み
- **Step 2**: テンプレートの §2 から §12 に対応する事実を原本から抽出する。読み取りは Phase 1 で選んだプロファイルの読み取り規約に従う。本文の節・項目と、対象コードの相対パス・1始まりの行番号を別々の記入材料として保持する。コード位置を本文用の材料へ混ぜず、位置を特定できない項目は空欄のまま設計単位根拠台帳へ回す。完了条件: 全章の本文材料と台帳材料が分離して揃っている
- **Step 3**: メッセージ定義書が `common_docs_root` にあれば、§10.2 のメッセージ ID を突合する。無ければ §10.2 は空欄とし、その旨を設計単位根拠台帳へ記録する。完了条件: メッセージの突合が済んでいる

### 表題の形式と前付けとの関係

本文冒頭の `# ` 見出し（表題）は「<対象名> <役割名>」の形式とする。役割名はファイル名から拡張子を除いた文字列と完全に一致させ、記入時に書き換えない。対象名（表示名）トークンは雛形の展開時に自動置換済みであり、記入時に対象名部分を書き換えない。対象名の末尾が役割名の先頭と同じ語で終わる場合は、対象名側から重複する語を落とし、同じ語が2回続けて現れないようにする（例: 対象名「注文API」＋ 役割名「API詳細設計書」→ 表題「注文API詳細設計書」）。

前付け（frontmatter）の識別名（`<種別>KEY`・`<種別>ID` 等）と本文の表題は、一致を求めない。前付けはマニフェストの識別子をそのまま使う機械可読の値であり、表題は対象の表示名を使う人が読む見出しである。両者が異なる文字列になっても構わない。

API詳細設計書の前付けは、次の 7 鍵を canonical な完全な集合とする。

| 鍵 | 値の決め方 |
|---|---|
| `api_key` | マニフェストの `unitKey` を使う |
| `api_id` | マニフェストの `unitId` を使う。空の場合も鍵を残して値を空欄とし、設計単位根拠台帳へ未確定事項として記録する |
| `method` | マニフェストの `method` を使う |
| `path` | マニフェストに独立した `path` があれば使う。無ければ `identifier` の先頭にある HTTP メソッドとそれに続く空白を除き、後半を path として決定的に分離する |
| `feature_key` | マニフェストに `featureKey` があれば使う。無ければ鍵を残して値を空欄とし、設計単位根拠台帳へ未確定事項として記録する |
| `source_ref` | マニフェストの `sourceFile` を使う |
| `unit_kind` | 固定値 `api` を使う |

この集合へ `title`・`login_required`・`category`・`auth`・`note` を追加せず、生成物にも残さない。

`delivery-payload/references/doc-extraction.json` の宣言に従い、実際の読取処理である `generation-engine/scripts/portal-input/build-manifests-from-docs.sh` は `api_key`・`api_id`・`source_ref`・`method`・`path` を読む。少なくとも `api_key`・`source_ref`・`method`・`path` が揃った文書を `kind=endpoint` と判定する。`unitId`（`api_id`）は欠落時に代替可能であるため、この判定条件には含めない。`generation-engine/scripts/build-portal.sh --build-manifests-from-docs` がこの読取経路を起動する。`unit_kind` と `feature_key` は現行の抽出器が参照する鍵ではないが、canonical 集合の一部として保持する。

## 重要な注意事項

- 原本に無い値を書かない。型・制約・既定値を推測で補わない

## 予想を裏切る挙動

- 実装済みのプロファイルは python と perl の 2 つ。判定は `files` の拡張子の最多で行うため、多言語混在のリポジトリでは意図しないプロファイルが選ばれうる。その場合は `unit_keys` で同一言語のユニットだけに絞って起動する
- 呼び出し追跡は 2 段まで。深い委譲構造を持つ実装では、末端の処理が設計単位根拠台帳に積み上がる
- 本スキルは原本を見ない検証ではない。画面詳細設計書と同じ品質保証を期待しない
- 実マニフェストでは `unitId` が全件空のことがある。その場合の出力先は `unitKey` 由来になるため、合成フィクスチャで確認した出力先と実データでの出力先が一致しないことがある
- ディスパッチ表を持つ構成では、`files` が入口モジュール 1 本だけを指し、`confidence` が全件 `low` になることがある。この状態でも中断せず、ディスパッチ表を解いて実装本体まで読む
- 非 HTTP 系のマニフェストには `kind` が `endpoint` のユニットが 1 件も無いことがある。業務単位が `dispatch-entry` として記録されるためで、この場合も対象として扱う

### check-design-doc-section-consistency.sh のテンプレート一致検査

**必要性**: 必須節の存在検査だけでは、全件が同じ短縮版の節構成を持つ場合や、§2・§3 の表から列が一律に欠ける場合を検出できない。生成のたびに現行テンプレートの全見出しと全表列を同じ基準で比較し、3件以上でも繰り返せる機械検査が必要である。

**代替案を採用しなかった理由**: 生成スキル本文へ固定した一覧だけでは実行時の逸脱を止められず、`scaffold-design-unit.sh --verify` は配置・frontmatter・必須トークンを対象として全表列を比較しない。新しい検査スクリプトへ分けると、既に第1層の検査から呼ばれている節検査と走査・判定責務が重複するため、既存検査を拡張する。

**保守責任者**: 人手（reverse-docs-skills 保守者）。API詳細設計書テンプレートの `##` 見出しまたは表の列を変更した場合、検査はテンプレートから実行時に抽出するため固定値の更新は不要だが、本スキルの「テンプレート正本契約」と test-cases.md を同時に更新する。

**廃棄条件**: API詳細設計書の生成が決定的なテンプレートエンジンへ移り、全見出し・全表列の保持を同等以上の検査で保証するようになった時。
