§1概要

このスキルは、既存のバックエンドコードから API 1 本ごとの詳細設計書を作る。対象はエンドポイント単位であり、複数の API をまとめた機能単位の設計書とは別物である。情報源は API 一覧の拡張マニフェストと、そのマニフェストが指す原本コードの 2 つに限る。原本から確定できない仕様値は推測で埋めず、要確認事項として残す。設計判断の理由だけは、コードコメントの観測と実装構造からの推定を区別して記録する。

§2出力

エンドポイント 1 本につき、以下の 4 点が生まれる。

エンドポイント 1 本ぶんの実装契約
受け取るパラメータの名前・型・必須の別・制約、返す構造とステータスコード、処理の順序、触るテーブルとトランザクションの範囲が、それぞれ原本の行番号を根拠として並ぶ。読んだ人は、そのエンドポイントを呼ぶ側の実装と、内部の振る舞いの両方を、原本を開かずに把握できる。
確定できなかったことの根拠記録
原本を読んでも型や制約が決まらなかった項目は推測で埋めず、§13 から参照する根拠資料へ記録される。
設計判断とその理由
実装で選ばれている方式と理由を、観測（コードコメント）と推定（実装構造）に分けて記録する。原本に無い代替案は補わない。
章の役割キーによる機械的な参照点
付録 B の章マップが、章の役割キーと節番号の対応を持つ。他のスキルや検査がこの設計書の特定の章を指すときに使える。

§3用語

拡張マニフェスト
API 一覧スキルが出力する JSON に、メソッド・認証要否・入出力の要約を付け足したもの。
原本を見ない検証
設計書の執筆役が原本コードを読まず、確定済みの事実表だけを情報源にする進め方。このスキルは採らない。
根拠を記録する資料
原本から確定できない事項と本文記述の根拠を記録し、API詳細設計書の §13 から参照する資料。

§4情報源と原本を見ない検証を採らない理由

画面詳細設計書は、原本を見ない検証を前提に書かれ、設計書だけからコードを再生成して原本と突き合わせる往復検証が成立する。API 単位ではその前提が置けない。事実表を供給する経路が存在しないためである。したがってこのスキルは原本だけを読み取る種類とし、生成した設計書を往復検証の対象にしない。品質は §6 の 8 つの機械検査で担保する。この違いを表で示す。

観点画面詳細設計書API詳細設計書（本スキル）
情報源確定済みの事実表のみ拡張マニフェストと原本コードの 2 つ
執筆時のコード読解禁止（原本を見ない検証）必須（原本だけを読み取る種類）
品質保証の方法設計書だけからのコード再生成と原本突合（往復検証）§6 の 8 つの機械検査

§6検証

Phase 4 で実行する 8 つの機械検査。1 つでも不合格なら Phase 3 へ差し戻し、上限 3 回で収束しなければ status=ERROR とする。

検査内容
検査1 章の完備生成した各設計書に §1 から §13 と章マップ（付録B）が存在することを確認する
検査2 根拠の実在記入した file:line 形式の根拠について、ファイルが source_dir 配下に実在することを確認する。実在しない根拠が 1 件でもあれば不合格とする
検査3 プレースホルダの残存APIKEY・APIID・METHOD・PATH・FEATUREKEY・SOURCEREF が本文に残っていないことを確認する
検査4 配置と前付け宣言された配置に必須ファイルがあり、frontmatter の鍵集合がテンプレートと一致することを確認する
検査5 設計判断12.5 が存在し、観測と推定の区分、推定の確からしさ、不明な選択肢の表記が規則どおりであることを確認する
検査6 単体テスト粒度全データ行に関数・メソッド名があり、外部契約のHTTPステータス観点が混在しないことを確認する
検査7 単体テスト配置API単体テスト設計書が単体テスト設計の配置にだけ存在することを確認する
検査8 テンプレート一致現行テンプレートの全 ## 見出しと、全表の所属節・小節・列見出し・順序・件数が完全一致することを確認する。§2 と §3 の列省略も不合格になる

§7制約と既知の限界

  • 実装済みの言語プロファイルは python と perl の 2 つで、どちらにも該当しない言語だけ status=ERROR を返して中断する
  • 呼び出しの追跡は 2 段までとし、それ以上は要確認事項へ積む
  • 原本を見ない検証ではないため、画面詳細設計書と同じ品質保証を期待できない
  • middleware と unresolved のユニットは対象外とする
