§1概要

このスキルは、既存のバックエンドコードから API 1 本ごとの詳細設計書を起こす。対象はエンドポイント単位であり、複数の API をまとめた機能単位の設計書とは別物である。情報源は API 一覧の拡張マニフェストと、そのマニフェストが指す原本コードの 2 つに限る。原本から確定できない事項は推測で埋めず、要確認事項として残す。

§2出力

エンドポイント 1 本につき、以下の 3 点が生まれる。

エンドポイント 1 本ぶんの実装契約
受け取るパラメータの名前・型・必須の別・制約、返す構造とステータスコード、処理の順序、触るテーブルとトランザクションの範囲が、それぞれ原本の行番号を根拠として並ぶ。読んだ人は、そのエンドポイントを呼ぶ側の実装と、内部の振る舞いの両方を、原本を開かずに把握できる。
確定できなかったことの一覧
原本を読んでも型や制約が決まらなかった項目が、推測で埋められずに列挙される。読んだ人は、どこを人に聞く必要があるかを最初に把握できる。
章の役割キーによる機械的な参照点
付録 B の章マップが、章の役割キーと節番号の対応を持つ。他のスキルや検査がこの設計書の特定の章を指すときに使える。

§3用語

拡張マニフェスト
API 一覧スキルが出力する JSON に、メソッド・認証要否・入出力の要約を付け足したもの。
盲検
設計書の執筆役が原本コードを読まず、封印済みの事実表だけを情報源にする進め方。このスキルは採らない。
要確認事項
原本から確定できず、人が判断するほかない事項。設計書の §10 に集約する。

§4情報源と盲検を採らない理由

画面詳細設計書は盲検で書かれ、設計書だけからコードを再生成して原本と突き合わせる往復検証が成立する。API 単位ではその前提が置けない。事実表を供給する経路が存在しないためである。したがってこのスキルは原本読解型とし、生成した設計書を往復検証の対象にしない。品質は §6 の 3 つの機械検査で担保する。この違いを表で示す。

観点画面詳細設計書API詳細設計書（本スキル）
情報源封印済みの事実表のみ拡張マニフェストと原本コードの 2 つ
執筆時のコード読解禁止（盲検）必須（原本読解型）
品質保証の方法設計書だけからのコード再生成と原本突合（往復検証）§6 の 3 つの機械検査

§6検証

Phase 4 で実行する 3 つの機械検査。1 つでも不合格なら Phase 3 へ差し戻し、上限 3 回で収束しなければ status=ERROR とする。

検査内容
検査1 章の完備生成した各設計書に §1 から §10 が存在し、あわせて付録 A・B も存在する。§ の章は grep -c '^## §' が 10 を返すことで確認し、付録は grep -c '^## 関連資料\|^## 章マップ' が 2 を返すことで確認する。付録の見出しは § を持たないため、前者の条件だけでは付録の存在を検証できない
検査2 根拠の実在記入した file:line 形式の根拠について、ファイルが source_dir 配下に実在することを確認する。実在しない根拠が 1 件でもあれば不合格とする
検査3 プレースホルダの残存APIKEY・APIID・METHOD・PATH・FEATUREKEY・SOURCEREF が本文に残っていないことを確認する

§7制約と既知の限界

  • Python 以外の言語は未実装で、status=ERROR を返して中断する
  • 呼び出しの追跡は 2 段までとし、それ以上は要確認事項へ積む
  • 盲検ではないため、画面詳細設計書と同じ品質保証を期待できない
  • middleware と unresolved のユニットは対象外とする
