## いつ使うか

機能設計書を作りたいとき、機能単位の集約した設計書を書きたいとき、複数の接続窓口をまとめた設計書を書きたいとき。

## いつ使わないか

機能一覧のページを作るとき（→ generating-feature-list-for-reverse-docs を使う）、接続窓口ごとの詳細設計書を作るとき（→ generating-api-detail-design-for-reverse-docs を使う）、画面の詳細設計書を作るとき（→ generating-reverse-detailed-design を使う）。

# 正本: reverse-docs-skills

# 機能設計書の執筆スキル

工程全体は orchestrating-ai-development-setup が案内する。本スキルは機能単位の集約設計書の執筆のみを担い、単独起動できる。起動引数は feature_manifest_path・output_dir・template_root の 3 つで、これらを渡せば動く。`unit_kind` は **feature 固定** であり、引数では受け取らない。

機能一覧の生成スキル（`generating-feature-list-for-reverse-docs`）は一覧 HTML のみを担い、設計書の雛形展開・生成・記入をしないと明記している。本スキルがその先を引き受け、テンプレート `リバース検証/機能/機能設計書.md` を展開して記入する。

## 集約設計書としての書き分け

機能設計書は集約設計書である。構成要素（API・画面・実行ファイル）の個別仕様は各構成要素の設計書を正とし、本書は値を再掲せずパスで参照する。

1 つの機能に複数のエンドポイントが同居する構成を前提とする。この構成で本書が担う固有の役割は次の 2 つであり、いずれも **機能側に 1 箇所だけ** 記述する。

| 対象 | 記述先 | 規約 |
|---|---|---|
| 共通処理 | §7.1 機能内の呼び出し一覧 | 複数の構成要素が同じ内部ヘルパーを呼ぶ場合、そのヘルパーを機能設計書に 1 回だけ記述する。各構成要素の個別設計書には重複して書かず、参照に留める |
| 共有状態 | §6.2 共有ストア・共有領域 | 複数の構成要素が同じ記憶域（セッションテーブル・共有ストア・一時領域）を介して連携する場合、その受け渡しを機能設計書に 1 回だけ記述する |

同じ内容を機能設計書と個別設計書の両方へ書くことを禁止する。2 つ目の実体を作ると、片方だけが更新される穴が生まれる。

## 実装契約の扱い（本スキルは書かない）

機能設計書は詳細設計の段階を持たない（配置の定義 `design-unit-layout.json` の `feature.phases.detail` が空）。実装水準の記述（どのファイルのどの関数か・型は何か・何に依存するか）は本書に書かない。書く場所は各構成要素の個別設計書の §実装契約（API は §9、バッチ・帳票・外部連携・テーブルは §7、画面は §15）である。詳細は `delivery-payload/references/実装契約定義.md` を参照する。

複数の構成要素が同じ実装（共有するデータ構造など）を使う場合も、機能設計書へは書かない。その実装を最初に定義した構成要素の個別設計書の §実装契約へ 1 回だけ記述し、他の構成要素は自分の §実装契約の「依存」の行へ、定義元の設計書へのパスを根拠として書く。値の再掲はしない。

## 使用タイミング

- 機能一覧が生成済みで、機能単位の集約設計書を作りたいとき
- 前提: `<output_dir>/<manifestsRoot>/feature-manifest.json` が生成済みであること（`manifestsRoot` は output-layout の物理配置キー。既定値 `docs/manifests`）
- 起動引数:
  - `feature_manifest_path`（必須。機能一覧マニフェストの絶対パス）
  - `output_dir`（必須。設計書の出力先ルート）
  - `template_root`（必須。テンプレート群のルート。実体は `delivery-payload/templates/`）
  - `unit_manifests`（任意。配下ユニットの拡張マニフェストのパス配列。API 一覧・画面一覧等。省略時は `<output_dir>/<manifestsRoot>/` 配下を機械的に列挙する）
  - `design_docs_root`（任意。構成要素の個別設計書のルート。参照パスの実在確認に使う）
  - `feature_keys`（任意。対象を絞る場合の機能キー配列。省略時は全件）

## 出力

| 項目 | 機能設計書 | 機能テスト設計書 | 機能単体テスト設計書 |
|---|---|---|---|
| 出力フォルダ | `<output_dir>/<featureUnitRoot>/feature-<機能識別子>/<unitPhaseDirNames.basic>/` | `<output_dir>/<featureUnitRoot>/feature-<機能識別子>/<unitTestDesignDir>/` | `<output_dir>/<featureUnitRoot>/feature-<機能識別子>/<unitTestDesignDir>/` |
| 出力ファイル | `機能設計書.md` | `機能テスト設計書.md` | `機能単体テスト設計書.md` |
| テンプレート | `<template_root>/リバース検証/機能/機能設計書.md` | `<template_root>/リバース検証/機能/機能テスト設計書.md` | `<template_root>/リバース検証/機能/機能単体テスト設計書.md` |

`featureUnitRoot` は output-layout の物理配置キー（既定値 `docs/design/features`）。表示用 `kindLabels.feature` は path に使わない。`unitPhaseDirNames.basic` は output-layout の `unitPhaseDirNames.basic` の値（既定値 `basic-design`）であり、scaffold-design-unit.sh が実際に展開する配置フォルダ名と一致させる（1-210）。`feature` の `phases.basic` は `機能設計書.md`、`phases.test` は `機能テスト設計書.md` と `機能単体テスト設計書.md` を宣言する。本スキルは `機能設計書.md` を Phase 3で、テスト設計書2点をPhase 4で記入する。

テスト成果物は全種別共通で、<unitTestDesignDir>/機能テスト設計書.md（設計単位1つの外部の振る舞い）と機能単体テスト設計書.md（関数・メソッド単位）の2文書とする。観点とケースは各文書の共通12節へ統合し、単位配下へ結合テスト文書を生成しない。

2文書とも本スキルの成果物である。機能テスト設計書は機能設計で確定した業務フローから、機能単体テスト設計書は詳細設計または入力資料で確定した関数・メソッドから観点とケースを記入する。対象関数が無い場合も雛形のまま完了せず、§1と§2に根拠付きで「該当なし」を記入する。完了時は両文書に未置換プレースホルダがなく、12見出し検査に合格していなければならない。

テンプレートの各章は表の列見出しと記入規則だけを持つ。値の欄は執筆時に埋める。

`<機能識別子>` はマニフェストの `unitId` を使う。`unitId` が空（`null` または空文字）の場合は `unitKey` を使う。両方が空の場合だけ当該機能を生成せず、`status=ERROR` で中断して hint に「出力先の識別子が確定しない」と当該機能の `unitNameGuess` を記録する。

実マニフェストでは `unitId` が全件空のことがある。一覧生成側が `unitId` を非必須フィールドとして扱うためである。合成フィクスチャでは埋まっていることが多く、この状態は実データでしか現れない。

`unitKey` をディレクトリ名に使う場合、パス区切り（`/`）と制御文字をそのまま使わない。含む場合はハイフンへ置き換えて使い、置換した事実を当該設計書の 要確認事項一覧へ記録する。

## 進捗管理（必須手順）

スキル開始時に `TaskCreate` で Phase 1〜5 のタスクを登録する。各 Phase 開始時に該当タスクを `in_progress` に、完了時に `completed` へ `TaskUpdate` で更新する。Phase 5 から Phase 3 または Phase 4 へ差し戻す場合は該当タスクを `in_progress` に戻す。実行環境に TaskCreate/TaskUpdate が存在しない場合は、出力先ディレクトリ内のタスク台帳ファイル（`task-ledger.md`）で同等の Phase 遷移記録を代替する。

## Phase 1: 起動引数の確認と対象確定

## Step 1-1: 起動引数の確認と対象確定

- **Step 1**: 必須 3 引数の実在を確認する（`test -f` / `test -d`）。いずれかが欠ける場合は `status=ERROR` で停止する。完了条件: 3 引数すべてが実在する
- **Step 2**: `feature_manifest_path` を Read し、`unitKind` が `feature` であること、`units` が 1 件以上あることを確認する。完了条件: マニフェストが確認済み
- **Step 3**: 配下ユニットのマニフェストを確定する。`unit_manifests` が渡されていればその集合、無ければ `<output_dir>/<manifestsRoot>/` 配下の拡張マニフェストを機械的に列挙する。完了条件: 配下ユニットの入力が確定済み
- **Step 4**: 対象機能を確定する。`feature_keys` が渡されていればその集合、無ければ `kind` が `feature` の全件とする。`unresolved` は対象外とする。完了条件: 対象機能の一覧が確定済み

**完了**: 3 引数が実在し、マニフェストが確認済みで、配下ユニットと対象機能が確定している

## Phase 2: 集約材料の収集

## Step 2-1: 機能ごとの材料収集

対象機能 1 件につき次を行う。

- **Step 1**: 機能マニフェストの `relatedScreens`・`relatedApis`・`relatedTables` から構成要素を確定し、配下ユニットのマニフェストと突合して識別子と個別設計書のパスを引く。突合できない参照は 要確認事項一覧へ記録する。完了条件: 構成要素一覧が確定済み
- **Step 2**: 構成要素の個別設計書が実在する場合はそれを Read し、共通処理と共有状態の候補を拾う。複数の構成要素が同じヘルパーまたは同じ記憶域を指している箇所を、機能側へ集約する対象として印を付ける。完了条件: 集約対象が特定済み
- **Step 3**: 個別設計書が存在しない構成要素については、値を推測で補わない。当該構成要素の行は識別子とパスだけを記載し、詳細は 要確認事項一覧へ回す。完了条件: 不足分が確定できなかった事項として整理済み

**完了**: 対象機能全件について、構成要素一覧と集約対象が揃っている

## Phase 3: 執筆

### テンプレートの配置

執筆の前に、テンプレートを出力先へ配置する。手作業で Read と Write を行わず、次のスクリプトを呼ぶ。

```bash
bash generation-engine/scripts/scaffold-design-unit.sh feature basic <output_dir> <識別子> <表示名> <template_root>
```

`<kind>` と `<phase>` は本スキルの担当に固定する（feature は basic phase のみを持ち、detail phase は無い）。配置済みのファイルへ記入する形で執筆する。

配置に失敗した場合は執筆へ進まず、`status=ERROR` を返す。

### 表題の形式と前付けとの関係

本文冒頭の `# ` 見出し（表題）は「<対象名> <役割名>」の形式とする。役割名はファイル名から拡張子を除いた文字列と完全に一致させ、記入時に書き換えない。対象名（表示名）トークンは雛形の展開時に自動置換済みであり、記入時に対象名部分を書き換えない。対象名の末尾が役割名の先頭と同じ語で終わる場合は、対象名側から重複する語を落とし、同じ語が2回続けて現れないようにする（例: 対象名「注文API」＋ 役割名「API詳細設計書」→ 表題「注文API詳細設計書」）。

前付け（frontmatter）の識別名（`<種別>KEY`・`<種別>ID` 等）と本文の表題は、一致を求めない。前付けはマニフェストの識別子をそのまま使う機械可読の値であり、表題は対象の表示名を使う人が読む見出しである。両者が異なる文字列になっても構わない。

## Step 3-1: テンプレートの展開と記入

**使用ツール**: Read / Write

- **Step 1**: 配置済みの `<output_dir>/<featureUnitRoot>/feature-<機能識別子>/<unitPhaseDirNames.basic>/機能設計書.md` へ記入する。`<機能識別子>` の決め方は「出力」節の規約に従う。frontmatter の `FEATUREKEY`・`FEATUREID`・`CATEGORY`・`SOURCEREF` をマニフェストの値で置換する。前付けの `feature_id`（テンプレートの `FEATUREID`）にはマニフェストの `unitId` を写す。`unitId` が空なら `feature_id` も空欄にし、その旨を 要確認事項一覧へ記録する。前付けの `source_ref`（テンプレートの `SOURCEREF`）にはマニフェストの `sourceFile` を写す。`sourceFile` は機能一覧生成側が付与しない非必須フィールドである(1-254。機能は複数の実装ファイルを束ねる集約であり、代表となる単一のソースファイルを持たない)。マニフェストに値が無い場合、`source_ref` は空欄のままとし、代表ファイルを推測で補わず、その旨を 要確認事項一覧へ記録する。完了条件: 全対象機能のファイルが配置済み
- **Step 2**: §1 から §10 を記入する。構成要素の個別仕様を再掲せず、§2.1 の表にはパス参照だけを置く。共通処理は §7.1 へ、共有状態は §6.2 へ、それぞれ 1 箇所だけ記述する。完了条件: §1 から §10 の記入が完了している
- **Step 3**: 記入できなかった章と項目を 要確認事項一覧へ列挙する。対象コードの位置は記録しない。完了条件: 当該資料へ確定できなかった事項が記録済み

**完了**: 全対象機能の設計書が記入済みである

## Phase 4: 機能テスト設計書・機能単体テスト設計書の執筆

## Step 4-1: 2つのテスト設計書を執筆する

**使用ツール**: Read / Write

テスト設計書では、§1を正常・異常・境界を含む全観点の一覧とする。
§5と§6には、§1のうち異常・境界の観点を§1と同じ観点キーで詳述する。
§5と§6では新しいケースを定義せず、§1の全観点に対応する実行ケースを§2だけへ記載する。
実行するテストの件数は、§2のデータ行数だけで数える。

機能テスト設計書（外部振る舞い用）の情報源は **Phase 3 で書き上げた機能設計書だけ**とする。原本コードも構成要素の個別設計書も読まない。機能単体テスト設計書（単体用）の情報源は、構成要素の詳細設計書または Phase 1〜2 で確定した入力資料に現れる関数・メソッドだけとする。対象関数が無い場合は、§1と§2に根拠付きで「該当なし」を記入する。どちらの文書も雛形のまま完了としてはならない。

```bash
bash generation-engine/scripts/scaffold-design-unit.sh feature test <output_dir> <識別子> <表示名> <template_root>
```

機能テスト設計書は、機能設計書の業務フローを検証する。構成要素（API・画面・実行ファイル）それぞれの関数単位テストを再掲せず、複数の機能・APIをまたぐ結合テストも扱わない。機能単体テスト設計書は、構成要素の詳細設計書または入力資料で確定した関数・メソッドを検証する。

- 複数の構成要素をまたぐ処理の流れが、意図した順序で動くか
- 構成要素が共有する状態（セッション・共有ストア・一時領域）の受け渡しが正しいか
- ある構成要素が失敗したとき、機能全体としてどう振る舞うか
- 機能内の共通処理（§7.1 機能内の呼び出し一覧に記載した内部ヘルパー）が、どの経路から呼ばれても同じ結果になるか

1. `<output_dir>/<featureUnitRoot>/feature-<機能識別子>/<unitTestDesignDir>/機能テスト設計書.md` と `機能単体テスト設計書.md` へテンプレートを配置して Read し、それぞれの12見出しを保持して記入する
2. 機能テスト設計書は、機能設計書の §6.2 共有ストア・共有領域・§7.1 機能内の呼び出し一覧・業務フロー・業務ルール・エラーと業務メッセージの各章から、上記の観点に該当する事項だけを作る。構成要素の個別仕様に由来する観点は作らず、各観点に由来する機能設計書の章を記録する。機能設計書で確定していない事項からは観点を作らず、要確認事項一覧へ移す
3. 機能単体テスト設計書は、構成要素の詳細設計書または入力資料で確定した関数・メソッドから観点とケースを作り、各観点に由来する資料と関数・メソッドを記録する。対象関数が無い場合は、§1と§2に根拠付きで「該当なし」を記入する
4. 2文書とも12見出しを保持したまま出力先へ Write する

**完了**: 機能テスト設計書・機能単体テスト設計書が出力され、前者の全観点は機能設計書の業務フローに由来して由来する章が、後者の全観点は詳細設計書または入力資料の関数・メソッドに由来して由来する資料が記録されている。対象関数が無い場合は、後者の§1と§2に根拠付きの「該当なし」が記入されている

## Phase 5: 検証

## Step 5-1: 機械検査

次の 7 つを実行する。テスト設計書2点に関する検査（由来の記録検査・情報源の検査）の不合格は Phase 4 で書き直し、それ以外の検査の不合格は Phase 3 で書き直して Phase 5 を再実行する。上限 3 回で収束しなければ `status=ERROR` とする。

- **検査1 章の完備**: 生成した各設計書に §1 から §11 が存在し、あわせて章マップも存在する。§ の章は `grep -c '^## §'` が 11 を返すことで確認し、§11 が関連資料であることと、`grep -c '^## 章マップ'` が 1 を返すことを確認する
- **検査2 全章の充足**: §1 から §11 の各章について、表の本文行が 1 行以上あるか、または当該章に対応する項目が 要確認事項一覧へ回っているかのいずれかを満たす。どちらも満たさない空章があれば不合格とする
- **検査3 参照実在**: §2.1 に記載した個別設計書のパスが実在する。`design_docs_root` が渡されていない場合は本検査を skip し、その旨を返却の hint に記録する
- **検査4 配置の検査**: `bash generation-engine/scripts/scaffold-design-unit.sh --verify feature basic <output_dir> <識別子>` と `bash generation-engine/scripts/scaffold-design-unit.sh --verify feature test <output_dir> <識別子>` を実行し、機能設計書・機能テスト設計書・機能単体テスト設計書の必須ファイル・トークン・章・配置を確認する。続けて `bash <template_root>/rules/checkers/check-unit-test-design-doc-sections.sh --check-file <機能テスト設計書.md>` と `bash <template_root>/rules/checkers/check-unit-test-design-doc-sections.sh --check-file <機能単体テスト設計書.md>` を実行し、両文書の12見出しの名前・順序・件数がテンプレートと一致することを確認する
- **検査5 プレースホルダの残存**: `FEATUREKEY`・`FEATUREID`・`CATEGORY`・`SOURCEREF` が本文に残っていない
- **検査6 由来の記録検査**: 機能テスト設計書の §1 テスト観点と §5 異常系の全行に由来する機能設計書の業務フローの章が、機能単体テスト設計書の同じ行に由来する詳細設計書または入力資料の関数・メソッドが記録されていることを確認する。対象関数が無い場合は、後者の§1と§2に根拠付きの「該当なし」があることを確認する

## 重要な注意事項

- 構成要素の個別仕様を再掲しない。値を持つのは個別設計書であり、本書はパスで参照する
- 共通処理と共有状態は機能側に 1 箇所だけ書く。個別設計書との二重記載を禁止する
- 原本コードを直接読まない。情報源は機能一覧マニフェスト・配下ユニットのマニフェスト・構成要素の個別設計書に限る
- 個別設計書が無い構成要素の内容を推測で補わない。要確認事項一覧へ回す
- 本スキルの成果物は機能設計書.md とテスト設計書2点（機能テスト設計書.md・機能単体テスト設計書.md）の 3 点。機能一覧の生成・更新は行わない
- 機能テスト設計書は1つの機能の業務フローを扱い、複数の機能・APIをまたぐ結合テストは扱わない
- 往復検証の対象外である。機能には対応する原本ファイルが存在せず、突合の相手がない

## 予想を裏切る挙動

- 構成要素の個別設計書が 1 枚も無い場合でも `status=ERROR` にしない。構成要素一覧を持つ設計書と、確定できなかった事項を持つ根拠記録資料を生成し、`unresolved_count` を大きくして返す
- 原本コードを読まないため、個別設計書の質が本書の質の上限になる
- 検査2 は「空章を許さない」ではなく「空章なら要確認事項一覧へ回っていること」を求める。書けないことを記録すれば合格する
- 実マニフェストでは `unitId` が全件空のことがある。その場合の出力先は `unitKey` 由来になるため、合成フィクスチャで確認した出力先と実データでの出力先が一致しないことがある
