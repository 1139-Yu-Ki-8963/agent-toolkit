# 機能設計書の執筆スキル

工程全体は orchestrating-reverse-docs-flow が案内する。本スキルは機能単位の集約設計書の執筆のみを担い、単独起動できる。起動引数は feature_manifest_path・output_dir・template_root の 3 つで、これらを渡せば動く。`unit_kind` は **feature 固定** であり、引数では受け取らない。

機能一覧の生成スキル（`generating-feature-list-for-reverse-docs`）は一覧 HTML のみを担い、設計書の雛形展開・生成・記入をしないと明記している。本スキルがその先を引き受け、テンプレート `リバース検証/機能/機能設計書.md` を展開して記入する。

## 集約設計書としての書き分け

機能設計書は集約設計書である。構成要素（API・画面・実行ファイル）の個別仕様は各構成要素の設計書を正とし、本書は値を再掲せずパスで参照する。

1 つの機能に複数のエンドポイントが同居する構成を前提とする。この構成で本書が担う固有の役割は次の 2 つであり、いずれも **機能側に 1 箇所だけ** 記述する。

| 対象 | 記述先 | 規約 |
|---|---|---|
| 共通処理 | §7.1 機能内の呼び出し一覧 | 複数の構成要素が同じ内部ヘルパーを呼ぶ場合、そのヘルパーを機能設計書に 1 回だけ記述する。各構成要素の個別設計書には重複して書かず、参照に留める |
| 共有状態 | §6.2 共有ストア・共有領域 | 複数の構成要素が同じ記憶域（セッションテーブル・共有ストア・一時領域）を介して連携する場合、その受け渡しを機能設計書に 1 回だけ記述する |

同じ内容を機能設計書と個別設計書の両方へ書くことを禁止する。2 つ目の実体を作ると、片方だけが更新される穴が生まれる。

## 使用タイミング

- 機能一覧が生成済みで、機能単位の集約設計書を作りたいとき
- 前提: `<output_dir>/一覧/機能一覧/feature-manifest.json` が生成済みであること
- 起動引数:
  - `feature_manifest_path`（必須。機能一覧マニフェストの絶対パス）
  - `output_dir`（必須。設計書の出力先ルート）
  - `template_root`（必須。テンプレート群のルート。実体は `shared/templates/`）
  - `unit_manifests`（任意。配下ユニットの拡張マニフェストのパス配列。API 一覧・画面一覧等。省略時は `<output_dir>/一覧/` 配下を機械的に列挙する）
  - `design_docs_root`（任意。構成要素の個別設計書のルート。参照パスの実在確認に使う）
  - `feature_keys`（任意。対象を絞る場合の機能キー配列。省略時は全件）

## 出力

| 項目 | 値 |
|---|---|
| 出力フォルダ | `<output_dir>/機能/feature-<機能ID>/` |
| 出力ファイル | `機能設計書.md` |
| テンプレート | `<template_root>/リバース検証/機能/機能設計書.md` |

## 進捗管理（必須手順）

スキル開始時に `TaskCreate` で Phase 1〜4 のタスクを登録する。各 Phase 開始時に該当タスクを `in_progress` に、完了時に `completed` へ `TaskUpdate` で更新する。Phase 4 から Phase 3 へ差し戻す場合は該当タスクを `in_progress` に戻す。実行環境に TaskCreate/TaskUpdate が存在しない場合は、出力先ディレクトリ内のタスク台帳ファイル（`task-ledger.md`）で同等の Phase 遷移記録を代替する。

## Phase 1: 起動引数の検収と対象確定

## Step 1-1: 起動引数の検収と対象確定

- **Step 1**: 必須 3 引数の実在を確認する（`test -f` / `test -d`）。いずれかが欠ける場合は `status=ERROR` で停止する。完了条件: 3 引数すべてが実在する
- **Step 2**: `feature_manifest_path` を Read し、`unitKind` が `feature` であること、`units` が 1 件以上あることを確認する。完了条件: マニフェストが検収済み
- **Step 3**: 配下ユニットのマニフェストを確定する。`unit_manifests` が渡されていればその集合、無ければ `<output_dir>/一覧/` 配下の拡張マニフェストを機械的に列挙する。完了条件: 配下ユニットの入力が確定済み
- **Step 4**: 対象機能を確定する。`feature_keys` が渡されていればその集合、無ければ `kind` が `feature` の全件とする。`unresolved` は対象外とする。完了条件: 対象機能の一覧が確定済み

**完了**: 3 引数が実在し、マニフェストが検収済みで、配下ユニットと対象機能が確定している

## Phase 2: 集約材料の収集

## Step 2-1: 機能ごとの材料収集

対象機能 1 件につき次を行う。

- **Step 1**: 機能マニフェストの `relatedScreens`・`relatedApis`・`relatedTables` から構成要素を確定し、配下ユニットのマニフェストと突合して識別子と個別設計書のパスを引く。突合できない参照は §11 要確認事項へ記録する。完了条件: 構成要素一覧が確定済み
- **Step 2**: 構成要素の個別設計書が実在する場合はそれを Read し、共通処理と共有状態の候補を拾う。複数の構成要素が同じヘルパーまたは同じ記憶域を指している箇所を、機能側へ集約する対象として印を付ける。完了条件: 集約対象が特定済み
- **Step 3**: 個別設計書が存在しない構成要素については、値を推測で補わない。当該構成要素の行は識別子とパスだけを記載し、詳細は §11 要確認事項へ回す。完了条件: 不足分が要確認事項として整理済み

**完了**: 対象機能全件について、構成要素一覧と集約対象が揃っている

## Phase 3: 執筆

## Step 3-1: テンプレートの展開と記入

- **Step 1**: `<template_root>/リバース検証/機能/機能設計書.md` を Read する。読み込んだ内容を `<output_dir>/機能/feature-<機能ID>/機能設計書.md` へ書き出す。`<機能ID>` はマニフェストの `unitId` を使う。中間ディレクトリが無ければ作成する。frontmatter の `FEATUREKEY`・`FEATUREID`・`CATEGORY`・`SOURCEREF` をマニフェストの値で置換する。完了条件: 全対象機能のファイルが配置済み
- **Step 2**: §1 から §10 を記入する。構成要素の個別仕様を再掲せず、§2.1 の表にはパス参照だけを置く。共通処理は §7.1 へ、共有状態は §6.2 へ、それぞれ 1 箇所だけ記述する。完了条件: §1 から §10 の記入が完了している
- **Step 3**: 記入できなかった章と項目を §11 要確認事項一覧へ列挙する。キーは連番を禁じ、内容を要約した意味語で付ける。完了条件: §11 が埋まっている

**完了**: 全対象機能の設計書が記入済みである

## Phase 4: 検証

## Step 4-1: 機械検査

次の 4 つを実行する。1 つでも不合格なら Phase 3 へ戻る。上限 3 回で収束しなければ `status=ERROR` とする。

- **検査1 章の完備**: 生成した各設計書に §1 から §11 が存在し、あわせて付録 A・B も存在する。§ の章は `grep -c '^## §'` が 11 を返すことで確認し、付録は `grep -c '^## 関連資料\|^## 章マップ'` が 2 を返すことで確認する
- **検査2 全章の充足**: §1 から §11 の各章について、表の本文行が 1 行以上あるか、または当該章に対応する項目が §11 要確認事項へ回っているかのいずれかを満たす。どちらも満たさない空章があれば不合格とする
- **検査3 参照実在**: §2.1 に記載した個別設計書のパスが実在する。`design_docs_root` が渡されていない場合は本検査を skip し、その旨を返却の hint に記録する
- **検査4 プレースホルダの残存**: `FEATUREKEY`・`FEATUREID`・`CATEGORY`・`SOURCEREF` が本文に残っていない

**完了**: 4 検査すべてが合格している（検査3 の skip を含む）

## 返却

本スキルは orchestrating-reverse-docs-flow の契約に準拠する。完了時に以下を返す。

- `status`: `DONE | ERROR`
- `artifacts`: 生成した機能設計書.md のパスの配列
- `unit_kind`: `feature`（固定値）
- `authored_count`: 生成した設計書の枚数
- `unresolved_count`: 全設計書の §11 に記録された要確認事項の合計件数

| ツール | 用途 |
|---|---|
| Read | マニフェスト・テンプレート・構成要素の個別設計書の参照 |
| Grep/Glob | 配下ユニットのマニフェストの列挙、プレースホルダ残存の確認 |
| Bash | 参照パスの実在確認、章の完備の確認 |
| Write | 設計書の書き出し |

| TaskCreate/TaskUpdate | Phase 1〜4 の進捗管理 |

## 重要な注意事項

- 構成要素の個別仕様を再掲しない。値を持つのは個別設計書であり、本書はパスで参照する
- 共通処理と共有状態は機能側に 1 箇所だけ書く。個別設計書との二重記載を禁止する
- 原本コードを直接読まない。情報源は機能一覧マニフェスト・配下ユニットのマニフェスト・構成要素の個別設計書に限る
- 個別設計書が無い構成要素の内容を推測で補わない。§11 要確認事項へ回す
- 本スキルの成果物は機能設計書.md のみ。機能一覧の生成・更新は行わない
- 往復検証の対象外である。機能には対応する原本ファイルが存在せず、突合の相手がない

## 予想を裏切る挙動

- 構成要素の個別設計書が 1 枚も無い場合でも `status=ERROR` にしない。構成要素一覧と要確認事項だけを持つ設計書を生成し、`unresolved_count` を大きくして返す
- 原本コードを読まないため、個別設計書の質が本書の質の上限になる
- 検査2 は「空章を許さない」ではなく「空章なら要確認事項へ回っていること」を求める。書けないことを記録すれば合格する
