# 検証で繰り返し指摘された事項のうち未解決のもの

外部の検証（この配布物を対象コードに適用しない状態で、配布物そのものを対象コードとして機械検証すること）で繰り返し指摘され、内部の記録では「完了」と記録した後も指摘が再発した事項を、ここへ記載する。台帳側の記録（`docs/tasks/指摘改善一覧.md`）はこのリポジトリ自身の作業記録であり配布対象外のため、配布物に同梱するこのファイルへ写す。

各項目は「現象」「現在の実測」「なぜ完全には解決していないか」「解決の条件」の4点で書く。実測には検証した時点のコミットハッシュを添える（`.claude/rules/always/verification/reverse-verification/rule.md` 規約4に準じる）。

## 設計文書だけからの一覧組み立てが、原本コードの参照解決に失敗し得る

**現象**: `build-manifests-from-docs.sh`（設計文書の frontmatter から API・テーブル・バッチ・帳票・外部連携・機能の一覧マニフェストを組み立てるスクリプト）は、各設計文書が記す `source_ref`（原本コードのファイルパス）の実在を検証項目に含む。この実在確認は、原本コード本体ではなく、設計文書の配置先（`<出力先>/docs/design/<種別>/`）を起点に相対解決する。

**現在の実測**（コミット `55bcd14b0cdfa5b971801b7aae31630c43034bb2` 時点）: `generation-engine/samples` を複製した検証用領域で `build-manifests-from-docs.sh` を直接実行したところ、6種別中5種別（API・バッチ・外部連携・帳票・テーブル）で「sourceFile-実在」検査が不合格になった。原因は、設計文書が記す `source_ref`（例: `src/api/audit.py`）が、原本コードの実際の置き場（対象リポジトリのルート）ではなく、設計文書の配置先を起点に解決されるため、原本コードそのものを設計文書の配置先へ複製しない限り検証を通らないことによる。`build-portal.sh --build-manifests-from-docs` はこの検証が1種別でも不合格になると全体を打ち切る実装であるため、この状態では6種別の拡張マニフェスト（`<種別>-manifest.ext.json`）が1件も生成されない。

一方、改善課題1-61の対応により、`build-portal.sh --build-manifests-from-docs` の自己テスト（ケース46）では、原本コードの複製をあらかじめ検証用フィクスチャへ用意することで、6種別すべての拡張マニフェストが生成されることを確認済みである。つまり、原本コードを設計文書の配置先へ複製する前提を満たせば動作するが、その前提を満たす手順は配布物のどこにも明文化されていない。

**なぜ完全には解決していないか**: 設計文書だけから一覧を組み立てるという触れ込みに反し、実際には原本コードの物理的な配置（設計文書の配置先を起点に解決できる場所）が要る。この前提が満たされない対象リポジトリでは、生成器だけでは一覧を再現できず、実行側が原本コードを適切な場所へ配置する独自の手順を用意する必要がある。

**解決の条件**: 次のいずれかが満たされること。
1. `source_ref` の実在確認を、設計文書の配置先起点ではなく、対象リポジトリのルート起点でも解決できるようにする
2. 原本コードを設計文書の配置先へ複製する手順を `build-portal.sh --build-manifests-from-docs` の使い方として明文化し、`--pre-build` 受け口等で自動化する

## ブラウザを使う自己テストの全体完走が、実行のたびに未確認のまま残る

**現象**: `build-portal.sh` の自己テストのうち、実ブラウザでの計測を伴うケース（用語辞書ページの意味投影・UI契約の検証）は、環境に Playwright パッケージが導入されていない場合スキップされる仕様である。導入されていれば実行され、単体では合格することを確認しているが、67ケースを超える自己テスト全体を、この計測ケースを含めて通しで完走させた記録が、繰り返し確認しようとするたびに見当たらない。

**現在の実測**（コミット `55bcd14b0cdfa5b971801b7aae31630c43034bb2` 時点）: 当該ケースが呼ぶ検査本体（`test-semantic-glossary-page.cjs`）を、Playwright パッケージが導入済みの環境から単体で実行したところ、`self-test: 2 PASS, 0 FAIL` で完了した。この実行は、通常のサンドボックス制約下ではブラウザの起動に失敗し判定不能（`[UNKNOWN]`）になり、制約を外した実行でのみ合格した。`build-portal.sh --self-test` 全体（67ケース超）を、この計測ケースを含めて通しで実行した記録は、今回も確認できなかった。所要時間が長い（過去の記録で815秒超）ため、確認を試みるたびに完走前に時間切れとなり、未確認のまま残っている。

**なぜ完全には解決していないか**: 個別の検査対象は合格することを繰り返し確認できているが、「自己テスト全体が実ブラウザ計測を含めて完走する」という、指摘が求める形そのものの確認記録がない。確認しようとするたびに、環境準備（Playwright 導入・サンドボックス制約の解除）と長い所要時間の両方が必要になり、通しでの完走確認が後回しになり続けている。

**解決の条件**: Playwright 導入済みかつサンドボックス制約なしの環境で、`build-portal.sh --self-test` を最後まで実行し、実ブラウザ計測を含む全ケースの合否を記録すること。長い所要時間そのものが障害になる場合は、計測ケースだけを分離して独立に実行できる入口を用意すること。

## 検証スクリプト群の集約実行で、失敗が0件にならない状態が繰り返し観測される

**現象**: 検証スクリプト群の自己テストを一括実行する集約（`run-layer-machine-checks.sh`）は、対象スクリプトの数が増減するたびに実行され、そのつど失敗（FAIL）の本数が記録されている。過去に「失敗5本」（このうち1本は `run-verification-loop.sh` が参照する `check-self-contained.sh` の不在という確定的な欠陥）が指摘され、その後「失敗0本」を根拠に完了と記録した。ところが、その後の実行でも失敗が0本にならない状態が繰り返し観測されている。

**現在の実測**（コミット `55bcd14b0cdfa5b971801b7aae31630c43034bb2` 時点）: 指摘が挙げた確定的な欠陥（`check-self-contained.sh` の不在）は解消済みで、`run-verification-loop.sh --self-test` の該当項目（依存-スクリプト実在）は単体で合格し、同スクリプトの自己テスト全体も10件中10件合格した。一方、対象スクリプト全体を集約実行した直近の実測では、対象192本のうち成功189本・失敗1本・判定不能2本であり、失敗0本ではなかった。この1本がどのスクリプトかは、今回の確認時点では特定できていない（集約実行は1回あたり長い時間を要するため、原因の特定は次回の対応へ持ち越す）。

**なぜ完全には解決していないか**: 指摘が挙げた具体的な欠陥は解消したが、「集約実行で失敗が0本になること」という完了の根拠そのものが、その後の実行で再現していない。対象スクリプトの数は往復検証のたびに増減するため、ある時点で0本だったとしても、次の時点で新たな失敗が発生し得る。この性質を踏まえた継続的な確認の仕組みが無いまま、単発の実測値だけを根拠に完了と記録してきたことが、指摘の再発につながっている。

**解決の条件**: 直近で失敗した1本を特定し、原因を修正すること。加えて、集約実行の結果を単発の実測値としてではなく、`record-verification-result.sh` による記録と `compare-with-previous.sh` による前回比較を毎回の対応に組み込み、失敗が新たに発生した場合に検知できるようにすること。

## 参考: 資料参照切れの指摘は、機械検査の常設によって解消済みである

配布物内の資料参照（相対リンク）が実在しないファイルを指す指摘は、`check-payload-references.sh` による機械検査で継続的に確認できる状態になっている。同スクリプトは `--self-test` を実装しており、第1層の集約実行（`run-layer-machine-checks.sh`）が対象スクリプトを動的に収集する際の対象に自動的に含まれる（`run-layer-machine-checks.sh --list` で確認済み）。このため、資料参照切れが再発した場合は、往復検証のたびに実行する第1層の集約実行で機械的に検知される。現在の実測（コミット `55bcd14b0cdfa5b971801b7aae31630c43034bb2` 時点）では `走査 31 件 / 違反 0 件` である。
