# 設計書の書き方の決まり

## 概要

設計書を書くときの記載形式と、各設計書が満たすべき完了状態の取り決め。

対象は要件定義書・基本設計書・詳細設計書の 3 文書である。上流の完了状態を満たさないまま下流の執筆へ進むと、下流で前提の欠落が見つかり手戻りになる。

本書は設計書に何の節を置くかの目録である。各節をどう書くかは、その主題を持つ規約が定める。目録と規範を分けることで、同じ主題を 2 箇所で定義しない。

## 規則

| 規則 | 内容 | 検査 |
|---|---|---|
| 追記章と補足章を作らない | 内容を足すときは適切な既存章を探して統合する。統合先がなければ章立てを設計し直し、どこへ置くかを決めてから書く | 静的解析: 設計書の見出しに「追記」「補足」「その他」で始まる章が無いかを走査する |
| 任意記載と省略記載をしない | 途中を「…」で省く書き方を禁じる。インタフェース定義が長い場合も全項目を書く | 静的解析: 設計書の本文に「…」「以下略」「等」で列挙を打ち切る記述が無いかを走査する |
| 要件定義書は合意した範囲を確定させる | 対象範囲・優先度・受入条件を確定する。外部仕様の策定と方式設計に必要な品質と制約も確定してから次工程へ進む | 静的解析: 要件定義書に対象範囲・優先度・受入条件の 3 見出しが存在するかを走査する ／ レビュー: 各見出しの内容が確定しており、外部仕様の策定と方式設計に必要な品質と制約も含めて未確定の記述が残っていないかを確認する |
| 基本設計書は詳細設計を書ける状態を作る | 外部仕様・業務ルールと例外系・非機能要件を満たす方式を確定する。データの整合性とトランザクション境界と排他方針も確定し、詳細設計を書き始める上での不明点を残さない | 静的解析: 基本設計書に完了状態の各項目に対応する見出しが存在するかを走査する ／ レビュー: 各見出しの内容に、詳細設計を書き始める上での不明点が残っていないかを確認する |
| 詳細設計書に設計の理由を書いてよい | 実装仕様と対応する設計の理由は詳細設計書へ記載してよい。「コードと 1 対 1」は理由の記載を禁じる定めではない。理由は仕様の代わりにせず、観測と推定を下記の形式で区別する | 判定不能: 理由が対応する実装仕様と整合しているか、観測と推定が意味上区別され、観測内容または推定根拠が妥当かは自然文の意味を読む必要があり、静的解析では判定できない |
| 本文には成果物を作った作業の単位を指す語を書かない | 生成作業を行った対話エージェント自身の編集単位（やり取りの回・作成途中の一時文書等）を、本文の構成説明として書かない | 静的解析: check-customer-facing-adequacy.sh が対話エージェントの編集単位を指す語（第7カテゴリ）の出現を検査する |
| 継続的な実施を宣言する記述は裏付けの有無を区別する | 継続的に実施・更新・監視する旨を書く場合は、それを担保する仕組み（自動検査・定期実行）が実在することを確認してから書く。仕組みが無い場合は、その旨と、対象に変更が生じた場合に必要な対応（再調査の要否等）を明記する | 判定不能: 裏付けとなる仕組みが実在するかどうかは自然文の意味を読む必要があり、静的解析では判定できない |
| 汎用の更新日欄を個別の事実の時点主張へ転用しない | 設計書の本文が特定の事実の時点を示す必要がある場合は、共通シェルの汎用の更新日表示欄を参照せず、その事実専用の記録（固定の日付記載、または当該事実に連動した専用の欄のいずれか）を持つ。汎用の更新日欄を他の事実の時点主張の根拠に転用しない | 判定不能: 汎用欄への転用の有無は自然文の意味を読む必要があり、静的解析では判定できない |

### 要件定義書

**定義**

要件がシステムに要求する事項を確定し、プロジェクトの範囲・優先度・受入条件を合意する文書である。
何を実現するかと、満たすべき品質と制約を明文化する。これを以降の設計・製造・テストの判断基準とする。

**主な内容**

- 業務要件（目的・業務プロセス・取引や会計や勘定や外部接続などの業務仕様・業務の言葉の決まり）
- 機能要件（利用者と外部システムから見える機能・入力と出力・例外時の要求・権限の要求）
- 非機能要件（性能・可用性・拡張性・セキュリティ・監査・運用・バックアップ・災害対策・保守性）
- 制約条件（法令と規制・社内標準・既存資産・移行条件・稼働時間・ネットワークの制約）
- 受入条件（完了の定義・受入テストの観点・検収条件・品質基準）
- 適用の範囲（対象範囲・対象外・前提条件・関係者の責務・変更管理の方針）

**完了状態**

- 対象範囲・優先度・受入条件が確定している
- 外部仕様の策定と方式設計に必要な要求（品質と制約）が確定している

### 基本設計書

**定義**

要件定義書で確定した要求を実現するための文書である。外部仕様と方式を確定し、詳細設計書を書き始められる状態を作る。
基本設計フェーズの完了とは、詳細設計書をコードと 1 対 1 の日本語記述として書けるだけの前提が、仕様として矛盾なく確定していることを指す。

**主な内容**

- 外部仕様（利用者と外部システムから見える仕様）
  - 画面（項目定義・入力制約・表示編集・遷移・エラー表示・権限制御）
  - 帳票（項目定義・出力条件・出力タイミング・レイアウト要件）
  - 外部インタフェース（形式・項目・コード体系・正常応答と異常応答・タイムアウト・リトライ・冪等性）
- 業務仕様の確定
  - 業務フロー・状態遷移・業務ルール（判定表と計算式）・例外条件
  - 取消と再実行と二重送信の取り扱い
  - 書き方の定義: 業務ルールと判定表は業務の判定の書き方の決まり、計算式は金額と数量の計算の決まり、状態遷移は状態の移り変わりの決まりが定める
- 方式設計（非機能要件を満たすための現実の方式）
  - 性能方式・可用性方式・セキュリティ方式・監査ログ方式・運用方式・バックアップ方式・災害対策方式
  - 書き方の定義: 性能方式は応答の速さと処理の量の決まり、可用性方式は稼働を続けることと復旧の決まり、セキュリティ方式は認証と入力と秘密の値の決まり、監査ログ方式は記録と監視の決まりが定める。運用方式・バックアップ方式・災害対策方式は対応する規約を持たないため本書が目録としてのみ扱う
- データ仕様の確定（詳細設計を開始できるために必要な範囲すべて）
  - 概念と論理の確定（エンティティの論理名・キー・整合性）
  - データフロー・更新責任・整合性の担保方針・保存期間・マスキング方針
  - トランザクション境界の方針・排他の方針・整合性の確保方針
- エラーと例外の仕様確定
  - エラー分類・エラーコード体系・利用者通知・ログ出力・リトライ可否・復旧手順に関わる仕様
- 単体テスト設計書（単体テスト設計書の決まりの定めに従う）

**完了状態**

- 外部仕様が曖昧さなく確定している（画面・帳票・外部インタフェース）
- 業務ルールと例外系（取消・二重送信・リトライ・タイムアウトなど）が矛盾なく確定している（書き方は業務の判定の書き方の決まり・金額と数量の計算の決まり・状態の移り変わりの決まりが定める）
- 非機能要件を満たす方式が確定している（性能・可用性・セキュリティ・監査・運用・災害対策）（書き方は認証と入力と秘密の値の決まり・応答の速さと処理の量の決まり・稼働を続けることと復旧の決まり・記録と監視の決まりが定める）
- データの整合性・トランザクション境界・排他の方針が確定している
- 詳細設計書を書き始める上での不明点が存在しない
- 単体テスト設計書が作成されている

### 詳細設計書

**定義**

基本設計書をもとに、各プログラムを製造できる水準まで内部仕様として確定する文書である。
ひとことで言えばコンパイルできない日本語記述のプログラムであり、コードと 1 対 1 に対応する。

**主な内容**

- クラス設計（クラス・属性・メソッド・可視性）
- メソッド設計（処理概要・前提条件・事後条件・入力と出力・例外）
- ロジック設計（分岐・ループ・判定表・状態遷移・疑似コードとフローチャート）
- 戻り値と引数（戻り値・引数・それぞれの型・有効な範囲・NULL 許容・初期値・桁と精度）
- エラー処理（例外の送出と捕捉・エラーコードの返却・リトライ判定・ログ出力点）
- データ定義（内部で扱うデータ構造の型・有効な範囲・寿命・整合性のチェック点）

**成果物の粒度**

- クラス・メソッド・分岐とループ・戻り値・引数について、それぞれの型や有効な範囲を日本語で記載できる状態
- 不明点があってはならない
- 製造担当が迷わず実装でき、レビューで仕様との差分を検知できる粒度
- コードと 1 対 1 に対応する
- 各プログラムを製造できる水準まで内部仕様を確定し、日本語で書いたプログラムとして読める粒度で記載する

**設計の理由**

設計の理由は詳細設計書へ記載してよい。テンプレートに設計判断を記録する節がある場合はその節へ、無い場合は理由が対応する設計項目へ併記する。理由を記載しても、実装するクラス・メソッド・分岐・型・有効な範囲などの仕様を省略してはならない。

- 実装、既存文書、設定、検証結果などに理由が明記されている場合は、`理由（観測）: <理由>（観測種別: <実装への明記・既存文書・設定・検証結果>／観測内容: <確認した内容>）` と書く。コードの位置は詳細設計書へ書かず、根拠を記録する別資料がある場合はその資料で管理する
- 観測した構造や挙動から理由を導いたものの、理由そのものは実装に明記されていない場合は、`理由（推定）: <理由>（推定根拠: <観測事実>）` と書く
- 観測と推定を同じ理由の中で混ぜない。両方を記録する必要がある場合は、それぞれを別の行に分ける
- 推定を観測済みの事実として断定しない。「推定」は理由の来歴を示す区分であり、実装仕様の不明点を残してよいという意味ではない

### 章構成と内容網羅の関係

章構成の正はテンプレートであり、内容の網羅の正はこの規約である。両者は別の階層にあり、一方のために他方を作り変えてはならない。

- テンプレートが定めるのは章・節の見出しとその並びである。生成物の章構成はテンプレートの見出しと一致させる。章の個数や順序を独自に増減しない
- この規約が定めるのは各章に書くべき内容（詳細設計書であれば6項目: クラス設計・メソッド設計・ロジック設計・戻り値と引数・エラー処理・データ定義）である。内容が規約の求める項目を満たさない場合、章構成を作り変えて帳尻を合わせるのではなく、テンプレートの既存の章・節の中に内容を書く
- 生成スキル・機械検査の本文が章番号に言及する場合、その番号はテンプレートの現行の章構成と一致していなければならない。スキル・検査を先に書き、テンプレートを後から追従させる順序を取らない

### 文書間の参照

**記法**

- 自書（同じ文書）の節を指す場合は `§N` とだけ書く。文書名を付けない
- 他文書の節を指す場合は `<文書名> §N` のように、節番号の前に文書名を書く。文書名を省くと自書の節番号と区別できない

**機械化の範囲**

- 第1（節番号の相互参照の実在）と第2（他文書を指す参照に文書名が付いているか）は機械で検査する。文書名を持たない `§N` が自書の見出しに実在しない場合、「壊れた自書参照」と「文書名の無い他文書参照」のどちらの可能性も区別せず不合格とする
- 第3（同じ語が単位の中で2つの概念を指していないか）と第4（同じ事実について文書間で断定と未確定が併存していないか）は機械化しない。語の多義・文書間の事実の整合は自然文の意味を読む必要があり、人手のレビューで判定する

### 他文書への参照の短縮

同じ他文書への参照を本文・表の中で繰り返す場合、毎回フルネームで書き出さず、初出で短縮形を宣言してから使う。

- 初出（通常は冒頭の段落）で、参照先の文書名・経路・何を確認できるかを1回だけ述べ、「以後、この参照を（<短縮ラベル>: <キー名>）と表記する」のように短縮形を宣言する
- 宣言した後の本文・表のセルでは、宣言した短縮形だけを使う。フルネームを本文中で繰り返さない
- 関連資料の節には、参照先のフルネームと経路を必ず置く。宣言は本文の読みやすさのためであり、関連資料の節が持つ参照先の実体情報を省略してよいという意味ではない
- 宣言なしに短縮形だけを使うことを禁止する。短縮形は必ず初出の宣言を伴う

## 違反時の手順

書き込みが止められた場合、足そうとした見出しの内容を、既存の章のどこに統合できるかを探す。統合先が見つからなければ、章立てを設計し直してから改めて書く。追記や補足という名目で章を新設しない。
