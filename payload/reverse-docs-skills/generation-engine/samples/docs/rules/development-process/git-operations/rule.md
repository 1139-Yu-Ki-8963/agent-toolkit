# コミットと枝の決まり

## 概要

コミット・枝・統合・変更依頼の運用の取り決め。

履歴は後から読む人のための記録であり、書いた本人のための記録ではない。何をなぜ変えたかが履歴から読み取れる状態を保つ。

共有した履歴の書き換えについては上書きの前に読む決まりが定める。

## 規則

| 規則 | 内容 | 根拠 | 検査 |
|---|---|---|---|
| 1コミットを1つの目的に絞る | 無関係な変更を同じコミットへ混ぜない | 混ざったコミットは、一部だけを戻すことができない | 静的解析: コミットの差分が複数の無関係なディレクトリへまたがっていないかを走査する ／ レビュー: 差分が単一の目的に対応しているかを確認する |
| 表題に何をしたかを書く | 表題へ変更の種別と対象を書き、「修正」「更新」だけで終えない。既定の形式は変更の種別と対象を含み、50文字以内とする | 表題を並べたときに履歴の流れが読めなくなる | 静的解析: 変更の種別と対象を含み50文字以内の形式に一致するかを走査する。値はこのプロジェクトの規則の表で上書きできる |
| 枝の名前に目的を入れる | 枝の名前へ作業の種別と対象を入れ、通し番号だけの名前にしない。既定の形式は `<種別>/<対象>` とする | 番号だけの名前からは、その枝が何の作業かが分からない | 静的解析: `<種別>/<対象>` の形式に一致するかを走査する。値はこのプロジェクトの規則の表で上書きできる |
| 生成物を版管理へ入れない | 依存の実体・作り出した成果物・手元の設定を除外の指定へ登録する | 生成物は差分が大きく、内容の変更を差分から読み取れなくなる | 静的解析: 除外の指定に、依存の実体と生成物の出力先が登録されているかを走査する |
| 統合の単位を小さく保つ | 1つの変更依頼が扱う変更を小さく保ち、レビューできる大きさにする。既定の上限は400行とする | 大きな差分はレビューの精度が落ち、指摘が出ないまま通る | 静的解析: 400 行を超えていないかを走査する。値はこのプロジェクトの規則の表で上書きできる |

## このプロジェクトの規則

上限と形式の具体的な値は、リバース解析が対象リポジトリを観測してこの表の行として起こす。

| 規則 | 内容 | 根拠 | 検査 |
|---|---|---|---|
| 未解析 | この規約に対応する実装の慣行は、まだ観測していない。リバース解析を実行して対象コードを分析すると、その結果からこの節へ規則が起こされる。解析を待たずに規則を決めたい場合は、この節へ直接書き足してよい | リバース解析が未実行である | 不可: 観測の有無は解析の実行結果に依存し、静的解析で判定できない |

## 違反時の手順

git add が止められた場合、対象パスをステージングから外し、`.gitignore` へ出力先ごと登録してから版管理の追跡対象外にする。この機会に、他の生成物も同じ出力先へ紛れ込んでいないかを確かめる。
