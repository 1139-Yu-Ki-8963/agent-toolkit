# 開発環境の組み立て方の決まり

## 概要

手元の開発環境を組み立てる手順と、依存および環境変数の扱いの取り決め。

環境の違いは、動くか動かないかという形でしか現れず、原因が環境にあると気付くまでに時間がかかる。新しく参加した人が、手順書だけで動く環境に到達できる状態を目標とする。

具体的な構築の手順は環境構築手順の成果物が持つ。本書は手順が満たすべき条件を定め、手順の中身は持たない。

## 規則

| 規則 | 内容 | 根拠 | 検査 |
|---|---|---|---|
| 構築手順は環境構築手順.html に集める | 環境を組み立てる具体的な手順は、生成された環境構築手順.html へ一元化し、本書を含む他の文書へ複製しない | 分散した手順は、どれが最新かを読み手が判断できない | 静的解析: 環境構築手順.html がリポジトリ内に1つ実在するかを走査する ／ レビュー: 他の文書に構築手順の複製が無いかを確認する |
| 必要な版を明示する | 言語処理系・実行環境・データベースの必要な版を、手順書と設定ファイルの両方へ書く | 版の食い違いは、動かない原因として最も見つけにくい | 静的解析: 版を宣言するファイルが実在し、手順書の記述と一致するかを走査する |
| 環境変数は雛形を版管理に置く | 必要な環境変数の名前と用途を雛形のファイルへ書き、値そのものは版管理へ入れない | 名前が分からないと、何を設定すればよいかを手順書からしか知れない | 静的解析: 環境変数の雛形ファイルが実在し、値を持つ実ファイルが版管理から除外されているかを走査する |
| 秘密の値を版管理へ入れない | 認証の鍵・合言葉・接続の文字列を版管理へ登録しない | 一度登録した値は履歴に残り、消しても復元できる | 静的解析: 版管理の追跡の対象に、認証の鍵らしい文字列を含むファイルが無いかを走査する |
| 起動の口を1つにする | 開発用の起動を1つのコマンドへまとめ、複数の手順を人が順に打つ形にしない | 手順が複数あると、順序を誤ったときの症状が環境の問題に見える | 静的解析: 設定ファイルの実行定義に、開発用の起動の入口が登録されているかを走査する ／ テスト: 起動コマンドを実行し、追加の手動操作なしで開発環境が立ち上がることを確かめる |
| 環境の差を手順書へ書く | 対応する動作環境と、環境ごとに異なる手順を手順書へ書く | 書かれていない差は、遭遇した人が毎回自力で調べることになる | 静的解析: 手順書に対応する動作環境を述べた記述があるかを走査する |

## 違反時の手順

git add が止められた場合、対象ファイルをステージングから外し、`.gitignore` へ登録してから版管理の追跡対象外にする。秘密の値を含まない雛形として配布したいファイルの場合は、ファイル名を `.env.example` / `.env.sample` / `.env.template` のいずれかに変えれば追加できる。
