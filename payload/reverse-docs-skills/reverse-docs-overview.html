リバース工程全体ガイド

既存コードからプロジェクトの設計ポータルを段階的に組み上げるスキル群の全体ガイド。スキル群を実行するにつれて閲覧用成果物のカードが追加され、使い込むほどプロジェクトの全容が一覧できるポータルサイトへ成長する。各スキルは単体でも動作する。AI が読む正本は docs/rules/ と docs/screens/、人間が閲覧する HTML はルート直下の project-portal/ に分離し、閲覧用成果物を持つスキルだけが正本または抽出結果から HTML を生成する。

正本と表示名
docs/rules/ と docs/screens/ は英語の機械安定パスを使い、Markdownの日本語タイトルと分類メタデータから project-portal/規約/・project-portal/画面/ の日本語表示を生成する。日本語表示のためにMarkdownのファイル名を日本語へ統一する必要はない。
HTMLの配置
docs/ 配下にHTMLポータルを置かない。規約以外の一覧・共通設計・API・テーブル・バッチ・帳票・外部連携・対応表・デザインも、閲覧用成果物はすべて project-portal/ 配下へ生成する。
検証用出力
プロジェクト内に verification/ を作らない。facts・比較ログ・スクリーンショット・往復検証の証跡が必要な処理は、作成前に「リバース検証用の一時成果物を保存するフォルダを作成します。プロジェクト外の出力先を指定してください」と説明し、Claude Code は AskUserQuestion、Codex は request_user_input で保存先を確認する。確認ツールを利用できない場合は OUTPUT_PATH_REQUIRED で停止する。

§2納品物の作成区分

この表は、リバース対象プロジェクトへ納品する成果物を、コード・設定・実測から事実を記入するものと、構造だけをテンプレートとして作成し、現場の明示的な根拠・判断・承認を後から記入するものに分けた一覧である。テンプレート専用の行には、架空の値・架空の規約・架空のサンプルを入れない。根拠が揃わない項目は空欄、対象外、または未確定として扱う。

判定原則: コードから直接確認できる構造・値・参照はリバース記入可。コードから業務目的、設計意図、要求水準、規範、承認事項を補うことは禁止。規約は、明示された規約・運用文書・承認がない限り「観測された実装慣行」に留め、docs/rules/ の規範として確定しない。

リバース記入 コード・設定・facts・実測などの根拠から記入　テンプレートのみ 構造だけを納品し、現場の根拠・判断後に記入

§3ポータルが充実していく仕組み

ポータル（project-portal/index.html）は project-portal/ 配下に生成された HTML だけを検知してカードを動的に生成する。スキルが docs/rules/・docs/screens/ の正本を更新した場合は対応する HTML をレンダリングし、HTMLを直接生成する一覧・設計図系スキルは所定のカテゴリへ出力する。build-portal.sh を再実行すると、新しいカードが現れる。右列は、ポータル上のどのカテゴリにカードが追加されるかを示す。

指揮役（orchestrating-reverse-docs-flow）は成果物の実在と契約に基づく依存順で自動実行する。任意スキルの単独起動は、そのスキルの入力契約と前提成果物が揃っている場合だけ許可する。「facts」は原本コードから抽出した宣言的契約の事実表を指す。「基準タグ」は、2 環境の完全一致を証明できた時点のコミットに打つ git タグ reverse-baseline/<scope> を指す。

§7責務境界の確定事項

工程をまたいで迷いやすい「どちらのスキルが持つか」の確定事項。ここに挙げた 7 点は仕様として確定しており、変更する場合は contract.md と各スキルガイドを同時に改訂する。

本HTMLの保守規約
正本はこのファイル自身（reverse-docs-overview.html）。更新契機はヘッダの meta-table に記載のとおりスキル構成・契約（contract.md）変更時。§5 の実装状況タグ（済／一覧のみ／段階計画）と §6 の対象外タグ（対象外）は、各スキル SKILL.md・contract.md の実装状況と一致させる。スキルの新設・削除・状態遷移の変更時は、本ファイルの該当タグを同一 commit 内で追従させ、陳腐化した記載を放置しない。
scaffold の正本
画面の骨組み生成スクリプトの正本は shared/scripts/scaffold-screen.sh の 1 本のみ。利用側スキルは引数渡しで呼び出し、複製・改変版を持たない。
単体テスト正本の一本化
単体テストコードの正本は、ファイル単位検証（rebuilding-screen-unit-from-docs）が保存した saved_test_paths（設計書リポジトリの テスト項目書/テストコード/単体/ 配下）の 1 系統のみ。画面単位検証（rebuilding-code-from-docs）はこれを対象コードリポジトリへ配置して実行するだけで、単体テストコードの新規作成は行わない。
E2E の責務分離
E2E（画面を実際に操作して端から端まで通す試験）は、作成が rebuilding-code-from-docs（mode=implement）、実行が syncing-reverse-env の動的比較。作る側と走らせる側を分けることで、試験内容が比較判定に引きずられない。
status の解釈権
syncing-reverse-env の返す PASS / FAIL は計測事実（一致したか）であり、意味の解釈（設計書の欠落か・許容差分か）は rebuilding-code-from-docs（mode=judge）が持つ。計測と解釈を混ぜない。
unlocking の単独完走
unlocking-reverse-target-screens が画面レジストリ記帳から syncing-reverse-env（mode=registry） 起動・基準タグ確立まで単独で完走するのは意図した正式仕様。開通の事実を知るのは本スキルだけであり、指揮役が能動的に検知できないため。
画面レジストリの正本
開通済み画面の記帳台帳の定義は docs/screens/reverse-screen-registry.yml。設計書リポジトリ側に置くため、スキル同期・上書きコピーの影響を受けない。unlocking 以外の子スキルは直接触れない。
