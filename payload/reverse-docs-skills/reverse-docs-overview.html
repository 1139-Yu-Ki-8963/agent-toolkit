AI駆動開発セットアップ 全体ガイド

対象リポジトリを AI 駆動開発ができる状態へ整えるスキル群の全体ガイド。整える対象にコードを持つリポジトリを含むため、既存コードから設計書を書き起こすコードリバースの工程を内包する。指揮役スキルの実行ひとつで、理想的なリポジトリ体系を作ることを目指す。各スキルは単体でも動作する。

§1これは何か

対象リポジトリへの働きかけを 3 つの役割に分ける。役割ごとの入力と出力は次のとおり。

役割入力出力
セットアップ対象リポジトリ（コードの有無を問わない）AI が読む定義、各 AI ツールの設定フォルダ、人間向けポータル
リバース既存コード定義への事実の書き込みと、そこから導出される設計書・一覧・ポータル
保守生成済みの定義と派生物定義と派生物のずれの検知と再生成

統括スキル 1 本（現行名 orchestrating-reverse-docs-flow。orchestrating-ai-development-setup への改称を予定するが、本稿ではこの現行名で記す）が、セットアップとリバースとポータル生成のすべてを扱う。保守は別スキルとして枝分かれし、統括経由でも単独起動でも呼び出せる。

§2特徴

プロジェクトポータル
人間が読む HTML の集まり。スキルを実行するたびにカードが増え、使い込むほど内容が育つ。
リバーススキル
facts（原本コードから抽出した宣言的契約の事実表）の封印と、再実装・比較による往復検証で、実装されていない機能を設計書へ書き込むことを防ぐ。
AI 駆動開発に必要なファイル群
AGENTS.md・CLAUDE.md・.claude/・.cursor/・.codex/。同じ形式で読めるツール同士は symlink で共有し、形式が異なるツールへは変換して用意する。
保守の仕組み
規約の連動、ポータルの保守、フィンガープリント台帳による定義と派生物のずれ検知。

§3入口のモード判定

対象リポジトリのコードの有無と画面の有無から、実行するモードを 3 通りに分ける。判定はサブプロジェクト単位でも行う。モノレポではバックエンドだけのサブプロジェクトがありうるため、リポジトリ全体で 1 つのモードには決めない。

判定モード動作
コードなし、または設計書のみセットアップのみ各 AI ツールの設定フォルダと定義の骨組みを作り、ポータルは空のカードで作る
コードあり、画面ありリバース全工程現行の工程をそのまま実行する
コードあり、画面なしリバース縮退画面に依存する工程を飛ばし、画面カードは選べない状態で表示する

定義と表示名
docs/rules/ と docs/screens/ は英語の機械安定パスを使い、Markdownの日本語タイトルと分類メタデータから project-portal/規約/・project-portal/画面/ の日本語表示を生成する。日本語表示のためにMarkdownのファイル名を日本語へ統一する必要はない。
HTMLの配置
docs/ 配下にHTMLポータルを置かない。規約以外の一覧・共通設計・API・テーブル・バッチ・帳票・外部連携・対応表・デザインも、閲覧用成果物はすべて project-portal/ 配下へ生成する。
規約本文の生成
docs/rules/ は型と定義だけの空雛形で納品し、コードから観測した実装慣行は規約本文へ書かない。観測は規約提案という別の成果物へ出し、取り込みの判断は現場のエンジニアが行う（取り込みスキル importing-rule-proposals）。
docs/common/の永続性
アーキテクチャ調査書と設計6文書（共通設計書・基盤設計・データ設計・UI共通設計・DESIGN.md・メッセージ定義書）は、再リバース時に更新され続ける永続文書として docs/common/ に置く。規約提案とページ証跡がこの文書を参照先として指すため、消してはならない。
検証用出力
プロジェクト内に verification/ を作らない。facts・比較ログ・スクリーンショット・往復検証の証跡、および作業記録・サンプル記録が必要な処理は、作成前に「リバース検証用の一時成果物を保存するフォルダを作成します。プロジェクト外の出力先を指定してください」と説明し、Claude Code は AskUserQuestion、Codex は request_user_input で保存先を確認する。確認ツールを利用できない場合は OUTPUT_PATH_REQUIRED で停止する。

§5判定原則と規約の流れ

判定原則: コードから直接確認できる構造・値・参照はリバース記入可。コードから業務目的、設計意図、要求水準、規範、承認事項を補うことは禁止。規約は、明示された規約・運用文書・承認がない限り「観測された実装慣行」に留め、docs/rules/ の規範として確定しない。

規約の扱いはこの原則を配置で保証する。docs/rules/ は空雛形で納品し、コードからの観測はそこへ書かない → 観測は規約提案として project-portal/ へ出す → 取り込みの判断は現場のエンジニアが行う → 取り込み後は適用操作で project-portal/規約/ と各 AI ツール形式（.mdc 生成等）の双方へ反映される、という流れを踏む。

§6保守の仕組みとスキル

納品する保守スキルは 3 本である。全モードで同一セットを納品し、実体は .claude/skills/ に置く。

スキル役割
syncing-derived-artifacts状態表示・適用・復旧の 3 操作を 1 本で担う。既定値なしの必須引数でモードを指定する
importing-rule-proposals規約提案の取り込みを担う。取り込みの判断は現場のエンジニアが行う
enabling-new-units後から現れた画面や種別を対象範囲へ加え、内部で適用操作へ委譲する

片側編集の検知は shared/scripts/check-derived-drift.sh に集約する。適用のたびに各派生物のハッシュを台帳（record）へ記録し、検査（status）が現在値と台帳を突合して不一致を報告する。判定にファイルの更新時刻は使わない。git checkout や別ツールの操作でも時刻は動くためである。画面名と表示コミットのずれ検知も同じ機構を使う。

§8ポータルが充実していく仕組み

ポータル（project-portal/index.html）は project-portal/ 配下に生成された HTML だけを検知してカードを動的に生成する。スキルが docs/rules/・docs/screens/ の正本を更新した場合は対応する HTML をレンダリングし、HTMLを直接生成する一覧・設計図系スキルは所定のカテゴリへ出力する。build-portal.sh を再実行すると、新しいカードが現れる。右列は、ポータル上のどのカテゴリにカードが追加されるかを示す。

指揮役（orchestrating-reverse-docs-flow）は成果物の実在と契約に基づく依存順で自動実行する。任意スキルの単独起動は、そのスキルの入力契約と前提成果物が揃っている場合だけ許可する。「facts」は原本コードから抽出した宣言的契約の事実表を指す。「基準タグ」は、2 環境の完全一致を証明できた時点のコミットに打つ git タグ reverse-baseline/<scope> を指す。
