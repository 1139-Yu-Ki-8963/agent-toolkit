# 実装契約の定義

7 種別の詳細設計に当たる文書へ足す「実装契約」の節が何を書く場所かを定める。正本は本ファイルである。判断の経緯は `docs/tasks/実装契約の置き場を全種別で揃える指示書.md` を参照する。

## 基本の 3 項目

API（`API詳細設計書.md` §10）と画面（`画面詳細設計書.md` §16）が既に持つ 3 項目を、全種別共通の出発点とする。

| 項目 | 内容 |
|---|---|
| ファイルと関数 | どのファイルのどの関数が処理を担うか |
| 型定義 | 扱う値の型 |
| 依存 | 何に依存するか |

## 種別ごとの追加判断

バッチ・帳票・外部連携・テーブルの 4 種別について、基本の 3 項目に追加が要るかを判断した。結論は 4 種別とも追加なしである。

| 種別 | 追加の要否 | 理由 |
|---|---|---|
| バッチ | 追加なし | 起動の引数・スケジュール等は拡張マニフェストと 実装記録 §2 データ定義が既に持つ。実装契約は呼び出し境界の記述に絞る |
| 帳票 | 追加なし | 出力の形式・改ページの単位は 実装記録 §2 データ定義が既に持つ。実装契約は呼び出し境界の記述に絞る |
| 外部連携 | 追加なし | 電文とタイムアウトは 実装記録 §2 データ定義が既に持つ。実装契約は呼び出し境界の記述に絞る |
| テーブル | 追加なし | スキーマの詳細は 実装記録 §2 データ定義が既に持つ。実装契約は読み書きを担う関数側の記述に絞る |

4 種別とも、扱うデータの詳細は既存の `実装記録 §2 データ定義` に残す。実装契約の節は「どのファイルのどの関数が読み書きするか」だけを追加する。項目を増やさないことで、種別間の節構成を単純に保つ。

## 章番号の変更

バッチ・帳票・外部連携・テーブルの 4 種別のテンプレートで、既存の `§7 要確認事項一覧` を `§8 要確認事項一覧` へ動かし、空いた `§7` に実装契約の節を新設した。

このリポジトリの `generation-engine/samples/` と `delivery-payload/references/gold-standard/` の配下には、この 4 種別の生成済み文書は 1 件も無い（`find` で確認済み）。既に生成済みの文書の移設は本指示書の対象外（触らない範囲）であり、今後どこかで生成済みの旧番号の文書（`§7 要確認事項一覧`）が見つかっても、新しいテンプレートへ合わせて書き換える必要はない。次に当該ユニットを再生成したときに新番号へ揃う。

その後、疑似コードの節を追加した際にもう一段の繰り下げが起きた（`docs/tasks/設計書へ疑似コードと戻り値を足す指示書.md` を参照）。バッチ・帳票・外部連携・テーブルの 4 種別は実装契約が `§7` から `§8` へ、要確認事項一覧が `§8` から `§9` へ動いた。API は実装契約が `§9` から `§10` へ、要確認事項一覧が `§10` から `§11` へ動いた。画面は実装契約が `§15` から `§16` へ、要確認事項一覧が `§16` から `§17` へ動いた（画面は §7 疑似コード の新設に伴い §7 以降すべてが 1 つ繰り下がった）。

機能（feature）には実装契約の節を持たせない（含めない）。

理由は 2 つである。

1. 配置の定義（`design-unit-layout.json` の `feature.phases.detail`）が空であり、機能は詳細設計の段階自体を持たない
2. 既存のスキル（`generating-feature-design-for-reverse-docs`）が、機能設計書と個別設計書へ同じ内容を重複して書くことを既に禁じている。実装契約という実装水準の記述を機能へも持たせると、この既存の禁止と衝突する

「含めない」を選んだため、機能設計書と個別設計書の重複しない境界を新たに定める必要はない。実装水準の記述は必ず各構成要素（API・画面・バッチ・帳票・外部連携・テーブル）の個別設計書の §実装契約に書く。この手順は `generating-feature-design-for-reverse-docs/SKILL.md` に明示した。

## 疑似コードと戻り値の扱い

`docs/tasks/設計書へ疑似コードと戻り値を足す指示書.md` の指摘に基づき、7 種別のうちメッセージ定義書を除く 6 種別（API・テーブル・バッチ・帳票・外部連携・画面）へ疑似コードの節と戻り値の記載欄を追加した。設計書にコードをそのまま貼ることは禁止し、例として一部を載せることだけを許す。

### 疑似コード

分岐と繰り返しの入れ子だけを日本語で書く。言語の構文・変数名・API 名は使わない。

```
良い: 利用者の権限が管理者なら、締め日を過ぎた明細も対象へ含める
悪い: if (user.role === 'admin') { includeClosedItems() }
```

実際のコードを貼ることを禁じる。原本の行を指したい場合は §実装契約の「ファイルと関数」から辿らせる。

書き方は次の 7 点に従う（改善課題1-294。人間語寄りと日本語コード寄りの相反する要望に、両立する具体的な書式で答える）。

1. 関数名はそのまま使う（役割へ置き換えない）
2. 制御構造は日本語で書き構造を保つ（もし〜ならば・繰り返しの終わり）
3. 分岐ごとに空行を入れる
4. 条件と本体を必ず改行して字下げする
5. 繰り返しは終わりを明示する
6. 字下げは全角の空白 2 つ
7. 変数名は書かない、役割で述べる

実例（対応済みの詳細設計書の疑似コード）:

```text
parse_bid_inputs を実行する
もし 入力検査が失敗したならば
　　fail_validation(検査エラー文) を返して終了する

run_validate_bid_request を実行する
もし run_validate_bid_request がエラー応答を返したならば
　　そのエラー応答を返して終了する

もし 検証結果が不合格ならば
　　validate_failure_envelope を実行して、その結果を返して終了する

検証結果を返して終了する
```

`IF`・`END IF`・`FOR`・`WHILE` のような実装言語の制御語と、字下げの半角の空白は使わない。`generation-engine/scripts/tests/check-pseudocode-code-mixing.sh` がこの 2 点を機械で見る。

置き場は、帳票・バッチ・テーブル・外部連携では `§ロジック` の直後（`§入出力の値` の直前）、API では `§処理フロー` の直後、画面では `§データフロー` の直後に、独立した節として置く。`§ロジック` の 3 つの表（分岐・繰り返し・判定表）は構造を列挙するもので順序の表現を持たないため、疑似コードは小節ではなく独立した節にした。

### 戻り値

既存の `§入出力の値` の表へ「区分＝戻り値」の行として書く。新しい表は足さない。型・有効な範囲・空値の許容は既存の列で表す。

`§入出力の値` を持たない API と画面は次の場所へ書く。

| 種別 | 置き場 |
|---|---|
| API | `§レスポンス` の `正常系の構造` の表（項目・型・常に存在・意味・根拠）をそのまま戻り値の記載として使う |
| 画面 | `§データフロー` 配下に「区分＝戻り値」の行を持つ小節（`### N.7 戻り値`）を新設する |

### メッセージ定義書

メッセージ定義書.md は対象に含めない。他の 6 種と構造が違い、`##` の見出しを 1 つも持たない。メッセージ定義書にも処理の分岐が現れると分かった時点で、対象に含めるかを改めて判断する。

### コード混入検査

疑似コードの節に実際のコードが混ざっていないかを `generation-engine/scripts/tests/check-pseudocode-code-mixing.sh` が検査する。言語の構文らしい記号（`{` `}` `=>` `===` `;`）や `if (`・`for (`・`function ` の並びを、疑似コードの節の本文から検出する。第 1 層の機械検証（`run-layer-machine-checks.sh`）がこの検査を自動的に拾う。

## 入出力の列の持ち主（OpenAPI が既に在る場合の様式パターン）

接続窓口の入出力（§2 リクエスト・§3 レスポンス）の書き方は、対象プロジェクトが OpenAPI 定義を既に持つかどうかで切り替える（改善課題1-296）。どちらの場合も OpenAPI 定義を新たに生成しない。リバース工程は既存コードの記録であり、仕様の正を新たに作る行為は範囲を超える（2026-08-28 のユーザー判断）。

| 場合 | §2・§3 の書き方 |
|---|---|
| 対象が当該接続窓口の OpenAPI 定義を持たない | 従来どおり、設計書の表が全列（型・必須・有効な範囲を含む）を持つ |
| 対象が当該接続窓口の OpenAPI 定義を既に持つ | 機械検証列は既存の OpenAPI を正とし、設計書は定義ファイルのパスとスキーマ名を明記して参照する。設計書側の表は下表の「設計書側が持つ列」だけを持つ |

列ごとの持ち主。判定基準は「1 つの項目だけを見て答えが決まるか、複数の項目・処理・時点をまたぐか」である。

| 持ち主 | 列 |
|---|---|
| OpenAPI 側 | 型・必須・空値の可否・有効な範囲・既定値・取り得る値の列挙・書式の制約・例・ステータスコードと応答の構造の対応 |
| 設計書側 | 業務上の意味・値の由来・同名項目の優先順位・項目間の条件・仕様と現行実装の食い違い・節の位置づけ |

全接続窓口に共通する応答の外枠は共通の設計文書（`共通設計書.md`）が持つ。「OpenAPI を正とする」とだけ書いて参照先のパスも設計書側の表も置かない空の節を禁止する。参照する場合は、定義ファイルのパス・スキーマ名・設計書側の列の表の 3 点を必ず置く。

## 構成要素をまたぐ実装の扱い

複数の構成要素が同じ実装（共有するデータ構造・共通関数など）を使う場合も、機能設計書へは書かない。その実装を最初に定義した構成要素の個別設計書の §実装契約へ 1 回だけ記述する。他の構成要素は自分の §実装契約の「依存」の行へ、定義元の設計書へのパスを根拠として書き、値を再掲しない。この扱いも `generating-feature-design-for-reverse-docs/SKILL.md` に明示した。

ただし、複数の設計単位（API・バッチ・帳票・外部連携）から呼ばれる共通基盤の関数（事前関門・共通受付・応答整形など）は、特定の構成要素が「最初に定義した」とは言えない。この場合は `基盤設計.md` §7 共通関数の契約を唯一の正とし、各設計単位の実装記録 §4.4 依存へ「基盤設計 共通関数の契約 <関数名>」と、その単位が渡す値・受け取る値の使い方だけを書く。契約が API の本数分に複製される形（1 つの契約が 50 箇所に載る等）を禁止する（改善課題1-275）。
