# 納品物フォルダ体系

本ファイルはリバース設計の納品物（成果物一式）の目録の正本である。各成果物を生成するスキルとの対応と実装状況をここで管理する。

画像からの文字起こし。リバース対象ユニットの成果物置き場（`<output_dir>` 配下）の全体構成と、各ファイルを生成するスキルの対応を示す。

実装状況の凡例: 【済】= 現行スキルが生成する成果物。【段階計画 Cycle 4】= 上位抽象化スキルが担う要件定義文書群（未実装）。テーブル・バッチ・帳票・外部連携の詳細設計書と基本設計書は実装済みのため、本群から外れた。

用語のリバース解析候補は納品物ではない。`generating-glossary-for-reverse-docs` は呼び出し元が明示した対象repo外の絶対パスへproposal YAMLとdiagnosticsだけを生成し、この体系へ直接書き込まない。

## 検証範囲と文書と単位の対応

| 検証する範囲 | 文書 | 配置する単位 | 対応する設計書 |
|---|---|---|---|
| 1つの関数・メソッド | `<種別>単体テスト設計書.md` | `<種別>-<キー>/テスト設計/` | `<種別>詳細設計書.md`（機能は機能設計書.md） |
| 1つの設計単位の外部の振る舞い | `<種別>テスト設計書.md` | `<種別>-<キー>/テスト設計/` | `<種別>基本設計書.md`（機能は機能設計書.md） |
| 1つの画面内の操作の流れ | 操作シナリオ仕様書.md | `screen-<キー>/テスト設計/` | 画面テスト設計書.md（画面だけが持つ） |
| 複数の画面・機能・APIの連携 | docs/test-cases/結合テスト仕様書.md | プロジェクト全体 | 複数の設計書 |

単位ごとのテスト設計書は結合テストを扱わない。結合テストは複数の画面・機能・APIの連携を対象とし、上位階層の `docs/test-cases/結合テスト仕様書.md` に記載する。

`<API 識別子>` と `<機能識別子>` はマニフェストの `unitId` を使い、空の場合は `unitKey` を使う。決め方の正本は各生成スキルの SKILL.md の出力節である。

## 検証記録（verification/）

検証記録は納品物ではないため `docs/` の外に配置する。`docs/` と同階層の `verification/` フォルダに格納する。

```
verification/
└── screen-<画面ID>/
    ├── facts/
    │   └── <run_id>/
    │       ├── facts.yml
    │       ├── facts.lock
    │       └── recount-report.txt
    ├── 単体-<対象ファイルbasename>/
    │   └── <timestamp>/
    │       └── (単体検証記録)
    └── <timestamp>/
        ├── 修正指示書.md
        ├── 最終報告.md
        └── (テストログ・差分レポート等)
```

docs 内に検証記録は一切存在しない。facts・単体検証記録・修正指示書・最終報告・テストログはすべて verification/ 配下に配置する。

## 出典

`納品物フォルダ体系.md`（提供されたスクリーンショット2枚）の文字起こし。文字起こしのみを目的とし、実際のディレクトリ・ファイルの生成は行っていない。実装状況（【済】/【段階計画 Cycle N】）は文字起こし後にリポジトリの現行スキル構成と突合して追記したもの。
