# 規約定義と派生生成の設計

本ファイルは reverse-docs-skills が対象リポジトリへ納品する「規約の定義」と、そこから各 AI ツール向けに生成する「派生物」の設計を定める文書である。定義から派生への一方向生成だけを扱い、派生物から定義を逆生成する経路は扱わない。本設計に対応する実装は揃っている。整合検査と派生生成のスクリプト、取り込みと同期のスキル定義、提案 HTML の生成が動作を確認済みである。未実装なのは、対象リポジトリのコードを調査して提案の中身を起こす工程の自動化であり、そこは現状スキルの手順として人と AI が実行する。

## 1. 全体像

規約の一生は提案・取り込み・適用の 3 段で構成する。

| 段 | 入力 | 出力 | 担当 |
|---|---|---|---|
| 提案 | 対象リポジトリのコード | 規約提案 HTML（リポジトリ外へ出力） | リバース工程 |
| 取り込み | 判定結果 JSON | `docs/rules/<親>/<子>/` の一式 | `importing-rule-proposals`（納品スキル） |
| 適用 | `docs/rules/` | `.claude/`・`.cursor/`・`.codex/`・`AGENTS.md`・`project-portal/規約/` | `syncing-derived-artifacts`（納品スキル） |

定義は `docs/rules/` だけである。`.claude/`・`.cursor/`・`.codex/`・`AGENTS.md`・`project-portal/規約/` はすべて `docs/rules/` から生成する派生物であり、直接編集の対象にしない。

## 2. docs/rules の構造

親カテゴリを 7 個、子カテゴリを 27 個の 2 階層で構成する。親フォルダは直下に宣言ファイルを持ち、1 つの子カテゴリは以下のフォルダを持つ。

```
docs/rules/<親>/
├── parent.yml               親カテゴリの宣言。必須
└── <子>/
    ├── rule.md                  規約本文（front matter 付き）。必須
    ├── check-<子>.sh            linter。checkable: true のとき必須
    ├── check-<子>.test.sh       linter の回帰テスト。linter があるとき必須
    └── design-notes.md          検査できない理由。checkable: false のとき必須
```

`parent.yml` は親カテゴリの宣言である。次の2鍵を持つ。

| 鍵 | 型 | 必須 | 用途 |
|---|---|---|---|
| `key` | 文字列 | 必須 | 親カテゴリの英語キー。フォルダ名と一致させる |
| `title` | 文字列 | 必須 | 日本語表示名。AGENTS.md とポータルの親見出しに使う |

規約に対するレビューを行うのは1体のレビュアーである。親カテゴリごとに担当を分けない。担当を分ける設計は、規約の分類とレビュアーの分け方が一致しない場合に宣言と実体の対応を管理する手間が生まれ、規約を1件足すたびに担当の割り当てを考えることになる。1体が全ての規約を見る形なら、規約が増えても構造は変わらない。

取り込みスキルが `parent.yml` を新規作成する場合、`title` は判定結果 JSON の `chapter` から章番号を取り除いた部分を使う。取り除く対象は先頭の数字、`第<数字>章`、`<数字>.<数字>` と、それに続く区切り記号である。

規約本文と検査スクリプトを同じフォルダに置く。規約を直すときに検査も直す動機が働く配置であり、両者が離れていると片方だけが古くなる。

規約フォルダの linter は `check-<子>.sh` とする。前置詞は検査することを表し、hook として登録したときの強さ（advisory または block）とは別の軸である。強さは `enforcement` 鍵が持つ。`agent-home` の hook 命名規則は hook 自体のファイル名を対象とするもので、規約フォルダの linter には適用しない。

検証と生成の道具は、納品先では対応する規約のフォルダ（`docs/rules/agent-operations/ai-config-asset-management/`）に配る。規約を扱うスクリプトは、対応する規約のフォルダへ置く。スクリプト専用のフォルダを作らない。`docs/rules/` の直下は規約の親カテゴリが並ぶ場所であり、そこに規約でないものを混ぜると、規約の一覧を見たときに何が規約で何が道具かが読み取れなくなる。規約とその規約を実行する道具が同じ場所にあれば、規約を読んだ人はその場で道具を見つけられる。

## 3. 規約に書いてよいものの条件

規約の規則は、次の 2 つの条件を満たすものだけを書く。

**条件 1: 違反が機械で検知できること。** 検知できない規則を書いても、守られたかどうかを確かめられない。常時または条件付きで注入される文章が増えるだけであり、読み手の注意を薄める。

検知の手段は、ファイルの内容の走査に限らない。Claude Code の hooks は次のタイミングで発火し、それぞれ違う対象を検査できる。この全体を検知の手段として数える。

| タイミング | 検査できる対象 |
|---|---|
| PreToolUse | ツール呼び出しの引数。コマンド文字列・書き込み先のパス・書き込む内容・委任の指示文 |
| PostToolUse | ツールの実行結果。出力・変更されたファイル |
| UserPromptSubmit | 利用者の発話 |
| Stop | エージェントの最終応答の本文 |
| SessionStart / SessionEnd | セッションの境界 |

**条件 2: 1 つの規約が 1 つの検査に対応すること。** 1 つの規約の中で異なるタイミングの検査が必要になる場合、その規約は複数の関心を持っている。分割する。

分割の判断は、規則ごとに必要なタイミングを並べて行う。2 種類以上に分かれるなら分割の対象である。

### 条件を満たさない規則の行き先

条件を満たさない規則は、規約フォルダに置かず、次のいずれかへ移す。

| 性質 | 移し先 |
|---|---|
| 工程の順序や作業の進め方を定めるもの | 開発フロースキルの該当フェーズ |
| 成果物を人が見て判断するもの | レビュー観点一覧 |
| 設計書に何を書くかを定めるもの | 設計書の書き方の決まりの記載項目 |
| 対象リポジトリの実態に依存し、汎用の規範たり得ないもの | どこにも置かない |

### この条件を設けた経緯

2026-08-15 の実測では、規約 27 件の規則 159 行のうち 23 行が機械で検知できなかった。当初はこれらを「不可」と注記して規約に残す方針だったが、検知できない規則は守られたかどうかを確かめられず、規約フォルダが守られない文章の置き場になる。条件を必須とし、満たさないものは移すことにした。

あわせて、規約 27 件のうち 10 件は 1 つの規約の中で 2 種類以上のタイミングの検査を必要としており、1 つの検査に対応していなかった。

## 4. rule.md の形式

front matter の鍵は以下のとおり定める。

| 鍵 | 型 | 必須 | 値域 | 用途 |
|---|---|---|---|---|
| `key` | 文字列 | 必須 | ケバブケース | 子カテゴリの英語キー。フォルダ名と一致させる |
| `title` | 文字列 | 必須 | 日本語 | 表示名。ポータルと AGENTS.md が使う |
| `parent` | 文字列 | 必須 | ケバブケース | 親カテゴリの英語キー |
| `summary` | 文字列 | 必須 | 1 文 | 規約の要約。Cursor の description になる |
| `scope` | 列挙 | 必須 | `always` / `scoped` | 常時注入か条件付きか |
| `paths` | 配列 | `scope: scoped` のとき必須 | glob パターン | 適用対象のパス |
| `enforcement` | 列挙 | 必須 | `advisory` / `none` | 検査の強さ |
| `checkable` | 真偽 | 必須 | true / false | 機械検査が可能か |
| `checker` | 文字列 | `checkable: true` のとき必須 | ファイル名 | linter のファイル名 |
| `uncheckableReason` | 文字列 | `checkable: false` のとき必須 | 1 文以上 | 検査できない理由 |
| `formatter` | 列挙 | 必須 | `prettier` / `biome` / `editorconfig` / `none` | 矯正設定の写し先 |
| `status` | 列挙 | 必須 | `draft` / `approved` | 派生生成の対象か |
| `origin` | 列挙 | 必須 | `template` / `proposal` / `manual` | 出自。ずれ検知で上書き可否の判断に使う |
| `workUnit` | 列挙 | 必須 | `file` / `process` / `artifact` | 規約が対象とする作業の単位（ファイルの中身 / 進め方 / 成果物の形）。ファイルを渡して読む規約を解決する処理（`resolve-applicable-rules.sh`）は `file` だけを返す（改善課題1-281） |

上表の 14 鍵は `docs/rules/**/rule.md` 専用の schema である。設計書を含む別種の Markdown へこの集合を流用しない。

詳細設計書の frontmatter は別 schema とする。機械可読な正本は `delivery-payload/references/detail-design-frontmatter-keys.json` とし、定義文書・テンプレート・生成物の鍵集合が食い違う場合は不合格とする。

### 詳細設計書の種別ごとの鍵集合

- API（api）: api_key・api_id・method・path・feature_key・source_ref・unit_kind・chapter_map
- テーブル（table）: table_key・table_id・table_name・table_subkind・source_ref・unit_kind・status
- バッチ（batch）: batch_key・batch_id・batch_name・batch_trigger_type・source_ref・unit_kind・status
- 帳票（report）: report_key・report_id・report_name・report_engine・source_ref・unit_kind・status
- 外部連携（external）: external_key・external_id・external_name・external_direction・source_ref・unit_kind・status

API詳細設計書の canonical な鍵集合は次の 8 鍵である。

| 鍵 | 値の由来 |
|---|---|
| `api_key` | APIマニフェストの `unitKey` |
| `api_id` | APIマニフェストの `unitId` |
| `method` | APIマニフェストの `method` |
| `path` | APIマニフェストの独立した `path`。無ければ `identifier` の HTTP メソッドより後ろを決定的に分離した値 |
| `feature_key` | APIマニフェストの `featureKey`。無い場合も空欄の鍵を保持する |
| `source_ref` | APIマニフェストの `sourceFile`。次項の代表ファイル選定契約に従う |
| `unit_kind` | 固定値 `api` |
| `chapter_map` | 章の役割キーと §番号の対応（`delivery-payload/references/chapter-map.md` の API の表）。生成器と検査が章を特定するために使う機械向けの対応表であり、本文には表示しない |

この 8 鍵と `rule.md` の 14 鍵には意味上の一対一対応が無い。API詳細設計書へ `title`・`login_required`・`category`・`auth`・`note` を追加せず、生成物にも残さない。

### source_ref の代表ファイル選定契約

- 1ファイルの場合: `source_ref` は、該当実装ファイルのリポジトリルート相対パス1件とする。
- 複数ファイルの場合: HTTP要求を最初に受ける代表ファイルを、ルーター、コントローラー、ハンドラーの順で1件選ぶ。同じ優先順位の候補が複数あるときは、APIマニフェストの `sourceFile` と一致するものを選ぶ。代表ファイルを起点に原本の呼び出し関係をたどり、複数モジュールの関数契約は本文へ記録する。
- 実装が0件の場合: `source_ref` の鍵を残して値を空欄にする。未検出の事実は、確認事項質問票（`confirmation-survey`）の入力へ記録する。`confirmation-item-ledger` を納品物として復活させない。

いずれの場合も絶対パスと行番号を含めない。`delivery-payload/references/doc-extraction.json` と `generation-engine/scripts/portal-input/build-manifests-from-docs.sh` は、前付けの単一パスを一覧マニフェストの `sourceFile` へ文字列として渡す。

### title の付け方

`title` は次の 2 つを満たすこと。

1. 語尾を「の決まり」で揃える。守るべき決まりを書いた文書であることが読み取れ、親カテゴリの名前（AIエージェント運用・開発プロセス・コード規約・品質保証・文書化規約・非機能要件・業務ドメイン規約）のいずれとも重ならない
2. 名前だけを見た人が、その規約が持つ規則を 1 つでも言い当てられること

語尾を「規約」や「要件」にしないのは、親カテゴリが既にその語を使っており、親と子が混ざるためである。

`checker` は規約に 1 つだけ宣言する。規約が持つ規則のうち、linter が実際に検査するのは一部である場合がある。規約全体が機械で検査されると読み違えないよう、どの規則を検査するかは linter のファイル冒頭のコメントと、規則表の検査列が示す。

`# <title>` の下に次の節を置く。

| 節 | 条件 | 書く主体 |
|---|---|---|
| `## 概要` | 必須 | ツール側 |
| `## 規則` | 必須。表で書く | ツール側 |
| `## このプロジェクトの規則` | 必須。`## 規則` と同じ列構成の表で書く | リバース解析 |
| `## 違反時の手順` | `enforcement` が `advisory` のとき必須。`none` のときは置かない | ツール側 |
| `## 設計判断` | `checkable: true` のとき必須。linter の必要性・代替案を採らなかった理由・保守責任者・廃棄条件の 4 項目を書く | ツール側 |

`enforcement` が `none` の規約は、機械が検知しない取り決めである。違反したときに何をするかは規約本文が述べる範囲であり、手順の節を設けない。

`origin` は 3 値のいずれかを持つ。`template`（空雛形のまま未記入のもの）・`proposal`（規約提案から取り込んだもの）・`manual`（現場が直接書いたもの）と区別する。

`## 規則` は、規則・内容・検査の 3 列、または規則・内容・根拠・検査の 4 列の表で書く。根拠をポータルへ表示しない方針では 3 列を選ぶ。検査の列は `<手段>: <方法>` の形で書き、その規則の違反をどの手段で見つけるかを明示する。1 つの規則に複数の手段が要る場合は ` ／ ` で区切って並べる。

3 列を選び、根拠を別に残す場合は、規約単位の `evidence.md` を当該 `rule.md` と同じフォルダへ置く。表は `規則・出典・確認記録` の 3 列とし、規則列には `rule.md` の規則名、出典列には参照先、確認記録列には確認日と確認結果を書く。このファイルは検証用の補足記録であり、派生規約へ複製せず、ポータルの規約ページおよび資料カードにも表示しない。

検査の列を必須にするのは、規約を書く時点で検査の可否を決めさせるためである。後から検査を足そうとすると、規則の書き方が検査に向かない形で固まっており、書き直しになる。検査できないと分かった規則も、なぜできないかがその場に残る。

`## このプロジェクトの規則` は、リバース解析が対象リポジトリの観測から起こした規則を置く節である。`## 規則` は役割と方針の水準を持ち、対象リポジトリを見なくても確定する内容だけを書く。本節はそれに対し、観測した実装慣行から起こした具体を持つ。列は `## 規則` と同じ 3 列または 4 列とする。

リバース解析の出力には 2 つの型がある。私たちが用意した規則を具体化する型と、私たちの枠に無い規則を新しく起こす型である。前者は名前の付け方の決まりに対する「このプロジェクトはキャメルケースを使う」のような具体化であり、後者は対象リポジトリ固有の実装慣行から生まれる規則である。どちらも同じ列構成の表で書けるため、節を 1 つ設けるだけで両方を受けられる。

観測できるものが無かった場合は、節を空にせず「観測なし」とその理由を書く。読み手が「調べていないのか、調べたが無かったのか」を区別できるようにするためである。

### 4.1 検査の手段

規則の違反を見つける手段は次の 4 つである。

| 手段 | 何ができるか | 誰が確かめるか |
|---|---|---|
| 静的解析 | ファイル・ツールの引数・対話の記録を走査して判定する。読んで判断する必要がない | 規約に同梱する linter |
| テスト | 実行して振る舞いを観測して判定する | 単体テスト設計書のテスト観点にもとづく試験 |
| レビュー | 成果物を読んで意味を判断する | 納品先で開発するAIエージェント。人が確かめることもあるが主体ではない |
| 判定不能 | 検査に必要な値や基準がどこにも定義されていない | 誰も確かめられない |

レビューを行うのは、納品先で開発するAIエージェントである。この納品物は、対象プロジェクトでAIが開発を進められる状態を作るためのものであり、規約はそのAIが読むものとして設計されている。レビューが手段の規則は、AIが成果物を読んで判断するための観点であり、AIのコンテキストへ載せる意味を持つ。人が確かめることもあるが、それは補助であって主体ではない。

この区別は重要である。レビューを人の作業として設計すると、レビューが手段の規則は「AIが読んでも行動が変わらない記述」になり、規約へ書く意味を失う。静的解析で見つけられないからといって規則を落とすのではなく、AIが読んで判断する観点として残すのが本来の姿である。

検査の列は、その規則の内容が求める確認を**すべて**受けるように書く。内容が「決める」「書く」だけを求めるなら存在の確認で足りるが、内容が「試して動くことを確かめる」「結果が正しいことを確かめる」を求めるなら、存在の確認だけでは足りない。足りない部分に必要な手段を追加する。

例を挙げる。

```
規則: 復旧の手順を書いて試す
内容: 障害からの復旧の手順を書き、実際に試して動くことを確かめる
検査: 静的解析: 復旧の手順書が実在するかを走査する ／ テスト: 手順に従って復旧を実行し、目標の時間内に戻ることを確かめる
```

手順書の実在だけを見ると、「試して動くことを確かめる」という後半が確かめられないまま残る。静的解析でできる形へ落とすために規則の要求を削ってはならない。

`判定不能` は、上限や形式のような値が規約本文のどこにも書かれていない場合に使う。この場合は値の既定を規約本文へ書いて手段を静的解析へ移すか、値を決められない理由を書く。値が無いまま `判定不能` を残すと、その規則は誰にも守れない。

### 4.2 linter の粒度

linter は規約に 1 つ置く。その規約の規則のうち、検査の手段に静的解析を含むものを**すべて**検査する。規則ごとに linter を分けない。

理由は front matter の `checker` が規約に 1 つだけ宣言される構造だからである。規則ごとに分けると、宣言の形・生成器・整合の検査をすべて作り直すことになる。1 本の linter が複数の規則を見る形なら、既存の構造をそのまま使える。

### 4.3 観点の一覧を別に持たない理由

テストとレビューが確かめる規則は、規約本文の検査列がその所在である。観点だけを集めた別の文書を作らない。

別の文書を作ると、規約の規則と観点の対応が切れる。どちらが正かが分からなくなり、片方だけが更新される。実際にかつてレビュー観点の一覧を別ファイルとして持っていたが、そのファイルは納品先へ配られないまま、存在を要求する検査だけが配られていた。納品直後に必ず違反になる状態だった。

単体テスト設計書の決まりとレビューの観点の決まりは、それぞれ「各規約の規則のうち検査の手段に自分を含むものを観点とする」という規則を持つ。これが受け皿であり、観点の実体は各規約が持つ。

レビューの観点を各規約が持つ形にすると、AIエージェントは作業中のファイルに適用される規約だけを読めばよい。観点を1つの文書へ集めると、関係のない観点まで読むことになり、コンテキストを無駄に使う。規約の適用範囲（`scope` と `paths`）がそのまま観点の適用範囲になるのは、この形の利点である。

### 4.4 tool-defined 規約が §4 の節構成しか持たない理由

`rule-taxonomy.json` で `toolDefined: true` を宣言する子カテゴリは `delivery-payload/templates/rules/tool-defined/` 配下に置く。これらは既定で、生成器が `enforcement: none`・`checkable: false` を固定する。そのため front matter が要求する節は `## 概要`・`## 規則`・`## このプロジェクトの規則` の 3 つだけになる。「なぜこの水準までしか書かないか」「なぜ空雛形にしないか」は納品物の本文へ書かず、この設計文書へ集約する。理由は節として本文に残すものではなく、テンプレートを書く側（ツール側）の判断だからである。

例外は、ツール側が linter を同梱する子カテゴリである。`rule-taxonomy.json` の子カテゴリが `checker` の値を宣言している場合、生成器は `checkable: true`・`enforcement: advisory`・`uncheckableReason: null` を出し、linter とその回帰テストを納品先の子フォルダへ配る。`enforcement` が `advisory` になるのは、`none` を「機械が検知しない取り決め」と定めているためである。検知する以上この値は使えない。この場合は `## 違反時の手順` の節が必須になり、節は 4 つになる。linter の実体は `delivery-payload/templates/rules/checkers/` に置く。

かつては `## この文書の位置づけ` という締めの節を本文へ置いていた。この節は 2 つのことを述べていた。役割と方針の水準までを持つという位置づけと、どの開発フローの段階で効くかである。前者はこの設計文書が述べる内容であり、納品物の本文が繰り返す必要はない。後者は `rule-taxonomy.json` の `phases` が値として持ち、規約とフローの対応ページがそこから生成される。同じ情報を本文にも持つと二重管理になるため、節を廃止した。

**`## 規則` が役割と方針の水準に留まる理由**: 本文の規則は、対象リポジトリを見なくても確定する役割と方針の水準に留める。対象リポジトリ固有の具体は「このプロジェクトの規則」の節がリバース解析から受ける。空欄のまま納品すると、AI エージェントがこの領域で判断の拠り所を持たないまま動くことになる。

**空雛形にせず本文入りで納品する理由**: 大半の規約は、現場の担当者が根拠を得てから記入する空雛形として納品する。以下の 4 件は例外であり、理由は個別に持つ。

| 子カテゴリ | 空雛形にしない理由 |
|---|---|
| `ai-config-asset-management` | 定義と派生の関係はツールの動作そのものが決めており、プロジェクトごとに変えられる余地がない |
| `portal-maintenance` | ポータルが生成物であることはツールの動作そのものが決めており、プロジェクトごとに変えられる余地がない |
| `document-writing` | 設計書の記載形式と工程ごとの完了状態は、リバース設計の往復検証が成立する前提そのものであり、既定の標準として本文入りで配る。対象リポジトリ固有の追加は、本文の規則を打ち消さない範囲で「このプロジェクトの規則」の節へ記す |
| `test-policy` | 単体テスト設計書を基本設計フェーズの成果物として扱うことは、設計書の完了状態の定義と一体であり、既定の標準として本文入りで配る |

`document-writing` と `test-policy` は、対象文書（要件定義書・基本設計書・詳細設計書・単体テスト設計書）の定義・主な内容・完了状態を持つ。これらは `## 規則` 配下の `###` 見出しへ書く。これらは規則の実体そのものであり、目録という位置づけの説明ではない。

## 5. 判定結果 JSON の形式

規約提案 HTML が出力し、取り込みスキルが読む形式である。スキーマは以下のとおり。

```json
{
  "proposalId": "string",
  "generatedAt": "ISO8601",
  "total": 0,
  "judged": 0,
  "decisions": [
    {
      "parent": "string（ケバブケース）",
      "key": "string（ケバブケース）",
      "chapter": "string",
      "title": "string（日本語）",
      "summary": "string（1文）",
      "decision": "adopt | hold | reject | pending",
      "proposedRule": "string",
      "scope": "always | scoped",
      "paths": ["string"],
      "enforcement": "advisory | none",
      "checkable": true,
      "checkMethod": "string",
      "sources": ["string"]
    }
  ]
}
```

書き込み先の特定には表示名ではなく `parent` と `key` を使う。日本語の表示名を後から変えても、`parent` と `key` が変わらない限り対応が壊れない。

`checkMethod` は `checkable: true` のとき、何をどう検査するかを自然文で持つ。取り込みスキルはこの記述を元に linter を生成する。

`summary` は規約提案 HTML を作る時点で書く1文であり、取り込みスキルは要約作業をせずそのまま front matter の `summary` へ写す。取り込み時に `proposedRule` を要約する設計だと、実行者ごとに要約結果がぶれる。書く工程を提案側の1箇所に固定し、取り込みを非決定的にしない。

## 6. 変換規則

front matter の各鍵が、どの派生物のどこへ写るかを以下の表で定める。

| 鍵 | `.claude/rules/` | `.cursor/rules/*.mdc` | `AGENTS.md` | `project-portal/規約/` |
|---|---|---|---|---|
| `scope` | 配置先が `always/` か `scoped/` かを決める | `alwaysApply` の真偽 | 使わない | 使わない |
| `paths` | rule の paths に写す | `globs` にそのまま写す | 使わない | 使わない |
| `summary` | 使わない | `description` に写す | 索引の説明文 | カードの説明文 |
| `title` | 使わない | 使わない | 索引の表示名 | ページ見出し |
| `parent` + `key` | 配置パスを組む | ファイル名 `<parent>-<key>.mdc` を組む | 参照パスを組む | 分類とページ名を組む |
| 本文 | そのまま複製 | front matter の下にそのまま複製 | 複製しない（参照パスのみ） | HTML へレンダリング |
| `parent.yml` の `title` | 使わない | 使わない | 親見出しに使う | `規約/` の分類名に使う |

Cursor は素の `.md` を無視し、`.mdc` 拡張子と front matter を必須とする。この仕様が上表の変換根拠である。

`AGENTS.md` には規約本文を複製しない。Codex は `AGENTS.md` を各階層で探索して連結する仕様のため、参照パスだけで規約本文へ到達できる。本文を複製すると、同じ内容を持つ 2 つ目の実体が生まれ、片側だけを編集して他方が古くなる穴が増える。

`status: draft` の規約は派生生成の対象外とする。

承認済みの規約が 1 件も無い場合でさえ、`AGENTS.md` の索引ブロックは空の内容で書き換わる。索引が定義の現在の姿を映すためであり、古い索引が残るほうが害が大きい。生成対象が 0 件であることと、書き込みが起きないことは別である。

## 7. linter の配線

linter のスクリプト実体は `docs/rules/<親>/<子>/check-<子>.sh` の 1 つだけとする。`.claude/`・`.cursor/`・`.codex/` の 3 ツールとも同じファイルを呼ぶ。各ツールへ生成するのは呼び出しの登録だけである。

| 変換先 | 生成するもの |
|---|---|
| `.claude/` | `settings.json` の hooks に呼び出しを登録 |
| `.cursor/` | hooks の該当イベントへ呼び出しを登録 |
| `.codex/` | `config.toml` の hooks へ呼び出しを登録 |

スクリプトは複製しない。複製すると片側だけが更新される穴が生まれるためである。

Cursor には `beforeShellExecution` 等の hook 機構があり、Codex は信頼されたプロジェクトでリポジトリ内の hooks を読む。この 2 点が配線可能であることの根拠である。

派生物の手作業編集は、規約から派生を一時領域へ生成し直して現物と比べることで検知する。ハッシュを記録した台帳は持たない。台帳は状態をファイルへ持つ仕組みであり、記録と現物がずれたときにどちらが正かを決められない。毎回その場で生成して比べれば、規約が唯一の正になる。生成前の複製も持たない。派生物は版管理下にあり、戻す手段は版管理が提供する。

検知の対象は、丸ごと生成されるファイルだけに絞る。対象は `.claude/rules/` 配下の `rule.md` と `.cursor/rules/*.mdc` である。`AGENTS.md` と各ツールの hooks 登録ファイルは、既存の内容の一部だけを差し替える方式のため対象外とする。ファイル全体の突合が人の手による他の編集でも変わり、規約由来のずれと区別できないためである。

## 8. レビューの配線

規則の検査列で手段が `レビュー:` のものは、機械では判定できない。人ではなく、納品先で動くレビュー専門のエージェントが判定する。この節はその配線を定める。

### 8.1 誰が判定するか

判定するのは `rule-reviewer` である。定義は `.claude/agents/rule-reviewer.md` に置き、生成器が納品先へ配る。

**作った本人は判定しない。** 書いた本人が自分で判定すると、書いたときの前提をそのまま正しいものとして扱う。前提そのものが誤っていた場合、その誤りは判定を通過する。作成の文脈を持たないエージェントが、規約だけを頼りに判定する。

レビュアーは読み取りの道具しか持たない（`Read`・`Grep`・`Glob`・`Bash`）。判定の途中で対象を書き換えられない。修正は委任元が別途行う。

### 8.2 1体で全ての規約を見る

レビュアーは1体である。規約の親カテゴリごとに担当を分けない。

分けない理由は、規約の分類が業務上の都合で決まるためである。分けると、規約を1件足すたびにどの担当が見るかを決めることになり、分類の変更が担当の変更を引き起こす。担当の宣言をどこかに持てば、宣言と実体がずれる余地も生まれる。1体が全てを見るなら、規約が増えても構造は変わらない。

### 8.3 観点をレビュアーに持たせない

レビュアーの定義に観点を書かない。委任時に渡された `rule.md` を Read して判定する。

観点を定義に書くと、規約を更新するたびにレビュアーの定義も更新することになる。2か所に同じ内容が並び、片方だけが更新される。規約が唯一の情報源であり、レビュアーはそれを読む側に徹する。

### 8.4 どの規約を渡すかを解決する

対象ファイルに適用される規約は、`resolve-applicable-rules.sh` が返す。置き場は `docs/rules/agent-operations/ai-config-asset-management/` である。

使い方は `resolve-applicable-rules.sh <対象ファイル> [<対象ファイル>...]` である。出力は対象ファイルと `rule.md` のパスをタブで区切った形で、1マッチにつき1行を返す。適用が無いファイルには `(none)` を返す。

解決の手順は次のとおり。

1. `docs/rules/` 配下の全 `rule.md` を集める
2. front matter の `scope` が `always` なら、`paths` によらず全ファイルに適用する
3. `scope` が `scoped` なら、`paths` の glob と対象ファイルのパスを照合する
4. マッチした `rule.md` のパスを返す

このスクリプトが担当を返さないのは、レビュアーが1体だからである。

### 8.5 いつ判定するか

納品する開発フロースキル（`dev-flow`）が、各フェーズのゲートで判定を起こす。ゲートはユーザーへ成果物を提示して確定を問う仕組みであり、**提示する前に判定を得て、提示物へ結果を添える。**

流れは次のとおり。フェーズの作業を終えたら、変更したファイルを列挙する。`resolve-applicable-rules.sh` で適用される規約を解決し、`rule-reviewer` へ委任する。規則ごとに PASS / FAIL / 対象外 が返る。ゲートで成果物と判定を並べて提示し、ユーザーが確定を判断する。

### 8.6 指摘があっても止めない

判定に指摘があってもゲートは出す。ユーザーが「この指摘は今回は許容する」と判断できるためである。

**禁じるのは、指摘を伏せて確定を問うことである。** 指摘を隠して「この内容で確定してよいですか」と問えば、ユーザーは指摘の存在を知らないまま確定する。レビューを挟む意味が失われる。

### 8.7 レビュアーが居ない場合

`.claude/agents/rule-reviewer.md` が存在しない環境では、判定の手順を飛ばす。飛ばしたことをゲートで明示する。

**自分で判定して代替してはならない。** 作った本人が自分で判定した結果は、判定として扱わない。この禁止を書かないと、レビュアーが配られていない環境で作業中のエージェントが自分で判定し、「レビュー済み」として提示する。8.1 で述べた理由がそのまま失われる。

### 8.8 静的解析との切り分け

1つの規則が複数の手段を持つことがある。たとえば「復旧の手順を書いて試す」の検査列は、手順書が実在するかを走査する静的解析と、手順に従って復旧し目標の時間内に戻ることを確かめるテストの2つを持つ。

この場合、静的解析の部分は linter が、テストの部分は単体テスト設計書のテスト観点が担う。レビュアーが照合するのは `レビュー:` の部分だけである。

レビュアーが静的解析の部分まで照合すると、linter と同じことを二重に行う。逆に切り分けを定めないと、どちらも見ない規則が生まれる。

## 9. フォーマッタの合成

linter と違い 1 対 1 にならない。Prettier、Biome、`.editorconfig` のいずれも、プロジェクトに 1 つしか設定ファイルを置けないためである。

`formatter` 鍵は写し先の種類だけを宣言する。矯正する値そのもの（インデント幅・引用符・行長）は front matter が持たない。値は規約本文が日本語で述べ、設定ファイルへの反映は人が行う。

生成スクリプトが検出できる矛盾は 1 種類だけである。`none` を除く `formatter` 指定に 2 種類以上の値が混在する場合（規約 A が `prettier`、規約 B が `biome`）を矛盾とし、生成を止めて報告する。同じ種類を指す規約が複数あることは矛盾ではない。

値の水準の矛盾を機械的に検出するには、front matter が矯正値そのものを持つ必要がある。これは本設計の対象外とし、12 節に記す。

## 10. 決定事項と根拠

以下の 2 点を決定事項として定める。

1. **`enforcement` は `advisory` と `none` の 2 値とし、`block` は初期対象外とする**。根拠：提案から自動生成された検査がいきなり作業を止めると、誤検知のたびに現場が規約そのものを不信に感じる。まず `advisory` で運用し、実績が出てから現場の判断で手作業により `block` へ昇格させる。昇格を提案から自動で行うことはしない
2. **取り込み直後の `status` は `draft` とする**。根拠：取り込みスキルの誤書き込みを 1 段止めるためである。`draft` の規約は派生生成の対象外であり、人が `approved` に変えたものだけが各ツールへ写る

## 11. 整合の検査

生成スクリプトは実行時に以下を検査する。

| 検査キー | 内容 | 不合格時 |
|---|---|---|
| 鍵-対応整合 | `checkable: true` なら `checker` が実在し、`false` なら `uncheckableReason` が非空 | 生成を止める |
| 検査-テスト同伴 | `checker` があるなら `check-<子>.test.sh` も実在する | 生成を止める |
| 適用範囲-必須 | `scope: scoped` なら `paths` が非空 | 生成を止める |
| 階層-一致 | `parent` と `key` がフォルダ名と一致する | 生成を止める |
| 矯正-矛盾なし | 複数規約の `formatter` 指定に矛盾がない | 生成を止めて矛盾を報告 |
| 派生-未承認除外 | `status: draft` の規約が派生物に含まれていない | 生成を止める |
| 親宣言-実在 | 各親フォルダに `parent.yml` が実在し、`key` がフォルダ名と一致する | 生成を止める |
| 規則-検査列 | `## 規則` の表が 3 列（規則・内容・検査）または 4 列（規則・内容・根拠・検査）である | 生成を止める |
| このプロジェクトの規則-存在 | `## このプロジェクトの規則` の節が存在する | 生成を止めず警告を出す |
| 検査-手段明示 | `## 規則` の表のすべての行の検査列が `静的解析:` `テスト:` `レビュー:` `判定不能:` のいずれかで始まる | 生成を止める |

「検査-手段明示」は本設計への定義のみを行い、実装は別の担当が行う。

「検査-手段明示」が見るのは `## 規則` の表だけである。`## このプロジェクトの規則` はリバース解析が観測から起こす節であり、解析を実行するまでは「観測なし」の 1 行しか置けない。この行の検査列は「観測の有無は解析の実行結果に依存し、静的解析で判定できない」という理由で `不可` から始まる。両方の節を対象にすると、解析前の規約が例外なく生成を止められることになる。

「このプロジェクトの規則-存在」だけは生成を止めない。配布の操作は `docs/rules/agent-operations/ai-config-asset-management/` に置く検査の道具を無条件に上書きするが、`rule.md` は既存を残す。この非対称のため、すでに納品したリポジトリへ納品し直すと、検査の道具だけが新しくなり規約本文は古いまま残る。

この検査を生成を止める扱いで配ると、納品し直しただけで既納品先の検査が全件不合格になる。警告に留めることで、新しい節を持たない規約の存在を知らせつつ、生成そのものは通す。

## 12. 触れない範囲

この設計は以下を扱わない。

- hook スクリプトの中身の自動生成。`checkMethod` の自然文から linter を書き起こす作業は取り込みスキルの責務であり、本設計は形式だけを定める
- 既存の規約提案 HTML の意匠
- `docs/screens/` と `docs/common/` の形式
- フォーマッタの矯正値そのものの合成。インデント幅・引用符・行長といった値を front matter が持たないため、値の水準での矛盾検出と自動合成は行わない。値は規約本文が述べ、設定ファイルへの反映は人が行う
- hooks のイベント種別の選び方。設計 7 節はファイル編集の後に検査を走らせる形だけを定める。コミットメッセージやブランチ名のように、ファイルの内容ではなく実行時の入力を検査する規約は、この形に合わない。どのイベントで走らせるかを規約ごとに選ぶ仕組みは、本設計の対象外とする
- 既存の定義を上書きしてよいかの機械検査。取り込みスキルは `origin` と `status` で上書きの可否を分けるが、その判断を機械が検査する仕組みは持たない。実行者が手順を守ることに依存する

現場が対象プロジェクトの固有情報（本番環境の呼び名・記録の置き場・使用する AI ツール名等）を追記する場合は、生成された `rule.md` の `## 規則` 節より後ろに、現場が新設する節を追加する。取り込み・適用の操作はいずれも既存ファイルを上書きしないため、現場が追記した節は再納品でも保持される。
