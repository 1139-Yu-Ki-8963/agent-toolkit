# ポータル保守設計

## 目的

ポータルは設計を読む入口であり、対象コードの写しや調査時点の証跡を保管する場所ではない。本設計は、対象コードが変わった後も人が追随して直し続けなければ正しさを保てない情報を、ポータルとその生成元へ載せないための境界を定める。

## 保守可能性の原則

同じ事実を対象コードとポータルの両方へ記録し、対象コードの変更だけではポータルが更新されない情報は載せない。情報の長短や詳しさではなく、変更時に単一の正本から再生成または文書内だけで更新できるかで判断する。このため、行番号だけ、短いコードだけ、表のセルに入る断片だけという例外は設けない。

設計が決める事項と、調査時点の実装を観測した記録は分離する。前者はポータルで保守し、後者は検証記録で保管する。

## 載せないもの

| 対象 | 載せない理由 |
|---|---|
| 対象コードの行番号 | 1行ずれるたびに参照が古くなり、書いた時点でしか正しくないため |
| 対象コードの中身 | 実装が変わるたびに古くなり、対象コードとの二重管理になるため。コード柵、インラインコード、表のセル、HTML の `pre` 要素など記載形式を問わない |
| 根拠列・根拠パス列 | 対象コードへの参照、レビュー記録、社内資料の出典が混在し、ポータルの更新責任だけでは正しさを保てないため |
| 調査時点の実装識別子 | 変数名、定数名、型の内部名などは設計ではなく実装変更に追随する情報であるため |
| 実装構造に依存する集計値 | ファイル数、行数、関数数などは実装の増減だけで古くなり、設計内容を表さないため |

## 載せてよいものと境界

| 対象 | 境界 |
|---|---|
| ファイルのパスと関数名 | 対象を探す入口として、行番号を含めずに記載してよい。関数の本体、変数名、引数の実装表現は写さない |
| 設計書内の節への参照 | 同じ文書またはポータルで保守する設計書の節を参照してよい。外部資料の版やレビュー記録を根拠として埋め込まない |
| 疑似コード | 日本語で書いた分岐と繰り返しの入れ子に限る。対象コードの構文、変数名、定数名、式、呼び出し断片を含めない |
| 設計が定める関数名 | 設計上の契約として保守する関数名は記載してよい。観測した関数の個数や関数本体は記載しない |

## 根拠情報の置き場

根拠情報はポータルのページ単位ではなく、検証を1回実行した単位で `verification/portal-evidence/` に残す。1回の検証につき1ファイルとし、ファイル名は検証日と検証対象を識別できる名前にする。生成するポータルからはリンクせず、検証工程の記録として管理する。

列は `設計単位`、`確認項目`、`参照先`、`確認方法`、`確認結果`、`確認時点` とする。参照先はファイルパスと関数名までとし、行番号やコードの中身を含めない。レビュー記録や社内資料を使った場合は、その保管先と版を参照先へ記録する。証跡の更新責任は検証の再実行に置き、ポータルの保守責任と混ぜない。

## 段階移行

既存の見本と様式には根拠列とコードの中身が残っているため、検査の既定動作は検出結果の報告だけとする。既存箇所の除去が完了するまでは、書き込み時の検査と明示した `--strict` で不合格にする。除去完了後は、配布先の検証で `--strict` を既定の合格条件へ切り替える。報告のみの期間も新規追加を許す猶予ではなく、変更対象に検出があれば追加前に解消する。
