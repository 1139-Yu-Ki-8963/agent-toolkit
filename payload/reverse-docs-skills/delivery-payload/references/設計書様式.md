# 設計書様式

## 1. 目的

本書は、新規設計とリバース解析で共通して使う設計書の様式を定める。成果物の形は作成方法に依存させず、情報源と記入手順だけを分ける。

## 2. 様式の定義

設計書の様式は `delivery-payload/templates/リバース検証/` 配下の Markdown テンプレートで定義する。既存の生成スキルとの互換性を保つため物理パスは維持するが、このテンプレート一式をリバース解析専用とは扱わない。新規設計でも同じファイルを複製して使う。

対象種別は API、画面、テーブル、バッチ、帳票、外部連携および機能である。プロジェクト共通の設計文書も同じ扱いとする。

新規設計用のテンプレートを別に複製してはならない。別の定義を持つと、章の追加や表の変更が片方だけに入り、作成方法によって成果物の形が変わるためである。

## 3. 新規設計での記入手順

1. 対象の種別と工程に対応するテンプレートを、定義元から設計単位の出力先へ複製する。
2. テンプレートの章名、章順および表の列を変えず、決定済みの要件と設計判断を各章へ記入する。
3. 未確定の事項は推測で本文へ書かず、各文書の「要確認事項一覧」へ記入する。
4. 要確認事項の状態、回答、起票日および反映先は設計書へ加えず、設計単位ごとの台帳で管理する。

新規設計では、要求、利用者との合意および設計判断を情報源とする。実装済みコードから導出できたかどうかは記録しない。

## 4. リバース解析での記入手順

1. 新規設計と同じテンプレートを、定義元から設計単位の出力先へ複製する。
2. 既存コード、既存文書および確認済みの解析結果を情報源として各章を記入する。
3. 確定できない事項は推測で本文へ書かず、各文書の「要確認事項一覧」へ記入する。
4. 導出過程、根拠、状態、回答、起票日および反映先は設計書の列へ加えない。確定できない事項は各文書の「要確認事項一覧」で管理する。
5. すべての設計文書で、本文・表・別資料のいずれにも対象コードの file:line や行番号を記録しない。
6. 設計書から別の記述を参照する場合は、上位設計書の節、自書の別節、または関数単位の契約を参照先とする。実装位置を参照先の代用にしない。

## 5. 要確認事項一覧

すべての設計書で、要確認事項一覧は次の 3 列とする。

| キー | 確認事項 | 確認先 |
|---|---|---|
| `<内容を要約した意味語>` | `<確定していない事項>` | `<回答できる担当者、部門または資料>` |

- キーは文書内および設計単位ごとの台帳で同じ値を使う。
- 「導出できなかった理由」「暫定扱いにしている節」「起票日」「状態」などの管理情報を列に加えない。
- 確認先が未確定の場合も列は削らず、未確定であることを値として記す。

## 6. 章立ての同一性

新規設計とリバース解析は、同じ物理テンプレートを複製する。そのため、同じ種別および工程であれば章名、章順および表の列は一致する。作成方法ごとの差は、3 節と 4 節で定めた情報源と記入手順だけであり、成果物へ別の章や管理列を追加してはならない。

## 7. 参照先列の記入規則

テンプレートの表が持つ「参照先」列には、文書内の参照だけを書く。参照の形は、上位の設計書の節、自書の中の別の節、または関数単位の契約への参照のいずれかである。挙動の記述（「〜した場合に〜する」「〜を送出する」等）や実装の位置（対象コードの file:line）を書いてはならない。挙動の記述が要る場合は、参照先の列ではなく本文の該当節へ書く。実装の位置は別資料にも記録しない。

## 8. 文体の区分

読み手が納品先である文書（設計書・単位ごとの資料）は敬体（です・ます）で書く。私たちの作業のための文書（記入規則・検証の記録）は常体でよい。この区分は文書の種類で決まり、文書の中で節ごとに切り替えない。

対象文書の判定は次のとおりとする。

| 種別 | 文体 | 対象の例 |
|---|---|---|
| 顧客提示の文書 | 敬体 | `delivery-payload/templates/リバース検証/` 配下の各設計書テンプレート（API 基本設計書・API 詳細設計書・画面詳細設計書・機能設計書・バッチ/帳票/外部連携の各設計書・テーブル定義書・ビジネス概要・アーキテクチャ調査書等） |
| 納品物の案内 | 敬体 | 納品先が成果物一式の配置と生成状況を読む `納品物フォルダ体系.md` |
| 私たちの作業のための文書 | 常体でよい | 記入規則を説明するテンプレート内の HTML コメント、詳細設計記述規約のような執筆規律そのものを定める内部文書、検証の記録。具体例は検査できない理由を記録する文書（`design-notes.md`）・納品するスキルの定義（`SKILL.md`）・レビューを担う定義（`rule-reviewer.md`） |
| このリポジトリの内部正本 | 常体でよい | 抽出・マニフェスト・用語契約・工程・報告・実装契約・規約生成・規約執筆・設計書様式を定める `facts-schema.md`・`manifest-schema-extensions.md`・`semantic-glossary-contract-v0.1.md`・`リバース工程設計.md`・`完了報告の書き方.md`・`実装契約定義.md`・`規約定義と派生生成の設計.md`・`規約定義の執筆手順.md`・`設計書様式.md` |
| 対象リポジトリへ配る内部規約 | 常体でよい | 人と AI の分担、AI 設定資産、文書執筆、命名、ポータル保守、レビュー、テスト設計の作業規律を定める `delivery-payload/templates/rules/tool-defined/` 配下の `ai-behavior.md`・`ai-config-asset-management.md`・`document-writing.md`・`naming.md`・`portal-maintenance.md`・`review-checklist.md`・`test-policy.md` |

生成スキルが顧客提示の文書へ自由記述の本文（要約・説明・冒頭の案内文等）を書く場合は、この区分に従い敬体で書く。表の列名・固定の見出し・プレースホルダはこの区分の対象外とする。

生成文書に常体の文末が混入していないかは機械検査できる。
検出する文末は「である」と「だ」である。
検査の本体は、配布物側の `check-document-style-register.sh` である。
生成エンジン側は、配布物側の本体を呼び出す（1-237）。

常体でよい文書を誤って不合格にしないため、除外の仕組みを持つ。
除外一覧は `document-style-exclusions.json` の `excludedBasenames` に置く。
各項目は、ファイル名と内部文書の配置条件を組にして持つ。
除外には、basenameと正規化したパスの配置条件を使う。
両方が一致する場合だけ除外する。
同じbasenameでも、顧客提示の配置にある文書は除外しない。
一覧を検査スクリプト自身へ直書きしない（1-260）。
対象を追加する場合は、本節の表と同JSONの両方を更新する。

自己テストは次のコマンドで実行する。

```bash
bash delivery-payload/templates/rules/checkers/check-document-style-register.sh --self-test
```

配布物を対象に検査する場合は、次のように対象を引数で指定する。

```bash
bash delivery-payload/templates/rules/checkers/check-document-style-register.sh delivery-payload/
```

## 9. 冒頭案内の記入規則

この規則は `delivery-payload/templates/リバース検証/` 配下の全 Markdown テンプレートに適用する。

- 冒頭案内には、読み手が各節で何を見て、確認・判断・回答など何をするかを書く。
- 本文に複数の節がある場合、冒頭案内を `節`・`内容`・`読み手へのお願い` の3列の表にし、本文の節ごとに1行を対応づける。
- 本文が1節だけの場合も、その節の内容と読み手へのお願いを明示する。
- 作る側の判断の理由、保管方法、作業の経緯、文書作成の方針、件数の内訳は冒頭案内に書かない。

テンプレート内の `INTRODUCTION_GUIDANCE` コメントは、この節への適用宣言である。

## 10. 節の位置づけ

設計文書の各節は、作り直しても使える層（仕様）と、今の作りに固有の層（現行実装）のどちらか、または両方を含む。読み手が節ごとに判断できるよう、`## §N` の見出しの直後に位置づけの1行を置く（改善課題1-287・1-302）。別の言語で作り直す検討では、どこを読めばよいかの印になる。

| 語 | 意味 | 書式 |
|---|---|---|
| 仕様 | 作り直しても使える層。業務の決まり・外部との契約・満たすべき性質 | `**この節の位置づけ: 仕様**` |
| 現行実装 | 今の作りに固有の層。実装の構造・内部のデータ・実装の判断 | `**この節の位置づけ: 現行実装。<理由を1文>。<作り直すときの扱い>**` |
| 仕様／現行実装 | 両方を含む節 | `**この節の位置づけ: 仕様／現行実装。<Xは仕様、Yは現行実装という対比の1文>**` |

- 語は「仕様」「現行実装」「仕様／現行実装」の3語に固定する。特定の言語名（Perl・PHP・Java 等）や、移行が起きるという前提を含む語を使わない
- 「現行実装」の節は、末尾に作り直すときの扱いを次のいずれか1つで書く。「作り直す際は引き継がない」「作り直す前に、〜を確かめる必要がある」「作り直す前に、〜を決める必要がある」
- 文書の冒頭（表題の直後）に、位置づけごとの節の一覧を次の書式で置く

```text
**この文書の位置づけ**（別の言語で作り直す場合は、まず「仕様」から読む）

- 仕様: §1 API概要、§2 リクエスト
- 現行実装: 該当なし（API実装記録 §1 疑似コード・§4 実装契約 へ分けた）
- 仕様／現行実装（詳細は各節の太字1行を見る）: 該当なし
```

- 様式が置く位置づけは初期値である。生成スキルは対象コードの実測に応じて節ごとに改めてよいが、語は上の3つから選ぶ。改めた場合は冒頭の一覧も合わせて直す
- `docs/scripts/check-section-classification.sh` が、様式の全節に位置づけの行があること、語が3つに限られること、言語名を含まないことを機械で見る
