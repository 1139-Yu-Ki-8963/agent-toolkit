## 共通ルール

### フェーズ運転

フェーズは 1 つずつ進める。各フェーズの末尾には HIL ゲートがあり、そこでは必ず停止し、承認のないまま次のフェーズへ進むことはしない。承認＝そのフェーズの確定である。

差し戻し（修正指示）を受けたとき、再びその HILゲートに戻る。後続のフェーズで、承認済みのフェーズに対して変更の必要が生じた場合は、該当フェーズまで戻って承認を取り直す。

`Phase1` や「HILゲート1」といった内部の管理記号は人間に見せない。いま何をした・次に何をするかを普通の言葉で言う。

### 規約レビュー

各フェーズのゲートで提示する前に、そのフェーズで作った成果物を規約へ照らす。**提示物にレビュー結果を必ず添える。** 指摘を隠して確定させないための手順である。

**手順**

1. そのフェーズで作成・変更したファイルを列挙する
2. 適用される規約を解決する

   ```
   bash docs/rules/agent-operations/ai-config-asset-management/resolve-applicable-rules.sh <ファイル> [<ファイル>...]
   ```

   出力は `<対象ファイル>` と `<rule.md のパス>` をタブで区切った形である。適用が無いファイルは `(none)` が返る

3. 返された `rule.md` の重複を除いた一覧を作る
4. `rule-reviewer` へ委任する。委任のプロンプトには次を必ず含める
   - レビューの対象となるファイルのパス一覧
   - 手順3で作った `rule.md` のパス一覧
   - このフェーズで何を作ったかの1文
5. 返ってきた判定を、ゲートの提示物へ添える

**レビュアーが居ない場合**

`.claude/agents/rule-reviewer.md` が存在しない場合、この手順を飛ばす。飛ばしたことをゲートで明示する（「規約レビュー: 実行せず（レビュアー未配置）」）。**自分でレビューして代替しない。** 作った本人が自分で判定した結果は、判定として扱わない。

**指摘があっても止めない**

指摘があってもゲートは出す。ユーザーが「この指摘は今回は許容する」と判断できるためである。指摘を伏せて「確定してよいですか」と問うことを禁じる。

### HILゲート

各フェーズの末尾にゲートを置き、次のとおり運転する。

1. 「規約レビュー」の手順を実行し、判定を得る。
2. そのフェーズの提示物（各フェーズで定義）と規約レビューの結果を示し、そのフェーズの問いを出す。
3. 「確定する」「さらに詳しく聞く」「自由記述」を選べる形で出す。
   選択UIを使う場合、自由記述の枠はハーネスが自動で付くため、選択肢として列挙するのは「確定する」「さらに詳しく聞く」の2つとする。
   選択UIが使えない環境では、3つとも番号付きテキストで出す。
4. 確定する → そのフェーズを確定し、次のフェーズへ進む。
   さらに詳しく聞く → 説明を足し、フェーズは進めずに同じゲートを出し直す。
   自由記述 → 差し戻し。同じフェーズに戻る。
5. Phase4 のゲートだけは「確定する」「差し戻す」の二値であり、「さらに詳しく聞く」を持たない。
   プランモード経路では `ExitPlanMode` に委ねる。フォールバック経路では 3 の形で「確定する」「差し戻す」を出す。
6. 選択肢のラベルは対象に合わせて言い換える（例: 要件を確定する / 完了を承認する）。

## Phase1 要件すり合わせ

### 追加の明示コンテキスト

#### 動作

Phase1 の入力は、自由形式の開発要件に関する情報である。

AI は現行調査と並行して、ユーザーが提供する要件の不明点を 1 問ずつ確認していく。集まった内容を「目的 / 対象機能 / 変更内容 / 影響範囲 / 受入条件」に整理したうえで、開発要件を固める。

事実を集める調査と成果物を変更する作業は混ぜず、まず現行調査を終えてから要件の不明点を確認する。あわせて、この開発要件について何ができたら完了かを、測ることのできる形で先に決めておく。各工程を終えてよい条件も、成果物の実在または出力で確かめられる形にしておくと、後続の工程で終わりの判断がぶれない。

**ゲート**

- 提示物: 整理済みの開発要件と、規約レビューの結果
- 問い: 「この内容で開発要件を確定してよいですか？」
- 確定するもの: 開発要件

#### 動作

## Phase4 実装プラン策定（動作確認観点一覧を内包）

### 追加の明示コンテキスト

TODO:src/*（正規表現的にあっているかもチェック）

#### 動作

プランモードが使える環境であれば `EnterPlanMode` を呼ぶ。プランモードの使用が拒否された場合や利用できない場合はフォールバックとして実装プラン MD（例: `実装プラン_<対象>.md`）を作成する。どちらの経路をとっても、成果物の中身とゲートの意味は同一とする。

このフェーズでは、実装後の動作確認を実装プランの一部として含めて策定し、実装と確認を同一プランで一体管理する。

作成するプランは開発要件に対して 1 本とし、次の順で構成する。フォールバックで MD を作る場合も構成は同じである。

1. 変更対象ファイル一覧。ファイルごとに、詳細設計のどこに対応するかを明記する。
2. 実装手順。実行順序と、各手順の完了条件を書く。
3. 動作確認観点一覧。観点・ケースごとに「事前準備 / 操作手順 / 入力 / 期待結果」を具体化する。
4. やらないこと。スコープ外とその理由を書く。

動作確認の観点・ケースは今回の実装差分に関係する範囲であり、既存実装の網羅的な回帰試験の設計ではない。

実装を誰かに委任する場合は、新規ファイルは全文、編集は変更前後の対、置換は仕様といった確定済みの内容を渡す。「変更対象ファイル一覧」には変更してよい範囲を明示し、着手前にその範囲を確定させておく。動作確認観点一覧の根拠は、コードではなく基本設計で確定した外部仕様・業務ルール・制約に置く。

**ゲート**

- 提示物: 実装プランと、規約レビューの結果
- 問い: プランモード経路では `ExitPlanMode` の承認要求。フォールバック経路では「このプランで確定してよいですか？」
- 確定するもの: 実装手順と動作確認の観点

## Phase5 実装と動作確認

### 追加の明示コンテキスト

なし

#### 動作

確定した実装プランの実装手順どおりにソースを変更する。続いて、実装プラン内の「動作確認観点一覧」と 1:1 で対応させながら、実際に動かして各ケースを確認し、結果を記録する。

プランに影響しない実装バグは自動修正する。これを除いて、作業中に不足や矛盾が判明した場合は、プランを勝手に拡張せず Phase4 に戻って承認を取り直す。

実装は Phase4 で決めた内容を反映する作業であり、決定そのものをこの段階でやり直さない。動作確認で得た結果や、委任した相手からの報告は、コマンドの出力や生成物のパスといった別の経路で裏を取ってから次の判断に使う。

共通化は、同じ形が2箇所目に現れてから部品として切り出す。1例しかない段階での共有化は、2例目が来たときに条件分岐で汚れる。

### 実装時の設計判断を設計書へ記録する

実装中に設計上の方式を選択した場合は、実装を終える前に次の手順を実行する。
対象は、複数の実装方式からの選択、既定値・境界値・再試行回数の決定、依存先・データ構造・責務の置き場の選択、および一見単純な方式をあえて採らなかった場合である。

1. 判断した本人が、その時点で確認できる事実を整理する。判断材料は、合意済みの要件・設計、実測した結果、利用中の仕様、またはユーザーが明示した方針に限る。
2. 対応する詳細設計書の「設計判断とその理由」節へ、1 判断につき 1 行を次の表形式で記録する。

   | 判断キー | 設計判断 | 選択理由 | 判断材料 | 選ばなかった選択肢 | 不採用理由 |
   |---|---|---|---|---|---|
   | `<変更単位で一意のキー>` | `<採用した方式>` | `<採用した理由>` | `<要件・実測結果・仕様・明示方針>` | `<比較した方式>` | `<採らなかった理由>` |

3. 判断や理由を、コードの形、一般論、過去の類似事例から推測して書かない。本人の判断、判断時の会話、または検証できる判断材料に存在しない内容は補わない。
4. 設計判断、選択理由、判断材料のいずれかを事実として記録できない場合は、判断行を作らず、同じ詳細設計書の「要確認事項一覧」へ「確認したい判断・不足している情報・確認先」を 1 行で記録する。確認が済むまでは、その判断を確定済みとして扱わない。
5. 設計書の変更を実装ファイルと同じ変更に含める。実装だけ、または設計書だけを先に完了扱いにしない。Phase4 で確定した変更対象ファイル一覧を実装後の差分と突き合わせ、規約レビューの対象には実装ファイルと対応する詳細設計書の両方を含める。

実装中の判断が Phase3 で承認した詳細設計と矛盾する場合は、先に Phase3 へ戻り、設計書を更新して承認を取り直す。承認後の内容を上記の表へ記録してから実装を続ける。

`rm` や `rm -rf` の実行前には、消える対象のパスを一覧で表示して確かめる。`push --force`・`reset --hard`・`rebase`・`filter-branch` のように履歴を書き換える操作は、影響を受けるブランチと他の作業者を確かめてから行う。ファイルを丸ごと書き換える前には現在の内容を読み、データの一括変更は実行前に同じ条件で対象の件数を数える。本番環境に対する破壊的操作は、開発環境と同じ手順で行わず、実行者・承認者・切り戻しの手段を決めてから実行する。

作業の途中経過は会話ではなくリポジトリへ残し、中断するときは次に何から始めるかを1文で書き残す。完了の報告には「できた」という申告ではなく、テストの出力・生成物のパス・差分を添える。途中で終えた作業は完了として報告せず、何が残っているかを書く。

外部へ送信するコマンドは、送信先と内容を確かめてから実行する。手元で実行できないコマンドは手順書へ書かず、実行できる形へ置き換える。

実装後は、共通ルールの「規約レビュー」を実行してから統合する。レビュー前の統合は、指摘が出ても戻す手数が大きい。

**ゲート**

- 提示物: 実装概要と、動作確認の全ケース pass の結果表と、規約レビューの結果
- 問い: 「この内容で完了としてよいですか？」
- 確定するもの: 要求 1 件の完了。承認をもって本手順を終了する。

### 完了の記録

承認を得たら、`docs/scope-and-progress/開発フロー完了記録.md` へ 1 節を追記する。ファイルが無ければ新規作成する。過去の節は書き換えず、新しい節を追記する。

追記する節の形式は次のとおり。既存の節がある場合も同じ形式に揃える。

```markdown
### <承認を得たISO8601日時>

| 項目 | 値 |
|---|---|
| 要求 | <Phase1で確定した開発要件の要約> |
| コミット | `<実装を含む最新コミットのハッシュ。全長40桁>` |

#### 実装概要

<Phase5の提示物にある実装概要>

#### 動作確認結果

| ケース | 結果 |
|---|---|
| <動作確認観点一覧のケース> | pass |

#### 規約レビュー結果

<Phase5の提示物にある規約レビューの判定>
```

ファイルを新規作成する場合は、次の前置き（`## 記録` 見出しまで）を先に書いてから節を追記する。

```markdown
# 開発フロー完了記録

この文書は、`/dev-flow` の Phase5 ゲートで完了承認を得るたびに 1 節を追記する台帳である。過去の節は書き換えない。

## 記録
```

動作確認結果の表は、Phase5 で確認した動作確認観点一覧のケースと 1:1 で対応させる。ケースを 1 件も確認していない状態では確定しない。結果の列は `pass` のみを書く。不合格のまま確定することはない（不合格が出た時点で Phase4 との整合を確認し、直してから再確認する）。

## self-test（合成フィクスチャ）

`/dev-flow --self-test` は、周囲のリポジトリを探索せず、`mktemp -d` で作った隔離ディレクトリだけを使って次を実行する。

1. 隔離ディレクトリを Git リポジトリとして初期化する。合成の詳細設計書と空の実装ファイルを作り、`git add` で基準状態を index へ登録する。コミットは作らない。詳細設計書の「設計判断とその理由」節には上記 6 列の空の表を置き、「要確認事項一覧」節も置く。
2. 空の実装ファイルと、次の判断材料を合成入力として与える。
   - 同じキーを 2 回以上検索するため、配列の全走査ではなくキー索引を採用する。
   - 合成計測では 1,000 件を 100 回検索し、全走査は 42 ms、キー索引は 3 ms だった。
3. Phase5 の手順を 1 件分実行し、実装ファイルへキー索引を使う処理を記述すると同時に、詳細設計書の表へ次の 1 行を記録する。

   | 判断キー | 設計判断 | 選択理由 | 判断材料 | 選ばなかった選択肢 | 不採用理由 |
   |---|---|---|---|---|---|
   | `lookup-index` | キー索引を使う | 同じキーを繰り返し検索するため | 合成計測: 1,000 件を 100 回検索し、全走査 42 ms、キー索引 3 ms | 配列の全走査 | 合成計測でキー索引より遅かったため |

4. Bash で次を検査する。
   - 実装ファイルは、項目列から `Map` を作る関数と、キーを受け取って索引から項目を返す関数を公開する。Node.js で実装ファイルを読み込み、戻り値が `Map` のインスタンスであること、末尾のキーで値を取得できること、存在しないキーでは `undefined` を返すことを実行して検査する。コメントや文字列に `new Map(` と `.get(` があるだけでは合格にしない。
   - 「設計判断とその理由」節の範囲だけを次の `##` 見出しまで抽出し、その範囲に `lookup-index` のデータ行が 1 件だけ存在する。
   - 対象のデータ行を `|` で分割して前後の空白を除き、判断キーから不採用理由までの 6 セルがすべて空でない。検査器の否定確認として、選択理由を空にした行は不合格になる。
   - index に登録した基準状態に対する `git diff --name-only` の結果が実装ファイルと詳細設計書の 2 件だけである。さらに `git status --porcelain` の結果が、この 2 ファイルの `AM` 行だけであることを検査する。片方だけ、未追跡ファイルがある、追加の index 変更がある、または 2 件以外の作業ツリー変更がある場合は不合格にする。
5. 4 条件がすべて成立した場合だけ `self-test PASS: 合成フィクスチャ1件の実装と設計判断の同時記録を確認` と報告する。1 条件でも不成立なら `self-test FAIL` と不成立の条件を報告し、通常フローは開始しない。終了時は隔離ディレクトリを削除する。
