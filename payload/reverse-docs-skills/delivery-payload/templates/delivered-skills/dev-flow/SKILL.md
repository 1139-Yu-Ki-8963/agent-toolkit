## 前提

- 規約: `docs/rules/<親カテゴリ>/<子カテゴリ>/rule.md`。件数は `docs/rules/` の実体が示す。各規約の front matter の `alwaysApply` と `paths` が適用範囲を示す
- 設計書の置き場: `docs/design/<種別>/<種別>-<キー>/` 配下。種別は `screens`・`apis`・`tables`・`batches`・`reports`・`externals`・`features`。基本設計は `basic/`、詳細設計は `detail/`、テスト設計は `test/`
- 要件定義: `docs/requirements/`
- 作業の記録: `docs/tasks/work-records/`

対象の設計種別を開発要件から一意に決められない場合は、Phase1 で確認してから Phase2 へ進む。

## 起動

引数ありで呼ばれたときは、引数を Phase1 の入力として Phase1 から開始する。

引数なしで呼ばれたときは、次の案内を 2〜3 行で出して停止する。次のユーザー入力を Phase1 の入力として扱う。

```
要件すり合わせ → 基本設計 → 詳細設計 → 実装プラン → 実装と動作確認 を、各段階で確認しながら一緒に進めます。
細かい技術の整理はこちらでやるので、やりたいこと・困っていることをそのまま教えてください（例:『〇〇が分かりにくい、△△したい』）。
```

## 共通ルール

### フェーズ運転

フェーズは 1 つずつ進める。各フェーズの末尾には確認の関門があり、そこでは必ず停止し、承認のないまま次のフェーズへ進まない。承認＝そのフェーズの確定である。

差し戻し（修正指示）を受けたとき、再びその関門に戻る。後続のフェーズで、承認済みのフェーズに対して変更の必要が生じた場合は、該当フェーズまで戻って承認を取り直す。

`Phase1` や「関門1」といった内部の管理記号は人間に見せない。いま何をした・次に何をするかを普通の言葉で言う。

### 規約の適用

各フェーズで成果物を作る前に、変更対象のファイルパスに `paths` が一致する規約を読み、その規則に従って書く。関門の提示物には、参照した規約の名前を添える。

### 確認の関門

各フェーズの末尾に関門を置き、次のとおり運転する。

1. そのフェーズの提示物（各フェーズで定義）を示し、そのフェーズの問いを出す
2. 「確定する」「さらに詳しく聞く」「自由記述」を選べる形で出す。選択UIを使う場合、自由記述の枠は自動で付くため、選択肢として列挙するのは「確定する」「さらに詳しく聞く」の 2 つとする。選択UIが使えない環境では、3 つとも番号付きテキストで出す
3. 確定する → そのフェーズを確定し、次のフェーズへ進む。さらに詳しく聞く → 説明を足し、フェーズは進めずに同じ関門を出し直す。自由記述 → 差し戻し。同じフェーズに戻る
4. Phase4 の関門だけは「確定する」「差し戻す」の二値であり、「さらに詳しく聞く」を持たない。プランモード経路では `ExitPlanMode` に委ねる
5. 選択肢のラベルは対象に合わせて言い換える（例: 要件を確定する / 完了を承認する）

## Phase1 要件すり合わせ

Phase1 の入力は、自由形式の開発要件に関する情報である。

現行調査と並行して、ユーザーが提供する要件の不明点を 1 問ずつ確認していく。集まった内容を「目的 / 対象機能 / 変更内容 / 影響範囲 / 受入条件」に整理したうえで、開発要件を固める。

事実を集める調査と成果物を変更する作業は混ぜず、まず現行調査を終えてから要件の不明点を確認する。あわせて、この開発要件について何ができたら完了かを、測ることのできる形で先に決めておく。

**関門**

- 提示物: 整理済みの開発要件
- 問い: 「この内容で開発要件を確定してよいですか？」
- 確定するもの: 開発要件

## Phase2 基本設計

Phase1 で合意した開発要件を元に、対応する設計単位の `basic/` にある設計書を差分更新する。設計書が無ければ同じ置き場へ新規作成する。対象は外部仕様・データ・エラーなど、該当する章のすべて。

ここでは、外部仕様・業務ルール・例外等が矛盾なく確定していることを確認する。あわせて、1 つの構成要素の停止が全体の停止になる単一の故障点を設計の時点で洗い出し、保存したデータを実際に復元できる手段を設計へ含める。用語の追加・変更・廃止は `docs/design/common/用語辞書.md` で行い、各設計書へ直接書き足さない。

**関門**

- 提示物: 反映した設計内容
- 問い: 「この内容で設計を確定してよいですか？」
- 確定するもの: 基本設計

## Phase3 詳細設計

Phase1〜2 の開発要件と基本設計を元に、対応する設計単位の `detail/` にある設計書を差分更新する。設計書が無ければ同じ置き場へ新規作成する。

ここでは、実装前に不明点ゼロであることを確認する。画面・外部との受け渡し・データの構造に関わる変更は、詳細設計の合意を実装より先に置く。実装の後に設計を変えると、実装したものを捨てることになる。

**関門**

- 提示物: 反映した設計内容
- 問い: 「この内容で設計を確定してよいですか？」
- 確定するもの: 詳細設計

## Phase4 実装プラン策定（動作確認観点一覧を内包）

プランモードが使える環境であれば `EnterPlanMode` を呼ぶ。使えない場合は実装プランの Markdown（例: `docs/tasks/実装プラン_<対象>.md`）を作成する。どちらの経路をとっても、成果物の中身と関門の意味は同一とする。

このフェーズでは、実装後の動作確認を実装プランの一部として含めて策定し、実装と確認を同一プランで一体管理する。作成するプランは開発要件に対して 1 本とし、次の順で構成する。

1. 変更対象ファイル一覧。ファイルごとに、詳細設計のどこに対応するかを明記する
2. 実装手順。実行順序と、各手順の完了条件を書く
3. 動作確認観点一覧。観点・ケースごとに「事前準備 / 操作手順 / 入力 / 期待結果」を具体化する
4. やらないこと。スコープ外とその理由を書く

動作確認の観点・ケースは今回の実装差分に関係する範囲であり、既存実装の網羅的な回帰試験の設計ではない。動作確認観点一覧の根拠は、コードではなく基本設計で確定した外部仕様・業務ルール・制約に置く。対応する設計単位の `test/` にテスト設計書があれば、その観点を起点にして今回の差分に関係するケースを選ぶ。テスト設計書に無い観点を新たに確認する場合は、同じテスト設計書へその観点を追記し、実装と同じ変更に含める。

実装を誰かに委任する場合は、新規ファイルは全文、編集は変更前後の対、置換は仕様といった確定済みの内容を渡す。「変更対象ファイル一覧」には変更してよい範囲を明示し、着手前にその範囲を確定させておく。

**関門**

- 提示物: 実装プラン
- 問い: プランモード経路では `ExitPlanMode` の承認要求。それ以外では「このプランで確定してよいですか？」
- 確定するもの: 実装手順と動作確認の観点

## Phase5 実装と動作確認

確定した実装プランの実装手順どおりにソースを変更する。続いて、実装プラン内の「動作確認観点一覧」と 1:1 で対応させながら、実際に動かして各ケースを確認し、結果を記録する。

プランに影響しない実装バグは自動修正する。これを除いて、作業中に不足や矛盾が判明した場合は、プランを勝手に拡張せず Phase4 に戻って承認を取り直す。実装は Phase4 で決めた内容を反映する作業であり、決定そのものをこの段階でやり直さない。動作確認で得た結果や、委任した相手からの報告は、コマンドの出力や生成物のパスといった別の経路で裏を取ってから次の判断に使う。

共通化は、同じ形が 2 箇所目に現れてから部品として切り出す。1 例しかない段階での共有化は、2 例目が来たときに条件分岐で汚れる。

### 実装時の設計判断を設計書へ記録する

実装中に設計上の方式を選択した場合は、実装を終える前に次の手順を実行する。対象は、複数の実装方式からの選択、既定値・境界値・再試行回数の決定、依存先・データ構造・責務の置き場の選択、および一見単純な方式をあえて採らなかった場合である。

1. 判断した本人が、その時点で確認できる事実を整理する。判断材料は、合意済みの要件・設計、実測した結果、利用中の仕様、またはユーザーが明示した方針に限る
2. 対応する詳細設計書の「設計判断とその理由」節へ、1 判断につき 1 行を次の表形式で記録する

   | 判断キー | 設計判断 | 選択理由 | 判断材料 | 選ばなかった選択肢 | 不採用理由 |
   |---|---|---|---|---|---|
   | `<変更単位で一意のキー>` | `<採用した方式>` | `<採用した理由>` | `<要件・実測結果・仕様・明示方針>` | `<比較した方式>` | `<採らなかった理由>` |

3. 判断や理由を、コードの形、一般論、過去の類似事例から推測して書かない
4. 設計判断、選択理由、判断材料のいずれかを事実として記録できない場合は、判断行を作らず、同じ表の行に判断キーだけを書き、設計判断の欄へ「未確定: <確認したい判断・不足している情報・確認先>」を 1 行で記録する。確認が済むまでは、その判断を確定済みとして扱わず、Phase5 の関門でその行を提示物に含めてユーザーへ示す
5. 設計書の変更を実装ファイルと同じ変更に含める。実装だけ、または設計書だけを先に完了扱いにしない

実装中の判断が Phase3 で承認した詳細設計と矛盾する場合は、先に Phase3 へ戻り、設計書を更新して承認を取り直す。

### 取り消せない操作の扱い

`rm` や `rm -rf` の実行前には、消える対象のパスを一覧で表示して確かめる。`push --force`・`reset --hard`・`rebase`・`filter-branch` のように履歴を書き換える操作は、影響を受けるブランチと他の作業者を確かめてから行う。ファイルを丸ごと書き換える前には現在の内容を読み、データの一括変更は実行前に同じ条件で対象の件数を数える。本番環境に対する破壊的操作は、実行者・承認者・切り戻しの手段を決めてから実行する。外部へ送信するコマンドは、送信先と内容を確かめてから実行する。

作業の途中経過は会話ではなくリポジトリへ残し、中断するときは次に何から始めるかを 1 文で書き残す。完了の報告には「できた」という申告ではなく、テストの出力・生成物のパス・差分を添える。途中で終えた作業は完了として報告せず、何が残っているかを書く。

**関門**

- 提示物: 実装概要と、動作確認の全ケース pass の結果表
- 問い: 「この内容で完了としてよいですか？」
- 確定するもの: 要求 1 件の完了。承認をもって本手順を終了する

### 完了の記録

承認を得たら、`docs/tasks/work-records/開発フロー完了記録.md` へ 1 節を追記する。ファイルが無ければ新規作成する。過去の節は書き換えず、新しい節を追記する。

```markdown
### <承認を得た日時>

| 項目 | 値 |
|---|---|
| 要求 | <Phase1で確定した開発要件の要約> |
| コミット | `<実装を含む最新コミットのハッシュ>` |
| 設計書 | <更新した設計書のパス。無ければ「影響なし」> |

#### 実装概要

<Phase5の提示物にある実装概要>

#### 動作確認結果

| ケース | 結果 |
|---|---|
| <動作確認観点一覧のケース> | pass |
```

動作確認結果の表は、Phase5 で確認した動作確認観点一覧のケースと 1:1 で対応させる。ケースを 1 件も確認していない状態では確定しない。不合格のまま確定することはない（不合格が出た時点で Phase4 との整合を確認し、直してから再確認する）。
