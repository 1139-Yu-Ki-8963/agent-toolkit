# 様式に見本が無く生成物と突き合わせられない問題を直す指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

42 の様式のうち 23 に、生成済みの見本が 1 件も無い。
様式を直しても、そのとおりに出るかを誰も確かめられない。見本を置く。

## なぜ必要か

2026-08-24 に実測した。

    様式            42 件
    見本がある様式    19 件（画面 6・共通 13）
    見本が無い様式    23 件（API 4・テーブル 4・バッチ 4・帳票 4・外部連携 4・機能 3）

**見本が無い種別は、様式と生成物を突き合わせる手立てが無い。**

過去に「生成された API 詳細設計書が 50 件すべて様式の節構成から外れている」という
指摘があった（改善課題 1-201）。同じことが今また起きていても、確かめる材料が無い。

同日、見本のある画面詳細設計書では実際にずれが見つかった。様式は欄名を
「根拠」から「参照先」へ改め終えていたのに、見本 10 件は古い名前のままだった。
**見本があったから見つかった。** 無い 23 様式では、同じずれが起きていても分からない。

### 作れることは確かめた

見本を作る道具は既にある。同日、次を実測した。

    scaffold-design-unit.sh api basic <出力先> order-list "受注一覧API"
      → docs/design/apis/api-order-list/基本設計/API基本設計書.md が出る
      → 節構成は様式と一致した

    prepare-verification-input.sh --output <出力先>
      → 全種別 42 件が出る（API 4・テーブル 4・バッチ 4・帳票 4・外部連携 4・機能 3・画面 6・共通 13）
      → API の基本設計書・詳細設計書とも節構成は様式と一致した

**道具が足りないのではなく、作った結果を見本として置いていないだけである。**

### 残る 2 件の未置換

疑似入力で作った見本には、関連資料へのパスが 2 件、記入欄のまま残る。

    APIテスト設計書   `<API基本設計書のパス>`
    API基本設計書     `<API詳細設計書のパス>`

同じ単位の中の別の資料を指すため、単位の置き場が決まれば埋められる。
見本を置くときに実際のパスへ置き換える。

## やること

1. **疑似入力の道具で全種別の見本を作る。** `prepare-verification-input.sh` を使う
2. **関連資料へのパスの記入欄を、実際のパスへ置き換える。** 上記 2 件
3. **見本を `generation-engine/samples/docs/design/` の下へ置く。** 既にある画面・共通と同じ並びにする
4. **見本のずれ検知の台帳を更新する。** `check-derived-drift.sh record` を同じ変更で行う
   （`.claude/rules/always/portal/template-sample-sync/rule.md` の規約 5）
5. **様式と見本の節構成が一致することを確かめる検査を作る。** 42 組すべてを対象にする

## 完了の判定

1. `generation-engine/samples/docs/design/` の下に、42 の様式それぞれに対応する見本がある
2. 見本に未置換の記入欄が残っていない
3. 様式と見本の節構成が一致する（新設する検査が終了コード 0 を返す）
4. `bash generation-engine/scripts/tests/check-evidence-column-removed.sh` が終了コード 0 を返す
5. `bash generation-engine/scripts/tests/check-derived-drift-ledger.sh` が終了コード 0 を返す
6. `bash .claude/rules/always/tasks/instruction-format/check-instruction-format.sh` が不合格 0 件

## 触らない範囲

- 様式そのものの中身。見本を置く作業であり、様式は変えない
- 既にある画面 6 件・共通 13 件の見本。増やす分だけを扱う
- 一覧の置き場の食い違い（`docs/tasks/design/` の別の指示書が扱う）

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 見本を何件ずつ置くか | 種別ごとに 1 単位ぶん。様式との突き合わせに要るのは 1 件で足りる | 複数の単位が並んだときの見え方を確かめたくなったとき |
| 疑似入力の中身をそのまま使うか | そのまま使う。疑似入力は様式の記入欄を検証用の固定値で埋めたものであり、様式どおりの形をしている | 見本を読み物としても使う方針へ変わったとき |
| 未置換 2 件をどう埋めるか | 同じ単位の中の実際の相対パスを書く | 単位をまたぐ参照が必要になったとき |
| 節構成の検査を新設するか既存へ足すか | 新設する。既存の `check-design-doc-section-consistency.sh` は詳細設計書 7 種別だけを対象とし、基本設計書・テスト設計書・共通文書を見ない | 既存の対象範囲を広げるほうが総量として小さいと分かったとき |

## 他の指示書との関係

`docs/tasks/design/一覧の置き場が三者三様になっている問題を直す指示書.md` は
一覧のページの置き場を扱う。本指示書は設計書の見本を扱う。対象が異なる。

## この指示書の位置づけ

様式と生成物を突き合わせる材料を揃える作業である。
材料が無い限り、様式を直しても届いたかどうかを確かめられない。

### 判断の記録

| 何を決めたか | 選んだもの | 選んだ理由 | 覆すと何が変わるか |
|---|---|---|---|
| 起票の前に作れるか試すか | 試してから起こす | 起票だけでは「本当に作れるのか」が分からないまま残る。実際に API で 1 種別作り、節構成が一致することを確かめてから書いた | 試さずに起こすと、道具が足りない場合に指示書が実行不能なまま残る |
| 見本を置く範囲 | 見本が無い 23 様式 | 既にある 19 件は動いている。増やす分だけを扱えば、変更の範囲が小さい | 全 42 件を作り直すと、既存の見本が持つ実際の内容が失われる |
| 判定1を目視のままにするか機械へ変えるか | 機械へ変える | 目視にした理由（対応表が無い）は、判定3の検査が種別ごとの対応表を持つ形で作られたことで解消した。実測で「見本なし 0 件」を返す | 目視のまま残すと、この指示書は恒久的に片付かない。目視の行が1件でもあると done/ へ移せないため |
