# 納品物の一覧を調査の直後に提示する段を設ける指示書

**状態**: 着手できる
**優先度**: 最高
**前提**: なし
**元の指摘**: 1-252

## この指示書は何か

統括スキルの第2段（アーキテクチャ調査）の直後に、対象がどういう性質のもので、納品物が何件になるかをユーザーへ示し、承認を得る段を設ける。いまは全工程を終えるまで示されない。

## なぜ必要か

統括スキルのフローは7段である（準備・アーキテクチャ調査・目録・共通書き起こしとポータル・静的単位の処理・動的な往復検証・判定と確定）。実測すると、この7段の本文に納品物の一覧という語も、それを作る生成器の名前も1件も現れない。生成器を呼ぶ記述は納品完了の条件（判定の手順）の1箇所だけであり、全工程を終えた後に初めて一覧が作られる。あわせて、対象種別の確定はユーザーの承認を経ない。

第2段の完了は内部の状態の確認だけであり、調査確定という状態と調査書のパスを確かめるにとどまる。第3段は実在しない種別を対象外の記録へ書くと定めるだけで、提示も承認も無い。

ある対象プロジェクトで次の実害が出た。第1に、対象種別の宣言が実態と食い違ったまま最後まで進んだ。対象外の記録は実在する種別を1つだけ挙げ、対象外を1つだけ挙げる。残る4種別は「ある」とも「対象外」とも宣言されていない。それでいながら、宣言されていない種別のうち1つには設計書が9単位・36ファイル存在する。宣言と実態の双方向の一致を見る検査は8件不合格であった。

第2に、全工程を終えてから一覧を作ったところ、60件のうち4件が「まだできていない」と出た。4件はいずれも画面に関わる成果物であり、この対象では画面を対象外と宣言している。採点の側が対象範囲を反映しきれていない。

第3に、完成の判定は「まだできていない」が0件であることを求める。上の2件が解けるまで判定が通らない。いずれも工程の最後に初めて判明した。機械的に決めた範囲が誤っていた場合、その間の作業がすべて無駄になる構造である。

実測で裏を取った事実は次のとおり。

```
統括スキル（.claude/skills/orchestrating-ai-development-setup/SKILL.md）の段
  Phase 1: 準備 / Phase 2: アーキテクチャ調査 / Phase 3: 目録
  Phase 4: 共通書き起こしとポータル / Phase 5: 静的ユニット処理
  Phase 6: 動的往復検証 / Phase 7: 判定と確定

同ファイル内の「納品物一覧」「deliverable-inventory」の出現   0件
生成器を呼ぶ記述の所在                                    docs/design/納品完了の条件.md（1箇所）
Phase 2 の完了条件                                       内部の状態の確認のみ
```

### 会話を1回に絞る（追記）

利用者から次の方針が示された。最初の起動以降は、調査の直後に方針を決める1回だけとする。

現状は準備の段に5箇所、判定と確定の段に1箇所の会話がある。準備の5箇所はいずれも起動引数の
不足を補うものである。判定と確定の1箇所は完了の承認である。

無人で動かす仕組み（headless）は既にあるが、これは会話を完全に無くす。求められているのは
調査後の1回を残す形であり、無人化とは異なる。

## やること

利用者の判断により、承認の得方・段の位置・提示の粒度は既に確定している。次の5点はこの指示書の前提とし、以降の手順はこれに従う。

- 承認をどう得るか: 選択肢を示して選ばせる。「この範囲で進む」「範囲を変える」等の選択肢を提示し、選んでもらう。選んだ内容を記録に残す
- 承認が得られなかったとき: 対象範囲を手で指定してもらう。どの種別を対象にするかを直接指定してもらい、その場で対象外の記録へ書く。指定の根拠も記録に残す
- 段をどこへ置くか: 第2段（アーキテクチャ調査）の直後
- 途中で範囲が変わったとき: 再度承認を得る。範囲が変わった時点で止まり、変更後の範囲を示して改めて承認を得る
- 提示の粒度: 2つを示す。1つは対象の性質（実在と判定した種別・対象外とした種別とその理由）、もう1つは納品物の件数（出力する件数・対象外の件数を種別ごとに）

これを反映する手順は次のとおり。

1. `.claude/skills/orchestrating-ai-development-setup/SKILL.md` の Phase 2 の最後（Step 2-6 の後、Phase 3 の前）に、新しい Step を追加する。この Step は次を行う。
   - `generation-engine/scripts/build-deliverable-inventory.sh` を呼ぶ。引数は既存の docs-inventory 呼び出しと同じ形（`<output_root> <html出力先> <md出力先>`）とする。この時点の暫定的な一覧を作る。新しい生成器は作らない
   - 一覧から、対象の性質（実在と判定した種別・対象外とした種別とその理由）と納品物の件数（種別ごとの出力件数・対象外件数）を取り出してユーザーへ提示する
   - この段では「まだできていない」を欠陥として扱わず、これから作る予定として提示する
   - 選択肢（「この範囲で進む」「範囲を変える」）を示して選ばせる
   - 「この範囲で進む」が選ばれたら、提示した範囲を確定する
   - 「範囲を変える」が選ばれたら、種別の名前を並べて選ばせる形で対象範囲を手で指定してもらい、その場で excluded-kinds.json（対象外の記録）へ書く
   - 選んだ内容（選択肢・指定内容・日時）を excluded-kinds.json と同じファイルへ、承認の経緯として追記する
2. Step 3-2（対象外種別と派生一覧を確定する）の本文を、上記で承認された対象種別を正として読み込む記述へ改める。承認を経ずに機械的な判定だけで対象種別を確定させる記述を残さない
3. Phase 7（判定と確定）の判定に、承認した時点の一覧と完成時の一覧を突き合わせる工程を追加する。承認した範囲がそのまま満たされたかを見る
4. 途中で対象範囲が変わった場合（例えば Phase 5 以降で新しい種別の実在が判明した場合）、その時点で提示・承認の段を再度実行する記述を置く。変わった旨を記録するだけで済ませない
5. `docs/scripts/check-inventory-approval-step.sh` を新設する。完了の判定のうち縦棒（`|`）を含む式は指示書の表へ直接書けないため、この指示書を実行する担当が本スクリプトへ切り出す
6. **準備の段の5箇所の会話を無くす。** 起動時に必要な引数をすべて受け取る形へ改める。
   不足があれば推測せず中断し、何が足りないかを示して終える。対話で補わない
7. **判定と確定の段の承認を無くす。** 承認時の一覧と完成時の一覧を突き合わせた結果を
   報告するだけとし、完了としてよいかを尋ねない。差があれば差を示して終える
8. **無人で動かす仕組み（headless）との関係を定める。** headless が true のときは
   調査後の1回も発行しない。false のときは調査後の1回だけを発行する。準備と判定の
   会話は true・false のどちらでも発行しない

## 完了の判定

1. `.claude/skills/orchestrating-ai-development-setup/SKILL.md` の Phase 2 の最後に新しい Step があり、`build-deliverable-inventory.sh` の呼び出しと、承認の選択肢（「この範囲で進む」「範囲を変える」）の両方を本文に含むこと。`bash docs/scripts/check-inventory-approval-step.sh --step-present` が終了コード0を返す
2. 新しい Step が Phase 3 より前（global_step の番号が Phase 3 の先頭より若い）に置かれていること。`bash docs/scripts/check-inventory-approval-step.sh --step-order` が終了コード0を返す
3. Step 3-2 の本文が、承認された対象種別を正として読む記述に変わっており、承認を経ずに機械判定だけで確定する記述が残っていないこと。`bash docs/scripts/check-inventory-approval-step.sh --step3-2-reads-approval` が終了コード0を返す
4. Phase 7 の判定に、承認時点の一覧と完成時の一覧を突き合わせる記述があること。`bash docs/scripts/check-inventory-approval-step.sh --final-crosscheck` が終了コード0を返す
5. 工程の途中の状態を模した試験用の入力（一部の種別だけが実在し、残りが「まだできていない」状態の入力）で新しい Step を実行し、「まだできていない」があっても停止せず先へ進むこと。`bash docs/scripts/check-inventory-approval-step.sh --self-test` が終了コード0を返す
6. 途中で対象範囲が変わった場合に、再度承認を得る記述があること（記録するだけの記述になっていないこと）。`bash docs/scripts/check-inventory-approval-step.sh --scope-change-reapproval` が終了コード0を返す
7. 統括スキルの準備の段に、利用者へ尋ねる記述が0件であること。
8. 統括スキルの判定と確定の段に、完了の承認を求める記述が0件であること。
9. 統括スキルで利用者へ尋ねる箇所が、調査の直後の1箇所だけであること。
10. headless が true のとき、その1箇所も発行しない形になっていること。

## 触らない範囲

- 既存の生成器（`build-deliverable-inventory.sh`）の判定の中身は変えない。呼ぶ時期を変えるだけ
- 新しい一覧の生成器を作らない
- 既に生成済みの対象プロジェクトの成果物の是正は行わない
- excluded-kinds.json のスキーマそのものは作り替えない。承認の経緯を追記するだけにする
- 無人で動かす仕組み（headless）そのものを廃止しない。会話の発行条件を変えるだけ
- 起動時に渡す引数の種類を増やさない。既にある引数で足りる形にする

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 選択肢の文言 | 「この範囲で進む」「範囲を変える」の2つから始める。3つ目が要ると分かった時点で足す | 2つでは足りない場面が実際に出たとき |
| 手で指定してもらう形式 | 種別の名前を並べて選ばせる。自由記述にしない | 種別の一覧に無いものを指定する必要が出たとき |
| 記録の置き場 | 対象外の記録と同じファイルへ、承認の日時と選んだ内容を追記する | 対象外の記録が承認の経緯を持つ設計でないと分かったとき |
| 起動引数が足りないときの中断の仕方 | 何が足りないかを一覧で示して終える。1件ずつ尋ねない | 足りない項目が多く、一覧では読み取れないと分かったとき |
| 判定の差を報告する形 | 承認時と完成時の一覧の差を表で示す。差が0なら「差なし」と1行書く | 差の件数が多く、表では読み取れないと分かったとき |
