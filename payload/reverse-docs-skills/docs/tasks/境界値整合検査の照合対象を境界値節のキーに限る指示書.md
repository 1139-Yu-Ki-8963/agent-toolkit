## 1. この指示書は何か

設計書間の整合検査（`check-design-code-consistency.sh`）が持つ、境界値の規則の照合対象を境界値の節のキーに限る指示書である。

## 2. なぜ必要か

設計書間の整合検査の境界値の規則は、単体テスト設計書の中で1列目の見出しが「キー」である表のすべての値を集める。同じ設計単位の詳細設計書のキーの表に無ければ不合格にする。ある対象プロジェクトの納品物へ当てると、1782件の不合格が出た。単体テスト設計書のキーの総数は1787件であり、99.7%が不合格になる。

節ごとの内訳は、テストケース一覧723件・テスト観点676件・異常系179件・要確認事項153件・境界値51件である。検査自身の説明は、単体テスト設計書の境界値キーと詳細設計書の判定表キーを対象と述べる。ところが境界値の節から来たものは51件であり、全体の2.9%にすぎない。

さらに様式の側が、テストケース一覧のキーとテスト観点のキーを別の名前空間として定めている。接続窓口の単体テスト設計書の様式のテストケース一覧の節は、対応する観点のキーという列を持つ。この列は、ケースのキーと観点のキーが別であることを前提にしている。様式どおりに書くと必ず不合格になる。

## 3. やること

1. `design-code-consistency.json`の`boundaryValueConsistency`へ、対象の節見出しを示すキーを追加する。値は「§6 境界値」とする。
2. `check-design-code-consistency.sh`の境界値キー抽出処理を、単体テスト設計書側の抽出範囲を手順1のキーが示す見出しから次の`## `見出しまでの区間に限るよう変更する。対象の節見出しは、検査スクリプトの中に書かず、定義ファイルから読む。
3. 詳細設計書側の判定表キーの抽出範囲は変更しない。
4. 自己テストへ、テストケース一覧・テスト観点・異常系・要確認事項の節にあるキーが対象から外れることを確かめるケースを追加する。
5. 自己テストへ、境界値のキーが判定表に無い入力では従来どおり不合格になるケースが引き続き通ることを確認する。
6. 自己テストへ、テストケース一覧のキーと境界値のキーが別の名前空間にある様式どおりの単体テスト設計書が、不合格にならないケースを追加する。

## 4. 完了の判定

1. 検査本体の自己テストが通る
2. 見本の出力を検査すると不合格が0件になる

## 5. 触らない範囲

- 件数の規則（`countConsistency`）の判定ロジックそのもの
- 詳細設計書側の判定表キーの抽出範囲そのもの
- 単体テスト設計書の様式（`delivery-payload/templates/リバース検証/`配下）のテストケース一覧・テスト観点の列構成

## 6. 決めていないこと

## 8. この指示書の位置づけ

`check-design-code-consistency.sh`が持つ2つの規則のうち、境界値の規則だけを対象にする指示書である。不合格の原因（照合範囲の広さと様式の名前空間の違い）は台帳の実測で特定済みのため、設計から始める必要はなく、そのまま実装に着手できる。優先度を最高としたのは、様式どおりに書くと必ず不合格になり、検査そのものが機能していないためである。
