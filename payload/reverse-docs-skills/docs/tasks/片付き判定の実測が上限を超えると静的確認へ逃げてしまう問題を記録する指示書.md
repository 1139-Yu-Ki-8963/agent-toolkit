# 片付き判定の実測が上限を超えると静的確認へ逃げてしまう問題を記録する指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

片付き判定（`docs/scripts/judge-task-done.sh`）の「確かめる手段」欄は、実測のコマンドを書く前提だが、実測が判定器の1コマンドあたりの上限（既定120秒）を超える場合、実測の代わりに常に成功する静的な確認（文字列の存在確認等）へ差し替えられることがある。この差し替えは完了の判定そのものを満たしたことにはならないが、外形上は「確かめる手段が終了コード0を返す」ため、片付き判定は区別できない。

## なぜ必要か

「高速化のあとに目視へ退いた判定を戻す指示書」の前提である「自己テストの所要時間が規約の件数に追いつかれる問題を片付ける指示書」（`docs/tasks/done/`）の判定1は、完了の判定で「所要時間が宣言値の7割以下であること」（210秒以下）を求めている。実測は126秒・153秒・145秒・141秒であり210秒以下を満たすが、判定器の1コマンドあたりの上限120秒を超える。記録には次の差し替え理由が明記されている。

> 判定器の1コマンドあたりの上限120秒を超えるため、確かめる手段を所要時間の計測から、1件だけを作り直す呼び方の実在確認（`grep -q 'restrict_ckey'`）へ差し替えた

この差し替えにより、確かめる手段は常に成功する文字列存在確認になり、実際の所要時間が210秒を超えて再び遅くなっても、片付き判定はそれを検知できない。

もう1つ、この指示書自身が`docs/tasks/done/`へ移った時点で、片付き判定の走査対象から構造的に外れることも判明した。`docs/scripts/judge-task-done.sh`が走査するglob（`$TASKS_DIR/*.md`）は`done/`を含まないため、一度移った指示書は二度と自動で再判定されない。実際に手動で`--only`を指定して`done/`配下のファイルへかけ直すと、サンドボックスの有無を問わず「判定不能」を返し、現在の仕組みでは自動の再確認が機能していない（原因未特定）。

**この問題には既存の別枠機構がある。** `docs/tasks/走っていない検査を集約へ載せる指示書.md`（main コミット`c6c2738d`）が記録するとおり、`generation-engine/scripts/verification/run-layer-machine-checks.sh`の`declared_long_running_known()`という関数が、上限を超えても「打ち切り」ではなく「宣言済み長時間」として扱う対象を持つ。登録は相対パスを1行足すだけで、現在は`generation-engine/scripts/build-portal.sh`・`generation-engine/scripts/unit-list/rebuild-screen-derived-pages.sh`の2本が登録されている。登録できるのは「単体で実行すれば完走するが、時間が上限を超えるもの」に限り、**落ちているものを登録してはならない**（落ちている事実が見えなくなるため）。この指示書が例示した`grep -q 'restrict_ckey'`への差し替えは、この既存の仕組みが知られていなかったために生じたと考えられる。

## やること

1. `docs/tasks/done/`配下の「確かめる手段」欄のうち、判定文が実測（所要時間・回数等）を求めているにもかかわらず、静的な確認（文字列の存在確認・ファイルの実在確認など、値を測らない確認）へ差し替えられている行を洗い出す。「確かめた内容」欄に「上限を超えるため差し替えた」旨の記述があるかを目印に探す
2. 洗い出した各行について、対象のコマンドが「単体で実行すれば完走するが、時間が上限を超えるもの」に当たるかを確認する。当たる場合は`generation-engine/scripts/verification/run-layer-machine-checks.sh`の`declared_long_running_known()`へ相対パスを1行追加し、「確かめる手段」を静的確認から実測のコマンドへ戻す。落ちているものは登録してはならない
3. 登録しても解決しない場合（対象コマンドが単体実行でも完走しない・`run-layer-machine-checks.sh`の走査対象外である等）に限り、「決めていないこと」の既定に従い明示欄（注記）方式を使う
4. `docs/scripts/judge-task-done.sh`が`done/`配下を走査対象に含めていないことをコードで確認し、その事実を本指示書の対応の記録へ残す
5. 手動で`done/`配下のファイルを`--only`で判定すると「判定不能」を返す件の原因を調査する。原因を特定できた場合は直す。特定できない場合は別指示書として切り出す

## 完了の判定

1. 洗い出した対象行すべてに、静的確認である旨の注記が「確かめた内容」欄に存在する
2. `docs/scripts/judge-task-done.sh`が`done/`を走査しないことの確認結果が本指示書に記録されている
3. `done/`配下のファイルを手動で`--only`判定した際の「判定不能」の原因調査結果（特定できた場合は修正結果、できなかった場合は切り出した指示書名）が記録されている

## 触らない範囲

- `docs/scripts/judge-task-done.sh`の判定ロジック自体（本指示書は記録上の注記追加までを対象とし、判定器の改修は別指示書に委ねる。今日直したばかりの22件の自己テストと干渉するため）
- 差し替え済みのコマンド自体（`grep -q 'restrict_ckey'`等）。有効な確認ではあるため削除しない。注記を添えるだけ

## この指示書の位置づけ

片付き判定の仕組み自体の穴（確かめる手段に静的確認を書ける設計上の隙、およびdone/移動後に再判定されない構造）を記録する指示書であり、個別の指示書1件の対応ではないため独立させた。
