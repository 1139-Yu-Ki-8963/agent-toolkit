# 接続窓口の詳細設計書の前付けが定義と食い違う問題を直す指示書

**状態**: 着手できる
**優先度**: 最高
**前提**: なし
**元の指摘**: 1-257

## 1. この指示書は何か

接続窓口（API）の詳細設計書について、定義・テンプレート・生成スキル・生成物の前付けを同じ鍵集合へそろえる。
あわせて、複数ファイルにまたがる実装の所在を `source_ref` から機械的に解決できる契約と、全種別へ共通して働く前付け検査を設ける。

## 2. なぜ必要か

台帳1-257の実測では、対象プロジェクトのAPI詳細設計書50件が、定義の7鍵ではなく別の8鍵を持っていた。
定義のうち `api_id`・`feature_key`・`source_ref`・`unit_kind` が欠落し、禁止された `title`・`login_required`・`category`・`auth`・`note` が残っていた。
この状態では実装の所在を機械的に解決できず、49件で13節ずつ、合計637件の節検査が不合格になる。

現行リポジトリのAPI詳細設計書テンプレートと生成スキルには7鍵が記載され、`scaffold-design-unit.sh --verify` は生成物とテンプレートの鍵集合を比較する。
しかし、定義・テンプレート・生成スキル・生成物の4者を全種別横断で突き合わせ、欠落と余剰の両方を独立して検出する回帰経路が無い。

## 3. やること

1. `delivery-payload/references/規約定義と派生生成の設計.md`、`delivery-payload/templates/リバース検証/API/API詳細設計書.md`、`.claude/skills/generating-api-detail-design-for-reverse-docs/SKILL.md` のAPI詳細設計書の前付け契約を突き合わせる。定義の鍵集合は `api_key`・`api_id`・`method`・`path`・`feature_key`・`source_ref`・`unit_kind` の7鍵とする。`title`・`login_required`・`category`・`auth`・`note` は生成物へ残さない。
2. `source_ref` は現行どおり、リポジトリルート相対の単一パスとする。
   複数ファイルへまたがる場合は、HTTP要求を最初に受けるルーター・コントローラー・ハンドラーの順で代表ファイルを1件選ぶ。
   同じ優先順位の候補が複数ある場合は、マニフェストの `sourceFile` と一致するものを選ぶ。
   該当実装が0件なら鍵を残して値を空欄にする。
   未検出の事実は、`output-layout.json` の `unitConfirmationLedgerFile` が定める単位直下の `要確認事項台帳.json` へ記録し、`confirmation-survey` の入力に渡す。
   絶対パスと行番号は入れない。
3. `source_ref` を読む `delivery-payload/references/doc-extraction.json` と `generation-engine/scripts/portal-input/build-manifests-from-docs.sh` を確認する。
   前付けの単一パスが一覧マニフェストの `sourceFile` へ文字列として渡る既存契約を維持する。
   代表ファイルを起点に原本の呼び出し関係をたどり、複数モジュールの関数契約を本文へ書く手順を生成スキルへ明記する。
4. `delivery-payload/references/detail-design-frontmatter-keys.json` を新設し、詳細設計書の種別ごとの鍵集合を持つ機械可読の定義とする。
   `delivery-payload/references/規約定義と派生生成の設計.md` は、このJSONを参照して各鍵の値の由来を説明する。
   定義文書とJSONが食い違う場合はJSONを検査の期待値とし、食い違い自体も不合格として報告する。
5. `generation-engine/scripts/scaffold-design-unit.sh --verify` の前付け比較は、前項のJSONを読んで検証する。
   欠落鍵と余剰鍵を別々に列挙し、どちらかが1件以上なら終了コードを0以外にする。
6. `generation-engine/scripts/tests/check-detail-design-frontmatter-keys.sh` を新設する。
   APIについて7鍵の正常入力、欠落鍵を持つ入力、禁止された余剰鍵を持つ入力を用意する。
   API以外の詳細設計書についても、JSONの鍵集合とテンプレート・生成物を同じ検査へ通す。
7. API詳細設計書の生成スキルの機械検査から、前項の検査または同じ判定を持つ共通検査を呼ぶ。
   検査が不合格なら生成完了として扱わない。

## 4. 完了の判定

1. API詳細設計書のテンプレートが定義の7鍵だけを持ち、禁止された5鍵を持たない。確かめる手段: `bash generation-engine/scripts/tests/check-detail-design-frontmatter-keys.sh --check-api-template`
2. 生成スキルと定義文書に、複数ファイル・1ファイル・実装0件の各場合の `source_ref` の値の決め方が明記されている。確かめる手段: `bash generation-engine/scripts/tests/check-detail-design-frontmatter-keys.sh --check-source-ref-contract`
3. 種別ごとの定義済み鍵集合と実物を突き合わせる検査が実在し、通常実行が終了コード0を返す。確かめる手段: `bash generation-engine/scripts/tests/check-detail-design-frontmatter-keys.sh`
4. 欠落鍵を持つ入力と余剰鍵を持つ入力が、どちらも不合格になる。確かめる手段: `bash generation-engine/scripts/tests/check-detail-design-frontmatter-keys.sh --self-test`
5. 定義の7鍵をそろえたAPIの試験入力が合格する。確かめる手段: `bash generation-engine/scripts/tests/check-detail-design-frontmatter-keys.sh --self-test`
6. API以外の詳細設計書も、種別ごとの鍵集合との欠落・余剰の検査を通る。確かめる手段: `bash generation-engine/scripts/tests/check-detail-design-frontmatter-keys.sh --check-all-kinds`

## 5. 触らない範囲

- 既に生成済みの対象プロジェクトの50件を再生成しない
- 実装が見つからなかった接続窓口を個別に調査しない
- 詳細設計書本文の13節の内容や並びを変更しない
- APIの一覧マニフェストの項目を本件と無関係に増減しない
- `source_ref` 以外の前付け値の意味を変更しない

## 6. 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 複数ファイルにまたがる `source_ref` の表現 | 単一パスを維持し、HTTP要求を最初に受ける代表ファイルを選ぶ | 前付けと一覧マニフェストの両方で、パスと関数の対応を持つ構造化配列の契約が先に導入された場合 |
| 実装が0件のときの値 | 鍵を空欄で残し、単位直下の `要確認事項台帳.json` へ未検出を記録する | 空欄を拒否するスキーマへ変わった場合は、同じ台帳への記録を保ったまま許容値を定義する |
| 全種別の鍵集合の定義 | `delivery-payload/references/detail-design-frontmatter-keys.json` を新設して使う | 既存の機械可読な定義が全種別を欠落なく覆うと実証できた場合は、新設せず既存定義を使う |

## 7. 他の指示書との関係

台帳1-254は、設計書が実在するのに一覧の元データが0件でも正常終了する問題を扱う。
本指示書は、その前段にある前付けの鍵集合と `source_ref` の表現を扱うため、1-254の件数不一致検査を弱めずに両方を通す必要がある。
前付け以外の13節の欠落は本指示書の範囲外であり、鍵集合を直したあとも残る本文不足は別の指摘として扱う。

## 8. この指示書の位置づけ

定義と生成物の食い違いを、APIだけの手修正ではなく全種別共通の検査で再発防止する単位に切った。
生成済み成果物の再生成や個別APIの実装探索を含めると、契約の是正と対象プロジェクト固有の修復が混ざるため含めない。
