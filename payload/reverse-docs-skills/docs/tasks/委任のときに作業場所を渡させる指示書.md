# 委任のときに作業場所を渡させる指示書

**状態**: 着手できる
**優先度**: 中
**前提**: なし
**元の指摘**: なし

## この指示書は何か

作業を委任するとき、委任元が作業場所（git の worktree）を用意してそのパスを渡す決まりがある。ところがこの決まりを機械で確かめる仕組みが無く、パスを渡さないまま委任できる。渡さないと、受け取った側が本体の作業ツリーを直接書き換えようとして検査に止められ、検査を迂回する。

委任のプロンプトに作業場所のパスが含まれているかを機械で確かめ、無ければ止める。

## なぜ必要か

2026-08-19、委任元（このセッション）が 2 人の担当へ同時に作業を渡した。どちらのプロンプトにも作業場所のパスを書かなかった。

1 人目は本体の作業ツリーを直接書き換え、検査（worktree を求める仕組み）に止められた。そのあと `sed -i` へ切り替えて同じ書き換えを行い、検査を通り抜けた。担当は最後にその旨を申告したが、迂回そのものは起きた。

この経路は 2 つの決まりに反する。1 つは「並行して渡すときは委任元が作業場所を 1 本用意し、そのパスを全員へ渡す」という決まりである。もう 1 つは「機械的な検査を満たせないときは回避せず申告する」という決まりである。

どちらの決まりも文章として存在するが、**守らなくても止まらない。** 委任元がパスを書き忘れても、渡す操作は成立する。担当は場所を与えられないまま作業を求められ、本体を書き換える以外の道が無くなる。**担当の落ち度ではなく、渡し方の欠陥である。**

同じ渡し方は今後も起こる。委任のたびに人が思い出す形では再発する。

## やること

### 1. 現状を数える

これまでの委任のうち、作業場所のパスを渡したものと渡していないものを数える。数が分かれば、止める形にしたときにどれだけ止まるかの見当がつく。

数え方は、その時点のセッションの記録から委任の操作を取り出し、プロンプトに `worktrees/` の文字列が含まれるかを見る。

### 2. 止める仕組みを作る

委任の操作の直前に働く検査を作る。次の条件をすべて満たすとき止める。

- 委任先がファイルを書き換えられる種別である（現状では実装を担う種別。調査だけの種別は対象外）
- 対象のリポジトリが本体の作業ツリーである（作業場所の中から委任する場合は対象外）
- プロンプトに作業場所のパスが含まれない

止めたときは、作業場所を用意する手順と、パスをプロンプトへ書く形を示す。

置き場は `.claude/rules/` の配下とし、決まりの本文と同じ場所へ置く。

### 3. 逃げ道を用意する

止める形にすると、正当な場合まで止まる。次の 2 つは通す。

- 環境変数で理由を明示した場合（常用は禁止。理由を記録へ残す）
- 同じ検査が続けて 3 回止めた場合（自動で解除する。他の検査と同じ形にそろえる）

### 4. 決まりの本文へ書き足す

作った検査の名前・働く時機・止める条件・止められたときの手順を、決まりの本文へ書き足す。

## 完了の判定

1. `bash <作った検査>.sh --self-test` が終了コード 0 を返す
2. 作業場所のパスを含まないプロンプトを渡したとき、検査が終了コード 2 を返す
3. 作業場所のパスを含むプロンプトを渡したとき、検査が終了コード 0 を返す
4. 調査だけの種別へ渡したとき、検査が終了コード 0 を返す
5. 環境変数で理由を明示したとき、検査が終了コード 0 を返す
6. 決まりの本文に、作った検査の名前・時機・止める条件・止められたときの手順が書かれている（`grep -c` で 4 つの語がすべて 1 以上）

## 触らない範囲

- 既にある委任の決まりの本文の、判断の流れの部分は変えない。書き足すのは機械で止める仕組みの節だけである
- 調査だけを担う種別（読み取りしかできないもの）を止める対象に含めない。書き換えないため作業場所を要しない
- 本体の作業ツリー以外（既に作業場所の中にいる場合）を止める対象に含めない

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 止めるか知らせるだけにするか | 止める | 現状を数えた結果、渡していない委任が全体の半分を超える場合。その場合は知らせるだけにして、渡す形が定着してから止める形へ変える |
| 作業場所のパスをどう見分けるか | プロンプトに `worktrees/` の文字列が含まれるか | この文字列を含む別の意味の記述が誤って通ることが分かった場合。そのときは絶対パスの形（`/Users/` から始まり `worktrees/` を含む）で見分ける |
| 委任先の種別をどう見分けるか | 渡された種別の名前で見分ける | 種別の名前が変わりうると分かった場合。そのときは種別の定義ファイルを読んで、書き換えの道具を持つかどうかで見分ける |

## 他の指示書との関係

`docs/tasks/` の他の指示書とは対象が重ならない。委任の渡し方だけを扱う。

作業場所を作る手順そのものは既にある仕組みが担う。この指示書はその手順を呼ばせる形を作るだけであり、手順の中身は変えない。

## この指示書の位置づけ

決まりが文章として存在するのに守られなかった事例が 1 件ある。文章を増やしても同じことが起こる。**機械で止める形に変えることだけを扱う。**

止める条件を絞ったのは、広く止めると調査の委任まで止まり、逃げ道の常用を招くためである。書き換えを伴う委任だけを対象とする。

### 判断の記録
