# 規約とフローの対応ページが対象プロジェクトの実態を反映しない配線漏れを直す指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: 1-62

## この指示書は何か

`generation-engine/scripts/rules/build-rule-flow-map.sh`は`--target-root <対象リポジトリのルート>`を指定できる。指定すると、対象プロジェクト側の`docs/rules/<親key>/<子key>/rule.md`の実在を読む。実体の無い規約は索引へ載せない。この機能は既に持つ。ところが、このスクリプトを`--target-root`付きで呼ぶ箇所が配布物のどこにも無い。この指示書は、その呼び出し箇所を配布物へ追加する。

## なぜ必要か

2026-08-25の実測で、`build-rule-flow-map.sh`を呼ぶ箇所が配布物に1件も無いことを確認した。

```
grep -rln "build-rule-flow-map" .claude/skills/
```

上記は0件を返す。`generation-engine/scripts/build-portal.sh`にも呼び出しが無い。`generation-engine/scripts/verification/run-layer-full-pipeline.sh`にも呼び出しが無い。`build-portal.sh`が`generator`フィールドを参照する箇所（487行目付近）は生成物の陳腐化検出の分類にしか使っていない。実際にスクリプトを起動する分岐ではない。

他の`generator`フィールドの値を実測した。規約カテゴリ群では`scaffold-rule-definitions`という別のスクリプト名がある。この名は`.claude/skills/orchestrating-ai-development-setup/SKILL.md`の「規約配布とAI設定資産生成の手順」から絶対パスで実際に呼ばれている。`build-rule-flow-map`はこの手順にも登場しない。

この結果、`--target-root`の機能は存在するが、それを渡す経路が配布物のどこにも配線されていない。対象プロジェクトへ納品した状態でこの索引ページを生成すると、常に`rule-taxonomy.json`の分類定義に載る全27件がそのまま出力される。改善課題1-62が指摘した「27件すべてが載った索引が出力された」は、`build-rule-flow-map.sh`単体のself-testでは検出できない。self-testは`--target-root`を明示的に渡した場合のフィルタが機能することしか確かめておらず、「配布物のどこからも渡されない」という配線の欠落までは確かめないためである。

## やること

1. `.claude/skills/orchestrating-ai-development-setup/SKILL.md`の「規約配布とAI設定資産生成の手順」（現在3手順）へ手順を追加する。追加する手順は`build-rule-flow-map.sh`を`--target-root <target_repo_path>`付きで呼ぶ。既存の手順1（`scaffold-rule-definitions.sh`）が`docs/rules/`を対象プロジェクトへ配置した後に実行する必要がある。`--target-root`はこのディレクトリの実在を読むためである
2. 追加する手順の出力先は`project-portal/foundation/規約とフローの対応.html`とする。`portal-catalog.json`の`rule-flow-map`ブループリントの`dir`と一致させる。`output_dir`起動引数からの組み立て方は「決めていないこと」を参照する
3. `bash generation-engine/scripts/rules/build-rule-flow-map.sh --self-test`を実行する。既存の8ケースを維持したまま通ることを確認する（回帰確認）
4. 追加した手順が実際に対象プロジェクトの`docs/rules/`実体を読むことを、合成フィクスチャ（分類定義より少ない件数の`docs/rules/`を持つ疑似の対象プロジェクト）で確認する

## 完了の判定

1. `.claude/skills/orchestrating-ai-development-setup/SKILL.md`が`build-rule-flow-map`という文字列を含む
2. 同SKILL.md内の`build-rule-flow-map.sh`の呼び出しが`--target-root`という文字列を伴う
3. `bash generation-engine/scripts/rules/build-rule-flow-map.sh --self-test`が終了コード0で完走する
4. 追加した手順が、`docs/rules/`を配置する手順（現行手順1）より後の位置にある

## 触らない範囲

- `build-rule-flow-map.sh`自身の`--target-root`のフィルタ・件数差報告のロジック（実装済みであり本指示書の対象外）
- `rule-taxonomy.json`の分類定義そのもの
- `scaffold-rule-definitions.sh`・`build-derived-rules.sh`など、既存3手順の処理内容

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 出力先パスの組み立て方（`output_dir`からどう`project-portal/foundation/規約とフローの対応.html`を導くか） | 既存の3手順と同じく絶対パスをその場で組み立てる（`<output_dir>/project-portal/foundation/規約とフローの対応.html`）。他のfoundation配下ページと同じ組み立て方に揃える | 既存のfoundation配下ページ（技術スタック等）が別の組み立て方をしている場合はそちらへ揃える |
| 手順を追加する位置（4手順目にするか、既存手順の中へ混ぜるか） | 新たに4手順目として追加する。既存3手順は「順序を逆にすると壊れる」という明示の依存関係を持つため、既存手順の中へ混ぜず独立させる | なし |
| `--catalog`オプションを明示するか省略するか | 省略する（スクリプトの既定値に従う）。既存3手順もcatalogを明示していない | 既定値が対象プロジェクトの構成と揃わない場合に明示指定へ切り替える |

## この指示書の位置づけ
