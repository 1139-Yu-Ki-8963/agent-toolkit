## この指示書は何か

一覧ページの資料リンクを直す。対象は `unit-list-template.html` の `DOC_GROUPS` 定義である。

`DOC_GROUPS` は現在、種別非依存の固定文字列「基本設計書」を使い続けている。種別ごとの文書名から動的にラベルを導く形へ変える。

## なぜ必要か

一覧から役割ごとの資料へ飛ぶリンクのラベルは、ユニットの種別に関わらず固定である。機能一覧ではラベルが「基本設計書」なのに、開く文書の見出しは「機能設計書」になる。文書の名前は種別ごとに異なるため、固定のラベルでは必ず食い違う組み合わせが生じる。

2026-08-25、`unit-list-template.html` を全文読んだ。541〜543行の `DOC_GROUPS` は、次のとおり種別非依存の固定文字列のままだった。

```javascript
{label: '基本', docs: [
  {label: '基本設計書', pathField: 'designDocPath', kind: 'basic'}
]},
```

`design-unit-layout.json` は種別ごとに異なる基本設計フェーズのファイル名を既に持っている（`kinds.feature.phases.basic` は `機能設計書.md` 等）。テンプレート側はこれを一切参照していない。

台帳（`docs/tasks/指摘改善一覧.md`）は本項目を一度「完了」と記録していた。根拠として示していた実測は「テンプレートから `documentLabelFromPath` を抽出し、ラベルを検査する」というものだった。

`grep -rn "documentLabelFromPath" .` でリポジトリ全体を検索したが該当は0件であり、この関数は実装されていない。自己テストも、ラベルの妥当性を検査するものは存在しない（`generation-engine/scripts/tests/` 配下を走査しても無関係な1件のみ）。記録が指す根拠そのものが実在しなかったため、実際の修正は行われていなかった。

## やること

1. `unit-list-template.html` の `unit-manifest` へ、ユニットの種別（`kind` 値）を埋め込む。既にマニフェストが種別を持つ場合はそれを使う（`build-unit-list.sh` が生成する manifest の `kind` フィールドを確認する）
2. `DOC_GROUPS` の「基本」グループのラベルを、種別ごとの文書名から導く関数を実装する（例: `documentLabelFromPath`）。`design-unit-layout.json` の `kinds.<kind>.phases.basic` の値を使うことを推奨する。値はファイル名から拡張子を除いたもの（例: `機能設計書.md` → `機能設計書`）とする
3. 解決方式を選ぶ（「決めていないこと」参照）。候補は2つ。1つは `design-unit-layout.json` をテンプレートのJS内へ直接埋め込む方式。もう1つはビルド時（`build-unit-list.sh`）に種別ごとのラベルを解決してプレースホルダへ渡す方式
4. 「詳細」「結合」「単体」「確認」グループのラベル（詳細設計書・結合テスト仕様書等）についても、同様に種別依存で食い違いが無いかを確認する。食い違いがあれば同じ方式で解決する。無ければ変更しない
5. `unit-list-template.html` またはビルドスクリプトの自己テストへ、機能一覧で「機能設計書」、API一覧で従来どおりの名前になることを検証するケースを追加する

## 完了の判定

1. 機能の一覧でラベルが「機能設計書」になる
2. APIの一覧では従来どおりの名前になる
3. ラベルと開く文書の見出しが一致する
4. `bash generation-engine/scripts/unit-list/build-unit-list.sh --self-test` が終了コード0で終わる
5. 追加した自己テストのケースが4のself-test出力に含まれる（`grep -q '\[PASS\] 1-83'` 等、ケース名は実装時に定める）

## 触らない範囲

- 文書名そのものの見直し（`design-unit-layout.json` の `phases.basic` の値自体を変えること）
- 「基本」以外のグループ構成（詳細・結合・単体・確認の並び）
- `build-unit-list.sh` の1-82（区分列の出力可否判定）の実装
