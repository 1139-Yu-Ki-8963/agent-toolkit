## 1. この指示書は何か

設計書間の整合検査（`check-design-code-consistency.sh`）が持つ、本文の件数と表の実数を突き合わせる規則の抽出位置と走査範囲を絞る指示書である。

## 2. なぜ必要か

設計書間の整合検査の件数の規則は、文書の中の「N個」「N件」「N箇所」を拾い、その直後の表の実データ行数と一致しなければ不合格にする。ある対象プロジェクトの納品物へ当てると、件数の不一致が765件出た。

このうち531件は、拾った数値が表の行の中にある。表の行の中の数値は、直後の表の行数を述べたものではない。残る234件も、本文の中で別の対象を数えた数値であり、直後の表の行数を述べたものではない。765件すべてが偽の検出であり、私たちの側で解消する手立てが無い。数値を消すか、表の直前に数値を書かないようにするしかなく、どちらも文書の質を落とす。

走査の範囲も宣言と食い違う。納品完了の条件を定める文書は、この判定の確認先を対象プロジェクトへ納品した設計書と述べる。ところが実装は、出力先の配下の全ての`md`を走査する。その結果、AI設定資産の定義が212件、ツール別のフォルダの派生物が60件、ポータルの元データが28件、対象に入る。これらは設計書ではない。

## 3. やること

1. 数値を拾う位置を、表の直前にある本文の行に限る。表の行の中とコードの囲みの中を除く。
2. その数値が直後の表を数えたものであることを、表への言及または表の直前の行であることで判定する。
3. 走査の範囲を宣言に合わせ、`docs/design`配下（`boundaryValueConsistency`の走査が既に使う範囲）に限る。
4. 自己テストへ、表の行の中にある数値を拾わないケースと、本文で別の対象を数えた数値を拾わないケースを追加する。
5. 自己テストへ、本文の件数と直後の表の行数が実際に食い違う入力では従来どおり不合格になるケースが引き続き通ることを確認する。

## 4. 完了の判定

1. 検査本体の自己テストが通る
2. 見本の出力を検査すると不合格が0件になる

## 5. 触らない範囲

- 境界値の規則（`boundaryValueConsistency`）の判定ロジックそのもの
- 定数値検査・業務ルール近傍検査を廃止した既存の方針
- `run_check`が単体テスト設計書の探索に使う`docs/design`直下2階層の走査そのもの

## 6. 決めていないこと

| 何を決めるか | 既定（担当者はこの値を選ぶ） | 覆すときの条件 |
|---|---|---|
| 走査範囲を絞る対象パス | `docs/design`とする。境界値の規則が既にこの範囲で走査しており、揃えることで2つの規則が同じ対象を見る | 対象プロジェクトの構成によって設計書の置き場が`docs/design`以外になると判明した場合は、その置き場の定義（`output-layout.json`）から動的に解決する |

## 8. この指示書の位置づけ

`check-design-code-consistency.sh`が持つ2つの規則のうち、件数の規則だけを対象にする指示書である。偽の検出の原因（抽出位置の広さと走査範囲の広さ）は台帳の実測で特定済みのため、設計から始める必要はなく、そのまま実装に着手できる。優先度を高としたのは、この規則が納品完了の条件の一部であり、偽の検出が765件残ると納品完了の判定自体が信頼できなくなるためである。
