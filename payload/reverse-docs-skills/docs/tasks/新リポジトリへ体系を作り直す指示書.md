# 新リポジトリへ体系を作り直す指示書

**状態**: 着手できる
**優先度**: 最高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

新リポジトリは `reverse-design-skills`（`~/Projects/reverse-design-skills`）である。この指示書は、このリポジトリ（reverse-docs-skills）の skill・要件・設計をそこへ作り直す作業の全体計画である。やることの順、各項の完了の判定、決めていないことの既定を 1 か所に持つ。旧リポジトリは配布済みの納品物の不具合修正だけを行い、新しい機能を足さない。

指示書「設計書リバース工程-要件定義から詳細設計までの順序を規約に合わせる指示書」の内容は本指示書に吸収し、同指示書は削除した。順序の是正は新リポジトリの reverse 単位の設計として行う。

## なぜ必要か

2026-09-02 の調査で、この体系には次の事実があった。

- 統括 skill が 43 本の skill 名を直書きしている。機能を 1 つ足すと統括の本文を直す必要がある
- 1 つの納品物を足すとき 8 か所を直す必要があり、どこを直すかが分からない
- 共有部品を 35 ファイルが読み、定義 2 件を 50 と 25 のファイルが読む。定義 JSON 22 件を手で同期している
- ポータルが必須の位置にあり、外せない結合が 5 か所ある
- 統括の本文と参照 3 文書に「要件定義」の語が 0 件で、要件定義書を持たない基本設計書を納品している。基本設計と詳細設計を同時に起動し、単体テスト設計書を詳細設計の段で作っている。これらは設計書の書き方の決まりと単体テスト設計書の決まりに反する
- 詳細設計へ進んでよいかの判定を持たない。基本設計書の完了状態を機械で確かめる検査と、それを繰り返させる hook が無い

放置すると、他の人が機能を足せない体系のまま、規約に反する順序で設計書を納品し続ける。

新リポジトリの要件と設計の決定は `docs/design/AI駆動開発の導入支援の要件.md` と `docs/design/体系の再設計.md`（いずれも新リポジトリ）にある。本指示書はその実施計画である。

## やること

順に進める。各項は新リポジトリで作業し、旧リポジトリは触らない（順 9 を除く）。

### 1. 決定を記録する

`docs/design/体系の再設計.md` の「まだ決めていないこと」から次の論点を「決定事項」へ移す。値は「決めていないこと」の既定に従う。

- リバースの順序: 一覧 → 要件定義 → 共通の基本設計 → 単位の基本設計と単体テスト設計書 → 基本設計の完了判定 → 共通処理の詳細設計 → 単位の詳細設計 → テスト文書 → 確認事項一覧。要件定義の情報源は調査書と一覧の元データに限る
- 機能の粒度: 作業ごとに 1 機能とし、種別は宣言の `kind` を引数で受ける
- 共有部品の置き場: `docs/skills/<単位>-shared/`
- 人に聞く場面: 範囲の承認・確認事項の提示・完了の受け入れの 3 回。詳細設計へ進む判定は機械検査と自己レビューの繰り返しで行い、人に聞かない
- python 専用の事実抽出の経路: 持ち込まない
- 検証の出力先: 対象リポジトリの外に置く

### 2. 設計書の書き方の決まりを版上げする

配る規約「設計書の書き方の決まり」（`document-writing`）に、基本設計書の完了状態を機械で確かめる検査 `check-basic-design-completion.sh` を足す。観点は同規約が定める完了状態そのものとする。外部仕様の確定・業務ルールと例外系・非機能の方式・データ整合とトランザクション境界と排他・不明点なし・単体テスト設計書の実在の 6 つである。検査は各観点の節の実在と記入、未確定の事項が確認事項一覧に登録されていること、単体テスト設計書の節と件数の一致を見る。合格の記録をコミットハッシュ付きで残す。

hook: 詳細設計書の置き場へ書き込むとき、その設計単位に合格の記録が無ければ止める。無人でも同じ。合格まで基本設計の機能へ差し戻して繰り返す。判定役は機械検査の後に文書のレビュー担当が観点表で読む。

規約の `checkable` を `true` にし `checker` に検査を宣言する。派生の機能で hook の登録が生成されることを確かめる。

### 3. 設計書リバース工程の決まりを新設する

配る規約に「設計書リバース工程の決まり」を足す。親は `verification`。規則は 5 つ。要件定義を基本設計より先に置く。基本設計フェーズを閉じてから詳細設計へ進む。単体テスト設計書は基本設計の段で作る。共通処理の詳細設計を単位の詳細設計より先に置く。要件定義 5 文書と共通処理の詳細設計書を納品物に登録する。検査 `check-reverse-design-order.sh` は統括の計画（`plan-setup.sh` の出力）に対して順序を確かめる。

### 4. 合格の集計を main へ取り込む

作業中の `setup-checking-acceptance` を完了させる。柱の表の読み取り、未確認時の終了コード 2、tests の所要時間の記録を含む。

### 5. 対応表を改版する

`docs/design/旧skillの対応表.md` を、束ねた粒度（新 37 本。setup 7・reverse 13・verify 4・portal 7・operate 6）へ改める。

### 6. 配布物の生成機能を作る

`setup-building-delivery`。`docs/skills/<単位>-*/` と `docs/skills/<単位>-shared/` から、単位ごとに `delivery-payload/<単位>/` を作る。tests と samples は含めない。

### 7. reverse 単位を持ち込む

順 1 の順序どおりに、次の順で機能を作る。

- `reverse-shared`（出力配置・分類軸・文字コード検出・様式の描画）
- `reverse-surveying-architecture`
- `reverse-listing-units`
- `reverse-writing-requirements`
- `reverse-writing-common-basic-design`
- `reverse-extracting-facts`
- `reverse-writing-basic-design`
- `reverse-checking-basic-phase`
- `reverse-writing-common-detail-design`
- `reverse-writing-detail-design`
- `reverse-writing-test-docs`
- `reverse-listing-confirmation-items`

1 機能ごとに tests を付け、合格の集計を通す。一覧と確認事項は JSON と Markdown で出し、HTML は portal 単位へ分ける。各機能は旧の見本と同じ入力から同じ出力（HTML を除く）が出ることを tests に含める。

### 8. 残る単位を持ち込む

verify・portal・operate・setup の残りを対応表に従って作る。portal は reverse の出力だけを入力にし、他の単位に portal の名前が無いことを欠落の検査で保つ。

### 9. 公開と旧の廃止

公開先の同期定義に `payload/reverse-design-skills` を登録する。単位が合格するごとに旧リポジトリの対応する skill を廃止する。

## 完了の判定

1. 新リポジトリの `docs/design/体系の再設計.md` の「まだ決めていないこと」に、順序・粒度・共有部品・人に聞く場面・python 経路・検証出力先の論点が残っていない
2. 新リポジトリに `check-basic-design-completion.sh` が実在し、自己テストが終了コード 0 を返す
3. 新リポジトリの規約の配置が生成する `document-writing/rule.md` の front matter で `checkable: true` である
4. 新リポジトリに「設計書リバース工程の決まり」の規約定義と `check-reverse-design-order.sh` が実在し、自己テストが終了コード 0 を返す
5. 新リポジトリで合格の集計 `check-acceptance.sh` が終了コード 0 を返す
6. 対応表の単位ごとの件数の合計が 37 である
7. 新リポジトリに `setup-building-delivery` が実在し、tests が終了コード 0 を返す
8. 合格の集計で reverse 単位が「合格」である
9. 統括の計画 `plan-setup.sh --units setup,reverse` が終了コード 0 を返す
10. 公開先の同期定義に `payload/reverse-design-skills` がある
11. 旧リポジトリの `.claude/skills/` に、対応表で reverse 単位へ移した skill が残っていない

## 触らない範囲

- 旧リポジトリの skill の中身（廃止以外）
- 設計書の書き方の決まりと単体テスト設計書の決まりの本文（完了状態の定義）。検査と hook を足すだけで、定義は変えない
- 旧リポジトリの `docs/tasks/作業課題一覧.md` と `docs/tasks/指摘改善一覧.md`

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 人に聞く場面の数 | 範囲の承認・確認事項の提示・完了の受け入れの 3 回 | 判定役の自己レビューが 3 回繰り返しても合格に至らない場合は、その単位だけ人へ差し戻す |
| python 専用の事実抽出の経路 | 持ち込まない | 対象に画面を持たない python のコードだけのプロジェクトが実際に現れた場合は、`kind` の 1 つとして reverse-extracting-facts に足す |
| 検証の出力先 | 対象リポジトリの外に置く | 対象の版管理の除外で同等の分離ができ、外に置けない環境が実際に現れた場合 |
| tests 1 本の上限（300 秒）を超えるもの | 未確認として合格に数えず、上限は変えない。tests を短くする | 短くできない tests が 3 本を超えた場合は上限を見直す |
| 機能の粒度 | 作業ごとに 1 機能、種別は `kind` の引数 | 種別ごとの分岐が 1 機能の中で 7 種別すべてに別のスクリプトを要する場合は、その作業だけ種別ごとに分ける |
| 共通処理の詳細設計書の置き場 | `docs/design/common/共通処理の詳細設計書.md` | 出力配置の定義の `commonRoot` が別の値なら、その値に従う |
| 基本設計の完了判定の判定役 | 機械検査の後に文書のレビュー担当が観点表で読む | 機械検査だけで観点 6 つを判定できる形が実測で確かめられた場合は判定役を外す |

## この指示書の位置づけ

新リポジトリへの作り直しは、順序の是正・機能の束ね直し・配布の仕組みが互いに依存し、別々の指示書に分けると片方だけが進んでずれる。そのため 1 つの指示書で順を固定する。個々の機能の作り方は新リポジトリの `docs/design/体系の再設計.md` と各機能の SKILL.md が持つ。
