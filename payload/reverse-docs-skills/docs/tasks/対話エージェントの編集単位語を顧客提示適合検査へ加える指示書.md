## 1. この指示書は何か

配布物の顧客提示適合検査（1-233が新設した検査）の検出語彙へ、対話エージェント自身の編集単位を指す語を加える指示書である。対象は`customer-facing-terms.json`と`check-customer-facing-adequacy.sh`である。あわせて、設計書執筆スキル向けの記入規則へ、本文には成果物を作った作業の単位を指す語を書かない旨を明記する。

## 2. なぜ必要か

ある対象プロジェクトの単体テスト設計書・結合テスト設計書について、既存の記載へテストコードとの対応状況を追記する作業をした。追記した説明文に、追記作業をした対話エージェント自身の編集の単位を指す語が複数回混入した。混入したのは、作業をした1回のやり取りの単位を指す語と、追記した文書の下書きファイルを指す語である。これらの語は本文の構成を読者へ説明する目的で書いたものだが、読者である納品先には何を指すか分からなかった。どの作業単位で追記したかという、成果物の外側の事情も露出していた。1-233として起票済みの顧客提示適合検査は、リバース解析の作業工程を指す語を検出対象とするが、対話型のエージェントが自身の編集単位を指す語は対象に含まない。対話型のエージェントが生成スキルを実行する限り、この種の語はどの種別の設計書でも生成時に混入しうる。

## 3. やること

1. `delivery-payload/references/customer-facing-terms.json`の`terms`配列へ、対話エージェントの編集単位を指す語のエントリを追加する。カテゴリは新設し「第7: 対話エージェントの編集単位語」とする。`machine`は`true`（機械で合否を確定できる）とし、`matchType`は`exact`とする
2. 追加する語は、台帳が挙げる2種（1回のやり取りの単位を指す語・下書きファイルを指す語）に対応させ、最低2件登録する。具体的な文字列は「決めていないこと」の既定に従う
3. `terms`配列は既に自由な追加を許す形式のため、検査スクリプト本体へのコード変更は不要である。台帳が求める「同種の語を追加できる形の一覧」は既存のJSON配列の構造がそのまま満たす
4. `customer-facing-terms.json`の`description`フィールドを、新設したカテゴリを含む記述へ更新する。既存の「本文が定める6種類」という記述を「7種類」へ改め、第7の説明を追記する
5. `document-writing.md`の規則テーブルへ、本文に作業の単位を指す語を書かない旨の記入規則を1行追加する。検査列には`check-customer-facing-adequacy.sh`を指す静的解析と書く
6. `check-customer-facing-adequacy.sh`の`self_test`関数へ、新設カテゴリの語を含む入力が不合格になるケースを1件追加する
7. 同スクリプトの既存の自己テストは、実物定義ファイルのカテゴリ数を`6`で固定した回帰ケース（「追加回帰3-6カテゴリすべての語が存在する」）を持つ。カテゴリを7種類へ増やすと、このケースが不合格になる。固定値`6`を`7`へ更新する

## 4. 完了の判定

1. `delivery-payload/references/customer-facing-terms.json`に第7のカテゴリの語が追加されている
2. `check-customer-facing-adequacy.sh`本体の自己テストが通る（新設語を含む入力の不合格化と、カテゴリ数回帰ケースの追随を含む）
3. 第1層の機械検証が拾うラッパー経由でも自己テストが通る
4. `document-writing.md`に本文へ作業単位語を書かない旨の記入規則が追加されている

## 5. 触らない範囲

- 顧客提示適合検査の走査対象（`<project_root>`配下の生成物に限る設計）
- 第2〜第6の既存カテゴリの語彙・machine区分・matchType
- `check-customer-facing-adequacy.sh`本体が持つ既存の判定ロジック（FAIL/REVIEWの分岐そのもの）
- `document-writing.md`の既存の規則行

## 6. 決めていないこと

| 何を決めるか | 既定（担当者はこの値を選ぶ） | 覆すときの条件 |
|---|---|---|
| 新設カテゴリの名称 | 「第7: 対話エージェントの編集単位語」とする（既存カテゴリが第1〜第6を占有しているため次番を採る） | 既存カテゴリの命名規則が数字接頭辞を使わない形へ変わったと判明した場合は、その形に合わせる |
| 追加する語の具体的な文字列 | 「ターン」（1回のやり取りの単位を指す語の代表）と「下書き」（追記した文書の下書きファイルを指す語の代表）の2語を最低限登録する | 実際に混入した語がこれと異なると判明した場合は、その語を優先して登録する。「下書き」が一般的すぎて誤検知（正当な文脈での使用）を招くと判明した場合は「下書きファイル」のようなより具体的な複合語に置き換える |
| matchTypeの値 | `exact`（単語としての完全一致） | 混入形が文末表現・言い回しである場合は`pattern`へ切り替える |

## 8. この指示書の位置づけ

既存の顧客提示適合検査へ語彙を1カテゴリ追加するだけで完結する、単独の小さな指示書である。データ（JSON定義ファイル）の追加が中心で検査スクリプト本体のロジック変更を要さないため、設計から始める必要はなく、そのまま実装に着手できる。優先度を高としたのは、顧客へ提示する文書に内部の作業事情が漏れる事故であり、1-233と同じ「顧客提示適合」という既に高優先度で扱ってきた分類に属するためである。
