## 1. この指示書は何か

文書の文体の検査（`check-document-style-register.sh`）へ除外の仕組みを設け、様式の定義が「常体でよい」と認めた文書を不合格にしないようにする指示書である。除外の対象一覧は検査スクリプトへ直書きせず、様式の定義側に持たせる。

## 2. なぜ必要か

文書の文体の検査（`check-document-style-register.sh`）は、顧客へ提示する文書が敬体で書かれていることを確かめる。判定の根拠は様式の定義（`delivery-payload/references/設計書様式.md` の文体の区分の節）であり、そこには2つの区分が明記されている。読み手が納品先である文書（設計書・単位ごとの資料）は敬体で書き、私たちの作業のための文書（記入規則・執筆規律そのものを定める内部文書・検証の記録）は常体でよいと定める。

ところが検査は後者を除外しない。ある対象プロジェクトで実行したところ165件が不合格になった。顧客へ提示する文書を敬体へ直した後も20件が残り、その全件が常体でよいと定義が認めた文書だった。内訳は3種である。第1に検査できない理由を記録する文書（`design-notes.md`）で24件。第2に納品するスキルの定義（`SKILL.md`）で20件。第3にレビューする担当の定義（`rule-reviewer.md`）で6件である。いずれも納品先の開発を担うものが読む内部の文書であり、顧客へ提示する設計書ではない。

検査に除外の仕組みが無いため、定義が常体を認めた文書を敬体へ直すか、不合格を放置するかの二択になる。前者は定義に反し、後者は検査の判定が使えなくなる。

## 3. やること

1. 検査へ除外の仕組みを設ける。除外の対象は様式の定義が「常体でよい」と述べる文書とし、その一覧を定義の側に持たせる（検査スクリプトへ直書きしない）
2. 実測から少なくとも次の3つを対象一覧に含める。検査できない理由を記録する文書（`design-notes.md`）・納品するスキルの定義（`SKILL.md`）・レビューする担当の定義（`rule-reviewer.md`）
3. テンプレート内の記入規則のコメントが除外されていることを確かめる。実測では本文だけを見ており、この点は既に正しい
4. 除外した件数を実行結果へ報告する
5. 除外の対象が定義の一覧に無い文書を除外していないことを検査自身が確かめる形とする（自己テストのケースとして持つ）
6. `--self-test` を用意し、除外の対象と対象外の両方が期待どおり判定されることを確認する

## 4. 完了の判定

1. `generation-engine/scripts/check-document-style-register.sh --self-test` が終了コード0を返す
2. 除外の対象の一覧が `delivery-payload/references/設計書様式.md` の側にあり、検査スクリプト内に直書きされていない
3. 同スクリプトの自己テストに、常体でよいと定義が認めた文書（`design-notes.md`・`SKILL.md`・`rule-reviewer.md`）を含むケースがある。それらに常体の文末があっても不合格にならない
4. 同スクリプトの自己テストに、顧客へ提示する文書に常体の文末があれば従来どおり不合格になるケースが含まれ、そのケースが合格する
5. 同スクリプトの自己テストの出力が除外した件数を含む
6. 同スクリプトの自己テストに、定義の一覧に無い文書名を除外していないことを確かめるケースが含まれ、そのケースが合格する

## 5. 触らない範囲

- 敬体・常体の判定語彙（`jodoRe`・`keitaiRe`）そのもの
- 顧客提示文書に対する敬体の要求そのもの
- `設計書様式.md` の文体の区分の節が定める2区分（納品先が読む文書は敬体・作業のための文書は常体）の定義内容
- 他の顧客提示適合検査（`check-customer-facing-adequacy.sh` 等）

## 6. 決めていないこと

| 何を決めるか | 既定（担当者はこの値を選ぶ） | 覆すときの条件 |
|---|---|---|
| 除外一覧の置き場 | `delivery-payload/references/設計書様式.md` の文体の区分の節に、除外対象のファイル名パターンを列挙する表を追加する | 既存の宣言駆動の定義ファイル（`design-doc-required-sections.json` 等）と同じJSON形式で持つべきと判明した場合は、新規のJSON定義ファイルへ切り替える |
| 除外の判定単位 | ファイル名（basename）の完全一致またはパターン一致とする（`design-notes.md`・`SKILL.md`・`rule-reviewer.md` の3種） | 同名で別役割のファイルが対象プロジェクトに存在し誤って除外される実例が見つかった場合は、パス全体での判定へ切り替える |
| 除外件数の報告形式 | 既存の他検査（`check-excluded-deliverables.sh` 等）に倣い、実行結果の末尾へ「除外 N 件」の形で出す | 既存の報告形式と衝突する場合は検査独自の形式にする |

## 7. 他の指示書との関係

- `docs/tasks/指摘改善一覧.md` の1-260から本指示書へ追跡できる
- 他の指示書には依存せず、本指示書だけで着手できる
- `check-customer-facing-adequacy.sh`（顧客提示適合の6分類検査）とは対象・判定式が異なり、本指示書は変更しない

## 8. この指示書の位置づけ

既存の文体検査1本に除外の仕組みを追加するだけで完結する、単独の小さな指示書である。除外対象は実測（165件中20件）で既に特定済みのため、設計から始める必要はなく、そのまま実装に着手できる。
