# 入口のページを開発フローで更新し続ける仕組みを作る指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

対象プロジェクトの入口のページ（納品する一覧・図・設計書の索引）は、コードが変わっても自動では更新されない。開発フローに更新の段を設け、古くなったことを機械で検知できるようにする。

## なぜ必要か

### 実測した事実

2026-08-19 時点で次を確かめた。

| 確かめたこと | 結果 |
|---|---|
| 開発フローの手順書が入口のページに触れる回数 | **0 回** |
| コードの現在地と入口のページの表示コミットを比べる検査 | **無い** |
| 何を変えたら何を作り直すかの定義 | **無い** |

開発フローの手順書（`delivery-payload/templates/delivered-skills/dev-flow/SKILL.md`）を「ポータル」「portal」で走査すると 0 件である。**コードを変えても入口のページは古いまま残る。**

### 既にあるものと、足りないもの

値のずれを見る検査（`generation-engine/scripts/check-derived-values.sh`）は既にある。ただし**比べているのは「定義（一覧の元データ・設計書の冒頭）」と「表示（入口のページ）」の一致だけ**である。

```
1. 画面名: 一覧の元データの値と、一覧・詳細ページの表示値の一致
2. 表示コミット: 設計書の冒頭の値と、入口・画面ページの表示値の一致
```

**コードの現在地とは比べていない。** そのため、コードが 100 コミット進んでも、定義と表示が揃っていれば合格し続ける。**古いことを検知できない。**

### 放置するとどうなるか

納品先のエンジニアと作業を担うエージェントは、入口のページを見て現状を把握する。**古い一覧を見て「この画面は無い」と判断したり、古い行数を見て規模を見誤ったりする。** 設計書だけを見て再構築する往復検証も、古い入力で走ることになる。

入口のページは「いま何があるか」を示す約束で作られている。**約束が守られていないことを誰も検知できない状態は、入口のページが無い状態より悪い。** あると信じて読むためである。

## やること

### 1. 鮮度の検知を作る

**コードの現在地と、入口のページが記録する表示コミットを比べる。**

- 対象プロジェクトの `git rev-parse HEAD` と、入口のページが持つ表示コミットを取る
- 両者が異なる場合、その間にコードの変更があったかを `git diff --name-only <表示コミット>..HEAD` で数える
- **入口のページの元になるファイルが変わっていれば古い**と判定する

「元になるファイル」は次の 3 に分ける。**すべてが古さの原因になるわけではない。**

| 変わったもの | 入口のページへの影響 |
|---|---|
| 画面・接続窓口・テーブル等の実装 | 一覧・図・設計書が古くなる |
| 設定ファイル・依存の定義 | 技術スタック・環境構築の手順が古くなる |
| 文書・コメントのみ | 影響しない場合がある |

**判定は「影響する変更が 1 件でもあれば古い」とする。** 影響しない変更まで古いと数えると、毎回落ちる検査になって読まれなくなる。

### 2. 何を作り直すかの依存関係を定義する

入口のページの各成果物が、何を入力にしているかを表にする。**表は宣言ファイルへ持つ。** スクリプトへ直書きすると、増えたときに追えなくなる。

想定する形は次である。

```
成果物 → 入力 → 作り直すコマンド
```

たとえば次のようになる。実際の対応は実装のときに確かめる。

| 成果物 | 入力 | 作り直すコマンド |
|---|---|---|
| 画面一覧 | 画面の実装ファイル | 画面の検出 → 一覧の元データ → 一覧の生成 |
| コードの行数 | すべての実装ファイル | 行数の計測 |
| 表同士のつながりの図 | テーブルの定義 | 図の生成 |
| 入口のページの件数と更新日 | 上記すべて | 入口のページの生成 |

**この表を作ることが本指示書の中心である。** 表が無いと、コードが変わったときに何を作り直せばよいかを人が毎回考えることになる。

### 3. 開発フローへ更新の段を設ける

`delivery-payload/templates/delivered-skills/dev-flow/SKILL.md` に、入口のページを更新する段を足す。

**置く位置は、実装が終わって統合する前とする。** 統合の後にすると、古いまま統合される時間が生まれる。

段の中身は次とする。

1. 鮮度の検知を走らせる
2. 古ければ、依存関係の表に従って作り直す
3. 作り直した結果を同じ変更へ含める

**作り直しを人の判断に任せてはならない。** 表に従って機械的に決まる形にする。判断を挟むと、忙しいときに飛ばされる。

### 4. 完了の記録へ入口のページの状態を残す

開発フローの完了記録（`docs/scope-and-progress/開発フロー完了記録.md`）へ、入口のページを更新したかどうかを残す。**更新した場合はその時点のコミット、しなかった場合は影響が無かったことの根拠を書く。**

## 完了の判定

1. 鮮度を検知するスクリプトが存在し、`--self-test` が終了コード 0 を返す
2. 依存関係の宣言ファイルが存在し、少なくとも 5 つの成果物について入力と作り直すコマンドを持つ
3. `delivery-payload/templates/delivered-skills/dev-flow/SKILL.md` に入口のページを更新する段が存在する（「ポータル」または「入口のページ」への言及が 1 件以上になる）
4. 完了記録の形式に、入口のページの状態を書く欄が存在する
5. 鮮度の検知が、この見本のリポジトリに対して判定を返す（合格・不合格のどちらでもよい。判定不能でないこと）

## 触らない範囲

- `generation-engine/scripts/check-derived-values.sh`。定義と表示の一致を見る検査であり、本指示書が作るのは**コードの現在地との比較**で、対象が異なる
- 既存の生成スクリプトの中身。作り直すコマンドとして呼ぶだけである
- `docs/tasks/` 配下の他の指示書

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 鮮度の判定を止める形にするか知らせる形にするか | **知らせる形にする。** 開発フローの中で作り直す段があるため、そこで直る。止める形にすると、影響の無い変更でも手が止まる | 作り直す段が飛ばされる実例が出た場合。そのときは止める形へ変える |
| 依存関係の宣言ファイルの置き場 | `delivery-payload/references/` の下に置く。既に `output-layout.json`・`unit-axes.json` など同種の宣言がある | 対象プロジェクトごとに違う形が要ると分かった場合 |
| 影響する変更の判定 | パスの前方一致で分ける。実装のフォルダが変わったら影響あり、文書のフォルダだけなら影響なし | 前方一致では分けられない構成のプロジェクトが出た場合 |
| 作り直しをどこまで自動でやるか | **全部やる。** 人が選ぶ形にすると飛ばされる | 作り直しに 10 分を超えるものが出た場合。その場合は分けて、重いものだけ人が選ぶ |
| 入口のページが無いプロジェクトの扱い | 鮮度の検知は何もせず終了コード 0 を返す。入口のページを持たないプロジェクトで毎回落ちると、検査が読まれなくなる | — |

## 他の指示書との関係

`走っていない検査を集約へ載せる指示書` が、検査が存在するのに走っていない問題を扱う。本指示書は、**検査そのものが無い**問題を扱う。

`用語集とガイドの食い違いを解消する指示書` と同じく、「情報源を定めたのに同期の仕組みが無い」形の問題である。**入口のページはコードを情報源とすると定めながら、同期の仕組みを持たない。**

## この指示書の位置づけ

入口のページを作る仕組みは既にある。**作ったあと保つ仕組みが無い。** 作る側と保つ側は関心が異なるため、保つ側を 1 件として切った。

依存関係の表と検査コマンドが実装で確定したため、状態を「着手できる」へ進めた。
