## この指示書は何か

`output-layout.json` は単位ディレクトリ直下のフォルダ名を定義する。フォルダ名は基本設計・詳細設計である。`unitPhaseDirNames`（basic-design・detail-design）で定義した。実際に単位フォルダを生成する `scaffold-design-unit.sh` はこの定義を読まない。「基本設計」「詳細設計」という日本語のフォルダ名がある。これをハードコードしたままである。生成スクリプトを定義に追従させる。

## なぜ必要か

`delivery-payload/references/output-layout.json` を確認すると、次の定義がある。

```
"unitPhaseDirNames": { "basic": "basic-design", "detail": "detail-design" }
```

一方 `generation-engine/scripts/scaffold-design-unit.sh` の `design_unit_phase_label()` がある。これは次のようにハードコードされている。

```
basic) echo "基本設計" ;;
detail) echo "詳細設計" ;;
```

`unitTestDesignDir`（テスト設計フェーズ）だけは `output_layout_get` を使う。これで定義値を読む。basicとdetailの2フェーズは読まない。

次のコマンドで単位を1件生成し、実際の階層を確認した。

```
bash generation-engine/scripts/scaffold-design-unit.sh api basic <出力先> api-sample01 サンプルAPI
```

生成された階層は次のとおりだった。定義（basic-design）と一致しなかった。

```
docs/design/apis/api-api-sample01/基本設計/API基本設計書.md
```

この食い違いにより、1-210で追加された検出関数がある。`detect_undefined_unit_phase_dirs` である。この関数は6種別すべての単位を見る。対象はAPI・テーブル・バッチ・帳票・外部連携・機能である。生成のたびに必ず警告を出す。この状態は1-210の完了記録自身が認めている。「現状の生成では既存のハードコードが新定義と一致しない」。「検出機能が常に警告を出す状態が続く」と記している。

放置すると、実際に生成される設計書のディレクトリ名がある。この名前は英数字化されないまま残る。1-208が定めた方針がある。「ディレクトリは英数字を使う」という方針である。この方針は、project-portal配下では守られる。単位内部の階層では守られない。加えて検出関数の警告が常態化する。本当に定義外の階層が紛れ込んだ場合の警告がある。これと、常に出る既知の警告を区別できなくなる。

## やること

1. `scaffold-design-unit.sh` の `design_unit_phase_label()` がある。この関数のbasic・detail分岐を、`unitTestDesignDir` と同じ方式に変更する。`output_layout_get` で `unitPhaseDirNames.basic`・`unitPhaseDirNames.detail` を読む形にする
2. 既存の単位フォルダの移行は本件の範囲外とする。対象プロジェクトには、既に生成済みのものがある。生成済みとは「基本設計」「詳細設計」の日本語フォルダである。1-210の完了条件も、既存生成物の改名を範囲外と明記している
3. 変更後、6種別で新規に単位を生成する。対象はapi・table・batch・report・external・featureである。basic-design・detail-designフォルダに配置されることを確認する
4. `detect_undefined_unit_phase_dirs` を実行する。新規生成した単位に対して警告が出なくなることを確認する
5. `scaffold-design-unit.sh` の既存の自己テストが壊れていないことを確認する。既存の自己テストは日本語ディレクトリ名を前提にした記述を複数持つ。テスト内の期待値も同時に更新する

## 完了の判定

1. 「なぜ必要か」節に示したコマンドを実行する。実行後、`<出力先>/docs/design/apis/api-api-sample01/basic-design/API基本設計書.md` が実在する
2. 同様にdetailフェーズで生成した場合、detail-designフォルダに配置される
3. `bash generation-engine/scripts/scaffold-design-unit.sh --self-test` を実行する。終了コード0で終わる
4. `design_unit_phase_label()` 関数の本体がある。この本体には「基本設計」「詳細設計」という直書きがある。この直書きが残っていない

## 触らない範囲

- `unitTestDesignDir`（テスト設計フォルダ名）。1-208で対象キー外と判断済みである。日本語のまま維持する
- screenUnitRoot配下（画面単位）。`scaffold-screen.sh` 側のハードコードは別スクリプトである。1-210も対象外としている
- `output-layout.json` の値そのもの。`unitPhaseDirNames`の値は既に定義済みで変更不要である
- 既存に生成済みの日本語フォルダ名を持つ単位の改名・移行
- `docs/tasks/` 配下、`delivery-payload/` 配下

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 実装方式 | `unitTestDesignDir` と同じ `output_layout_get` 呼び出しに揃える。既存のtestフェーズと同じ形にする。読み方を1種類に保つ。 | `output_layout_get` の呼び出しコストがある。このコストが生成の所要時間に無視できない影響を与えることがある。そう分かった場合は、値をキャッシュする方式へ変える |
| 既存の自己テストの期待値更新の範囲 | 既存ケースだけを更新する。対象は `design_unit_phase_label()` の出力に依存するケースである。無関係なケースの期待値は変更しない。 | 更新範囲を広げないと自己テストが通らないと分かった場合 |

## 他の指示書との関係

1-208（project-portal配下の英数字化）と1-209（旧構成の置き場検出）がある。これらと同じ方針がある。方針は「ディレクトリ名は英数字」である。この方針を単位内部の階層に適用する作業である。1-209・1-210で追加された検出関数がある。`detect_stale_portal_placeholders`・`detect_undefined_unit_phase_dirs`である。どちらも削除せず警告のみを行う設計である。本件もその設計を変更しない。

## この指示書の位置づけ

`output-layout.json` への定義追加と検出関数の追加は1-210で完了済みである。本件は、その定義を実際の生成スクリプトが読むようにする。実装の追従だけを扱う。定義側と生成側を同じコミットで両方変えなかった理由がある。理由は1-210の完了記録にある。「定義への追加と検出の仕組みまでを本項目の範囲とする」とある。生成スクリプトの改修は意図的に別作業として切り出されていた。本件はその切り出された残りの作業を独立した指示書として起こす。
