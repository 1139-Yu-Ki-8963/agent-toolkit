# 対象外の記録が2つの意味で読まれる問題を直す指示書

**状態**: 着手できる
**優先度**: 最高
**前提**: なし
**元の指摘**: 1-255

## 1. この指示書は何か

対象外の記録（`docs/scope-and-progress/excluded-kinds.json` の `excludedKinds`）を、整合の検査（`check-excluded-kinds-consistency.sh`）と納品物一覧の生成器（`build-deliverable-inventory.sh`）が別の意味で読む。前者は設計単位の6種別との完全一致を求め、後者はそこに載っていれば「対象なし」と判定する。この2つの要求は両立できない。6種別以外の納品物（例: 状態遷移図）を対象外にする経路が無いためである。納品物の対象外を受ける新しい鍵を設け、整合の検査は触らずに生成器だけが両方の鍵を読む形にする。

## 2. なぜ必要か

指摘の詳細は台帳の1-255を見よ。ここでは実装に必要な点だけを補う。

`delivery-payload/references/deliverable-inventory.json` は60件の納品物の証拠源を宣言する。このうち `dependsOnKind` を持つ8件は、依存先の6種別が対象外になれば連動して「対象なし」になる。ところが `evidenceSource` が `none` で `dependsOnKind` も持たない納品物（entity-state など）は、対象外にする経路が無い。実測では、entity-state を `excludedKinds` へ直接追記すると、整合の検査（6種別との完全一致を求める）が不合格になる。整合の検査を変えずに、この種の納品物を対象外にできる別の鍵が要る。

## 3. やること

1. `docs/scope-and-progress/excluded-kinds.json` の同じファイルへ、`excludedKinds` の兄弟として `excludedDeliverables` 配列を追加する。要素は `{kind, label, reason, category}` とする。`category` は `上流不在`（上流の記述が存在しないため作れない）または `対象不在`（対象そのものが存在しない）のいずれかとする。`output-layout.json` に新しい配置キーは追加しない。既存の `excludedKinds` パスが指す同一ファイルを使うため、新しい物理配置は要らない（判断の根拠は本指示書9節を見よ）。
2. `generation-engine/scripts/build-deliverable-inventory.sh` の `load_excluded_kinds` を、`.excludedKinds` に加えて `.excludedDeliverables // []` も読み、両方を連結して返す形にする。`resolve_state` のシグネチャは変えない。`excluded_reason_for_kind` の呼び出し側は変更不要。読めない・キーが無い場合は従来どおり `[]` へフェイルオープンする（判定不能にしない）。
3. `generation-engine/scripts/unit-list/check-excluded-kinds-consistency.sh` は変えない。6種別との完全一致を求める判定をそのまま保つ。
4. `.claude/skills/orchestrating-ai-development-setup/references/contract.md` の `## excluded-kinds.json` 節へ、`excludedDeliverables` の形式と `category` の2値を明記する。あわせて `generation-engine/scripts/build-deliverable-inventory.sh` の冒頭コメント（状態判定の節）へ、`excludedDeliverables` を読む旨を追記する。
5. `docs/scripts/check-excluded-deliverables.sh` を新設する。既定の実行では、`excludedDeliverables` の形式が定義文書（contract.md）に明記されているかを確かめる。`--check-resolution` で、(a) `excludedDeliverables` へ6種別以外の kind を載せた入力で生成すると当該行が「対象なし」になること、(b) 6種別の `excludedKinds` へ6種別以外を混ぜた入力で整合の検査が不合格になること、の両方を実際に確かめる。`--self-test` で単体の判定を確かめる。
6. `generation-engine/scripts/tests/check-excluded-deliverables.sh` を新設する。`docs/scripts/check-excluded-deliverables.sh --self-test` を呼ぶだけの薄いラッパーとする（`check-depends-on-kind.sh` の先例と同じ形）。
7. 触った資産の設計判断を `.claude/rules/always/tasks/instruction-format/rule.md` の「設計判断」節へ追記する。

## 4. 完了の判定

1. `excludedDeliverables` の形式が定義文書に明記されていること。確かめる手段: `bash docs/scripts/check-excluded-deliverables.sh`
2. 検査が、`excludedDeliverables` へ6種別以外を載せた入力で「対象なし」判定を確かめること。確かめる手段: `bash docs/scripts/check-excluded-deliverables.sh --check-resolution`
3. 同じ状態で整合の検査が合格を保つこと。確かめる手段: `bash docs/scripts/check-excluded-deliverables.sh --check-resolution`
4. 6種別の `excludedKinds` へ6種別以外を混ぜると整合の検査が従来どおり不合格になること（回帰がないこと）。確かめる手段: `bash docs/scripts/check-excluded-deliverables.sh --self-test`
5. 生成器の自己テストに回帰が無いこと。確かめる手段: `bash generation-engine/scripts/build-deliverable-inventory.sh --self-test`

## 5. 触らない範囲

- 整合の検査（`check-excluded-kinds-consistency.sh`）の判定を変えない。6種別との完全一致を保つ
- `dependsOnKind` の仕組みを変えない（1-253 で直したばかり）
- 生成済みの対象プロジェクトの記録を是正しない
- 他の指示書を変更しない
- `.claude/rules/scoped/portal/page-conventions/rule.md` を直接編集しない（生成物である）
- `delivery-payload/templates/` 配下を編集しない（テンプレート同期規約の対象になるため）

## 6. 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| `excludedDeliverables` の置き場を新しいファイルに分けるか | 分けない。同一ファイル（`excluded-kinds.json`）の兄弟キーとする。整合の検査は特定のjqパスしか読まず、対象JSON全体のキー集合を検証しないため、新キーの追加が既存判定へ影響しない（実測で確認済み） | 整合の検査が将来オブジェクト全体のキー集合を検証する形へ変わった場合 |
| `category` フィールドを必須にするか | 必須にする。理由の書き方の区別（検収方法5）を機械で確かめられるようにするため | 自由記述の理由文だけで区別を機械判定できる別の手段が見つかった場合 |

## 7. 他の指示書との関係

台帳の1-253は `dependsOnKind` の宣言漏れを直す指示であり、依存先が6種別であることを前提とする仕組みそのものは変えない。本項目は、依存先を持たない納品物（6種別に属さないものを対象外にしたい場合を含む）を対象にした別の経路を追加するもので、1-253とは対象が重ならない。台帳の1-252は統括スキルへ調査結果の提示・承認段を設ける指示であり、対象種別の宣言ずれ全般を扱う。本項目はその中の1事例（対象外の記録が2つの意味で衝突する）に絞って先に直す。

## 8. この指示書の位置づけ

台帳1-255が指摘する事象（対象外の記録を2つの仕組みが別の意味で読み、両立できない）は、片方の仕組みだけを直しても再発しうる。新しい鍵を設けて役割を分離し、整合の検査は変えないという最小差分で、両方の仕組みが矛盾なく機能する状態を作る。この指示書は、その鍵の新設と生成器の対応という1事例に絞った粒度で切る。

| 何を決めたか | 選んだもの | 選んだ理由 | 覆すと何が変わるか |
