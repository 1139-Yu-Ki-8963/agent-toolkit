## この指示書は何か

更新履歴（リリースノート）ページを、通常のポータル生成が入力から作り直せるようにする指示書である。あわせて、生成器の修正だけを完了の根拠にせず「既に生成済みの納品物へ検査を当てて0件になること」を完了条件へ加える。

## なぜ必要か

`build-portal.sh` の永続化対象再生成ループがある。位置は `generation-engine/scripts/build-portal.sh` の4669〜4697行目、`for detail_spec in` ブロックである。この対象は `techstack`・`env`・`glossary` の3種のみである。更新履歴は含まれない。

`.claude/skills/generating-release-notes-for-reverse-docs/SKILL.md` の Phase3（整合検証）には永続化ステップが無い。`generating-tech-stack-for-reverse-docs/SKILL.md` の Phase3 Step3 は永続化ステップを持つ。そこでは `output-layout.sh` で `manifestsRoot` を解決する。`<output_dir>/<manifestsRoot>/detail-pages/<kind>-page-data.json` へ保存する。release-notes 側にはこの手順が無い。

page-data.json の保存先は `$CLAUDE_JOB_DIR/tmp/release-notes-page-data.json`（同SKILL.md 116行目）のままである。ここは一時領域であり、版管理へ残らない。

`build-portal.sh` の `--self-test` ケース49g（同ファイル1259〜1377行目付近）がある。ここは既存の更新履歴HTMLを「別生成器が作ったリリースノート」として扱う。保持し、削除しない状態をPASS条件とする。これは、通常のポータル生成が更新履歴ページを自動的に作り直す設計になっていないことを直接示す。

生成器（`generation-engine/scripts/detail-pages/build-detail-page.sh`）を直しても、通常のポータル生成からその生成器を通す手段が無い。古いページが納品物に残り続ける。

台帳の1-203はこの生成器の修正を「完了」とした。しかし対象プロジェクトへ配った既存の納品物（既に生成済みのHTML）には修正が反映されなかった。検証する側からは「未解決」と判定された。

生成器の修正だけを完了の根拠にすると、同じ食い違いが今後の項目でも起こりうる。

`docs/tasks/指摘改善一覧.md` を配布物全体で `grep -rn "既に生成済みの納品物へ当てる"` すると0件であり、完了条件にこの観点が明記されていないことも確認済みである。

6. `generation-engine/samples` を「既に生成済みの納品物」として使う。このリポジトリ自身の見本であり、対象プロジェクトが手元に無いための代替対象である。`generation-engine/scripts/tests/test-e2e-portal.sh` を当てる。更新履歴ページに関する不合格が0件であることを確認し、記録する。
