# 規約とフローの対応見本を生成する指示書

**状態**: 着手できる
**優先度**: 中
**前提**: なし
**元の指摘**: 1-264

## 1. この指示書は何か

既存の生成器を使って「規約とフローの対応」の見本HTMLを作り、見本の派生物台帳と納品物一覧を現物へ一致させる指示書である。

## 2. なぜ必要か

生成器、カタログ登録、入力の分類データ、見本側の規約27件はそろっているが、宣言された見本HTMLだけが無い。生成器は規約派生物の生成器とポータルの最終組み立てから独立しており、他の基盤見本を個別生成した記録にも含まれていない。現行の見本再生成経路にこの独立生成器が含まれないため、出力だけが取り残されたと判断できる。その結果、納品物一覧はHTMLの不在と `evidenceSource: none` の宣言に従い「未生成」「判定の材料が無い」と報告する。

## 3. やること

1. `bash generation-engine/scripts/rules/build-rule-flow-map.sh delivery-payload/references/rule-taxonomy.json generation-engine/samples/project-portal/foundation/規約とフローの対応.html --project-name sample-project --generated-at 2026-07-30T00:00:00Z --catalog delivery-payload/references/portal-catalog.json --target-root generation-engine/samples` を実行する。
2. `bash generation-engine/scripts/build-deliverable-inventory.sh generation-engine/samples generation-engine/samples/project-portal/foundation/納品物一覧.html generation-engine/samples/docs/納品物一覧.md --project-name sample-project --generated-at 2026-07-30T00:00:00Z --catalog delivery-payload/references/portal-catalog.json --deliverable-inventory delivery-payload/references/deliverable-inventory.json` を実行する。
3. すべての生成後に `bash generation-engine/scripts/check-derived-drift.sh record generation-engine/samples` を実行し、`generation-engine/samples/derived-fingerprints.json` を更新する。
4. 完了の判定を実行し、生成物と判定結果を同じコミットへ含める。

## 4. 完了の判定

1. `generation-engine/samples/project-portal/foundation/規約とフローの対応.html` が実在する。
2. `generation-engine/samples/docs/納品物一覧.md` の「規約とフローの対応」が「出力あり」である。
3. `bash generation-engine/scripts/tests/check-derived-drift-ledger.sh` が終了コード0を返す。
4. `bash generation-engine/scripts/tests/test-portal-conventions.sh generation-engine/samples` が不合格0件で終了コード0を返す。
5. `bash docs/scripts/report-progress.sh` が「総数: 122件」を出して終了コード0を返す。
6. `bash .claude/rules/always/tasks/instruction-format/check-instruction-format.sh` が不合格0件で終了コード0を返す。
7. `bash generation-engine/scripts/tests/check-broken-verdict-rows.sh` が終了コード0を返す。
8. 課題キー `1-264` を含むコミットの後で `git status --porcelain` が空である。

## 5. 触らない範囲

- `build-rule-flow-map.sh` の生成ロジックと自己テスト
- `portal-catalog.json` と `deliverable-inventory.json` の宣言
- 規約27件の定義と派生HTML
- 「アーキテクチャ調査書」など、今回と別の未生成納品物
- 検査の合格条件と不合格判定

## 6. 決めていないこと

| 事項 | 担当者が選べる具体的な既定 | 覆す条件 |
|---|---|---|
| 見本のプロジェクト名 | 既存の基盤見本と同じ `sample-project` を使う | 見本全体の正本で別名が定義されていることを実測した場合 |
| 生成日時 | 既存の基盤見本と同じ `2026-07-30T00:00:00Z` を渡す | 見本全体の正本で別の固定日時が定義されている場合 |
| 規約の掲載範囲 | `--target-root generation-engine/samples` を指定し、見本に実在する規約だけを載せる | 見本が分類データ27件の全件掲載を固定値として要求する場合 |
| 生成連鎖の恒久修正 | 今回は見本の欠落だけを直し、生成器同士の呼び出し関係は変えない | 別課題で見本一括再生成への組み込みが明示された場合 |

## 7. 他の指示書との関係

既存の納品物一覧の状態判定やポータル見本再生成を変更した指示書の成果を利用する。状態判定の仕様変更や一括再生成経路の再設計は行わないため、既存指示書と実装範囲は重ならない。

## 8. この指示書の位置づけ

生成可能だが作られていなかった見本1件を、既存の宣言と生成器に従って補う作業である。生成器の新設や検査の緩和ではなく、欠けた派生物と台帳を一致させる。

### 判断の記録

| 何を決めたか | 選んだもの | 選んだ理由 | 覆すと何が変わるか |
|---|---|---|---|
| 欠落の直し方 | 既存生成器を見本へ直接実行する | 生成器、入力、出力宣言がそろい、欠けているのが派生HTMLだけだから | 一括生成へ組み込む場合は生成スクリプトと回帰テストの変更が追加される |
| 状態判定の扱い | `evidenceSource: none` を変更しない | HTMLが実在すれば先に「出力あり」と判定され、判定を弱める必要がないから | 宣言を変えると別の証拠形式とその検査が必要になる |
| 規約の範囲 | 見本ルートに実在する27件を使う | 親7件・子27件が分類データと見本側の両方で一致したから | 件数が不一致なら生成ページの掲載件数と差異報告が変わる |
| 恒久的な生成連鎖 | 今回は変更しない | ユーザーの実装指示が見本作成、一覧再生成、台帳更新に限定されているから | 別課題として一括生成の責務と呼び出し順を設計する必要がある |
