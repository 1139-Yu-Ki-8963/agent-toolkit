## この指示書は何か

第 1 層の集約が、終了コード 2（判定不能）を終了コード 1（不合格）と同じ扱いにしている。判定不能の規約が求める区別を集約へ実装する。

## なぜ必要か

`.claude/rules/always/verification/indeterminate-result/rule.md` は、実行できなかったことと不合格を区別し、判定不能は終了コード 2 と `[UNKNOWN]` の札で表すと定める。同規約は、既存の合否の札へ理由を書き添えるだけの扱いを明示的に禁じている。後から出力を読む人が不合格として数えてしまうからである。

ところが集約（`generation-engine/scripts/verification/run-layer-machine-checks.sh`）の合否の判定は 399 行目の `[ "$RUN_RC" -eq 0 ]` の真偽だけである。終了コード 2 はこの条件が偽になるため 402〜404 行目の `else` へ落ち、`FAIL` として数えられる。終了コードの値を 0・1・2 で見分ける条件式は、このスクリプトのどこにも無い。

実害が出ている。2026-08-19、走っていない検査 7 件を集約へ載せる作業で、2 件が実行に必要なものをこの環境に持たないことが分かった。`test-project-semantic-glossary-race.sh` は PyYAML を要して終了コード 2 で終わり、`test-validate-semantic-glossary.sh` は `.venv` を要して終了コード 1 で終わる。載せると、環境の準備が無いことが不合格として現れ、集約全体の終了コードが 1 になる。そのため載せられなかった。区別があれば載せられた。

放置すると、環境の準備に依存する検査は集約へ載せられないままになる。載せなければ走らない。走らない検査は、検査が無いのと変わらない。

## やること

1. 集約の合否の判定へ、終了コード 2 を独立して扱う分岐を足す。札は `[UNKNOWN]` とする
2. 集計行へ判定不能の件数を足す
3. 集約自身の終了コードを決める箇所（426 行目）で、判定不能を失敗として数えないようにする
4. 集約へ `--self-test` を足す。既にある場合はケースを足す。ケースの名前は `判定不能-不合格と区別` と `判定不能-集約の終了コードに影響しない` の 2 件とする
5. 環境の準備が無くて落ちる既存 2 件を集約へ載せ直す。両スクリプトの冒頭に、載せ直す条件が書いてある

## 完了の判定

1. 集約の自己テストが終了コード 0 で終わる
2. 集約の自己テストの出力に `判定不能-不合格と区別` のケースが現れる
3. 集約の自己テストの出力に `判定不能-集約の終了コードに影響しない` のケースが現れる
4. 配線漏れの検査の自己テストが終了コード 0 で終わる（既存の検査を壊していないこと）

## 触らない範囲

- 各検査スクリプトが返す終了コードそのもの。集約の受け取り方だけを変える
- 集約の時間の上限の仕組み（`declared_long_running_timeout` と打ち切りの記録）
- `docs/tasks/` 配下
- `delivery-payload/` 配下

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 判定不能の札 | `[UNKNOWN]` を使う。判定不能の規約が定める語である | 集約の既存の札（`PASS`・`FAIL`・`SUSPECT`・`TIMEOUT`・`DECLARED-LONG`）と衝突すると分かった場合 |
| 判定不能を集約全体の終了コードへ反映するか | 反映しない。判定不能は実行できなかったことであり、成果物の欠陥ではない | 判定不能が常に出る状態が続き、検査が形だけになると分かった場合 |
| 集計行の書き方 | 既存の集計行の末尾へ「判定不能 N 本」を足す | 集計行が長くなりすぎて読めないと分かった場合 |
| 環境の準備が無くて落ちる 2 件をこの周で載せ直すか | 載せ直す。区別が入れば載せられる。各スクリプトの冒頭に載せ直す条件が書いてある | 区別を入れても別の理由で落ちると分かった場合 |
