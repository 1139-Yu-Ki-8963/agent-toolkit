# 片付き判定に実測の段階を足す指示書

**状態**: 着手できる
**優先度**: 最高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

`docs/scripts/judge-task-done.sh` の片付き判定へ、「記録の語を読む」だけでなく「判定の条件を実際に走らせて満たすか確かめる」段階と、「元の指摘を覆っているか照合する」段階を足す。現状は記録の状態欄が「完了」という語であるかどうかしか見ておらず、その語の裏付けを取っていない。

## なぜ必要か

判定器は 3 条件を見る。

| 条件 | 何を見るか |
|---|---|
| 記録が済んでいる | 状態の欄の**語**が「完了」「対象外」「判断待ち」のいずれか。「未着手」「対応中」が残れば止める |
| main へ入っている | コミット欄のハッシュが実在し main の祖先か |
| 公開が済んでいる | payload が main と一致しているか |

**「確かめた内容」の欄を 1 度も読んでいない。** 走査するコードに `確かめた内容` という語が 0 件である。実際に `LC_ALL=C grep -c '確かめた内容' docs/scripts/judge-task-done.sh` を実行すると結果は `0` である。

つまり「完了」という 2 文字と、実在するコミットのハッシュが 1 個あれば通る。判定の条件が実際に満たされたかは見ない。

**これが実害を出した。** `done/` の 23 件・判定 168 件をサブエージェント 4 手で実測したところ、4 件が完了していなかった。

```
未着手の指示                    判定17 が EXIT=1（生成物のずれ 28 件）。記録は exit 0 と書いていた
規約の名前を中身が読める形へ改める   判定13 が不合格（16 ファイルに旧い題名が残る）
読み手で分ける規約               判定1・3 が不合格
スキル実装計画                  「対象外」6 件すべてに理由が無い
```

いずれも状態欄が「完了」だったので判定器を通った。

**本来 3 段階あるべきものが 1 段目しか無い。**

| 段階 | 何を確かめるか | 現状 |
|---|---|---|
| 1. 書式 | 記録の形・コミットの実在・公開の同期 | 判定器がやる |
| 2. 実測 | 各判定の条件を実際に走らせて満たすか | 無い |
| 3. 照合 | 元の指摘を覆っているか | 無い |

段階 2 が無いために、168 件を人手で走らせる必要があった。**この作業自体が本来は機械の仕事である。**

段階 3 が無いために、`実装契約の置き場を全種別で揃える指示書` は判定 15 件すべてを満たしながら、元の指摘のうち疑似コードと戻り値を落としていた。指示書が指摘の一部しか拾っていなくても誰も気づかない。

2026-08-18、この照合の向きが誤っていたことが分かった。`docs/tasks/work-records/改善反映台帳.md` は反映が済んだ記録であり、そこに載るキーに指示書が無いのは正常な終わりの状態である。台帳を起点に「指示書に現れないもの」を欠落として数える向きでは、片付いた 44 件を欠落として報告し続けることになり、何度直しても数字が減らない。指示書が主張するキーを起点に、台帳へ検証方法と結果を伴う行があるかを見る向きへ改めた。改めた結果、片付けたと主張しながら反映の記録が無いものを検出できるようになった。

## やること

### 段階 2 の作り

**判定の表へ「確かめる手段」の列を足す。** いまの 4 列（判定・状態・コミット・確かめた内容）を 5 列にする。書き方の見本は次のとおりである（見本であり、この節そのものは判定の対象ではない）。

```
| 判定 | 確かめる手段 | 状態 | コミット | 確かめた内容 |
|---|---|---|---|---|
| 1. <判定> | `bash 〜 --self-test` | 完了 | <ハッシュ> | <実行の要点> |
```

**「確かめる手段」の欄にはコマンドだけを書く。** 説明を混ぜない。判定器はこの欄のコマンドを実行し、終了コード 0 なら満たすとする。

コマンドで表せない判定（文面の評価など）は `目視` と書く。判定器は `目視` の行を「機械では確かめられない」として数え、**1 件でもあれば `done/` へ移すことを止める。**

**状態の欄は判定器が書き込む形にする。** 人が「完了」と書けないようにする。これが今回の事故の直接の原因だからである。

### 段階 3 の作り

指示書の「やること」に、元の指摘のキー（`1-42` 等）を書く決まりにする。判定器は、指摘の一覧に載っているキーがいずれかの指示書に現れるかを数え、落ちているキーを報告する。

**この方法は今日、改善反映台帳と課題一覧の突き合わせで実際に効いた。** 15 件のキーがどちらに載っているかを数えて食い違いを見つけた。

### 移行

既存の記録をこの形へ移す必要がある。対象は、この指示書を作成した時点の `docs/tasks/done/` の 26 件と直下の指示書である。**移行を含めて 1 つの作業とする。**

## 完了の判定

1. 判定の表が 5 列（判定・確かめる手段・状態・コミット・確かめた内容）である
2. 規約（instruction-format/rule.md）が 5 列の形を定めている
3. 判定器が「確かめる手段」の欄のコマンドを実行する
4. 終了コードが 0 以外の判定があれば `done/` へ移すことを止める
5. `目視` の行が 1 件でもあれば `done/` へ移すことを止める
6. 状態の欄を判定器が書き込む
7. 指示書が主張するキーについて、台帳に裏付けの行があるかを見る処理がある
8. 裏付けの無いキーを報告する
9. 判定器の自己テストが終了コード 0 を返す
10. 自己テストが、実測で不合格になる判定を止めることを確かめるケースを持つ
11. この指示書を作成した時点の `docs/tasks/done/` の 26 件と直下の指示書が 5 列の形へ移っている
12. 指示書の形の検査（`check-instruction-format.sh --self-test`）が終了コード 0 を返す

## 触らない範囲

- 判定器の 3 条件のうち「main へ入っている」「公開が済んでいる」の判定
- `docs/tasks/work-records/` 配下
- コミット直前の検査（`docs/scripts/check-task-done-move.sh`）の呼び出し方

## この指示書の位置づけ

この仕組みが無い限り、他のすべての指示書の完了が信用できない。段階 1（書式）だけでは「完了」と書けば通ってしまい、実測（段階 2）と照合（段階 3）が抜けたまま `done/` へ積み上がる。この指示書は片付き判定の仕組みそのものを直す 1 件として独立させ、他の指示書の内容には踏み込まない。
