# 指摘の追跡を機械で読める形にする指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

画像から書き起こした指摘と、それを片付ける指示書との対応を、機械で読める形にする。いまは対応が本文の地の文にしか無く、片付いたと主張する指示書がどの指摘を覆っているのかを機械で辿れない。指示書の冒頭に元の指摘を書く欄を足し、検査と片付き判定をそれに合わせる。

## なぜ必要か

`docs/scripts/judge-task-done.sh --cross-check` は、指示書が主張する指摘のキーに、反映の記録（`docs/tasks/work-records/改善反映台帳.md`）の裏付けがあるかを見る。ところが「指示書が主張するキー」を本文の地の文から拾うほかなく、次の実測が出た。

| 走査 | 件数 |
|---|---|
| 本文から `1-NN` の形をすべて拾う（緩い） | 64 件 |
| 見出し `### 1-NN.` と `原番号 1-NN` だけに絞る | 55 件 |
| 差（工程番号などの誤り） | 9 件 |

差の実物は `| 前提 | Stage 1-3の成果物 |` のような工程の番号である。指摘のキーではない。

絞ったあとの 55 件はすべて `docs/tasks/指摘改善一覧.md` の見出しであり、**`docs/tasks/done/` に片付いた指示書は元の指摘のキーを 1 件も機械で読める形で持っていない。** 指摘から指示書へ、指示書から片付きへの追跡が構造として存在しない。

放置すると、片付いたと主張する指示書がどの指摘を覆ったのかを誰も確かめられない。指摘が片付いていないのに指示書だけが `done/` へ移る状態を、機械で見つけられない。

## やること

1. 指示書の冒頭 3 行（状態・優先度・前提）に続けて、4 行目として元の指摘を書く欄を足す

```
**元の指摘**: 1-62, 1-65, 1-81
```

   覆う指摘が無い指示書（仕組みの改善など、画像由来でないもの）は `なし` と書く。空欄にしない

2. `.claude/rules/always/tasks/instruction-format/rule.md` の「冒頭に置く 3 行」の節を 4 行に改め、書き方と `なし` の扱いを定める

3. `.claude/rules/always/tasks/instruction-format/check-instruction-format.sh` の検査 2（冒頭の 3 行）を 4 行の検査に改める。値の形は `1-NN` をカンマ区切りで並べたもの、または `なし` に限る。自己テストのケースを足す

4. `docs/tasks/` の直下・`design/`・`done/` の全指示書へ 4 行目を足す。値は各指示書の本文と `docs/tasks/work-records/改善反映台帳.md` を突き合わせて決める。判別できないものは `なし` とし、その旨を「対応の記録」の判断の記録へ書く

5. `docs/scripts/judge-task-done.sh` の `extract_claimed_keys` を、4 行目の欄だけを読む形に改める。本文の走査をやめる。自己テストのケースを足す

## 完了の判定

1. `bash .claude/rules/always/tasks/instruction-format/check-instruction-format.sh --self-test` が終了コード 0 を返す
2. `bash .claude/rules/always/tasks/instruction-format/check-instruction-format.sh` の不合格が 0 件になる
3. `docs/tasks/` の直下・`design/`・`done/` の全 `*.md` が `**元の指摘**:` で始まる行を持つ（`grep -L` の結果が 0 件）
4. `bash docs/scripts/judge-task-done.sh --self-test` が終了コード 0 を返す
5. `bash docs/scripts/judge-task-done.sh --cross-check` が、本文ではなく 4 行目の欄からキーを読んでいる（自己テストのケースで確かめる）

## 触らない範囲

- `docs/tasks/work-records/改善反映台帳.md`。記録であり、後から書き換えると当時の記帳が失われる
- 各指示書の「対応の記録」の判定の表（状態・コミット・確かめた内容の 3 列）
- `generation-engine/` 配下

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 4 行目を必須にするか任意にするか | 必須にする。値が無い場合は `なし` と書かせる。任意にすると、書いていないのか覆う指摘が無いのかを読み手が区別できない | 全指示書への追記が 1 セッションで終わらないと実測で分かった場合。その場合は直下と `design/` を先に必須化し、`done/` を後続へ回す |
| `done/` の既存指示書へ遡って足すか | 足す。足さないと片付いたものの追跡がいつまでも空のままになり、この指示書の目的が達せられない | 上と同じ |
| 判別できない指示書の扱い | `なし` と書き、判断の記録へ「本文と台帳から判別できなかった」と残す。推測でキーを書かない | 台帳の側に対応を書き足す別の手段が見つかった場合 |

## 他の指示書との関係

`片付き判定に実測の段階を足す指示書` が段階 3（元の指摘との照合）を実装した。本指示書はその段階 3 が読む入力を、本文の地の文から機械で読める欄へ移す。段階 3 の実装そのものは変えない。

## この指示書の位置づけ

段階 3 の照合は、向きを 2 度直し、台帳の書き方の揺れにも対応した。それでも入力が地の文である限り、工程番号を指摘のキーと取り違える誤りは無くならない。入力の形そのものを変えるところで 1 件として切った。
