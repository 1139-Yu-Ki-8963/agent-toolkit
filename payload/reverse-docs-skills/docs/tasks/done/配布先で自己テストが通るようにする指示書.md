# 配布先で自己テストが通るようにする指示書

**状態**: 着手できる
**優先度**: 中
**前提**: なし
**元の指摘**: なし

## 1. この指示書は何か

配布物に同梱した自己テストが、配布先の置き場所によって結果が変わる状態を直す。どこに置いても同じ結果になるようにする。

この指示書は指示であり、実装ではない。読んだ担当者が作業する。

## 2. なぜ必要か

### 2.1 実測した状態

同じ自己テストを 2 か所で実行し、結果が食い違うことを確かめた。

| 実行した場所 | 結果 |
|---|---|
| このリポジトリ | 終了コード 0。全ケース合格 |
| 配布物の中 | 終了コード 1。1 件が不合格 |

不合格になったのは次の 1 件である。

```
[FAIL] entryFile-実在(サンプル): リポジトリのルート起点sourceDirの解決に失敗した
```

### 2.2 原因

自己テストは、対象の置き場所を決めるために**リポジトリの境界を探す**。探し方は、自分の位置から上へ遡って版管理の目印を見つけることである。

配布物は、公開リポジトリの中の一区画として置かれている。そのため上へ遡ると、**配布物の境界を越えて公開リポジトリの境界に当たる。**

実測すると、配布物の中で境界を尋ねたところ、配布物ではなく公開リポジトリの場所が返った。

```
配布物の中で境界を尋ねる → 公開リポジトリの場所が返る
```

その結果、対象の置き場所が配布物の外を指し、実在の確認に失敗する。

### 2.3 なぜ困るか

**配布先での動作を保証できない。**

配布物は、対象プロジェクトの中に置かれる。対象プロジェクトが版管理されていれば、同じことが起きる。配布物の自己テストは、置かれ方によって落ちる。

**「すべての自己テストが成功すること」という条件が、置き場所によって達成できない。** 実際、配布物を上位のリポジトリの下に置いた状態では達成できていない。

### 2.4 同じ探し方をする箇所

境界を探す処理は、配布物の中に 6 本ある。

```
generation-engine/scripts/check-worktree-commit-guard.sh
generation-engine/scripts/audit-consistency.sh
generation-engine/scripts/build-portal.sh
generation-engine/scripts/verification/verification-env.sh
generation-engine/scripts/verification/run-layer-full-pipeline.sh
generation-engine/scripts/unit-list/prepare-screen-rebuild-sample-fixture.sh
```

不合格が出たのは 1 本だが、**同じ探し方をする箇所が他にもある。**

## 3. やること

### 3.1 境界の探し方を決める

配布物の中で境界を探すとき、**配布物の範囲で打ち切る**ようにする。

上へ遡る途中で配布物の目印を見つけたら、そこで止める。それより上を参照しない。

**目印に何を使うかは担当者が決める。** 決めるときは次を満たすこと。

- 配布物に必ず含まれるもの
- 対象プロジェクトが偶然同じものを持たないもの
- 配布物の一番上の階層にあるもの

### 3.2 不合格が出た箇所を直す

まず、実際に不合格が出た箇所を直す。

対象は `generation-engine/scripts/unit-list/validate-manifest.sh` の、対象の置き場所を解決する処理である。

### 3.3 同じ探し方をする箇所を調べる

2.4 に挙げた 6 本それぞれについて、次を確かめる。

| 確かめること | 内容 |
|---|---|
| 何のために境界を探しているか | 対象の置き場所か、版管理の操作か、別の目的か |
| 配布先で問題になるか | 上位のリポジトリを参照すると誤動作するか |
| 直す必要があるか | 問題になるなら直す。ならないなら理由を記録する |

**版管理の操作そのものが目的の箇所は、直す対象ではない可能性がある。** たとえば作業ツリーの状態を見る処理は、上位のリポジトリを見ることが正しい場合がある。**役割を読んで判断すること。**

### 3.4 両方の置き方で確かめる

直したあと、2 つの置き方で自己テストを実行する。

| 置き方 | 期待 |
|---|---|
| 上位にリポジトリを持つ配置 | 終了コード 0 |
| 独立したリポジトリとしての配置 | 終了コード 0 |

**どちらか一方だけで確かめない。** 片方だけ通る状態が、いまの問題そのものである。

### 3.5 置き場所によらないことを確かめ続ける

置き場所によって結果が変わらないことを、機械で確かめ続ける形にする。

**新しい仕組みを作らない。** 既にある機械検証の集約（`generation-engine/scripts/verification/run-layer-machine-checks.sh` が集めるもの）に、2 つの置き方で実行する検査を足す。

## 4. 完了の判定

次のすべてを満たすこと。

1. 境界の探し方が決まり、使う目印が記録されている
2. 目印が 3.1 の 3 条件を満たすことが確かめられている
3. `validate-manifest.sh` の自己テストが、配布物の中で終了コード 0 になる
4. 同じ自己テストが、独立したリポジトリとしての配置でも終了コード 0 になる
5. 6 本それぞれについて、直す必要があるかの判断と理由が記録されている
6. 直す必要があると判断した箇所がすべて直っている
7. 直さないと判断した箇所について、その理由が読んで分かる形で残っている
8. 2 つの置き方で実行して結果を比べる検査がある
9. その検査が機械検証の集約に載っており、実行される
10. その検査が、結果が食い違ったときに不合格を出す

## 5. 触らない範囲

- 自己テストの判定条件そのもの（境界の探し方だけを直す）
- 公開リポジトリ側の構成
- 配布物の置き場所の決まり
- `.claude/rules/` 配下（このリポジトリ自身の規約であり、配る資産とは別）

## 6. 決めていないこと

次は、作業する担当者が決める。

1. **配布物の目印に何を使うか**。3.1 の 3 条件を満たすものを選ぶ
2. **6 本それぞれを直すかどうか**。3.3 の観点で判断する
3. **2 つの置き方で確かめる検査の置き場と名前**。既にあるスクリプトの付け方に揃える

## 7. 他の指示書との関係

他の指示書とは対象が重ならない。どれを先に実施してもよい。

## 8. この指示書の位置づけ

配布物は対象プロジェクトの中に置かれる。置かれ方によって自己テストが落ちると、配布先で動くことを確かめられない。境界を配布物の範囲で打ち切り、置き場所によらず同じ結果になる状態にする。あわせて、その性質が保たれ続けることを機械で確かめる。

## 9. 対応の記録

対応する担当者が周ごとに更新する。状態は「未着手」「対応中」「完了」「対象外」の4つを使う。
「対象外」にした行は、確かめた内容の欄へ、なぜその判定が成立しないかを書く。
判定は「## 4. 完了の判定」が挙げる10件をそのまま使う。
