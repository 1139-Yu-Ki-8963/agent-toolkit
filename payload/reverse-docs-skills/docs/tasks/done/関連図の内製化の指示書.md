## 1. この指示書の目的

改善課題 1-26（6回目の指摘）「配布物の生成器では現在のポータルを再現できず、実行側の独自スクリプトに依存している」には、関連図（画面遷移図・ER図・状態遷移図）だけが配布物の生成器から生成できないという残件がある。この残件は過去に「完了条件の改訂」という形で決着済みだが、ユーザーは実測結果を踏まえて方針を変え、段階的に確かめながら関連図の内製化を進める判断をした。本指示書はその段階的な作業手順を定める。

## 2. 課題の原文（引用）

出典: `docs/ledgers/改善課題タスク一覧.md:233` 以降「1-26. 配布物の生成器では現在のポータルを再現できず、実行側の独自スクリプトに依存している（6回目の指摘）」。

> **検収方法**: 配布物の生成器だけを使って実行側の独自スクリプトなしにポータル一式が生成できること。生成されたポータルに規約ページ・種別別一覧・対応表・関連図がすべて含まれること。

> **完了条件**: 配布物の生成器だけでポータル一式が再現できること。実行側が独自に作った個々のスクリプトの取り込み可否の判断までを含む。実行側固有の表示調整の取り込みは本項目の対象外。

> **再検証時の追加実測（2026-08-16）**: 大きく前進し、残るのは関連図のみ。配布物の生成器だけを実行して、規約ページとトップページに加え、種別別の一覧10種と対応表5種が生成されるようになった。設計文書から入力データを組み立てる経路が新設され、一気通貫の入口も加わって203件の生成が合格した。関連図だけが生成されない。説明書には関連図の入力を設計文書から組み立てる処理を取り込まないという方針が残っており、理由として関連図の入力が求める出典参照と確信度に対応する記載欄が設計文書に無く文書からは復元できないと述べている。起票側からは、この方針を維持するなら完了条件を関連図を除く形へ改めてほしいという申し出がある。判定の基準は既に分母から関連図を除いており、判定の側と完了条件の側で範囲が食い違っている。**この項目は完了条件の改訂の可否が決まるまで閉じられない。**

つまり過去の決定は「設計文書に出典参照・確信度の欄を足すこと自体が、情報アクセス規律（工程が進むほど参照できる情報を狭める規律。README.md の「情報アクセス規律の段階的縮小」原則）を崩す」という懸念に基づいて、関連図の内製化を見送っていた。

ユーザーは今回、実測結果（第4節）を見たうえで、この懸念を無条件に受け入れるのではなく、**段階的に確かめながら進める**方針を選んだ。3つの関連図のうち、状態遷移図はそもそも設計文書に既に出典参照の欄があり、欄を足す必要が無いかもしれない。ER図は出典参照だけで済み確信度は不要。画面遷移図だけが確信度という新しい概念を要求する。この違いを無視して「関連図は一律に取り込まない」と決めていたことが、過去の決定の粗さである。

**ただし、規律を崩す懸念そのものは消えていない。**各段階の作業者は、自分が今から足そうとしている欄が「工程が進むほど参照できる情報を狭める規律」に抵触しないかを判断すること。抵触すると判断した場合は、その段階の作業を中断し、止まってユーザーへ確認すること。抵触するかどうかを機械的に判定する基準は無いため、作業者自身の判断に委ねる。判断に迷う場合も、進めずに確認すること。

### 段階1: 状態遷移図（欄の追加が不要な可能性）

**まず、本当に欄の追加なしで生成できるかを確かめる。**

1. `データ設計.md` §6「状態遷移表」の「根拠パス」列を、生成器（`build-manifests-from-docs.sh` や `build-portal.sh` の前処理経路）が読んでいるかを実際にコードを追って確認する
2. 読んでいなければ、読むように生成器側の抽出処理を実装する。**この段階で設計文書側（`データ設計.md` テンプレート）に欄を足さない。**足さずに済むなら、それが最善である
3. `entity-state` 用の入力データ（`nodes[]` / `edges[]`）を、`データ設計.md` §6 のテーブル行から機械的に組み立てられるようにする。`edges[].sourceRef` には「根拠パス」列の値を使う
4. 実際に `build-detail-page.sh --page entity-state` を実行し、状態遷移図が生成されることを実測で確かめる
5. 足さずに済まないと判明した場合（根拠パス列だけでは entity/nodes/edges を復元できない等）は、何が足りないかを具体的に報告し、この段階の作業をここで止める。ユーザーへ確認すること

### 段階2: ER図（確信度は不要）

出典参照と関連の種別（cardinality）を `テーブル定義書.md` §6.3 外部キー へ足す。

1. 出典参照の書き方は、既存の作法に揃える。`データ設計.md` §6 の「根拠パス」列、または生成器内で使われている `sourceFile` / `source_ref` の命名慣行を確認し、新しい形を発明しない
2. cardinality の値域（例: 一対一・一対多・多対多）を決める。**決めた値域をテンプレート（`テーブル定義書.md`）の該当セルへプレースホルダとして明記する**（例: `<実測: 一対一 | 一対多 | 多対多>` のような形式。既存テンプレートの実測プレースホルダの書式に揃える）
3. `relations[]` 用の入力データ（`from` / `to` / `cardinality` / `sourceRef`）を、`テーブル定義書.md` §6.3 の行から組み立てられるように生成器側の抽出処理を実装する
4. 欄を足したテンプレートから ER 図が実際に生成されることを実測で確かめる（`build-detail-page.sh --page er`）

**確信度は足さない。**ER図のスキーマ（`relations[]`）は confidence を要求しない（第4.2節）。

### 段階3: 画面遷移図（確信度の定義が先に要る）

実測の結果、確信度の欄を新設せずに済んだ。出典参照を、入力の仕様が既に許す文書参照形式（文書パス＋節見出しの組）で表せば足り、`画面基本設計書.md` §6「画面遷移の業務文脈」が既に持つ遷移元・遷移先・契機の3列だけから矢印を組み立てられた。確信度の値は空のままとし、値を捏造していない。空でも描画が崩れないことを実描画で確認済み。

**この段階だけ、前提として確信度の定義が要る。**

1. 確信度の値域と判定基準を決める。第4.6節に挙げた既存の `nameConfidence`（`confirmed` / `inferred`）に揃えるか、`build-unit-list.sh` に見つかった別の `confidence`（`high` / `medium`）に揃えるか、まったく新しい値域にするかを検討し、**決めた理由を設計判断として記録する**（記録先は第7節参照）
2. 「何をもって `confirmed`（または採用した値域の高信頼側）とし、何をもって `inferred`（または低信頼側）とするか」の判定基準を明文化する。**値域を決めるだけでは足りない。**基準が無ければ書く人によって値がばらつく
3. 出典参照と確信度を `画面基本設計書.md` §6「画面遷移の業務文脈」へ足す。列の追加位置・書式は既存の実測プレースホルダの書式に揃える
4. `nodes[]` / `edges[]`（`edges[].sourceRef` と `edges[].confidence` を含む）用の入力データを、`画面基本設計書.md` §6 の行から組み立てられるように生成器側の抽出処理を実装する
5. 欄を足したテンプレートから画面遷移図が実際に生成されることを実測で確かめる（`build-detail-page.sh --page transition`）

## 10. 完了条件

この節はいったん次の経緯で改訂していた。いったんは確信度の欄を足す前提で見送り、完了条件から外した。画面遷移図だけが確信度という新しい概念を要求しており、確信度は値そのものではなく値の確からしさを表す判断のメタ情報であるため、設計書だけを読む再実装の工程が「推定」とされた辺をどう扱うかという新しい運用判断を生むと考えたためである。

その後の実測で、この除外の前提が崩れた。入力の仕様が出典参照に文書参照形式を既に許しており、画面基本設計書 §6「画面遷移の業務文脈」が遷移元・遷移先・契機の3列を既に持つため、確信度の欄を足さずに矢印を作れた。確信度は空のままとし、値を捏造していない。表示に使われていないことを実描画で確認した。よって過去の懸念（確信度の欄の新設が情報アクセス規律を崩す）は生じない。この結果、完了条件を関連図3種へ戻す。
