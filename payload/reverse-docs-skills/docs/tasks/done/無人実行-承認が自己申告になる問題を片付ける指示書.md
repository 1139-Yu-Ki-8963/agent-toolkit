# 無人実行-承認が自己申告になる問題を片付ける指示書

**状態**: 着手できる
**優先度**: 中
**前提**: なし
**元の指摘**: なし

## この指示書は何か

一覧生成スキルはユーザーへの確認を経て承認を記録する設計だが、担当者として無人実行すると対話ができず、承認済みの印（`approvedByUser: true`）が自己申告として記録される問題を片付ける。`AIセットアップ検証の未決課題を片付ける指示書.md` の見送り5件の1件として起票する。

## なぜ必要か

`generating-screen-list-for-reverse-docs/SKILL.md` の Step 6（71行目）は「検出戦略宣言を作成し、AskUserQuestionで承認を取る」と定め、完了条件に `approvedByUser: true` を求める。`validate-manifest.sh` はこの値が `true` であることを機械検査する（`strategy.approvedByUser == true` の検査）。

しかし headless（無人実行）時は AskUserQuestion が使えない。他の分岐（92行目のセルフチェックゲート、106行目の検出失敗時）は headless=true 時の代替フローが明記されているのに対し、Step 6 だけは headless 時にどう `approvedByUser` を決めるかの記述が無い。実態としては、無人実行の担当者（Claude）が自分で `true` と書き込むしかなく、これは「ユーザーが承認した」という値の意味と食い違う。この食い違いが記録に残らないと、後から `approvedByUser: true` を見た人が「人間が確認済み」と誤読し、実際には無人実行時に自己判断で通過させた戦略を無検証のまま前提にしてしまう。

## やること

### いま実装できる緩和策

`strategy` オブジェクトへ、無人実行時にAIが自己判断で `approvedByUser: true` とした場合を区別するフィールドを追加する。既存の `approvedByUser: true/false` の意味（`validate-manifest.sh` が検査する値）は変更しない。新設フィールド名は `approvalMode`（値: `"user"` = 対話でユーザーが承認 / `"self"` = 無人実行時にAI自身が妥当性を確認して進めた）とする。

- `.claude/skills/generating-screen-list-for-reverse-docs/SKILL.md` の Step 6 完了条件へ、headless=true 時は `approvalMode: "self"` を戦略JSONへ追記して進める旨を追記する
- `.claude/skills/generating-screen-list-for-reverse-docs/references/screen-detection.md` の戦略JSON例に `approvalMode` フィールドの例を追加する
- `generation-engine/scripts/unit-list/validate-manifest.sh` の検査2（strategy-承認）は `approvedByUser` の値のみを見る現行仕様を変えない（`approvalMode` は情報記録のみで合否に影響させない。理由は「決めていないこと」参照）

### 限界を明示する記述の追加

`.claude/skills/generating-screen-list-for-reverse-docs/SKILL.md` の Step 6 の記述直後へ、次の趣旨の1文を追加する。

> headless=true（無人実行）時は AskUserQuestion による対話承認ができないため、`approvedByUser` はAI自身が調査結果の妥当性を確認したうえでの自己判断となる。この場合 `approvalMode: "self"` を併記し、対話承認と区別できる状態を保つ。

### 判断が変わる条件

無人実行の枠組み自体（`orchestrating-ai-development-setup` の headless モード）が対話的な中間承認を挟めるように変更された場合、この限界は解消する。その場合 `approvalMode` フィールドは不要になるが、既存の記録との後方互換のため廃止せず残す。

## 触らない範囲

- `generation-engine/scripts/unit-list/validate-manifest.sh` の検査2（strategy-承認）の合否判定そのもの（`approvedByUser` の値のみで判定する現行仕様は変えない）
- 他の一覧生成スキル（API・テーブル・バッチ・帳票・外部連携・機能）への同様の対応（本指示書は画面一覧生成スキルのみを対象とする。他スキルへの展開は別途判断が必要なため対象外とする）
- `orchestrating-ai-development-setup` の headless モードの動作そのもの

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| `approvalMode` を `validate-manifest.sh` の合否判定に含めるか | 含めない。情報記録のみとする。理由: 合否判定に含めると、既に生成済みの過去のマニフェスト（`approvalMode` フィールドを持たない）が新たに不合格になり、後方互換を壊す | 過去のマニフェストを全件再生成する方針が決まった場合、合否判定に含めることを検討する |
| 画面一覧以外の6スキル（API・テーブル・バッチ・帳票・外部連携・機能）へも同じフィールドを展開するか | 展開しない。まず画面一覧1件で実運用を確認してから広げる | 画面一覧での運用に問題が無いと確認できた場合、他スキルへ横展開する |
