# 設計書へ疑似コードと戻り値を足す指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

7 種別（API・テーブル・バッチ・帳票・外部連携・画面・メッセージ）の詳細設計書テンプレートへ、疑似コードの節と戻り値を書く場所を追加する。`実装契約定義.md` へその扱いを追記し、疑似コードへ実際のコードが混ざっていないかを見る検査を作って第 1 層の機械検証（`run-layer-machine-checks.sh`）へ載せる。

## なぜ必要か

指摘は 3 点だった。実測すると 1 点だけが直っている。

**疑似コード — 7 種別すべてで 0 件。欄そのものが無い。**

```
API詳細設計書.md / テーブル定義書.md / バッチ詳細設計書.md / メッセージ定義書.md /
外部連携詳細設計書.md / 帳票詳細設計書.md / 画面詳細設計書.md
すべて 疑似コード=0（`LC_ALL=C grep -c '疑似コード' <file>` で確認済み）
```

**ロジック設計 — 直っている。** 指摘の時点では API と画面の 2 種だけだったが、いまはテーブル・バッチ・帳票・外部連携の 4 種が `## §3 ロジック` を持つ（`delivery-payload/templates/リバース検証/<種別>/` 配下の各テンプレートで確認済み）。中身は 3 つの表（3.1 分岐・3.2 繰り返し・3.3 判定表）である。

**戻り値 — API に 1 箇所あるだけ。** `API詳細設計書.md` の `## §4 処理フロー` → `### 4.2 内部呼び出し` の表が「呼び出し先 / 引数 / 戻り値 / 根拠」という列見出しを持つのみで、API 自身のレスポンス（`## §3 レスポンス`）の戻り値を記録する場所ではない。他の 6 種は「戻り値」の語が 0 件。データ定義のほうは帳票・バッチ・テーブル・外部連携の 4 種が `## §6 データ定義` と `## §4 入出力の値`（要素名・区分・名前・型・有効な範囲・空値の許容・初期値・桁と精度の 8 列）を持つ。

抜けた原因は、`delivery-payload/references/実装契約定義.md` が定めた項目が 3 つ（ファイルと関数・型定義・依存）だけで、疑似コードと戻り値がそこに入っていなかったことである。先行指示書（`docs/tasks/done/実装契約の置き場を全種別で揃える指示書.md`）は「実装契約の置き場を全種別で揃える」という題で対象を 3 項目に限っており、判定 15 件すべてを満たしながら指摘の一部（疑似コード・戻り値）を落としていた。

放置すると、次の往復検証・規約レビューで同じ指摘が繰り返され、実装契約の 3 項目が揃っていることをもって「対応済み」と誤認され続ける。

## やること

### 決めた線引き

ユーザーの指示は「設計書にコードをそのまま書くのは禁止だが、例として一部を載せるのは可」である。これを次の形に落とす。

**疑似コード**は、分岐と繰り返しの入れ子だけを日本語で書く。言語の構文・変数名・API 名を使わない。

```
良い: 利用者の権限が管理者なら、締め日を過ぎた明細も対象へ含める
悪い: if (user.role === 'admin') { includeClosedItems() }
```

実際のコードを貼ることを禁じる。原本の行を指したい場合は §実装契約の「ファイルと関数」から辿らせる。

**戻り値**は、既存の `§入出力の値` の表に「区分＝戻り値」の行として書く。新しい表を足さない。型・有効な範囲・空値の許容は既存の列で表す。`§入出力の値` を持たない API と画面は、「決めていないこと」節で既定を定める。

### 作業

1. `§入出力の値` を持つ 4 種別（帳票・バッチ・テーブル・外部連携）の詳細設計書の雛形へ、疑似コードの節を `## §3 ロジック` の直後（`## §4 入出力の値` の直前）に足す。節番号は既存の `## §4` 以降をすべて 1 つずつ繰り下げる（`## §4 入出力の値` → `## §5`、`## §5 エラー処理` → `## §6`、`## §6 データ定義` → `## §7`、`## §7 実装契約` → `## §8`、`## §8 要確認事項一覧` → `## §9`）
2. API（`## §4 処理フロー` の直後）と画面（`## §6 データフロー` の直後）にも、同じ考え方で疑似コードの節を足す。挿入位置以降の節番号をすべて 1 つずつ繰り下げる
3. `§入出力の値` を持たない API と画面へ、戻り値をどこへ書くかを「決めていないこと」節の既定に従って決め、該当の節へ「区分＝戻り値」の行、または同等の記載欄を足す
4. `実装契約定義.md` へ、疑似コードと戻り値の扱い（本節「決めた線引き」の内容）を書き足す
5. 疑似コードにコードが書かれていないかを見る検査を `generation-engine/scripts/tests/` 配下へ新規に作る。言語の構文らしい記号（`{` `}` `=>` `===` `;`）や、`if (`・`for (`・`function ` の並びを、疑似コードの節の本文から検出する。`--self-test` を持たせる
6. その検査を第 1 層の集約（`generation-engine/scripts/verification/run-layer-machine-checks.sh`）が動的に拾えることを `--list` で確認する。個別の配線作業（同スクリプトの改修）は、対象が `--self-test` を引数処理する `.sh` であれば自動的に拾われるため、通常は追加の配線作業を要しない。拾われない場合は `generation-engine/scripts/tests/check-verification-wiring.sh` を実行し、原因を確認したうえで対応する

**「メッセージ定義書.md」は `## §` の見出しを 1 つも持たない。** 他の 6 種と構造が違うため、対象に含めるかを担当者が決める。既定は「含めない」とし、理由を記録させる。

## 完了の判定

すべて機械で確かめられる形にする。

1. 帳票・バッチ・テーブル・外部連携・API・画面の 6 種別の詳細設計書の雛形に疑似コードの節がある（`LC_ALL=C grep -c '疑似コード'` が 6 件すべてで 1 以上）
2. メッセージ定義書.md を対象に含めたかどうかが「決めていないこと」の既定どおり記録されている（含めない場合は `LC_ALL=C grep -c '疑似コード' delivery-payload/templates/リバース検証/プロジェクト共通/メッセージ定義書.md` が 0 のままでよい）
3. 疑似コードの節が、帳票・バッチ・テーブル・外部連携では `## §3 ロジック` の直後（`## §4 入出力の値` の直前）にある。API では `## §4 処理フロー` の直後にある。画面では `## §6 データフロー` の直後にある（`grep -n '^## ' <file>` の出力で見出しの並びを確認する）
4. 挿入した節ぶんの節番号の繰り下げが全箇所で一貫している（`grep -n '^## §' <file>` で番号の連番が欠番・重複なく並ぶことを確認する）
5. 帳票・バッチ・テーブル・外部連携・API・画面の 6 種別で戻り値を書く場所がある（`LC_ALL=C grep -c '戻り値'` が 6 件すべてで 1 以上）
6. 戻り値のために新しい表を足していない（帳票・バッチ・テーブル・外部連携の `§入出力の値` の列数が 8 列のまま。`sed -n '/^## §.* 入出力の値/,/^## /p' <file>` で見出し行の列数を数えて確認する）
7. `delivery-payload/references/実装契約定義.md` に「疑似コード」と「戻り値」の両方の語が存在する（`LC_ALL=C grep -c '疑似コード\|戻り値' delivery-payload/references/実装契約定義.md` が 1 以上）
8. 疑似コードにコードが混ざっていないかを見る検査が `generation-engine/scripts/tests/` 配下に実在する
9. その検査の `--self-test` が終了コード 0 を返す
10. その検査が `run-layer-machine-checks.sh --list` の出力に現れる
11. 見本（`generation-engine/samples/`）を対象とする既存の自己テスト（`generation-engine/scripts/tests/test-portal-conventions.sh` 等、テンプレート変更前から実行していたもの）が、テンプレート変更前と同じ合否を保つ。見本自体を再生成するかどうかは `.claude/rules/always/portal/template-sample-sync/rule.md` の対象表に従う（同表は `delivery-payload/templates/リバース検証/` 配下を同期の対象外と定めており、本指示書が変更するテンプレートは全件この配下にあるため、見本の再生成は不要である）
12. `check-design-doc-section-consistency.sh --self-test` が終了コード 0 を返す（節構成の検査を壊していないこと）

## 触らない範囲

- `§ロジック` の 3 つの表（3.1 分岐・3.2 繰り返し・3.3 判定表）の列構成
- `§実装契約` の 3 項目（ファイルと関数・型定義・依存）
- `§入出力の値` の 8 列（区分列へ「戻り値」を値として書き足すことは対象。列そのものの追加・削除・改名は対象外）
- 節の番号の付け方（`§N` の形式）。番号を繰り下げることは対象内だが、`§N` を `N.` や別の記法へ変えることは対象外
- `generation-engine/samples/` 配下の生成済みサンプル（対象テンプレートは同期対象外のため、そもそも再生成の必要が無い）
- 雛形そのものの中身を除く、他のすべてのファイル

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| メッセージ定義書を対象に含めるか | 含めない。他の 6 種と構造が違い、§ の見出しを 1 つも持たない | メッセージ定義書にも処理の分岐が現れると分かったとき |
| 疑似コードを独立した節にするか、§ロジック の小節にするか | 独立した節にする。§ロジック の 3 つの表は構造を列挙するもので、順序の表現を持たない | 節が増えすぎて読み手が追えなくなったとき |
| API と画面で戻り値をどこへ書くか | API は `## §3 レスポンス` の `### 3.1 正常系の構造` の表へ「区分＝戻り値」相当の行、または同表の既存列（項目・型・常に存在・意味・根拠）をそのまま戻り値の記載として使う。画面は `## §6 データフロー` 配下に「区分＝戻り値」の行を持つ小節を新設する | 既存の節の意味と食い違うと分かったとき |
| 疑似コードの検査を新規スクリプトにするか、既存スクリプトへ追加するか | 新規スクリプトにする。既存の `generation-engine/scripts/tests/` 配下の検査はいずれも別の観点（節構成・列数・網羅等）を持ち、疑似コードの中身（コード混入の有無）を見る検査とは判定式が異なる | 疑似コードの検査と同じ判定式を持つ既存スクリプトが見つかったとき |

## この指示書の位置づけ

実装契約の置き場を揃える先行指示書は完了として片付いたが、その完了条件が指摘 3 点のうち 2 点（疑似コード・戻り値）を対象に含めていなかったため、指摘が再現した。対象を疑似コードと戻り値の 2 点に絞り、7 種別（うち対象外の可能性があるメッセージ定義書を除く 6 種別）へ横断して足す作業として、先行指示書とは独立した粒度で切った。
