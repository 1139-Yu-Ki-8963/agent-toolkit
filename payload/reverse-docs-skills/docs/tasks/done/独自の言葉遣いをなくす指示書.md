# 独自の言葉遣いをなくす指示書

**状態**: 着手できる
**優先度**: 中
**前提**: なし
**元の指摘**: なし

## 1. この指示書は何か

スキルの定義とガイドで使われている、この場所でしか通じない言葉を洗い出し、誰にでも分かる言葉へ置き換える。あわせて、同じことが再び起きないように、使ってはいけない言葉を機械で見つける仕組みを作る。

この指示書は指示であり、実装ではない。読んだ担当者が作業する。

## 2. なぜ必要か

### 2.1 実際に使われている言葉

スキルの定義（`SKILL.md`）とガイド（`references/guide.html`）を走査した。次の言葉が出ている。

| 言葉 | 出ているファイル数 |
|---|---|
| 派生 | 62 |
| 束 | 54 |
| 正本 | 46 |
| 差し戻し | 45 |
| 委任 | 33 |
| 検収 | 32 |
| 台帳 | 28 |
| 起こす | 19 |

| 盲検 | 9 |
| 発火 | 9 |
| 降格 | 5 |
| 昇格 | 5 |
| 束ねる | 3 |
| 起票 | 2 |

一般の開発の現場で使う言葉ではないものが混じっている。「封印」「盲検」「起票」「発火」は、この場所の言い回しである。

### 2.2 実際の文面

```
封印済みfactsと共通文書から画面詳細設計書を執筆する執筆役。
TRIGGER when: facts封印後の設計書執筆・再執筆。
SKIP: facts抽出（→extracting-unit-facts-from-code）、盲検検証（→rebuilding-screen-unit-from-docs）
```

```
## Phase 1: preflight（起動引数検収・スキャフォールディング）
```

初めて読む人は、次を推し量ることになる。

- 「封印」とは何をすることか。取り消せるのか
- 「盲検」とは何を見ないことか
- 「検収」は誰が誰に対して行うのか
- 「preflight」と「スキャフォールディング」は日本語にならないのか

### 2.3 なぜ困るか

**読み手はこの場所を知らない。** スキルの定義は納品先で AI エージェントが読み、ガイドは納品先のエンジニアが読む。どちらもこの場所の言い回しを知らない。

言葉が分からないと、次が起きる。

| 起きること | 例 |
|---|---|
| 手順を誤って解釈する | 「封印」を「変更禁止」と解釈し、後から直せないと思い込む |
| 探せない | 「台帳」を探すが、実物のファイル名は別の語で書かれている |
| 使うのをやめる | 意味の取れない語が続くと、読むこと自体を諦める |

### 2.4 いまある仕組みでは足りない

使ってはいけない語を機械で見つける仕組みは既にある。`delivery-payload/references/rule-banned-terms.json` である。

**ただし対象が規約の本文だけで、語も 7 語しかない。** スキルの定義とガイドは対象外である。

用語をまとめた文書（`docs/guides/用語集.md`）もあるが、17 行しかない。上に挙げた 16 語のうち、そこに載っているものはごく一部である。

## 3. やること

### 3.1 対象を洗い出す

スキルの定義とガイドの全文から、**この場所でしか通じない言葉**を洗い出す。

洗い出しの手順を次とする。

1. `.claude/skills/*/SKILL.md` と `.claude/skills/*/references/guide.html` の全文を対象にする
2. 2.1 に挙げた 16 語を起点に、実際の使われ方を読む
3. **起点の 16 語以外にも同種の語がないかを探す。** 探し方は担当者が決めてよいが、**16 語だけを直して終わりにしない**
4. 洗い出した語それぞれについて、次を記録する

| 記録すること | 内容 |
|---|---|
| 語 | その言葉 |
| 出ている場所 | ファイルと行 |
| 何を指しているか | その場所で実際に何を意味しているか |
| 判定 | 置き換える／残す |
| 残す場合の理由 | なぜその語でなければならないか |

記録の置き場は `docs/tasks/` とし、この指示書とは別のファイルにする。

### 3.2 置き換えるかどうかを判定する

**判定の基準を次とする。**

> この場所を知らない人が、その語を初めて見て意味を取れるか。取れないなら置き換える。

**残してよいのは次の 2 つだけである。**

| 残してよい場合 | 例 |
|---|---|
| 一般の開発で広く使われている | 「コミット」「テスト」「レビュー」 |
| その場所で意味を説明している | 初出のところに「〜のこと」と 1 行の説明がある |

**「短いから」「言い換えると長くなるから」は残す理由にならない。** 長くなっても意味が取れるほうがよい。

### 3.3 置き換える

判定で「置き換える」となった語を、誰にでも分かる言葉へ置き換える。

置き換えの案を次に示す。**そのまま使う必要はない。実際の使われ方を読んで決めること。**

| 置き換える語 | 案 |
|---|---|
| 封印 | 確定（変更しない状態にすること） |
| 盲検 | 原本を見ない検証 |
| 検収 | 受け取りの確認 |
| 起票 | 記録する／登録する |
| 発火 | 実行される／動く |
| 昇格・降格 | 扱いを上げる・下げる |
| 周 | 回 |
| 束 | まとまり |
| 起こす | 作る／書く |
| preflight | 実行前の確認 |
| スキャフォールディング | 雛形の展開 |

**「正本」「派生」「台帳」は、置き換えるか説明を添えるかを慎重に決める。** これらは仕組みの中核を指しており、置き換えると別の意味になりうる。

### 3.4 使ってはいけない語の仕組みを広げる

`delivery-payload/references/rule-banned-terms.json` の対象と語を広げる。

| 広げる先 | いまの対象 | 広げた後 |
|---|---|---|
| 対象 | 規約の本文だけ | 規約の本文・スキルの定義・ガイド |
| 語 | 7 語 | 3.2 の判定で「置き換える」となった語すべて |

**語ごとに、置き換え先を持たせること。** 見つけたときに「これをこう直す」と伝えられる形にする。

いまの形（語の並びだけ）では置き換え先を持てないため、形を変える必要がある。**既にある 7 語の扱いを壊さないこと。**

### 3.5 見つける仕組みを作る

広げた語の一覧に照らして、スキルの定義とガイドを走査する検査を作る。

置き場は `generation-engine/scripts/` とし、名前は既にあるスクリプトの付け方に揃える。

**検査は次を出すこと。**

- 見つかった語
- ファイルと行
- 置き換え先

**この検査を、機械検証の集約（`generation-engine/scripts/verification/run-layer-machine-checks.sh` が集めるもの）に載せる。** 載せる方法は既にある検査に揃える。

### 3.6 用語をまとめた文書を実態に合わせる

`docs/guides/用語集.md` は 17 行しかない。3.1 で洗い出した語のうち「残す」と判定したものを、この文書へ載せる。

**載せるのは残す語だけである。** 置き換えた語は載せない。載せると、使ってよい語だと誤解される。

## 4. 完了の判定

次のすべてを満たすこと。

1. 洗い出しの記録が `docs/tasks/` にあり、語ごとに 5 項目（語・場所・意味・判定・理由）が埋まっている
2. 記録に、起点の 16 語以外の語も含まれている
3. 「残す」と判定した語すべてに、残す理由が書かれている
4. 「置き換える」と判定した語が、スキルの定義とガイドから 0 件になっている
5. `rule-banned-terms.json` の対象に、スキルの定義とガイドが含まれる
6. `rule-banned-terms.json` の語それぞれが、置き換え先を持つ
7. 既にある 7 語が、いまと同じように働く
8. 走査する検査が `generation-engine/scripts/` にあり、`--self-test` が終了コード 0 を返す
9. その検査が、見つかった語・場所・置き換え先の 3 つを出す
10. その検査が機械検証の集約に載っており、実行される
11. その検査を全スキルへ実行し、見つかる語が 0 件になる
12. `docs/guides/用語集.md` に、残すと判定した語が載っている
13. 置き換えた語が `docs/guides/用語集.md` に載っていない
14. スキルガイドの体裁の検査（`generation-engine/scripts/skill-guide/apply-guide-style.sh --self-test`）が終了コード 0 を返す

### 実装判断: check-internal-jargon.sh の誤検知修正

新設した検査は、当初「束」の検出が136件あったが、実際には「収束」「未収束」という正当な複合語の一部を誤って拾っていた（例:「上限3回で収束しなければ」が「束」として検出される）。原因は `grep -F` による単純な文字列一致が、複合語の内部に含まれる部分文字列も区別なく拾うためである。

この環境の `grep` は BSD grep（FreeBSD由来）であり、`-P`（PCRE の後読み・後読み）を持たない。そのため「束」を含む既知の安全な複合語（収束・未収束・束ねる）を、走査の直前に「束」の文字を一切含まないプレースホルダ（`SAFEWORD`）へ一時的に置き換えてから `grep -n -F "束"` する方式で対処した（`grep_term_matches()` 関数、「束」の場合のみ分岐）。**この一時置換は複合語を誤って拾わないための意図的な回避策であり、次に触る人が「余計な前処理」と見て取り除くと同じ誤検知が再発する。取り除く前に、この節と該当箇所のコメントを読むこと。**

同様の衝突は「起こす」でも発生した。「採録→書き起こす」の置換（`57bf9e0f`）により生まれた「書き起こす」「書き起こし」「未書き起こし」が、後から追加した禁止語「起こす」を誤って含んでしまうためである。これは自分自身が行った置換が新しい誤検知の原因になった事例であり、「束」と同じ SAFEWORD 方式で対処した（`14a3cd8d`）。

加えて、enum 値（`status=封印済み` 等の実装が実際に返す値）は、指示書5節の「コードの中の識別子」に相当するため走査対象から除外する必要があった。当初は `status=X` の直接代入形とバージョン付き値（`Xv0`等）だけを除外していたが、実際には Markdown のテーブル形式での enum 列挙（`` | status | `封印済み` \| `中断` | ``）と HTML のタグ表示（`<span class="tag pass">封印済み→...`）という2つの追加の形が残存していた。これらはバッククォート囲み、または `class="tag ...">` 直後という機械的に判定可能な特徴を持つため、この2条件を除外ロジックへ追加して対応した（`14a3cd8d`）。

誤検知の修正の経緯（件数の推移）: 136件（束の誤検知）→ 31件（束を修正後、残りは封印のenum） → 0件（enumのテーブル・タグ表示も除外後）。
