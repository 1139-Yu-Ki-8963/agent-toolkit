## この指示書は何か

`generation-engine/scripts/tests/test-badge-nav-contrast.cjs`（および同種の構造を持つ`test-matrix-header-compact-layout.cjs`）は、`data-theme`属性の切替直後、わずか数フレーム（実測で4 rAFフレーム程度）しか待たずにコントラスト比を計測する。対象要素（`.pt-nav-item`等）に`transition: all 0.12s`が指定されている場合、切替直後の計測はCSSトランジションの中間値を拾うことがあり、同一コード・複数回実行でも実測値が大きくばらつく（2.48〜5.01の範囲で観測）。この揺れは検査対象の実装の正しさとは無関係な、検査スクリプト自体の計測タイミングの欠陥である。

## なぜ必要か

## 追加の実測（2026-08-19）

対策（遷移の完了を待つ購読と祖先をたどる走査）が入ったあとも、集約の中でこの検査は落ちる。落ちるのは明るい配色の 2 件だけである。

```
FAIL: light配色 / サイドバー通常項目の文字: コントラスト比 1.90（基準 4.5）
FAIL: light配色 / サイドバー現在地項目の文字: コントラスト比 1.07（基準 4.5）
```

色の値を突き合わせ、比を計算した。

| 状態 | 通常項目 | 現在地項目 |
|---|---|---|
| 正しい組み合わせ（明るい配色の文字と明るい配色の背景） | 6.65 | 12.27 |
| 明暗が単純に混ざった場合（明るい文字と暗い背景） | 2.49 | 1.18 |
| **検査の報告** | **1.90** | **1.07** |

**報告値は、明暗が単純に混ざった値よりさらに低い。** つまり文字色と背景のどちらか一方だけが切り替わった状態ではない。**両方が遷移の途中の補間値を取っている。**

使った色の値は次のとおりで、テンプレート（`delivery-payload/templates/tokens.css`）と見本（`generation-engine/samples/project-portal/一覧/API一覧/API一覧.html`）で一致することを確認した。見本が古いという原因は否定できる。

```
明るい配色  --sub: #4B5A70   --navon: #102A43   --panel3: #F7F9FC   --accent-soft: rgba(2,132,199,0.10)
暗い配色    --sub: #A8B3C3   --navon: #EAF6FF   --panel3: #141A23   --accent-soft: rgba(76,194,255,0.17)
```

### 番号と件数は落ちない

同じ親要素の中で、番号（`.pt-nav-num`）と件数（`.pt-nav-count`）は 4.5 以上で合格している。落ちるのは文字だけである。

文字は `.pt-nav-item` 自身の `color: var(--sub)` を使い、番号と件数は別のトークンを使う。**`.pt-nav-item` には `transition: all 0.12s` が付いており、番号と件数には付いていない。** 対策が待つ対象に `.pt-nav-item` が入っているかを確かめる。

### 次に確かめること

1. 対策の `collectTransitioningAncestors` が `.pt-sidebar` を走査の対象に含めているか。サイドバーの背景（`--panel3`）が遷移する場合、その完了も待つ必要がある
2. CSS 変数の切り替えそのものが `transitionend` を発火するか。変数の値の変更は要素の `transition` を経由せず、`transitionend` が飛ばない場合がある。飛ばなければ購読は空振りし、タイムアウトの側に落ちる
3. タイムアウトの余裕（`marginMs`）が 0.12 秒の遷移に対して足りているか

### 待ち方の実装を読んで分かったこと（2026-08-19）

待ち方は次の形である。

```
document.documentElement.setAttribute('data-theme', <配色>);
await Promise.all(<9要素>.map(el => waitForElementSettle(el, 200)));
```

`waitForElementSettle` は要素と祖先の遷移の時間を測り、`transitionend` を購読して全部が終わるのを待つ。終わらない場合は「遷移の時間 + 余裕 200 ミリ秒」で打ち切る。

ここから 3 つの疑いが出る。

#### 疑い 1: 購読が属性の変更より後にある

`setAttribute` を実行した**あとで** `transitionend` を購読する。遷移は属性の変更で始まるため、購読を登録するまでの間に終わったものはイベントを取りこぼす。取りこぼすと購読は空振りし、打ち切りの側に落ちる。

ただし打ち切りは「120 + 200 = 320 ミリ秒」であり、遷移の 120 ミリ秒より長い。**打ち切りに落ちても最終の値になるはずである。** この疑いだけでは報告値を説明できない。

#### 疑い 2: 測る順序が明るい配色から始まる

配色は明るい・暗いの順で測る。**明るい配色が最初である。**

初期状態は `data-theme` を持たず、システムの設定に従う。**システムが暗い表示なら、最初の測定は暗い色から明るい色への切り替えの直後になる。** 2 番目（暗い配色）は、既に明るい配色が確定した状態からの切り替えとなり、条件が異なる。

実際、落ちるのは明るい配色の 2 件だけであり、暗い配色は 6 件すべて合格している。**順序の非対称と、落ちる側の非対称が一致する。**

#### 疑い 3: 終わったことの判定がプロパティを見ない

`transitionend` を受けたとき、どのプロパティの遷移が終わったかを見ずに、要素が一致すれば「終わった」と扱う。`transition: all` は色・背景・枠線など複数のプロパティで別々にイベントを発火する。**最初の 1 つで完了と判定すると、文字色の遷移が終わる前に測ってしまう。**

`transition: all 0.12s` は全プロパティが同じ時間のため同時に終わるはずだが、発火の順序に差があれば取りこぼす。

### 確かめる手順

疑い 2 を先に確かめる。**手数が最も少なく、当たれば決定的である。**

1. 測る順序を暗い配色から先に変えて実行し、落ちる側が入れ替わるかを見る
2. 入れ替われば、原因は順序（初期状態からの最初の切り替え）である
3. 入れ替わらなければ疑い 1 と 3 へ進む

疑い 2 が当たった場合の直し方は、**最初の測定の前に捨て測りを 1 回入れる**ことである。属性を設定して待ち、その結果を使わずにもう一度同じ配色で測る。初期状態からの切り替えを測定の対象から外す。

## 原因の確定（2026-08-19 実測）

**疑い 2（測る順序）が原因である。** 実測で確かめた。

測る順序を暗い配色から先に入れ替えて実行したところ、**終了コード 0・不合格 0 件**になった。

| 測る順序 | 通常項目の文字 | 現在地項目の文字 | 結果 |
|---|---|---|---|
| 明るい → 暗い（現行） | 1.90 | 1.07 | 不合格 2 件 |
| 暗い → 明るい（入れ替え） | 4.97 | 12.28 | 不合格 0 件 |

現在地項目の 12.28 は、色の値から計算した理論値 12.27 とほぼ一致する。**配色は正しく、最初の測定だけが途中の値を拾っていた。**

初期状態は `data-theme` を持たず、システムの設定に従う。最初の測定はその状態からの切り替えの直後になる。2 回目以降は確定した状態からの切り替えのため、待ち方が正しく働く。

### 直し方

**順序の入れ替えで直してはならない。** 入れ替えると、こんどは暗い配色が最初になり同じ問題が移るだけである。実測でたまたま合格したのは、暗い配色の比が元々高い（8.70・11.34）ため、途中の値でも基準を超えたからである。

正しい直し方は、**最初の測定の前に捨て測りを 1 回入れる**ことである。

1. 測定に入る前に、いずれかの配色を設定して待つ
2. その結果を使わずに捨てる
3. そのうえで明るい・暗いの順に本来の測定を行う

これで初期状態からの切り替えが測定の対象から外れ、どちらの配色も「確定した状態からの切り替え」になる。

### 疑い 1 と 3 の扱い

疑い 1（購読の位置）と疑い 3（完了の判定がプロパティを見ない）は、**この原因の確定によって直ちに直す必要は無くなった。** ただし理屈としては残る欠陥であり、捨て測りを入れたあとも同種のばらつきが出る場合に見直す。
