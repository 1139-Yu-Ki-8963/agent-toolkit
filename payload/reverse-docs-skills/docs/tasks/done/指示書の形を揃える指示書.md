# 指示書の形を揃える指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## 1. この指示書は何か

`docs/tasks/` に置く 17 件の指示書の形を、`.claude/rules/always/tasks/instruction-format/rule.md` が定める必須 8 節と冒頭 3 行へ揃える。この指示書自身も同じ形式に従う。

この指示書は指示であり、実装ではない。読んだ担当者が作業する。

## 2. なぜ必要か

実測した状態は次のとおりである。この数字を担当者は前提として使ってよい。

| 実測したこと | 結果 |
|---|---|
| 指示書の数 | 17 件 |
| 節が 8 件の標準の形 | 11 件 |
| 標準から外れる | 6 件 |
| 「完了の判定」の節を持たない | 3 件 |
| 冒頭 3 行（状態・優先度・前提）を持つ | 0 件 |

**標準から外れる 6 件の内訳**

```
未着手の指示.md                    18 節
関連図の内製化の指示書.md            13 節
スキル実装計画.md                   13 節
自己設計書整備の指示書.md            11 節
独自の言葉遣いをなくす指示書.md        9 節
人とAIの分担を定める指示書.md          7 節
```

**節の数だけでは判定できない実例**: `納品物置き場の再構成構想.md` は節の数こそ 8 だが、節の名前が必須の 8 つと 1 つも一致しない（背景・project-setup・命名の判断・実測で判明した事実・着手前に必要な調査・移設の方法を先に決める必要がある・実施の順序・見送った判断）。数を数えるだけの検査ではこの食い違いを見逃す。名前も見る検査が要る。

**「完了の判定」の節を持たない 3 件**

```
関連図の内製化の指示書.md      → 「## 10. 完了条件」という名前で持つ（節名が違う）
自己設計書整備の指示書.md      → 「## 8. 完了条件」という名前で持つ（節名が違う）
納品物置き場の再構成構想.md    → 相当する節を 1 つも持たない
```

前の 2 件は中身自体は完了条件を書いているが、規約が定める節名「完了の判定」と一致しない。検査スクリプトは節名の一致を見るため、このままでは不合格になる。

**定めていない状態の語**

`スキル実装計画.md` の「対応の記録」表に「対象外」が 6 件ある。規約はこの語を認めるが、理由を「確かめた内容」へ書くことを求める。実測したところ、この 6 件は「検証の対象がこのリポジトリに無く、ここでは検証しない」という理由が既に書かれている。担当者は他の指示書で「対象外」を使う場合に、同じように理由が書かれているかを確かめる。

これらの食い違いを放置すると、指示書を引き受けた担当者は毎回「この指示書はどの状態か」「完了をどう確かめるか」を自分で読み解く作業から始めることになる。読み解きに要する手間は指示書の数だけ繰り返される。

## 3. やること

### 作業1: 全 17 件へ冒頭の 3 行を足す

各指示書の表題の直後へ次を置く。

```
**状態**: <着手できる / 設計から始める>
**優先度**: <最高 / 高 / 中 / 低>
**前提**: <先に完了している必要がある指示書の名前。無ければ「なし」>
```

値の決め方は次のとおりとする。

| 何を見るか | 何を書くか |
|---|---|
| 「やること」が具体の作業まで書けている | 状態は「着手できる」 |
| 「やること」が方針の段階で止まっている | 状態は「設計から始める」 |
| 「決めていないこと」にユーザーしか決められない事項がある | その事項に既定を添えて書き直し、状態は「着手できる」とする |
| 「他の指示書との関係」に先行が書いてある | 前提にその名前を書く |

優先度は、既にタスクリストに付けた値をそのまま使う。

```
最高: 検証の結果を信用できるようにする指示書.md /
      対象プロジェクトの実態を反映させる指示書.md
高:   検査を規則と対応させる指示書.md /
      配布物だけでポータルを再現できるようにする指示書.md /
      実装契約の置き場を全種別で揃える指示書.md
中:   上記以外のすべて（この指示書が対象とする 17 件から、
      移す 1 件を除いた残り全部）
```

### 作業2: 標準から外れる 6 件の節を揃える

対象は「未着手の指示.md」「関連図の内製化の指示書.md」「スキル実装計画.md」「自己設計書整備の指示書.md」「独自の言葉遣いをなくす指示書.md」「人とAIの分担を定める指示書.md」の 6 件である。節を消すのではなく、必須 8 節のどれかへ中身を入れる。

**内容の種類による寄せ先（一般則）**

| 今ある節 | どこへ入れるか |
|---|---|
| 背景と経緯 / 課題の原文（引用）/ 現状の事実（実測値） | なぜ必要か |
| 着手順序と依存関係 / 段階的に進める | やること |
| 完了条件 / 注意事項 | 完了の判定 |
| 禁止事項 | 触らない範囲 |
| 過去の決定との関係 | 他の指示書との関係 |
| この指示書の目的 | この指示書は何か |

**個別の対応**

- `未着手の指示.md`: 17 件の個別の課題見出し（`## ER図にカラム一覧付きのテーブル詳細タブを追加する` 等）は、いずれも作業項目である。「やること」直下の `###` 小見出しへ格下げして集約する。既存の「## 対応の記録」節はそのまま活かす。個別の課題ごとに書かれている完了の条件は、まとめて新設する「完了の判定」節へ移す
- `スキル実装計画.md`: `## Stage 1: ...` から `## Stage 6: ...` までの段階見出しは、「やること」直下の `###` 小見出しへ格下げする。「## 完了の判定」と「## 対応の記録」は既に規約どおりの名前を持つため、そのまま残す
- `自己設計書整備の指示書.md`: 「## 8. 完了条件」を「## 完了の判定」へ改名する。中身の条件文は変えない
- `関連図の内製化の指示書.md`: 「## 10. 完了条件」を「## 完了の判定」へ改名する。中身の条件文は変えない
- `独自の言葉遣いをなくす指示書.md`: 「## Phase 1: preflight（起動引数検収・スキャフォールディング）」は作業の一段階であり、「やること」直下の `###` 小見出しへ格下げする
- `人とAIの分担を定める指示書.md`: 必須 8 節のうち「他の指示書との関係」が丸ごと欠けている。本文の「触らない範囲」節に既にある「3.3 の判断基準（`検査を規則と対応させる指示書.md` の 3.4 が定める）」という言及を抜き出し、新設する「他の指示書との関係」節へ移す

### 作業3: 完了の判定を持たない 1 件を移す

`納品物置き場の再構成構想.md` は「完了の判定」に相当する節を 1 つも持たず、構想の段階であり機械で終わりを判定できない。`docs/design/` へ移す。

`スキル実装計画.md` は「## 完了の判定」の節を既に持つため、移す対象に含めない。作業2の対象として `docs/tasks/` に残す。

移す前に、他の指示書からの参照を確かめる。

```
LC_ALL=C git grep -n 'plans/納品物置き場の再構成構想' -- ':!docs/tasks/納品物置き場の再構成構想.md'
```

実測した結果、このパスによる参照は `docs/tasks/` の外側を含めて 0 件である（終了コード 1）。ただし `docs/ledgers/` に名前だけの言及がある可能性があるため、担当者は移した後に次のコマンドでパスを持つ言及だけを洗い出し、見つかれば新しい置き場へ書き換える。

```
LC_ALL=C git grep -rn '納品物置き場の再構成構想'
```

移した先で、指示として引き受けられる形（完了の判定を書ける形）になった時点で `docs/tasks/` へ戻す。

### 作業4: 対応の記録の節を全件へ足す

規約が定める形の記録の節を、まだ持たない指示書へ足す。

```
## <番号>. 対応の記録

### 判定の充足状況

| 判定 | 確かめる手段 | 状態 | コミット | 確かめた内容 |
|---|---|---|---|---|
| 1. <判定の内容> | `<コマンド>` | 未着手 | — | — |

### 判断の記録

| 何を決めたか | 選んだもの | 選んだ理由 | 覆すと何が変わるか |
|---|---|---|---|
```

既に持つ指示書（`スキル実装計画.md`・`未着手の指示.md`・`自己設計書整備の指示書.md`・`関連図の内製化の指示書.md`）は、状態の語が「未着手」「対応中」「完了」「対象外」の 4 つに収まっているかを確かめる。`スキル実装計画.md` の「対象外」6 件は、確かめた内容の欄に理由が書かれていることを実測済みである。他の指示書で「対象外」を使う場合も同じように理由を書く。

### 作業5: 「決めていないこと」へ既定を足す

全 17 件の「決めていないこと」の節を、表の形へ直す。列は次の 3 つとする。

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|

**既定の無い事項を残してはならない。** 既定が無いと担当者がそこで止まる。既定は、判断の材料が多いほう・手戻りが小さいほうを選ぶ。

該当が無い指示書は「なし」と 1 行だけ書く。空欄にしない。

### 作業6: 検査を通す

```
bash .claude/rules/always/tasks/instruction-format/check-instruction-format.sh
```

不合格が 0 件になるまで直す。この検査スクリプトが本指示書の時点で存在しない場合は、先に規約側の担当者へ作成を依頼してから実行する。

## 4. 完了の判定

次のすべてを満たすこと。

1. `docs/tasks/` の全 `*.md` が必須の 8 節を持つ（検査スクリプトが不合格 0 件）
2. 全件が冒頭の 3 行（状態・優先度・前提）を持つ
3. 状態の値が `着手できる` / `設計から始める` のいずれかである
4. 優先度の値が `最高` / `高` / `中` / `低` のいずれかである
5. `納品物置き場の再構成構想.md` が `docs/tasks/` に存在しない
6. `納品物置き場の再構成構想.md` が `docs/design/` に存在する
7. `LC_ALL=C git grep -n 'plans/納品物置き場の再構成構想'` が `docs/tasks/` 配下で 0 件を返す
8. 全件が対応の記録の節を持つ
9. 記録の状態の語が定めた 4 つ（未着手 / 対応中 / 完了 / 対象外）以外を含まない
10. `check-instruction-format.sh` が終了コード 0 を返す
11. 全件の「決めていないこと」が、既定の列を持つ表または「なし」の 1 行である
12. `docs/tasks/` 配下に「判断待ち」の見出しが 0 件（`LC_ALL=C git grep -c '判断待ち' -- docs/tasks/` で確認）

## 5. 触らない範囲

## 6. 決めていないこと

次は、作業する担当者が決める。迷ったら既定を選び、選んだ結果を「判断の記録」へ残す。

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 中優先度の指示書のうち、どれを先に引き受けるか | ファイル名の `LC_ALL=C sort` の昇順で先頭から引き受ける | 先に引き受けた指示書が他の指示書の前提になっていると分かったとき |
| 移す 1 件（`納品物置き場の再構成構想.md`）を `docs/design/` のどのフォルダへ置くか | `docs/design/` の直下へ置く | 既存の並びに同じ性質の文書が集まるフォルダがあり、そこへ置くほうが探しやすいとき |
| `未着手の指示.md` の個別課題を「完了の判定」へ集約する粒度 | 1 対 1 で書き写す | 書き写した結果が 30 件を超え、判定が読み切れなくなったとき |

## 7. 他の指示書との関係

この指示書は他の 17 件すべてに先行する。形が揃うまで、引き受けた側は毎回同じところで止まる。

## 8. この指示書の位置づけ

指示書の中身ではなく形だけを扱う。中身の作業は各指示書が持つ。形と中身を 1 つの指示書で扱うと、どちらも中途半端に終わる。
