# 上限まで2秒しかない検査に余裕を持たせる指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

第1層の集約が `build-portal.sh --self-test` を走らせるとき、打ち切りまでの余裕が
2 秒しかない。実行環境の負荷が少し変われば結果が変わる。余裕を持たせる。

## なぜ必要か

2026-08-24 に実測した。

    build-portal.sh --self-test の所要時間      122 秒（パイプ無し・出力破棄）
    集約が使う上限（既定）                       120 秒
    上限を実時間へ直したときの打ち切り点          約 124 秒

集約は `timeout` コマンドを持たない環境向けに、0.2 秒ごとの生存確認で上限を
測っている。この見張りには誤差があり、名目の上限より実時間のほうが長くなる。
同日の実測では次のとおりだった。

    名目 10 秒 → 実時間 11 秒
    名目 30 秒 → 実時間 31 秒

誤差は約 3〜10% である。名目 120 秒なら実時間は約 124 秒になる。

**つまり build-portal は打ち切り点の 2 秒手前で通っている。**現に集約では
`[PASS]` として完走しているが、負荷が少し上がれば `[TIMEOUT]` へ落ちる。

落ちた場合、集約は失敗として数える。**検査の内容には何の問題も無いのに、
第1層の合否が実行環境の混み具合で変わる。**合格を数える意味が失われる。

同じ理由で既に 8 本が上限の宣言（`declared_long_running_timeout`）へ登録
されている。登録済みの上限は 150〜300 秒である。build-portal は登録されて
いない。

## やること

1. `build-portal.sh` を上限の宣言へ登録し、既定より長い上限を与える
2. 登録した上限は、実測の所要時間に対して十分な余裕を持つ値とする
3. 集約を走らせ、build-portal が `[PASS]` のまま、失敗が 0 本のままであることを
   確かめる

## 完了の判定

1. `build-portal.sh` が上限の宣言（`declared_long_running_timeout`）へ登録されている
2. 登録した上限が 200 秒以上である
3. 集約の自己テストが終了コード 0 を返す
4. `bash .claude/rules/always/tasks/instruction-format/check-instruction-format.sh` が不合格 0 件

判定 1・2 は、所要時間そのものを測ると 122 秒かかり、片付けの判定器の時間の
上限を超えるため機械で確かめられない。かわりに、余裕を持たせる手立てを
実際に取ったかどうかを確かめる。

## 触らない範囲

- build-portal が検査する内容そのもの。ケースを減らさない
- 他の 8 本の上限の宣言の値
- 見張りの仕組み（0.2 秒ごとの生存確認）そのもの

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 余裕の持たせ方 | 上限の宣言へ登録して上限を延ばす。所要時間を縮める道は、内訳が多数のケースへ薄く分散しており 1 箇所を直しても届かないと実測で分かっている | 所要時間を上限の 80% 以下へ縮められる見込みが立ったとき |
| 与える上限の値 | 200 秒。既に登録済みの 8 本のうち最も短い値と揃える。実測 122 秒に対して 60% 以上の余裕を持つ | 実測が 160 秒を超えるようになったとき |
| 見張りの誤差そのものを直すか | 直さない。誤差は 3〜10% で、上限に十分な余裕があれば影響しない | 誤差が 20% を超える実測が出たとき |

## 他の指示書との関係

`docs/tasks/宣言で除外された長時間の検査を走らせる指示書.md` は、宣言で
除外されて走っていない検査を走る形にする作業だった。その目的は達成済みで、
宣言済み長時間は 0 本である。同指示書は「集約の宣言の仕組み」を触らない範囲と
定めているため、上限の宣言への登録は同指示書では扱えない。本指示書が引き継ぐ。

同指示書の判定 1（build-portal が 120 秒以内）は、所要時間を縮める道が
実測で行き止まりと分かり「対象外」で止まっている。本指示書は所要時間ではなく
余裕を扱うため、判定が重ならない。

## この指示書の位置づけ

検査の結果が実行環境の混み具合で変わる状態を解消する作業である。
検査の内容には触れず、打ち切りまでの余裕だけを広げる。
