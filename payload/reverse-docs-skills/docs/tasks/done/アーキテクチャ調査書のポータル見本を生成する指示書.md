# アーキテクチャ調査書のポータル見本を生成する指示書

**状態**: 着手できる
**優先度**: 中
**前提**: なし
**元の指摘**: 1-265

## 1. この指示書は何か

既存の汎用ポータル生成器を使ってアーキテクチャ調査書の見本HTMLを作り、納品物一覧と見本の派生物台帳を現物へ一致させる指示書である。

## 2. なぜ必要か

アーキテクチャ調査スキルは `docs/design/common/アーキテクチャ調査書.md` だけを出力し、見本Markdownも実在する。一方、カタログは人が読むポータル成果物として `project-portal/foundation/アーキテクチャ調査書.html` を宣言する。このHTMLが見本に無いため、納品物一覧は `evidenceSource: none` の状態判定に従い「未生成」「判定の材料が無い」と報告する。

HTML生成器が無いわけではない。`build-portal.sh` は `surveyDoc` を既知の基盤文書に含め、共通Markdown文書を基盤HTMLへ変換する既存経路を持つ。基盤設計書、共通設計書、データ設計書、メッセージ定義書、UI共通設計書も、作成スキルはMarkdownだけを出力し、この汎用変換を通してカタログのHTMLを作る。同じ先例へ合わせ、カタログやスキルの契約を変えず、欠けた見本HTMLを生成するのが最小の修正である。

ただし、実物の見本を出力先にして `build-portal.sh` を実行すると、対象HTMLの生成前に、prepared inputが無い既存3ページ（技術スタック・環境構築手順・用語辞書）をstaleと検知して終了コード1になる。別ページの正本入力をこの課題で追加せずに既存の汎用変換を使うため、worktree内の一時コピーにだけ `run_prepared_detail_pages_self_test`（techstack/env/glossaryのprepared inputを作る自己テスト）と同じ正規schemaのprepared inputを置いて生成する。

## 3. やること

1. `tmp="$(mktemp -d "$PWD/.tmp-1-265.XXXXXX")"` でworktree内に一時ディレクトリを作り、`case "$tmp" in "$PWD"/.tmp-1-265.*) ;; *) exit 1 ;; esac` で返されたパスの接頭辞を検証する。
2. `cp -R generation-engine/samples "$tmp/sample"` で見本を複製し、`mkdir -p "$tmp/sample/docs/manifests/detail-pages"` でprepared inputの置き場を作る。
3. `build-portal.sh` の `run_prepared_detail_pages_self_test`（techstack/env/glossaryのprepared inputを作る自己テスト）と同じ正規schemaを使い、`techstack-page-data.json` と `env-page-data.json` を `jq -n` で `$tmp/sample/docs/manifests/detail-pages` に作る。`semantic-glossary-sample-page-data.json` は `jq` で `generatedAt` を `2026-08-18T00:00:00Z` に固定し、`$tmp/sample/docs/manifests/detail-pages/glossary-page-data.json` として作る。
4. `bash generation-engine/scripts/build-portal.sh . "$tmp/sample" "$tmp/sample/project-portal" --project-name sample-project --generated-at 2026-08-18T00:00:00Z --catalog delivery-payload/references/portal-catalog.json` を実行する。第1引数の `.` は対象リポジトリ、第2・第3引数は一時コピーの文書ルートとポータル出力先である。終了コード0と `$tmp/sample/project-portal/foundation/アーキテクチャ調査書.html` の実在を確認する。
5. `cp "$tmp/sample/project-portal/foundation/アーキテクチャ調査書.html" generation-engine/samples/project-portal/foundation/アーキテクチャ調査書.html` で、生成した対象HTMLだけを実物へ反映する。
6. Step 1と同じ `case` で `$tmp` の接頭辞を再検証し、`git clean -nd -- "$tmp"` で削除対象を確認してから `git clean -fd -- "$tmp"` で削除する。`find "$PWD" -maxdepth 1 -name '.tmp-1-265.*' -print` が空であることを確認する。
7. `bash generation-engine/scripts/build-deliverable-inventory.sh generation-engine/samples generation-engine/samples/project-portal/foundation/納品物一覧.html generation-engine/samples/docs/納品物一覧.md` を実行し、Markdown版とHTML版の納品物一覧を再生成する。
8. すべての生成後に `bash generation-engine/scripts/check-derived-drift.sh record generation-engine/samples` を実行し、`generation-engine/samples/derived-fingerprints.json` を更新する。
9. 完了の判定を実行し、生成物と派生物台帳を同じコミットへ含める。

## 7. 他の指示書との関係

「規約とフローの対応見本を生成する指示書」と同じく、納品物一覧が報告した見本の欠落を補う。ただし今回は個別生成器ではなく、共通Markdownを変換する既存の汎用ポータル生成器を使う。納品物一覧の状態判定やカタログを再設計した既存指示書の成果は変更しない。

## 8. この指示書の位置づけ

Markdown正本から人向けポータルHTMLを作る既存経路を見本へ適用し、60件の納品物一覧をすべて「出力あり」にそろえる作業である。新しい生成器の追加や一覧の検査緩和ではなく、既存の宣言、出力レイアウト、汎用変換を一致させる。

### 判断の記録

| 何を決めたか | 選んだもの | 選んだ理由 | 覆すと何が変わるか |
|---|---|---|---|
| 欠落の直し方 | 既存の汎用ポータル生成器でHTMLを作る | `build-portal.sh` が `surveyDoc` を共通Markdown変換へ明示的に含め、宣言済みのHTML出力先へ変換できるから | カタログをMarkdownへ変える場合はポータル上の人向け成果物と他の基盤文書の扱いが変わる |
| stale検知を保った生成方法 | 見本の一時コピーに `run_prepared_detail_pages_self_test`（techstack/env/glossaryのprepared inputを作る自己テスト）と同じ正規schemaのprepared input 3件を置き、生成した対象HTMLだけを実物へ反映する | 実物へ別3ページのprepared inputを追加する場合は課題範囲とコミット内容が広がり、一時コピーが不要になる |
| 進行担当の見立て | MarkdownとHTMLの不一致は正しいが、HTML生成器が無いという点は現行コードでは採用しない | 汎用生成器の実装と、同じ形の基盤設計書・共通設計書など5件の先例を実測したから | 汎用生成器が使えない場合は個別生成器の新設かカタログ変更が必要になる |
| カタログの扱い | `architecture-survey` のHTML登録を維持する | `output-layout.json` の `surveyDoc` と `build-portal.sh` の変換先がカタログの宣言と一致するから | Markdownを直接一覧へ載せる場合はカタログ探索とポータル表示の契約を再設計する必要がある |
| `evidenceSource: none` の意味 | HTMLが無いときに対象なしを証明するマニフェストを持たない宣言として維持する | 一覧生成器は最初にHTML実在を調べ、無い場合だけこの値から「未生成」「判定の材料が無い」を返すから | 証拠形式を追加する場合は宣言、生成器、自己テストの変更が必要になる |
