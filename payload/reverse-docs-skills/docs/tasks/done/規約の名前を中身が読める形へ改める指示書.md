# 規約の名前を中身が読める形へ改める指示書

**状態**: 着手できる
**優先度**: 中
**前提**: `検査を規則と対応させる指示書.md`（先に実施しないと検査の名前を二度変えることになる）
**元の指摘**: なし

**着手の順序: `docs/tasks/検査を規則と対応させる指示書.md` を実施した後に着手する。** 先に名前を変えると、検査の名前を二度変えることになる。

## 1. この指示書は何か

納品先へ配る規約 27 件の名前を、中身が読み取れる形へ改める。あわせて語尾を揃え、名前が中身を表すことを求める規則を配る命名規約へ足す。

この指示書は指示であり、実装ではない。読んだ担当者が作業する。

## 2. なぜ必要か

### 2.1 語尾が揃っていない

27 件すべてが「守るべき決まりを書いた文書」であるのに、語尾が 6 種類ある。

| 語尾 | 件数 | 例 |
|---|---|---|
| 規約 | 13 | コーディング規約・命名規約・Git運用規約 |
| 要件 | 5 | セキュリティ要件・性能要件・監視要件 |
| 方針書 | 2 | テスト方針書・レビュー方針書 |
| 規則 | 2 | 計算規則・業務規則 |
| 定義 | 1 | 用語定義 |
| 制約 | 1 | 状態遷移の制約 |

読み手は「要件と規約は違うものか」「方針書は守らなくてよいのか」を考えることになる。守るべき度合いが語尾で変わるなら、その差は定義されているべきである。定義されていない。

### 2.2 名前から中身が読み取れない

名前を見ても何が書かれているか分からないものがある。

| 名前 | 実際の中身 | 読み取れるか |
|---|---|---|
| 破壊的操作の安全規約 | ファイルを上書きする前に読む | 読み取れない |
| ポータル保守規約 | 生成した HTML を直接編集しない | 「ポータル」が何か分からない |
| セッション管理規約 | 完了報告に実行結果を添える | 読み取れない |
| AI設定資産の管理規約 | 定義は docs に置き、派生は生成物として扱う | 「設定資産」が何か分からない |
| 定型運用の規約 | 手順を文書に固定し、間隔と失敗時の扱いを書く | 「定型運用」が何か分からない |

読み手は納品先のエンジニアと AI エージェントであり、このリポジトリの語彙を知らない。

### 2.3 配る命名規約が自分自身に適用されていない

配る命名規約は 4 つの規則を持つ。

| 規則 | 内容 |
|---|---|
| 不透明な省略を使わない | 読み手が展開できない省略を使わない |
| 通し番号を識別子にしない | 連番だけの名前を付けない |
| 動くものは動詞から始める | 処理を行う関数と実行するファイルの名前を動詞から始める |
| 表記の形式を対象ごとに固定する | 対象ごとに大文字と小文字の使い分けを 1 つに固定する |

規約の名前はこの規則に照らして書かれていない。加えて、**名前が中身を表すことを求める規則そのものが無い。** 4 つはいずれも形式の話であり、名前と中身の対応を求めていない。

自分が定める規則を自分が守っていない状態は、規約全体の説得力を損なう。

## 3. やること

### 3.1 語尾を 1 つに揃える

27 件の語尾を 1 つに揃える。

**どの語尾にするかは担当者が決める。** 決めるときは次を満たすこと。

- 守るべき決まりを書いた文書であることが読み取れる
- 27 件すべてに無理なく付けられる
- 親カテゴリの名前（7 件）と混同しない

揃えた語尾を、規約の書き方を定める文書へ記す。置き場は `delivery-payload/references/規約定義と派生生成の設計.md` とする。

### 3.2 中身が読み取れない名前を改める

2.2 に挙げた 5 件を含め、27 件すべてを見直す。

**判定の基準を次とする。**

> この規約を知らない人が名前だけを見て、そこに書かれている規則を 1 つでも言い当てられるか。

言い当てられない名前を改める。改めた名前は、その規約が持つ規則から導く。

**「破壊的操作の安全規約」は、名前だけでなく中身も食い違っている。** 題名は取り消しの効かない操作を扱うと言うが、規則は「上書きの前に既存を読む」の 1 件である。**この 1 件は別の指示書（`docs/tasks/人とAIの分担を定める指示書.md`）の対象と重なるため、そちらの結論を待ってから名前を決める。**

### 3.3 名前が中身を表すことを求める規則を足す

配る命名規約へ、次の趣旨の規則を 1 件足す。

> 名前から、それが何であるかが読み取れること。名前だけを見た人が中身を推し量れない名前を付けない。

**規則の文言・内容・根拠・検査の 4 列は、既にある規則の書き方に揃えて自分で書く。** 上は趣旨であり、そのまま写す文ではない。

検査の列には、機械で判定できる範囲を書く。**判定できないなら `不可:` と理由を書く。** 名前と中身の対応は意味の判断を含むため、機械で判定できない可能性が高い。無理に判定できることにしない。

### 3.4 名前の変更を全体へ追従させる

名前を変えると、次が追従を要する。**すべてを洗い出してから変えること。**

| 追従先 | 何が入っているか |
|---|---|
| `delivery-payload/references/rule-taxonomy.json` | `title` の値 |
| `delivery-payload/templates/rules/tool-defined/*.md` | 各ファイルの 1 行目の題名 |
| `delivery-payload/references/portal-catalog.json` | ポータルのカードの題名 |
| 各規約の本文 | 他の規約を参照する記述 |
| `generation-engine/samples/` 配下 | 生成済みの見本 |
| `.claude/rules/scoped/portal/category-grouping/rule.md` | カテゴリの構成の記述 |

**ファイル名（`<key>.md`）と分類の鍵（`key`）は変えない。** 変えると参照が広範囲に壊れる。変えるのは表示に使う題名だけとする。
