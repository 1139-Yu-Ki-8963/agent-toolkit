## この指示書は何か

配線漏れの検査が、集約の実際の収集結果を見ずに判定している。集約の収集条件が広がったことで両者が一致しなくなり、検査が誤って「漏れなし」と報せる。検査の側を集約の収集条件と一致させる。

## なぜ必要か

配線漏れの検査（`generation-engine/scripts/tests/check-verification-wiring.sh`）は、判定を次の2つで行う。

- 検査1: 「検査として実行できるファイル」を自前で列挙し、集約の一覧と突き合わせる
- 検査2: `--self-test` を持たないものを警告する。ただし本文に `集約の対象外` の文字列があれば警告しない

**どちらも、集約が実際に何を拾っているかを見ていない。** 検査1は自前の列挙、検査2は文字列の一致で判定する。

2026-08-19、集約の収集条件へ「名前が `test-*.sh` に一致するものを拾う」経路が加わった（`run-layer-machine-checks.sh` の `list_targets` 106 行目）。この経路は `--self-test` の有無を一切見ない。**検査の側はこの経路を知らないままである。**

実測（2026-08-19・コミット `37e803b7` 時点）は次のとおりである。

| 観点 | 実測 |
|---|---|
| 集約が拾う件数 | 160 件 |
| 検査1が突き合わせる母集合 | 125 件 |
| `--self-test` を持たないが名前で拾われるもの | 7 件（すべて集約に含まれる） |
| `集約の対象外` の目印を持つもの | 13 件 |
| そのうち実際には集約に含まれるもの | **9 件** |
| 検査2の警告 | **0 件** |

**警告 0 件は「配線漏れが無い」ことを意味しない。** 7 件は目印によって警告から外れているだけで、実際には全件が集約に載っている。検査は「漏れなし」と報せるが、その判定は集約の実際の収集結果を一度も見ていない。

放置すると次が起きる。集約の収集条件を変えるたびに、検査の側が知らないまま乖離が広がる。**検査が「漏れなし」と報せ続けるため、乖離そのものに誰も気付かない。** 検査があることが、かえって誤った安心を与える。

## やること

1. 検査1が突き合わせる母集合を、集約の実際の収集結果と一致させる
2. 検査2の目印の判定を、実際の収集結果と突き合わせる形にする。目印を持ちながら集約に含まれるものは、別の警告として報せる
3. 自己テストへケースを足す。ケースの名前は `収集条件-集約と一致` とする

## 完了の判定

1. 配線漏れの検査の自己テストが終了コード 0 で終わる
2. 自己テストの出力に `収集条件-集約と一致` のケースが現れる
3. 検査1が突き合わせる母集合の件数が、集約が拾う件数と一致する
4. 集約が拾う件数が 160 件を下回らない

## 触らない範囲

- 集約の収集条件（`list_targets`）そのもの。**検査の側を合わせる**
- 集約が終了コード 2 を判定不能として区別する分岐
- 目印の文字列（`集約の対象外`）。文字列の改名は別の指示書が扱う
- 目印を持ちながら集約に含まれる 9 件そのもの。報せる形にするところまでが本件である
- `docs/tasks/` 配下
- `delivery-payload/` 配下

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 母集合の揃え方 | 集約の `--list` を呼んで得た一覧をそのまま母集合にする。収集条件を写して二重に持たない | 集約を呼ぶと所要時間が延びて判定器の上限（既定 120 秒）を超えると分かった場合は、収集条件だけを共通の関数へ切り出し、両者から読む形へ変える |
| 目印を持ちながら集約に含まれるものの報せ方 | 新しい警告として報せる。既存の警告と混ぜない。件数も別に数える | 警告の種類が増えて読めなくなると分かった場合は、既存の警告へ理由を添える形にする |
| 9 件をこの周で直すか | 直さない。検査が報せる形にするところまでを範囲とする。報せた結果の扱いは、報せられてから決める | 9 件のうちに、集約に載っていること自体が誤りのものがあると分かった場合 |
| 検査2が対象とするファイル名のパターン | いまのまま（`check-*.sh`・`validate-*.sh`・`test-*.sh`）を保つ | 集約の収集条件が別の名前のパターンを加えたと分かった場合 |

## 他の指示書との関係

`検査の除外の目印を内容が読める形へ改める指示書`（`docs/tasks/` 直下）は目印の**文字列**の改名を扱い、本件は目印の**判定の中身**を扱う。順序の依存はない。

`走っていない検査を集約へ載せる指示書`（`docs/tasks/` 直下）の作業で集約の収集条件が広がったことが、この乖離の直接の原因である。あちらの作業自体は正しく、乖離は検査の側が追従していないために生じている。

## この指示書の位置づけ

検査の側だけを扱う。集約の収集条件は触らない。両方を同時に変えると、どちらが原因で件数が変わったのかを後から読み取れなくなる。乖離を報せる形にすることと、報せられた 9 件をどうするかは別の判断であり、前者だけを本件の範囲とする。
