# 実装契約の置き場を全種別で揃える指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

**優先度: 高。詳細設計書がその目的を果たせない状態である。**

## 1. この指示書は何か

設計書の 7 種別について、実装水準の記述(どのファイルのどの関数か・型は何か・何に依存するか)を書く場所を揃える。

この指示書は指示であり、実装ではない。読んだ担当者が作業する。

## 2. なぜ必要か

### 2.1 実装契約を持つのは 7 種別のうち 2 種別だけ

雛形を実測した結果である。

| 種別 | 実装契約に当たる節 | 中の項目 |
|---|---|---|
| API | `§9 実装契約` | ファイルと関数・型定義・依存 |
| 画面 | あり | 同じ 3 つ |
| バッチ | **無い** | — |
| 帳票 | **無い** | — |
| 外部連携 | **無い** | — |
| テーブル | **無い** | — |
| 機能 | **無い** | 詳細設計の段階自体を持たない |

### 2.2 5 種別の詳細設計書の構成

バッチ・帳票・外部連携の 3 種別は、同じ 7 章の構成を持つ。

```
§1 構成要素      §2 処理の定義    §3 ロジック(分岐・繰り返し・判定表)
§4 入出力の値    §5 エラー処理    §6 データ定義    §7 要確認事項一覧
```

`§6 データ定義` の中身は種別ごとに違う。

| 種別 | §6 の中身 |
|---|---|
| バッチ | 扱うデータ構造・コミットの単位・排他の制御・件数と実行時間の目安 |
| 帳票 | 出力項目の編集・集計・改ページと明細の繰り返し |
| 外部連携 | 電文の項目定義・変換の処理・タイムアウトと冪等性 |

**いずれも扱うデータの話であり、実装の契約ではない。** どのファイルのどの関数が処理するか、型は何か、何に依存するかを書く場所が無い。

### 2.3 なぜ困るか

**詳細設計書は、それだけを読んで実装できる状態を作るための文書である。**

API と画面は「どのファイルのどの関数か」「型は何か」「何に依存するか」を書ける。**残る 5 種別は書けない。**

同じ「詳細設計書」という名前を持ちながら、達せられる水準が種別によって違う。読み手は種別ごとに何が書いてあるかを覚える必要がある。

### 2.4 機能は段階そのものを持たない

機能(feature)は、配置の定義で詳細設計の段階が空と定められている。

これ自体は意図されたものである。根拠が 2 か所に書かれている。

> 機能の `detail` が空配列である理由は、機能設計書が集約設計書であり、構成要素の個別仕様は各構成要素の設計書を正とするためである。機能そのものの詳細設計という段階を持たない。

**ただし、実装水準の記述に出会ったときにどこへ書くかが定まっていない。** 機能設計書の雛形は 11 章を持つが、そのすべてが業務の記述である。

ある対象プロジェクトで、機能ごとに実装水準の記述を持つ文書が 9 件存在し、置き場を失った実例がある。

## 3. やること

### 3.1 実装契約の項目を定める

**まず、実装契約として何を書くかを定める。**

API と画面が持つ 3 つを出発点とする。

| 項目 | 内容 |
|---|---|
| ファイルと関数 | どのファイルのどの関数が処理を担うか |
| 型定義 | 扱う値の型 |
| 依存 | 何に依存するか |

**種別ごとに追加が要るかを判断する。** たとえばバッチなら起動の引数、帳票なら出力の形式が要るかもしれない。**判断した結果を記録すること。**

### 3.2 5 種別へ実装契約の節を足す

バッチ・帳票・外部連携・テーブルの 4 種別の詳細設計に当たる文書へ、実装契約の節を足す。

**節の名前と位置は API に揃える。** API は `§9 実装契約` を `§10 要確認事項一覧` の直前に置いている。

**既存の章の番号を動かす場合は、その旨を記録すること。**

### 3.3 機能の扱いを決める

機能は詳細設計の段階を持たない。**実装水準の記述をどう扱うかを決める。**

| 方針 | 内容 |
|---|---|
| 含める | 機能設計書の中に実装契約の節を設ける |
| 含めない | 機能には持たせず、構成要素の設計書へ書くことを手順へ明示する |

**選んだ理由を記録すること。**

「含める」を選ぶ場合、既存のスキル定義が「同じ内容を機能設計書と個別設計書の両方へ書くことを禁止する」と述べている。**重複しない境界を定める必要がある。**

「含めない」を選ぶ場合、**構成要素をまたぐ実装(複数の構成要素で共有するデータ構造など)の置き場を決める必要がある。**

### 3.4 執筆の手順を揃える

各種別の設計書を書くスキルの手順に、実装契約の節へ何を書くかを足す。

**API の手順を参照し、他の種別も同じ粒度で書けるようにする。**

### 3.5 配置の定義へ理由を書く

配置の定義(`delivery-payload/references/design-unit-layout.json`)の機能の項目に、詳細設計の段階が空である理由と、実装水準の記述の扱いを短く書く。

**いまはこの定義だけを読んでも、なぜ空なのかが分からない。** 理由は別の 2 つの文書に書かれており、この定義からは辿れない。

### 3.6 揃っていることを機械で確かめる

全種別の詳細設計に当たる文書が実装契約の節を持つことを、機械で確かめる形にする。

**新しい仕組みを作らない。** 既にある自己検査へ足す。足す先は `generation-engine/scripts/scaffold-design-unit.sh` の自己検査、または設計書の節構成を検査するスクリプトとする。

機能を「含めない」と決めた場合は、**機能だけが対象外であることを検査の中に明示する。**

## 4. 完了の判定

次のすべてを満たすこと。

1. 実装契約として書く項目が定められ、記録されている
2. 種別ごとの追加の要否が判断され、記録されている
3. バッチ・帳票・外部連携・テーブルの 4 種別が実装契約の節を持つ
4. その節の名前と位置が API に揃っている
5. 既存の章の番号を動かした場合、その旨が記録されている
6. 機能の方針が「含める」「含めない」のどちらかで決まり、理由が記録されている
7. 「含める」を選んだ場合、構成要素の設計書と重複しない境界が定まっている
8. 「含めない」を選んだ場合、実装水準の記述をどこへ書くかが手順に書かれている
9. どちらの方針でも、構成要素をまたぐ実装の記述の扱いが書かれている
10. 各種別の設計書を書くスキルの手順に、実装契約の節へ何を書くかが書かれている
11. 配置の定義から、機能の詳細設計が空である理由に辿り着ける
12. 全種別の詳細設計に当たる文書が実装契約の節を持つことを確かめる検査がある
13. 機能を対象外とした場合、その旨が検査の中に明示されている
14. その検査が既にある自己検査に足されており、終了コード 0 を返す
15. 各種別を含む疑似入力で生成し、実装契約の節が実在することを確かめている

## 5. 触らない範囲

- API と画面の既存の実装契約の節(他がこれに揃える)
- 各種別の既存の章の内容(節を足すだけ)
- 機能に詳細設計の段階を作ること(配置の定義の `detail` を空でなくすること)
- 既に生成済みの文書の移設
- `.claude/rules/` 配下(このリポジトリ自身の規約であり、配る資産とは別)

## 6. 決めていないこと

次は、作業する担当者が決める。

1. **種別ごとに実装契約へ追加する項目**(バッチの起動の引数、帳票の出力の形式など)
2. **機能を「含める」か「含めない」か**
3. **構成要素をまたぐ実装の記述の扱い**
4. **配置の定義へ理由を書く形**
5. **検査を足す先**(配置のスクリプトの自己検査か、節構成の検査か)

## 8. この指示書の位置づけ

詳細設計書は、それだけを読んで実装できる状態を作るための文書である。ところが 7 種別のうち実装契約を書けるのは 2 種別だけで、残る 5 種別は書く場所を持たない。同じ名前の文書が、種別によって達せられる水準が違う。全種別で揃え、揃っていることを機械で確かめ続ける。
