## この指示書は何か

テーブル・バッチ・帳票・外部連携の4種別の詳細設計書テンプレートへ、種別の判定材料を書く欄を追加する。あわせて `delivery-payload/references/doc-extraction.json` の該当4種別へ `kindMapping` 宣言を追加し、`generation-engine/scripts/portal-input/build-manifests-from-docs.sh` がそれを読んで `kind` を解決できるようにする。

## なぜ必要か

改善課題1-66（設計文書から作るマニフェストが種別を判定せず、常に要確認へ回される）の対応で、APIはfrontmatterの `method`・`path` から `kind`（`validate-manifest.sh` が求める値域: `endpoint` 等）を解決できたが、table・batch・report・externalの4種別は同じ解決ができなかった。

原因は判定不能ではなく、判定に使える情報を書く欄がテンプレートに無いことである。4種別それぞれの `kind` の値域は次のとおりで、いずれも原本コードを読めば人間が判別できる情報のはずである。

| 種別 | `kind` の値域（`validate-manifest.sh` 定義） |
|---|---|
| table | table・view・migration |
| batch | scheduled・triggered |
| report | template・generator |
| external | client・webhook |

featureは `validate-manifest.sh` の値域検査の対象外のため、この現象自体が生じない。放置すると、設計文書のみからマニフェストを組み立てる経路（`build-portal.sh --build-manifests-from-docs`）で、この4種別の項目が一覧の「要確認」表へ回され続け、一覧のリンクが出ない状態が続く。

## やること

1. table・batch・report・externalの4種別の詳細設計書テンプレート（`delivery-payload/templates/リバース検証/` 配下）のfrontmatterへ、種別の判定材料を書く欄を1つずつ追加する
   - table: 物理テーブルかビューかマイグレーションかを示す欄（例: `table_subkind`）
   - batch: スケジュール起動か外部トリガー起動かを示す欄（例: `batch_trigger_type`）
   - report: テンプレート方式か動的生成方式かを示す欄（例: `report_engine`）
   - external: 自分から呼ぶ側か webhook で受ける側かを示す欄（例: `external_direction`）
   - 具体的なキー名は着手時に決めてよい（「決めていないこと」参照）
2. `delivery-payload/references/doc-extraction.json` の該当4種別へ、`kindMapping`（必須フィールドと値の対応）を追加する。1-66で追加済みのapiの `kindMapping` を参考にする
3. `generation-engine/scripts/portal-input/build-manifests-from-docs.sh` の1-66実装（`kindMapping` を読んでkindを解決する分岐）が、この4種別でも動くことを確認する（コードの変更は基本的に不要な想定だが、`unresolvable.unitKey`・`unresolvable.sourceFile` の代替値行はkindを解決しない不変条件が引き続き効くことを確かめる）
4. self-testへ検査を追加し、4種別それぞれで欄を埋めた場合にkindが解決されること、埋めない場合はunresolvedのままであることを確認する

### 自己テストへ足すケースの名前

判定 4・5 の確かめる手段は、`generation-engine/scripts/portal-input/build-manifests-from-docs.sh --self-test` の出力に次の 2 行が現れることを見る。実装のときは、この名前どおりのケースを自己テストへ足す。名前が 1 文字でも違うと判定が通らない。

```
[PASS] 検査8: 種別の判定材料の欄を埋めた場合にkindが解決される
[PASS] 検査9: 種別の判定材料の欄を埋めない場合はkindがunresolvedのまま
```

既存の自己テストは 9 件で、いずれも `[PASS] 検査N: <説明>` の形をとる。同じ形に揃える。

## 完了の判定

1. `grep -c "table_subkind\|batch_trigger_type\|report_engine\|external_direction" delivery-payload/templates/リバース検証/*/*.md` が4件以上を返す（4テンプレートすべてに欄が追加されている）
2. `jq -e '.kinds.table.kindMapping and .kinds.batch.kindMapping and .kinds.report.kindMapping and .kinds.external.kindMapping' delivery-payload/references/doc-extraction.json` が true を返す
3. `bash generation-engine/scripts/portal-input/build-manifests-from-docs.sh --self-test` が終了コード0で終わる
4. 欄を埋めた合成フィクスチャで生成したマニフェストの `units[0].kind` が `unresolved` 以外になる（4種別それぞれで確認）
5. 欄を埋めない合成フィクスチャで生成したマニフェストの `units[0].kind` が `unresolved` のままである（4種別それぞれで確認）

## 触らない範囲

- api・feature・screenの既存のkind解決ロジック（1-66で対応済み・featureは対象外のまま）
- `validate-manifest.sh` の値域定義そのもの（`kind_allowed` の値は変更しない）
- 過去に生成済みの設計文書への遡及的な欄の追記

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 4つの欄の具体的なキー名 | 本文中の例（`table_subkind`・`batch_trigger_type`・`report_engine`・`external_direction`）をそのまま使う | 既存のfrontmatterキーと衝突する、または命名規約に反すると分かった場合 |
| 欄の値の語彙（例: table_subkindに入れる文字列） | `validate-manifest.sh` の値域の英語表記（table/view/migration等）をそのまま値として使う | 対象プロジェクトの実態に合わせて別の語彙が必要だと分かった場合 |
| 既存の生成済みサンプル（`generation-engine/samples/`）への反映要否 | テンプレート変更に伴い `.claude/rules/always/portal/template-sample-sync/rule.md` の規約に従い同一コミットで再生成する | サンプルに該当種別の文書が無く再生成対象が無いと分かった場合 |
