# 対象プロジェクトの実態を反映させる指示書

**元の指摘**: なし

**優先度: 最高。3.1 は現場が書いた内容が消える実害を止める。**

## 1. この指示書は何か

配布物の生成が、対象プロジェクトの実態を読まずに配布物の中の定義だけで動く箇所を直す。現場が書いた内容が消える、実在しないものが載る、といった状態を止める。

この指示書は指示であり、実装ではない。読んだ担当者が作業する。

## 2. なぜ必要か

### 2.1 現場が書いた内容が消える

規約を配置するスクリプトを既存の規約フォルダに対して実行すると、**現場が「このプロジェクトの規則」の節へ書き込んだ内容が失われる。**

実測（対象 26 本）は次のとおりである。

```
実行前  表のデータ行 115 行（21 本に分散）
実行後  表のデータ行  26 行（全ファイルがプレースホルダ 1 行のみ）
```

原因を特定した。既存のファイルをスキップする条件が「ツール側が本文を定める規約でない」ときに限られている。ところが分類の定義は 27 の子カテゴリすべてを「ツール側が本文を定める」と宣言している。**したがってスキップの条件を 1 本も通らず、既存のファイルは常に丸ごと上書きされる。**

これは以前の是正の副作用である。「ツール側が本文を定める規約は他の経路の本文で上書きされてはならない」という意図は正しいが、**上書きの単位がファイル全体になっている。**

しかも雛形自身が、この節へ書き込むよう現場を促している。

```
<!-- リバース解析が対象リポジトリの観測から起こした規則を置く。 -->
| 未解析 | この規約に対応する実装の慣行は、まだ観測していない。… |
```

**促しておきながら、次に配置を走らせるとその内容を消す。受け口として成立していない。**

現場は回避策として、実行前に 26 本の節を退避し、実行後に書き戻している。**手作業であり、規約が増えるたびに繰り返す必要がある。**

### 2.2 観測から起こした規則を入れる経路が無い

規約の設計文書は「このプロジェクトの規則」の節を必須と定め、書く主体を「リバース解析」と明記している。**ところがこの節へ内容を入れる経路が配布物の中に見つからない。**

実測で 3 点を確かめた。

| 確かめたこと | 結果 |
|---|---|
| 規約提案を起こすスキルの対象 | ツール側が本文を定める子カテゴリを対象外と定めている |
| 分類の定義の 27 子カテゴリ | すべてツール側が本文を定めると宣言されている |
| 取り込みのスキルが作る節 | 「概要」「規則」「違反時の手順」の 3 つで、当該の節を含まない |

配置のスクリプトが入れるのはプレースホルダ 1 行のみである。

### 2.3 適用範囲に対象側の値を宣言する受け口が無い

規約の前付けの適用範囲は、配置のスクリプトが分類の定義から直接読んで書き出す。**対象プロジェクト側で固有の値を宣言する受け口が配布物の中に無い。**

生成物の置き場には対象側の上書きを読む仕組みがあるが、適用範囲には無い。このため対象プロジェクトに実在するディレクトリへ適用範囲を合わせても、**配置を実行するたびに既定値へ戻る。** 実測では 26 本すべてで既定値へ置き換わった。

### 2.4 索引が対象プロジェクトの実際の構成を反映しない

規約とフローの対応を示す索引のページは、配布物の中の分類の定義から直接組み立てられる。**対象プロジェクト側の規約フォルダの実態を読まない。**

ある対象プロジェクトでは、配る規約を 26 件とし、分類の定義が持つ 27 件目を意図して外した。この状態で索引を生成したところ、**27 件すべてが載った索引が出力された。** 存在しない規約への案内が 1 件含まれる状態である。生成のコマンドは終了コード 0 で完了し、不整合の警告も出ない。

**2.3 と同じ構造である。** どちらも配布物の中の定義だけを情報源としている。

## 3. やること

### 3.1 上書きの単位をファイルから節へ下げる

**以前の是正を巻き戻さない。** 「規則」の節は常に上書きでよい。

上書きの単位を、ファイルから節へ下げる。

| 節 | 既存があるとき |
|---|---|
| 概要 | ツールの本文で上書き |
| 規則 | ツールの本文で上書き |
| このプロジェクトの規則 | **既存を保持する。ただしプレースホルダ 1 行だけの場合はツールの本文で上書きしてよい** |
| 違反時の手順 | ツールの本文で上書き |

**プレースホルダだけの場合を上書きの対象に含める理由**は、現場が何も書いていない状態で雛形の改訂が届かなくなることを防ぐためである。

### 3.2 観測から起こした規則を入れる経路を用意する

「このプロジェクトの規則」の節へ内容を機械で入れる経路を 1 つ用意する。

**推奨する形**は、取り込みのスキルの本文生成に当該の節を加え、判定の結果の入力から当該の節の行を渡せるようにすることである。

**既存内容の保持（3.1）とは別に、初回の投入ができることをもって完了とする。**

### 3.3 適用範囲に対象側の受け口を設ける

適用範囲に、対象プロジェクト側の上書きを読む受け口を設ける。

**形式は、生成物の置き場の上書きと同じにする。** 対象側の宣言ファイルを読み、キー単位で合成する。

**適用範囲以外の前付けの鍵は対象外とする。**

### 3.4 索引が対象側の実態を情報源に含める

索引の生成が、対象プロジェクト側の規約フォルダの実在を情報源に含めるようにする。

分類の定義に存在しても対象側に実体が無い規約は、**索引へ載せないことを推奨する。** 実体が無い旨を明示して載せる形でもよい。

あわせて、**分類の定義の件数と対象側の実体の件数が食い違う場合に、生成のときに件数の差を報告する。**

## 4. 完了の判定

次のすべてを満たすこと。

1. 現場が書き込んだ「このプロジェクトの規則」の内容が、配置の再実行で失われない
2. プレースホルダ 1 行だけの節は、従来どおり雛形の本文で上書きされる
3. 「概要」「規則」「違反時の手順」の上書きの挙動が変わらない
4. 配置のスクリプトの自己テストが終了コード 0 で通る
5. 現場側の退避と書き戻しの手作業が不要になる
6. 分類の定義が宣言する全子カテゴリについて、「このプロジェクトの規則」へ内容を機械で入れる経路が 1 つ以上存在する
7. 当該の節の行を含む判定の結果の疑似入力を用意し、取り込みの手順で処理して、生成された規約に当該の節と行が入ることを確かめている
8. 対象側の宣言により適用範囲を上書きでき、配置の再実行で失われない
9. 宣言の無い子カテゴリは既定値を保つ
10. 分類の定義より少ない件数の規約フォルダを持つ疑似入力で索引を生成し、載る件数が対象側の実体の件数と一致する
11. 同じ疑似入力で、件数の差が生成のときの出力へ報告される

## 5. 触らない範囲

- 分類の定義そのものの変更
- 適用範囲以外の前付けの鍵
- 既に生成済みの規約の内容
- `.claude/rules/` 配下（このリポジトリ自身の規約であり、配る資産とは別）

## 6. 決めていないこと

次は、作業する担当者が決める。

1. **節の単位で上書きする実装の方法**
2. **「このプロジェクトの規則」へ入れる経路をどのスキルへ持たせるか**
3. **索引で実体が無い規約を載せないか、明示して載せるか**
4. **対象側の宣言ファイルの置き場と形式**

## 8. この指示書の位置づけ

4 件とも「配布物の中の定義だけを情報源とし、対象プロジェクトの実態を読まない」という同じ構造から生じている。現場が書いた内容が消え、実在しない規約が索引に載り、対象へ合わせた設定が毎回戻る。対象側の実態を情報源に含めることで、4 件が同時に解ける。

対応する担当者が周ごとに更新する。状態は「未着手」「対応中」「完了」「対象外」の4つを使う。
「対象外」にした行は、確かめた内容の欄へ、なぜその判定が成立しないかを書く。
判定は「## 4. 完了の判定」が挙げる11件をそのまま使う。
