# 納品物の状態判定を正しくする指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

**優先度: 高。納品完了の条件が満たせない原因である。**

## 1. この指示書は何か

納品物の状態を判定するスクリプトが、対象が存在しない成果物を「対象なし」と判定できず、件数の取得も常に 0 を返す状態を直す。

この指示書は指示であり、実装ではない。読んだ担当者が作業する。

## 2. なぜ必要か

### 2.1 対象が存在しない成果物を「対象なし」と判定できない

納品物の状態を判定するスクリプトは、状態を「出力あり」「対象なし」「未生成」の 3 分岐で決める。判定は 2 つの条件だけで行われる。実ファイルの有無と、証拠の源がマニフェストである場合のマニフェストの件数である。

**一方、納品物の定義には証拠の源を持たない項目が多数あり、これらは実ファイルが無い限り恒久的に「未生成」と判定される。**

ある対象プロジェクトでは、画面を持たないことを実測で確定した。全エンドポイントが API 専用の経路にのみ登録され、応答は固定の形式で、画面の雛形は 0 件だった。

**この事実を対象外の記録ファイルへ書いたが、判定は変わらなかった。** 判定のスクリプトが当該の記録ファイルを参照していないためである。

結果として、画面に依存する成果物 8 件が「未生成」として残り続ける。

```
画面遷移図・テスト観点表・テストケース一覧・権限画面マトリクス
権限機能マトリクス・CRUD図・画面-API-テーブル対応表・確認事項質問票
```

**対象が存在しないため作ることができず、かつ対象なしと判定される経路も無い状態である。**

納品完了の条件は「未生成だけが未達を表す」と定めているため、**この 8 件がある限り当該の条件を満たせない。**

### 2.2 件数の判定が常に 0 を返す

同じスクリプトが、マニフェストの件数を数える箇所で、定義ファイルの値をそのまま `jq` の式へ埋め込んでいる。

**この値は JSON Pointer の記法（先頭がスラッシュの形）であり、`jq` の構文としては不正である。**

実測で確かめた内容は次のとおりである。

| 確かめたこと | 結果 |
|---|---|
| 定義ファイルの値 | 7 種別のうち 1 種別が `/screens`、残る 6 種別が `/units` |
| 実行結果 | いずれも `jq` が構文エラー（終了コード 3） |
| エラーを捨てた後 | 件数は 0 |

**標準エラーを捨てて既定値 0 へ倒す書き方になっているため、件数は常に 0 へ固定される。**

判定は 3 分岐だが、実ファイルの有無を先に見るため、実ファイルがある項目は正しく「出力あり」になり、この不具合の影響を受けない。**影響が出るのは実ファイルが無く、かつマニフェストが実在する場合である。** この経路では件数が常に 0 になるため、必ず「対象なし」と判定される。

その結果、**マニフェストが 0 件でないのに実ファイルが無いという不整合を報告する分岐が、恒久的に到達できない。** 実測では、50 件のマニフェストを実ファイル無しの状態で判定させたところ「対象なし・対象 0 件のため生成されない」と出力された。本来は不整合として報告されるべき状態である。

あわせて、同じスクリプトの自己テストは 0 件のマニフェストだけを検証しており、**0 件でない場合の不整合の検出を試していない。この経路は回帰テストの網の外にある。**

## 3. やること

### 3.1 対象が存在しない場合に「対象なし」と判定する

対象が存在しないことを記録した場合に、依存する成果物が「対象なし」と判定されるようにする。

**推奨する形**は、判定のスクリプトが対象外の記録ファイルを参照し、除外された種別に依存する成果物を「対象なし」へ倒す方式である。

あわせて、**納品物の定義の各項目へ「どの種別に依存するか」を宣言する欄を設ける。** 除外の判定を機械で伝えられるようにする。

### 3.2 件数の取得を正しくする

定義ファイルの値を `jq` の記法へ変換してから式へ渡す。または定義ファイルの値そのものを `jq` の記法へ改める。

あわせて、**`jq` が失敗した場合に既定値へ倒さず、エラーとして報告するようにする。**

**件数の取得に失敗した状態を「対象 0 件」と同一視しない。**

### 3.3 回帰テストの網を広げる

自己テストに、次のケースを足す。

| 足すケース | 確かめること |
|---|---|
| 0 件でないマニフェストを実ファイル無しで判定 | 「対象なし」ではなく不整合として報告される |
| 0 件のマニフェスト | 従来どおり「対象なし」と判定される |
| 件数の取得に失敗 | 既定値へ倒さずエラーが報告される |
| ある種別を対象外として記録 | 当該の種別に依存する成果物が「対象なし」と判定される |
| 除外の記録が無い | 従来どおり「未生成」と判定される |

## 4. 完了の判定

次のすべてを満たすこと。

1. 対象外として記録した種別に依存する成果物が「対象なし」と判定される
2. 除外の記録が無い場合は従来どおり「未生成」と判定される
3. 証拠の源がマニフェストである項目の既存の判定の挙動が変わらない
4. 納品物の定義の各項目に「どの種別に依存するか」を宣言する欄がある
5. 件数の取得が正しい値を返す
6. 0 件でないマニフェストを実ファイル無しで判定させると、不整合として報告される
7. 0 件のマニフェストでは従来どおり「対象なし」と判定される
8. 件数の取得に失敗した場合に、既定値へ倒さずエラーが報告される
9. 3.3 に挙げた 5 つのケースが自己テストにある
10. その自己テストが終了コード 0 で通る

## 5. 触らない範囲

- 証拠の源がマニフェストである項目の既存の判定の挙動
- 納品物の定義の項目の増減
- `.claude/rules/` 配下（このリポジトリ自身の規約であり、配る資産とは別）

## 6. 決めていないこと

次は、作業する担当者が決める。

1. **対象外の記録ファイルをどう参照するか**
2. **「どの種別に依存するか」の欄の形式**
3. **定義ファイルの値を変換するか、値そのものを改めるか**

## 8. この指示書の位置づけ

納品完了の条件は「未生成だけが未達を表す」と定める。ところが対象が存在しない成果物を「対象なし」と判定する経路が無く、8 件が恒久的に未生成のまま残る。加えて件数の取得が常に 0 を返すため、不整合を報告する分岐へ到達できない。どちらも、判定の結果を信用できるかに直結する。
