# 認証要否-ルーター登録時の一括付与を追えない問題を片付ける指示書

**状態**: 着手できる
**優先度**: 中
**前提**: なし
**元の指摘**: なし

## この指示書は何か

認証の要否は依存関数の名前から判定するが、ルーター登録時に一括で付与される依存は個々のエンドポイントの記述に現れないため検出できない問題を片付ける。2026-08-11 の実測では対象アプリの141件中111件がこれに当たる。`AIセットアップ検証の未決課題を片付ける指示書.md` の見送り5件の1件として起票する。

## なぜ必要か

`generation-engine/scripts/extract/extract-api-metadata.sh` の `authRequired` 判定（64〜82行目）は、エンドポイントの関数ブロック内に現れる認証パターン（`Depends(...)` 等）を見て判定するため、`include_router(router, dependencies=[Depends(require_auth_user)])` のようにルーター登録時に一括付与される認証依存を検出できない。この既知の限界とfail-safe方針（欠落を優先し誤ったfalseを出さない）は既にスクリプトのコメント（77〜82行目）に明記されている。

しかし、この限界の記述はスクリプト内部のコメントに留まり、`.claude/skills/generating-api-detail-design-for-reverse-docs` 等、この抽出結果を使う側のSKILL.mdには反映されていない可能性がある。抽出結果を消費する側がこの限界を知らないと、`authRequired` が欠落した111件を「認証不要」と誤読するリスクが残る。

## やること

### いま実装できる緩和策（実装済みの確認）

fail-safe方針（欠落を優先し誤ったfalseを出さない）は既に `extract-api-metadata.sh` 77〜82行目に実装済みである。新たな抽出ロジックの実装（ルーター変数からの `include_router` 呼び出しを別途走査し配下の全エンドポイントへ伝播させる仕組み）は、コメント自身が「別の仕組みが必要」と明記する規模の改修であり、本指示書のスコープ外とする（「決めていないこと」参照）。

行うのは、この限界をAPI関連の生成スキル（消費側）にも伝播させることである。

- `.claude/skills/generating-api-detail-design-for-reverse-docs/SKILL.md` に、`authRequired` が欠落している場合の扱い（推測で埋めない、原本を確認する等の既存の方針があればそれに従い、無ければ「欠落 = 未確認」であり「認証不要」と解釈しないことを明記する）を追加する
- 同様の消費箇所（`generating-api-basic-design-for-reverse-docs` 等）に同じ限界の記述があるかを確認し、無ければ追加する

### 限界を明示する記述の追加

`.claude/skills/generating-api-detail-design-for-reverse-docs/SKILL.md` の認証要否を扱う箇所へ、次の趣旨の1文を追加する。

> `authRequired` が欠落している場合、それはルーター登録時に一括付与される認証依存（`include_router` の `dependencies` 引数等）を抽出器が検出できないことによる欠落であり、「認証不要」を意味しない。原本のルーター登録箇所を確認してから記述する。

### 判断が変わる条件

ルーター変数からの `include_router` 呼び出しを別途走査し、配下の全エンドポイントへ認証依存を伝播させる仕組みが実装された場合、この限界は解消する。
