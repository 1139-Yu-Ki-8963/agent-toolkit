## この指示書は何か

`scaffold-design-unit.sh` の `--verify` は、展開した設計書に未置換のプレースホルダが残っていないかを検査する。ところが検査の対象は種別ごとに 1 つのトークンだけであり、それ以外の欄は未記入のままでも合格する。検査の対象を、テンプレート由来の全大文字トークン全体へ広げる。

## なぜ必要か

`generation-engine/scripts/scaffold-design-unit.sh` の 328 行目は `grep -qF "$token"` である。`$token` は `delivery-payload/references/design-unit-layout.json` の `kinds.<種別>.token` から取る 1 件だけで、テーブルなら `<TABLENAME>`、バッチなら `<BATCHNAME>` である。この 1 件しか見ない。

2026-08-18、テーブル・バッチ・帳票・外部連携の詳細設計書テンプレートへ、種別の判定材料の欄（`table_subkind`・`batch_trigger_type`・`report_engine`・`external_direction`）を足した。値は全大文字のプレースホルダ（`TABLESUBKIND` 等）である。これらは `token` と一致しないため、未記入のまま残っても `--verify` は合格を返す。

放置すると次が起きる。判定材料の欄が未記入のまま設計書が配置され、マニフェストを組み立てる処理が種別を解決できず、その項目が一覧の要確認へ回る。ところが配置の検査は合格を返しているため、なぜ要確認へ回るのかが分からない。失敗が失敗として現れない。

同じ経路は今回足した 4 欄に限らない。`table_key: TABLEKEY` のような既存の欄も `token` と一致しないため、未記入のまま合格する。

## やること

1. `scaffold-design-unit.sh` の `--verify` へ、テンプレート由来の全大文字トークンの残存検査を足す
2. 検査の対象とするトークンの求め方を決める（「決めていないこと」の既定に従う）
3. `generation-engine/scripts/tests/test-design-unit-scaffold.sh` へ 2 件のケースを足す。未置換の欄を 1 つ残した合成データが不合格になるケースを `未置換-全大文字トークン` の名前で、すべて置換した合成データが合格するケースを `置換済み-全大文字トークンなし` の名前で足す

## 完了の判定

1. 未置換の全大文字トークンを 1 つ残した合成データに対し `--verify` が終了コード 1 を返すケースが回帰テストに存在し、そのケースが合格する
2. すべて置換した合成データに対し `--verify` が終了コード 0 を返すケースが回帰テストに存在し、そのケースが合格する
3. `generation-engine/scripts/tests/test-design-unit-scaffold.sh` が終了コード 0 で終わる
4. `generation-engine/scripts/tests/check-design-unit-file-completeness.sh --self-test` が終了コード 0 で終わる

## 触らない範囲

- `design-unit-layout.json` の `kinds.<種別>.token`（種別識別子の置換そのもの）
- `prepare-verification-input.sh` の `ALLCAPS_TOKENS`（疑似入力を埋める別の仕組みであり、対象も発火の時機も異なる）
- `scaffold-screen.sh`（画面は 3 サブフォルダ 8 ファイルの束を扱う別経路であり、実績がある）
- 既に配置済みの設計書への遡及的な検査
