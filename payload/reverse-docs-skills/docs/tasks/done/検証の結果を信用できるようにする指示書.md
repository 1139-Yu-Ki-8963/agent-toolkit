# 検証の結果を信用できるようにする指示書

**状態**: 対応中
**優先度**: 最高
**前提**: なし
**元の指摘**: なし

**優先度: 最高。3.1 は他のすべての課題の解決を速める。**

## 1. この指示書は何か

自己テストの結果が、失敗の理由を残さない・置き場所によって変わる・存在しない資料を指す、という 3 つの状態を直す。検証の結果を信用できる状態にする。

この指示書は指示であり、実装ではない。読んだ担当者が作業する。

## 2. なぜ必要か

### 2.1 失敗の理由が残らない

自己テストの多くが、検査する対象の出力を捨てたうえで、終了コードだけを見て失敗を報告する。

```
if ! bash "$script_path" ... >/dev/null 2>&1; then
  echo "  [FAIL] <ケース名>" >&2
```

**失敗したという事実は残るが、なぜ失敗したかは残らない。**

出力を捨てる記述は、配布物の中に **684 箇所**ある。そのうち失敗の報告が直後にあるものが、実測で 274 箇所ある。

**実際に原因の特定を妨げた。** ある失敗の理由を突き止めるには、配布物を複製して出力の抑制を外し、実行し直す必要があった。判明した理由は「引数 1 つあたりの上限を超過」という、**出力を見れば 1 行で分かるもの**だった。

第 1 層の機械検証は 84 本を実行する。そのすべてで同じ構造の失敗が起こりうる。**失敗が出るたびに実行環境を再現するのでは、検証の回転が上がらない。**

### 2.2 置き場所によって結果が変わる

検証まわりのスクリプトの自己テストが、配布物自身の版を、配布物のルートを起点とした版管理の問い合わせで取得する設計になっている。

**配布物が版管理の下に無い場所へ置かれると版を取得できず、失敗する。**

逆に、たまたま祖先のディレクトリが別のリポジトリだった場合は、**無関係なリポジトリの版を拾って見かけ上成功する。** 実測では、同じ配布物を 2 か所に置いて機械検証を実行したところ、成否が場所によって入れ替わった。

配布物は利用者のリポジトリへ配る前提であり、版管理の下に置かれるとは限らない。**同じ配布物で結果が変わる状態では、機械検証の結果を信用できない。**

### 2.3 存在しない資料への参照がある

配布物の資料の参照を機械で調べ、参照先の実在を 1 件ずつ確かめた。

実測では、配布物の中の説明が `.claude/rules/always/publish/complete/rule.md` を 2 箇所で参照しているが、**そのファイルは配布物に含まれていない。**

配布物に含まれる規約は 2 件だけであり、この参照先はその 2 件に入っていない。**読み手は存在しないファイルへ導かれる。**

しかも参照の文面は「正本として参照する」と述べている。**正本として案内された文書が読めない状態である。**

## 3. やること

### 3.1 失敗の理由を残す

**この項目を最初に実施する。** 他の課題の原因究明が、実行環境の再現なしに行えるようになる。

検査する対象の出力を捨てず、変数または一時ファイルへ受ける。成功した場合は従来どおり何も出さず、**失敗した場合のみ、受けておいた出力を失敗の報告に添えて出す。**

**成功が続く限り、見え方は従来と変わらない。**

**一度に全部を直す必要はない。** 機械検証が実際に失敗を報告するスクリプトから順に直す。

### 3.2 版の取得を置き場所に依存させない

版の取得に失敗した場合を異常として扱わず、**版が不明である旨を明示したうえで検証を続ける。**

祖先を遡って版管理のリポジトリを探す挙動をやめ、**探索の範囲を配布物のルートに限る。**

### 3.3 存在しない参照を解消する

配布物の中から、参照先が存在しないものを無くす。

**方法は 2 つある。箇所ごとに選ぶ。**

| 方法 | 使う場面 |
|---|---|
| 参照先を実在するファイルへ向ける | 同じ内容が別の場所にある場合 |
| 参照を外して本文に要点を書き写す | 参照先が配布物に含まれない場合 |

**「正本」と述べている参照については、実際にどの文書が正本かを確定する。**

### 3.4 参照の検査を機械検証へ組み込む

判定の基準は「健全」の条件として「解決できないリンクが無いこと」を挙げている。

**この検査を第 1 層の機械検証へ組み込む。** 以後は自動で検出できる。

組み込みの可否も、この作業で判断する。組み込まない場合は理由を記録する。

### 3.5 切れている参照を性質で分けて扱う

配布物の全体で相対の参照を調べたところ、切れているものが 12 件あり、性質が 3 つに分かれる。

| 種類 | 件数 | 内容 | 扱い |
|---|---|---|---|
| 実在しない資料への参照 | 6 | 説明と規約が存在しないファイルを指す | 3.3 の対象 |
| 様式の中の見本用の画像 | 4 | 様式と手順書の中の画像の参照。実体を持たない | **意図を確認して判断する** |
| 記法の誤りで参照になったもの | 2 | 本文の一部が誤って参照の記法に取り込まれた | 記法を直す |

**画像の 4 件は、記入例としてそのまま置く意図であれば対象外である。** ただし生成物へそのまま出るなら、読み手には壊れた画像に見える。**どちらかを確定すること。**

## 4. 完了の判定

次のすべてを満たすこと。

1. 検査する対象をわざと失敗させたとき、その失敗の理由が自己テストの出力に現れる
2. すべて成功する場合の出力が、この作業の前と変わらない
3. 機械検証が失敗を報告するスクリプトすべてで、1 と 2 が満たされる
4. 版管理の下に無い場所へ配布物を置いて機械検証を実行し、版の取得に起因する失敗が 0 本になる
5. 祖先が別のリポジトリである場所へ置いて実行し、4 と同じ結果になる
6. 版が不明である場合、その旨が出力に現れる
7. 配布物の中の資料の参照を機械で調べ、参照先が存在しないものが 0 件になる
8. 「正本」と述べている参照が、実在する文書を指している
9. 参照の検査が第 1 層の機械検証に組み込まれている、または組み込まない理由が記録されている
10. 画像の 4 件について、意図が確定し記録されている
11. 記法の誤り 2 件が直っている

## 5. 触らない範囲

- 個々の失敗そのものの是正（別の指示書が扱う）
- 個々のスクリプトが検証する機能そのもの
- 参照先の文書の内容の充実
- `.claude/rules/` 配下（このリポジトリ自身の規約であり、配る資産とは別）

## 6. 決めていないこと

次は、作業する担当者が決める。

1. **出力を受ける方法**。変数か一時ファイルか
2. **どのスクリプトから直すか**。機械検証が失敗を報告するものから順に
3. **版が不明である旨をどう出すか**
4. **参照の検査を第 1 層へ組み込むかどうか**
5. **画像 4 件を記入例として残すか、実体を用意するか、参照を外すか**

## 8. この指示書の位置づけ

失敗の理由が残らないと、原因を突き止めるたびに実行環境の再現が要る。置き場所によって結果が変わると、成功が本物か判別できない。存在しない資料を正本として案内すると、読み手は行き止まりに当たる。3 つとも、検証の結果を信用できるかどうかに直結する。
