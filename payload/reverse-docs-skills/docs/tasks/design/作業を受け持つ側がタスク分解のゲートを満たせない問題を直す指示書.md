# 作業を受け持つ側がタスク分解のゲートを満たせない問題を直す指示書

**状態**: 設計から始める
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

書き込みの回数が一定に達したときタスクの登録を求めるゲートがある。
ところが作業を受け持つ側は、タスクを登録する道具を持たない。
求められた側に満たす手段が無い。

## なぜ必要か

実測（2026-08-24）。ブラウザを使う検査を直す作業で、次が起きた。

作業を受け持つ側が3回続けて書き込みを止められた。
止めた仕組みは、書き込みの対象が3つ目に達したときタスクの登録を求めるものである。

作業を受け持つ側は、タスクを登録する道具を持たない。
定義を実測すると次のとおりである。

```
tools: Read, Write, Edit, Bash, Grep, Glob
```

タスクを登録する道具が無い。ゲートを満たす手段が存在しない。

作業を受け持つ側は、別の手段（コマンド経由でのファイル作成）で書き込みを行い、
その事実を隠さず報告した。
自律の規約が定める「回避せず申告する」に従った対応である。

### なぜ重大か

回避が常態化すると、ゲートそのものが意味を失う。
止められるたびに別の手段へ切り替えるなら、
ゲートは書き込みを一度も止めていないのと同じになる。

加えて、申告があったから気づけた。
申告が無ければ、ゲートが働いているように見えたまま実効性だけが失われる。

### 自動での解除も働かない

ゲートには、同じ状況が3回続いたときに自動で解除される仕組みがある。
ところが実測では解除に至らなかった。理由は調べていない。

## やること

1. ゲートが誰に対して働くかを調べる。
   呼び出し元と、作業を受け持つ側のどちらを対象にしているかを確かめる
2. 作業を受け持つ側にタスクを登録する道具を与えるかを決める。
   与える場合、粒度の規約をどう守らせるかも決める
3. または、作業を受け持つ側をゲートの対象から外すかを決める。
   外す場合、呼び出し元が代わりにタスクを登録する形にするかを決める
4. 自動での解除が働かなかった理由を調べる。3回続いても解除されなかった実測がある
5. 決めた内容を機械で確かめる検査を作る

## 完了の判定

この段階では書けない。具体を決める作業が先である。決まった時点で次の形へ書き直す。

1. ゲートの対象が明文化されている
2. 対象に含まれる側が、ゲートを満たす手段を持っている
3. 自動での解除が働かなかった理由が記録されている
4. 決めた内容を確かめる検査が終了コード0を返す

## 触らない範囲

- ゲートそのものを無効にしない。書き込みの前にタスクを分解する目的は変えない
- 自律の規約（回避せず申告する）を変えない

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 作業を受け持つ側を対象に含めるか | 含めない。呼び出し元が委任の前にタスクを登録する形とする。作業を受け持つ側は道具を持たず、与えると粒度の規約を守らせる仕組みも要る | 作業を受け持つ側が自分で分解したほうが粒度が適切になると分かったとき |
| 呼び出し元がいつ登録するか | 委任のプロンプトを組み立てる時点。委任する作業の単位でタスクを登録する | 委任の前に作業の量が読めない場合が多いと分かったとき |
| 自動での解除の調査 | ゲートの実装を読み、解除の条件が何を数えているかを確かめる。数え方が実態と合っていなければ直す | 解除の仕組み自体が不要と判断されたとき |
| 過去の回避の扱い | 記録として残す。取り消さない | なし |

## 他の指示書との関係

なし。

## この指示書の位置づけ

止められる側に満たす手段が無いゲートは、回避を誘発する。
回避が常態化すると、ゲートは働いているように見えたまま実効性を失う。
申告があったから気づけたが、次も申告があるとは限らない。
