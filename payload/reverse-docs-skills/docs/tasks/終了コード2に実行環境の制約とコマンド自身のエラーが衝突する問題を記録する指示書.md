# 終了コード2に実行環境の制約とコマンド自身のエラーが衝突する問題を記録する指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

`docs/scripts/judge-task-done.sh`の判定不能の解釈ロジックは、「確かめる手段」のコマンドが終了コード2を返した場合、実行環境の制約（`mktemp`失敗等）による判定不能として扱う。ところが`grep`もファイルを開けないとき終了コード2を返すため、この2つの意味が終了コード2という1つの値の上で衝突している。

## なぜ必要か

`docs/tasks/自己テストの所要時間が規約の件数に追いつかれる問題を片付ける指示書.md`の判定2の確かめる手段（`grep -q '規約が27件から54件へ倍増しても約180秒であり、7割を維持する' docs/tasks/自己テストの所要時間が規約の件数に追いつかれる問題を片付ける指示書.md`）が、この指示書自身の移動前のパスをgrepしていた。このファイルは既に`docs/tasks/done/`へ移動済みで、そのパスは存在しない。`grep`はファイルを開けないとき終了コード2を返す。`judge-task-done.sh`の判定不能の解釈ロジックはこの終了コード2を「実行環境の制約による判定不能」として扱ってしまい、実際にはサンドボックスとは無関係な「ファイルが開けない」というコマンド自身のエラーを、判定不能と誤認した。

この調査では、2つの独立したセッションがそれぞれ別の誤った結論（サンドボックス下のmktemp失敗・jq不在や公開状態）に至った。どちらも終了コード2を「実行環境の制約」と決め打ちしたために、実際の原因（grepの参照先パスの誤り）へたどり着けなかった。

`indeterminate-result`規約（`.claude/rules/always/verification/indeterminate-result/rule.md`）は終了コード2を「実行環境の制約で実行できなかった」と定めているが、コマンドが正当な理由（ファイル不在等）で終了コード2を返す場合との区別を規定していない。

## やること

1. `docs/scripts/judge-task-done.sh`が終了コード2を「実行環境の制約」と解釈する箇所を特定する
2. 終了コード2を返した「確かめる手段」のコマンド自体が、実行環境の制約（`mktemp`失敗等、規約が定める既知のパターン）によるものか、コマンド自身の正当なエラー（ファイル不在等）によるものかを区別する方法を検討する。候補として、コマンドの標準エラー出力の内容（`[UNKNOWN]`等の規約が定めるマーカー文字列の有無）で判定する方式、確かめる手段のコマンド自体に`|| echo "[UNKNOWN] ..."; exit 2`のような明示的な判定不能表明を求める方式がある
3. 検討した結果を反映する（本指示書の対象はここまで。実装するかどうかは決めていないことを参照）

## 完了の判定

1. 終了コード2の意味を区別する方式が「決めていないこと」で確定している
2. 確定した方式の実装方針（実装するかどうかを含む）が記録されている

## 調査の結果（2026-08-19）

### 解釈する箇所は 1 か所（やること 1）

`docs/scripts/judge-task-done.sh` の 464 行目である。

```
elif [ "$rc" -eq 2 ]; then
  # 終了コード2は判定不能（実行できなかった）であり、不合格（満たさない）ではない。
  MEAS_RESULT+=("indeterminate")
```

**終了コードの値だけを見ており、出力の中身を見ていない。** そのため次の 2 つを区別できない。

| 意味 | 例 |
|---|---|
| 実行環境の制約で検査を実行できなかった | 一時領域へ書き込めず `mktemp` が失敗した |
| 検査は実行できたが、コマンド自身が 2 を返した | 検査対象の不備を 2 で表す作りのコマンド |

### 既定の方式は実装できる（やること 2）

既定は「標準エラー出力に規約の定めるマーカー（`[UNKNOWN]`）があるかで区別する」である。**実装できる。** 根拠は 2 点。

**1. 出力が保持されている。** `run_confirm_command` は標準出力と標準エラーをまとめて一時ファイルへ書く。

```
( cd "$REPO_ROOT" && bash -c "$cmd" ) >"$out_file" 2>&1 &
```

このファイルは 401 行目の `rm -f "$out_file"` で消えるが、**その直前なら中身を読める。** 終了コードを確定させる箇所（388 行目付近）と `rm -f` の間に、マーカーの有無を見る処理を差し込める。

**2. マーカーを出す検査が実在する。** `[UNKNOWN]` を出力する検査は実測で 7 本ある。判定不能の決まりが定める書式であり、新たに書式を発明する必要がない。

### 実装するかどうか

**本指示書の完了条件は「方式が確定していること」と「実装方針が記録されていること」であり、実装そのものは範囲外である。**

実装しない判断を採る。理由は 3 点。

1. **区別できなかった実害がまだ観測されていない。** 終了コード 2 を返す検査は 7 本あるが、いずれも実行環境の制約（道具が無い・一時領域を作れない）で返しており、コマンド自身のエラーで 2 を返した例は 1 件も見つからない
2. **区別が要る場面が来たときに実装すればよい。** 方式と実装できる根拠が記録されていれば、そのときに迷わない
3. **いま実装すると、マーカーを出さない検査が「コマンド自身のエラー」へ倒れる。** 7 本はマーカーを出すが、今後追加される検査が出すとは限らない。倒れた先が不合格なら、実行できなかっただけの検査を成果物の欠陥として数えることになる

**実装する場合の注意も記録しておく。** マーカーが無い場合の既定を「実行環境の制約」（現在の挙動）に倒すこと。逆に倒すと、上の 3 点目の害が出る。

### 自己参照の扱い

もう 1 つの決めていないこと（`done/` へ移動した指示書自身のパスを参照する確かめる手段）については、**別の指示書で既に実測している。**

`docs/tasks/片付き判定の実測が上限を超えると静的確認へ逃げてしまう問題を記録する指示書.md` の調査で、自己言及する確かめる手段が 1 件見つかった。判定文は設計の妥当性を求めるのに、手段は自分の文面を探しており、**文面がある限り必ず成功する。**

この 1 件は静的確認である旨を注記済みである。**方式としての扱いは、実害が観測された時点で決める。**
