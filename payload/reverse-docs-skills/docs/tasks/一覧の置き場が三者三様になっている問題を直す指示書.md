# 一覧の置き場が三者三様になっている問題を直す指示書

**状態**: 着手できる
**優先度**: 高
**前提**: なし
**元の指摘**: なし

## この指示書は何か

一覧のページをどこへ置くかについて、3 つの定めが食い違っている。
どれを正とするかを決め、他をそれへ揃える。

## なぜ必要か

2026-08-24 に検証ループを通しで走らせて分かった。

    配置の定義（output-layout.json）        project-portal/lists/screens/画面一覧.html
    ポータルのカタログ（portal-catalog.json）  project-portal/一覧/画面一覧/画面一覧.html
    生成器のコメント（build-screen-list.sh）   既定は project-portal/一覧/画面一覧/画面一覧.html

見本（generation-engine/samples）も両方に散らばっている。

    project-portal/一覧    11 件
    project-portal/lists    8 件

**どちらへ揃えても、揃えなかった側の検査が落ちる。**

### 網羅の検査そのものも内部で食い違っている（2026-08-24 追記）

網羅の検査（`check-coverage.sh`）は、画面一覧だけを配置の定義から取り、
他の一覧はカタログから取る。同じ検査の中で 2 つの定めを混ぜている。

    画面一覧      配置の定義から   lists/screens/画面一覧.html（英字）
    他の一覧 9 件  カタログから    一覧/API一覧/API一覧.html（日本語）

第 3 層を戻した後に測ると、欠落は 9 件から 1 件へ減った。残る 1 件は画面一覧
であり、**どちらへ揃えても必ず 1 件は落ちる状態になっている。**

    第3層を英字へ揃えたとき  欠落 9 件（他の一覧がカタログと合わない）
    第3層を日本語へ戻したとき 欠落 1 件（画面一覧が配置の定義と合わない）

揃える対象に `check-coverage.sh` の画面一覧の取り方を加える。

同日、第 3 層の出力先を配置の定義（英字）へ揃えたところ、設計書から一覧への
戻りリンク 2 件は直ったが、網羅の判定で一覧 9 件が欠落になった。
差し引きで悪化したため、その変更は戻した。

    変更前  網羅 合格 / 生成物のリンク切れ 2 件
    変更後  網羅 9 件欠落 / 生成物のリンク切れ 0 件

**片側だけを直すと、もう片側が壊れる。** 3 つの定めのどれを正とするかを
先に決めない限り、この行き来が続く。

### 直す量の実測（2026-08-24 追記）

どちらへ揃えるかを決めるにあたり、両側を指す箇所を数えた。走査対象は `generation-engine/`・
`delivery-payload/`・`docs/` である。

| 側 | ファイル数 | 行数 |
|---|---|---|
| 英字（`project-portal/lists`） | 16 | 81 |
| 日本語（`project-portal/一覧`） | 34 | 143 |

日本語側が2倍以上多い。日本語へ揃えれば直すのは英字側の16ファイルで済む。英字へ揃えると
34ファイルを直すことになる。**この数の差が、日本語を正とする根拠である。**

当初は「配置の定義1つと見本8件」と見積もっていたが、実測はその2倍を超えた。

## やること

1. **日本語の側（`project-portal/一覧/...`）を正とする。** 3つの定めのうちカタログと生成器の既定が既に日本語であり、見本も日本語側が11件・英字側が8件で日本語が多い。英字へ揃えると直す箇所が増える。この判断を覆すのは、納品先で機械がパスを扱う場面が増え、英字のほうが扱いやすいと分かったときに限る
2. **正でないほうを、正へ揃える。** 実測（2026-08-24）で英字（`project-portal/lists`）を指すのは
   16ファイル・81行である。内訳は次のとおり

   | 置き場 | ファイル数 |
   |---|---|
   | `generation-engine/scripts/tests` | 3 |
   | `generation-engine/scripts/extract` | 3 |
   | `generation-engine/scripts` | 3 |
   | `delivery-payload/references` | 3 |
   | `generation-engine/samples` | 1 |
   | `docs/tasks/work-records` | 1 |

   `delivery-payload/references` の3件は `checker-real-world-cases.json`・`output-layout.json`・
   `portal-entry-dependencies.json` である。カタログ（`portal-catalog.json`）が英字を指す箇所は
   0件であり、変更を要さない
3. **設計書のテンプレートが書く戻りリンクを、正へ合わせる。**
4. **検証ループを通しで走らせ、網羅と健全の両方が合格することを確かめる。**
5. **`docs/scripts/check-list-path-unified.sh` を作る。** 完了の判定6の式（縦棒を含む）は指示書の表へ直接書けないため、この指示書を実行する担当がスクリプトへ切り出す（前例: `check-confirmation-target.sh`・`check-mktemp-placement.sh`）。

## 完了の判定

1. 一覧の置き場を定める箇所が 1 つになる（他はそこを参照する）
2. `bash generation-engine/scripts/verification/check-coverage.sh` の欠落が 0 件になる
3. `bash generation-engine/scripts/tests/test-e2e-portal.sh` の不合格が 0 件になる
4. `bash generation-engine/scripts/verification/run-layer-full-pipeline.sh --self-test` が終了コード 0 を返す
5. `bash .claude/rules/always/tasks/instruction-format/check-instruction-format.sh` が不合格 0 件
6. `grep -rn 'project-portal/lists' generation-engine/ delivery-payload/ docs/ | wc -l` が0を返す

## 触らない範囲

- 一覧のページの中身。置き場だけを扱う
- 画面・API・テーブル等の設計書そのものの置き場（`docs/design/` 配下）
- 図・対応表・基盤の置き場（同じ食い違いがあれば別の指示書で扱う）

## 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 揃える順序 | 定義とカタログを先に揃え、見本を最後に作り直す。見本は定義から生成できるため | 見本を手で保守する運用へ変わったとき |
| 図・対応表・基盤も同時に見るか | 見ない。一覧だけを扱う。同じ食い違いがあれば別に起こす | 一覧を揃える作業の中で、図や対応表も同じ箇所を触ると分かったとき |

## 他の指示書との関係

なし。この食い違いは他のどの指示書も扱っていない。

## この指示書の位置づけ

同じことを定める箇所が 3 つあり、互いに食い違っている状態を 1 つへ寄せる作業である。
どれを正とするかは決めの問題であり、実装より先に決める必要がある。
