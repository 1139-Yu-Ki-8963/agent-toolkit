# 実装の変更に設計書の表示コミットが追従しない問題を直す指示書

**状態**: 着手できる
**優先度**: 中
**前提**: なし
**元の指摘**: 1-259

## 1. この指示書は何か

配る開発フロー（`delivery-payload/templates/delivered-skills/dev-flow/SKILL.md`）のPhase5へ、実装の変更が及んだ設計単位の`source_ref`（設計書の前付けが持つ、抽出時点のコミットハッシュ）を更新する段を新設する。あわせて完了記録の形式へ更新結果を残す欄を足し、段の有無を機械で確かめる検査を設ける。

## 2. なぜ必要か

版の管理はコミットのハッシュ（全長40桁）で行う設計である。設計書の前付けは`source_ref`に抽出した時点のハッシュを持ち（`delivery-payload/references/facts-schema.md`が「抽出時点のコミットSHA（`git -C <target_repo_path> rev-parse HEAD`で実測）」と定義する）、`generation-engine/scripts/check-derived-values.sh`が前付けの値とポータル・画面ページの表示値の一致を検査する。

ところが配る開発フローのPhase5が持つ更新の段は「入口のページを更新する」だけである（同ファイル212行目）。この段は`check-portal-entry-freshness.sh`で入口のページの鮮度を判定し、古ければ依存の宣言（`delivery-payload/references/portal-entry-dependencies.json`）が選んだ成果物を作り直す。完了記録にも「入口のページ」の更新コミットを残す欄がある（同241〜242行目）。

個々の設計書の`source_ref`を、実装が変わったときに更新する段が存在しない。同ファイルを`source_ref`で検索すると0件である。つまりコードを直しても、設計書の前付けは抽出した時点のハッシュを指したままになる。

この食い違いは`check-derived-values.sh`が「表示コミット-ポータル」「表示コミット-画面」として検知する。検知はするが、開発フローの中に直す段が無い。検知された後に誰が何をするかが定まっていない。

## 3. やること

1. 配る開発フロー（`delivery-payload/templates/delivered-skills/dev-flow/SKILL.md`）のPhase5に、「入口のページを更新する」の直前へ新しい見出し「設計書の表示コミットを更新する」を置く。この段は、実装の変更が及んだ設計単位を機械的に洗い出し、各設計単位の`source_ref`を更新する手順を持つ。対象の洗い出し方法は「決めていないこと」の既定に従う。
2. 更新対象を人が選ばない形にする。入口のページの段が依存の宣言（`portal-entry-dependencies.json`）に従って対象を機械的に決めているのと同じ考え方を採る。
3. `docs/scope-and-progress/開発フロー完了記録.md`へ追記する節の形式（同ファイル222〜238行目）へ、更新した設計単位とその更新後のハッシュを残す欄を足す。「入口のページ」欄と同じく、更新しなかった場合は影響が無い理由を残す形にする。
4. `check-derived-values.sh`が「表示コミット-ポータル」「表示コミット-画面」を検知した後、開発フローの本文からその対処（本指示書で新設する段）へ辿れる記述にする。
5. 新設した段の有無を機械で確かめる検査を設ける。検査はPhase5のSKILL.md本文の構造を静的に読み、段の見出し・完了記録の欄・対象の機械的な決定という3点が揃っているかを確認する。段を欠いた入力（見出しが無い、または欄が無いSKILL.mdの写し）に対しては不合格を返す。

## 4. 完了の判定

1. 配る開発フローのPhase5に`source_ref`の更新の段が存在する。確かめる手段: `grep -n '設計書の表示コミットを更新する' delivery-payload/templates/delivered-skills/dev-flow/SKILL.md`
2. 更新の対象を人が選ばない形になっている（対象の選び方が機械で決まる記述である）。確かめる手段: `bash generation-engine/scripts/tests/check-source-ref-refresh-step.sh --check-mechanized-selection`
3. 完了記録の形式に更新した設計単位とハッシュの欄がある。確かめる手段: `grep -n '設計書' delivery-payload/templates/delivered-skills/dev-flow/SKILL.md`
4. `check-derived-values.sh`が検知した後にやることが開発フローの本文から辿れる。確かめる手段: `bash generation-engine/scripts/tests/check-source-ref-refresh-step.sh --check-detection-link`
5. 更新の段を持つことを機械で確かめる検査が存在する。確かめる手段: `bash generation-engine/scripts/tests/check-source-ref-refresh-step.sh`
6. その検査が、段を欠いた入力に対して不合格を返す。確かめる手段: `bash generation-engine/scripts/tests/check-source-ref-refresh-step.sh --self-test`

## 5. 触らない範囲

- `check-derived-values.sh`の判定式そのもの（画面名・表示コミットの突合ロジック）は変更しない
- `check-portal-entry-freshness.sh`と入口のページの段の既存の挙動は変更しない
- 既に納品済みの対象プロジェクトの開発フロー定義の是正は行わない
- `check-derived-values.sh`が既に検知している個別の不一致（対象プロジェクトごとの実際のずれ）の解消は行わない
- API・テーブル・バッチ・帳票・外部連携・機能・画面という7種別の詳細設計書テンプレート本文の構成は変更しない

## 6. 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 更新対象の設計単位の選び方 | 種別ごとのユニットルート（`output-layout.json`の`<kind>UnitRoot`）配下の全詳細設計書について、各`source_ref`が指すパス配下に、その`source_ref`のコミット以降の変更（`git diff --name-only <source_ref>..HEAD -- <パス>`）があれば更新対象とする | 依存の宣言（`portal-entry-dependencies.json`と同種の構造化データ）を新設し、種別ごとの入力パスの対応をそちらで持つ実装に変わった場合はそちらへ従う |
| 新しい`source_ref`の値 | `git rev-parse HEAD`（更新実行時点のHEAD） | `facts-schema.md`の`source_ref`の定義が変わった場合はその定義に従う |
| 新設する段の置き場所 | Phase5の「入口のページを更新する」の直前に新しい見出し「設計書の表示コミットを更新する」を置く | 別の段構成にすると既存のPhase5承認フロー（ゲート・完了の記録の順序）と矛盾すると判明した場合は、矛盾しない位置へ動かす |
| 検査スクリプトの名前・置き場 | `generation-engine/scripts/tests/check-source-ref-refresh-step.sh`とする。`docs/scope-and-progress/page-conventions/rule.md`の`check-inventory-approval-step.sh`と同じ、SKILL.md本文の構造をgrepする形の検査にする | 既存の検査（`check-derived-values.sh`等）へ機能を統合できると判明した場合はそちらへ統合する |
| 完了記録の欄の名前・書式 | 「入口のページ」欄に倣い「設計書」欄を追加し、値は「更新: `<設計単位のキーとコミットの一覧>`」または「影響なし: `<理由>`」とする | 別の記録形式が既に他の指示書で定義されている場合はそちらに揃える |

## 7. 他の指示書との関係

台帳1-257は、接続窓口の詳細設計書の前付けの鍵集合そのものの食い違いを扱う。本指示書は、鍵集合が揃っていることを前提に、`source_ref`という値を実装の変更へ追従させる運用の段が無いことを扱う。両者は独立して進められる。

`.claude/rules/scoped/portal/page-conventions/rule.md`の「設計判断」節に記録された`check-inventory-approval-step.sh`は、SKILL.mdの構造をgrepで検査する同種の先例である。本指示書の検査スクリプトはこの形に揃える。

## 8. この指示書の位置づけ

`check-derived-values.sh`という検知の仕組みは既にあるが、検知された不一致を実際に解消する運用の段が開発フローに欠けているという、検知と是正の間の欠落1点に絞って切った。検知ロジックの拡張（他種別の設計書への対象拡大等）や、対象プロジェクトごとの個別の是正は含めない。
