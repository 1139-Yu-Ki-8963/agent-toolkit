# 設計書が実在するのに元データが0件でも通る問題を直す指示書

**状態**: 着手できる
**優先度**: 最高
**前提**: なし
**元の指摘**: 1-254

## 1. この指示書は何か

設計文書の前付けから種別ごとの一覧の元データを組み立てる処理は、
単位フォルダが実在するのに組み立てられた件数が0件（または一部欠落）でも、
終了コード0のまま正常終了する。
0件・部分欠落を検知して標準エラーへ報告するようにする。

## 2. なぜ必要か

実測（改善課題1-254）。
設計文書からマニフェストを組み立てる処理
（`generation-engine/scripts/portal-input/build-manifests-from-docs.sh`）を、
ある対象プロジェクトの納品物へ実走した結果、接続窓口は50件、機能は0件だった。
機能は設計書が9件あるのに0件になる。

対象プロジェクトの9件はいずれも `feature_key` と `title` の2項目しか持たず、
`feature_id`・`category`・`source_ref` を欠いていた。
組み立ては終了コード0で正常終了し、整合の検査（`validate-manifest.sh`）も
15項目すべて合格した。
0件であることが不合格として現れないため、一覧の元データが空のまま気付かれない。

### このリポジトリの様式は既に揃っている

指摘は「機能の設計書の様式が2項目しか持たない」と述べるが、
このリポジトリの様式（`delivery-payload/templates/リバース検証/機能/機能設計書.md`）を
実測すると、既に5項目を持つ。

    feature_key
    feature_id
    category
    source_ref
    unit_kind

組み立ての宣言（`delivery-payload/references/doc-extraction.json` の
`kinds.feature.mapping`）が求める4項目
（`unitKey`←`feature_key`・`unitId`←`feature_id`・`category`←`category`・
`sourceFile`←`source_ref`）はすべて揃っている。
様式の修正は不要であり、範囲外とする。

### 前付けの不足だけでは0件にならない

組み立ての処理を読むと、前付けの一部が欠けても、
その単位は「未確認」の代替値で埋められたまま組み立てられた件数へ数えられる。
0件になるのは、単位フォルダ自体が正規の命名
（`scaffold-design-unit.sh` が作る `<kind>-<単位ID>` の形）でない、
または設計文書のファイル自体が見つからない場合である。
残る問題は、この場合に0件・部分欠落が沈黙のまま通ることである。

## 3. やること

1. `generation-engine/scripts/portal-input/build-manifests-from-docs.sh` を直す。
   種別ごとに、単位フォルダの数（正規の命名を持つものだけを数える）と
   組み立てられた件数を突き合わせ、食い違えば標準エラーへWARNとして出す。
   単位フォルダが1つも無い種別（0件が正しい種別）は対象から外す。
   加えて、単位フォルダの命名そのものが正規の形
   （`<kind>-<単位ID>`）と一致しない場合も検知する。
   この場合は正規の命名を持つフォルダの数が0のまま件数の突き合わせをすり抜けるため、
   root直下のディレクトリ数と正規の命名を持つ数を別に突き合わせ、
   前者が1以上で後者が0のときも命名不一致のWARNを出す
   （検討過程で確認: 前付けの項目を欠いた設計書は代替値で埋められて件数に
   数えられ続けるため、9件が0件になる実際の事象は前付けの不足だけでは
   再現しない。単位フォルダの命名が正規の形でない場合に0件になることを
   確かめた上で、この検知を追加した）
2. 終了コードは0のまま続ける。
   既存の「0件時はWARNのみで続行する」設計を踏襲する。
   `build-portal.sh` は本処理の終了コードが非0なら生成連鎖全体を止めるため、
   食い違いを理由に非0へ変えると、部分的な食い違いのたびに
   全体の生成が止まる。
   標準エラーへの報告だけで足りるとする
3. 機能の一覧を作る生成スキルの定義に、`feature_id` と `source_ref` の
   決め方が明記されているかを確かめる。
   `feature_id` は `.claude/skills/generating-feature-design-for-reverse-docs/SKILL.md`
   のStep 3-1に既に明記されていた
   （`unitId` が空なら `FEATUREID` を空欄のまま要確認事項一覧へ記録する）。
   `source_ref` の決め方は明記が無かったため追記する。
   機能は複数の実装ファイルを束ねる集約であり、代表となる単一のソースファイルを
   持たない。
   代表を1つ選ぶ・一覧で持つのいずれも根拠なく決めると捏造になるため、
   `unitId` と同じ非必須フィールドの扱い（値が無ければ空欄のまま要確認事項一覧へ
   記録する）としたことを、生成側
   （`.claude/skills/generating-feature-list-for-reverse-docs/SKILL.md`）と
   記入側
   （`.claude/skills/generating-feature-design-for-reverse-docs/SKILL.md`）の
   両方へ明記する
4. 検査を新設する。
   名前は `docs/scripts/check-manifest-count-mismatch.sh` とする

検査の要件は次とする。

- 単位フォルダの数と組み立てられた件数の食い違いが、対象スクリプトに対して
  実際に検知されるかを確かめる
- 合格なら `[PASS]`、不合格なら `[FAIL]` と該当箇所を出す
- 走査対象が存在しない場合は `[UNKNOWN]` と理由を出して終了コード2
- `--self-test` を実引数として処理する
- self-testに、前付けから項目を欠いた入力で食い違いが出るケースと、
  単位フォルダが0件の種別で報告が出ないケースを含める
- 一時ファイルを作る場合は置き場を明示する
  （`mktemp "${TMPDIR:-/tmp}/check-manifest-count-mismatch.XXXXXX"`）
- `diff` や `comm` の引数へプロセス置換（`<(...)`）を渡さない
- このスクリプト自身を走査で不合格にしない
- 設計判断を `.claude/rules/always/tasks/instruction-format/rule.md` の
  設計判断の節へ追記する

## 4. 完了の判定

6. `bash generation-engine/scripts/portal-input/build-manifests-from-docs.sh --self-test` が終了コード0を返す
7. `bash .claude/rules/always/tasks/instruction-format/check-instruction-format.sh` が終了コード0を返す

## 5. 触らない範囲

- 機能の設計書の様式（`delivery-payload/templates/リバース検証/機能/機能設計書.md`）を
  変えない。実測で既に4項目を持つ
- 生成済みの対象プロジェクトの成果物を是正しない
- 接続窓口（external）の処理を変えない（回帰を避ける）
- 他の指示書を変更しない
- `.claude/rules/scoped/portal/page-conventions/rule.md` を直接編集しない（生成物である）

## 6. 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 食い違い検知時の終了コード | 0のまま（WARNのみ）。既存の0件時の扱いと同じにし、生成連鎖（`build-portal.sh`）を止めない | 食い違いを重大な欠陥として扱い、生成連鎖全体を止める方針が別途決まったとき |
| `source_ref` の代表選定アルゴリズムを作るか | 作らない。`unitId` と同じ非必須フィールドの扱いとし、値が無ければ空欄のまま要確認事項一覧へ記録する | 機能を構成する複数ファイルから代表を機械的に選ぶ具体的な規則が別途決まったとき |
| 単位フォルダの数え方 | `scaffold-design-unit.sh` が作る正規の命名（`<kind>-<単位ID>`）を持つフォルダだけを数える。既存の `document_path_canonical_unit_dir` の判定をそのまま使う | 正規の命名を持たない単位フォルダも数える必要が別途決まったとき |
| 集約抽出（table・batch・external）でのWARNの扱い | そのまま受け入れる。集約抽出は一覧文書（例: `テーブル一覧.md`）の行から件数を決めるため、実在する単位フォルダの数と件数が一致しない場合がありうる。この食い違いは終了コードを変えない標準エラーへの報告に留まるため、成果物の欠陥ではない誤報が混じっても実害は無い | 集約抽出の種別で誤報が頻発し実運用上の妨げになると分かったとき。その場合は種別ごとに検知の要否を宣言（`doc-extraction.json`側）で切り替える方式を検討する |

## 7. 他の指示書との関係

依存する指示書は無い。
機能の一覧・機能の設計書を扱う他の指示書と対象が重ならない場合は独立して進めてよい。

## 8. この指示書の位置づけ

食い違いの検知は、組み立て処理1本に閉じた変更である。
生成スキルの定義の追記は、機能を扱う2スキルに閉じた変更である。
どちらも他の種別・他の処理へ波及しないため、1つの指示書にまとめて切った。
