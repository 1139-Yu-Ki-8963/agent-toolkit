## 結論

配布対象の検査スクリプト（checker）本体29件へ、この環境で違反入力を与えたところ、29件すべてが違反を検出または通知した。

`rule-taxonomy.json` が宣言しない checker が2件あり、規則数と判定数の検査でも1規約が「不足」になった。
また、ユーザー指定の検査コマンドには、存在しないパスと未対応の `--help` が含まれていた。

## 観点2：検査が本当に違反を検出するか

### 実行方法

checker冒頭の入力契約と既存の自己テストを読み、本体のフック入口またはコマンドライン（CLI）入口へ違反入力を与えた。
内部関数の直接呼び出しだけで済ませず、配布先で使う入口を通した。

代表例は次のとおりである。

```bash
printf '%s' '{"tool_name":"Write","tool_input":{"file_path":"a.js","content":"const key = \"AKIAIOSFODNN7EXAMPLE\";"},"cwd":""}' \
  | bash delivery-payload/templates/rules/checkers/check-secret-literal-in-code.sh
```

```text
終了コード=2
[SECRET-LITERAL-IN-CODE-BLOCK] 拒否[秘密の値をコードへ書かない]
```

既存ファイル、セッション記録（transcript）、git状態が必要な8件は、リポジトリ直下の一時ディレクトリで実行した。
一時ディレクトリ名は `.verify-delivered-rules.XXXXXX` 形式とし、各ケースの `trap` で削除した。
これらは違反検出用に手作業で作った入力であり、過去の生成物を再利用したものではない。

## 観点3：規約の定義と検査の対応

規約分類表（taxonomy）である `rule-taxonomy.json` の構造は `parents[].children[]` である。
子規約27件すべてが、異なるcheckerを1件ずつ宣言している。

```bash
jq '[.parents[].children[]] | {
  rules:length,
  checker_count:(map(.checker)|map(select(.!=null))|length),
  unique_checker_count:(map(.checker)|map(select(.!=null))|unique|length)
}' delivery-payload/references/rule-taxonomy.json
```

```json
{
  "rules": 27,
  "checker_count": 27,
  "unique_checker_count": 27
}
```

taxonomyが宣言する27件はすべて実在した。
一方、checker本体29件のうち次の2件はtaxonomyから宣言されていない。

- `check-customer-facing-adequacy.sh`
- `check-instruction-writing.sh`

この2件はtool-defined規約27件のcheckerとは異なる対象を検査する。
前者は顧客提示文書、後者は指示書が対象である。
したがって27規約と27checkerの対応自体は閉じているが、taxonomyはcheckerディレクトリ全29件の用途を宣言する一覧にはなっていない。

指定されたhelpコマンドの結果は次のとおりである。

```text
$ bash generation-engine/scripts/rules/validate-rule-definitions.sh --help
ERROR: ルートディレクトリが存在しません: --help
終了コード=1
```

このスクリプトは `--help` を実装しておらず、入口自体は実行された。
ただし、`--help` を規約ルートのパスとして検査し、そのディレクトリが存在しないため終了1になった。

補足として、次の実在する入口も実行した。

```text
$ bash generation-engine/scripts/rules/validate-rule-definitions.sh --self-test
13ケースすべてPASS
self-test 全項目 PASS
終了コード=0

$ bash generation-engine/scripts/rules/validate-rule-definitions.sh generation-engine/samples/docs/rules
検査合格: 27 件の rule.md が全検査に合格
終了コード=0
```

後者はサンプルの `docs/rules` 定義を検査するものであり、taxonomyに未宣言のchecker2件を検出する検査ではない。

文書レビュー中に同じ自己テストを再実行した際は、`project-section-missing` ケースが終了1になり、自己テスト全体も終了1になった。
その直後に同じ作業場所と同じコマンドで再実行すると、13ケースすべてPASS、終了0へ戻った。
一時ファイル内の別規約へ予期しない `front-matter鍵-欠落` が出たが、間欠結果の原因は判定できていない。


この検査が数える対象は次のとおりである。

- 規則の数：tool-defined規約の `## 規則` 表で、検査列が `不可:` または `判定不能:` から始まらない行。
- 判定の数：checkerファイル全体に現れる `拒否[規則名]`、`通知[規則名]`、`許可[規則名]`、`対象外[規則名]` の異なる規則名。
- 対応関係：taxonomyの `parents[].children[].checker`。
- 走査上の制約：コメントと実際の出力を区別しない。

不足した規則名は `運営文書の置き場を固定する` である。
この規則の検査列は `レビュー:` で始まるため、規則数には数えられる。
対応checkerの `check-temp-file-tracked.sh` は、この規則名の判定を出していない。
その結果、規則7件に対して判定6件となる。

## 実行不能・環境要因

一時領域への書き込み失敗は発生しなかった。
一方、空の利用者環境では `check-instruction-writing.sh` が配布物外の辞書を見つけられず、違反判定を実行できなかった。
スクリプトは終了1を返したが、対象内容の不合格ではなく判定不能として扱った。

メインセッションからcheckerをまとめて直接実行しようとした際、ツール実行前（PreToolUse）フックが `[CLAUDE-COMPAT-BLOCK]` で止めた。
これはcheckerの不合格ではない。
コマンド実行専任のサブ担当へ同じコマンドを委任すると、対象checkerまで到達して実行できた。

`check-direct-commit-to-integration-branch.sh` の一時gitリポジトリを使うケースも、最初の非対話実行は外側のPreToolUseフックに止められた。
同じ入力を直接checkerへ渡す対話シェルで再実行し、終了コード2と拒否判定を確認した。
