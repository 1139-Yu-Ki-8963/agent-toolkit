## 観点3: 判定不能の理由が残るか

残らない。
`run-layer-machine-checks.sh` は終了コード2だけで `UNKNOWN` を決め、子出力を表示する処理を `FAIL` の場合だけ実行する。
全件集約の2本でも、強制した一時試験環境の3本でも、表示されたのはスクリプト名、実行件数、終了コードだけだった。

このため、集約結果だけを読む人は「実行できなかった」ことは分かるが、具体的な理由を判断できない。
区別できない理由は、YAMLを読むPythonライブラリのPyYAML欠落、隔離環境用のPython実行系不在、`mktemp` 失敗、辞書欠落である。
また、終了コード2を返すだけで `[UNKNOWN]` ラベル、操作名、想定原因を欠く子検査も、集約器は判定不能として受理する。
`docs/tasks/work-records/2026-08-23-検証の仕組みの検証.md` の「穴9: 集約器が子検査の判定不能契約を検証せず、理由を集約出力から落とす」を実際の実行で再現した。

## 実行できなかったものと試行上の注意

- 5本を `bash <script>` の形で直接起動した最初の試行は、対象へ到達する前に実行前フックの `[CLAUDE-COMPAT-BLOCK]`、終了コード2で止まった。
  この値は各検査の結果へ数えていない。
  `env /bin/bash <script>` で同じ引数を渡して対象本体まで到達させた。
- `TMPDIR=/dev/null` は `docs/scripts/check-task-ledger-sync.sh` の引数なし `mktemp -d` を失敗させなかった。
  自己テストは3件成功、終了コード0になったため、この試行は採用しなかった。
  Bashへ失敗する `mktemp` 関数を注入して再実行し、終了コード2を確認した。
- 全件集約は途中停止せず完走した。
  実行不能として未判定の集約対象は無い。
  `build-portal.sh` は検査不能ではなく集約器が明示した時間上限到達として、判定不能や失敗へ混ぜず打ち切り1本に数えた。
- 一時試験環境 `.verify-unknown-aggregation` は検証直後に削除した。
  存在しない辞書はパスだけを指定し、ファイル自体を作っていない。

## 最終判定

- 終了コード2の件数分類: 対象3本を失敗と分離したが、子検査の契約適合は確認していない。
- 5本の判定不能契約: 不合格。
  実際に実行した5経路のうち、2経路が想定原因を欠き、1経路が失敗操作名を欠く。
  別の角括弧なし経路も確認した。
- 判定不能理由の保持: 不合格。
  理由を集約出力から落とす。
- 判定不能契約の検証: 不合格。
  終了コード2以外を検証しない。
- 今日の是正後の失敗数: 不合格。
  0本から2本へ増え、規約宣言是正と配備先自己テストの不整合を確認した。

検証対象のスクリプト、配布物、既存記録は変更していない。
