## 1. この指示書は何か

スキルの一覧ページを手書きから生成物へ変える。あわせて週ごとのスキルの状態を記録する台帳を新設する。今週を基準点として記録を始め、翌週から「何本増えたか」と「どのスキルが書き直されたか」を出せる状態にする。

## 2. なぜ必要か

`docs/guides/成果物一覧.html` には生成器が無い。`成果物一覧` という文字列を含むスクリプトはリポジトリ内に0件で、生成物であることを示す目印も入っていない。52行の表を人が並べたページである。

このままでは週ごとの更新が回らない。毎週52行を手で直すことになり、スキルの中身と表示がずれても誰も気づけない。

週ごとの増減を後から復元することもできない。コミットの全34件が 2026-08-21 の同一日にあり、最古のコミットが「【初期化】履歴を作り直して単一の初回コミットとする」である。`.claude/skills/` を変更したコミットもこの1件だけで、タグは0件である。先週が何本だったかを示す記録がリポジトリのどこにも無い。

したがって今週を基準点として記録を始めるほかない。

## 3. やること

### 3.1 週ごとの状態を記録する

`docs/scripts/snapshot-skills.sh` を新設する。

引数は次の3つとする。

- `--ledger <台帳のパス>` — 既定は `docs/tasks/work-records/週次スナップショット.md`
- `--week <YYYY-Www>` — 既定は今日が属する週（`date +%G-W%V` の値）
- `--self-test`

`.claude/skills/*/` を走査し、スキル1本につき次の4項目を取る。

| 項目 | 取り方 |
|---|---|
| 日本語名 | SKILL.md の設定欄の `日本語名` |
| 説明 | SKILL.md の設定欄の `description` |
| 段の数 | SKILL.md の `^## Phase` に一致する行の数 |
| 道具の数 | `scripts/` 配下のファイル数。フォルダが無ければ 0 |

台帳の `## 記録` 見出しの直後へ新しい週の節を足す。新しい記録が上に来るようにする。節の形は次のとおり。

```
### 2026-W34

**基準日**: 2026-08-21
**基準のコミット**: <40文字のコミット番号>
**スキル本数**: 52

| スキル | 日本語名 | 説明 | 段の数 | 道具の数 |
|---|---|---|---|---|
```

同じ週の節が既にあれば、上書きせずに終了コード1で拒否する。二重に記録することを防ぐためである。

`mktemp` を使う場合は判定不能規約（`.claude/rules/always/verification/indeterminate-result/rule.md`）に従う。失敗したら `[UNKNOWN]` を出して終了コード2で終える。

### 3.2 前の週と突き合わせる

`docs/scripts/compare-skill-snapshots.sh` を新設する。

引数は `--ledger <台帳のパス>` と `--self-test` の2つとする。

台帳の最新2件の節を読み、次の3条件でリリース候補を挙げる。

| 条件 | 何が変わったか | 見る項目 |
|---|---|---|
| 新しく増えた | 選べるものが増えた | 前の週に無く今週にあるスキル |
| 選び方が変わった | 利用者の選び方が変わった | 日本語名または説明 |
| できることが変わった | 手順か道具が変わった | 段の数または道具の数 |

候補ごとに、どの条件に当たったかを出力する。

前の週の節が無ければ「基準点のみ。比較できません」と出して終了コード0で終える。これは不合格ではない。

採否は人が決める。決めた結果は台帳の当該週の節へ「判断の記録」として書き足す。

### 3.3 成果物一覧を生成物へ変える

`docs/scripts/build-deliverable-list.sh` を新設する。

引数は次の3つとする。

- `--output <出力先>` — 既定は `docs/guides/成果物一覧.html`
- `--ledger <台帳のパス>` — 既定は `docs/tasks/work-records/週次スナップショット.md`
- `--self-test`

現行の `docs/guides/成果物一覧.html` の見た目を保つ。配色・版面・表の列（成果物の名称・日本語の名称・説明・ガイド）を変えない。

表の中身は `.claude/skills/*/SKILL.md` の設定欄から作る。

台帳の最新2件から「今週の変化」の節を作り、統計欄の直後へ置く。この節に書くのは次の3つだけとする。

1. 今週の本数と前の週との差
2. 新しく加わったスキルの名前とできること
3. 書き直したスキルの名前と何が変わったか

コミット番号・検査のコマンド・「実測値」等の語を出力してはならない。`docs/guides/` 配下は社外向けの記述制限（`.claude/rules/always/docs/audience-split/rule.md`）が働き、これらを含むと書き込み自体が止まる。

### 3.4 第1層の機械検証へ載せる

`generation-engine/scripts/tests/` へ次の3本を置く。いずれも本体の `--self-test` を呼び、終了コードをそのまま返すだけのものとする。

- `check-skill-snapshot.sh`
- `check-skill-snapshot-compare.sh`
- `check-deliverable-list-build.sh`

`docs/scripts/` 配下は第1層の集約（`generation-engine/scripts/verification/run-layer-machine-checks.sh`）の走査対象に入らない。走査対象は `generation-engine/scripts/` と `delivery-payload/templates/rules/checkers/` の2箇所だけである。ラッパーを置くことで集約に載せる。

### 3.5 設計判断を書く

新設する6本について設計判断を書く。置き場は `.claude/rules/scoped/portal/page-conventions/rule.md` の `## 設計判断` 節とする。同節には `check-skill-frontmatter.sh` の設計判断が既にあり、スキルを対象とするスクリプトの設計判断をここへ置く先例が成立している。

見出しは4つとする。本体3本はそれぞれ独立の見出しとし、ラッパー3本は1つの見出しにまとめる。

| 見出し |
|---|
| `### snapshot-skills.sh` |
| `### compare-skill-snapshots.sh` |
| `### build-deliverable-list.sh` |
| `### generation-engine/scripts/tests/ のスキル週次記録ラッパー3本` |

各見出しに4項目（必要性・代替案を採用しなかった理由・保守責任者・廃棄条件）を書く。

## 4. 完了の判定

1. 週ごとの状態を記録するスクリプトが自己テストを通る
2. 前の週と突き合わせるスクリプトが自己テストを通る
3. 成果物一覧を作るスクリプトが自己テストを通る
4. 台帳の最新の節が持つスキル本数が、スキルのフォルダ数と一致する
5. 成果物一覧を作り直しても既存の内容と差が出ない
6. 成果物一覧が社外向けの記述制限の検査を通る
7. 第1層の集約の一覧に、新設したラッパー3本が載る
8. 設計判断の4つの見出しが規約へ書かれている

## 5. 触らない範囲

| 対象 | 理由 |
|---|---|

| `docs/scripts/` の既存3本 | 対象が違う |

## 7. 他の指示書との関係

依存する指示書は無い。

着手前に `docs/tasks/` の他の指示書を確かめる。`docs/guides/成果物一覧.html` と `docs/scripts/` を対象とする指示書が他にあれば、同時に着手しない。

## 8. この指示書の位置づけ

週次の報告という1つの目的に対し、記録・突き合わせ・表示の3つをまとめて1件とした。3つは互いに依存する。記録が無ければ突き合わせができず、突き合わせが無ければ表示する内容が作れない。片方だけを入れても報告が出ないため分割しない。

スキル自身への版番号の付与は含めない。git が版を持つため設定欄を触る必要が無い。52本すべてを改修する作業は、この目的に対して重すぎる。
