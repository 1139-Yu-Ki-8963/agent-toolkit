# テストの一覧を全種別から作れるようにする指示書

## 1. この指示書は何か

テストケース一覧とテスト観点表が画面を前提に作られており、画面を持たない対象プロジェクトでは1件も生成されない。集約元を全種別へ広げ、呼び出しの手順へ載せる。

## 2. なぜ必要か

ある対象プロジェクトのポータルを実測すると、一覧フォルダに8件（API・テーブル・バッチ・メッセージ・外部連携・帳票・機能・用語辞書）はあるが、テストの一覧が1件も無かった。

原因は呼び出しの構造にある。

| 何が | どうなっているか |
|---|---|
| テスト観点表 | 派生一覧として扱われ、前提条件が「メッセージ定義書または画面ごとの単体テスト観点表が存在すること」 |
| テストケース一覧 | 種別ループにも派生一覧にも含まれず、呼び出し元が0件 |
| スキル自身の説明 | 「画面ごとのテスト仕様書を横断集約」と述べ、画面を前提としている |

当該プロジェクトは画面が対象外の宣言を持ち、API・テーブル・バッチ・外部連携・機能・帳票のみを扱う。**画面前提の条件が成立せず、両方とも起動されない。**

配布物の側もこの未生成を把握しており、「60件中57件が出力あり、3件が未生成」と記録している。ただし**原因が画面前提の設計であることと、画面が対象外のプロジェクトでは構造的に生成できないことは書かれていない。**

## 3. やること

### 第1に、集約元を画面から全種別へ広げる

集約元は各単位の `テスト設計/` 配下のテスト設計書とする。7種別×2枚が対象になる。画面固有の「操作シナリオ仕様書」は、画面が存在する場合のみ加える。

前提条件を「いずれかの種別のテスト設計書が出力先に存在すること」へ改める。

### 第2に、テストケース一覧を呼び出しの手順へ載せる

現在は呼び出し元が0件であり、スキルが存在しても起動されない。種別ループの後に走る派生一覧として、テスト観点表と同じ位置へ加える。

### 第3に、集約した行へ種別の列を持たせる

どの種別の単位から来た行かを、納品先が判別できるようにする。

## 4. 完了の判定

1. 集約元の定義が画面固有ではなく全種別を対象としている
2. 前提条件が「いずれかの種別のテスト設計書の存在」になっている
3. テストケース一覧が呼び出しの手順に載っている
4. 画面を持たない入力（APIのみ）を試験用に組んでポータルを生成し、テストケース一覧とテスト観点表の両方が出力される
5. 出力に種別の列があり、集約元の種別が判別できる
6. 納品完了の条件の未生成3件の記述から、テストケース一覧が外れている

## 5. 触らない範囲

- 画面向けの既存の生成経路（画面が存在する場合の振る舞いを変えない）
- 既に生成済みのポータル（再生成で足りる）
- `docs/tasks/` 配下の他の指示書

## 6. 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 種別の列の見出し | 「種別」 | 既存の一覧で別の語を使っている場合はそれに揃える |
| 画面の操作シナリオ仕様書の扱い | 画面が存在する場合のみ集約元へ加える | 画面が無くても同等の資料がある種別が見つかった場合は対象を広げる |
| 前提条件を満たさない場合の振る舞い | 一覧そのものを生成しない（現在と同じ） | 空の一覧を出すほうが納品先に親切だと判断できる根拠が得られた場合 |
| 試験用の入力をどこへ置くか | 版管理の外（一時領域） | なし |

## 7. 他の指示書との関係

`1-248`（テストケース一覧の節が異常系と境界値を含まない）と同じテスト設計書を扱うが、こちらは「一覧が生成されるかどうか」、あちらは「生成された文書の節の構成」を扱う。同時に着手すると同じテンプレートを触る可能性があるため、片方が終わってから次へ進む。

## 8. この指示書の位置づけ

画面を持たない対象プロジェクトで、テストの一覧が構造的に生成できない問題を解く。設計の前提を「画面がある」から「いずれかの種別がある」へ広げる作業として切り出した。
