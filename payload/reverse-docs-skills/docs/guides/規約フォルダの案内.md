# 規約フォルダの案内

対象プロジェクトへ納品される `docs/rules/` の全ファイルについて、それが何で、誰がいつ使い、どう繋がるかを説明する。

この文書は納品先の読み手（開発するAIエージェントと人間のエンジニア）に向けて書く。

## 1. 何のためのフォルダか

`docs/rules/` は、そのプロジェクトで守るべき取り決めを置く場所である。取り決めを文章で置くだけでなく、**違反を見つける仕組みまで含めて配る。**

規約は27件あり、全部で110行の規則を持つ。各規則には「どうやって違反を見つけるか」が書かれている。

## 2. フォルダの構成

```
docs/rules/
├── agent-operations/                    AIエージェント運用（5件）
│   ├── parent.yml
│   ├── ai-behavior/                       AIエージェント行動規約
│   ├── ai-config-asset-management/        AI設定資産の管理規約
│   ├── destructive-operation-safety/      破壊的操作の安全規約
│   ├── routine-operations/                定型運用の規約
│   └── session-management/                セッション管理規約
├── business-domain/                     業務ドメイン規約（4件）
│   └── business-rules/ calculation-rules/ glossary/ state-transitions/
├── code-standards/                      コード規約（4件）
│   └── coding-style/ component-architecture/ directory-structure/ naming/
├── development-process/                 開発プロセス（5件）
│   └── development-environment/ development-flow/ git-operations/
│       release-and-delivery/ tools-and-commands/
├── documentation-standards/             文書化規約（2件）
│   └── document-writing/ portal-maintenance/
├── non-functional-requirements/         非機能要件（5件）
│   └── availability/ observability/ performance/ scalability/ security/
└── quality-assurance/                   品質保証（2件）
    └── review-checklist/ test-policy/
```

親カテゴリが7つ、その下に子カテゴリが27ある。**子カテゴリ1つが規約1件である。**

`docs/rules/` の直下には規約の親カテゴリしか置かない。規約でないものを混ぜると、一覧を見たときに何が規約かが読み取れなくなる。

## 3. ファイルの全件

合計142ファイルが配られる。

| ファイル | 件数 | 何か |
|---|---|---|
| `rule.md` | 27 | 規約の本文。規則の表を持つ |
| `design-notes.md` | 27 | その規約をなぜ置くかの記録 |
| `rule.html` | 27 | ポータルで読むための表示用。`rule.md` から生成される |
| `parent.yml` | 7 | 親カテゴリの宣言 |
| `check-*.sh` | 25 | 規約ごとの linter |
| `check-*.test.sh` | 25 | linter の回帰テスト |
| `build-derived-rules.sh` | 1 | 規約から各ツールの設定を生成する |
| `validate-rule-definitions.sh` | 1 | 規約の書き方が正しいかを検査する |
| `check-rule-drift.sh` | 1 | 生成物が手で書き換えられていないかを見る |
| `resolve-applicable-rules.sh` | 1 | 対象ファイルに効く規約を返す |

最後の4本は `agent-operations/ai-config-asset-management/` に置く。**規約を扱う道具は、その主題を持つ規約と同じ場所に置く。** スクリプト専用のフォルダは作らない。

## 4. rule.md の中身

### 4.1 front matter

ファイルの先頭に13個の鍵を持つ。

| 鍵 | 何を表すか |
|---|---|
| `key` | 規約の英語キー。フォルダ名と一致する |
| `title` | 日本語の表示名 |
| `parent` | 親カテゴリのキー |
| `summary` | 規約の要約1文 |
| `scope` | `always`（常時読む）か `scoped`（該当ファイルのときだけ読む）か |
| `paths` | `scoped` のとき、どのファイルに効くか（glob の配列） |
| `enforcement` | `advisory`（機械が検知する）か `none`（検知しない）か |
| `checkable` | linter を持つか |
| `checker` | linter のファイル名 |
| `uncheckableReason` | linter を持たない理由 |
| `formatter` | 整形の道具の指定 |
| `status` | `approved`（配布の対象）か `draft`（下書き）か |
| `origin` | 出自。`template` / `proposal` / `manual` |

`scope` と `paths` が読み込みを制御する。**触っているファイルに関係する規約だけが読まれる。** 27件すべてを常に読むわけではない。

### 4.2 節

4つの節を持つ。

```
## 概要                    この規約が何を扱うか
## 規則                    守るべきことの表
## このプロジェクトの規則    リバース解析が観測から起こした規則
## 違反時の手順             機械が検知する規約だけが持つ
```

### 4.3 規則の表

規則・内容・根拠・検査の4列を持つ。

```
| 規則 | 内容 | 根拠 | 検査 |
|---|---|---|---|
| 金額を小数で扱わない | 金額の計算に、誤差の出る小数の型を使わない | 誤差の出る小数の型は10進の値を正確に表せない | 静的解析: 金額を扱う項目の型に、誤差の出る小数が使われていないかを走査する |
```

**検査の列が、この規約体系の中心である。** そこに「誰がどうやって違反を見つけるか」が書かれている。

## 5. 違反を見つける4つの手段

検査の列は `<手段>: <方法>` の形で書く。手段は4つある。

| 手段 | 出現数 | 誰が確かめるか |
|---|---|---|
| 静的解析 | 109 | 同じフォルダの linter が自動で止める |
| テスト | 12 | 単体テスト設計書のテスト観点にもとづく試験 |
| レビュー | 26 | レビュー専門のエージェント |
| 判定不能 | 1 | 検査に必要な値が決まっていない。誰も確かめられない |

規則は110行だが、手段の合計は148になる。**1つの規則が複数の手段を持つためである。**

```
| 復旧の手順を書いて試す | 障害からの復旧の手順を書き、実際に試して動くことを確かめる | … |
  静的解析: 復旧の手順書が実在するかを走査する
  ／ テスト: 手順に従って復旧を実行し、目標の時間内に戻ることを確かめる |
```

手順書があるかは機械が見られる。実際に戻れるかは動かさないと分からない。**片方だけでは、規則が求めている確認にならない。**

## 6. 静的解析はどう動くか

規約が `checker` を宣言していると、その linter が同じフォルダに置かれる。

```
docs/rules/business-domain/calculation-rules/
├── rule.md                        「金額を小数で扱わない」等の規則
├── check-currency-float-type.sh   その規則を検査する linter
└── check-currency-float-type.test.sh
```

`build-derived-rules.sh` が、この linter を `.claude/settings.json` などへ hooks として登録する。**登録後は、規約に反する操作をした瞬間に止まる。**

1つの linter は、その規約のうち手段に静的解析を含む規則を**すべて**検査する。規則ごとに linter を分けない。

linter を持たない規約が2件ある（定型運用の規約と拡張性要件）。どちらも規則が意味の理解を要し、機械では判定できない。**数を揃えるために動かない linter を作らない。**

## 7. レビューはどう動くか

検査の手段が `レビュー:` の規則は、機械では判定できない。レビュー専門のエージェント（`rule-reviewer`）が判定する。

### 7.1 流れ

```
AIがファイルを変更
      ↓
resolve-applicable-rules.sh <変更したファイル>
      ↓  そのファイルに効く規約を返す
rule-reviewer へ委任（規約のパスと対象を渡す）
      ↓  レビュアーが規約を Read して照合
規則ごとに PASS / FAIL / 対象外
      ↓
開発フローのゲートで、成果物と一緒にユーザーへ提示
```

### 7.2 作った本人は判定しない

書いた本人が自分で判定すると、書いたときの前提をそのまま正しいものとして扱う。前提そのものが誤っていた場合、その誤りは判定を通過する。**作成の文脈を持たないエージェントが、規約だけを頼りに判定する。**

レビュアーは読み取りの道具しか持たない。判定の途中で対象を書き換えられない。

### 7.3 レビュアーは1体

規約の親カテゴリごとに担当を分けない。分けると、規約を1件足すたびにどの担当が見るかを決めることになる。**1体が全てを見るなら、規約が増えても構造は変わらない。**

### 7.4 観点はレビュアーに持たせない

レビュアーの定義に観点を書かない。委任時に渡された `rule.md` を読んで判定する。**規約が唯一の情報源であり、レビュアーは読む側に徹する。**

観点だけを集めた別のファイルも作らない。作ると規約の規則と観点の対応が切れ、片方だけが更新される。

## 8. テストはどう動くか

検査の手段が `テスト:` の規則は、単体テスト設計書のテスト観点へ入る。テスト方針書がこの受け皿の規則を持つ。

```
規約の検査列（テスト:）
      ↓
各設計単位の単体テスト設計書 §1 テスト観点
      ↓
ポータルのテスト観点一覧
```

規約が求めたテストが、どのテストで担保されるかを一覧から辿れる。

## 9. 開発フローとの繋がり

納品されるスキル `dev-flow` が、5つのフェーズで開発を進める。

```
Phase1 要件すり合わせ
Phase2 基本設計
Phase3 詳細設計
Phase4 実装プラン策定
Phase5 実装と動作確認
```

**各フェーズの終わりに、成果物とレビュー結果をユーザーへ提示する。** ユーザーはその両方を見て、次へ進んでよいかを判断する。

```
【ゲート】
  提示物: 反映した設計内容と、規約レビューの結果
  問い:   「この内容で設計を確定してよいですか？」
```

指摘があってもゲートは出す。ユーザーが「今回は許容する」と判断できるためである。**禁じているのは、指摘を伏せて確定を問うことである。**

レビュアーが配られていない環境では、レビューの手順を飛ばす。飛ばしたことをゲートで明示する。**自分で判定して代替してはならない。**

## 10. 規約を変えるとき

### 10.1 規則を足す・直す

`rule.md` の `## 規則` の表を編集する。検査の列には必ず手段を書く。

```
静的解析: <ファイルの何を走査するか>
テスト: <何を実行して何を観測するか>
レビュー: <何を読んで何を判断するか>
判定不能: <何が定義されていないか>
```

手段を書かないと `validate-rule-definitions.sh` が生成を止める。

### 10.2 このプロジェクト固有の規則を足す

`## このプロジェクトの規則` の表へ書く。`## 規則` と同じ4列である。

この節はリバース解析が対象プロジェクトを観測して起こす。上限や形式のような、プロジェクトごとに違う値もここへ入る。**`## 規則` の側は、どのプロジェクトでも変わらない役割と方針の水準に留める。**

### 10.3 変えたあとに実行するもの

```
bash docs/rules/agent-operations/ai-config-asset-management/validate-rule-definitions.sh docs/rules
bash docs/rules/agent-operations/ai-config-asset-management/build-derived-rules.sh docs/rules . --apply
```

1つ目が規約の書き方を検査し、2つ目が `.claude/rules/` などの設定を生成し直す。

### 10.4 生成物を手で書き換えない

`.claude/rules/` や `.cursor/rules/` は `docs/rules/` から生成される。手で書き換えると、次の生成で消える。

書き換えられていないかは次で見る。

```
bash docs/rules/agent-operations/ai-config-asset-management/check-rule-drift.sh docs/rules .
```

規約から生成し直して、いまある生成物と比べる。**記録を持たず、毎回その場で作って比べる。** そのため規約が常に唯一の正になる。

## 11. 各ファイルの詳細

### parent.yml

親カテゴリの宣言。2つの鍵を持つ。

```yaml
key: code-standards
title: コード規約
```

### rule.md

規約の本文。4節の詳細は第4節を参照。

### design-notes.md

その規約をなぜ置くかの記録。規約の中身が変わるとき、元の判断を知るために読む。

### rule.html

`rule.md` をポータルで読むための表示用。`build-portal.sh` が生成する。**直接編集しない。**

### check-*.sh と check-*.test.sh

規約ごとの linter とその回帰テスト。linter は `--self-test` を持ち、テストはそれを呼ぶ。

```
bash docs/rules/<親>/<子>/check-<名前>.test.sh
```

### build-derived-rules.sh

規約から `.claude/rules/`・`.cursor/rules/`・`AGENTS.md` の索引・各ツールの hooks 登録を生成する。一方向の生成であり、生成物から規約へ戻る経路はない。

### validate-rule-definitions.sh

規約の書き方を検査する。front matter の鍵の値域、規則表の列数、検査列に手段があるかなどを見る。

### check-rule-drift.sh

生成物が手で書き換えられていないかを見る。第10節を参照。

### resolve-applicable-rules.sh

対象ファイルに効く規約を返す。

```
bash docs/rules/agent-operations/ai-config-asset-management/resolve-applicable-rules.sh src/app.ts
```

出力は対象ファイルと `rule.md` のパスをタブで区切った形で、1つの規約につき1行を返す。効く規約が無ければ `(none)` を返す。

## 12. 規約の外にあるもの

### .claude/agents/rule-reviewer.md

レビュー専門のエージェントの定義。第7節を参照。

### .claude/skills/

3本のスキルが配られる。

| スキル | 何をするか |
|---|---|
| `dev-flow` | 5つのフェーズで開発を進める。各フェーズでレビューを回す |
| `importing-rule-proposals` | 規約の提案を取り込んで `docs/rules/` へ書く |
| `syncing-derived-artifacts` | 生成物を作り直し、ずれを見つけ、戻す |

### .claude/rules/ と .cursor/rules/ と AGENTS.md

`docs/rules/` から生成される。**直接編集しない。**
