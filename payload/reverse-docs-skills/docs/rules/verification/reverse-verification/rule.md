# リバース検証運用規約（REVERSE-VERIFICATION）

リバース設計スキル群の検証手順を、実行側リポジトリの散文から本規約へ移し、判定の基準を機械が読める形で定義する。

## 規則

| 規則 | 内容 | 根拠 | 検査 |
|---|---|---|---|
| 出力先の分離 | 検証の生成物を納品先へ出力しない。出力先は版管理の外に置く | 納品物へ検証専用の生成物を混入させないため | 判定不能: 出力先の指定は実行者の運用に依存し、静的解析では判定できない |
| 既存成果物の入力禁止 | 既存の成果物（検証対象の生成器が過去に出力した生成物）を検証の入力として使わない。テンプレートと疑似入力は含まない | 検証の対象と入力を分離し、自己参照による見かけ上の合格を防ぐため | 判定不能: 入力データの由来は静的解析では判定できない |
| 実行省略の禁止 | 実行を伴う検証を「実行が要る」という理由で省略しない。省略してよいのは実行を試みたうえで実行できなかった場合だけである | 退避の常態化を防ぐため（登録済み7件が登録以降1件も実行されなかった実績がある） | 判定不能: 実行を試みた形跡の有無は退避記録の文面判断を要し、様式が固まっていないため機械検証できない |
| コミットハッシュの明記 | 判定の結果には、検証した時点のコミットハッシュを全長で必ず添える。 | 判定結果がどの版に対するものかを後から追跡できるようにするため。 | 静的解析: `docs/scripts/check-verdict-hash-ancestry.sh` が台帳と判定表のコミット欄のハッシュを、統合先の祖先として確かめる。 |
| 解決記録の保存 | 解決と判定した指摘を記録から消すときは、判定の根拠と再実行できる検査の手順を残す。 | 判定の追跡可能性と再現性を保つため。 | 静的解析: `docs/scripts/check-ledger-completion-reproducibility.sh` が完了行の再実行コマンド、または理由の有無を確かめる。 |

## このプロジェクトの規則

| 規則 | 内容 | 根拠 | 検査 |
|---|---|---|---|
| 観測なし | このリポジトリ自身の検証運用は上記5規則で閉じており、対象リポジトリの観測から新たに起こす規則は無い | 本規約はリバース設計スキル群自身の検証運用を定義するものであり、対象プロジェクトの観測結果ではないため | 観測なし |

## 背景

検証の定義がこれまで実行側リポジトリの散文に置かれていた。そのためスキルを変えても手順が追従しなかった。判定の基準も文章のままで、機械が読めなかった。実行を伴う検証は「実行が要る」という理由で退避でき、退避先に積まれた 7 件は登録の以降に 1 件も実行されていない。

## 規約

1. 検証の生成物を納品先へ出力しない。出力先は版管理の外に置く
2. 既存の成果物を入力として検証しない。既存の成果物とは、検証の対象である生成器が過去に出力した生成物を指す。テンプレートと疑似入力は含まない
3. 実行を伴う検証を「実行が要る」という理由で省略しない。省略してよいのは実行を試みたうえで実行できなかった場合だけである。退避の記録には、何をどう試して何がどう失敗したかを書く
4. 判定の結果には、検証した時点のコミットハッシュを全長で必ず添える
5. 解決と判定した指摘を記録から消すときは、判定の根拠と再実行できる検査の手順を残す

## 検証の実行方法

各スクリプトは `generation-engine/scripts/verification/` 配下にある。

| 目的 | コマンド |
|---|---|
| 第 1 層の実行 | `run-layer-machine-checks.sh` |
| 疑似入力の整備 | `prepare-verification-input.sh --output <出力先>` |
| 第 3 層の実行 | `run-layer-full-pipeline.sh --output <出力先>` |
| 網羅の判定 | `check-coverage.sh --output <生成物のディレクトリ>` |
| 再現の判定 | `check-reproducible.sh --first <1回目> --second <2回目>` |
| 健全の判定 | `check-sound.sh --output <生成物のディレクトリ>` |
| 別モードの骨格 | `run-authoring-mode.sh --output <出力先> --enable` |

## 機械強制

| timing | スクリプト | 挙動 |
|---|---|---|
| 手動実行・第1層の集約 | `docs/scripts/check-verdict-hash-ancestry.sh` | 台帳と判定表のコミット欄のハッシュが統合先の枝の祖先として実在するかを確かめる。1件でも欠ければ終了コード1 |
| 手動実行・第1層の集約 | `docs/scripts/check-ledger-completion-reproducibility.sh --strict` | 完了と書いた状態行に再実行できるコマンド、または機械で確かめられない理由があるかを確かめる。両方を欠く見出しが1件でもあれば終了コード1 |

規約4（版の明記）と規約5（解決記録の保存）は上の2件が担う。
当初はどちらも目視判断を要するとしていたが、実測（2026-08-28）で
機械的に確かめられることを確認したため、判定不能から静的解析へ改めた。

残る3規約（出力先の分離・既存成果物の入力禁止・実行省略の禁止）には
hook による機械強制を設けない。

理由は次のとおりである。退避の記録から「実行を試みた形跡があるか」を機械で判定するには、記録の書き方に依存する判定が要る。記録の様式が固まる前に検査を作ると、様式の変更のたびに検査が壊れる。まず本規約と検証のスクリプトを運用し、記録が実際にどう書かれるかを見てから判断する。

この判断は、本規約を書いた時点では規約 5 項目の違反を機械で止められないことを意味する。この限界を明記する。

各スクリプトの `--self-test` は、上表の第 1 層の実行（`run-layer-machine-checks.sh`）に含まれる。これが唯一の自動検査である。

## 違反検知時の手順

機械強制が無いため、注入タグごとの手順ではなく、規約 5 項目それぞれについて違反を見つけたときの手順を書く。

### 規約 1（出力先の分離）に違反した場合

1. 納品先に混入した検証の生成物を洗い出す
2. 版管理の外（`.gitignore` 対象のディレクトリ等）へ移すか削除する
3. 検証コマンドの `--output` 引数を版管理の外へ向け直してから再実行する

### 規約 2（既存成果物の入力禁止）に違反した場合

1. 検証の入力に使った成果物が、検証対象の生成器自身の過去の出力かどうかを確認する
2. 該当する場合、その検証結果を無効として扱う
3. `prepare-verification-input.sh` で作った疑似入力に差し替えてから再実行する

### 規約 3（実行省略の禁止）に違反した場合

1. 「実行が要る」とだけ書かれた退避記録を洗い出す
2. 対応する検証コマンドを実際に実行する
3. 実行できた場合は結果を記録に反映する
4. 実行できなかった場合は、試した方法と失敗の内容を記録へ書き足す

### 規約 4（コミットハッシュの明記）に違反した場合

1. コミットハッシュを欠いた判定結果を洗い出す
2. 検証した時点の `git rev-parse HEAD` の全長ハッシュを判定結果へ追記する

### 規約 5（解決記録の保存）に違反した場合

1. 根拠や再実行手順を残さずに消された指摘がないかを記録の履歴から確認する
2. 判定の根拠と再実行できる検査の手順を書き戻す
