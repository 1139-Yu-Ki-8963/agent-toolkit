# ポータル HTML 規約（PORTAL-PAGE-CONVENTIONS）

リバース設計ポータルの生成 HTML に適用する合格基準。テンプレートから生成された全ページが統一されたデザインシステムと構造規約に準拠していることを検証する。portal-reviewer が本ファイルを Read して照合する。

## 適用対象

`delivery-payload/templates/` 配下のテンプレートから生成された HTML ファイル、および `generation-engine/samples/` 配下のサンプル HTML。ポータルトップも共通シェルを使うため、他のページと同じ観点で検査する。

文書ビューア型も共通シェルを使うため、他のページと同じ観点で検査する。文書の本文は共通シェルのメインペイン内でスクロールする。

`generation-engine/samples/規約提案/` と `delivery-payload/templates/rule-proposal/` 配下は適用対象から外す。規約提案 HTML（サンプルとその生成元テンプレート）はポータルのページではなく、リポジトリ外へ出力して現場のエンジニアが判定するための独立した成果物である。ポータル共通シェルを使わず、意匠は `delivery-payload/references/規約定義と派生生成の設計.md` が参照する別の定義に従う。同じ検査を当てると、意匠の違いをすべて不合格として数えることになる。

スキルガイド HTML（`.claude/skills/*/references/guide.html`）も適用対象から外す。スキルの使い方を読む人へ向けた説明書であり、成果物のポータルとは読み手も用途も異なる。共通シェルを使わず独自の意匠を持つため、同じ検査を当てるとスキルを 1 本増やすたびに不合格が増え、件数を合否の判定に使えなくなる。ガイド HTML の体裁は `.claude/rules/always/skill-guide/html/rule.md` が担当する。

`delivery-payload/templates/partials/` 配下も適用対象から外す。ページへ埋め込む断片であり、単体では明暗の色定義も全画面レイアウトも持ちえない。完成したページに求める基準を断片へ当てることになる。

次の4資料も適用対象から外す。

- `docs/guides/reverse-docs-overview.html`
- `docs/design/portal/ポータル設計基盤.html`
- `docs/guides/納品物ガイド.html`
- `docs/guides/成果物一覧.html`

いずれもこのリポジトリ自身の説明資料であり、生成されるポータルのページではない。
除外はディレクトリではなくファイル名で指定する。
対象リポジトリでは `docs/` 配下にポータルのページが置かれることがある。
ディレクトリごと外すと検査すべきページまで落ちるためである。

以上の除外を入れた結果、本規約の検査は不合格 0 件を合格の基準として使える。ただし `generation-engine/scripts/tests/test-portal-conventions.sh` の除外リスト（`-not -path` の一覧）はディレクトリ走査モードのみに効く実装であり、ファイル単体を指定して実行した場合はこの除外を経由しない。`docs/guides/納品物ガイド.html` を単体指定で検査すると FAIL するが、これは検査対象外という本節の判断のとおりであり、ページとしての不合格ではない。

対象アプリのリポジトリで検証する場合、`test-portal-conventions.sh <ディレクトリ>` は配下の `*.html` を無差別に再帰走査するため、このツール群が生成した HTML と対象アプリが元から持つ無関係な HTML（このツール群と無関係な既存ドキュメント等）が混ざる（改善課題キー: ポータル規約検査-対象範囲）。生成物だけを対象にするには `test-portal-conventions.sh --file-list <ファイル一覧のパス>`（1 行 1 パスの改行区切りテキスト）を使う。一覧は `check-derived-drift.sh` が保守する `derived-fingerprints.json` のキーから組み立てることを想定する。既定のディレクトリ・単一ファイル指定の挙動は変更しない。

## カラーシステム

| 観点キー | 検査内容 |
|---|---|
| 色トークン-旧値禁止 | 刷新前のトークン値がファイル内に存在しないこと。ライト系は `#F6F8FA`・`#D1D9E0`・`#AFB8C1`・`#0969DA`・`#218BFF`・`#DDF4FF`・`#54AEFF`・`#BC4C00`・`#FFF1E5`・`#1A7F37`・`#DAFBE1`・`#CF222E`、ダーク系は `#15171C`・`#1C1F26`・`#21262D`・`#30363D`・`#484F58`・`#E8E5DC`・`#B6B3AB`・`#888784`・`#58A6FF`・`#79C0FF`・`#132D4B`・`#1F6FEB` |
| 色トークン-新値存在 | `#0F1217`（ダークの背景）・`#4CC2FE`（ダークのアクセント）・`#FF6E4F`（差し色）が CSS 変数定義に存在すること |
| テーマ-定義 | `prefers-color-scheme` のメディアクエリと、`data-theme="dark"`・`data-theme="light"` の両方の属性セレクタが存在すること |

## 全画面フィットレイアウト

| 観点キー | 検査内容 |
|---|---|
| 全画面-高さ固定 | ページコンテナに `height: 100vh` が指定されていること。`min-height: 100vh` は違反 |
| 全画面-overflow制御 | ページコンテナに `overflow: hidden` が指定されていること |
| 全画面-スクロール領域 | メインコンテンツ領域（`.table-area`・`.dp-main`・`.pt-main`・`.pt-tablewrap` のいずれか）に `overflow-y: auto` または `overflow: auto` が指定されていること |
| sticky-thead | テーブルを持つページで `thead` に `position: sticky` が指定されていること |
| 共通シェル-サイドバー | `class="pt-sidebar"` が存在すること |
| 共通シェル-方眼紙 | 方眼紙背景の `background-size` 指定が存在すること |

## デザインの基本形

| 観点キー | 検査内容 |
|---|---|
| 角丸-ゼロ | `border-radius` の値が `0` 以外にならないこと。刷新後のデザインは角丸を使わない |
| 影-オフセットのみ | `box-shadow` にぼかし半径を持つ影が無いこと。3 つ目の長さが `0` 以外の指定を禁止する。`inset` 指定は対象外 |

## 一覧ページ固有（id="unit-manifest" または id="screen-manifest" を持つページ）

| 観点キー | 検査内容 |
|---|---|
| 一覧-列数上限 | `<thead>` 内の `<th>` が 6 個以下であること（シェブロン列含む。JS による任意列追加は対象外）。静的な `<thead>` は画面名・ルート・区分の 3 列を持ち、画面区分・必要権限・関連API・設計書は値が 1 件でもある場合のみ JS が実行時に任意列として末尾へ追加する。画面 ID は列ではなく展開行の詳細に表示する |
| 一覧-展開グループ分離 | JS 内に `detail-group-label` と `evidence` の両キーワードが存在すること |
| 一覧-details禁止 | `<details class="module-group">` が存在しないこと。ただし、分割軸を宣言するページは除外する。分割軸の宣言は `data-split-axis="<軸キー>"` の有無で判定する |
| 一覧-common-files禁止 | `class="common-files"` が存在しないこと |
| unresolved-条件付き | unresolved セクションが `empty` または `has-items` のクラスで条件分岐していること |
| 一覧-分割軸マーカー | `<details class="module-group">` を使うページは、その群を包む要素に `data-split-axis="<軸キー>"` を持つこと。分割を宣言していないページで `details` を使うことを禁止する |

## ポータルトップの画面なし縮退

`portal-catalog.json` の blueprint が `disabledWhenEmpty: true` を持つ種別は、対象リポジトリに実ファイルが 0 件でもカードを消さず、選べない状態で残す。

| 観点キー | 検査内容 |
|---|---|
| 縮退-無効カード表示 | `disabledWhenEmpty: true` の種別が 0 件のとき、カードが消えずに `data-disabled="true"` を持って残ること |
| 縮退-リンク無効化 | 無効カードがリンクとして機能しないこと（`href` を持たないか `aria-disabled="true"` を持つ） |

## 重要度コールアウト

通常表へ埋没させてはいけない注意喚起は、共通シェルの `.pt-callout` と重要度修飾クラスを組み合わせて表示する。
見出しをコールアウトの先頭要素に置き、色帯とアイコンの両方で重要度を区別する。

| 重要度 | CSSクラス | Material Symbols名 | 適用対象 |
|---|---|---|---|
| 注意 | `.pt-callout.pt-callout--caution` | `info` | 補足確認が必要だが、作業を継続できる事項 |
| 警告 | `.pt-callout.pt-callout--warning` | `warning` | 未解決リスク、要確認事項一覧、判断前に解消すべき事項 |
| 重要 | `.pt-callout.pt-callout--important` | `priority_high` | 承認済み決定、変更禁止条件、見落とすと成果物の意味が変わる事項 |

要確認事項一覧・未解決一覧は1件以上ある場合だけ「警告」を適用する。
0件を示す空状態へ警告色を付けない。
アイコンはGoogle Fonts CDNから読み込むMaterial Symbols Outlinedを、`material-symbols-outlined pt-callout__icon`の専用`span`で表示する。
共通CSSには`info`・`warning`・`priority_high`だけの公式フォントサブセットを埋め込み、CDN遮断時も同じアイコン表示を保つ。
本文の強調だけを目的にコールアウトを乱用せず、通常の説明は従来のパネル・表・注記を使う。

## 設計判断

### shell-injection.sh

**必要性**: 共通シェル（サイドバー・フッター・方眼紙背景）を22本のテンプレートへ入れる。
実体を1箇所で保守しながら、共通資産をインライン注入した単一HTMLとして出力する必要がある。
Material Symbols OutlinedのGoogle Fonts CDNだけは、アイコン表示に必要な外部依存として許可する。
同じ3アイコンの公式フォントサブセットを共通CSSへ埋め込み、オフライン表示を維持する。
既存の`tokens.css`注入と同じマーカー置換を使い、サイドバーのナビ項目はカタログから組み立てる。
組み立てとプレースホルダ解決を6本のビルドスクリプトへ複製すると、保守点が6倍になる。
共通関数を1本のスクリプトに閉じ、各ビルドスクリプトが`source`して呼ぶ。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: ビルドスクリプトから呼ぶ共通関数であり、対話セッションのツール呼び出しでは代替できない
- 既存 Makefile ターゲット拡張: このリポジトリに Makefile は存在せず、新規導入は本スクリプト専用の依存を増やすだけになる
- package.json scripts 追加: 同様に、このリポジトリはビルド設定を持たない
- `render-template.sh` への統合: あちらは汎用の文字列置換エンジンであり、カタログの構造やサイドバーの仕様を知るべきでない。関心が異なる

**保守責任者**: 人手（ユーザー）。`partials/` のファイル構成やマーカー名を変える場合は、本スクリプトと `page-conventions/rule.md` を同時に更新する。

**廃棄条件**: 共通シェルを廃止した時、またはテンプレートの部分結合をビルド基盤が標準で提供するようになった時。

### unit-axes.sh

**必要性**: 分類軸と任意列の宣言（`delivery-payload/references/unit-axes.json`）は、リポジトリ既定・プロジェクト全種別上書き・種別別上書きの 3 階層を持つ。これらをキー単位で deep merge して解決する必要がある。この解決規則を `build-unit-list.sh` だけに実装すると問題が生じる。manifest パスだけを引数に単独実行される `validate-manifest.sh` と、`--self-test` で直接叩かれる `build-feature-list.sh` がある。この両者が、同じ規則を再実装することになる。結果として、build と validate が別の宣言を見る二重基準が生まれる。`render-template.sh` / `shell-injection.sh` と同じ共通関数として実装する。複数ビルダーが source する形で 1 本に閉じるのが唯一の現実的な手段である。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: ビルドスクリプトと検証スクリプトの双方から呼ぶ共通関数であり、対話セッションのツール呼び出しでは代替できない
- 既存 Makefile ターゲット拡張: このリポジトリに Makefile は存在せず、新規導入は本スクリプト専用の依存を増やすだけになる
- package.json scripts 追加: 同様に、このリポジトリはビルド設定を持たない
- `render-template.sh` への統合: あちらは汎用の文字列置換エンジンであり、宣言のスキーマやマージ規則を知るべきでない。関心が異なる
- `portal-catalog.mjs` と同じ Node.js 実装: 消費者が全て bash スクリプトである。`jq` は既に全ビルダーと `validate-manifest.sh` の必須依存として導入済みのため、新たに Node.js 依存を足す理由がない

**保守責任者**: 人手（ユーザー）。宣言のスキーマ（`valuePolicy` の値・`column.show` の値・`split` の構造）を変える場合は、本スクリプトの `unit_axes_validate` を更新する。あわせて `delivery-payload/references/unit-axes.json` と本 rule.md も同時に更新する。

**廃棄条件**: 分類軸の宣言化を廃止した時、または列定義の宣言解決をビルド基盤が標準で提供するようになった時。

### check-manifest-persistence.sh

**必要性**: 一覧生成スキルごとにマニフェストの永続化先が非対称だった問題（改善課題 1-136）に対し、生成後の実在を機械判定するため。定義文書の記述だけでは実際に永続化されたかを確認できない。7 種別（画面・API・テーブル・バッチ・帳票・外部連携・機能）の一覧フォルダを横断して検査する必要があり、共通関数として 1 本に閉じるのが妥当である。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 7 種別分の存在確認を毎回手動実行するとトークンを浪費し、往復検証セッションのたびに同じ確認作業を繰り返すことになる
- `validate-manifest.sh` への統合: あちらは manifest の中身（スキーマ・重複・summary 整合性）の検証を担っており、ファイルの配置場所（永続化されたかどうか）の検査は関心が異なる
- 各一覧生成スキルへの個別実装: 7 種別で同じ「HTML が実在するならマニフェストも実在するはず」という検査ロジックが重複する

**保守責任者**: 人手（ユーザー）。一覧種別を追加した場合は本スクリプトの `manifest_name_for_folder` 対応表に行を追加する。

**廃棄条件**: 一覧フォルダとマニフェスト名の対応が宣言ファイル（`delivery-payload/references/unit-axes.json` 等）から解決できるようになった時。

### check-derived-drift.sh

**必要性**: 定義から生成した派生物（ポータル HTML 等）が手作業で編集されると、定義との対応が壊れたまま気付けない。生成時にハッシュを台帳（derived-fingerprints.json）へ記録し、以後の突合で MODIFIED と DELETED と ADDED を検知する。同じ突合をコミット時 hook と CI と手動実行の 3 経路から呼ぶため、判定を 1 本のスクリプトへ集約する。判定はハッシュだけで行い、更新時刻は使わない（git checkout や別ツールでも時刻は動くため）。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 3 経路から同じ判定を呼ぶ必要があり、都度組み立てると経路ごとに判定がずれる
- 既存 test-portal-conventions.sh への同居: あちらは HTML の規約適合（色やレイアウト）の検査であり、定義と派生の一致という関心が異なる
- Makefile / package.json scripts 追加: このリポジトリはどちらも持たない

**保守責任者**: 人手（ユーザー）。検知対象を値のレベル（画面名や表示コミットの突合）へ広げる際も本スクリプトへ集約する。

**廃棄条件**: 派生アダプターと保守の仕組み（AI駆動開発セットアップ構想の Phase C と Phase D）自体を廃止した時。

### output-layout.sh

**必要性**: 生成スクリプト 26 ファイルが出力先の日本語パスを直書きしており、物理配置の変更（`docs/` への移行）が全ファイル書き換えになる。パスの定義を `delivery-payload/references/output-layout.json` へ集約し、リポジトリ既定と対象側上書きの 2 階層をキー単位で合成して解決する共通関数が必要である。解決規則を各スクリプトへ個別実装すると、生成と検証が別の宣言を見る二重基準が生まれる（`unit-axes.sh` と同じ判断）。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 生成と検証の双方から呼ぶ共通関数であり、対話セッションのツール呼び出しでは代替できない
- `unit-axes.sh` への同居: あちらは分類軸と列定義の宣言解決であり、出力配置という関心が異なる
- `render-template.sh` への統合: あちらは汎用の文字列置換エンジンであり、配置の宣言を知るべきでない

**保守責任者**: 人手（ユーザー）。配置キーを増減する場合は `output-layout.json` と本節と self-test を同時に更新する。

`layout.<種別>UnitRoot`（`screenUnitRoot`・`apiUnitRoot`・`tableUnitRoot`・`batchUnitRoot`・`reportUnitRoot`・`externalUnitRoot`・`featureUnitRoot` の7キー）は各種別の設計書単位文書だけの物理rootを表す。既定値は `screenUnitRoot=docs/design/screens`・`apiUnitRoot=docs/design/apis`・`tableUnitRoot=docs/design/tables`・`batchUnitRoot=docs/design/batches`・`reportUnitRoot=docs/design/reports`・`externalUnitRoot=docs/design/externals`・`featureUnitRoot=docs/design/features`。表示用の `kindLabels.<種別>` は物理pathへ流用しない。値は非空の安全な相対パス（`/` 区切りの1つ以上のsegment）に限定し、JSON null・空文字・絶対パス・`.`・`..`・backslash・find globメタ文字（`* ? [ ]`）を解決時に拒否する。7キーは互いに、および `unitsRoot`・`commonRoot` ともNFC比較で衝突できない（`output-layout.sh` の `output_layout_validate` が一括検査する）。`screenUnitRoot` は一覧root、画面遷移、matrix、テンプレート原本、samples、リポジトリ外の `verification/` へ連動させない。

**廃棄条件**: 出力配置の宣言化を廃止した時、または配置解決をビルド基盤が標準で提供するようになった時。

### build-confirmation-survey-data.sh

### check-pseudocode-code-mixing.sh

**必要性**: `docs/tasks/設計書へ疑似コードと戻り値を足す指示書.md` の指摘（7 種別すべてで疑似コードの節が 0 件だった）へ対応し、API・テーブル・バッチ・帳票・外部連携・画面の 6 種別の詳細設計書テンプレートへ疑似コードの節を新設した。この節は「設計書にコードをそのまま貼ることを禁じ、分岐と繰り返しの入れ子だけを日本語で書く」という線引きを持つが、この禁止は今後テンプレートを改訂する人が繰り返し守る必要があり、目視だけに頼ると言語の構文（`{` `}` `=>` `===` `;`・`if (`・`for (`・`function `）が紛れ込んでも気付けない。第 1 層の機械検証（`run-layer-machine-checks.sh`）が動的に拾える形（`--self-test` を実引数として処理する `.sh`）で置くことで、テンプレート改訂のたびに繰り返し検査される。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: テンプレートを改訂するたびに疑似コードの節を目視で確認すると、確認の省略・見落としを繰り返す
- 既存 `check-argjson-unbounded-value.sh` への機能追加: あちらは `generation-engine/scripts/` 配下のシェルスクリプト自身が持つ `jq --argjson` の安全性が関心であり、`delivery-payload/templates/` 配下の Markdown テンプレートの記述内容とは対象・判定式が異なる
- 既存 `check-design-doc-section-consistency.sh` への機能追加: あちらは節構成・表題形式の一致が関心であり、節の中身（コードが混入していないか）の検査とは判定式が異なる
- 既存 Makefile ターゲット拡張: このリポジトリに Makefile は存在せず、新規導入は本スクリプト専用の依存を増やすだけになる
- package.json scripts 追加: 同様に、このリポジトリはビルド設定を持たない

**保守責任者**: 人手（ユーザー）。検出パターン（言語の構文らしい記号・キーワード）を増減する場合は本スクリプトの `CODE_RE` を同時に更新する。

**廃棄条件**: 疑似コードの節自体を廃止した時、またはコード混入の検出を別の静的解析ツールが標準で保証するようになった時。

## 機械強制

| timing | スクリプト | 挙動 |
|---|---|---|
| build-*.sh --self-test | generation-engine/scripts/tests/test-portal-conventions.sh | 生成後 HTML の規約検査。FAIL なら self-test も FAIL |
| 手動実行 | generation-engine/scripts/check-doc-claim-freshness.sh | `docs/` 配下の Markdown を走査し、時点の表明がない未完了の断定があれば exit 1 |
| run-layer-machine-checks.sh の集約（自動収集） | generation-engine/scripts/tests/check-design-unit-file-completeness.sh | 配置の定義（design-unit-layout.json）が挙げる全種別・全phase・screenについて、宣言ファイルが実際に生成されるかを横断的に確認し、1件でも欠落すれば exit 1 |

## 違反検知時の手順

1. FAIL した観点キーを確認する
2. テンプレート（`delivery-payload/templates/` 配下）の該当箇所を修正する
3. サンプルを再生成して再検証する
