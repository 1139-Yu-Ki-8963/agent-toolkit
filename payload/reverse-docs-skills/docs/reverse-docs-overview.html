AI駆動開発セットアップ 全体ガイド

対象リポジトリを AI 駆動開発ができる状態へ整えるスキル群の全体ガイド。整える対象にコードを持つリポジトリを含むため、既存コードから設計書を書き起こすコードリバースの工程を内包する。指揮役スキルの実行ひとつで、理想的なリポジトリ体系を作ることを目指す。各スキルは単体でも動作する。

位置づけこのファイル自体が最新の記述であり、更新のたびに直接書き換える(reverse-docs-overview.html) 更新契機スキル構成・契約(contract.md)変更時 対象読者AI駆動開発セットアップの利用者・保守者 関連文書README.md · .claude/skills/orchestrating-reverse-docs-flow/references/contract.md · shared/references/リバース工程設計.md · AI駆動開発セットアップ構想.md

概要

1.1 これは何か — 対象リポジトリへの働きかけを3つの役割に分ける
セットアップ
入力
対象リポジトリ(コードの有無を問わない)
出力
AIが読む定義、各AIツールの設定フォルダ、人間向けポータル
リバース
入力
既存コード
出力
定義への事実の書き込みと、そこから導出される設計書・一覧・ポータル
保守
入力
生成済みの定義と派生物
出力
定義と派生物のずれの検知と再生成

統括スキル1本(現行名 orchestrating-reverse-docs-flow。orchestrating-ai-development-setup への改称を予定するが、本稿ではこの現行名で記す)が、セットアップとリバースとポータル生成のすべてを扱う。保守は別スキルとして枝分かれし、統括経由でも単独起動でも呼び出せる。

1.2 特徴
プロジェクトポータル
人間が読むHTMLの集まり。スキルを実行するたびにカードが増え、使い込むほど内容が育つ。
リバーススキル
facts(原本コードから抽出した宣言的契約の事実表)の封印と、再実装・比較による往復検証で、実装されていない機能を設計書へ書き込むことを防ぐ。
AI駆動開発に必要なファイル群
AGENTS.md・CLAUDE.md・.claude/・.cursor/・.codex/。同じ形式で読めるツール同士は symlink で共有し、形式が異なるツールへは変換して用意する。
保守の仕組み
規約の連動、ポータルの保守、フィンガープリント台帳による定義と派生物のずれ検知。

定義と表示名
docs/rules/ と docs/screens/ は英語の機械安定パスを使い、Markdownの日本語タイトルと分類メタデータから project-portal/規約/・画面/ の日本語表示を生成。ファイル名を日本語へ統一する必要はない
HTMLの配置
docs/ 配下にHTMLポータルを置かない。一覧・共通設計・API・テーブル・バッチ・帳票・外部連携・対応表・デザインの閲覧用成果物はすべて project-portal/ へ生成
規約本文の生成
docs/rules/ は型と定義だけの空雛形で納品し、観測した実装慣行は規約本文へ書かない。観測は規約提案という別成果物へ出し、取り込みの判断は現場のエンジニアが行う(importing-rule-proposals)
末端カテゴリの実体
docs/rules/ の親7つはグループ化のための入れ物。実体を持つのは子27の末端カテゴリに置く rule.md
規約/との連動
project-portal/規約/ では親がサブグループ、子がページとして1対1で完全一致。この対応関係は宣言として保持し、ずれ検知の対象とする。現行の20ページ構成は移行前の形で、親7・子27の確定に伴い27枚へ連動更新される(コミュニケーションのページは廃止)
docs/common/ の永続性
アーキテクチャ調査書と設計6文書は再リバース時に更新され続ける永続文書。規約提案とページ証跡が参照先として指すため、消してはならない
検証用出力: プロジェクト内に verification/ を作らない。facts・比較ログ・スクリーンショット・往復検証の証跡、作業記録・サンプル記録が必要な処理は、作成前に「リバース検証用の一時成果物を保存するフォルダを作成します。プロジェクト外の出力先を指定してください」と説明し、Claude Code は AskUserQuestion、Codex は request_user_input で保存先を確認する。確認ツールを利用できない場合は OUTPUT_PATH_REQUIRED で停止する。
2.2 プロジェクトポータル / 2.3 AIツール設定
プロジェクトポータル: project-portal/ 配下に生成する、人間が読むためのHTMLの集まり。閲覧用の成果物はすべてここへ生成する(配置定義は 2.1)。スキルを実行するたびにカードが増え、使い込むほど内容が育つ。
AIツール設定: 各AIツールが docs/ の定義へ到達するための派生アダプター一式(AGENTS.md・CLAUDE.md・.claude/・.cursor/・.codex/)。同形式は symlink 共有、異形式へは変換(.cursor/rules/ は front matter 付き .mdc へ変換、.codex/config.toml は MCP 設定を持ち、規約と指示は AGENTS.md の階層連結で届く)。
2.4 作成区分と判定原則

納品する成果物を、コード・設定・実測から事実を記入するものと、構造だけをテンプレートとして作成し、現場の明示的な根拠・判断・承認を後から記入するものに分けた一覧。テンプレート専用の行には架空の値・規約・サンプルを入れない。根拠が揃わない項目は空欄、対象外、または未確定として扱う。

リバース記入 コード・設定・facts・実測などの根拠から記入テンプレートのみ 構造だけを納品し、現場の根拠・判断後に記入

残る課題

設計書を生成するスキルは 6 種別すべてで揃い、テンプレートの章立ても入った。残るのは次の 1 点である。

課題内容
展開スクリプトテンプレートの複製と配置と検証を機械で保証する層を持つのは画面だけである。他種別はスキルの手順で配置する

基本設計書は要確認事項一覧の章を持つ。コードから導出できない事項は本文へ書かず、この章へ移す。利用者の区分・業務上の背景・制約を設けた理由がこれに当たる。

単体テスト設計書の位置づけ

単体テスト設計書は基本設計フェーズの成果物である。テスト方針書が「根拠は基本設計で確定した仕様であり、コードを根拠にしない」と定めるためである。基本設計のスキルが基本設計書を書き上げたあと、その基本設計書だけを情報源として続けて生成する。

画面は例外である。既存の単体テスト観点表は詳細設計の成果物として、実装済みの関数名を対象に書く方式で動いている。実績を尊重して現状を維持しており、他の 5 種別とは位置づけが異なる。

判定原則: コードから直接確認できる構造・値・参照はリバース記入可。コードから業務目的、設計意図、要求水準、規範、承認事項を補うことは禁止。規約は、明示された規約・運用文書・承認がない限り「観測された実装慣行」に留め、docs/rules/ の規範として確定しない。「テンプレートのみ」は空の構造・列・見出しだけを納品する意味であり、もっともらしい値を埋めたサンプルを納品する意味ではない。
