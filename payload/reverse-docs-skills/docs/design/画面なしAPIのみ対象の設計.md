# 画面なし・API のみの対象に向けた設計

**時点**: 2026-08-28 に実測した内容に基づく。

## 1. この文書は何か

検証する側は、画面を持たず API だけを持つコードを対象に AI 駆動開発を行っている。このスキル群はその対象で使えるものになっていない。個別の検査を黙らせる対応を繰り返した結果、検証側から 22 件が未解消と判定されている。本文書は、画面なし・API のみの対象でこのスキル群が成立するための設計を定め、22 件をその設計の下で解消する道筋を示す。

## 2. 対象の輪郭

検証側の対象は、台帳（`docs/tasks/指摘改善一覧.md`）に記録された実測から次の規模である。

| 種別 | 件数 |
|---|---|
| 画面 | 0（対象外） |
| API（接続窓口） | 50 |
| 機能 | 9 |
| テーブル | 35 |
| バッチ・帳票・外部連携 | 各 1 |

この輪郭を「API のみ」と呼ぶ。画面が無いだけであり、他の種別は揃っている。

## 3. 現状の欠陥（実測）

| 欠陥 | 実測 | 影響 |
|---|---|---|
| API のみの見本が無い | `generation-engine/samples-no-screen/` は 6 種別すべてを「該当なし」とする見本で、ファイル 10 件。API・テーブル・機能を 1 件も持たない | 前任の「画面 0 件で通る」検収は、何も生成しない経路を確かめただけである。検証側の対象では何も確かめていない |
| 納品物の依存宣言が画面に偏っている | `deliverable-inventory.json` で `dependsOnKind=screen` を持つ 11 件のうち 6 件は画面が無くても成立する。CRUD 図・画面-API-テーブル対応表・権限機能マトリクス・テスト観点表・テストケース一覧・確認事項質問票である | API のみの対象でこの 6 件が「対象なし」になり、納品物が欠ける。検証側はこれを設計の欠落として指摘している（1-253 の「ロジック変更なし」） |
| 網羅の分母が画面を固定で含む | `check-coverage.sh` は画面のマニフェスト 2 件と画面一覧を無条件に分母へ入れ、対象外の記録（`excluded-kinds.json`）を読まない（参照 0 件） | API のみの対象で網羅判定が通らない |
| 依存宣言が単一値 | `dependsOnKind` は 1 つの種別しか書けない。「API またはテーブルのどちらかがあれば成立」を表せない | CRUD 図（API×テーブル）のような複数種別に依存する納品物を正しく判定できない |
| 検収の状態行が対象と対応していない | 22 件の状態行の多くが「画面 0 件の合成入力で一気通貫が成功」という同じ文で埋まっている | 各項目の検収方法の項目ごとの判定になっていない。検証側が再現できない |
| 配布外の資産への依存 | `run-verification-loop.sh` が公開対象外の `check-self-contained.sh` を依存として要求していた。 | 配布先で「依存-スクリプト実在」が必ず不合格になる。定義側では依存一覧から外し済み（同期は 2026-08-28 06:41）。検証側の再実行で確認が要る |

## 4. 設計原則

1. **対象の輪郭は 1 箇所で宣言する。** 対象側の対象外の記録の `presentKinds`・`excludedKinds` を唯一の定義とする。記録の置き場は output-layout の excludedKinds キーが指す `excluded-kinds.json` である。生成・判定・分母はすべてここから導く。画面の有無を個別のスクリプトが独自に判断しない
2. **納品物の依存は「必要とする種別の集合」で宣言する。** 単一の `dependsOnKind` を、`requiresAnyOf`（列挙した種別のうち 1 つでも対象なら成立）と `requiresAllOf`（すべて対象のとき成立）へ改める。画面だけに依存する納品物は `requiresAllOf: ["screen"]` と書く
3. **見本は輪郭ごとに持つ。** 全種別あり（`samples/`）・API のみ（新設）・全種別なし（`samples-no-screen/`）の 3 つを持ち、検査と検収はこの 3 つに対して行う。検証側の対象に最も近いのは API のみの見本であり、22 件の検収はこの見本で行う
4. **検収は検証側と同じ方式で自己確認する。** 配布先（`~/github-public/agent-toolkit/payload/reverse-docs-skills/`）で実行する。課題キーごとに対応するファイルの差分と検収コマンドの終了コードを記録する

## 5. 変更点

### 5.1 定義

| 定義 | 変更 |
|---|---|
| `delivery-payload/references/deliverable-inventory.json` | `dependsOnKind` を `requiresAnyOf` / `requiresAllOf` へ置き換える。画面-API-テーブル対応表・CRUD 図・権限機能マトリクスは `requiresAnyOf: ["api"]` とする。テスト観点表・テストケース一覧・確認事項質問票は 7 種別すべてを `requiresAnyOf` に列挙する。画面遷移図・権限画面マトリクス・デザインシステム・部品棚卸し・アイコンカタログは `requiresAllOf: ["screen"]` とする。共通文書の共通設計書・UI共通設計も同じく `requiresAllOf: ["screen"]` とする。`generating-reverse-common-docs` の定義が既に画面依存と宣言しているためである |
| `.claude/skills/orchestrating-ai-development-setup/references/contract.md` | 依存宣言の新しい語彙と、対象の輪郭の宣言が唯一の定義である旨を書く |
| `delivery-payload/references/納品物フォルダ体系.md` | 画面が無い対象で生成される納品物の集合を表で示す |

### 5.2 生成器・検査

| スクリプト | 変更 |
|---|---|
| `generation-engine/scripts/build-deliverable-inventory.sh` | 集合宣言を解決する。判定は「対象なし（依存先がすべて対象外）」「未生成（依存先が 1 つ以上対象なのに実ファイルが無い）」を区別する |
| `docs/scripts/check-depends-on-kind.sh` | 集合宣言の網羅を検査する形へ改める（1-253。ロジック変更） |
| `generation-engine/scripts/verification/check-coverage.sh` | 分母を `excluded-kinds.json` と集合宣言から導く。画面が対象外なら画面のマニフェスト・一覧・画面依存の納品物を分母から外す |
| `generation-engine/scripts/verification/run-layer-full-pipeline.sh` | 画面が対象外のとき、画面依存の段を「対象なし」として記録し、API・テーブル・機能の段は実際に生成する（現状は画面 0 件の空マニフェストで続行するだけ） |
| `generation-engine/scripts/extract/build-matrix-data.sh` | `--screen-manifest` を任意にし、画面軸が空でも API×テーブル（CRUD）・機能×API（権限機能）を出す |
| `generation-engine/scripts/unit-list/check-manifest-persistence.sh` | 拡張マニフェストの `addedUnitCount` と `weakEvidenceRatio` を読み、対象 1 件以上で追加 0 件・弱い根拠の割合 1.0 を不合格にする（1-88） |
| `generation-engine/scripts/verification/prepare-verification-input.sh` | `--profile api-only` を足し、画面を除く 6 種別の疑似入力（各種別 1 件）を配置し、対象外の記録に画面を書く |

### 5.3 見本

`generation-engine/samples-api-only/` を新設する。中身は API のみの疑似入力から一気通貫で生成した納品物一式である。`excluded-kinds.json` は `presentKinds` に画面以外の 6 種別、`excludedKinds` に画面を持つ。`derived-fingerprints.json` を同じコミットで記録する。

### 5.4 スキル

`orchestrating-ai-development-setup` の Phase 2（調査）で輪郭を確定し、Step 2-7 の納品物一覧の提示で集合宣言に基づく「生成される納品物」を示す。Phase 5 で画面依存の段を飛ばす判断を、スキルの手順ではなく輪郭の宣言に委ねる。

区分 B の状態行は、次の形に揃える。「画面 0 件で通る」という文を使わない。

```
**状態**: 完了。検収1は満たす。確かめたコマンドは `<API のみの見本を対象にしたコマンド>` である。検収2は …
```

## 7. 検証の方法

1. 配布先で `bash docs/scripts/check-payload-layer1.sh` を実行し、失敗 0 本を確かめる
2. 配布先で API のみの疑似入力から一気通貫を 2 回実行し、網羅・再現・健全の 3 判定が通ることを確かめる
3. API のみの見本で納品物一覧を生成し、「未生成」が 0 件、「対象なし」が画面一覧と画面依存の 7 件（共通文書 2 件を含む）だけであることを確かめる
4. 22 件それぞれの検収コマンドを配布先で実行し、終了コードを状態行へ記録する
5. 検証側と同じ方式（課題キー → 対象ファイルの差分）を `git diff --stat` で自己確認し、変更の無いキーが残っていないことを確かめる

## 8. 決めていないこと

| 何を決めるか | 既定（迷ったらこれを選ぶ） | 覆すときの条件 |
|---|---|---|
| 依存宣言の語彙 | `requiresAnyOf` / `requiresAllOf` の 2 つ | 既存の `dependsOnKind` を読む外部の道具が見つかったとき（互換の読み口を 1 版だけ残す） |
| API のみの見本の規模 | 各種別 1 件（疑似入力の配置が種別ごとに代表 1 件を選ぶ既存の仕組みに揃える。検収は件数ではなく納品物の成立を見る） | 検収に複数件の再現が要ると分かったとき（疑似入力の配置へ件数の指定を足す） |
| 画面依存の納品物の集合 | 画面遷移図・権限画面マトリクス・デザインシステム・部品棚卸し・アイコンカタログ・共通設計書・UI共通設計の 7 件 | 生成元のスキルが画面以外の証拠で成立すると実測で分かったとき |
| `samples-no-screen/` の扱い | 全種別なしの見本として残す。名前は変えない | 名前が誤解を生むと判断したとき（`samples-empty/` へ改名） |
