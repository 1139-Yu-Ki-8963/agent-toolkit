# generation-engine/scripts/skill-guide 群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は `skill-guide/` 1 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する。

対象は `generation-engine/scripts/skill-guide/` 配下の `.sh` 2 本（実測。`find generation-engine/scripts/skill-guide -name '*.sh' | wc -l`）。

## 2. この群が何をするか

`.claude/skills/*/references/guide.html`（各スキルの説明書。`.claude/rules/always/skill-guide/html/rule.md` 準拠）の体裁・参照パスの整合を保つ。

| スクリプト | 役割 |
|---|---|
| `apply-guide-style.sh` | 全スキルガイドの `<style>` 中身を `delivery-payload/templates/skill-guide/guide-style.css` へ統一する注入スクリプト。統一適用の妥当性を検査する `--self-test`（9項目）も持つ |
| `check-guide-script-paths.sh` | ガイド本文に書かれた `generation-engine/`・`delivery-payload/` 配下のパス参照が実在するかを検査する |

両スクリプトとも対象は同じ集合（`.claude/skills/*/references/guide.html`）だが、検査する観点が異なる。`apply-guide-style.sh` は見た目（CSS）の統一、`check-guide-script-paths.sh` は本文が指す参照パスの実在確認を担う。

## 3. 群内スクリプトの呼び出し関係

`apply-guide-style.sh` と `check-guide-script-paths.sh` は互いを呼ばない（実測: `grep -n` で群内相互呼び出しは0件）。いずれも引数なしのCLIとして独立に呼べる。

## 4. 他の群との依存関係

- `delivery-payload/templates/skill-guide/guide-style.css`（この群の外、`delivery-payload/` 配下）を `apply-guide-style.sh` が正本として参照する
- `.claude/rules/always/skill-guide/html/rule.md` が本群の設計判断（ADR形式: 必要性・代替案・保守責任者・廃棄条件）と検査8項目の定義を既に持つ。本文書は「なぜこのスクリプトが要るか」ではなく「なぜこの実装（コマンドの選び方・一時ファイルの扱い）を採ったか」を扱い、対象が異なる
- `.claude/skills/*/references/guide.html`（51件、この群の外）を両スクリプトが読み書きする対象とする

## 5. 共通する実装上の判断（群全体に共通する背景）

個別スクリプトの詳細設計（`詳細設計書.md`）に書く「実装判断」のうち、複数スクリプトへ横断的に現れる背景を先にここへまとめる。

### 5.1 明示テンプレート付き `mktemp` の使用（裸の `mktemp` を避ける）

`apply-guide-style.sh` の `apply_one`（1ガイドへの実書き込み用一時ファイル）と `check-guide-script-paths.sh` の `self_test`（自己検査用の一時ディレクトリ）は、いずれも明示テンプレート付きの `mktemp` を使う。理由は他群（`extract/`・`rules/`）と同じで、裸の `mktemp` が `$TMPDIR` を無視しサンドボックス実行環境で失敗するため（改善課題「一時ディレクトリ-作成先」）。

`check-guide-script-paths.sh` はさらに一歩踏み込み、明示テンプレート付きでも失敗しうる環境（書き込み自体を拒む環境）を想定し、`mktemp -d ... 2>/dev/null` と `|| tmp=""` に加えて `[ -z "$tmp" ] || [ ! -d "$tmp" ]` の明示チェックを行い、失敗時は自己検査自体を「不合格1件」として報告してから抜ける（クラッシュさせず、判定可能な形で終える）。この二段構えは他群の同種処理より一段慎重である。

この判断は環境（サンドボックス実行環境かどうか）に依存する。**手元の許可された開発環境で裸の `mktemp` に書き換えても、または `check-guide-script-paths.sh` の二段チェックを簡略化しても動いて見えることがあるが、それを理由に外すな。**

### 5.2 `LC_ALL=C` によるロケール非依存の決定的な順序付け

`check-guide-script-paths.sh` の `scan_dir` は、`find`・`grep` の出力を `LC_ALL=C sort` へ通す。素直な形（ロケール指定なしの `sort`）は実行環境の照合順序（collation）に依存し、走査順・報告順が環境によって変わりうる。この群のこの用途は `rules/validate-rule-definitions.sh` の `LC_ALL=C awk`（多バイト文字列の等値比較の誤判定を避ける目的）とは異なる系統の理由であり、こちらは「決定的な順序を保証する」ことが目的である。`rules/check-rule-drift.sh` の `list_targets` も同じ目的で `LC_ALL=C sort` を使う（`rules/` 群の詳細設計書参照）。
