# generation-engine/scripts/verification 群 詳細設計書

対象は `docs/tasks/自己設計書整備の指示書.md` 4.5節の手順で洗い出した第1優先（素直でない実装を持つ）11本。群全体の役割・呼び出し関係・共通する背景は `基本設計書.md` を参照する。ここでは各スクリプトの実装契約と、なぜその実装を採ったかという実装判断を書く。

各節の「実装判断」は指示書4.2節の4点（1: なぜ素直な形を採らなかったか、2: 実測値、3: 環境依存かどうか、4: 過去に消えて再発した経緯）に沿って記載する。

## run-layer-machine-checks.sh

### 実装契約

- 引数: `[--repo <リポジトリのパス>] [--list] [--self-test] [--timeout <秒>]`
- 環境変数: `TMPDIR`
- 出力: 対象スクリプトごとに `[PASS|FAIL|SUSPECT|TIMEOUT|DECLARED-LONG] <相対パス> — ...` の行、末尾に集計行（対象・成功・失敗・途中停止の疑い・打ち切り・宣言済み長時間・総ケース数）
- 終了コード: 失敗・途中停止の疑い・打ち切りのいずれかが1本でもあれば`exit 1`。すべて成功なら`exit 0`。`--timeout` に正の整数以外を渡すと`exit 2`
- 副作用: `run_one()` が対象スクリプトごとに `mktemp` で出力捕捉用の一時ファイルを作り実行後に削除する。`set -m`/`set +m` でジョブ制御モードを一時的に切り替える

### 実装判断

1. **なぜ素直な形を採らなかったか**: 1本あたりの実行時間上限を `timeout <秒> <cmd>` という素直な形（`timeout`/`gtimeout` コマンドを使う形）ではなく、対象スクリプトをバックグラウンドで起動し0.2秒間隔でポーリングして生存確認し、上限超過時に `set -m` で作ったプロセスグループへ SIGTERM→SIGKILL を送る形にしている。理由はこの環境に `timeout` コマンドも `gtimeout` コマンドも実在しないため（本体コメント参照。`command -v timeout`・`command -v gtimeout` がともに何も返さないことを実測済み）。
2. **実測値**: 引数なしで走らせた全体実測（対象132本・版 `645377f31c32532f95286fa9a4084331d01e3efa`）: 所要時間1819秒 / 総ケース数1444件 / 成功114本 / 失敗17本 / 打ち切り0本 / 途中停止の疑い0本。この規模でもポーリング実装が全体の所要時間を破綻させないことを示す根拠になる。
3. **環境に依存するかどうか**: 依存する。`timeout`/`gtimeout` が存在する環境（多くのLinux配布やGNU coreutils導入済みのmacOS）へ持ち込んでも、それを理由にポーリング実装を素直な `timeout` 呼び出しへ戻すな（この環境に存在しないという制約は変わらない）。
4. **過去に消えて再発した経緯**: 記録なし。この実装は当初からポーリング方式で書かれている。

副次的な非自明箇所として、`declared_long_running_timeout()`（実測150〜260秒の対象への個別上限）と `declared_long_running_known()`（実測300秒超の対象を `DECLARED-LONG` として区別し打ち切り扱いにしない）の2表がある。両方とも改善課題1-52への対応であり、機能自体（抽出ロジックの検証範囲）を変更する権限が無いスクリプトの実行時間を、上限側の宣言で吸収するための設計である。本体コメント（176〜253行目）に実測値・登録理由が既に記載済みのため本節では重複記載しない。

## run-layer-full-pipeline.sh

### 実装契約

- 引数: `--output <出力先> [--repo <リポジトリのパス>] [--input <疑似入力の位置>] [--keep] [--self-test]`
- 環境変数: なし（`TMPDIR` は `verification-env.sh` 経由で間接的に参照）
- 出力: 段ごとに `[OK|FAIL|SKIP] <段名> — <詳細>` の行、末尾に集計行（段数・成功・失敗・スキップ・生成ファイル数）
- 終了コード: `--output` が版管理下のパスなら`exit 1`（何も実行しない）。1段でも失敗があれば最終的に`exit 1`。すべて成功またはスキップのみなら`exit 0`
- 副作用: `verification-env.sh` を通じてスクラッチ作業領域を作り、既定では終了時に削除する（`--keep` で保持）。`OUTPUT_DIR` 配下へ10段の生成物を書く

### 実装判断

1. **なぜ素直な形を採らなかったか**: 3点ある。
   (a) `stage_rules_scaffold()` は `rules/scaffold-rule-definitions.sh` の呼び出しに `--apply` を条件分岐なしで常に付ける。素直な形（呼び出し元がフラグを都度判断する形）を避けている。理由: 同スクリプトは `--apply` を付け忘れると規約が0件のまま試行実行（dry-run）で終わる。この事故は `.claude/rules/scoped/portal/page-conventions/rule.md` の設計判断節に既知の事故パターンとして記録済みだったが、本スクリプト自身には理由が無かった（本作業でコメントを追記した）。第3層は無人で繰り返し実行される経路であり、呼び出し側の判断に委ねると同じ事故を再現しうるため、選択の余地を無くしてある。
   (b) `resolve_output_dir_realpath()` は `realpath` コマンドを使わず `( cd "${path}" && pwd -P )` で実体パスを解決する。理由はこの環境に `realpath` コマンドが無い可能性があるため（本体コメント728〜731行目に既存記載）。macOSの `${TMPDIR:-/tmp}` は `/private/tmp` へのシンボリックリンクであり、`build-portal.sh` は祖先を辿ってシンボリックリンクを含むパスを拒否するため、後続の段へ渡す前に一度だけ解決する必要がある。
   (c) `is_output_inside_git()`/`_nearest_existing_ancestor()` は `--output` に指定されたパスが未作成でも判定できるよう、実在する祖先ディレクトリまで遡ってから `git rev-parse --is-inside-work-tree` を呼ぶ。素直な形（パスをそのまま `git -C` へ渡す）は、パスが未作成の場合に `git` コマンド自体が失敗し判定できない。
2. **実測値**: (a) は実測値なし（事故そのものは既知の記録から確認したが本スクリプトでの再現実測はしていない）。(b)(c) は実測値なし。
3. **環境に依存するかどうか**: (a) は環境非依存（呼び出し手順の問題であり実行環境には依存しない）。(b) はmacOS固有の`$TMPDIR`シンボリックリンク構成と`realpath`コマンドの有無に依存する。(c) は環境非依存（`--output` に未作成パスを渡すという呼び出しパターン一般への対策）。**(b) について、`realpath` コマンドが存在する環境で試しても、それを理由に `pwd -P` 経由の解決を外すな。**
4. **過去に消えて再発した経緯**: (a) は記録なし（この段自体が新設時から `--apply` 固定で書かれている）。(b)(c) も記録なし。

### 関連図3種の配線（stage_design_pages への追加）

`portal-input/extract-entity-state-page-data.sh`・`extract-er-page-data.sh`・`extract-transition-page-data.sh` の3本は実装済みだったが、`run-layer-full-pipeline.sh` のどの段からも呼ばれておらず、一気通貫の実行では関連図3種（状態遷移図・ER図・画面遷移図）が生成されなかった（`docs/tasks/関連図の内製化の指示書.md` が求める完了条件の到達を妨げていた）。

1. **なぜ新しい段を作らず `stage_design_pages()` へ足したか**: 独立した `stage_relation_diagrams()` を新設する案もあったが、(a) 3本とも「抽出 → `detail-pages/build-detail-page.sh` でHTML化」という、同じ段が既に持つデザイン系3種（design-system/component-inventory/icon-catalog）と同型の処理であること、(b) `self_test()` の「段-定義数」検査が10段固定を検査しており、新設すると `stage_keys`・`stage_name`・`run_stage`・「段-定義数」の4箇所を同時に変える必要が生じ、変更範囲が広がることから、既存段への追加にとどめた。
2. **出力先を `${PORTAL_DIR}/図` にした根拠**: `delivery-payload/references/portal-catalog.json` の該当3 blueprint（`screen-transition`・`er-diagram`・`entity-state`）の `discovery.glob` がそれぞれ `project-portal/図/画面遷移図.html`・`project-portal/図/ER図.html`・`project-portal/図/状態遷移図.html` を指しており、この配置以外では `build-portal.sh` のポータルトップ discovery がカードを検出できない。
3. **entity-state/er の抽出失敗を段の失敗にしない理由**: 両抽出器は自身の設計として「材料が0件（設計文書が雛形のプレースホルダ行のみ、または文書自体が不在）」の場合に WARN を stderr へ出しつつ exit 0 で空の page-data.json を書く（捏造しない設計。各スクリプトのヘッダコメント参照）。この exit 0 を段の失敗として扱わないことで、材料の有無という往復検証の実データ依存な事情と、抽出器・配線自体の正しさを区別できるようにした。
4. **transition だけ screen-manifest.json 不在・不正時に exit 1 として扱う理由**: transition は entity-state/er と異なり `nodes[]`/`manifestContentHash` を screen-manifest.json から必須で組み立てる契約であり、代替できない。このため screen-manifest.json 自体が欠けている場合は「材料が無い」ではなく実行契約違反として `any_fail=1` にする。
5. **実測（版 `e93c4e1a2cd7b3ddb4c8c9bee8b536369dbe9cad`）**: 疑似入力（`delivery-payload/templates/リバース検証/` 由来）を使った自己検証実行では、entity-state=0件/0件（データ設計.md §6がプレースホルダ行のみ）、er=1件/0件（テーブル定義書.md は配置されるが §6.3 がプレースホルダ行のみ）、transition=0件/0件（画面検出フォールバックにより screen-manifest.json の screens が空になり、加えて画面基本設計書.md §6 もプレースホルダ行のみ）となった。抽出器自体と配線が正しく機能することは、実データを持つ `generation-engine/samples`（`docs/design/common/データ設計.md` 等）を `output_dir` として個別に渡した実測で確認済み: entity-state は46件/43件、transition は43件/6件を得た（ER は samples に `docs/design/tables` 自体が無く0件/0件だが、抽出器自身の `--self-test` は6件全PASSで実データ時の非0動作を検証済み）。生成された3HTMLの埋め込みJSON件数は対応する page-data.json の件数と一致することを確認した。ポータルトップの `portal-categories` にも3カードが有効状態（`href` 付き、非disabled）で載ることを確認した。
6. **環境依存**: しない（材料の有無は疑似入力の内容に依存するのであって実行環境には依存しない）。
7. **過去に消えて再発した経緯**: 記録なし（今回が初回配線）。

### stage_type_extraction: 検出0件のとき既存の画面一覧を残す（前節6点目の既知の限界の解消）

前節6点目は、`stage_type_extraction`が`detect-screens.sh`の結果（成功時の実検出結果、失敗時は`write_empty_screen_manifest`の空マニフェスト）で`${OUTPUT_DIR}/docs/manifests/screen-manifest.json`を無条件に上書きし、`prepare-verification-input.sh`が組み立てた疑似入力の画面一覧（1件）を一気通貫の実行時に必ず消してしまうという既知の限界だった。この上書きを、検出結果の中身（`screens`配列の件数）を見てから書き込み先を決める判断へ置き換えた。

1. **なぜ`detect-screens.sh`を直接呼ばず出力先を分離したか**: `detect-screens.sh`は`${MANIFESTS_DIR}/screen-manifest.json`を直接の出力先として渡されると、成功・失敗を問わずその場で上書きする。上書きするかどうかの判断を呼ぶ側（段）へ持たせるには、まず別名（`screen-manifest.detected.json`）へ書かせてから、既存件数と検出件数を比較し、その結果に応じて本来の出力先へ`mv`するか、既存を温存して検出結果を捨てるかを選ぶ必要がある。`detect-screens.sh`自体は変更しない（変更禁止の指示に基づく）。
2. **判定基準を`detect-screens.sh`の終了コードではなく実際に書かれた内容にした理由**: 当初は終了コード（成功=0/失敗=非0）で分岐する案を検討したが、実測でこの前提が崩れた。このリポジトリ自身（アプリケーションコードを持たない）に対して`detect-screens.sh`を実行すると、`DETECTION_FAILED: ルーティング定義も慣習ディレクトリも検出できませんでした`のメッセージの後、`STRATEGY_SHARED_FILE: unbound variable`という別の未修正のバグで終了コード非0のまま止まる。この際、`detect-screens.sh`は自身の設計どおり`screens: []`（`detectionSummary.method: "none"`, `screenCount: 0`）を含む妥当なマニフェストを出力先へ書き終えた**後**にクラッシュしており、「検出結果の中身は0件」という情報自体は取得できる状態にある。終了コードだけで分岐すると、この「0件だが妥当な内容が書かれているケース」と「クラッシュにより出力先ファイル自体が存在しないケース」を区別できず、後者しか想定していない`write_empty_screen_manifest`のフォールバックに丸めてしまう。そこで、終了コードは`any_fail`（段の成否表示）にのみ反映し、上書き可否の判定は常に「別名ファイルへ書かれた`screens`配列の件数（ファイルが無ければ0件扱い）」で行うよう統一した。
3. **既存を残す条件を「検出0件 かつ 既存1件以上」に限定した理由**: 指示（検出が1件以上のときはこれまでどおり置き換える。振る舞いを変えるな）に従い、検出件数が1件以上のときは既存の有無によらず`mv`で置き換える（従来どおり）。検出0件・既存も0件のときは、置き換えても既存を残しても結果は同じ（空のまま）だが、`mv`による置き換え（別名ファイルが存在すればそれを採用、無ければ`write_empty_screen_manifest`で妥当な空マニフェストを新規に書く）を選び、コード分岐を1本に絞った。
4. **段のログへの記録形式**: 既存を残した場合は`screen=<終了コード>(検出0件・既存<N>件のため既存を残した); `の形で`detail`へ追記する（`<N>`は既存の`screens`配列の件数）。この文字列は指示が明示した形式（「検出0件・既存N件のため既存を残した」）をそのまま踏襲した。
5. **実測（版`9be58f88e97b0d64088016027e525afe264d776f`）**: `run-layer-full-pipeline.sh --output "$TMPDIR/pipe-final"`を実行し、`種別別の抽出`段のログに`screen=1(検出0件・既存1件のため既存を残した); `が記録されることを確認した（`screen=1`は上記2点目のバグによる`detect-screens.sh`の終了コード）。生成された3HTML（`project-portal/図/状態遷移図.html`・`ER図.html`・`画面遷移図.html`）に埋め込まれた`page-data`のJSONを実際に取り出して数えた結果は、状態遷移図=3節/2辺、ER図=1実体/1関連、画面遷移図=1節/1辺であり、3種とも辺（関連）が1件以上になった。段の集計は10段中9段OK・1段FAIL（`種別別の抽出`。`detect-screens.sh`自身の未修正バグによる終了コード非0が原因であり、画面一覧の温存自体は成功している）、生成ファイル数329。`run-layer-full-pipeline.sh --self-test`は既存19ケースを含めすべてPASS（19件/19件）。
6. **環境依存**: 判定ロジック自体（既存件数と検出件数の比較）は環境非依存。ただし5点目で観測した`detect-screens.sh`の終了コード非0（`STRATEGY_SHARED_FILE: unbound variable`）は、このリポジトリ自身に対して実行した場合に再現する`detect-screens.sh`側の未修正の別バグであり、本変更のスコープ外（`detect-screens.sh`は変更禁止の指示に基づく）。加えてこのバグの手前で、macOS標準の`mktemp`（`-p`無指定の書式）がサンドボックスの書き込み許可ディレクトリ外（`confstr(_CS_DARWIN_USER_TEMP_DIR)`が指す`/var/folders/.../T/`）を既定で使うため、サンドボックス配下では`detect-screens.sh`冒頭の`mktemp`呼び出し自体が`Operation not permitted`で失敗しうることも実測で確認した（`detect-screens.sh`は`${TMPDIR:-/tmp}`を明示指定しない`mktemp`呼び出しを多数持つ。他の検証スクリプト群は軒並み`${TMPDIR:-/tmp}/...`形式で`mktemp`を呼んでおり、この点で`detect-screens.sh`だけが異なる）。いずれの経路（`mktemp`自体の失敗による無出力、またはクラッシュ前の0件出力）でも、本変更の判定ロジックは「検出0件」として同じように扱うため、上書き防止という結論には影響しない。
7. **過去に消えて再発した経緯**: 記録なし（前節6点目で既知の限界として記録された直後の対応であり、今回が初回修正）。

## prepare-verification-input.sh

### 実装契約

- 引数: `--output <出力先ディレクトリ> [--repo <リポジトリのパス>]`、または `--self-test`
- 環境変数: なし
- 出力: `--output` 配下へ、雛形を種別ごとの配置構造で複製し、frontmatterのプレースホルダを固定値で埋めた設計文書一式。加えて `<output>/verification-source/<種別英語キー>/` へ疑似コードを複製する（`stage_fixture_code`）
- 終了コード: `TEMPLATE_ROOT` 不在・未知のテンプレート（配置先マッピング未定義）・代表とする疑似コードが1件も無い場合に`exit 1`。`--self-test` はケース不合格があれば`exit 1`
- 副作用: `--output` 配下へのファイル複製・書き換え（`sed -i.bak` の一時バックアップは都度削除）。雛形（`TEMPLATE_ROOT`）自体への書き込みは行わない

### 実装判断

1. **なぜ素直な形を採らなかったか**: 3点ある。
   (a) `first_fixture_relpath()`・`run_prepare()` のファイル列挙・`hash_dir()`・`collect_frontmatter()` の計4箇所で、ソートにロケール既定の照合順位ではなく `LC_ALL=C sort` を使う。素直な形（ロケール指定なしの `sort`）は、実行環境の `LANG`/`LC_ALL`（`ja_JP.UTF-8` 等）によって辞書順ソートの結果が変わりうるため、「先頭の1件を代表として選ぶ」処理の決定性や、`hash_dir()` によるディレクトリ内容ハッシュ比較（`self_test()` の「雛形-不変」ケースが前提にする）を環境依存にしてしまう。
   (b) 日付を現在時刻ではなく固定値 `2026-01-01`（`FIXED_DATE`）、コミットハッシュを固定値 `0000000000000000000000000000000000000000`（`DUMMY_COMMIT`）で埋める。素直な形（実行時の現在時刻・実際のコミットハッシュを使う形）は、往復検証が求める「再現」（同じ入力で2回実行し生成物が一致すること）の判定と衝突する（本体コメント44行目に既存記載）。
   (c) 置換対象をfrontmatterと、frontmatterの識別子語を再掲する見出し行に限定し、本文中の自由記述プレースホルダ（`<実測: 実行コマンド>` 等）を対象外とする。素直な形（雛形全体を無差別に置換する形）を避けている。理由: `build-manifests-from-docs.sh` はfrontmatterしか読まないため（本体コメント11〜17行目に既存記載）、本文の自由記述プレースホルダは何百通りもあり機械的に「意味の分かる」値を割り当てる根拠が無い。
2. **実測値**: (a)(b)(c) いずれも実測値なし。

## run-authoring-mode.sh

### 実装契約

- 引数: `--output <出力先> [--repo <リポジトリのパス>] [--enable] [--dry-run] [--permission-mode <値>] [--self-test]`
- 環境変数: なし
- 出力: `--dry-run`時は実行予定のコマンド文字列。`--enable`かつ`--dry-run`無しの場合は`claude -p`の実行結果
- 終了コード: `--enable`無しでの実行は何もせず`exit 0`（骨格のみで実際の対話モデル呼び出しには進まない）。引数不正は`exit 1`

### 実装判断

1. **なぜ素直な形を採らなかったか**: 2点ある。
   (a) 対話モデルの呼び出しへ進む経路を`--enable`の明示指定がない限り塞ぎ、既定では骨格の検査（引数検査・段定義・依存スクリプト実在の確認）のみを行う。素直な形（既定で対話モデルを呼ぶ形）を避けている。理由は2点（本体コメント10〜14行目に既存記載）: 対話モデルの実行は自己テストとして回せない（`--self-test`は判断を要する処理そのものを検査対象にできない）ことと、実行のたびに出力が揺れるため往復検証が求める「再現」判定と衝突すること。
   (b) `--permission-mode`に既定値を持たせず、指定しなければ`claude -p`の呼び出しに`--permission-mode`を一切付けない（claude側の既定＝対話的な承認に委ねる）。素直な形（承認を迂回する`acceptEdits`等を既定にする形）を避けている。理由は承認の迂回を既定へ含めないという明示方針（本体コメント27〜30行目に既存記載）。無人で走らせる必要が生じたときは、呼び出し元が`--permission-mode`を明示して責任を持つ設計である。
2. **実測値**: 実測値なし。
3. **環境に依存するかどうか**: (a)は環境非依存（対話モデルという実行方式そのものの性質への対策）。(b)は環境非依存（承認方針という運用上の設計）。ただし`--enable`を実際に実行する経路はサンドボックスの外向き接続制限に依存する（本体コメント43〜44行目に既存記載）。**手元でサンドボックスを無効化して動くことを確認しても、それを理由に`--enable`を既定へ含めるな。**
4. **過去に消えて再発した経緯**: 記録なし。この骨格は新設時から`--enable`必須で書かれている。
