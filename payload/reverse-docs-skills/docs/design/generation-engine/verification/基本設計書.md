# generation-engine/scripts/verification 群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/done/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は `verification/` 1 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する。先行して作った `extract/`・`unit-list/` の書き方と構成に揃える。

対象は `generation-engine/scripts/verification/` 配下の `.sh` 13 本（実測。`find generation-engine/scripts/verification -name '*.sh' | wc -l`）。

## 2. この群が何をするか

このリポジトリ自身の検証設計文書（`docs/design/reverse-verification/設計.md`。配布対象外）が定める往復検証（原本コードから設計書を作り、設計書だけから再生成して原本と突合する検証）を実行する。第1層（機械検証の自己テスト横断実行）・第3層（一気通貫の生成連鎖）・4判定（網羅・自立・再現・健全）・実行記録と退避記録の台帳への記録・前回との比較までを担う。

大きく5系統に分かれる。

| 系統 | スクリプト | 役割 |
|---|---|---|
| 使い捨て環境の管理 | `verification-env.sh` | 版管理下から独立した作業領域の発番・作成・削除・版（コミットハッシュ）の記録 |
| 疑似入力の整備 | `prepare-verification-input.sh` | `delivery-payload/templates/リバース検証/` の雛形を検証用の固定値で埋めて配置する |
| 実行エンジン | `run-layer-machine-checks.sh`（第1層）・`run-layer-full-pipeline.sh`（第3層）・`run-authoring-mode.sh`（対話モデルを挟む別モードの骨格。既定は無効） | 実際の生成・検証コマンド群を正しい順序・正しい引数契約で呼ぶ |
| 4判定の判定器 | `check-coverage.sh`（網羅）・`check-self-contained.sh`（自立）・`check-reproducible.sh`（再現）・`check-sound.sh`（健全） | 生成物ディレクトリ（または2つの生成物ディレクトリの比較）を判定基準に照らして合否を返す |
| 記録・比較・入口 | `record-verification-result.sh`・`record-deferral.sh`・`compare-with-previous.sh`・`run-verification-loop.sh` | 検証結果・退避の記録を台帳へ追記し、前回との比較を行い、これら全段を1本のコマンドで回す入口を提供する |

## 3. 群内スクリプトの呼び出し関係

`run-verification-loop.sh` が唯一の統合入口であり、他8本を `bash` サブプロセス経由で正しい順に呼ぶ（実測。同スクリプトの `dependency_scripts()` と各 stage 関数から）。

1. `version` — `verification-env.sh`（`source` して `verification_env_record_version` を呼ぶ。他はサブプロセス呼び出し）
2. `layer1` — `run-layer-machine-checks.sh --repo <対象> --timeout <秒>`（`--skip-layer1` で省略可）
3. `prepare-outputs` — `verification-env.sh` の `verification_env_setup` を2回呼び、使い捨ての出力先を2つ用意する
4. `layer3` — `run-layer-full-pipeline.sh --output <出力先> --repo <対象>` を2回実行する（1回目・2回目の生成物を再現判定に使う）
5. `judge` — `check-coverage.sh`（1回目）・`check-self-contained.sh`・`check-reproducible.sh --first <1回目> --second <2回目> --ignore-timestamps`・`check-sound.sh`（1回目）
6. `record` — `record-verification-result.sh`（`--no-record` で省略可）
7. `compare` — `compare-with-previous.sh --ledger <実行記録のパス>`
8. `teardown` — `verification_env_teardown`（2つの出力先を破棄する。既定。`--keep` の引数は設けない）

`run-layer-full-pipeline.sh` はさらに内部で `verification-env.sh`・`../output-layout.sh`（この群の外）を `source` し、`prepare-verification-input.sh`・`portal-input/build-manifests-from-docs.sh`・`unit-list/detect-screens.sh`・`extract/` 配下の各抽出・`unit-list/build-*.sh`・`matrix/build-matrix-pages.sh`・`detail-pages/build-detail-page.sh`・`rules/scaffold-rule-definitions.sh`・`build-portal.sh` を正しい順序で呼ぶ（10段。詳細設計書の該当節参照）。

`run-authoring-mode.sh`・`record-deferral.sh` は `run-verification-loop.sh` からは呼ばれない独立したスクリプトである。前者は生成連鎖へ挟み込む位置の骨格のみを持つ既定無効の別モードであり、後者は人手が実行を試みて失敗したときに手動で退避を記録するための道具である。

## 4. 他の群との依存関係

- `../output-layout.sh`（`generation-engine/scripts/` ルート直下、この群の外）を `prepare-verification-input.sh`・`run-layer-full-pipeline.sh`・`check-coverage.sh` が `source` し、出力配置パスの宣言解決に使う
- `portal-input/`・`unit-list/`・`extract/`・`matrix/`・`detail-pages/`・`rules/`・`generation-engine/scripts/build-portal.sh`（ルート直下）を `run-layer-full-pipeline.sh` が生成連鎖の各段として呼ぶ
- `generation-engine/scripts/tests/test-e2e-portal.sh`・`generation-engine/scripts/tests/test-portal-conventions.sh` を `check-sound.sh` が委譲先として呼ぶ（本群からは変更しない。既存2本の設計判断は `page-conventions/rule.md` 側の管轄）
- `delivery-payload/references/portal-catalog.json`・`output-layout.json`・`rule-taxonomy.json` を `check-coverage.sh` が分母の定義元として読む
- `delivery-payload/templates/リバース検証/` を `prepare-verification-input.sh` が疑似入力の雛形として読む
- `generation-engine/scripts/` 配下と `delivery-payload/templates/rules/checkers/` 配下の `--self-test` を持つ全スクリプトを `run-layer-machine-checks.sh` が横断実行する（この群自身の各スクリプトも対象に含まれる。自己参照的な依存）
- `docs/tasks/作業課題一覧.md`（このリポジトリ自身の台帳。配布対象外。検証の実行と退避の記録はここへ集約した）を `record-verification-result.sh`・`record-deferral.sh`・`compare-with-previous.sh` が読み書きする

## 5. 共通する実装上の判断（群全体に共通する背景）

個別スクリプトの詳細設計（`詳細設計書.md`）に書く「実装判断」のうち、複数スクリプトへ横断的に現れる背景を先にここへまとめる。個々のスクリプトの節では重複記載を避け、この節への参照に留める。

### 5.1 実行結果の集計に使う一時ディレクトリ・一時ファイルは明示テンプレート付きで作る

この群のスクリプトが `--self-test` 用に作る一時ディレクトリ（`mktemp -d "${TMPDIR:-/tmp}/<script>-selftest.XXXXXX"` の形）は、`extract/` 群 5.1節が確立した「裸の `mktemp -d` を避ける」規約をそのまま踏襲している。この群では全スクリプトが `--self-test` 用途でこの形を使っており、独自の退行や独自の実測は無い（標準的な自己テスト用一時領域として扱い、個別の実装判断としては記載しない）。

例外は `run-layer-machine-checks.sh` の `run_one()` と `check-reproducible.sh` の `checkrepro_compare()` で、こちらは `--self-test` 以外の本番経路でも明示テンプレート付き `mktemp` を使う。前者は対象スクリプトの標準出力を捕捉するための一時ファイルであり、後者は2つの生成物ディレクトリのファイル一覧を保持する一時ファイルである。いずれも `${TMPDIR:-/tmp}/<用途>.XXXXXX` の形であり、`extract/`群5.1節と同じ「サンドボックス実行環境で裸の `mktemp -d` が失敗する」という理由に基づく。

### 5.2 ロケール既定の照合順位ではなく `LC_ALL=C` を明示する

この群には2種類の `LC_ALL=C` 使用がある。

1. **ソート順の固定**（`prepare-verification-input.sh` の `LC_ALL=C sort`）: ロケール（`LANG`/`LC_ALL`）によって辞書順ソートの結果が変わりうるため、「先頭の1件を代表として選ぶ」処理や、ディレクトリ内容のハッシュ計算の入力順を、実行環境のロケール設定に関わらず決定的にする。詳細は詳細設計書の該当節（本体コメントを直接参照する形で記載）を見る。
2. **マルチバイト文字列比較の不具合回避**（`compare-with-previous.sh` の `LC_ALL=C awk`）: macOS 標準 awk（one true awk）は `en_US.UTF-8` ロケール下で、多バイト文字列同士の `==` 比較が常に真を返す既知の不具合を持つ（strcoll ベースの比較が CJK 文字の照合順位を区別できないため）。`extract/` 群5.3節の `LC_ALL=C` 用途（非UTF-8原本のバイト単位走査）とは目的が異なり、こちらは「UTF-8の文字列同士の等価判定を正しく行う」ための固定である。

両者とも環境依存（macOS 標準ツールの挙動に起因）であり、手元の環境で問題が再現しないことを理由に外してはならない。

### 5.3 `awk -v` の代わりに一時ファイル + `getline` で複数行の値を差し込む

`record-verification-result.sh`・`record-deferral.sh` はいずれも、台帳へ差し込む節（複数行の Markdown ブロック）を `awk -v` へ直接渡さず、一時ファイルへ書き出してから `getline` で読み込む。BSD/macOS 標準 awk は `-v` に複数行の値を渡すと `"newline in string"` エラーになるためであり、`extract/` 群の `extract-screen-metadata.sh`（詳細設計書参照）が採る対策と同種である。

## 7. 詳細設計を個別に持たないスクリプト（第3優先: 素直でない実装なし）

以下2本は、実際にコードを読んだ結果、2.1節が挙げる「素直でない実装」（一時ファイルを経由すること自体に議論の余地がある・環境変数受け渡し・ロケール明示・特定コマンドの回避・冗長な二重チェック）には該当しないと判断した。

- `check-sound.sh`: 既存2本の検査器（`test-e2e-portal.sh`・`test-portal-conventions.sh`）へ丸ごと委譲し、終了コードと出力を集計するだけの薄いラッパー。`--self-test` 用の `mktemp -d`（5.1節の標準形）以外に非自明な実装は無い
- `run-verification-loop.sh`: 8段の呼び出し順序と引数の受け渡しに徹する統合入口であり、呼び出す各スクリプト側の非自明な実装（本文書6節の11本）を集約するだけで、この入口自身が独自に非自明な実装を持つ箇所は無い
