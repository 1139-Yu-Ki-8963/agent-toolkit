# generation-engine/scripts/detail-pages 群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は `detail-pages/` 1 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する。

対象は `generation-engine/scripts/detail-pages/` 配下のスクリプト 8 本（実測。`.sh` 6 本 + `.py` 1 本 + テストの `.sh` 1 本。`fixtures/` はデータ、`page-data-schema.md` は正本スキーマ文書でありスクリプトではない）。

## 2. この群が何をするか

用語辞書・技術スタック・画面遷移図・ER図・環境構築手順・状態遷移図・リリースノート・デザインシステム・コンポーネント棚卸し・アイコンカタログの10種別（`build-detail-page.sh` の `--page` 値）について、page-data.json（正本スキーマ: `page-data-schema.md`）からHTMLを決定的に生成する「詳細ページ」系の共通ビルダー群である。

| 系統 | スクリプト | 役割 |
|---|---|---|
| 共通ビルダー・検証エンジン | `build-detail-page.sh`・`validate-page-data.sh` | page-data.json を検証し、`--page` 種別ごとのテンプレートへ描画したHTMLを固定ファイル名で書き出す |
| 画面遷移図の橋渡し | `build-detail-pages-from-screen-manifest.sh`・`check-screen-transition-manifest-alignment.sh` | 画面マニフェスト（raw/ext）から画面遷移図の page-data.json を決定的に組み立て、raw/ext/page-data 3資産の整合を検査してから `build-detail-page.sh` を呼ぶ |
| 用語辞書の投影 | `project-semantic-glossary.py` | 承認済み用語集YAML（`glossary/`群の成果物）を用語辞書ページ用の page-data v0.2 へ投影する |
| サンプル再生成 | `regenerate-semantic-glossary-sample.sh`・`regenerate-sequence-samples.sh` | このリポジトリ自身の `generation-engine/samples/` を決定的に再生成する（`.claude/rules/always/portal/template-sample-sync/rule.md` が求めるテンプレート-サンプル同期のための道具） |
| 回帰テスト | `test-project-semantic-glossary-race.sh` | `project-semantic-glossary.py` のTOCTOU対策（5.1節）を検証中ファイル差し替えのレースで再現する |

## 3. 群内スクリプトの呼び出し関係

- `build-detail-pages-from-screen-manifest.sh` は自身の内部から `validate-page-data.sh`・`check-screen-transition-manifest-alignment.sh`・`build-detail-page.sh` を順に呼ぶ（該当箇所）。この3本は群内で唯一の呼び出し連鎖である
- `build-detail-page.sh` は内部で `validate-page-data.sh` を呼ぶ（該当箇所）。`--page` 種別を問わず全 page-data.json がこの検証を通る
- `regenerate-semantic-glossary-sample.sh` は `project-semantic-glossary.py` → `build-detail-page.sh` の順に呼ぶ（該当箇所）
- `regenerate-sequence-samples.sh` は群内の他スクリプトを呼ばない（`screen-sequence-template.html` を直接描画する独立系統。用語辞書・画面遷移図とは異なるテンプレートを持つため呼び出し連鎖に加わらない）
- `test-project-semantic-glossary-race.sh` は `project-semantic-glossary.py` を直接起動する（群内の呼び出し関係ではなく回帰テストとしての起動）

## 4. 他の群との依存関係

- `../render-template.sh`・`../shell-injection.sh`（`generation-engine/scripts/` ルート直下、この群の外）を `build-detail-page.sh`・`regenerate-sequence-samples.sh`・`rule-proposal/build-rule-proposal.sh` 等が共通で `source` する
- `project-semantic-glossary.py` は `glossary/validate-semantic-glossary.sh`・`glossary/validate-semantic-glossary.py` を `subprocess.run` 経由で呼ぶ（この群の外、`glossary/` 群への依存）。用語辞書の投影は「承認済みであることをこのCLIが再検証してから初めて投影する」という設計であり、`glossary/` 群が正とする承認判定ロジックを重複実装しない
- `regenerate-semantic-glossary-sample.sh`・`test-project-semantic-glossary-race.sh` は `glossary/fixtures/valid-glossary.yaml`・`glossary/fixtures/canonical-registry`（`glossary/` 群のフィクスチャ）を入力に使う
- `verification/run-layer-full-pipeline.sh`・各種一覧生成スキルの後段が、この群の出力（詳細ページHTML）をポータルへ組み込む消費側である

## 5. 共通する実装上の判断（群全体に共通する背景）

個別スクリプトの詳細設計（`詳細設計書.md`）に書く「実装判断」のうち、複数スクリプトへ横断的に現れる背景を先にここへまとめる。

### 5.1 明示テンプレート付き `mktemp`（裸の `mktemp` を避ける）

この群のスクリプトが一時ファイル・一時ディレクトリを作る箇所（`build-detail-page.sh` 該当箇所、`build-detail-pages-from-screen-manifest.sh` 該当箇所、`check-screen-transition-manifest-alignment.sh` 該当箇所、`validate-page-data.sh` 該当箇所、`regenerate-semantic-glossary-sample.sh` 該当箇所、`test-project-semantic-glossary-race.sh` 該当箇所、`project-semantic-glossary.py` の `tempfile.NamedTemporaryFile`/`tempfile.mkstemp`）は、いずれも明示テンプレート・明示ディレクトリ付きの形を使う。裸の `mktemp -d`（テンプレート省略）は `$TMPDIR` を無視し、書き込み許可の外にある既定の一時領域を使うため、サンドボックス実行環境では失敗する（`extract/` 群の基本設計書 5.1節と同じ理由。`docs/ledgers/検証で見つかった改修課題.md` 該当箇所「一時ディレクトリ-作成先」）。**手元の開発環境で裸の `mktemp` に書き換えても動いて見えることを理由に、明示テンプレートを外すな。**

### 5.2 出力先ディレクトリ内での一時ファイル経由アトミック書き込み

`build-detail-page.sh`（該当箇所）・`build-detail-pages-from-screen-manifest.sh`（該当箇所）・`project-semantic-glossary.py`（`write_atomic`）は、最終出力と同じディレクトリ内に一時ファイルを作ってから `mv`/`os.replace` する。`$TMPDIR` 配下に一時ファイルを作ってから最終出力先へ `mv` すると、両者が別ファイルシステムの場合に `mv` がコピー+削除へフォールバックし、途中でプロセスが中断すると不完全なファイルが最終パスに残りうる。同一ディレクトリ内で `mktemp` してから `mv`/`os.replace` すれば、同一ファイルシステム内のリネームとしてアトミックに完了する。

### 5.3 sha256 コマンドの実行時解決（`shasum`/`sha256sum` の分岐）

`build-detail-pages-from-screen-manifest.sh`（`manifest_hash`）・`check-screen-transition-manifest-alignment.sh`（自己テスト・本体）は、`command -v shasum` の可否で `shasum -a 256` と `sha256sum` を切り替える。macOS標準には `sha256sum` が無く `shasum -a 256` を使う必要があり、Linuxでは逆に `sha256sum` が一般的である。同じ分岐は `extract/extract-screen-metadata.sh` の `sha256_12()` に既存の理由コメント付きで存在する（先行実装）。**手元の環境（どちらか一方のコマンドしか試していない）だけで動作確認しても、両方のコマンドが分岐として残っていることの妥当性を疑うな。**

## 7. 詳細設計を個別に持たないスクリプト（第3優先: 素直でない実装なし）

以下2本は、実際にコードを読んだ結果、5.1〜5.2節の共通判断（明示テンプレート付きmktemp・アトミック書き込み）以上の個別の「素直でない実装」を持たないと判断した。

- `regenerate-semantic-glossary-sample.sh`: 固定フィクスチャ（引数省略時）か一時ファイル（引数指定時）かで出力先を切り替えるが、これは仕様上の分岐であり回避策ではない
- `regenerate-sequence-samples.sh`: 出力先の物理配置を直書きせず `output-layout.sh` 経由で解決する設計判断・既存サンプルからの値引き継ぎに python3 を使う理由は、いずれもスクリプト本体のヘッダコメント（該当箇所）と `.claude/rules/scoped/portal/page-conventions/rule.md`「### regenerate-sequence-samples.sh」に既存の記載があり、新たな加筆を要しなかった
