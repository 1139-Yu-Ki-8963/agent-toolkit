# generation-engine/scripts ルート直下群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/done/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は、どのサブディレクトリにも属さない「ルート直下」1 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する。

対象は `generation-engine/scripts/` 直下（サブディレクトリを含まない）の `.sh`・`.mjs`・`.py` 合計 32 本（実測。`find generation-engine/scripts -maxdepth 1 -type f | wc -l`）。指示書 4.3 節が定める 12 群のうち最後の 1 群にあたる。

## 2. この群が何をするか

この群は 2 つの性質を併せ持つ。

- **他の 11 群が共通して使う土台**を提供する（プレースホルダ置換・共通シェル注入・出力配置解決・分類軸解決・文字コード判定）
- **facts.yml パイプライン・整合性検査・ポータル生成・運用ガード**という、どのサブディレクトリにも収まらない個別の道具を収める

役割で 5 系統に分ける（連番は分類の便宜上のものであり、識別子ではない）。

### A. 共通ヘルパー関数（他群から `source` される）

| ファイル | 役割 |
|---|---|
| `render-template.sh` | 単一パス方式のプレースホルダ置換を担う共通関数（`render_template`）。テンプレート内の全マーカーを1回の走査で解決する |
| `shell-injection.sh` | 共通シェル（`delivery-payload/templates/partials/`）を `render_template` のマーカー引数へ展開する共通関数（`shell_injection_args`） |
| `output-layout.sh` | 生成物の出力配置（日本語パスを含む）の宣言（`output-layout.json`）をリポジトリ既定・対象側上書きの2階層で解決する共通関数 |
| `unit-axes.sh` | 分類軸・任意列の宣言（`unit-axes.json`）をリポジトリ既定・プロジェクト全種別上書き・種別別上書きの3階層で解決する共通関数 |
| `detect-encoding.sh` | 非UTF-8原本の文字コードを候補復号可否の実測で決定的に判定する共通スクリプト。他スクリプトから `source` されると `to_utf8_for_scan` 関数のみを提供する（改善課題1-131） |

## 3. 群内スクリプトの呼び出し関係

A系統（共通ヘルパー）はこの群の内側からも使われる。実測（`grep -n 'source ' generation-engine/scripts/*.sh`）:

- `audit-consistency.sh`・`scaffold-design-unit.sh`・`scaffold-screen.sh`・`check-derived-values.sh`・`build-portal.sh`・`build-deliverable-inventory.sh` が `output-layout.sh` を `source` する
- `shell-injection.sh` が `render-template.sh` を `source` する
- `build-portal.sh`・`build-deliverable-inventory.sh` が `render-template.sh` を `source` する
- `build-deliverable-inventory.sh` が `shell-injection.sh` を `source` する
- `build-portal.sh` が `portal-catalog.mjs` を `node` 経由で呼ぶ

B・C・D・E系統のスクリプト同士が互いを `bash` 経由で直接呼び出すことはない（実測: 群内相互呼び出しは A系統への依存以外に0件）。全スクリプトは独立して呼べるCLIであり、呼び出し順序は `.claude/skills/*/SKILL.md` の各手順、または `verification/run-layer-full-pipeline.sh` 等のオーケストレータが決める。

## 4. 他の群との依存関係

この群は**他の11群すべての土台**である。A系統（共通ヘルパー）は次のように広く `source` される（実測。`grep -rl` で確認）。

- `output-layout.sh`・`render-template.sh`・`shell-injection.sh`・`unit-axes.sh`・`detect-encoding.sh` は、`detail-pages/`・`extract/`・`matrix/`・`portal-input/`・`rule-proposal/`・`rules/`・`tests/`・`unit-list/`・`verification/` の各群から `../<ファイル名>` の形で `source` される
- 特に `extract/` 群の全スクリプト（`extract-ai-assets.sh` を除く）は `../detect-encoding.sh` を `source` する（`extract/基本設計書.md` 4節に既述）
- `detail-pages/`・`matrix/`・`rule-proposal/`・`unit-list/` の各HTML生成スクリプトは `../render-template.sh`・`../shell-injection.sh` を `source` する

逆方向の依存（この群が他群を呼ぶ）は薄い。`build-portal.sh` は他群が生成した成果物（マニフェスト・一覧HTML・規約定義展開）を**読み取る**が、他群のスクリプトを直接 `source`・実行はしない（成果物は `verification/run-layer-full-pipeline.sh` 等のオーケストレータが先に生成しておく前提）。

`verification/` 群の `run-layer-machine-checks.sh`（第1層の自己テスト横断実行）・`run-layer-full-pipeline.sh`（第3層の一気通貫）は、この群の多くのスクリプト（`build-portal.sh`・`seal-facts.sh`・`check-facts-sufficiency.sh` 等）を対象・段として扱う。`run-layer-machine-checks.sh` は `build-portal.sh` を実測815秒の「宣言済み長時間」スクリプトとして明示的に登録している（同スクリプト該当箇所）。

## 5. 共通する実装上の判断（群全体に共通する背景）

個別スクリプトの詳細設計（`詳細設計書.md`）に書く「実装判断」のうち、複数スクリプトへ横断的に現れる背景を先にここへまとめる。

### 5.1 明示テンプレート付き `mktemp`（裸の `mktemp` を避ける）

この群のスクリプトが一時ファイル・一時ディレクトリを作るとき、`mktemp -d "${TMPDIR:-/tmp}/<script>-work.XXXXXX"` の形で明示テンプレートを付ける。引数を省略した裸の `mktemp`/`mktemp -d` は `$TMPDIR` を無視し、書き込み許可の外にある既定の一時領域を使うため、サンドボックス実行環境では失敗する（`extract/基本設計書.md` 5.1節と同じ理由）。この対策は `check-derived-drift.sh`・`prefill-design-from-facts.sh` の本番経路（自己テストに限らない箇所）に存在する。他のほとんどのファイル（`check-agent-config-index.sh`・`check-doc-claim-freshness.sh`・`scaffold-screen.sh`・`unit-axes.sh`・`validate-env-config.sh` 等）にも同型の `mktemp -d` があるが、いずれも `--self-test` 内に限られる定型の書式であり、本番経路での失敗リスクという固有の実装判断を新たに述べる対象ではないため、個別の詳細設計は割愛する（7節参照）。

`check-derived-drift.sh` はこの群のうち唯一、裸の `mktemp` から明示テンプレートへ実際に修正した記録を持つ（コミット `803d84cdaad314cf21f8b1dadb9e2119524e0d15`「台帳の道具が一時領域を作れず止まる」）。

**既知の欠陥として残っているもの**: `add-sync-entry.sh` は `--self-test` 内で引数なしの裸の `mktemp -d`（テンプレートなし）を使っている。これは他ファイルと同じ理由で書き込みを拒む環境では失敗しうるが、指示書の指示により**素直でない実装としてではなく既知の欠陥として記録するにとどめ、修正はしない**。

### 5.2 ロケールを明示指定する（`LC_ALL=C`）

`audit-consistency.sh`・`check-derived-drift.sh`・`prefill-design-from-facts.sh` は、`sort`・`comm`・`awk` の呼び出しへ `LC_ALL=C` を明示する。理由は次の2種に分かれる。

- **日本語（多バイト文字）を含む対象を既定ロケール依存にしない**: 転記・走査の対象（画面詳細設計書.md 等）は日本語を含み、既定ロケール下では「不正なマルチバイト列」の警告や、意味の異なるキーを同一と判定する縮退が起こりうる（`extract/基本設計書.md` 5.3節と同種の理由。改善課題1-131）
- **列挙順序を環境非依存にする**: `find | sort` の照合順序はロケールデータに依存し、環境ごとに違いうる。決定的な順序を要する処理（`check-derived-drift.sh` の `list_targets`）はこれを避ける

`audit-consistency.sh` はこの対策の退行を検知する自己テスト（ケース29「整合検査-文字環境依存の回帰防止」）を持つ。全 `sort -u`/`comm -23`/`comm -13` 呼び出しが `LC_ALL=C` を伴うことを静的検査する。

### 5.3 `jq --argjson` の直接展開を避けファイル経由で渡す

この群には `extract/` 群・`build-matrix-data.sh` ほど顕著な該当箇所は無い。`build-portal.sh` の `--argjson` 使用（該当箇所）はテスト密度・規模集計等の小さな要約値であり、列や行の一覧を渡す箇所ではないため、この節の対象には含めない。`generation-engine/scripts/` 全体を横断する静的検査は `tests/check-argjson-unbounded-value.sh` が担う（許可リスト方式）。

## 7. 詳細設計を個別に持たないスクリプト（第3優先: 素直でない実装なし）

以下27本は、実際にコードを読んだ結果、次のいずれかに該当し、指示書2.1節が挙げる「素直でない実装」（一時ファイルを経由すること自体に議論の余地がある・環境変数受け渡し・ロケール明示・特定コマンドの回避・冗長な二重チェック）には該当しないと判断した。

**(a) `--self-test` 内に限られる定型の `mktemp -d` のみを持つもの**（本番経路には現れず、5.1節の対策がテスト用フィクスチャの後始末という一般的な用途にとどまる）:

- `backtest-facts-against-gold.sh`・`build-deliverable-inventory.sh`・`check-agent-config-index.sh`・`check-derived-values.sh`・`check-doc-claim-freshness.sh`・`check-doc-coverage-against-gold.sh`・`check-facts-sufficiency.sh`・`check-glossary-sync.sh`・`check-photo-findings-29.sh`・`check-prefill-markers.sh`・`check-worktree-commit-guard.sh`・`output-layout.sh`・`scaffold-design-unit.sh`・`scaffold-screen.sh`・`seal-facts.sh`・`shell-injection.sh`・`unit-axes.sh`・`validate-code-metrics.sh`・`validate-env-config.sh`

**(b) `mktemp`/`LC_ALL=C` を主要な走査対象に持たず、grep該当が `export`（一般的な変数宣言）や地の文（コメント中の言及）にとどまるもの**:

- `canonicalize-facts-scalars.py`（コメント中に `LC_ALL=C` への言及があるのみ。実装はPython標準の`errors="surrogateescape"`によるデコード安全化）
- `check-doc-coverage-against-gold.sh`（該当箇所の `export const` はJS識別子の一般的宣言であり本規約の対象外）
- `portal-catalog.mjs`（`export function` はESモジュールの標準的な公開手段であり回避対象ではない）

**(c) grep該当なし（32本のうち上記以外）**:

- `check-improvement-ledger.mjs`・`check-phase-step-structure.mjs`・`check-runbook-presence.sh`・`render-template.sh`・`validate-reverse-authoring-inputs.py`

`detect-encoding.sh` は本文中に `mktemp -d`・`LC_ALL=C` への言及を複数持つが、いずれも「呼び出し元が用意する」「本スクリプトが依存しないようにする」という説明であり、本ファイル自身の実装が明示テンプレート付き `mktemp`・`LC_ALL=C` 回避を新たに要する箇所ではない。加えて本ファイルは既にADR形式の設計判断コメント（該当箇所: 必要性・代替案・保守責任者・廃棄条件）を持ち、指示書4.2節の実質を満たしているため、個別の詳細設計は割愛する。
