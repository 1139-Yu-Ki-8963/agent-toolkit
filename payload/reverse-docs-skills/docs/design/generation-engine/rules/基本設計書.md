# generation-engine/scripts/rules 群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は `rules/` 1 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する。

対象は `generation-engine/scripts/rules/` 配下の `.sh` 5 本（実測。`find generation-engine/scripts/rules -name '*.sh' | wc -l`）。同ディレクトリには `rule.md` も置かれているが、これは Markdown の設計判断記録（本群のスクリプトが「なぜ存在するか」を書いたADR）であり、`.sh` ではないため本節の対象数には含めない。

## 2. この群が何をするか

対象リポジトリ（納品先）へ配る規約定義（`docs/rules/<親>/<子>/rule.md`）から、実行系ツール（`.claude/`・`.cursor/`・`.codex/`）が読む派生物一式を生成し、生成後の整合性を検証する。

| スクリプト | 役割 |
|---|---|
| `validate-rule-definitions.sh` | `docs/rules/<親>/<子>/rule.md` の front matter・本文の整合性を検査する。設計9節が定める7検査＋front matter 13鍵の必須・値域検査を行う |
| `build-derived-rules.sh` | `docs/rules/` の定義から `.claude/rules/`・`.cursor/rules/`・`AGENTS.md` 索引・3ツールのhooks登録・MCPサーバー設定（`.mcp.json`・`.codex/config.toml`）を生成する。実行の最初に `validate-rule-definitions.sh` を呼び、不合格なら生成しない |
| `check-rule-drift.sh` | 生成済みの派生物（`.claude/rules/**/rule.md`・`.cursor/rules/*.mdc`）が手作業で編集され、定義とずれていないかを検知する。台帳は持たず、毎回その場で再生成して現物と突き合わせる |
| `scaffold-rule-definitions.sh` | まっさらな対象リポジトリへ規約定義一式（親7・子27）の空雛形を配置する。実装フローが必須とする `flow-values.yml`・`rule.md` の初期配置も担う |
| `build-rule-flow-map.sh` | `delivery-payload/references/rule-taxonomy.json` から「規約とフローの対応」ページ（納品先ポータルの1ページ）を生成する。フェーズから引く見方と規約から引く見方の2通りを1枚に持つ |

## 3. 群内スクリプトの呼び出し関係

- `build-derived-rules.sh` は `validate-rule-definitions.sh` を **source**（`bash` での別プロセス起動ではない）し、`run_validate` 関数をそのまま呼ぶ。検証を通ってから生成するという手順（同ファイル冒頭コメント29行目）を1回の起動で完結させるための選択（詳細設計書参照）
- `check-rule-drift.sh` は `build-derived-rules.sh` を `bash` の別プロセスとして `--apply` 付きで呼び、一時ディレクトリへ生成し直した結果と現物を突き合わせる
- `scaffold-rule-definitions.sh` の `--deploy-rule-scripts` は、`build-derived-rules.sh`・`validate-rule-definitions.sh`・`check-rule-drift.sh` の3本を対象リポジトリへ複製する（重複実装せず既存3本をそのまま配る）
- `build-rule-flow-map.sh` は他の4本のいずれも呼ばず、`rule-taxonomy.json` を単独で読んで独立に動く。ルート直下の `../render-template.sh`・`../shell-injection.sh` を `source` する（共通シェル注入。他群の生成スクリプトと共通）

## 4. 他の群との依存関係

- `delivery-payload/references/規約定義と派生生成の設計.md`（設計3節・5節・6節・9節）が変換規則・検査規則の定義元。5本すべてがこの設計文書を参照する
- `delivery-payload/references/rule-taxonomy.json`（親7・子27の宣言）を `scaffold-rule-definitions.sh` と `build-rule-flow-map.sh` が読む
- `build-rule-flow-map.sh` は `generation-engine/scripts/render-template.sh`・`generation-engine/scripts/shell-injection.sh`（ルート直下、この群の外）を `source` する。ポータルの共通シェル（サイドバー・フッター・方眼紙背景）注入は他の生成スクリプト（`matrix/`・`unit-list/` 等）と同じ仕組みを使う
- `verification/run-layer-full-pipeline.sh`（この群の外）は、規約検証を第3層の生成連鎖には含めない（規約定義の生成は往復検証の対象外。`build-portal.sh` がポータル生成時に `build-rule-flow-map.sh` を呼ぶ経路がある）

## 5. 共通する実装上の判断（群全体に共通する背景）

個別スクリプトの詳細設計（`詳細設計書.md`）に書く「実装判断」のうち、複数スクリプトへ横断的に現れる背景を先にここへまとめる。個々のスクリプトの節では重複記載を避け、この節への参照に留める。

### 5.1 明示テンプレート付き `mktemp` の使用（裸の `mktemp` を避ける）

この群のスクリプトが一時ファイル・一時ディレクトリを作る箇所（`check-rule-drift.sh` の `cmd_check`・`build-derived-rules.sh` の `run_build`・`scaffold-rule-definitions.sh` の `scan_banned_terms`、および各スクリプトの `--self-test`）は、いずれも `mktemp [-d] "${TMPDIR:-/tmp}/<script>-<用途>.XXXXXX"` の形で明示テンプレートを付けて作る。引数を省略した裸の `mktemp` は `$TMPDIR` を無視し、書き込み許可の外にある既定の一時領域を使うため、サンドボックス実行環境（Claude Code のサンドボックスファイルシステム制限等）では失敗する（改善課題「一時ディレクトリ-作成先」。`docs/ledgers/検証で見つかった改修課題.md` 40行目に記録済み、状態は「完了」）。

同種の問題は、このリポジトリの別ファイル（`generation-engine/scripts/check-derived-drift.sh`）で実際に発生し修正された実績がある（コミット `803d84cdaad314cf21f8b1dadb9e2119524e0d15`「台帳の道具が一時領域を作れず止まる」）。`extract/` 群の基本設計書（5.1節）にも同じ背景が記載されている。`rules/` 配下の各ファイル自身がこの形へ退行した記録は見当たらないが、退行を検知する自己テストは持たない（`extract-component-inventory.sh` 等が持つ「mktempをシムで記録し明示テンプレートの使用を検証する」自己テストは、この群には無い）。

この判断は環境（サンドボックス実行環境かどうか）に依存する。**手元の許可された開発環境（サンドボックスなし）で裸の `mktemp` に書き換えても動いて見えることがあるが、それを理由に明示テンプレートを外すな。**

### 5.2 非日本語ロケールでの走査固定（`LC_ALL=C`）

`validate-rule-definitions.sh` の `検査-手段明示` 検査は、front matter本文（日本語を含む）を `awk -F'|'` で走査し、セルの値を比較する。macOS標準の awk（BSD awk）は、デフォルトロケール（UTF-8）下で多バイト文字列同士の等値比較を誤判定し、両辺が日本語だと比較が常に真になる不具合を持つ。この不具合により、規約の本文にある違反（検査列に手段の接頭辞が無い行）を見逃していた。`LC_ALL=C` を指定してバイト単位の比較に固定することで回避する。

この対策は、`extract/` 群が扱う「非UTF-8原本のバイト単位走査」（改善課題1-131）とは別の系統の問題である。`extract/` 群の対策は非UTF-8原本へのフォールバックが理由だが、本群の `validate-rule-definitions.sh` が読む `rule.md` は常にUTF-8で著述される前提であり、原因は原本のエンコーディングではなく **BSD awkの多バイト文字列比較の不具合そのもの** にある。

**過去に消えて再発した経緯**: この不具合は2026-08-16、コミット `eae9816d6f4a735a8881a592dab58db993b4f566`「日本語比較のロケール指定漏れと疑似入力の配置を直す」で発見・修正された。同じコミットで `LC_ALL=C` の指定漏れが本群を含む計5箇所（`extract/aggregate-test-viewpoints.sh` 2箇所・`extract/convert-message-doc-to-manifest.sh`・`extract/extract-table-metadata.sh`・`rules/validate-rule-definitions.sh`）で見つかった。本群のこの箇所自体が過去に `LC_ALL=C` を持っていて消えた記録は無く、当初から指定が漏れていたものが今回のコミットで初めて是正された。**手元の検証用データ（日本語の値が一致しないケースだけを試す等）でこの不具合が再現しないことを理由に `LC_ALL=C` を外すな。**

### 5.3 サブプロセス起動を避け `source` で関数を再利用する

`build-derived-rules.sh` は `validate-rule-definitions.sh` を `bash` 経由の別プロセスとして呼ばず、`source`（`.` コマンド）して `run_validate` 関数を直接呼ぶ。素直な形（`bash "${SCRIPT_DIR}/validate-rule-definitions.sh" "$root"` のような別プロセス起動）を避けている。理由は、生成の直前に検証するという手順（`build-derived-rules.sh` 冒頭コメント29行目）を1回のプロセス起動で完結させるため。`validate-rule-definitions.sh` 側は、source時に自動でコマンドとして実行されないよう `[ "${BASH_SOURCE[0]:-$0}" = "$0" ]` というガード（同ファイル末尾、715〜718行目）を持つ。このガード自体が「他スクリプトからsourceされて関数だけ再利用される」という設計を裏付ける既存の証跡である。

**環境依存かどうか**: 依存しない。macOS・Linuxいずれのbashでも同じ挙動になる、実行方式（プロセス数）の選択であり、OS差は無い。

**実測値**: 実測値なし（プロセス起動コストの計測は行っていない）。

**過去に消えて再発した経緯**: 記録なし。`validate-rule-definitions.sh` 側のガードコメントは既存だが、`build-derived-rules.sh` 側（source する側）には理由コメントが無かったため、本作業で追記した。

## 6. 詳細設計を個別に持つスクリプト（第1優先: 素直でない実装を持つもの）

`詳細設計書.md` を参照。以下4本について、実装契約と実装判断の節を持つ。

- `validate-rule-definitions.sh`
- `build-derived-rules.sh`
- `check-rule-drift.sh`
- `scaffold-rule-definitions.sh`

## 7. 詳細設計を個別に持たないスクリプト（第3優先: 素直でない実装なし）

`build-rule-flow-map.sh` は、実際にコードを読んだ結果、一時ファイル・環境変数・ロケール指定・特定コマンドの回避・冗長な二重チェックのいずれにも該当しないと判断した。理由は次のとおり。

- 唯一の `mktemp -d` は `--self-test` のスクラッチ領域作成のみで、本番経路（`run_build`）は一時ファイル・一時ディレクトリを一切使わない
- 入力データ（`rule-taxonomy.json`）は常にこのリポジトリ内の機械可読なJSONであり、非UTF-8原本へのフォールバックという `extract/` 群の背景（5.2節参照）が生じる余地がない。実際に `LC_ALL=C` の指定は無い
- `validate_phase_vocabulary`（未知の`phases`値を検出してエラー停止する関数）は、宣言の変化を検知する通常の防御的検証であり、素直な形を避けた実装ではない
