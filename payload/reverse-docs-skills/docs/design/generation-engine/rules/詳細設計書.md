# generation-engine/scripts/rules 群 詳細設計書

対象は `docs/tasks/done/自己設計書整備の指示書.md` 4.5節の手順で洗い出した第1優先（素直でない実装を持つ）4本。群全体の役割・呼び出し関係・共通する背景は `基本設計書.md` を参照する。ここでは各スクリプトの実装契約と、なぜその実装を採ったかという実装判断を書く。

各節の「実装判断」は指示書4.2節の4点（1: なぜ素直な形を採らなかったか、2: 実測値、3: 環境依存かどうか、4: 過去に消えて再発した経緯）に沿って記載する。

## validate-rule-definitions.sh

### 実装契約

- 引数: `<docs/rules のルート>`、または `--self-test`
- 環境変数: なし
- 出力: 標準出力へ検査サマリ、標準エラーへ不合格・警告の一覧
- 終了コード: 全rule.mdが7検査とfront matter 13鍵を満たせば `exit 0`。1件以上不合格なら `exit 1`。`--self-test` は期待どおりの検出ができなければ `exit 1`
- 副作用: なし（読み取り専用）。`--self-test` のみ `mktemp -d` でスクラッチ領域を作り削除する

### 実装判断

1. **なぜ素直な形を採らなかったか**: `検査-手段明示` 検査（front matter本文の `## 規則` 表を走査し、検査列に手段の接頭辞があるかを確認する）で `LC_ALL=C awk` を使う。素直な形（ロケール指定なしの `awk`）は、macOS標準の awk（BSD awk）がデフォルトロケール（UTF-8）下で多バイト文字列（日本語の値）同士の等値比較を誤判定し、比較が常に真になる不具合を持つため避けている。誤判定により、本来検出すべき「検査列に手段の接頭辞が無い」違反を見逃す。
2. **実測値**: 実測値なし（誤判定の再現には日本語の値を含む具体的なfront matterでの比較が要り、本作業では数値化していない）。
3. **環境に依存するかどうか**: 依存する。この不具合はmacOS標準のBSD awk固有であり、GNU awk（Linux等）では発現しない可能性がある（未検証）。**手元の検証データで問題が再現しないことを理由に `LC_ALL=C` を外すな。**
4. **過去に消えて再発した経緯**:
   | 時点 | コミット（全長） | 内容 |
   |---|---|---|
   | 2026-08-16 | `eae9816d6f4a735a8881a592dab58db993b4f566` | 「日本語比較のロケール指定漏れと疑似入力の配置を直す」。本行を含む計5箇所（`extract/aggregate-test-viewpoints.sh` 2箇所・`extract/convert-message-doc-to-manifest.sh`・`extract/extract-table-metadata.sh`・本ファイル）で `LC_ALL=C` の指定漏れが見つかり修正された |

   この時点以前に本行が `LC_ALL=C` を持っていて消えた記録は無く、当初から指定漏れだったものが今回のコミットで初めて是正された（「再発」ではなく「初回是正」）。ただし同種の指定漏れが複数箇所で同時に見つかったことから、単発の誤りではなく系統的なリスクとして扱う。

## build-derived-rules.sh

### 実装契約

- 引数: `<docs/rules のルート> <出力先リポジトリルート> [--apply]`、または `--deploy-rule-scripts <出力先リポジトリルート>`、または `--self-test`
- 環境変数: `TMPDIR`（一時ファイルの既定親。未設定時は `/tmp`）
- 出力: `.claude/rules/**/rule.md`・`.cursor/rules/*.mdc`・`AGENTS.md` の索引ブロック・3ツールのhooks登録・`.mcp.json`・`.codex/config.toml`（`--apply` 時のみ実書き込み。既定はdry-runで標準出力へ列挙のみ）
- 終了コード: `validate-rule-definitions.sh` が不合格、または引数不正で `exit 1`。正常終了は `exit 0`
- 副作用: `mktemp`（検証結果の一時ファイル）を作り削除する。`--apply` 時は出力先リポジトリへの実書き込みを行う

### 実装判断

1. **なぜ素直な形を採らなかったか**: 2点ある。
   (a) `validate-rule-definitions.sh` を独立コマンドとして `bash` 起動せず `source` する。素直な形（`bash "${SCRIPT_DIR}/validate-rule-definitions.sh" "$root"` という別プロセス起動）を避けている。`source` することで `run_validate` 関数を同一プロセス内でそのまま呼べ、「検証してから生成する」という手順を1回の起動で完結できる。`validate-rule-definitions.sh` 側は `source` 時の自動実行を避けるガード（`[ "${BASH_SOURCE[0]:-$0}" = "$0" ]`、同ファイル該当箇所）を既に持つ。
   (b) `run_validate` の標準出力・標準エラーを `mktemp` で作った一時ファイルへ一旦落とす。素直な形（`run_validate "$root"` を直接呼び出力をそのまま流す）は、正常時（大半のケース）にも検証結果の詳細が毎回標準出力へ流れる。一時ファイル経由にすることで、正常時は表示せず、不合格時だけ `cat` でまとめて表示する。
2. **実測値**: 実測値なし（(a)はプロセス起動コストの計測なし、(b)は出力量の計測なし）。
3. **環境に依存するかどうか**: (a) は環境非依存（実行方式の選択であり、OS差は無い）。(b) の一時ファイル自体は明示テンプレート付き `mktemp` を使っており、この部分はサンドボックス実行環境に依存する（基本設計書5.1節参照）。**手元の書き込み制限が無い環境で裸のmktempに戻しても動くことを理由に、明示テンプレートを外すな。**
4. **過去に消えて再発した経緯**: (a) は記録なし。`validate-rule-definitions.sh` 側のガードコメントは既存だったが、`build-derived-rules.sh` 側（source する側）には理由コメントが無かったため、本作業で追記した。(b) は基本設計書5.1節と同じ「一時ディレクトリ-作成先」の背景（`docs/ledgers/検証で見つかった改修課題.md` 該当箇所）。

## check-rule-drift.sh

### 実装契約

- 引数: `<docs/rules のルート> <出力先リポジトリルート>`、または `--self-test`
- 環境変数: `TMPDIR`
- 出力: 標準出力へ `MODIFIED:`/`DELETED:`/`ADDED:`/`CLEAN:` のいずれかの判定行
- 終了コード: ずれなし `exit 0` / ずれあり `exit 1` / 前提不足（root不在・生成失敗等）`exit 2`
- 副作用: `mktemp -d` で一時ディレクトリを作り、`build-derived-rules.sh --apply` で再生成した後、削除する

### 実装判断

1. **なぜ素直な形を採らなかったか**: 2点ある。
   (a) 生成済み派生物の変更検知に、ハッシュを記録した台帳を使わず、毎回その場で `docs/rules/` の定義から一時ディレクトリへ再生成し、現物と `diff -q` で突き合わせる。素直な形（ハッシュ台帳を持ち、以後の実行で台帳との差分を見る）は、記録と現物がずれたときにどちらが正かを決められないという弱点を持つ（台帳自体が更新漏れで古くなりうる）。定義から毎回再生成する方式であれば `docs/rules/` が常に唯一の正であり続ける。この判断はスクリプト冒頭（該当箇所）に既に詳しく記載済み。
   (b) 一時ディレクトリを明示テンプレート付きの `mktemp -d` で作る（基本設計書5.1節と同じ理由）。
2. **実測値**: 実測値なし。
3. **環境に依存するかどうか**: (a) は環境非依存（判定方式の選択であり、OS差は無い）。(b) はサンドボックス実行環境かどうかに依存する。**手元の書き込み制限が無い環境で裸のmktempに戻しても動くことを理由に、明示テンプレートを外すな。**
4. **過去に消えて再発した経緯**: (a) は記録なし（設計時点から一貫してこの方式）。(b) は基本設計書5.1節と同じ背景。この箇所自体には理由コメントが無かったため、本作業で追記した。

## scaffold-rule-definitions.sh

### 実装契約

- 引数: `<rule-taxonomy.json> <出力先リポジトリルート> [--apply] [--with-skills] [--deploy-rule-scripts]`、または `--self-test`（詳細な引数構成はスクリプト本体の使い方コメントを参照。既定はdry-run）
- 環境変数: `TMPDIR`
- 出力: `docs/rules/<親>/<子>/rule.md`・`parent.yml`・`design-notes.md`（`--apply` 時のみ実書き込み。既存 `rule.md` は上書きしない）
- 終了コード: 引数不正等で `exit 1`。`--self-test` はケース不合格があれば `exit 1`
- 副作用: `mktemp` で禁止語走査用の一時ファイルを作り削除する。`--apply` 時は出力先リポジトリへの実書き込みを行う

### 実装判断

1. **なぜ素直な形を採らなかったか**: 2点ある。
   (a) `scan_banned_terms` 関数が、禁止語一覧（`delivery-payload/references/rule-banned-terms.json`）を1件ずつ `grep` で走査せず、全語を1つの一時ファイルへ書き出してから `grep -f <一時ファイル> -F` で全対象ファイルを1回だけ走査する。素直な形（禁止語ごとに `grep` を1回呼ぶループ）は、ファイル数×語数の回数だけ `grep` プロセスをforkする。この最適化の理由は本体コメント（該当箇所）に既に記載済み。
   (b) 一時ファイルを明示テンプレート付きの `mktemp` で作る（基本設計書5.1節と同じ理由）。
2. **実測値**: (a) は「ファイル数×語数ぶんループすると自己テスト全体が数分規模に膨らむため」という定性的な記載のみで、具体的な秒数の実測値は本体コメントに無い。(b) は実測値なし。
3. **環境に依存するかどうか**: (a) は環境非依存（フォーク回数削減はOSに依らず有効）。(b) はサンドボックス実行環境かどうかに依存する。**(a) について、対象ファイル数・禁止語数が少ない手元検証で体感差が無いことを理由にループ方式へ戻すな。(b) について、手元の書き込み制限が無い環境で裸のmktempに戻しても動くことを理由に、明示テンプレートを外すな。**
4. **過去に消えて再発した経緯**: (a) は記録なし（本体コメントに既に理由があり、消えて再発した実績は見当たらない）。(b) は基本設計書5.1節と同じ「一時ディレクトリ-作成先」の背景。この箇所自体には理由コメントが無かったため、本作業で追記した。
