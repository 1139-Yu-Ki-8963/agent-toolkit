# ポータル試行の記録

作業Cの着手前に、既存の生成器（`generation-engine/scripts/build-portal.sh`）をこのリポジトリ自身へ向けて実際に試した記録。`docs/tasks/done/自己設計書整備の指示書.md` 6.1 節が定める「まず既存の生成器を自分へ向けて試し、合わなければ専用のページへ落とす」の実施結果である。確認した時点のコミット: `759c19b32de189ebe8ab9e799f9a2740a76a231e`。

## 試したこと

出力先は版管理の外（`$TMPDIR` 配下）に取った。リポジトリの中へは一切出力していない。

```
bash generation-engine/scripts/build-portal.sh "<このリポジトリのルート>" "<TMPDIR>/self-portal-trial/docs" "<TMPDIR>/self-portal-trial/portal"
```

## 結果

### 1回目: symlink検査で拒否された

macOS では `/tmp` が `/private/tmp` への symlink である。`$TMPDIR` はこの `/tmp` 配下を指すため、`build-portal.sh` 内の `assert_no_symlink_output_path`（書込先へ至る経路上の symlink を1つでも検出したら fail closed で拒否する検査）が `/tmp` の時点で symlink と判定し停止した。

```
Error: write path must not contain a symbolic link: /tmp
```

対処として `realpath "$TMPDIR"` で `/private/tmp/...` へ解決した実体パスを渡し直した。この対処自体は生成器の前提（symlinkを含む出力先を許さない）が正しく働いた結果であり、生成器側の不具合ではない。

### 2回目: 第2引数（DOCS_ROOT）の事前存在が要る

`<出力先>/docs` を新規に指定したところ、`DOCS_ROOT` が事前に存在しないディレクトリだったため異常終了した。

```
ERROR: ディレクトリが存在しません: /private/tmp/claude-501/self-portal-trial/docs
ERROR: ENOENT: no such file or directory, stat '/private/tmp/claude-501/self-portal-trial/docs'
```

`build-portal.sh` はこの引数を「新規に作る出力先」としてではなく「既に対象リポジトリの設計書一式（`docs/design/screens/screen-*/` 等の各種別ユニットルート）が置かれている場所」として前提にしている。`mkdir -p` で空のディレクトリを事前に作ってから再実行した。

### 3回目: 実行は通ったが、生成された索引（カード）が0件だった

空の `docs` ディレクトリを渡した状態で実行すると、エラーなく完走し `index.html` を書き出した（`OK: wrote .../portal/index.html`、終了コード0）。

生成された `index.html` を確認すると、`portal-catalog.json` が定義する全7カテゴリ（`project`・`standards`・`design`・`list`・`cross`・`ai`・`design-tools`）のセクションは存在するが、いずれも中身のカードが0件だった（`<section class="pm-cat" id="cat-project"></section>` のように空要素のまま）。

## どの前提が合わなかったか（具体的に）

`build-portal.sh` はポータルの「最終組み立て」の役割しか持たない。`portal-catalog.json` の各 blueprint は、`discovery` フィールドに固定の `glob`（例: `project-portal/基盤/技術スタック.html`、`project-portal/lists/screens/画面一覧.html` 等）を持ち、**この glob に一致する、既に別の `generating-<種別>-for-reverse-docs` スキルが生成済みの HTML ファイル**を `DOCS_ROOT` 配下から探して列挙するだけである。`build-portal.sh` 自身は Markdown の設計書から HTML を生成する処理を持たない。

このリポジトリ自身の成果物（作業Aで作った12群の `基本設計書.md`/`詳細設計書.md`、`.claude/rules/` の `rule.md`、`.claude/skills/` の `SKILL.md`/`guide.html`、`docs/design/reverse-verification/` の記録、`docs/ledgers/` の台帳）は、以下の2点で `portal-catalog.json` の前提と食い違う。

1. **種別（kind）が存在しない**: `portal-catalog.json` の7カテゴリ・全 blueprint は `screen`/`api`/`table`/`batch`/`report`/`external`/`feature`/`message`/`test-case` 等の業務種別、または `tech-stack`/`glossary`/`design-system` 等の特定の固定成果物を前提にしている。「スクリプト群の設計書」「規約」「スキル一覧」「検証の記録」「台帳」に対応する blueprint は1件も存在しない
2. **入力形式が食い違う**: 仮に対応する blueprint を新設したとしても、`discovery` は「`DOCS_ROOT` 配下に既に生成済みの HTML」を探す仕組みであり、Markdown（`基本設計書.md` 等）や `.claude/` 配下の設定ファイル（`rule.md`・`SKILL.md`）を直接は扱えない。それらを一覧のカードにするには、Markdown → HTML へ変換する新しい `generating-*` スキルの新設が要る

これは指示書6.1節が挙げた例（`portal-catalog.json` の blueprint が業務種別を前提にしており非業務種別の追加には `<kind>UnitRoot` の新設が要る、という具体性）と同型の結果である。今回はさらに一段深く、`<kind>UnitRoot` の新設だけでは足りず、Markdown を HTML へ変換する専用の生成スキルまで新設しないとカードが1件も生成できないことが実測で判明した。

## 判断

6種の索引（スクリプト群の設計書・規約・スキル一覧・検証の記録・台帳・既存の説明資料）はいずれも Markdown・`.claude/` 配下の設定ファイル・既存 HTML への単純なリンクで足り、業務種別のカード化・discovery の仕組みは不要である。既存の生成器を無理に拡張するコストが目的（読む場所への索引）に見合わないため、6.1節の判断基準（「合わなければ専用のページへ落とす」）に従い、専用ページ（`docs/portal/index.html`）を新設する。
