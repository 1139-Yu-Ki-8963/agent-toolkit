# generation-engine/scripts/tests 群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は `tests/` 1 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する。

対象は `generation-engine/scripts/tests/` 配下（`lib/`・`sequence-diagram/`・`unit-list/` の3サブディレクトリを含む）の `.sh`・`.cjs`・`.mjs` 計38本（実測。`find generation-engine/scripts/tests -type f \( -name '*.sh' -o -name '*.cjs' -o -name '*.mjs' \) | wc -l`）。本数が多いため、指示書の指示（「基本設計書では1本ずつ列挙せず、役割ごとにまとめて述べてよい」）に従い、役割ごとの4分類でまとめる。

## 2. この群が何をするか

対象リポジトリへ生成した成果物（ポータルHTML・設計文書・台帳等）が、規約・整合性・見た目の基準を満たしているかを検査する。役割は大きく4系統に分かれる。

| 分類 | 代表的な形 | 該当スクリプト |
|---|---|---|
| (A) リポジトリ横断の静的整合検査 | `check-*.sh`。対象ファイル群をテキストとして走査し、規約違反・参照切れ・整合性のずれを報告する。`--self-test` で判定ロジック自体の妥当性を検証する | `check-argjson-unbounded-value.sh`・`check-delivery-doc-links.sh`・`check-delivery-glossary.sh`・`check-derived-drift-ledger.sh`・`check-design-doc-section-consistency.sh`・`check-dev-flow-completion.sh`・`check-overview-consistency.sh`・`check-portal-catalog.sh`・`check-portal-rule-exclusions.sh`・`check-screen-api-linkage-contract.sh`・`check-skill-reference-paths.sh`・`check-verification-wiring.sh`・`check-wired-socket-drift.sh`（13本） |
| (B) 台帳・構造のNode.js検査 | `.test.mjs`。台帳（Markdown）や構造定義をNode.jsでパースし、件数・構造の妥当性を検査する | `check-phase-step-structure.test.sh`（bashラッパー）・`check-improvement-ledger.test.mjs` |
| (C) 実描画（ヘッドレスブラウザ）によるE2E・リグレッション | `.cjs`/`.mjs`。生成済みHTMLをヘッドレスブラウザで開き、レイアウト計測・操作イベント・DOM構造を検証する。共有ヘルパー（`lib/find-cached-browser.cjs`）を使う | `test-e2e-portal.sh`・`test-portal-conventions.sh`・`test-portal-conventions-regression.sh`・`test-er-diagram-hub-card-font-size.cjs`・`test-er-diagram-table-detail-tab.cjs`・`test-matrix-header-compact-layout.cjs`・`test-non-applicable-density.sh`・`test-portal-disabled-card-interaction.cjs`・`test-screen-doc-appendix-collapse.cjs`・`test-screen-doc-column-width.cjs`・`test-screen-doc-markdown-renderer.cjs`・`test-screen-doc-section-order.cjs`・`test-screen-doc-unresolved-callout.cjs`・`test-semantic-glossary-page.cjs`・`test-transition-diagram-initial-summary.cjs`・`sequence-diagram/test-sequence-diagram-lanes.mjs`・`sequence-diagram/test-sequence-diagram-splitting.mjs`・`lib/find-cached-browser.cjs`（18本） |
| (D) 生成フローの往復試験 | 実フィクスチャで生成スクリプト連鎖を実行し、決定性・失敗時の扱い・出力の配置を検証する。多くは「本ファイルの実行自体が回帰検証にあたる」ため `--self-test` を持たない | `test-basic-design-jsx-authored-flow.sh`・`test-design-unit-scaffold.sh`・`test-python-facts-flow.sh`・`test-screen-unit-root-layout.sh`・`unit-list/test-rebuild-screen-derived-pages.sh`（5本） |

## 3. 群内スクリプトの呼び出し関係

- (C)分類のスクリプトは `lib/find-cached-browser.cjs`（改善課題1-181で1箇所へ集約されたPlaywrightキャッシュ探索ロジック）を共有して使う
- それ以外のスクリプト同士は互いを呼ばない（各自が独立したCLIとして完結する）
- `generation-engine/scripts/verification/run-layer-machine-checks.sh`（この群の外）が、本群の `--self-test` を持つ全スクリプト・全 `.test.*` を動的に列挙し横断実行する（第1層・機械検証）。`check-verification-wiring.sh` 自身は、この動的列挙から漏れているスクリプトが無いかを検査する（「検査として実行できるファイルが集約の`--list`出力に漏れなく含まれているか」）

## 4. 他の群との依存関係

- (A)分類の多くは `generation-engine/scripts/output-layout.sh`（配置解決）・`generation-engine/scripts/unit-axes.sh`（分類軸解決）など、ルート直下の共通スクリプトをsourceする
- `check-argjson-unbounded-value.sh` は `generation-engine/scripts/` 配下の全 `.sh`（他の全群を含む）を検査対象とする横断linter
- (D)分類は `unit-list/`・`extract/`・`rules/` 等、他群の生成スクリプトを実際に呼び出して連鎖の決定性を確認する
- `generation-engine/samples/`（この群の外、リポジトリ内の実サンプル）を(C)(D)分類の多くがフィクスチャとして使う

## 5. 共通する実装上の判断（群全体に共通する背景）

### 5.1 明示テンプレート付き `mktemp` の使用（裸の `mktemp` を避ける）

本群のほぼ全スクリプトの `--self-test`（(A)(B)分類）や本番の試験実行（(D)分類）が、明示テンプレート付きの `mktemp [-d] "${TMPDIR:-/tmp}/<script>-<用途>.XXXXXX"` を使う。理由は他群（`extract/`・`rules/`・`skill-guide/`）と同じで、裸の `mktemp` が `$TMPDIR` を無視しサンドボックス実行環境で失敗するため（改善課題「一時ディレクトリ-作成先」）。

### 5.2 失敗を検知して自己検査を「不合格1件」として終える二段構え

`check-delivery-doc-links.sh`・`check-delivery-glossary.sh`・`check-portal-rule-exclusions.sh`・`check-skill-reference-paths.sh`・`check-verification-wiring.sh` 等（(A)分類の複数本）の `self_test` は、`mktemp -d ... 2>/dev/null) || tmp=""` または `mktemp -d ... || { ...; return 1; }` の形で、一時ディレクトリ作成自体が失敗しうることを想定し、失敗時は「一時ディレクトリを作れないため自己検査を実行できない」という不合格1件として明示的に終える（クラッシュに任せない）。このエラーメッセージ自体が理由を語っており、追加のコメントを要しない程度に自己説明的である。`skill-guide/check-guide-script-paths.sh`（別群）にも同型のパターンがある。

### 5.3 `LC_ALL=C` によるロケール非依存の決定的な順序付け

`check-delivery-doc-links.sh`・`check-portal-rule-exclusions.sh`・`check-skill-reference-paths.sh` は、`find`・`grep` の出力を `LC_ALL=C sort` へ通す。理由は `skill-guide/` 群の基本設計書5.2節と同じで、実行環境の照合順序に依存しない決定的な順序（走査順・報告順）を保証するため。

## 6. 詳細設計を個別に持つスクリプト（第1優先: 素直でない実装を持つもの）

`詳細設計書.md` を参照。以下5本について、実装契約と実装判断の節を持つ。本群は本数が多いため、全スクリプトを対象とせず、実際にコードを読んで「一時ファイルの扱い・既知の欠陥・特定手法の意図的な回避」が明確に確認できたものだけを選んだ。

- `check-argjson-unbounded-value.sh`（既にスクリプト本体が詳細な設計判断コメントを持つ。本群のもう1つの実例）
- `check-portal-catalog.sh`（**既知の欠陥**。指示書の指示により直さず記録のみ行う）
- `unit-list/test-rebuild-screen-derived-pages.sh`（symlink祖先回避・Git履歴依存の排除の2点）
- `lib/find-cached-browser.cjs`（ブラウザの自動ダウンロードを避けキャッシュ探索へ切り替えた背景）
- `check-improvement-ledger.test.mjs`（追記型台帳に対する固定行数比較の回避）

## 7. 詳細設計を個別に持たないスクリプト（第3優先）

上記5本以外の33本は、実際にコードを読んだ結果、5.1〜5.3節に挙げた群共通のパターン（明示テンプレート付きmktemp・自己検査の失敗検知・`LC_ALL=C`）の範囲にとどまり、かつそれらのパターン自体は既にエラーメッセージや既存コメントで自己説明的であるため、個別の詳細設計は省略する。将来これらのスクリプトへ新たな非自明な実装（一時ファイル経由・環境変数受け渡し・特定コマンドの回避・冗長な二重チェック）を加える場合は、本文書の対象へ追加し、指示書4.2節の4点を書くこと。
