## check-argjson-unbounded-value.sh

### 実装契約

- 引数: `[--target <generation-engine/scripts のパス>]`、または `--self-test`
- 環境変数: `TMPDIR`
- 出力: 標準出力へ検査結果（許可リスト外の `--argjson` 使用の一覧、または「PASS」）
- 終了コード: 許可リスト外の使用が1件以上あれば `exit 1`。`--self-test` はケース不合格があれば `exit 1`
- 副作用: `--self-test` のみ `mktemp -d` でスクラッチ領域を作り削除する

### 実装判断

このスクリプト自体が `generation-engine/scripts/` 配下の他ファイルの「素直でない実装」（`jq --argjson` の直接展開回避）を検出するlinterであり、本作業（`docs/tasks/done/自己設計書整備の指示書.md` 2.1節）の直接の動機となった実例を扱う。スクリプト本体の冒頭コメント（該当箇所）が指示書4.2節の4点をほぼそのまま満たす形で既に記載済みのため、本節では要約と補足のみ書く。

1. **なぜ素直な形を採らなかったか**: 検出方式に「変数名の規則（`*cols*`/`*rows*`等の『可変長らしい』名前を検出する）」という単純な方式Aではなく、「現存する全 `--argjson` 使用箇所を洗い出し、ファイルパス・jq側引数名・渡す値の3つ組を許可リスト化するdefault-deny方式B」を採った。理由は、方式Aでは今回まさに実際に起きた回帰（`main_cols_json`という「らしい」名前から`mainColumns`というjq側の別名を経由し`--argjson m`という抽象的な1文字名で渡される）のような、キーワードを含まない別名での再導入を確実には拾えないため。
2. **実測値**: 引数長の上限はLinuxで131,071バイト（本体コメント該当箇所）。
3. **環境に依存するかどうか**: 依存する。macOSにはこの引数長上限が実質無く、対象OSのLinuxにはある。**手元（macOS）で問題が再現しないことを理由に、対策を外したり許可リストを緩めたりするな。**
4. **過去に消えて再発した経緯**: 本体コメント該当箇所に既に詳述されている。要点は指示書2.1節と同じ（`970a9cc99d45bcbe51c437f3c4623aecb98012d5` で対策 → `ac9c6df82e51e3dc641c6b9154b2909940e3e0fb` で回帰 → `eff91aa06a71f89072b7b525710173406f0f8098` で再対策）。この回帰こそが本スクリプト新設の直接の理由であり、「対策を入れる」だけでは同じ経路が再び壊れても気付けないことを示す実例である。

## check-portal-catalog.sh（既知の欠陥・self_test は判定不能化で対応済み、capture_golden は未対応のまま）

### 実装契約

- 引数: 省略時（既定の検証・比較を実行）、または `--self-test`、または `--capture-golden --commit <sha> --repo-root <dir> --output <file>`
- 環境変数: `TMPDIR`（本来使われるべきだが、`capture_golden` 内の裸の `mktemp` は実際には参照していない。下記「実装判断」参照）
- 出力: `node portal-catalog.mjs` の `validate`/`compare` の結果、および本体のセマンティック用語辞書ブループリント検査
- 終了コード: 検査不合格・JSON構造不正で `exit 1`。`self_test` 内の `mktemp -d` 失敗時は `exit 2`（`[UNKNOWN]`、判定不能規約準拠）
- 副作用: `capture_golden`（該当箇所、裸の `mktemp`/`mktemp -d` のまま）・`self_test`（該当箇所、判定不能化済み）で一時ファイル・一時ディレクトリを作る

### 実装判断

**本スクリプトの `mktemp` は当初（該当箇所）他群・本群の他スクリプトと異なり明示テンプレートを持たない裸の呼び出しだった。** 改善課題1-57（自己テストが失敗の理由を示さない）への対応として、`self_test`（該当箇所）だけを判定不能規約（`.claude/rules/always/verification/indeterminate-result/rule.md`）の形へ是正した。`capture_golden`（該当箇所）は自己テスト経路（`run-layer-machine-checks.sh` が呼ぶ既定・`--self-test`）から呼ばれないため対象外とし、裸の呼び出しのまま残す。

1. **なぜ素直な形（裸のmktemp）のままなのか（`capture_golden` について）**: 意図的な設計判断ではなく、他群・本群の他スクリプトに適用されている「明示テンプレート付きmktemp」（基本設計書5.1節）の対策が、本関数にはまだ適用されていない未対応箇所である。`self_test`（該当箇所）については、明示テンプレート形式ではなく判定不能規約の形（`if !` 構文での失敗チェック・`[UNKNOWN]`ラベル・`exit 2`）を採った。理由は、この規約が「実行できなかった」と「不合格だった」を機械的に区別する形として1-57が優先する対応だったため。
2. **実測値**: `self_test` の是正後、サンドボックス制約下では `[UNKNOWN]`・`exit 2`（`bash generation-engine/scripts/tests/check-portal-catalog.sh --self-test` を通常実行）、制約解除（`dangerouslyDisableSandbox: true`）では全9ケースPASS・`exit 0` になることを確認した。
3. **環境に依存するかどうか**: 依存する。書き込み許可の外にある既定の一時領域を使うため、`$TMPDIR` が書き込み制限のあるサンドボックス実行環境を指す場合に失敗しうる（基本設計書5.1節と同じ機序）。`capture_golden`（該当箇所）は次にこのファイルへ触れる際に、他群と同じ明示テンプレート形式（`mktemp [-d] "${TMPDIR:-/tmp}/check-portal-catalog-<用途>.XXXXXX"`）へ是正することが望ましいが、自己テスト経路の対象外であるため本作業のスコープ外として温存する。
4. **過去に消えて再発した経緯**: 記録なし（他ファイルのような「対策が入って消えた」という経緯ではなく、そもそも対策が入っていなかった）。

## unit-list/test-rebuild-screen-derived-pages.sh

### 実装契約

- 引数: なし（実行するだけで一連のフィクスチャ試験を行う）。`--self-test` は持たない（本ファイルの実行自体が回帰検証にあたるため。改善課題1-138の横断検収条件の対象外と明記済み）
- 環境変数: `TMPDIR`
- 出力: 標準出力へ各ケースの結果（`ERROR:`/`FAIL:` があれば異常終了）
- 終了コード: いずれかのケース不合格で `exit 1`。全ケース通過で `exit 0`（スクリプト末尾まで到達）
- 副作用: `mktemp -d` で一時ディレクトリを作り、`run_rebuild` で複数回の再生成を行い、削除する（`trap ... EXIT`）

### 実装判断

1. **なぜ素直な形を採らなかったか**: 2点ある。
   (a) `mktemp -d` の直後に `tmp="$(cd "$tmp" && pwd -P)"` で物理パスへ解決する。素直な形（`mktemp -d` の結果をそのまま使う）は、macOSで `/tmp` が `/private/tmp` へのsymlinkであるため、`build-portal.sh` の `assertNoLexicalSymlink`（書込先の祖先パスにsymlinkを許さないfail-closed検査）がsymlink祖先を理由にrebuildそのものを拒否してしまう（改善課題1-97）。本体コメント該当箇所に既に記載済み。
   (b) フィクスチャの入力元を、素直な形（固定commitのGit履歴を `git show <commit>:...` で参照する）ではなく、`generation-engine/samples/` 配下のchecked-in raw manifestを直接読む方式にしている。理由は本体コメント該当箇所に既に記載済み：固定commitがチェックアウト環境のGit履歴に存在しない場合に即時停止する問題と、本リポジトリがモノレポのサブディレクトリとして配置される環境でGit-toplevel前提のパス解決が破綻する問題の両方を、Git・commitへの依存を排することで解消した。
2. **実測値**: 実測値なし。
3. **環境に依存するかどうか**: (a) は依存する。macOS固有の `/tmp` symlink構造に起因し、Linux等symlinkを介さない環境では顕在化しない可能性がある（未検証）。**手元がLinux等でこの問題が再現しないことを理由に、`pwd -P` による物理パス解決を外すな。**(b) は依存する。モノレポのサブディレクトリとして配置されるかどうかという、リポジトリの配置構成に依存する問題。**単体のリポジトリとしてチェックアウトした手元環境で問題が再現しないことを理由に、Git履歴参照方式へ戻すな。**
4. **過去に消えて再発した経緯**: (a) は改善課題1-97として記録済み（本体コメントに既述）。(b) は「旧実装はprepare-screen-rebuild-sample-fixture.sh経由で固定commitのGit履歴を参照していた」という記載から、過去に別方式だったことが分かる（本体コメント該当箇所）。いずれも本作業時点で理由コメントが既に十分であり、新たな加筆は行っていない。

## lib/find-cached-browser.cjs

### 実装契約

- エクスポート: `findCachedBrowser()` 関数（引数なし、戻り値: 見つかったブラウザ実行ファイルの絶対パス文字列、無ければ空文字列）
- 環境変数: `PLAYWRIGHT_BROWSERS_PATH`（優先的に探索するキャッシュルート）・`LOCALAPPDATA`（Windows環境でのキャッシュルート）
- 出力: なし（関数の戻り値のみ）。副作用なし（読み取り専用のファイルシステム走査）
- 終了コード: 該当なし（モジュールであり、CLIとして単独実行されない）

### 実装判断

1. **なぜ素直な形を採らなかったか**: (C)分類のDOM計測系テスト（ヘッドレスブラウザで実描画するE2E試験）が、素直な形（Puppeteer/Playwrightの `launch()` に任せ、必要ならブラウザを自動ダウンロードさせる）ではなく、OS標準のキャッシュ格納場所（`~/Library/Caches/ms-playwright`・`~/.cache/ms-playwright`・`%LOCALAPPDATA%\ms-playwright`、および `PLAYWRIGHT_BROWSERS_PATH` 環境変数が指す場所）を再帰的に走査し、既にキャッシュ済みのブラウザ実行ファイルを探して使う。ネットワーク接続が制限されうる実行環境（このリポジトリの開発環境を含む）では、テスト実行のたびにブラウザをダウンロードする自動処理が失敗しうるため。
2. **実測値**: 実測値なし。
3. **環境に依存するかどうか**: 依存する。ネットワーク接続が制限されている、またはブラウザが未キャッシュの環境では、本関数が空文字列を返し呼び出し側のテストが失敗しうる。**ネットワーク接続が自由な手元環境で自動ダウンロードが機能することを理由に、この探索ロジックを外して `launch()` の既定動作へ戻すな。**
4. **過去に消えて再発した経緯**: 改善課題1-181（本体コメント該当箇所）「この探索ロジックが一部のテストにしか実装されておらず、環境変数未指定時にブラウザを検出できないテストが存在した」ことを受け、1箇所へ集約した。集約前は各テストが個別に（不完全な形で）実装しており、再発というより「重複と欠落の是正」にあたる。

## check-improvement-ledger.test.mjs

### 実装契約

- 実行方法: Node.js標準のテストランナー（`node --test`）経由、または `run-layer-machine-checks.sh` の動的列挙対象（`test-*.mjs` として拾われる）
- 入力: `docs/tasks/指摘改善一覧.md`（実在の台帳ファイル）と、テスト内で組み立てる合成データの両方
- 終了コード: `node --test` の標準的な仕組みに従う（1件でもアサーション不合格があれば非0）
- 副作用: なし（読み取り専用）

### 実装判断

1. **なぜ素直な形を採らなかったか**: `docs/tasks/指摘改善一覧.md`（実在のファイル、追記型で行数が増え続ける）に対する検査で、素直な形（`result.totalDataRows === <特定の固定値>` という厳密一致比較）ではなく、(a) `totalDataRows >= 259` という下限チェック、(b) `columnCountHistogram` が全行6列に集約されるという構造検査、(c) `unverifiedExactCount <= unverifiedContainsCount <= totalDataRows` という値同士の大小関係の検査、の組み合わせに置き換えている。素直な厳密一致は、台帳へ正当な行が追記されるたびに陳腐化してFAILする。
2. **実測値**: 実測値なし（259という下限値は「現時点の実測行数」であり、将来の追記を妨げない下限としての性質を持つ）。
3. **環境に依存するかどうか**: 依存しない。台帳の行数増加という運用上の性質に起因する問題であり、OS・実行環境の差ではない。**行数が259を上回っている手元の状態を見て「もう固定値比較で十分」と判断し、下限チェック・構造検査へ戻すな（台帳は今後も追記され続けるため、固定値比較は再び陳腐化する）。**
4. **過去に消えて再発した経緯**: 記録なし。本体コメント該当箇所・該当箇所に既に理由が記載されており、新たな加筆は行っていない。

## test-non-applicable-density.sh

### 実装契約

- 実行方法: 固定5サンプル（`generation-engine/samples/` 配下の画面詳細設計書.md 5件）に対する回帰試験。`--self-test` フラグは持たず、本ファイルの実行自体が回帰検証にあたる
- 出力: 標準出力へ `[PASS]`/`[FAIL]` 行
- 終了コード: いずれかの検査が不合格なら `exit 1`
- 副作用: なし（読み取り専用）

### 実装判断

1. **なぜ素直な形を採らなかったか**: `summary_count` を求める awk 呼び出しに `LC_ALL=en_US.UTF-8` を明示している。負の文字クラス（`[^[:space:]）)]`）で全角文字（`）`）を除外して根拠の有無を判定するが、`LC_ALL=C` の下ではこの負の文字クラスが全角文字を正しく除外できず、根拠が正しく記入された行まで誤って未記入と判定する偽陽性を生む。使い分けの一般原則は `.claude/rules/always/design-record/implementation-decision/rule.md`「ロケールの使い分け」節を参照する。
2. **実測値**: 「本領域は全項目非該当（根拠: ...）」という正しく記入された行に対し、`LC_ALL=C` 下では誤って検出（偽陽性）、`LC_ALL=en_US.UTF-8` 明示後は誤検出なしを実測した（改善課題1-241、bash 5.3.15 / macOS 標準 awk 20200816）。本スクリプト自体も、デフォルトロケールと `LC_ALL=C` を明示的に付与した呼び出しの両方で `[PASS]` が揃うことを実測した。
3. **環境に依存するかどうか**: 依存する。呼び出し元シェルの環境変数に `LC_ALL=C` が設定されているかどうかに依存する。**手元の環境で偽陽性が再現しないことを理由に `LC_ALL=en_US.UTF-8` の明示を外すな。**
4. **過去に消えて再発した経緯**: 記録なし。改善課題1-241で新規に発見・是正した。
