# generation-engine/scripts/unit-list 群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は `unit-list/` 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する2群目である（1群目は `docs/design/generation-engine/extract/` を参照）。

対象は `generation-engine/scripts/unit-list/` 配下の `.sh` 13 本（実測。`find generation-engine/scripts/unit-list -name '*.sh' | wc -l`）。

## 2. この群が何をするか

対象リポジトリの原本コードを走査して画面を検出し、種別ごとの一覧 HTML（画面一覧・API一覧等7種別・機能一覧）を生成し、それらの入力となるマニフェスト（JSON）のスキーマ・整合性を検証し、生成済み一覧 HTML からマニフェストを復元・再生成するトランザクション管理までを担う。大きく5系統に分かれる。

| 系統 | スクリプト | 入力 | 出力 |
|---|---|---|---|
| 画面検出 | `detect-screens.sh` | ソースディレクトリ（React/Next.js等） | `screen-manifest.json`（raw。`screens[]`・`detectionSummary` 等） |
| 一覧HTML生成 | `build-screen-list.sh`・`build-feature-list.sh`・`build-unit-list.sh` | 拡張済みマニフェスト（`unit-list`自身は生成しない。`extract/`群が拡張したものを受け取る） | 画面一覧・機能一覧・汎用一覧（API/テーブル/バッチ/帳票/外部連携/message/test_viewpoint/test_case）のHTML |
| マニフェスト検証 | `validate-manifest.sh`・`validate-message-manifest.sh`・`validate-test-case-manifest.sh`・`validate-test-viewpoint-manifest.sh` | マニフェストJSON | 標準エラーへの `[PASS]`/`[FAIL]` 診断行、終了コード |
| 永続化・整合性チェック | `check-manifest-persistence.sh`・`check-screen-manifest-consistency.sh` | 出力ディレクトリ、raw/ext 両マニフェスト | 標準エラーへの診断、終了コード |
| 復元・再生成トランザクション | `restore-screen-manifest.sh`・`rebuild-screen-derived-pages.sh` | 生成済み一覧HTML（埋め込みJSON）、raw manifest | 復元されたmanifest、13派生成果物の一括再生成 |
| テスト専用フィクスチャ | `prepare-screen-rebuild-sample-fixture.sh` | 過去commitのcheck-in済みHTML | テスト用のraw fixture一式 |

## 3. 群内スクリプトの呼び出し関係

群内スクリプト同士は次のとおり呼び合う（実測。`grep -rn '"\$SCRIPT_DIR/'`）。

- `build-unit-list.sh` は `unit_kind` に応じて `build-screen-list.sh`（`screen`）・`build-feature-list.sh`（`feature`）へ委譲するか、自前の汎用テンプレートで生成する（それ以外の種別）。委譲時は `--axes` へ事前解決した分類軸ファイルを明示的に渡す（8節・実装判断参照）
- `build-unit-list.sh`・`build-screen-list.sh`・`build-feature-list.sh` はいずれも生成前に `validate-manifest.sh` を呼び、検証失敗ならビルドを中止する。`build-unit-list.sh` は種別によって `validate-test-viewpoint-manifest.sh`・`validate-message-manifest.sh`・`validate-test-case-manifest.sh`・`validate-manifest.sh` のいずれかへ切り替える
- `restore-screen-manifest.sh` は復元後のmanifestを `validate-manifest.sh` で検証してからコミットする
- `rebuild-screen-derived-pages.sh` は群内の `validate-manifest.sh`（raw manifestの事前検証）・`check-screen-manifest-consistency.sh`（raw/ext突合）を呼び、群外の `extract/extract-screen-metadata.sh`・`extract/build-matrix-data.sh`・`extract/build-permission-function-data.sh`・`detail-pages/build-detail-pages-from-screen-manifest.sh`・`matrix/build-matrix-pages.sh`・`build-portal.sh`（ルート）を正しい順序で呼ぶオーケストレータである
- `prepare-screen-rebuild-sample-fixture.sh`・`check-manifest-persistence.sh`・`check-screen-manifest-consistency.sh` は群内の他スクリプトを呼ばない独立したCLIである

## 4. 他の群との依存関係

- `../output-layout.sh`（`generation-engine/scripts/` ルート直下）を `check-manifest-persistence.sh`・`check-screen-manifest-consistency.sh`・`validate-manifest.sh`・`rebuild-screen-derived-pages.sh` が `source` する。出力配置パスの宣言解決を担う共通ヘルパー
- `../unit-axes.sh`（同ルート直下）を `build-feature-list.sh`・`build-screen-list.sh`・`build-unit-list.sh`・`validate-manifest.sh` が `source` する。分類軸・任意列の宣言解決を担う共通ヘルパー
- `../shell-injection.sh`（同ルート直下）を `build-feature-list.sh`・`build-screen-list.sh`・`build-unit-list.sh` が任意（存在すれば）で `source` する。共通シェル（サイドバー等）の注入を担う
- `extract/` 群が拡張したマニフェスト（`screen-manifest.json`等）をこの群は入力として受け取る（この群は manifest の「拡張」ではなく「生成・検証・復元」を担う）。`validate-manifest.sh` は `unit_kind=table` かつ `--migrations-dir` 指定時のみ `extract/extract-table-metadata.sh` を再実行して履歴突き合わせを行う（逆依存）
- `rebuild-screen-derived-pages.sh` は `extract/`・`detail-pages/`・`matrix/`・ルート直下の `build-portal.sh` を横断して呼ぶ、群を越えたオーケストレータである
- `verification/run-layer-full-pipeline.sh` がこの群のスクリプト（`detect-screens.sh`・`build-screen-list.sh`・`build-unit-list.sh`・`build-feature-list.sh`）を正しい順序で呼ぶ、群の外側からの呼び出し元である

## 5. 共通する実装上の判断（群全体に共通する背景）

個別スクリプトの詳細設計（`詳細設計書.md`）に書く「実装判断」のうち、複数スクリプトへ横断的に現れる背景を先にここへまとめる。個々のスクリプトの節では重複記載を避け、この節への参照に留める。

### 5.1 mktemp+mvの2段でファイル拡張子付き一時ファイルを作る

`build-feature-list.sh`・`build-screen-list.sh`・`build-unit-list.sh`・`validate-manifest.sh` の4本は、`.json` 拡張子付きの一時ファイルを `_base="$(mktemp "テンプレート.XXXXXX")"; out="${_base}.json"; mv "$_base" "$out"` という mktemp+mv の2段で作る。素直な形（`mktemp "テンプレート.XXXXXX.json"` で拡張子をテンプレートへ直接後置する1回呼び出し）は、乱数展開（`XXXXXX` の置換）が効かない環境があったため避けている。コミット `93eb2d6793dd30f0ae8320b372c823177c8f301c`（2026-08-14・「【バグ修正】一時ファイル名の乱数展開を効かせる」）で4本まとめて1回呼び出しから2段へ書き換えられた。手元（macOS/BSD `mktemp`）では1回呼び出し（`mktemp "テンプレート.XXXXXX.json"`）でも乱数展開が正しく行われることを実測で確認したが、この修正コミットの表題どおり乱数展開が効かない環境が存在したことが書き換えの動機である。具体的にどの `mktemp` 実装（GNU coreutils・util-linux等）で効かなかったかは、コミットメッセージ・本文からは読み取れない。

### 5.2 mktempの作成先を`${TMPDIR:-/tmp}`ではなく最終出力先の同一ディレクトリにする

`restore-screen-manifest.sh`（`tmp_out`）と `rebuild-screen-derived-pages.sh`（`transaction_root`・`backup_root`）は、一時ファイル・一時ディレクトリを `${TMPDIR:-/tmp}` 配下ではなく、最終的な出力先（`$MANIFEST_OUT`・`$output_root`）と同じ親ディレクトリへ作る。理由は、コミット段で `mv` により一時領域から最終出力先へ移すためである。`mv` は同一ファイルシステム上であれば原子的な rename になるが、別ファイルシステムをまたぐと copy+delete へ縮退し、中断時に一部だけ移動済みという非原子的な状態を許してしまう。`${TMPDIR:-/tmp}` は最終出力先と別ファイルシステムになりうる（例: `/tmp` が tmpfs、出力先が永続ボリューム）ため、意図的に避けている。

### 5.3 `LC_ALL=C`によるバイト単位比較（detect-screens.sh）

`detect-screens.sh` の3箇所（`classify_screen()`内の親画面解決2箇所、クラスタ引き当て1箇所）は `awk` の呼び出しに `LC_ALL=C` を明示する。既定ロケールの `awk` は日本語（マルチバイト文字）を含むフィールドの `==` 比較を誤判定することがあり、コミット `763861cd73b3b27f0e3b4c3441ead8b0155383b5`（2026-08-10・「【バグ修正】日本語比較の誤判定と配置由来の空振りを直す」）で実際にこの3箇所へ `LC_ALL=C` が追加され、誤判定が修正された。extract群5.3節の `LC_ALL=C`（非UTF-8原本への `to_utf8_for_scan` フォールバック対策）とは発生源が異なる。こちらは `to_utf8_for_scan` を経由せず、日本語文字列同士の等価比較そのものが既定ロケールで狂う問題への対策である。

### 5.4 `--slurpfile`によるファイル経由の値渡し（detect-screens.sh）

`resolve_files_subcommand()` 内の `jq --slurpfile updates "$rf_updates_file"` は、更新後の画面配列をシェル変数へ代入して `--argjson` で渡す素直な形を避け、一時ファイル経由で渡している。本体コメント（525行目）に「jqの値受け渡しは一時ファイル+--slurpfileで行う(引数長・エスケープ事故を避ける)」と既に記載済みであり、extract群5.4節と同種の対策（引数長上限回避）である。

### 5.5 既知の欠陥として直さないもの: `detect-screens.sh`の裸`mktemp`（60箇所）

`detect-screens.sh` は一時ファイル・一時ディレクトリの作成に、明示テンプレート（`mktemp "${TMPDIR:-/tmp}/<名前>.XXXXXX"`）を一切使わず、引数なしの裸の `mktemp`／`mktemp -d` を60箇所（実測。`grep -n 'mktemp' generation-engine/scripts/unit-list/detect-screens.sh | wc -l` = 60、うち `XXXXXX` を含む行は0件）で使っている。裸の `mktemp` は `$TMPDIR` を無視し、OSの既定一時領域（macOSでは `/var/folders/.../T/`）を使うため、書き込みが許可されていない実行環境では失敗する。

これは実際にこの作業中に実測した。本セッションの環境（`TMPDIR=/tmp/claude-501`、サンドボックス実行環境）で `mktemp` を引数なしで実行すると次のとおり失敗する。

```
$ echo "TMPDIR=$TMPDIR"; mktemp
TMPDIR=/tmp/claude-501
mktemp: mkstemp failed on /var/folders/qb/_25w1xv13fs8lh1z_6cwmvbc0000gn/T/tmp.07hrPwnKbb: Operation not permitted
```

同じ理由で、`detect-screens.sh --self-test` を同環境で実行すると、スクリプト冒頭（引数解析より前、91〜93行目）の裸`mktemp`呼び出しでただちに失敗し、`--self-test` が求めるどの検査にも到達しない。

```
$ bash generation-engine/scripts/unit-list/detect-screens.sh --self-test
mktemp: mkstemp failed on /var/folders/qb/_25w1xv13fs8lh1z_6cwmvbc0000gn/T/tmp.dZwvRI81y6: Operation not permitted
```

`docs/ledgers/検証で見つかった改修課題.md`（40行目「一時ディレクトリ-作成先」、対象「抽出スクリプト群」、状態「完了」）は同種の欠陥を `extract/` 群の3スクリプトについてのみ修正済みとしており、`unit-list/detect-screens.sh` はこの修正の対象に含まれていない。つまり `detect-screens.sh` の60箇所は、対象スクリプト群を限定した過去の改修が及ばなかった未修正の欠陥であり、現時点でも実際に失敗する。

**この欠陥はこの周では直さない。**`docs/tasks/自己設計書整備の指示書.md` の指示に従い、直す対象であることの記録として本節へ残す。60箇所を一括で明示テンプレートへ書き換える修正は、影響範囲が広く（呼び出し元・自己テストのフィクスチャパス前提を含め）本作業（コメント追記のみ）のスコープを超える。

## 7. 詳細設計を個別に持たないスクリプト（第3優先: 素直でない実装なし）

以下6本は、実際にコードを読んだ結果、2.1節が挙げる「素直でない実装」（一時ファイルを経由すること自体に議論の余地がある・環境変数受け渡し・ロケール明示・特定コマンドの回避・冗長な二重チェック）には該当しないと判断した。理由は次のとおり。

- `check-manifest-persistence.sh`: `--self-test` 用の `mktemp -d` のみ（明示テンプレート付き。5.1〜5.2節のような同一ファイルシステム制約や乱数展開の問題を持たない標準的な自己テスト用一時領域）。本体の永続化検査ロジック自体は `output-layout.sh` の宣言解決とファイル存在確認のみで、素直でない実装は無い
- `check-screen-manifest-consistency.sh`: 同上（`--self-test` 用の `mktemp -d` のみ）。`--argjson` の使用（104・109行目）は固定の許可値リストであり、`check-argjson-unbounded-value.sh` の許可リスト外検査も通過している（可変長の懸念なし）
- `prepare-screen-rebuild-sample-fixture.sh`: テスト専用のフィクスチャ生成スクリプト（改善課題1-138の横断検収条件の対象外と本体コメントに明記済み）。`mktemp -d "$(dirname "$output")/.screen-fixture.XXXXXX"` は出力先と同じディレクトリに作るが、`cp -a` でコピーするだけで `mv` によるコミットは行わないため、5.2節のような同一ファイルシステム制約の理由には該当しない。単に「テスト実行ごとの隔離された作業場所」という一般的な用途であり、素直でない実装とは判断しなかった
- `validate-message-manifest.sh`・`validate-test-case-manifest.sh`・`validate-test-viewpoint-manifest.sh`: いずれも `--self-test` 用の `mktemp -d`（明示テンプレート付き）のみ。検証ロジック自体はマニフェストのJSONスキーマ・必須フィールドの確認であり、一時ファイル経由・環境変数受け渡し・ロケール明示のいずれも使わない
