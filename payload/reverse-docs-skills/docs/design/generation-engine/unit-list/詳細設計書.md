対象は `docs/tasks/done/自己設計書整備の指示書.md` 4.5節の手順で洗い出した第1優先（素直でない実装を持つ）7本。群全体の役割・呼び出し関係・共通する背景は `基本設計書.md` を参照する。ここでは各スクリプトの実装契約と、なぜその実装を採ったかという実装判断を書く。

## build-feature-list.sh

### 実装契約

- 引数: `<manifest.json> <output-html-path> [--portal-dir <path>] [--project-name <name>] [--axes <file>] [--catalog <file>]`、または `--self-test`
- 環境変数: `TMPDIR`（一時ファイルの既定親。未設定時は `/tmp`）
- 出力: `<output-html-path>`（機能一覧HTML）
- 終了コード: 引数不足・`validate-manifest.sh`失敗等で `exit 1`。正常終了は `exit 0`
- 副作用: `_embed_manifest_base`/`EMBED_MANIFEST`（sourceDirが絶対パスの場合のみ作る正規化済み一時JSON、`trap`で削除）を作る

### 実装判断

1. **なぜ素直な形を採らなかったか**: `EMBED_MANIFEST`（HTMLへ埋め込む正規化済みマニフェストの一時JSON）を、`mktemp` のテンプレートへ直接 `.json` を後置する1回呼び出し（`mktemp "テンプレート.XXXXXX.json"`）ではなく、拡張子なしでmktempしてから `mv` で `.json` を付与する2段の形にしている。基本設計書5.1節参照。
2. **実測値**: 手元（macOS/BSD `mktemp`）では1回呼び出しの形（`mktemp "テンプレート.XXXXXX.json"`）でも乱数展開は正しく行われることを実測した（`mktemp "${TMPDIR:-/tmp}/test-XXXXXX.json"` を実行し、`XXXXXX` がランダムな文字列へ置換された実ファイルが作られることを確認）。修正コミットが対象とした「乱数展開が効かない環境」がどの `mktemp` 実装かは、コミットメッセージ・本文に記載が無く読み取れない。
3. **環境に依存するかどうか**: 依存する。`mktemp` の実装（GNU coreutils・util-linux・BSD等）によってテンプレート内の拡張子後置サポートが異なる可能性がある。**手元（macOS）で1回呼び出しの形に戻しても動くことを理由に、mktemp+mvの2段を1回呼び出しへ戻すな。**
4. **過去に消えて再発した経緯**: 記録なし（再発ではなく、コミット `93eb2d6793dd30f0ae8320b372c823177c8f301c`（2026-08-14・「【バグ修正】一時ファイル名の乱数展開を効かせる」）による初回の対策導入）。本作業でこの経緯を本体コメントへ追記した（追記前は理由コメントが無かった）。

- 出力: `<output-html-path>`（画面一覧HTML。`--split-by`指定時は複数ファイルへ分割）

### 実装判断

1. **なぜ素直な形を採らなかったか**: 2点ある。(a) 分類軸の解決結果（`axes_resolved`）を素直にシェル変数のまま `validate-manifest.sh` へ引き継がず、いったん `AXES_RESOLVED_FILE` へ書き出してから `--axes` で明示的に渡している。理由は本体コメント（該当箇所、既存）に詳しい: `validate-manifest.sh` は自前でも軸宣言を解決できるが、その解決起点は渡されたmanifestのディレクトリになる。`$MANIFEST` を一時ファイル（`DETECTED_MANIFEST`）へ差し替えた後にそのまま渡すと、`validate-manifest.sh` 側だけ一時ディレクトリを起点に再解決してしまい、sibling の `unit-axes.json` 上書きを見失う二重基準が生まれる。`resolve_unit_axes` は明示ファイル指定時に再マージしない（冪等）ため、解決済みの結果を明示的に渡すことで二重基準を避けている。(b) `EMBED_MANIFEST` のmktemp+mvの2段（build-feature-list.shと同じ。基本設計書5.1節参照）。
2. **実測値**: (a) は実測値なし（論理的な二重基準の回避であり、環境や規模に依存する数値的な閾値は無い）。(b) はbuild-feature-list.shの節を参照。
3. **環境に依存するかどうか**: (a) は環境に依存しない。サンドボックスやOSの違いではなく、`validate-manifest.sh` 側が独自に軸解決を行う設計そのものから生じる論理的な整合性の問題であり、常に成立しうる。**「今回は結果が一致したから」という理由で `--axes` の明示渡しを省略するな。**(b) はbuild-feature-list.shの節と同じ。
4. **過去に消えて再発した経緯**: (a) は明確な再発記録なし。既に本体コメントとして詳細に記載済みであり、本作業での追記は行っていない。(b) はbuild-feature-list.shの節と同じコミット（`93eb2d6793dd30f0ae8320b372c823177c8f301c`）。

## validate-manifest.sh

### 実装契約

- 引数: `<manifest.json> [--unit-kind <kind>] [--axes <file>] [--migrations-dir <dir>]`、または `--self-test`
- 環境変数: `TMPDIR`
- 出力: 標準エラーへ項目ごとの `[PASS]`/`[FAIL]` 診断行
- 終了コード: 1件でも `[FAIL]` があれば `exit 1`。全項目PASSで `exit 0`
- 副作用: `unit_kind=table` かつ `--migrations-dir` 指定時のみ `_recompute_out_base`/`recompute_out`（`extract-table-metadata.sh`の再計算結果を書く一時JSON）を作り、使用後に`rm -f`する。`--self-test`実行時は`mktemp -d`の自己テスト用一時ディレクトリを作る

### 実装判断

1. **なぜ素直な形を採らなかったか**: 2点ある。(a) `table-メタデータ-履歴突き合わせ`検査で、`extract-table-metadata.sh`の再計算結果を書く`recompute_out`を、`.json`拡張子直付けの1回mktempではなく、mktemp+mvの2段で作る（build-feature-list.shと同じ理由。基本設計書5.1節参照）。(b) `--self-test`の冒頭で、`mktemp -d`が返した`$tmp`をそのまま使わず`cd "$tmp" && pwd`で再取得している。本体コメント（該当箇所、既存）に理由が詳しい: macOSの既定`TMPDIR`（`/var/folders/.../T/`）は末尾スラッシュ付きの場合があり、`mktemp`の返り値にこれが混入すると二重スラッシュを含むパスになる。本体側（`validate-manifest.sh`本体、または呼び出し元）はパスの解決時に`cd && pwd`で組み立てており、`cd`が二重スラッシュを暗黙に正規化するため、自己テスト側が生値の`$tmp`を使うと文字列としては一致しない（実体は同じディレクトリを指すが、比較に使うと不一致になる）。生成直後に同じ正規化を通すことで、以降の比較・フィクスチャ生成が本体側と同じ正規化済みの値を使うよう揃えている。
2. **実測値**: (a) は実測値なし（build-feature-list.shと同じコミットによる対策）。(b) は実測値なし（macOSの`TMPDIR`既定値が末尾スラッシュ付きであることは本体コメントに既に明記済み）。
3. **環境に依存するかどうか**: (a) は依存する（build-feature-list.shの節と同じ）。(b) は依存する。macOS固有の`TMPDIR`既定値（末尾スラッシュ付き）に起因する問題であり、末尾スラッシュを付けない`TMPDIR`環境では顕在化しない。**「手元の`TMPDIR`に末尾スラッシュが無く問題が起きない」ことを理由に、この正規化を外すな。**
4. **過去に消えて再発した経緯**: (a) はbuild-feature-list.shの節と同じコミット（`93eb2d6793dd30f0ae8320b372c823177c8f301c`）。(b) は明確な再発記録なし。既に本体コメントとして詳細に記載済みであり、本作業での追記は行っていない（(a)の箇所にのみコメントを追記した）。

2. **実測値**: (a) 実測値なし（コミットの表題「日本語比較の誤判定」が誤判定の実例そのものであり、数値的な閾値等は無い）。(b) 実測値なし（extract群5.4節・extract-table-metadata.shの節と同種の引数長上限だが、本箇所自体での失敗実測は無い）。(c) 基本設計書5.5節に実測を記載した。本セッションで`TMPDIR=/tmp/claude-501`（書き込み可能なサンドボックス領域）を設定していても、裸`mktemp`はこれを無視してOS既定の`/var/folders/.../T/`を使い、`Operation not permitted`で失敗することを実際に確認した。同じ理由で`detect-screens.sh --self-test`自体が、引数解析より前（該当箇所）で即座に失敗し、どの検査にも到達できないことも確認した。
3. **環境に依存するかどうか**: (a) は環境（ロケール設定）に依存する。日本語を含まない対象リポジトリや、既定ロケールが元々`C`/`POSIX`系の環境では顕在化しない。**手元の環境で誤判定が再現しないことを理由に`LC_ALL=C`を外すな。**(b) は環境（引数長上限）に依存する（extract群5.4節と同じ）。(c) は環境（書き込み許可のあるディレクトリ範囲）に依存する。サンドボックス実行環境等、OS既定の一時領域が書き込み不可な環境でのみ失敗する。

### 不具合修正: 検出失敗時の未定義変数参照（2026-08-17）

- **症状**: 画面を1件も検出できず`DETECTION_FAILED`（該当箇所の意図どおり`exit 3`でハード停止する経路）に入ると、その直後にEXITトラップが走り、`STRATEGY_SHARED_FILE`/`STRATEGY_ALIAS_FILE`/`STRATEGY_ALL_ENTRIES_FILE`という3変数を参照して`set -u`（該当箇所）により`unbound variable`で異常終了していた。サンドボックスの外でも再現するため環境要因ではない。
- **原因**: EXITトラップは該当箇所で早期に登録されるが、参照している3変数は9-2節の通常検出フロー（該当箇所、`allow_method`等による検出成功後にのみ到達する）でしか`mktemp`代入されない。検出0件で該当箇所のハード停止（該当箇所）に落ちる経路はこの代入より手前で`exit 3`するため、トラップ発火時点で3変数は未定義のままだった。
- **対処**: 該当箇所のトラップ内の該当3変数の参照を`"${VAR:-}"`形式に変え、未定義でも空文字として扱われるようにした（`rm -f ""`は無害であることを実機確認済み）。検出成功後に3変数が実際に`mktemp`で埋まっている経路では従来どおり実ファイルが削除される。ハード停止時の終了コード（`exit 3`）・検出ロジック自体には一切手を入れていない。
- **確認**: (1) 画面を持たないディレクトリに対する実行で`unbound variable`が消え、`exit 3`が保たれることを確認した。(2) 画面を持つfixture（`generation-engine/samples/project-portal/lists/screens/fixtures`、Pages Router形式）で14画面を`fallback-directory`方式で検出できることを確認した（既存の検出結果に影響なし）。(3) `--self-test`は63 PASS・0 FAILのまま。

## rebuild-screen-derived-pages.sh

### 実装契約

- 引数: `--raw-manifest <path> --target-repo <path> --api-manifest <path> --output-root <path> (--generated-at <iso8601> | SOURCE_DATE_EPOCH=<epoch>) [--table-manifest <path>] [--feature-manifest <path>] [--roles <csv>] [--design-docs-dir <path>] [--doc-view-dir <path>] [--catalog <path>] [--project-name <name>] [--sites <file>] [--site-key <key>]`、または `--self-test`
- 環境変数: `SCREEN_REBUILD_KEEP_TMP`（異常終了時に一時領域を残しデバッグを可能にする）・`SCREEN_REBUILD_INJECT_FAIL`（自己テスト用の障害注入）
- 出力: `$output_root`配下の13派生成果物（画面一覧・詳細ページ・マトリクス4種・ポータル等）を一括更新
- 終了コード: 引数不足・入力不在・生成連鎖の途中失敗・整合性チェック失敗で`exit 1`（`SCREEN_REBUILD_INJECT_FAIL`指定時は注入した専用コード）。正常終了は`exit 0`
- 副作用: `transaction_root`・`backup_root`（`$output_root`と同じ親ディレクトリへ作る一時ディレクトリ）を作り、生成連鎖の全段を`transaction_root`配下で完成させてから`$output_root`へ`mv`でコミットする。失敗時は`rollback()`が`backup_root`の退避内容から復元する

### 実装判断

1. **なぜ素直な形を採らなかったか**: `transaction_root`・`backup_root`を素直な形（`${TMPDIR:-/tmp}`配下）ではなく、`$output_root`の親ディレクトリ（sibling）へ作っている。コミット段（`commit_started=1`以降）で`transaction_root`配下の各ファイルを`$output_root`配下へ`mv`するが、`mv`は同一ファイルシステム上であれば原子的なrenameになる一方、別ファイルシステムをまたぐとcopy+deleteへ縮退し、途中で中断した場合に一部だけ移動済みという非原子的な状態を許してしまう。`${TMPDIR:-/tmp}`は`$output_root`と別ファイルシステムになりうる（例: `/tmp`がtmpfs、出力先が永続ボリューム）ため、siblingにすることで同一ファイルシステム上のrenameを保証し、トランザクションの原子性（本体冒頭コメント「sibling transaction」）を成り立たせている。加えて、コミット前後で`snapshot_unmanaged()`により管理対象外ファイルのハッシュを取得し`cmp`で突合する一見冗長な二重チェック（該当箇所）も持つ。これは、生成連鎖の途中で呼ばれる`build-portal.sh`等の後段処理が、管理対象（`managed[]`）以外の既存出力を意図せず変更していないかを検出するための安全装置である。
2. **実測値**: 実測値なし（`mv`のファイルシステムをまたぐ場合の非原子化は一般に知られた挙動であり、この環境での再現実験は行っていない）。
3. **環境に依存するかどうか**: 依存する。`${TMPDIR:-/tmp}`と`$output_root`が同一ファイルシステムかどうかは実行環境（マウント構成）に依存する。**手元の環境で`${TMPDIR:-/tmp}`と`$output_root`がたまたま同一ファイルシステムにあり問題が起きないことを理由に、sibling配置をやめてTMPDIR配下へ戻すな。**
4. **過去に消えて再発した経緯**: 記録なし。本体コメント「sibling transaction」（該当箇所）はこの設計を短く示していたが、`mv`の原子性という具体的な理由は本作業で追記した（追記前は「sibling」という結論のみで理由の記載が無かった）。

## restore-screen-manifest.sh

### 実装契約

- 引数: `<screen-list.html> <manifest-out.json> [--repo-root <path>]`、または `--self-test`
- 環境変数: `TMPDIR`
- 出力: `<manifest-out.json>`（HTMLへ埋め込まれた`application/json`ブロックから復元したscreen-manifest）
- 終了コード: 埋め込みブロック不在・JSON不正・スキーマ検証失敗で`exit 1`。正常終了は`exit 0`（復元先パスを標準出力へ）
- 副作用: `tmp_out`（`$MANIFEST_OUT`と同じディレクトリへ作る一時ファイル、`trap`で削除）を作り、検証成功後に`$MANIFEST_OUT`へ`mv`する。`--repo-root`指定時は`tmp_out_repo_root`も同様に作る

### 実装判断

1. **なぜ素直な形を採らなかったか**: `tmp_out`を素直な形（`${TMPDIR:-/tmp}`配下）ではなく、`$MANIFEST_OUT`と同じディレクトリへ作っている。本体冒頭コメント（該当箇所、既存）に「Restore its embedded application/json block into the canonical manifest path atomically」とあるとおり、該当箇所で`tmp_out`から`$MANIFEST_OUT`へ`mv`することで、検証済みJSONへの原子的な置き換えを行う設計である。`rebuild-screen-derived-pages.sh`と同じ理由（基本設計書5.2節）で、`${TMPDIR:-/tmp}`が`$MANIFEST_OUT`と別ファイルシステムだと`mv`がcopy+deleteへ縮退し、原子性が崩れるため、同一ディレクトリへ作ることで同一ファイルシステム上のrenameを保証している。
2. **実測値**: 実測値なし（`rebuild-screen-derived-pages.sh`と同じく、この環境での再現実験は行っていない）。
3. **環境に依存するかどうか**: 依存する。`${TMPDIR:-/tmp}`と`$MANIFEST_OUT`の配置先が同一ファイルシステムかどうかは実行環境に依存する。**手元の環境で問題が起きないことを理由に、`${TMPDIR:-/tmp}`配下への作成へ戻すな。**
4. **過去に消えて再発した経緯**: 記録なし。本体冒頭コメントは「atomically」という結論のみを示しており、`mv`の同一ファイルシステム制約という具体的な理由は本作業で追記した（追記前は理由の記載が無かった）。
