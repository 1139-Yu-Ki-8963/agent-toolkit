# generation-engine/scripts/extract 群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は `extract/` 1 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する最初の1群分である。

対象は `generation-engine/scripts/extract/` 配下の `.sh` 17 本（実測。`find generation-engine/scripts/extract -name '*.sh' | wc -l`）。

## 2. この群が何をするか

原本コード（対象リポジトリのソース）または設計文書（Markdown）を読み取り、`unit-list/` 群が扱う各種マニフェスト（画面・API・テーブル・バッチ・帳票・外部連携・機能）へメタデータを追加する「拡張マニフェスト」を作る。加えて、マトリクス（権限・CRUD・トレーサビリティ）や確認事項質問票のデータ導出、デザインシステム系のページデータ（トークン・コンポーネント棚卸し・アイコンカタログ）の抽出も担う。

大きく4系統に分かれる。

| 系統 | スクリプト | 入力 | 出力 |
|---|---|---|---|
| 種別別メタデータ抽出（原本コード読み取り） | `extract-api-metadata.sh`・`extract-table-metadata.sh`・`extract-batch-metadata.sh`・`extract-report-metadata.sh`・`extract-external-metadata.sh`・`extract-feature-metadata.sh`・`extract-screen-metadata.sh` | 種別マニフェスト（入力） + 原本ソースディレクトリ（`extract-table-metadata.sh` はマイグレーションSQLディレクトリ） | 拡張マニフェスト（既存フィールドは変更せず、検出できたフィールドのみ追加。検出根拠が弱い値は出力しない fail-safe） |
| マトリクス・確認事項の導出（マニフェストのみ読み取り、ソースコードは読まない） | `build-matrix-data.sh`・`build-permission-function-data.sh`・`build-confirmation-survey-data.sh` | 拡張済みマニフェスト群 | `permission-matrix.json`・`crud-matrix.json`・`traceability.json`・`confirmation-survey.json` |
| デザインシステム系抽出（ソースディレクトリまたは `DESIGN.md` を読み取り） | `extract-design-tokens-from-designmd.sh`・`extract-component-inventory.sh`・`extract-icon-usage.sh` | `DESIGN.md` またはソースディレクトリ | デザイントークン・コンポーネント棚卸し・アイコンカタログの各 page-data JSON |
| テスト・メッセージ系の変換・集約 | `convert-message-doc-to-manifest.sh`・`aggregate-test-viewpoints.sh`・`aggregate-test-cases.sh` | メッセージ定義書・テスト観点表・テスト仕様書（いずれも Markdown） | メッセージ manifest・テスト観点 manifest・テストケース manifest |
| AI設定資産抽出 | `extract-ai-assets.sh` | リポジトリ root（rules/skills/subagents/hooks） | AI設定資産ページ用 JSON |

## 3. 群内スクリプトの呼び出し関係

`extract/` 内のスクリプト同士が互いを `bash` 経由で直接呼び出すことはない（実測: `grep -rn` で群内相互呼び出しは0件）。全スクリプトは独立して呼べる CLI であり、呼び出し順序は群の外側（`generation-engine/scripts/verification/run-layer-full-pipeline.sh`・`generation-engine/scripts/unit-list/rebuild-screen-derived-pages.sh` 等のオーケストレータ）が決める。

`run-layer-full-pipeline.sh` が定める実行順序（実測。同スクリプトの stage 定義から）:

1. 種別別抽出（`extract-api-metadata.sh`・`extract-table-metadata.sh`・`extract-batch-metadata.sh`・`extract-report-metadata.sh`・`extract-external-metadata.sh`・`extract-feature-metadata.sh`）が各種別の拡張マニフェストを作る
2. `build-matrix-data.sh`（画面・API・テーブル・機能の拡張マニフェストを読む）→ `build-permission-function-data.sh`（`build-matrix-data.sh` が出した `permission-matrix.json` を変換する）
3. デザイン系（`extract-design-tokens-from-designmd.sh`・`extract-component-inventory.sh`・`extract-icon-usage.sh`）は他のどの抽出結果にも依存せず独立に動く
4. `extract-screen-metadata.sh`（`--api-manifest` を渡すと `extract-api-metadata.sh` の出力を読んで `relatedApis` を解決する。任意依存）→ `convert-message-doc-to-manifest.sh` → `aggregate-test-viewpoints.sh` → `aggregate-test-cases.sh` → `build-confirmation-survey-data.sh`（マトリクス出力・画面拡張マニフェスト・要確認事項群を横断集約する最終段）

## 4. 他の群との依存関係

- `../detect-encoding.sh`（`generation-engine/scripts/` ルート直下、この群の外）を `extract-ai-assets.sh` を除く全スクリプトが `source` する。非UTF-8原本の走査を安全に行うための共通ヘルパーであり、`to_utf8_for_scan` 関数を提供する（改善課題1-131）
- `unit-list/` 群が発行する種別マニフェスト（`screen-manifest.json` 等）を入力として受け取る（この群は manifest の「作成」ではなく「拡張」を担う）
- `matrix/build-matrix-pages.sh`・`skill-guide/` 等、この群より後段の群がこの群の出力（拡張マニフェスト・マトリクスJSON）を入力として消費する
- `verification/run-layer-full-pipeline.sh` がこの群のスクリプトすべてを正しい順序で呼ぶオーケストレータである

## 5. 共通する実装上の判断（群全体に共通する背景）

個別スクリプトの詳細設計（`詳細設計書.md`）に書く「実装判断」のうち、複数スクリプトへ横断的に現れる背景を先にここへまとめる。個々のスクリプトの節では重複記載を避け、この節への参照に留める。

### 5.1 明示テンプレート付き `mktemp -d` の使用（裸の `mktemp -d` を避ける）

この群のスクリプトは一時ディレクトリを `mktemp -d "${TMPDIR:-/tmp}/<script>-work.XXXXXX"` の形で作る。引数を省略した裸の `mktemp -d` は `$TMPDIR` を無視し、書き込み許可の外にある既定の一時領域を使うため、サンドボックス実行環境（Claude Code のサンドボックスファイルシステム制限等）では失敗する（改善課題「一時ディレクトリ-作成先」。`docs/ledgers/検証で見つかった改修課題.md` 該当箇所に記録済み、状態は「完了」）。

同種の問題は、このリポジトリの別ファイル（`generation-engine/scripts/check-derived-drift.sh`）で実際に発生し修正された実績がある（コミット `803d84cdaad314cf21f8b1dadb9e2119524e0d15`「台帳の道具が一時領域を作れず止まる」。コミットメッセージ: 「引数なしのmktempはTMPDIRを無視し、書き込みを拒まれる場所を使う」）。関連する同種修正として `ce95fbb72d3e0ec26da42bb36ad761586f308d13`（ガイドのパス検査）もある。ただし `extract/` 配下のファイル自身がこの形で退行した記録は見当たらない（3本の自己テストが予防的にこの退行を検知する。5.2節参照）。

この判断は環境（サンドボックス実行環境かどうか）に依存する。**手元の許可された開発環境（サンドボックスなし）で裸の `mktemp -d` に書き換えても動いて見えることがあるが、それを理由に明示テンプレートを外すな。**

### 5.2 「裸の mktemp -d に戻っていないか」を検証する自己テスト

`extract-component-inventory.sh`・`extract-design-tokens-from-designmd.sh`・`extract-icon-usage.sh` の3本は、`mktemp` をシム（差し替え関数）で記録し、`TMP_DIR` 生成が明示テンプレートを使っていることを構造的に検証する自己テストを持つ（5.1節の退行を機械的に検知する）。他の抽出スクリプトも同じ明示テンプレートの形は使うが、この自己テストは3本にしか無い（実測）。

### 5.3 非UTF-8原本に対するバイト単位走査（`LC_ALL=C`）

`../detect-encoding.sh` の `to_utf8_for_scan` はエンコーディング判定が `UTF-8`/`UNKNOWN`/空のいずれかであれば変換をスキップし、変換対象と判定してもPython変換自体が失敗すれば原本へフォールバックする（同関数の実装、該当箇所）。つまり `scan_design_md`・`scan_file` 等の「走査用に変換したはず」の変数は、非UTF-8の原本のままである場合が構造的に残る。この残存ケースで `awk`/`grep`/`tr` がUTF-8ロケール下だと「不正なマルチバイト列」の警告を出したり、走査結果が乱れたりすることを避けるため、`LC_ALL=C` を明示してバイト単位の走査に固定する。この対策は `extract-api-metadata.sh`・`extract-design-tokens-from-designmd.sh`・`extract-external-metadata.sh`・`extract-report-metadata.sh`・`extract-component-inventory.sh` に存在する（実測）。改善課題1-131が背景。

### 5.4 `jq --argjson` の直接展開を避けファイル経由（`--slurpfile`）で渡す

列・値の一覧をコマンドライン引数へ直接展開すると、件数の多い対象で `jq: Argument list too long` になりうる。上限はOSに依存し、Linuxには存在するがmacOSには無いため、開発機（macOS）では再現しないまま本番相当の環境（列数の多いテーブルを持つ対象リポジトリ、または引数長上限の低い実行環境）でのみ発現しうる。この対策は `extract-table-metadata.sh`（実際に一度退行し再発した。詳細設計書の該当節参照）と `build-matrix-data.sh` に存在する。

**手元の環境で `jq: Argument list too long` が再現しないことを理由に、一時ファイル経由の受け渡しをシェル変数への直接代入へ戻すな。**

## 7. 詳細設計を個別に持たないスクリプト（第3優先: 素直でない実装なし）

以下10本は、実際にコードを読んだ結果、一時ファイル・`mktemp`・`--slurpfile` の使用が単位ごとのパッチ蓄積という素直な構造（1件ずつ `.jsonl` へ追記し、最後に `jq --slurpfile` で1回だけマージする）にとどまり、2.1節が挙げる「素直でない実装」（一時ファイルを経由すること自体に議論の余地がある・環境変数受け渡し・ロケール明示・特定コマンドの回避・冗長な二重チェック）には該当しないと判断した。理由は各スクリプトの節を参照。

- `aggregate-test-cases.sh`
- `aggregate-test-viewpoints.sh`
- `build-confirmation-survey-data.sh`
- `build-permission-function-data.sh`
- `convert-message-doc-to-manifest.sh`
- `extract-ai-assets.sh`
- `extract-batch-metadata.sh`
- `extract-external-metadata.sh`
- `extract-feature-metadata.sh`
- `extract-report-metadata.sh`

`extract-external-metadata.sh`・`extract-report-metadata.sh` は5.3節の `LC_ALL=C` 対策を持つが、対策箇所に既に理由コメントがあり新たな加筆を要しなかったため、個別の詳細設計は持たず本書5.3節の共通事項として扱う。
