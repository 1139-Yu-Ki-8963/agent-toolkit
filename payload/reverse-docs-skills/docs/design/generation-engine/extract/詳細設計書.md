## document-paths.sh

### 実装契約

- 呼び出し方：sourceして `document_paths_add_existing <input-json> <actual-file> <link-value> <field>...` を呼ぶ。
- 出力：`actual-file` が通常ファイルとして実在し、`link-value` が空でなく、フィールドが1件以上渡された場合だけ、入力JSONの各指定フィールドへ同じリンク値を設定する。条件を満たさない場合は入力JSONをそのまま返す。
- `fields`（可変長のフィールド一覧）はJSON配列として構築する。入力JSONとともに標準入力のJSONストリームで `jq -s` へ渡す。`jq` は先頭値を入力オブジェクト、2番目の値をフィールド配列として扱い、配列をreduceして返す。

### 実装判断（改善課題1-249: fieldsの標準入力経由化）

1. 素直な形を採らなかった理由
   資料パス用フィールドの名前は、文書宣言に応じて増える可変長配列である。
   このため、`jq --argjson fields "$fields_json"`による直接渡しは採らない。
   入力JSONとfieldsを標準入力から`jq -s`へ渡し、配列をreduceする。
2. 実測値
   この`fields`自体で引数長超過を再現した実測値はない。
   一方、リポジトリには900列のテーブルで失敗した記録がある。
   `check-argjson-unbounded-value.sh`と`extract-table-metadata.sh`節に記録がある。
   記録された単一引数の実測上限は131,071バイトである。
3. 環境に依存するかどうか
   依存する。OSやプロセスの引数長上限は環境により異なる。
   `fields`が少ない対象では再現しない。
   **手元で再現しないことを理由に、直接`jq --argjson fields "$fields_json"`へ戻してはならない。**
4. 過去に消えて再発した経緯
   `check-argjson-unbounded-value.sh`は2026-08-23に許可リスト外使用を報告した。
   報告対象は`--argjson fields`である。
   本課題でこの値を可変長と判断し、この箇所では初めて標準入力経由へ書き換えた。
   過去の再発記録はない。

## finalize-extension-manifest.sh

### 実装契約

- 引数： `<base-manifest.json> <extended-manifest.json> [--unit-array units|screens] [--rules-file <json>] [--rule <name>|<searched-for>]`、または `--self-test`
- 環境変数： `TMPDIR`（自己テスト用一時ディレクトリの既定親。未設定時は `/tmp`）
- 出力： `<extended-manifest.json>`（対象側規則の追加フィールドと `detectionSummary.diagnostics.extensionExtraction` を反映した拡張マニフェスト）
- 終了コード： 全ユニットで追加項目を検出できない場合は `exit 2`、入力不正は `exit 1`、正常終了は `exit 0`
- 副作用： 出力先と同じディレクトリへ一時ファイルを作り、`jq` の出力完成後に対象ファイルへ `mv` する。
  異常終了時は `trap` で一時ファイルを削除する

### 実装判断

1. **なぜ素直な形を採らなかったか**： `jq` の出力を `<extended-manifest.json>` へ直接リダイレクトせず、出力先と同じディレクトリの一時ファイルへ完成させてから `mv` する。
   直接書き込む形では、`jq` が評価途中で失敗した場合に既存マニフェストを空または部分出力へ置き換えうる。
   確定したJSONだけを反映するため、一時ファイルをトランザクション境界として使う。
2. **実測値**： 実測値なし。
3. **環境に依存するかどうか**： 環境非依存。
   途中失敗時に既存出力を壊す危険はOSによらない。
   同一ディレクトリへ一時ファイルを置くことで、一時領域と出力先が別ファイルシステムになる構成を避ける。
   **手元の正常系で直接リダイレクトが成功することを理由に、一時ファイル経由を外すな。**
4. **過去に消えて再発した経緯**： 記録なし。
   コミット `a2c015e1` で本スクリプトが導入された時点から一時ファイル経由で処理していたが、その実装判断は本体コメントと本設計書のどちらにも記録されていなかった。

### 実装判断（追記: overrides の受け渡し）

1. **なぜ素直な形を採らなかったか**: `--rules-file` で読んだ `unitOverrides`（対象単位1件ごとに1要素を持つ配列）を `OVERRIDES_JSON` としてコマンドライン引数（`--argjson overrides`）へ直接渡さず、一時ファイル（`$overrides_tmp`）経由の `--slurpfile` で渡す。`unitOverrides` は対象側が単位ごとに宣言する可変長の値であり、件数に比例して伸びうる。同じ呼び出しの `--argjson rules "$RULES_JSON"` は変更していない。`RULES_JSON` は呼び出し側（`extract-*-metadata.sh` 各スクリプト）が `--rule` を固定個数（3〜5個）だけ渡す設計であり、伸びないため対象外とした。
2. **実測値**: 実測値なし（`unitOverrides` を大量に持つ実際のRULES_FILEでの失敗実測は無い。件数の伸び方が構造的に有界でないことを理由に対策した）。
3. **環境に依存するかどうか**: 依存する。`ARG_MAX` の上限はOSに依存し、`unitOverrides` が少数の対象リポジトリでは再現しない。**手元で少数の`unitOverrides`しか試さず問題が起きないことを理由に、`--slurpfile` 経由の受け渡しを外すな。**
4. **過去に消えて再発した経緯**: `check-argjson-unbounded-value.sh`（改善課題1-52）が許可リスト外の `--argjson overrides` として検出したため、2026-08-21に `--slurpfile` 経由へ書き換えた。導入時からの再発ではなく初回の対策である。

## extract-screen-metadata.sh

### 実装契約

- 引数: `<screen-manifest.json> <source-dir> <output.json> [--api-manifest <api-manifest.json>] [--design-docs-dir <dir>] [--link-base-dir <dir>] [--doc-view-dir <dir>] [--doc-view-link-base-dir <dir>] [--generated-at <iso8601>] [--manifest-content-hash <sha256>]`、または `--self-test`
- 環境変数: `TMPDIR`
- 出力: `<output.json>`（`screens[]` の各要素へヒューリスティックで抽出したフィールドを追加した拡張マニフェスト）
- 終了コード: 引数不足・入力ファイル不在等で `exit 1`。正常終了は `exit 0`
- 副作用: `SCAN_WORKDIR`・`TMP_WORK` の2つの一時ディレクトリを作り、`trap` で削除する

### 実装判断

1. **なぜ素直な形を採らなかったか**: `resolve_wrapper_api_paths` は、共通クライアント関数（パスを変数で受け取るラッパー）経由のAPI呼び出しを解決するために、検索文字列（対応表の各エントリ）ごとに `grep` を1回ずつ呼ぶ素直な形を避けている。素直な形だと画面数×対応表件数の回数だけ `grep` プロセスを fork する。代わりに検索文字列一覧を事前に1ファイルへ切り出し、`grep -f` で対象ファイル群を1回だけ走査してから、一致した文字列とパスの引き当てを `awk` の2ファイル入力（`NR==FNR` 照合）で行う。
2. **実測値**: 画面35件×対応表159件の対象アプリで、素直な形（検索文字列ごとの `grep` 起動）は実行時間が20秒→2分超に劣化した（本体コメント参照）。
3. **環境に依存するかどうか**: 部分的に依存する。フォーク回数削減自体は件数（画面数×対応表件数）に依存し、対象アプリの規模が小さければ体感できない。加えて、一致した検索文字列を `awk` へ渡す経路で、複数行文字列を `-v` で渡すとBSD awk（macOS標準）で `"newline in string"` エラーになるため、一時ファイル経由の2ファイル入力にしている（この部分はOS依存: macOS標準のBSD awkでのみ問題が顕在化する。GNU awkでは発生しない可能性があるが未検証）。**対象アプリの規模が小さく体感できないことを理由に、検索文字列ごとの `grep` 呼び出しへ戻すな。**
4. **過去に消えて再発した経緯**: 記録なし。この最適化とBSD awk回避の理由は本体コメント（該当箇所・該当箇所）に既に記載済みで、消えて再発した実績は見当たらない（`git log --follow` で本ファイルの独立した履歴は追えなかった。フォルダ移動を跨いだ完全な変遷は未確認）。

## extract-api-metadata.sh

### 実装契約

- 引数: `<api-manifest.json> <source-dir> <output.json> [--screen-manifest <json>] [--table-manifest <json>] [--survey-doc-path <md>]`、または `--self-test`
- 環境変数: `TMPDIR`
- 出力: `<output.json>`（`units[]` の各要素へ検出できたフィールドのみ追加した拡張マニフェスト。検出根拠が弱い値は出力しない fail-safe）
- 終了コード: 引数不足・入力ファイル不在等で `exit 1`。正常終了は `exit 0`
- 副作用: `SCAN_WORKDIR`（走査用一時ディレクトリ）、`patches_jsonl`・`patches_json`（パッチの一時ファイル）を作り削除する

### 実装判断

1. **なぜ素直な形を採らなかったか**: `route_receivers_from_source`・`route_method_from_source` の両関数が、ルートソースコードの空白除去に `LC_ALL=C tr -d '[:space:]'` を使う。素直な形（ロケール指定なしの `tr -d`）を避けている。`$src`（呼び出し元では `scan_file`）は `to_utf8_for_scan` の変換結果だが、同関数はエンコーディング判定が `UNKNOWN` の場合や変換失敗時には非UTF-8の原本へフォールバックする（`../detect-encoding.sh` 該当箇所の実装で確認）。フォールバック時にデフォルトロケール（UTF-8想定）で `tr` を実行すると「不正なマルチバイト列」の警告が出うるため、`LC_ALL=C` でバイト単位の走査に固定している。
2. **実測値**: 実測値なし。
3. **環境に依存するかどうか**: 依存する。対象リポジトリの原本ファイルが非UTF-8（Shift_JIS等）で、かつ `to_utf8_for_scan` の変換が失敗した場合にのみ問題が顕在化する。UTF-8のみのリポジトリで試す手元検証では再現しない。**手元の検証用リポジトリ（UTF-8のみ）で問題が起きないことを理由に `LC_ALL=C` を外すな。**
4. **過去に消えて再発した経緯**: 記録なし。今回の作業時点で該当箇所に理由コメントが無いことを発見し、本作業で追記した（改善課題1-131と同種の対策だが、この2箇所には後から追従漏れがあった可能性がある。他ファイル（`extract-external-metadata.sh`・`extract-report-metadata.sh`・`extract-component-inventory.sh`）には同種のコメントが既にあった）。

- 出力: `<output-dir>/permission-matrix.json`・`<output-dir>/crud-matrix.json`・`<output-dir>/traceability.json` の3ファイル
- 終了コード: 引数不足・必須マニフェスト不在・`--manifest-content-hash` の形式不正（64桁小文字16進以外）で `exit 1`
- 副作用: `STAGING_DIR`（`$OUTPUT_PARENT/.${OUTPUT_NAME}.matrix-staging.XXXXXX`）を作り、3ファイルを組み立てたのち `$OUTPUT_DIR` へ `mv` する。異常終了時は `trap`（`cleanup_matrix_transaction`）が未確定の出力を削除する

### 実装判断

1. **なぜ素直な形を採らなかったか**: 3点ある。(a) 各マニフェスト（screen/api/table/feature）をシェル変数へ代入せず、各 `jq` 呼び出しへ `--slurpfile` でファイルから直接読ませる。素直な形（マニフェスト全体をシェル変数へ代入し `--argjson` で渡す）は `ARG_MAX` 超過で失敗しうる。(b) 3つの出力ファイルを `$OUTPUT_DIR` へ直接ずつ書き出さず、隠しの `STAGING_DIR`（`$OUTPUT_DIR` と同じ親ディレクトリ配下）へ組み立ててから、全件完成後に一括で `mv` する。素直な形（`$OUTPUT_DIR` への直接書き出し）は、途中で失敗した場合に3ファイルのうち一部だけが更新された不整合な状態を残しうる。(c) CRUD判定材料が不正または不足のため除外したAPIのunitKey一覧（`skipped_api_keys_json`）を、コマンドライン引数（`--argjson skippedApiKeys`）へ直接渡さず、一時ファイル（`$SKIPPED_API_KEYS_FILE`）へ書き出してから `--slurpfile skippedApiKeys` で渡す。この一覧はAPI件数に比例して伸びる可変長の値であり、(a)と同じ`ARG_MAX`超過のリスクを持つ。
2. **実測値**: 実測値なし（(a)・(c)はいずれもextract-table-metadata.shと同種の問題であり、`build-matrix-data.sh` 自身での失敗実測は無い）。
3. **環境に依存するかどうか**: (a)・(c)は依存する。`ARG_MAX` の上限はOSに依存し、マニフェストが小さい対象リポジトリや、上限の高いOS（macOS）では再現しない。(b) は環境非依存（途中終了時の不整合という一般的なリスクへの対策であり、OS差は無い）。**(a)・(c)について、手元の小規模な検証用マニフェストで問題が起きないことを理由に、`--slurpfile` 経由の受け渡しを外すな。**
4. **過去に消えて再発した経緯**: (a) は明確な再発記録なし（extract-table-metadata.sh と同種の対策として、この作業で本体コメントへ「引数長の上限はOSに依存する」旨を補った）。(b) は再発記録なし。(c) は `check-argjson-unbounded-value.sh`（改善課題1-52）が許可リスト外の `--argjson` として検出したため、2026-08-21に `--slurpfile` 経由へ書き換えた。導入時からの再発ではなく初回の対策である。
