# generation-engine/scripts/glossary 群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は `glossary/` 1 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する。

対象は `generation-engine/scripts/glossary/` 配下のスクリプト3本（実測。`.sh` 2本 + `.py` 1本。`fixtures/` はテスト用データ、`.venv/`（`.gitignore` 対象）は実行環境、`requirements.txt` は依存宣言でありスクリプトではない）。

`README.md` は本群のうち `validate-semantic-glossary`（薄いshellラッパー + python本体の対）と `test-validate-semantic-glossary` について、既に「必要性・代替案不採用理由・保守責任者・廃棄条件」形式のADR（設計判断）を持つ。本文書はこれと重複させず、README.mdを正として参照しつつ、README.mdが扱っていない個別の実装判断（実装契約の詳細・「なぜその一行がそうなっているか」レベルの理由）を補う。

## 2. この群が何をするか

「用語集」（semantic glossary）のYAML文書（glossary/proposal/changeの3種別）を、contract v0.1.6 のスキーマ・整合規則に照らして検証する基盤である。この群自体は用語集の作成・編集は行わず、検証のみを担う。

| 系統 | スクリプト | 役割 |
|---|---|---|
| 検証エンジン本体 | `validate-semantic-glossary.py` | スキーマ検証・registry横断検証（重複key・循環参照・operation-key一意性・承認履歴・publication突合）を行い、診断reportを組み立てる |
| 呼び出し口（薄いラッパー） | `validate-semantic-glossary.sh` | python実行環境（venv/システム/`GLOSSARY_PYTHON`指定）を解決してpython本体を呼び、依存不足時に構築手順を追加提示する |
| 回帰テスト | `tests/test-validate-semantic-glossary.sh` | 3 kind・診断report・終了コード・実行障害の組み合わせを1つの決定的な入口で反復検証する |

## 3. 群内スクリプトの呼び出し関係

`validate-semantic-glossary.sh` が `validate-semantic-glossary.py` を呼ぶ（該当箇所、解決した`$PYTHON_BIN`経由）。`tests/test-validate-semantic-glossary.sh` は `validate-semantic-glossary.sh`（`$VALIDATOR`）を呼んで動作を検証する（自身が直接 `validate-semantic-glossary.py` を呼ぶ経路は `assert_report` 内の検証用python呼び出しのみで、対象スクリプトの呼び出しではない）。

## 4. 他の群との依存関係

- `detail-pages/project-semantic-glossary.py` の `run_validator()` がこの群の `validate-semantic-glossary.sh` を `subprocess.run` 経由で呼ぶ（この群の外からの唯一の消費者）。用語辞書ページへの投影は、この群が行う「承認済みであることの検証」を通過して初めて行われる（`detail-pages/`群の基本設計書4節参照）
- `detail-pages/regenerate-semantic-glossary-sample.sh`・`detail-pages/test-project-semantic-glossary-race.sh` は `glossary/fixtures/valid-glossary.yaml`・`glossary/fixtures/canonical-registry` を入力に使う（この群のフィクスチャへの依存）
- `../../schemas/semantic-glossary/1.0.0/`（`generation-engine/schemas/` 配下、この群の外）にある正本スキーマ（`validate-semantic-glossary.py` の `schema_dir()` が参照。加えて `tests/test-validate-semantic-glossary.sh` は同ディレクトリの `validation-report.schema.yaml` を参照する）

## 5. 共通する実装上の判断（群全体に共通する背景）

### 5.1 出力先ディレクトリ内での一時ファイル経由アトミック書き込み

`validate-semantic-glossary.py` の `write_report()`（該当箇所）は、最終出力（`--report`）と同じディレクトリ内に `tempfile.mkstemp()` で一時ファイルを作ってから `os.replace()` する。`detail-pages/`群の基本設計書5.2節と同じ理由（別ファイルシステム越しの `mv` はアトミック性を失う）であり、このリポジトリで繰り返し現れる標準的な安全策として扱う。個別スクリプトの節では新規の理由コメントを追加していない（既に自明なパターンであり、他ファイルとの重複記載を避けた）。

### 5.2 実行環境（Python版数・依存パッケージ版数）の厳密固定

この群のスクリプトは、実行に使うPythonの版数（3.13系のみ許可。範囲比較でなく完全一致）・依存パッケージの版数（PyYAML>=6,<7、jsonschema[format]>=4.23,<5）を、いずれも厳密に検査してから処理を始める。`glossary/.venv`（`requirements.txt`から構築する専用venv）という単一の実行環境に固定する設計であり（README.md「必要性」節）、`validate-semantic-glossary.sh`（`GLOSSARY_PYTHON`未指定時は`.venv`のpythonを優先し、無ければ`python3`へフォールバックする）・`validate-semantic-glossary.py`（`dependency_modules()`の厳密版数チェック）の両方がこの前提を守るための仕組みを持つ。

## 7. 詳細設計を個別に持たないスクリプト（第3優先: 素直でない実装なし）

`tests/test-validate-semantic-glossary.sh` は、実際にコードを読んだ結果、`set +e`/`set -e` で終了コードを捕捉してから比較する定型パターン（複数箇所に出現）が中心であり、これは「意図的に非0終了しうるコマンドの終了コードを`set -e`下で捕捉する」ための標準的で最も素直な手段である（他に単純な代替手段がない）。README.mdの「test-validate-semantic-glossary」節に既にADRがあり、本群固有の追加の「素直でない実装」は見当たらなかった。
