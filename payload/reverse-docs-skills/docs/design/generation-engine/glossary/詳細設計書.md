## validate-semantic-glossary.py

### 実装契約

- 引数: `--kind glossary|proposal|change --input <yaml> [--registry <path>] [--report <path>]`
- 環境変数: なし（本体はpython版数・依存パッケージ版数を自ら検査し、環境変数での切替は持たない）
- 出力: `--report` 指定時、診断report（`contractVersion`/`status`/`sourceKind`/`sourceRef`/`counts`/`findings[]`）をJSONでアトミックに書き出す。未指定時はファイル出力なし
- 終了コード: `run()` の戻り値をそのまま `main()` が返す。`--report` が `--input`／registry内のsource fileと同一実体を指す場合は `2`。依存不足・版数不一致は `SGD_DEPENDENCY` としてreportの `status="unavailable"` に反映されつつ `run()` の戻り値で非0を返す
- 副作用: `--report` 指定時のみ、出力先ディレクトリ内に一時ファイル（`tempfile.mkstemp(prefix=f".{path.name}.", dir=...)`）を作り `os.replace()` で確定させる。失敗時は一時ファイルを `unlink` する

### 実装判断

1. **なぜ素直な形を採らなかったか**: 2点ある。
   (a) `dependency_modules()`（115〜145行目）が、Pythonの版数を `sys.version_info[:2] != (3, 13)` という完全一致で検査する。素直な形（`>= (3, 10)` 等の範囲比較）を避けている。本ツールは `glossary/.venv`（`python3.13 -m venv` で構築する専用venv。README.md「必要性」節）という単一の実行環境に固定する設計であり、範囲比較にすると想定外のPythonマイナーバージョン（stdlibの挙動がマイナーバージョン間で変わりうる）でも通過してしまう。
   (b) `paths_refer_to_same_file()`（1622〜1629行目）が、`Path.resolve()` の一致比較と `os.path.samefile()`（`OSError`時は`False`）の両方を併用する。素直な形（`resolve()`の一致だけで同一ファイル判定する）を避けている。`resolve()`は絶対path化・symlink解決までは同一化するが、2つの異なるハードリンク（同じinodeを指す別々のディレクトリエントリ）はそれぞれ別のpathへ`resolve()`されるため一致しない。`samefile()`（`st_dev`/`st_ino`の比較）を併用しないと、ハードリンク経由で`--report`が`--input`やregistry内のsource fileと同じ実体を指すケースを見逃し、「入力とregistryのbyte列を変更しない」という保証（README.md「Operation keyと出力先の保護」節）が破れる。
2. **実測値**: 実測値なし（いずれも具体的な不一致・衝突の再現実験はこの作業では行っていない）。
3. **環境に依存するかどうか**: (a) は依存する。実行に使うPythonの版数構成そのものに依存する検査であり、他のPython版数の環境で実行すると意図的に拒否される。**手元でPython 3.13以外でも動作しそうに見えることを理由に範囲比較へ緩めるな。** (b) は環境に依存しない（ファイルシステムのハードリンク機構自体はOSに共通する概念だが、`resolve()`単独の弱点はハードリンクが実在するあらゆる環境で共通して起こりうる）。
4. **過去に消えて再発した経緯**: 記録なし。今回の作業時点で該当2箇所に理由コメントが無いことを発見し、本作業で追記した。

## validate-semantic-glossary.sh

### 実装契約

- 引数: `validate-semantic-glossary.py` にそのまま委譲する引数（`--kind`/`--input`/`--registry`/`--report`）、または `--self-test`
- 環境変数: `GLOSSARY_PYTHON`（python実行系の明示指定。未指定時は `glossary/.venv/bin/python`、それも無ければ `python3`）
- 出力: `validate-semantic-glossary.py` の標準出力・標準エラーをそのまま中継する。依存不足検知時（後述）はHINT行を標準エラーへ追加する
- 終了コード: `validate-semantic-glossary.py` の終了コードをそのまま返す（`exit "$status"`）
- 副作用: 標準エラー退避用の一時ファイル（`mktemp "${TMPDIR:-/tmp}/validate-semantic-glossary-stderr.XXXXXX"`）を作り、`trap` でEXIT時に削除する

### 実装判断

1. **なぜ素直な形を採らなかったか**: python本体の標準エラーを、素直な形（パイプで直接 `grep` へ渡して判定する）ではなくファイル（`$STDERR_FILE`）へいったん書き出してから使う（111〜133行目）。標準エラーは「呼び出し元へそのまま中継する」（`cat "$STDERR_FILE" >&2`）用途と「`SGD_DEPENDENCY`相当の失敗かどうかをHINT追加のために`grep`で判定する」用途の2箇所で必要であり、パイプは1回しか消費できないため、ファイルへ退避して2回読む必要がある。あわせて `set +e`/`set -e` で python呼び出し前後を挟み、`set -e` 環境下でも非0終了コードを捕捉してから続行できるようにしている。
2. **実測値**: 実測値なし。
3. **環境に依存するかどうか**: 依存しない。シェルのパイプ・リダイレクトの一般的な制約（1回しか消費できない）に基づく設計であり、OS・サンドボックスには依存しない。
4. **過去に消えて再発した経緯**: 記録なし。111〜113行目に「なぜHINTを追加するか」の既存コメントはあったが、「なぜファイルへ退避するか」の理由は無く、本作業で追記した。
