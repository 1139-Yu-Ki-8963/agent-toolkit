対象は `docs/tasks/自己設計書整備の指示書.md` 4.5節の手順で洗い出した第1優先（素直でない実装を持つ）1本。群全体の役割・呼び出し関係は `基本設計書.md` を参照する。ここでは実装契約と、なぜその実装を採ったかという実装判断を書く。

## build-manifests-from-docs.sh

### 実装契約

- 引数: `<output_dir> <出力先ディレクトリ> [--unit-kind <種別>]`、または `--self-test`
  - `<output_dir>`: 設計文書が展開済みのプロジェクトルート（`scaffold-design-unit.sh` の展開先と同じ意味）
  - `<出力先ディレクトリ>`: `<kind>-manifest.json` を書き出す先
  - `--unit-kind`: 省略時は宣言（`doc-extraction.json`）にある全種別（api/table/batch/report/external/feature）を処理する
- 環境変数: 明示的な参照なし（`TMPDIR` は `--self-test` の一時ディレクトリ生成でのみ使用）
- 出力: `<出力先ディレクトリ>/<kind>-manifest.json`（種別ごとに1ファイル）
- 終了コード: `jq` 不在・`output_dir` 不在・未知の `--unit-kind` 指定・`build_manifest_for_kind` 内の宣言欠落（`unitRootKey`/`docFileName` 無し）で `exit 1`。個々の種別で `validate-manifest.sh` の検証に失敗した場合、当該種別はエラーだが処理は継続し、最後に `overall_rc=1` で終了する（1種別の失敗が他種別の処理を止めない設計）。正常終了は `exit 0`
- 副作用: `mkdir -p "$dest_dir"`。設計文書が0件でも空のマニフェスト（`unitCount: 0`）を書き出す（フェイルセーフ。存在しないディレクトリを走査した場合は`find`をスキップし`units_json="[]"`のまま進む）

### 実装判断

1. **なぜ素直な形を採らなかったか**: `designDocPath`（一覧HTMLの行から個別の設計書ページへ遷移するための相対パス）の算出に、bash単体での文字列操作ではなく `python3 -c 'import os,sys; print(os.path.relpath(...))'` を使う（本体179〜187行目）。素直な形（bashの文字列操作だけで相対パスを組み立てる、または `command -v python3` の判定を省いて常にpython3を呼ぶ）を避けている。理由は2つある。(a) bash自体には相対パス計算の標準機能が無く、`unit_list_dir_abs`（一覧HTMLの置き場）と `design_doc_html`（設計書の変換後パス）という2つの絶対パスから相対パスを機械的に導く処理を、bashの文字列操作だけで階層の深さ違いを含めて正しく実装するのは非現実的である。(b) `command -v python3` の判定（一見冗長な二重チェックに見える）は、python3が対象環境に常に存在するとは限らないことへの備えである。判定を外して常にpython3を呼ぶ形にすると、python3不在の環境でこの関数全体が失敗しうる。
2. **実測値**: 実測値なし。python3が実際に不在の環境での失敗は、この作業では未実施（環境依存のため）。
3. **環境に依存するかどうか**: 依存する。python3の有無は、この生成器を実行する側の環境に依存する。**手元の開発機に常にpython3が入っていることを理由に、`command -v python3` の判定を外すな。**外すとpython3不在の環境でこの関数自体が失敗するか、または（エラー握り潰しの実装次第では）不正確な値を `designDocPath` へ書き込みかねない。現行実装はpython3不在時にフィールド自体を付けない（捏造しない）フェイルセーフを取っている。
4. **過去に消えて再発した経緯**: 記録なし。この機能はコミット `8869a0ddb721bf22087c9fc153eeef8394b436be`「設計書への遷移先を供給する」（改善課題1-36）で新設された時点から、現在と同じ `command -v python3` によるフェイルセーフ付きの形で実装されている。それ以前に別形（判定なしの直接呼び出し等）が存在して後から本形へ変わった、あるいは本形が一度失われて復帰した、という履歴は見当たらない（`git log --follow` で本ファイルの独立した履歴は5件）。

### 実装判断（改善課題1-67: unitKey・sourceFileの代替値埋めとkind不変条件）

改善課題1-67（マッピングで導けなかった必須項目が欠落し、`validate-manifest.sh` の必須フィールド検査で終了コード1になる）への対応で、`build_manifest_for_kind` に `unit_needs_unresolved_kind` というローカル変数を追加した（本体、マッピングループの直後）。この変数は追加した時点では**参照されない**（常に計算されるだけで、後続のkind決定には使わない）。

1. **なぜ素直な形を採らなかったか**: 素直な形は「フラグを計算する箇所と、実際に使う箇所を同じコミットで揃える」ことだが、今回は使う側（改善課題1-66: frontmatterからkindを解決する分岐）を別コミットで追加する計画のため、フラグだけを先に用意した。理由は、フラグが表す不変条件（`unitKey`・`sourceFile` を代替値で埋めた行は、kindを非unresolvedにしてはならない）を、1-66の実装より先に文書とコードの両方へ固定しておく必要があったため。代替値の `sourceFile`（例: `"未確認"`）は実在しないパス文字列であり、その行のkindを非unresolvedにすると `validate-manifest.sh` の `sourceFile-実在` 検査（`kind != "unresolved"` の行だけを検査する）に必ずひっかかり終了コード1で止まる。この依存関係を知らない次の編集者が「未使用変数」として `unit_needs_unresolved_kind` を削除すると、1-66の実装時にこの不変条件が再度失われる。
2. **実測値**: `--self-test` の検査7（本体）で、`unitKey`・`sourceFile` を欠いた合成データを与えたとき、代替値で埋まり `kind` が `unresolved` のまま `validate-manifest.sh` を通ることを実測済み。
3. **環境に依存するかどうか**: 依存しない。
4. **過去に消えて再発した経緯**: 記録なし（今回新設）。**次にこの変数を参照する実装（改善課題1-66）を書く際は、代替値で埋まった行のkindをunresolved以外にしないこと。** この節ごと削除するのは、`unit_needs_unresolved_kind` を実際に使う分岐が実装され、かつその分岐がこの不変条件を守っていることを確認してからにする。

### 実装判断（改善課題1-66: kind解決がsourceFile-実在検査を起こす連鎖。kindMappingを他種別へ広げる作業者は必読）

改善課題1-66でapiに `kindMapping`（`method`・`path` が揃えば `kind` を `"endpoint"` へ解決する宣言）を追加した直後、この変更自体は自身の `--self-test` を通過した。ところが、この変更をmainへ統合した**後**になって、`generation-engine/scripts/build-portal.sh` 側の既存 `--self-test`（ケース43。1-66とは無関係な、`--build-manifests-from-docs` の合成フィクスチャ検証）が壊れていることが、改善課題1-61（拡張マニフェスト生成）の作業中に判明した。

**壊れた理由（連鎖）**:

1. `kindMapping` により、`method`・`path` を両方持つAPI文書の `kind` が `"unresolved"` から `"endpoint"` へ解決されるようになった
2. `validate-manifest.sh` の `sourceFile-実在` 検査（`generation-engine/scripts/unit-list/validate-manifest.sh:261`付近）は `kind != "unresolved"` の行**だけ**を対象に、`sourceFile`（`source_ref` frontmatterの値）が実際にファイルとして存在するかを検査する。`kind == "unresolved"` の行はこの検査を通らず、常にPASSしていた
3. ケース43の合成フィクスチャは `source_ref: src/api/users.py` という、実在しないパスを指すAPI文書だった。1-66導入前は `kind` が常に `"unresolved"` だったため②の検査対象にならず問題が顕在化しなかったが、1-66導入後は `kind` が `"endpoint"` に解決され、②の検査対象になり、実在しないパスへの参照として `[FAIL]` になった
4. `build-manifests-from-docs.sh` は各種別の組み立て後に `validate-manifest.sh` を自分で呼ぶため、この `[FAIL]` は `build_manifest_for_kind` の非0終了として `build-manifests-from-docs.sh` 自身の終了コードへ伝播し、それを呼ぶ `build-portal.sh --build-manifests-from-docs` も `ERROR: --build-manifests-from-docs failed` で終了コード1になる

**この連鎖はいつでも再発する**。`kindMapping` を新しい種別（table・batch・report・external）へ広げる場合、その種別の合成フィクスチャ・実データが実在しない`sourceFile`を参照していれば、同じ理由で `sourceFile-実在` 検査が新たに有効になり、そこで初めて壊れる。1-66単体の `--self-test`（`build-manifests-from-docs.sh` 自身の自己テスト）は自分のフィクスチャにダミー実体を用意していたため気づけず、**別ファイル（`build-portal.sh`）が持つ既存の自己テストのフィクスチャまでは見ていなかった**ことが、mainへ統合された状態で発覚が遅れた直接の原因である。`kindMapping` を追加するときは、`build-manifests-from-docs.sh` 自身の `--self-test` だけでなく、**`build-portal.sh --self-test` 全件（特にケース43・46のような `--build-manifests-from-docs` を経由する既存ケース）も実行して確認すること。**

**対応**: `build-portal.sh` のケース43・46の合成フィクスチャへ、`source_ref` が指す位置にダミーの実体ファイルを用意した（`generation-engine/scripts/build-portal.sh` の該当箇所にコメントで理由を記載済み）。

### 実装判断（改善課題1-61: `set -euo pipefail` 下でのパイプ経由の抽出呼び出し）

`build-portal.sh` は冒頭で `set -euo pipefail` を宣言している。改善課題1-61で `--build-manifests-from-docs` 実行時に `extract-<種別>-metadata.sh` を呼ぶループを追加した際、出力にプレフィックスを付けるため `bash "$ext_script" ... | sed "s/^/INFO: .../" >&2` という形でパイプを組んだ。

1. **なぜ素直な形を採らなかったか**: 素直に `bash "$ext_script" ... | sed ...` とだけ書くと、`pipefail` の下では抽出スクリプト（パイプの左側）が非0で終了した場合、パイプ全体の終了コードがその非0値になる（`sed` が右側で常に0で終わっても関係ない）。ガードを付けずにこの非0終了を放置すると、`set -e` により `build-portal.sh` 全体が、抽出失敗の内容を示すエラーメッセージを一切出さないまま即座に停止する。抽出処理は原本コードへのヒューリスティックな静的解析であり、検出できないことは異常ではない（各 `extract-*.sh` のヘッダコメント参照）。そのため個々の種別の抽出失敗でビルド全体を止めてはならないという設計意図（コード内コメントに明記済み）と、素直な書き方の実際の挙動が矛盾していた
2. **実測値**: この矛盾は実際に踏んだ。ケース43の合成フィクスチャ検証時、抽出呼び出しではなく `build-manifests-from-docs.sh` 自身の `validate-manifest.sh` 呼び出し（上記1-66の連鎖）が非0で終了し、`build-portal.sh --self-test` の実行が該当ケースの出力の途中で説明なく停止する形で顕在化を確認した
3. **環境に依存するかどうか**: 依存しない。`set -euo pipefail` はシェルの標準機能であり、bashのバージョン等に依存しない
4. **過去に消えて再発した経緯**: 記録なし（今回新設）。`bash "$ext_script" ... | sed ... || ext_rc=$?` の形で終了コードを明示的に捕捉するガードを外すと、この問題が再発する。ガードを外す・簡略化する変更を行う前に、必ずこの節を読むこと

### 補足: 群全体で共通する `--argjson` の扱い（このスクリプト固有ではない一般的注意）

`build_manifest_for_kind` は種別1件分の全ユニットを蓄積した配列 `units_json` をそのまま `jq --argjson units "$units_json"` へ渡す（本体237行目）。これは `extract/extract-table-metadata.sh` が過去に一時ファイル経由（`--slurpfile`）への対策を入れてから回帰した箇所（`docs/design/generation-engine/extract/詳細設計書.md` 参照）と同種の潜在リスク（対象リポジトリの設計文書数が非常に多い場合の引数長超過）を理論上持つ。ただし、これは「素直でない実装」（今回の作業が対象とする、既にある回避策）ではなく、逆に「まだ回避策を入れていない素直な実装」である。`tests/check-argjson-unbounded-value.sh` の許可リストに現状レビュー済みとして登録されている（同checkerのヘッダコメントが明記するとおり、この登録は将来にわたる安全の証明ではない）。本作業はスクリプトの振る舞いを変えない指示のもとで行っているため、この作り替え（`--slurpfile`化）は本文書の対象に含めず、既知の潜在リスクとして記録するに留める。

### 実装判断（改善課題1-52: targetTablesの一時ファイル経由化）

1. **なぜ素直な形を採らなかったか**: API種別のunit組み立て中、`extract_api_target_tables`で設計書§7.1/7.2の表から抽出した対象テーブル一覧（`target_tables_json`）を、素直な形（`jq --argjson tables "$target_tables_json"`でコマンドライン引数へ直接展開する形）ではなく、一時ファイル（`$target_tables_file`）経由の`--slurpfile`で渡す。この一覧は対象文書の§7の表の行数に比例して伸びうる可変長の値であり、`extract-table-metadata.sh`のmainColumnsと同種の`ARG_MAX`超過リスクを持つ。
2. **実測値**: 実測値なし（大量の対象テーブルを持つ実際のAPI設計書での失敗実測は無い）。
3. **環境に依存するかどうか**: 依存する。`ARG_MAX`の上限はOSに依存し、対象テーブル数が少ないAPIでは再現しない。**手元で対象テーブル数の少ないAPIしか試さず問題が起きないことを理由に、`--slurpfile`経由の受け渡しを外すな。**
4. **過去に消えて再発した経緯**: `check-argjson-unbounded-value.sh`（改善課題1-52）が許可リスト外の`--argjson tables`として検出したため、2026-08-21に`--slurpfile`経由へ書き換えた。導入時からの再発ではなく初回の対策である。

### 実装判断（改善課題1-249: unitの標準入力経由化）

1. 素直な形を採らなかった理由
   集約文書から作る`unit_obj`は、unit fieldsとdocument Path fieldsの増加に伴い伸びる。
   このため、`jq --argjson unit "$unit_obj"`による直接渡しは採らない。
   `enriched`と`unit_obj`を標準入力から`jq -s`へ渡す。
   `.[0] + [.[1]]`で従来どおり末尾へ追加し、OSやプロセスの引数長上限を避ける。
2. 実測値
   このunit自体で引数長超過を再現した実測値はない。
   一方、リポジトリには900列のテーブルで失敗した記録がある。
   checkerと`extract-table-metadata.sh`節には、単一引数の実測上限131,071バイトが記録されている。
3. 環境に依存するかどうか
   依存する。OSやプロセスの引数長上限は環境により異なる。
   unit fieldsやdocument Path fieldsが少ない対象では再現しない。
   **手元で再現しないことを理由に、直接`jq --argjson unit "$unit_obj"`へ戻してはならない。**
4. 過去に消えて再発した経緯
   checkerは2026-08-23に許可リスト外の`--argjson unit`使用を報告した。
   本課題でこの値を可変長と判断し、この箇所では初めて標準入力経由へ書き換えた。
   過去の再発記録はない。

## extract-entity-state-page-data.sh

対象: `docs/tasks/関連図の内製化の指示書.md` 5節「段階1: 状態遷移図」。改善課題1-26の残件（関連図の入力データを設計文書から組み立てる経路が無い）のうち、状態遷移図（`entity-state`）1本を対象にした実装。

### 実装契約

- 引数: `<output_dir> <出力page-data.jsonのパス>`、または `--self-test`
  - `<output_dir>`: データ設計.md が展開済みのプロジェクトルート（`output-layout.json` の `dataDesignDoc` を `<output_dir>` からの相対で解決する）
  - `<出力page-data.jsonのパス>`: 組み立てた `page-data.json` を書き出すファイルパス
- 環境変数: 明示的な参照なし（`TMPDIR` は `--self-test` の一時ディレクトリ生成でのみ使用）
- 出力: `<出力page-data.jsonのパス>` に `pageKind: "entity-state"` の page-data.json（`nodes[]`/`edges[]` を含む）
- 終了コード: `jq` 不在・`output_dir` 不在で `exit 1`。データ設計.md 不在・`§6 状態遷移表` 見出し不在・データ行0件（雛形のプレースホルダ行のみ）のいずれの場合も、`nodes`/`edges` が空の page-data.json を書き出し WARN を stderr へ出したうえで `exit 0` とする（`build-manifests-from-docs.sh` の0件時フェイルセーフと同じ設計。遷移を捏造しない）
- 副作用: `mkdir -p "$(dirname "$dest_file")"`

### 必要性

状態遷移図の生成（`build-detail-page.sh --page entity-state`）が要求する `page-data.json`（`nodes[]`/`edges[]`）は、これまで `generating-entity-state-for-reverse-docs` スキルの対話的な抽出（Claude自身がRead/Writeでデータ設計.md §6の表を読み、手作業でnodes/edgesへ変換する）にのみ依存しており、配布物の生成器（決定的スクリプト）だけでは再現できなかった（改善課題1-26）。段階1新設時点のデータ設計.md §6状態遷移表は「根拠パス」列を末尾に持つ6列構成であり、`build-manifests-from-docs.sh`・`build-portal.sh`・`doc-extraction.json` のいずれもこの列を読んでいないことをコード追跡で確認済みだった（後述「実測値」）。その後、改善課題1-234でテンプレートの§6状態遷移表から根拠パス列が削除され、現行は5列（エンティティ/状態/遷移前/契機/遷移後）のみである（改善課題1-240）。現行テンプレートに証跡パスを持つ列は存在しないため、`edges[].sourceRef` は値を持たない設計（常に空文字列）とした。表の各行を `nodes[]`/`edges[]` へ変換する処理（状態列→遷移前列→遷移後列の順で(エンティティ,状態)の組を初出順に集める、行を1 edgeへ変換する等）は、対話セッションのたびに手作業で再現するとトークンを浪費し、既存の生成済みサンプル（`generation-engine/samples/project-portal/図/状態遷移図.html`）が前提とする並び順（初出順）を毎回正しく再現できるとは限らない。決定的なスクリプトとして1本に固定し、`build-manifests-from-docs.sh`・`build-portal.sh`の生成パイプラインから繰り返し呼べる形にする必要がある。

### テンプレートへの列追加とcardinalityの値域

`テーブル定義書.md` §6.3 外部キーには元々「出典参照」「関連の種別」の列が無く、文書だけからは復元できなかった（指示書4.3節・4.4節）。段階2では次の2列を追加した。

- **出典参照**: 既存の作法（`データ設計.md` §6 の「根拠パス」列）に揃え、列名は「出典参照」とした（`page-data-schema.md` の `relations[].sourceRef` フィールド名に合わせた命名）。新しい形は発明していない
- **関連の種別（cardinality）**: 値域を「一対一・一対多・多対多」の3値とし、テンプレートの該当セルへ `<実測: 一対一 または 一対多 または 多対多>` の書式で明記した（既存の実測プレースホルダの書式は `UI共通設計.md` 等に前例があり、列挙は `|` ではなく「または」で区切る書式に揃えた。`|` はMarkdownの表の区切り文字と衝突するため）。「多対一」を独立した値として立てなかった理由: §6.3 の各行は「参照元テーブル（from・現在の文書自身）→参照先テーブル（to・参照先のテーブル列）」の向きで記録される。cardinalityは参照先（to・親）を基準にした「親1行に対し子が何行対応するか」を表す値として定義し、通常の外部キー（子の多くの行が親の1行を参照する）は「一対多」で過不足なく表現できる。「多対一」は同じ関係を子側から読んだ場合の別表記に過ぎず、独立の値を立てると同じ関係が2通りの文字列で書かれうる曖昧さを生む。「多対多」は本抽出器が§6.3の行を機械的に1関係へ変換するだけでは通常生じない（中間テーブル経由の関係を人が判断して記述する場合の値として温存する）

### 参照先テーブルの解決（table_key / table_name 両対応）

段階2着手時点で、§6.3「参照先のテーブル」セルに何を書く慣行か（`table_key`のような内部識別子か、`table_name`のような日本語表示名か）がこのリポジトリ内に確立していなかった（`build-manifests-from-docs.sh` の自己テストフィクスチャでは `table_key: users` / `table_name: ユーザー` と両者が異なる値を取りうることを確認済み）。本スクリプトは収集済み全テーブルの `table_key` と `table_name` の両方を解決対象にしたマップを組み立て、セルの値がどちらの慣行で書かれていても解決できるようにした。解決できない場合は `relations[]` へ加えず `unresolved[]` へ理由付きで記録する。これは `validate-page-data.sh` の孤児参照検査（`relations[].from`/`.to` が `entities[].key` に存在しない場合を FAIL とする。ただし `unresolved[]` 記載の参照は対象外）に適合させるための必須の設計であり、単なる丁寧さの上乗せではない。未解決のまま `relations[]` に生の文字列を混ぜて出力すると `build-detail-page.sh` が生成そのものを拒否する（同スクリプトはvalidate-page-data.shがPASSしない限り書き出さない）。

### 情報アクセス規律への抵触判断

`README.md`「情報アクセス規律の段階的縮小」原則は、extracting（原本コードを読む）→ authoring（封印済みfactsと共通文書のみを読む）→ rebuilding（設計書のみを読む盲検）という**工程間で各段階が読んでよい情報源**を規定するものであり、設計書自身が保持する値の種類を制限するものではない。今回追加した2列は次の理由で抵触しないと判断した。

- 「関連の種別」は設計文書自身が完結して持つ値（`一対一`/`一対多`/`多対多`のいずれか）であり、rebuilding段階がこの値を読むのに設計書の外（原本コード）を参照する必要が無い。ER図の生成はこの値をそのまま表示するだけで、追加の情報源を要求しない
- 「出典参照」は`データ設計.md`§6の「根拠パス」列と同じ性質の証跡ポインタであり、段階1で同種の列（根拠パスは元々存在した列だが、性質としては同じ「原本コードへのパス参照」）を読む経路を新設した際にも同じ懸念が生じうる箇所だったが、指示書はその段階を止めずに完了させている。出典参照は生成されたER図の中で人間が確認するための注記であり、rebuilding段階（設計書のみを読む盲検で再実装する工程）がこの値を消費してentities/relations自体を再構成するわけではない（entities/relationsの実体は列自体の値として設計書に書かれる）
- 過去の決定（`改善課題優先順位.md:139`）が懸念した「工程が進むほど参照できる情報を狭める規律を崩す」は、確信度（confidence）のような**判断の質**を表すメタ情報を新設することへの懸念が本質だったと読める。確信度は本段階では追加していない（指示書4.2節のとおりER図のスキーマはconfidenceを要求しない）

以上により、抵触しないと判断し作業を継続した。

### 必要性

画面遷移図の生成（`build-detail-page.sh --page transition`）が要求する`page-data.json`の`edges[]`は、これまで`generating-screen-transition-for-reverse-docs`スキルの対話的な抽出にのみ依存しており、配布物の生成器（決定的スクリプト）だけでは再現できなかった（改善課題1-26）。既存の生成済みサンプル（`generation-engine/samples/project-portal/図/画面遷移図.html`）は`edges: []`・`edgesStatus: "未抽出"`のまま配布されており、画面遷移図が矢印を1本も持たない状態が既定になっていた。画面基本設計書.md §6の業務文脈の表からnodes/edgesへ変換する処理（自画面注記のownKeyへの直接解決、名前解決マップによるfromName/toNameのunitKeyへの変換、解決できない行のunresolved[]への振り分け）は、対話セッションのたびに手作業で再現するとトークンを浪費し、`validate-page-data.sh`の孤児参照検査を確実に満たす保証もない。決定的なスクリプトとして1本に固定し、生成パイプラインから繰り返し呼べる形にする必要がある。

### 代替案を採用しなかった理由

- Bash ツール直叩き: 複数の画面基本設計書.mdを横断した§6データ行の抽出・自画面注記の解決・名前解決・unresolved振り分けを対話セッションのたびに手動で行うと、判定基準がぶれ、`validate-page-data.sh`の孤児参照検査で毎回失敗しうる
- 画面基本設計書.mdへの「出典参照」「確信度」列の追加: 指示書が当初想定していた形。実測で列を足さなくても矢印を作れることが分かった（本節「出典参照とconfidenceの形」）ため、テンプレートへの列追加という影響範囲の広い変更を回避した
- 既存 `extract-entity-state-page-data.sh`・`extract-er-page-data.sh` への機能統合: 前者は単一文書の単一セクションを読む設計、後者は複数ファイルを横断するが解決対象は参照先テーブルのみである。本スクリプトは複数の画面基本設計書.mdを横断しつつ、raw screen-manifest.jsonからのnodes/manifestContentHash復元という`entity-state`/`er`が持たない責務を追加で持つ。同居させると復元ロジックが異質な形で混入する
- `generating-screen-transition-for-reverse-docs` スキルへの機能追加・置き換え: あちらは対話モデルが判断を伴う抽出を行う設計であり、本スクリプトが決定的に代替するのは「§6の行→edgesへの機械的変換と解決」という無判断の部分のみ。スキル自体は単独起動できる独立した経路として残す（本作業ではスキルのSKILL.md自体を変更しない）
- 既存 Makefile ターゲット拡張・package.json scripts 追加: このリポジトリはどちらも持たない

### 試して捨てた方法

`run-layer-full-pipeline.sh` の `--input` フラグを「既に用意した疑似入力をそのまま使う」意味だと誤解し、1 回目の検証で全種別 unitCount=0 という誤った結果を出した。実際は `prepare-verification-input.sh` へ転送されるだけの引数であり、転送先は `--output` しか受け付けない。`--input` を付けず `--output` だけを渡せば、スクリプト自身が疑似入力の生成から一貫して行う。同じ検証をする人はこの誤解を踏まないこと。

### 触ると壊れる箇所

`validate-manifest.sh` の sourceFile 解決は、`.git` の祖先が見つからない場合に `manifest_dir`（マニフェスト自身の置き場所）へフォールバックする。`build-manifests-from-docs.sh` の自己テストのように `dest_dir`（マニフェストの置き場所）と `output_dir`（設計文書の置き場所）を別のディレクトリにする自己テストを書くと、sourceFile の解決の基準が `output_dir` ではなく `dest_dir` の側になる。検査 7 とケース 43・46 のフィクスチャは、いずれもこの前提で実体ファイルの置き場所を計算している。

### 中身が薄いことは欠陥ではない

`extract-<種別>-metadata.sh` 群はヒューリスティックな抽出であり、原本が実在しても検出の条件（`CREATE TABLE` 構文の一致等）に合わなければ黙って項目を付けない fail-safe の設計である。`.ext.json` の中身が本体とほぼ同じ（拡張のフィールドが空）でも、それ自体は欠陥ではなく「検出できなかった」ことを意味する。中身の充実度を機械で検査する仕組みは現状なく、存在の確認だけを行う。`kindMapping` を他の種別へ広げる作業では、この「存在するが中身が薄い」状態を見て慌てないこと。
