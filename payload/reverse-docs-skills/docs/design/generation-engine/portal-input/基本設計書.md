# generation-engine/scripts/portal-input 群 基本設計書

## 1. この文書の位置づけ

このリポジトリ自身の `generation-engine/scripts/` は、対象リポジトリへ設計書を生成する道具である。その道具自身には、これまで設計書が無かった（`docs/tasks/自己設計書整備の指示書.md` 2.1〜2.2 節）。本文書は `portal-input/` 群について、納品物と同じ二層構造（基本設計書・詳細設計書）を適用する4群目である（1群目は `docs/design/generation-engine/extract/`、2群目は `docs/design/generation-engine/unit-list/`、3群目は `docs/design/generation-engine/matrix/` を参照）。

対象は `generation-engine/scripts/portal-input/` 配下の `.sh` 1本（実測。`find generation-engine/scripts/portal-input -name '*.sh' | wc -l`）。この群も `matrix/` 群と同じく単一スクリプトで構成される。

## 2. この群が何をするか

配布物の生成器だけではポータルを再現できず、実行側の独自スクリプトに依存していた問題（改善課題1-26）への対応として新設された経路である。API・テーブル・バッチ・帳票・外部連携・機能の非画面6種別について、既に書かれた設計文書（Markdown）の frontmatter から一覧マニフェスト（`<kind>-manifest.json`）を機械的に組み立てる。抽出元の形式は `delivery-payload/references/doc-extraction.json` の宣言に外出しされており、特定の文書構成に依存しない。

画面は対象外である。画面のfrontmatter体系（`screenKey`/`route`/`entryFile`）が他種別と異なるため（`doc-extraction.json` の `excluded` 節参照）。

frontmatterから導けない項目（`kind`・`confidence`・`detectionMethod`・`fileCount`・API以外の`identifier`）は捏造せず、宣言の `unresolvable` 節が定める代替値で埋める（`kind` を明示的に `unresolved` にする理由・`confidence` を `low` にする理由・`strategy.approvedByUser` を強制的に `true` にする理由は、`.claude/rules/scoped/portal/page-conventions/rule.md` の「## 設計判断」内「### build-manifests-from-docs.sh」節に既に記載済み。本文書は同節を正とし、重複記載しない）。

| 系統 | スクリプト | 入力 | 出力 |
|---|---|---|---|
| 設計文書からのマニフェスト組み立て | `build-manifests-from-docs.sh` | 展開済み設計文書一式（`output-layout.json` の `<kind>UnitRoot` 配下）+ `doc-extraction.json` の宣言 | `<dest_dir>/<kind>-manifest.json`（api/table/batch/report/external/feature の6種別） |

## 3. 群内スクリプトの呼び出し関係

群内に呼び出し関係は存在しない（実測: スクリプトが1本のみ）。`build-manifests-from-docs.sh` は `<output_dir> <出力先ディレクトリ> [--unit-kind <種別>]` を受け取る単発 CLI として独立して呼べる。

## 4. 他の群との依存関係

- `../output-layout.sh`（`generation-engine/scripts/` ルート直下）を `source` し、`<kind>UnitRoot` の解決（`resolve_output_layout`・`output_layout_get`・`output_layout_kind_label`）を委譲する
- `unit-list/validate-manifest.sh` を種別1件ごとに直接呼び、組み立てたマニフェストの検証まで一貫して行う（本体`build_manifest_for_kind`関数の最終行）
- `delivery-payload/references/doc-extraction.json`（宣言ファイル。抽出元の frontmatter キー名・走査基点・導けない項目の代替値を定義）を読み込む
- `build-portal.sh`（ルート）・`verification/run-layer-full-pipeline.sh`・`verification/prepare-verification-input.sh` がこの群のスクリプトを呼ぶ側である（実測: `grep -rln "portal-input/build-manifests-from-docs.sh" generation-engine/scripts/`）
- `tests/check-argjson-unbounded-value.sh` の許可リストに、この群の `jq --argjson` 使用箇所（`u`・`unitCount`・`units`・`unresolvedCount`）が登録済みである（本体該当箇所・該当箇所）。この登録は「現時点でレビュー済み・安全と判断した」という記録であり、将来にわたる安全の証明ではない（同checkerのヘッダコメント該当箇所）。`units` は種別1件分のマニフェストへ蓄積する全ユニット配列であり、対象リポジトリの設計文書数が非常に多い場合は `extract-table-metadata.sh` と同種の引数長超過リスクを理論上持つが、この作業時点でその作り替え（`--slurpfile`化）は行っていない（振る舞いを変えない本作業のスコープ外）

## 5. 共通する実装上の判断

この群は単一スクリプトのため、複数スクリプトへ横断する共通の背景は無い。ただし本体ヘッダコメント（該当箇所）が群全体の実装方針として「macOS bash 3.2 互換（`mapfile` / `declare -A` 不使用）」を明記しており、これは関数内のローカル配列操作・`while read` によるファイル名候補の走査（`find_name_args`組み立て）など、スクリプト全体にわたる書き方の制約として現れる。実装判断は個別スクリプトの節（`詳細設計書.md`）にまとめて記載する。

## 6. 詳細設計を個別に持つスクリプト（第1優先: 素直でない実装を持つもの）

`詳細設計書.md` を参照。`build-manifests-from-docs.sh` 1本について、実装契約と実装判断の節を持つ。

## 7. 詳細設計を個別に持たないスクリプト

無し（群の唯一のスクリプトを第1優先として選定したため）。
