# 指示書の片付け方

`docs/tasks/` に置いた指示書は、作業が終わった後もそのまま残り続けると、今どれが進行中でどれが片付いたのかを目で追わないと分からなくなる。この文書は、片付いたかどうかを機械で確かめ、片付いたものだけを `docs/tasks/done/` へ移す手順を定める。

## 片付いたと判定する条件

次の条件をすべて満たした指示書だけを「片付いた」とみなす。判定する処理は `docs/scripts/judge-task-done.sh` に実装している。

| 条件 | 中身 |
|---|---|
| 記録が済んでいる | 指示書に「対応の記録」の節があり、「### 判定の充足状況」の表に判定の行が1件以上あり、状態がすべて「完了」または「対象外」である。「未着手」「対応中」「判断待ち」が1件でも残っていれば満たさない |
| 実測が済んでいる | 「### 判定の充足状況」の表が「判定・確かめる手段・状態・コミット・確かめた内容」の5列であり、各行の「確かめる手段」欄のコマンドを実際に実行してすべてが終了コード0を返す。「確かめる手段」の列が無い古い4列の表は満たさない。`目視` と書かれた行が1件でもあれば（機械では確かめられないため）満たさない。コマンドが時間の上限（既定120秒。`--timeout`で変更可）を超えたら「未確認」として満たさない |
| main へ入っている | 指示書が挙げるコミットが、すべて main の祖先である。コミットの実在を `git cat-file -e` で確かめてから、`git merge-base --is-ancestor` で祖先関係を判定する。「対象外」だけで構成され実在するコミットを持たない指示書は、対象なしとして満たしたものとして扱う。ただし「完了」が1件以上あるのに実在するコミットが1件も無い場合は満たさない |
| 公開が済んでいる | リポジトリ全体で1回だけ判定する。payload が現在の main と一致し、agent-toolkit の payload を運ぶ枝（現在の HEAD）に未 push のコミットが0件であれば「反映済み」とする |

**「実測が済んでいる」条件は、記録の状態欄が「完了」という文字列を書けば通っていた問題への対応として追加した。** 状態欄の文字列は自由記述であり、条件が実際に満たされたかを裏付けずに「完了」と書けてしまう。実際に `docs/tasks/done/` の指示書を実測したところ、状態欄が「完了」のまま実際には条件を満たしていない指示書が見つかった。「確かめる手段」欄へコマンドそのものを書かせ、判定のたびに実行して終了コードで判定することで、文字列だけでは検知できない偽の完了を機械的に検知する。「状態」欄は人が直接書くのではなく、`bash docs/scripts/judge-task-done.sh --write` を実行して判定器に書き込ませる。

## 段階3（照合）: 元の指摘のキーが指示書に現れるか

段階1（書式）と段階2（実測）は、指示書1件それぞれの内側だけを見る。指示書が元の指摘の一部しか拾っていなくても、指示書自身の書式と実測がすべて通っていれば移せてしまう。実際に `実装契約の置き場を全種別で揃える指示書` は判定15件すべてを満たしながら、元の指摘のうち疑似コードと戻り値を落としていた。

`bash docs/scripts/judge-task-done.sh --cross-check` は、元の指摘のキー（`docs/tasks/指摘改善一覧.md` の項目名にある「（原番号 1-NN）」）を集め、`docs/tasks/` 直下と `done/` の指示書のいずれかにそのキーが現れるかを数える。いずれの指示書にも現れないキーがあれば、そのキーを一覧で報告する。既定の実行（引数なし）・`--apply`・`--write`・`--self-test` の動きは変えず、`--cross-check` を指定したときだけ照合する独立した動作にした。

キーの情報源には指示書が冒頭に持つ「元の指摘」欄だけを使い、`docs/tasks/指摘改善一覧.md` の見出し「### 1-NN.」は使わない。あの文書自身が `docs/tasks/` 直下の指示書である。見出しがその文書自身の中に存在するため、あの文書の見出しをキーの情報源にすると走査対象（`docs/tasks/` 直下 + `done/`）にあの文書自身が含まれ、どのキーも必ずその場で見つかってしまう。照合が欠落を検知できない恒真式になってしまうため、走査対象に含まれない `work-records/改善反映台帳.md` をキーの情報源とする。

`--cross-check` が報告した「現れないキー」は、そのまま欠落として扱う。指示書のどこかに漏れなく書かれているはずのキーが実際には見当たらないという検出結果であり、機械的に直すものではない。報告されたキーごとに、対応する指摘が本当にどの指示書にも記載されていないのか、記述の書き方が単語境界一致でたまたま拾えなかっただけなのかを人が確認する。

キーの情報源に台帳だけを使う一方で、走査対象（`docs/tasks/` 直下 + `done/`）には `docs/tasks/指摘改善一覧.md` 自身も含まれる。実測（2026-08-18時点）では「現れる」と判定された45キーのうち27キーは、`docs/tasks/指摘改善一覧.md` 以外のどの指示書にも現れず、あの文書自身の見出しでのみ現れていた。あの文書はそれ自体が指摘の記録であり指示書としても扱われるため走査対象から除く判断はしていないが、「現れる」の27キーは「専用の対応指示書へ引き継がれた」ことまでは意味しない。この違いを見たい場合は、キーごとに `grep -lE '\bキー\b' docs/tasks/*.md docs/tasks/done/*.md` を実行し、ヒットしたファイルが `docs/tasks/指摘改善一覧.md` だけかどうかを確かめる。

## 判断待ちを済みに数えない理由

判断待ちを済みに数えない。判断待ちは未解決である。担当の手で進められない状態であっても、決定が出れば作業が発生する。`done/` は解決し公開まで済んだものの置き場であり、決定を待っている状態のものを入れると、決定が出たときに気付く契機が失われる。

判断待ちが残る指示書は `docs/tasks/` に残す。判断が出て記録が「完了」または「対象外」へ変われば、そこで初めて移せる。

## 公開を指示書ごとに追わず、全体で1回だけ判定する理由

payload への同期は、指示書1件ごとに個別の反映作業を行う形ではなく、reverse-docs-skills の main の状態をまるごと写す形で行われる。したがって、payload が現在の main と一致していれば、main に入っている作業はすべて公開済みだと言える。指示書ごとに公開状況を追うと、同じ同期作業の結果を指示書の数だけ重複して確かめることになり、判定の手間が増えるだけで結果は変わらない。

公開が答えるべき問いは「reverse-docs-skills の成果が公開されたか」であり、agent-toolkit の他の作業用の枝が進行中であることはこの問いへの答えを変えない。そのため、未 push の確認は payload を運ぶ枝（現在 checkout している枝）だけを見る。agent-toolkit で誰かが別の作業用の枝を進めていても、その枝の未 push は判定に含めない。運ぶ枝の追跡先（`@{u}`）が解決できない場合は、押し出せているかどうかが分からない状態のため「判定不能」で止め、「反映済み」とはしない。

## 判定から移動までの流れ

1. 判定するには、`bash docs/scripts/judge-task-done.sh` を引数なしで実行する。「公開の状態」の1行、「移せる」の一覧、「移せない」の一覧（理由付き）が出る。この時点ではファイルを一切動かさない
2. 移せない理由を読むには、「移せない」に挙げられた指示書ごとに、理由（記録なし・確かめる手段の列が無い・判定の行が0件・目視の行がある・実測で満たさない判定がある・確かめる手段が時間の上限を超えた（未確認）・判断待ちが残る・未着手/対応中が残る・完了があるのに実在するコミットが1件も書かれていない・main に入っていないコミットがある・公開が未反映）のどれに当たるかを確かめる。記録が足りない指示書は指示書側の「対応の記録」を書き足す。確かめる手段の列が無い場合は5列の形へ書き直す。実測で満たさない場合は判定の条件を実際に満たしてから `--write` で状態欄を書き直す。判断待ちが残る場合は、決定が出て記録が「完了」または「対象外」へ変わるのを待つ。コミットが main に入っていない場合は、そのコミットが実際に main へ統合されるのを待つ。公開が未反映の場合は、CLAUDE.md の公開完遂フローに従って同期・push を済ませる
3. `--apply` で移すには、対応が済んだら、判定を再実行して「移せる」に入ったことを確かめてから、`bash docs/scripts/judge-task-done.sh --apply` を実行する。「移せる」に挙がった指示書だけを `docs/tasks/done/` へ `git mv` し、git のステージへ載せる。この時点ではコミットしない
4. コミットするには、ステージされた移動を、他の変更と混ぜずに単独でコミットする

## 誰がやるか

指示書の移動は、進行の管理を受け持つ側が行う。指示書に書かれた作業そのものを担当する側は移動しない。担当は目の前の指示書を進めることに集中し、片付いたかどうかの判断と移動は、複数の指示書を横断して見ている進行管理側が担う。

移動と、進行中の指示書に対する判定の記録更新が同じコミットに混ざると、そのコミットが「何をした変更か」を読み取れなくなる。担当が対応の記録を書き足す作業と、進行管理側が片付いた指示書を移す作業は、それぞれ別のコミットに分ける。

## 移した後に書き足すときの扱い

`docs/tasks/done/` へ移した指示書に追記が必要になった場合、その場所のファイルを直接書き換えてはならない。`docs/tasks/` へ戻してから書き足す。理由と手順の詳細は `docs/tasks/done/この場所について.md` を参照する。

## 判定器を迂回してはならない

`bash docs/scripts/judge-task-done.sh` が「移せる」に挙げていない指示書を、`git mv` で手動で `docs/tasks/done/` へ移してはならない。過去に一度、判定器が3条件のいずれも満たさないと示した状態のまま、ユーザーの判断を根拠として7件を判定器を経由せず `done/` へ移したことがあった（コミット `2eaf4f86`）。移された指示書は、起こしたばかりで対応の記録が伴っておらず、コミット欄が空のものを含んでいた。判定器が意味を持つのは、判定器が止めたものを別の手段で通せない場合に限る。条件を満たしていないと判定器が示した場合は、対応の記録を書き足す・コミットを main へ統合する・公開を完遂するのいずれかで実際に条件を満たしてから移す。判定器自体の判定条件が誤っていると考える場合は、`judge-task-done.sh` を直接書き換えて条件を緩めるのではなく、判定条件そのものの妥当性を指示書として起こして検討する。

## 設計判断

### check-task-done-move.sh

**必要性**: `judge-task-done.sh` は「移せる」かどうかを一覧で示す判定器だが、示すだけであり、`git mv` による手動の移動そのものを止める力を持たない。実際に、判定器が3条件のいずれも満たさないと示した状態のまま、7件が判定器を経由せず `docs/tasks/done/` へ移された実例がある（コミット `2eaf4f86`）。判定器が実効性を持つには、移動が確定する直前（`git commit` の直前）のタイミングで staged の変更を機械的に検査し、条件を満たさない移動を止める仕組みが要る。`judge-task-done.sh` は `docs/tasks/*.md`（直下）しか走査しないため、既に `docs/tasks/done/` へ移された staged 状態のファイルをそのままでは判定できない。使い捨ての `git worktree` を HEAD から作り、staged content を `docs/tasks/` 直下へ書き戻してから `judge-task-done.sh` を実行することで、判定の実装を複製せずに済ませている。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: commit のたびに staged の変更を確認し、対象ファイルを一時的な場所へ複製し、判定を手で組み立てる作業を繰り返すと確認の省略・見落としが生じる。実際に7件の迂回が起きたのは、この手作業の確認に依存していたためである
- `judge-task-done.sh` 自体への機能追加: あちらは「一覧を出す」道具であり、staged の変更を検査して commit を止める関心とは異なる。両者を1本に混ぜると、一覧表示という素の呼び出し（`bash docs/scripts/judge-task-done.sh`）でも commit 前提の検査が誤発火しかねない
- 既存 Makefile ターゲット拡張・package.json scripts 追加: このリポジトリはどちらも持たない

**保守責任者**: 人手（ユーザー）。`judge-task-done.sh` の3条件（記録が済んでいる・main へ入っている・公開が済んでいる）や出力形式（「移せる:」の一覧の書式）を変える場合は、本スクリプトの出力解析（`awk` による「移せる:」節の抽出、`grep -F -- "- $base"` による対象の一致判定）を同時に確認する。

**廃棄条件**: `docs/tasks/done/` による退避の運用を廃止した時、または `judge-task-done.sh` による片付き判定の仕組み自体を廃止した時。
