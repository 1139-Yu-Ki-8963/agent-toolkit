# 用語管理Skill仕様書

## 1. 位置づけ

用語管理Skillは、複数のWebアプリで共有する業務概念と、画面、API、データベース、コード、文書に現れる表現を結び付ける意味基盤を管理する。

用語集は全変数一覧ではない。
採録対象は、設計、実装、レビュー、利用者向け説明で同じ意味を保つ必要がある概念に限る。

現行の `generation-engine/samples/一覧/用語辞書/用語辞書.html` は、14列を持つ閲覧用の意味辞書である。
列は意味キー、日本語名、英語名、定義、適用範囲、分類、コード名、型名、DB名、API名、UI表示名、許容値、状態、備考とする。
本仕様は、この表示を承認済み用語のポータル投影として残しつつ、定義に保守情報と統制情報を追加する。

## 2. 目的

- 人が使う業務語と、AIやコードが使う識別子の意味を一致させる。
- 複数アプリ、複数リポジトリ、複数の技術層で同じ概念を追跡できるようにする。
- AI設計とAI実装が、承認済みの定義、別名、禁止語、命名規則を参照できるようにする。
- リバース解析の観測結果を、承認済み定義へ直接混入させずに審査できるようにする。
- 用語変更の影響範囲と判断履歴を残す。
- 人向けポータル、設計書、レビュー支援に同じ定義から情報を供給する。

## 3. 非目的

- ローカル変数、引数、CSSクラス、生成物の全件収集は行わない。
- コードの出現頻度だけで業務概念を確定しない。
- AIの推定だけで定義を承認しない。
- 用語keyを表示順や採番のための連番IDとして使わない。
- ポータルHTMLを定義にしない。
- 用語管理Skillがアプリコードを自動改名しない。

## 4. Skillの構成

### 4.1 管理Skill

現行Skill名は `managing-semantic-glossary` とする。
型は `orchestration` とし、照会、提案審査、追加、更新、廃止、検証、公開投影を順序付きで統制する。

現行配置は `.claude/skills/managing-semantic-glossary/` とする。
確定frontmatterは次のとおりである。

```yaml
---
name: managing-semantic-glossary
description: |
  承認済み用語の変更と公開を統制する。
  TRIGGER when: 用語集の照会、提案審査、追加、更新、廃止、検証、公開時。
  SKIP: 解析候補の抽出だけを行う時、全変数一覧を作る時。
invocation: managing-semantic-glossary
type: orchestration
allowed-tools: [Read, Write, Edit, Bash, Grep, Glob, AskUserQuestion]
---
```

対象リポジトリ固有の候補抽出は、各解析Skillまたはアダプターへ分離する。
Skill本文に特定プロジェクトの絶対パスを埋め込まない。

### 4.2 実行モード

| モード | 目的 | 主な入力 | 主な出力 | 書き込み |
|---|---|---|---|---|
| `lookup` | key、表示名、別名、コード表現から承認済み用語を検索する | 検索語、対象scope | 用語レコード、関係、利用箇所 | なし |
| `review-proposal` | 解析候補を採用、差し戻し、却下、保留する | 提案ファイル、審査者、判断 | 審査済み提案、採用時の変更案 | 提案領域のみ |
| `add` | 新しい概念を登録する | 承認済み追加要求 | 用語レコード、変更履歴 | 定義へ追加 |
| `update` | 定義、表現、関係を更新する | key、変更内容、根拠 | 更新レコード、影響分析 | 定義を更新 |
| `deprecate` | 用語を廃止または後継用語へ移行する | key、理由、後継key | 廃止情報、移行案 | 定義を更新 |
| `validate` | 構造、意味、参照、命名、重複を検査する | 用語集 | 検査結果 | なし |
| `publish` | 承認済み用語から派生物を生成する | 用語集、表示設定 | ポータル用データ | 派生物のみ |

`publish` は定義を編集しない。
派生物の手修正はずれとして検出する。
現行版のpublish対象はportalだけである。
`ai_index`は`review_required/not_implemented`で停止し、将来タスクで実装する。

## 5. 責務

### 5.1 管理Skillが担う責務

- 定義の場所、schema version、content versionを解決する。
- keyを一意に解決し、同名異義を含む表示名と別名はscopeと関係を使って曖昧性を解消する。
- 追加、更新、廃止の状態遷移を検査する。
- 変更前に重複、類義、禁止語、命名、参照整合、影響範囲を検査する。
- 承認者と根拠を履歴へ記録する。
- 解析候補と承認済み用語を混在させない。
- ポータルと将来のAI向け索引が参照する承認済み定義を提供する。
- 検査結果を機械可読形式と人向け要約の両方で返す。

### 5.2 管理Skillが担わない責務

- リポジトリ全体から候補を抽出する処理は各解析Skillが担う。
- 業務上の正しさの最終判断は、承認者が担う。
- アプリコードの一括改名は、影響分析後に別の実装Skillが担う。
- 翻訳の品質保証は、将来のローカライズSkillが担う。
- ポータルの表示実装はポータル生成Skillが担う。

## 6. 管理対象

### 6.1 登録対象

- 業務主体、業務対象、役割、価値オブジェクト
- 属性、識別子、状態、区分、イベント
- 業務処理、計算規則、制約で参照する概念
- API、データベース、画面、コードで複数箇所に現れる共有概念
- プロジェクト固有の意味を持つ技術用語
- 設計やレビューで誤解が起きやすい略語

### 6.2 原則として登録しない対象

- 1箇所だけで使う自明なローカル変数
- フレームワーク標準の語で、プロジェクト固有の定義を持たないもの
- 一時ファイル名、生成ハッシュ、ビルド番号
- 表示順だけを表す番号
- 意味を説明できない略語
- 根拠がなく、解析Skillが推定しただけの概念

## 7. 定義と派生物

| 種別 | 役割 | 更新主体 |
|---|---|---|
| 用語YAML | 承認済み用語の単一情報源 | 用語管理Skillと承認者 |
| 提案YAML | 解析Skillが作る候補の審査待ち領域 | 解析Skill、保守Skill、審査者 |
| 変更履歴 | 変更理由、審査者、移行情報の記録 | 用語管理Skill |
| ポータル用データ | 人向け検索と表示 | publish処理 |
| AI向け索引 | 設計、実装、レビュー時の検索用 | 将来のpublish拡張。現行版では生成しない |
| 用語辞書HTML | 承認済み用語の閲覧用投影 | ポータル生成Skill |

提案YAMLから用語YAMLへの昇格は、承認操作だけが行える。
ファイル移動や配列連結だけで昇格させてはならない。

## 8. 提案状態と用語ライフサイクル

提案の承認状態と、承認済み用語のライフサイクルは別の状態機械である。

提案の主遷移は次のとおりである。

```text
detected -> needs_review -> approved -> merged
                |
                +-> changes_requested / rejected / deferred
```

`merged`は提案内容が用語集へ反映された状態である。
`rejected`は定義へ採用しないと判断した状態であり、提案履歴側にのみ残す。

承認済み用語のライフサイクルは次のとおりである。

```text
active -> deprecated -> retired
```

- `active`：設計、実装、ポータル、レビューで利用できる承認済み状態。
- `deprecated`：新規利用を禁止するが、既存参照の移行期間中は解決可能な状態。
- `retired`：移行が完了し、通常検索から除外する状態。

承認済み用語YAMLが持つ状態はactive、deprecated、retiredだけとする。
提案の`approved`から用語の`active`へ、単一の状態遷移として接続してはならない。
承認操作と用語集への反映を経て、用語ライフサイクルを開始する。

`active` を物理削除してはならない。
意味変更を伴うkeyの再利用も禁止する。

## 9. ポータル標準列

### 9.1 一覧の標準列

一覧は次の14列を列名も含めて固定する。用途の異なる名前を「主なコード対応」のような集約列へ潰してはならない。

| 列名 | 目的 |
|---|---|
| `key` | AI、設計、コード間の安定した一意参照 |
| `term_ja` | 日本語の代表用語 |
| `term_en` | 英語の代表用語 |
| `definition` | 概念の境界を含む定義 |
| `scope` | 適用する業務・システム範囲 |
| `category` | entity、attribute、value等の概念分類 |
| `code_name` | 変数・プロパティ等の代表コード名 |
| `type_name` | クラス・型・enum等の型名 |
| `db_name` | テーブル・列等のDB名 |
| `api_name` | APIのfield・parameter名 |
| `ui_label` | 画面表示名 |
| `allowed_values` | 状態・区分等の許容値 |
| `status` | active、deprecated、retired |
| `notes` | 機械判定に使わない補足 |

### 9.2 詳細パネルへ移す項目

別名、禁止表記、全表現、関係、例、反例、制約、機密区分、根拠、変更履歴は詳細パネルへ表示する。
一覧へ全項目を横並びにしない。

### 9.3 候補レビュー画面の列

候補画面は承認済み一覧と分け、提案key、提案用語、推定定義、観測事実、推定内容、根拠、信頼度、既存類似語、影響範囲、承認状態を表示する。

## 10. 完了条件

管理Skillの1回の操作は、次の条件をすべて満たした時に完了とする。

- 入力schemaと状態遷移が妥当である。
- error級の検査結果が0件である。
- 変更操作では、根拠、変更理由、実行者、審査者が記録されている。
- 影響分析が必要な変更では、影響先と移行方針が記録されている。
- 提案採用では、承認済みレコードへ決定的に変換できる。
- 派生物生成では、定義のcontent versionと生成元versionを記録している。

## 11. 予想を裏切る挙動

- `customer_id` は変数名の収集結果ではなく、顧客を一意に識別する業務概念として定義できる場合だけ独立した用語にする。
- 同じ表示名でも意味が違えば別keyにする。keyの衝突回避だけを目的とする無意味な接尾辞は使わない。
- 定義の誤字修正は小変更だが、定義の境界を変える変更はkeyを維持しても破壊的変更になり得る。
- コードで未使用でも、法令、契約、移行、教育資料で使われている用語は未使用とは限らない。
