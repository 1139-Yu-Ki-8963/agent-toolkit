# 用語運用ルール

## 1. 役割

| 役割 | 責務 |
|---|---|
| requester | 追加、変更、廃止の理由と根拠を提出する |
| steward | 定義、scope、別名、表現を整備する |
| business approver | 業務上の正しさを承認する |
| technical approver | API、DB、コードへの影響と移行可能性を承認する |
| maintainer | schema検証、重複検査、履歴、version更新を行う |
| publisher | 承認済み定義から派生物を再生成する |

同じ人が複数の役割を持てるが、AIだけをbusiness approverにしてはならない。

## 2. 追加ルール

1. requesterは、追加理由と標準14フィールドを提出する。
   - `key`、`term_ja`、`term_en`、`definition`、`scope`、`category`、`code_name`
   - `type_name`、`db_name`、`api_name`、`ui_label`、`allowed_values`、`status`、`notes`
   - 未知・該当なしは仕様で許された空値を明示し、別の名前へ集約しない。
2. 保守Skillは、key衝突、表記衝突、類義語、禁止語、命名、根拠を検査する。
3. stewardは、既存概念の別名や下位概念で表現できないことを確認する。
4. business approverはdefinitionとscopeを承認する。
5. technical approverはrepresentationと移行影響を承認する。
6. 管理Skillはactiveとして定義へ追加し、minor versionを更新する。

新しい用語を、分類や検索の都合だけで追加しない。
既存用語のalias、relation、scope追加で表現できる場合は新規keyを作らない。

## 3. 更新ルール

### 3.1 patch相当

- 誤字の修正
- 根拠参照の位置更新
- 意味を変えない説明改善
- 新しいrepresentationの追加
- notesや例の追加

### 3.2 minor相当

- 新用語の追加
- 新aliasの追加
- 新しい非破壊的relationの追加
- scopeの追加。ただし既存利用者の意味を変えない場合に限る

### 3.3 major相当

- key変更
- definitionの対象境界変更
- 用語の分割または統合
- scope縮小
- 許可表記の禁止化
- activeからdeprecatedへの遷移
- 外部契約に使うrepresentationの変更

major変更は影響分析と移行計画を必須にする。

## 4. 廃止ルール

公開済み用語の物理削除を禁止する。

1. `deprecated` にし、理由、後継key、移行期限を記録する。
2. 命名レビューは、新規利用をerrorまたはwarningにする。
3. 既存参照を影響一覧で追跡する。
4. active参照が0件になり、運用、契約、教育資料の確認が終わった後に `retired` にする。
5. retiredレコードは通常一覧から隠せるが、key解決と履歴参照のために保持する。

draftで一度も公開されず、他レコードから参照されず、監査上の保持義務がない誤登録だけは物理削除を許可する。

## 5. レビュー手順

| 手順 | 確認内容 | 合格条件 |
|---|---|---|
| 構造検査 | schema、必須項目、列挙値 | error 0件 |
| 命名検査 | 意味key、略語、禁止一般語 | error 0件 |
| 重複検査 | key、term_ja、term_en、alias、各コード名 | 未裁定衝突0件 |
| 意味検査 | definition、例、反例、category、scope | approverが境界を説明できる |
| 根拠検査 | source、decision ref | active用語に根拠がある |
| 影響検査 | 直接、派生、意味、互換性 | 移行対象と担当が明示される |
| 承認検査 | approver | 役割を持つ承認者が設定される |
| 派生検査 | ポータル、辞書 | 定義versionと一致する |

AI索引は将来の派生物である。
現行版では`ai_index`要求を`review_required/not_implemented`で停止し、派生検査の対象に含めない。

## 6. version管理

`schema_version` と `content_version` を分ける。

- schema versionはYAMLの構造変更を表す。
- content versionは用語の意味とライフサイクルの変更を表す。
- 派生物は両versionと生成時刻を記録する。
- Git commitは変更理由と対象keyを示す。
- 1変更要求は、相互に依存する用語群を除き、1つの主目的に絞る。
- pull requestには追加、更新、廃止、影響、承認者、再生成結果を記載する。

## 7. 複数アプリ運用

- organizationまたはproduct共通用語を優先し、アプリごとの複製を避ける。
- アプリ固有の意味差がある場合はscopeを限定する。
- 同じlabelで意味が違う場合は、意味を表す限定語をkeyへ加える。
- アプリ固有用語を共通scopeへ昇格する時は、全利用アプリの影響分析を行う。
- registryを物理分割しても、共通索引でkey、alias、禁止語の衝突を検査する。

## 8. ポータル運用

- 通常の用語辞書にはactiveとdeprecatedを表示する。
- deprecatedには後継keyと移行期限を表示する。
- retiredは履歴検索でだけ表示する。
- 解析候補は別画面、別URL、別権限にする。
- 一覧では主要列だけを表示し、全根拠と全representationは詳細パネルへ置く。
- 人向け表示から定義のkeyとversionへ到達できるようにする。

## 9. AI利用ルール

- AI設計とAI実装はactive用語を優先して使う。
- deprecated用語を新規生成しない。
- 見つからない概念は、新しいkeyを勝手に確定せず候補として返す。
- definitionとrepresentationが矛盾する場合は、定義を自動修正せず差異を報告する。
- 未承認候補は検索補助に使えても、命名規範や業務規則には使わない。

## 10. 監査頻度

| 契機 | 実施内容 |
|---|---|
| 用語変更ごと | schema、命名、重複、影響、派生ずれ |
| アプリrelease前 | deprecated新規利用、禁止語、参照切れ |
| 四半期 | 承認者記録、根拠鮮度、未使用候補、類義語 |
| 大規模移行前 | key、外部契約、DB、eventの影響全件 |
| schema major更新時 | 全用語の移行検証と旧schemaの読取方針 |

## 11. 予想を裏切る挙動

- content versionは用語件数ではなく、利用者へ与える意味上の影響で上げる。
- HTML上の列順変更は定義のschema version変更ではない。
