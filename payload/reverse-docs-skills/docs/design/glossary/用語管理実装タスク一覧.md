# 用語管理実装タスク一覧

## 1. 前提

この文書は現行版の実装状況と後続タスクを管理する。
現行v0.1で完了した基盤、互換経路だけが完了した範囲、将来の対象を分けて扱う。

タスクkeyは内容を表す意味語を使い、連番IDを使わない。
E2EはEnd-to-Endを指し、候補抽出から派生物生成までの一巡検証を意味する。
T2は、現行の詳細ページ設計で用語辞書に割り当てられた対訳辞書型テンプレートを指す。

## 2. 実装状況

### 2.1 現行v0.1で完了

- 共通契約、正式YAML schema、代表fixture、意味整合validator
- 用語管理Skillと用語保守Skillの手順、契約テスト、AI forward-test
- proposal、change、glossaryを分離した審査契約と二者承認境界
- 承認済み用語からポータルpage-dataとサンプルHTMLへの決定的な投影

### 2.2 互換経路まで完了

- 既存のリバース用用語生成Skillは、対象repo外へproposalだけを出力する候補生成専用経路に変更した。
- 旧5項目のポータル入力は読み取り互換を維持するが、自動移行や意味keyの推定は行わない。

### 2.3 将来の対象

- API、DB、画面、コード、文書ごとの候補adapterと専用の重複・類義語検出器
- 既存用語データの移行処理、候補審査UI、本番registry配置
- AI利用向け索引、versionずれgate、用語ライフサイクルのE2E検証

現行版の`ai_index`要求は`review_required/not_implemented`で停止し、成果物を生成しない。

## 4. 並列化の目安

registry契約後は、schemaと管理Skill骨格を並列実行できる。

schema確定後は、意味整合validator、重複と類義語の検出、解析候補adapterを並列実行できる。

管理Skill、validator、閲覧用投影は現行v0.1で完了している。
AI索引は将来タスクとして、候補adapterや移行処理と独立に着手できる。

審査workflow、既存データ移行、governance gate、E2E検証は依存順に実行する。
