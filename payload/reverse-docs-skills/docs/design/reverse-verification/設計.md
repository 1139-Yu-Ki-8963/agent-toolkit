# リバース検証の設計

本書はリバース設計スキル群に対する検証の設計を定める。検証の対象はスキル群そのものであり、生成された成果物の業務的な正しさではない。確かめるのは、このリポジトリのスキルと同梱スクリプトだけで、設計書とポータル一式を空の状態から生成できるかである。

## 検証の 3 層

| 層 | 内容 | 実行の頻度 | 検出できるもの |
|---|---|---|---|
| 第 1 層 機械検証 | 自己テストの実行、定義の整合検査、文字列の走査 | 毎回（時間上限を設ける） | 退行、記述の不整合 |
| 第 2 層 単体生成 | スキル 1 本を入力データで実行し、生成物を検査する | 毎回（上限を設ける） | そのスキル単体の欠陥 |
| 第 3 層 一気通貫 | 空の出力先から順に実行し、成果物一式を生成する | まとまった変更の直後 | 依存の欠落、実行順序の誤り、生成器だけでは再現できない部分 |

本書が実装を定めるのは第 1 層と第 3 層である。第 2 層は各スキルの自己検証が担うため、本書では扱わない。

第 1 層の対象は 88 本ある。上限がなければ、全体の実行は 16 分を超える。1 本の遅れが、全体の実行を止める。そのため、1 本あたりに時間上限を設ける。既定は 120 秒とする。上限に達した対象は、打ち切りとして記録する。これは失敗と区別する。打ち切られた対象は、検証されないまま残る。上限を延ばし、個別に確かめる。

初回の実測では、上限を 5 秒とした。対象は全 88 本である。成功は 18 本、失敗は 4 本であった。途中停止の疑いは 14 本、打ち切りは 52 本であった。総ケース数は 315 件であった。途中停止の疑いの 14 本は、自己テストがありながら、ケースを 1 件も実行せずに成功する状態であった。この型は、個々の出力を目視で追わない限り気付けない。第 1 層を設けた理由が、ここにある。

**既存の成果物を入力として検証してはならない。** 既に存在する生成物を見ている限り、それが何によって作られたかは分からないためである。

## 既存の成果物とは何か

| 語 | 意味 |
|---|---|
| 既存の成果物 | 検証の対象である生成器が、過去に出力した生成物 |
| 代表例 | `generation-engine/samples/` 配下の生成済み HTML |
| 含まないもの | テンプレートと疑似入力。これらは生成器の出力ではない |

## 4 つの判定基準

検証の合否は、以下 4 観点の全合格で決める。

| 観点 | 合格条件 |
|---|---|
| 網羅 | 分母の一覧に載る成果物が、生成物にすべて存在すること |
| 自立 | このリポジトリのスキルと同梱スクリプトだけで生成できること |
| 再現 | 同じ入力で 2 回実行し、生成物が一致すること |
| 健全 | 生成物に、解決できないリンク・空のページ・未変換の記法が無いこと |

自立の判定には限界がある。判定は参照パスの静的な走査で行い、走査の範囲は第 3 層の生成連鎖が実際に呼び出すスクリプトに限る。引数や環境変数から実行時に組み立てられる外部のパスは、この方法では捕まらない。実行時に外部の呼び出しを遮断する仕組みは設けない。

## 網羅の分母

網羅の判定は、次の分母に載る成果物がすべて生成されたかで行う。

| 成果物 | 件数 | 生成する経路 |
|---|---|---|
| 画面一覧のマニフェストと一覧 | 3 | `unit-list/detect-screens.sh` と `unit-list/build-screen-list.sh` |
| 種別別の一覧 | 9 | `unit-list/build-unit-list.sh` ほか |
| マトリクスと対応表 | 5 | `matrix/build-matrix-pages.sh` |
| 規約の階層 | 61 | `rules/scaffold-rule-definitions.sh --apply` |
| デザインシステムと棚卸しとアイコン | 3 | `detail-pages/build-detail-page.sh` |
| ポータルのトップページ | 1 | `build-portal.sh` |
| 共通文書の HTML | 疑似入力の件数による | `build-portal.sh` |

分母の総件数は 82 件である。ただしこの値は `rule-taxonomy.json` の内容に依存して変わる。

規約の階層の 61 件は、親 7 件の `parent.yml`、子 27 件の `rule.md`、子 27 件の `design-notes.md` の合計である。規約の階層の件数は、`rule-taxonomy.json` の親と子の件数から導く。親と子の数が変われば分母も変わるため、固定の値ではなく、判定のスクリプトは同一ファイルから毎回導出する。

分母には含めない成果物もある。

| 除外する成果物 | 除外の理由 |
|---|---|
| 各種の基本設計書と詳細設計書 | 本文の執筆に判断を要する |
| 技術スタックと環境構築手順とリリースノートと用語辞書 | 入力データを組み立てるスクリプトが無い |
| アーキテクチャ調査書 | 調査結果の記述に判断を要する |
| 状態遷移図と ER 図と画面遷移図 | 入力データの組み立てが未整備である |
| スクリーンショット | 画面の操作を伴う |
| 画面レジストリと対象外種別の記録 | 呼び出し元が記帳する |
| テストの観点表と仕様書 | 既存の流用か生成対象かが目録から確定できない |
| シーケンス図 | 目録が当面は手書きと記す |
| AI 設定資産 | 抽出元が対象リポジトリの `.claude/` 配下であり、疑似入力がこれを持たない |
| 複雑度プロファイル | 別モードの第 2 呼び出しが要り、通常の呼び出しでは作られない |

## 実行環境の隔離

検証の実行環境は、確認対象の外へ切り離す。

| 規定 | 内容 |
|---|---|
| 作業ツリー | 検証ごとに使い捨てのものを用意し、終了時に破棄する |
| 出力先 | 版管理の外へ置く。版管理下のディレクトリへ出力しない |
| 納品先 | 読み取りのみとし、書き込みを一切行わない |
| 終了時 | 作業ツリーと出力先を削除する。残すのは判定の結果と、失敗の再現に要る最小限の記録だけとする |

## 検証結果の扱い

使い捨ての作業ツリーと生成物は、一時領域の `reverse-verification` 配下へ置き、終了時に破棄する。判定結果は検証コマンドの標準出力と終了コードで確認する。反復する実行結果を課題形式へ変換しても意味をなさないため、専用の記録ファイルへ追記しない。

## 退避の条件

実行を伴う検証を省略してよいのは、実行を試みたうえで実行できなかった場合だけである。「実行が要る」という理由での省略を禁じる。実行できない状態が未解決課題になる場合だけ、`docs/tasks/作業課題一覧.md` の7項目形式で管理する。

この一文が無いと、実行を伴う検証が構造的に省略されるためである。実測として、退避先に積まれた 7 件は登録の以降に 1 件も実行されていない。退避の理由欄も「実行が要る」と書かれているだけであった。

本規定に対する専用の記録機能は設けない。検証の合否は実行時の終了コードで判定する。
