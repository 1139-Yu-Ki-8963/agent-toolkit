## 実装判断

本節は、今の実装が素直に見えない書き方を採っている箇所について、なぜその書き方を採ったかを記録します。本群は本数が多いため、実際にコードを読んで非自明な実装が確認できたものだけを対象とします。

### check-argjson-unbounded-value.sh: 変数名の規則ではなく許可リスト方式を選ぶ

可変長の値を安全でない渡し方（コマンドライン引数への直接展開）で扱っていないかの検出方式には、変数名の規則（「可変長らしい」名前を検出する）を使いません。現存する使用箇所を洗い出し3つ組（対象ファイル・渡し先の引数名・渡す値）を許可リスト化する方式を採ります。変数名の規則では、キーワードを含まない別名を経由した再導入を確実には拾えないためです。実際にこの経路は一度対策が入った後、名前を変えながら3段階を経て回帰した実績があります。

### check-portal-catalog.sh: 既知の欠陥として温存する箇所がある

本検査の一部（黄金データの取得機能）は、まだ書き込み許可の範囲を指定しない一時ファイルの作り方のままです。自己確認の経路には含まれないため、この作業では温存し、次に触れる際に他の箇所と揃えることが望ましいと記録します。

### unit-list/test-rebuild-screen-derived-pages.sh: 作業場所の解決を2点で工夫する

一時的な作業場所を、実行環境の記号的な経路のままではなく実体の経路へ解決してから使います。実行環境によっては一時領域が別名（シンボリックリンク）を経由しており、後段の書き込み許可検査がこの別名を理由に処理そのものを拒否することがあるためです。また、フィクスチャの入力元を、特定の履歴（コミット）への参照ではなく、リポジトリ内に保存済みの実データを直接読む方式にしています。特定の履歴がチェックアウト環境に存在しない場合や、リポジトリの配置構成によって履歴解決の前提が崩れる場合の両方を避けるためです。

### lib/find-cached-browser.cjs: 自動ダウンロードに頼らずキャッシュを探す

実描画検査が使うブラウザを、素直な形（起動時に自動でダウンロードさせる）ではなく、既に一般的な場所へキャッシュされたブラウザ実行ファイルを探して使います。ネットワーク接続が制限されうる実行環境では、検査実行のたびにブラウザをダウンロードする処理が失敗しうるためです。

### check-improvement-ledger.test.mjs: 厳密一致ではなく下限・構造の検査にする

追記型で行数が増え続ける台帳に対する検査で、特定の件数との厳密一致ではなく、下限件数の確認・列構成の検査・値同士の大小関係の検査を組み合わせます。厳密一致は、台帳へ正当な行が追記されるたびに陳腐化して不合格になるためです。

### test-non-applicable-density.sh: 走査にロケールを明示する

根拠の記入有無を判定する走査に、既定のロケール設定ではなく明示した設定を使います。既定の設定下では、全角文字を除外する判定が正しく働かず、正しく記入された行まで誤って未記入と判定する事例が実際にありました。
