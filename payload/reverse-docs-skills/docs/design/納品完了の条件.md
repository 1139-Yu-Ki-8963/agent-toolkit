# 納品完了の条件

## 1. この文書の位置づけ

本書は、リバース設計スキル群を対象プロジェクトへ適用した結果を「納品してよい状態」と
判定するための条件を定める。2026-08-16 時点で、このリポジトリには納品物 60 件の一覧
（`delivery-payload/references/portal-catalog.json`・`deliverable-inventory.json`）はあるが、
それが揃えば開発を始められるという条件を定めた文書は無かった。定義が無いため、対象プロ
ジェクトへ適用するたびに「終わったかどうか」を都度判断し直す状態が続いていた。

条件は次の口頭指示を機械で判定できる形へ落とした結果である。

```
リバース → ポータル作成 → docs の内容作成 → AI の rules など作成 →
そこから開発フローが通せて、とりあえず納品OK
```

判定するタイミングは、対象プロジェクトへリバース設計スキル群を適用したあとである。この
リポジトリ自身（雛形・サンプル）の状態を判定する文書ではない。

このリポジトリの役割は、対象プロジェクトへ渡す納品物を作るところまでである。納品物が
実際に動くかどうかの検証は、納品先の現場が担う。次の5段のうち、第1段から第4段までは
このリポジトリの責任で判定する。第5段は納品先が判定する。

## 2. 5段の条件

口頭指示の 4 矢印は、実行対象として 5 つの段に分かれる。ポータル作成と docs の内容作成
は別の生成器が担当し、判定の材料も別だからである。

| 段 | 名称 | 何が終われば次へ進めるか | 判定の方法（要約） | 誰が判定するか |
|---|---|---|---|---|
| 第1段 | リバース | 実在する種別すべてで一覧とマニフェストが生成されること | 一覧 HTML の実在確認とマニフェスト永続化検査の終了コード | このリポジトリ |
| 第2段 | ポータル作成 | ポータルのトップと各ページが生成され、リンクが切れていないこと | ポータル生成コマンドの終了コードと、ポータル規約検査・E2E 検査の不合格件数 | このリポジトリ |
| 第3段 | docsの内容作成 | 共通文書と対象種別の設計書が生成されること | 納品物一覧の生成結果にある状態列の確認 | このリポジトリ |
| 第4段 | AIのrules作成 | 規約定義が配布され、AI設定資産が生成されること | 規約配布・派生生成コマンドの終了コードと整合検査の終了コード | このリポジトリ |
| 第5段 | 開発フローが通る | 配った `/dev-flow` スキルで 1 件の変更を Phase1〜Phase5 まで完走できること | Phase5 確定時に残す完了記録の実在確認スクリプトの終了コード | 納品先 |

### 第1段 リバース

対象コードから種別ごとの一覧を作る段階である。実在種別は
`surveying-architecture-for-reverse-docs` が判定し、対象外の種別は
`<output_dir>/docs/scope-and-progress/excluded-kinds.json` へ記録される
（`delivery-payload/references/output-layout.json` の `excludedKinds` キーが指す配置）。

| 判定キー | 判定項目 | 確認先 | 判定コマンド・代替確認 | 実行主体 |
|---|---|---|---|---|
| reverse-list-html | 一覧 HTML の実在 | `<output_dir>/project-portal/lists/<labelDir>/<種別>一覧.html`（`output-layout.json` の `unitListHtml`。`<labelDir>` は `kindDirNames` が指す英字ディレクトリ名） | `bash generation-engine/scripts/unit-list/check-excluded-kinds-consistency.sh --present-lists <output_dir>`（6種別と派生機能一覧を検査） | このリポジトリ（納品する側） |

| reverse-excluded-kinds | 対象外種別の記録 | `excluded-kinds.json` の宣言と、6種別の一覧 HTML・基本・拡張マニフェスト、対象外記録の実在 | `bash generation-engine/scripts/unit-list/check-excluded-kinds-consistency.sh <output_dir>`（宣言と成果物実態の双方向一致を検査） | このリポジトリ（納品する側） |

覧などの既存一覧から作る派生一覧であり、この段の対象に含める。

<portal_output_dir>/derived-fingerprints.json` で生成物のパス一覧が得られる）。台帳のキーは
`<portal_output_dir>` を基点とした相対パスであり、`test-portal-conventions.sh` の相対パス
解決も実行時カレントディレクトリ基準のため、検査コマンドは `<portal_output_dir>` へ `cd`
してから実行する（実測: `generation-engine/samples` を対象にこの手順で実行し PASS=1110・FAIL=0 を確認

準備する。`manifestsRoot`は`delivery-payload/references/output-layout.json`を既定値とし、
`<output_dir>/output-layout.json`があれば重ね合わせて解決する。
技術スタックは`generating-tech-stack-for-reverse-docs`でアーキテクチャ調査書§2を
定義ファイルの実測値と突合する。検証済みpage-dataは`techstack-page-data.json`へ保存する。
環境構築手順は`generating-env-guide-for-reverse-docs`で同調査書§3を主データ源として整理する。
検証済みpage-dataは`env-page-data.json`へ保存する。用語辞書は承認済みの用語集を
`generation-engine/scripts/glossary/validate-semantic-glossary.sh`で検証する。
`project-semantic-glossary.py`で投影したpage-dataは`glossary-page-data.json`へ保存する。
入力の欠落は第2段の`portal-build`が`SKIP`として記録する。対応する古いHTMLが残っている
場合は同じ段で不合格にする。古いHTMLも無い場合は、第3段の`docs-inventory`が対象ページを
「未生成」として不合格にする。

AI設定資産は第4段の派生生成後に再抽出する。抽出結果が0件なら`SKIP`を記録し、古い
AI設定資産ページが残っている場合は`rules-ai-assets-portal`を非0終了として不合格にする。

### 第5段 開発フローが通る

配った `/dev-flow` スキルで、要件すり合わせから実装と動作確認まで 1 件通す段階である。
この段は納品先が判定する。このリポジトリが用意するのは、判定できる仕組み（完了記録を
残す手順と、それを確かめる検査）である。完了記録の手順は対象リポジトリへ配る
`/dev-flow` に含め、検査スクリプトは納品先が本ツールの
`generation-engine/scripts/tests/check-dev-flow-completion.sh` を使う。検査スクリプト自体は
対象リポジトリへ配布しない。

`/dev-flow` は対話で進行するフェーズ運転スキルであり、各フェーズの確定はユーザーの承認
を必要とするため、フェーズの進行そのものは終了コードだけで機械判定できない。2026-08-16
時点で、Phase5 確定時の提示物（実装概要・動作確認結果表・規約レビュー結果）を対象プロ
ジェクトの作業記録として保存する形式を定め、その実在を確認するスクリプトを作った。

| 判定キー | 判定項目 | 確認先 | 判定コマンド・代替確認 | 実行主体 |
|---|---|---|---|---|
| dev-flow-record | 完了記録の生成 | `<対象repoルート>/docs/scope-and-progress/開発フロー完了記録.md` | 機械判定不可。納品先が `/dev-flow` を対話実行し、Phase5 の承認後に「完了の記録」節が追記されたことを確認する | 納品先（納品する側は実行しない） |
| dev-flow-validate | 完了記録の実在・中身 | 記録の実在・必須項目・動作確認結果 | `bash <本ツールのルート>/generation-engine/scripts/tests/check-dev-flow-completion.sh <対象repoルート>` | 納品先（納品する側は実行しない） |

判定できるのは「Phase5 が少なくとも 1 回確定され、その記録が要件を満たす形で残ってい
るか」までである。フェーズの承認そのものを無人で再現する手段（`/dev-flow` を無人で 1 往
復させる最小のシナリオ実行器）は、2026-08-16 時点では作っていない。この判定を実行する
のは納品先であり、このリポジトリは仕組みを渡すところまでを担う。

## 3. とりあえず納品OKの水準

すべての種別・すべての工程が完成している必要はない。次の制約を前提に水準を分ける。

| 制約 | 内容 |
|---|---|
| 画面 | 一覧・facts 抽出・設計書執筆（基本設計・詳細設計）・往復検証の全工程が確立している |
| API・テーブル・バッチ・帳票・外部連携 | 一覧生成と設計書執筆（基本設計・詳細設計）の生成器は実装済みである（例: `generating-api-basic-design-for-reverse-docs`・`generating-table-definition-for-reverse-docs`・`generating-external-detail-design-for-reverse-docs` 等が実在し、2026-08-11 の実適用記録でも合格している）。facts 抽出は `extracting-unit-facts-from-code` が `screen`・`python` の 2 プロファイルしか実装しておらず、この 5 種別は facts.yml を経由せず一覧マニフェストと基本設計書を情報源にする別経路で書く。往復検証（`rebuilding-code-from-docs`）は画面専用の引数契約でのみ実装されている |

`README.md` の種別×工程の対応表は「設計書執筆: 未対応」と記すが、2026-08-16 時点の実装
と食い違う（上記の生成器が実在する）。表の記述が古いとみられる。facts 抽出が非画面 5 種
別で未実装である点と、往復検証が画面専用である点は実装のとおりであり、正しい制約として
扱う。

この制約のもとで、非画面 5 種別に残る未対応工程は facts 抽出と往復検証の 2 つだけであ
る。「とりあえず納品OK」の水準は次のとおりとする。

| 段 | 必須 / 任意 | 水準 |
|---|---|---|
| 第1段 リバース | 必須 | 実在する全種別で一覧生成が完了していること。facts 抽出は画面のみ必須とする |
| 第2段 ポータル作成 | 必須 | ポータルが生成され、規約検査・E2E 検査ともに不合格 0 件であること |
| 第3段 docsの内容作成 | 必須（共通文書・画面の設計書）／任意（非画面 5 種別の設計書） | 共通文書 6 件は必須。画面の基本設計書・詳細設計書は一覧に載る画面全件が対象。非画面 5 種別の基本設計書・詳細設計書は生成器が実装済みだが、往復検証で裏取りできないため全件化は任意とし、標本での生成があれば水準を満たす |
| 第4段 AIのrules作成 | 必須 | 規約 27 件が配布され、整合検査に合格し、AI設定資産一式（`.claude/`・`.cursor/`・`.codex/`・`AGENTS.md`）が実在すること |
| 第5段 開発フローが通る | 必須（仕組みの提供）。実際に通す判定は納品先の作業であり、このリポジトリの必須要件には含めない | このリポジトリは対象へ配る `/dev-flow` の雛形と、本ツール内の `check-dev-flow-completion.sh` を用意する。Phase1〜Phase5 を実際に完走させ、完了記録を確かめるのは納品先の作業である |

## 4. 判定の手順

対象プロジェクトへ適用したあと、判定キーの順に実行する。`reverse-list-html`から
`rules-flow-prerequisites`までは、このリポジトリを使って納品する側が実行する。
`dev-flow-record`と`dev-flow-validate`は納品先だけが実行し、納品する側の合否件数へ
含めない。各判定キーは2節の詳細表の1行だけに対応する。
`<対象プロジェクトの表示名>` には、納品依頼者と合意した利用者向けの正式名称を指定する。
リポジトリのフォルダ名からは決めず、合意した名称をコマンドの実行者が明示的に渡す。
たとえば、`--project-name "経費精算システム"` と指定する。

# 実行主体: このリポジトリ（納品する側）

# reverse-manifests-exist: 基本・拡張マニフェストの実在
bash generation-engine/scripts/unit-list/check-excluded-kinds-consistency.sh --manifests <output_dir>

# reverse-excluded-kinds: 対象外種別の宣言と成果物の実態
bash generation-engine/scripts/unit-list/check-excluded-kinds-consistency.sh <output_dir>

# portal-build: ポータル生成
source generation-engine/scripts/output-layout.sh

detail_input_dir="<output_dir>/$manifests_root/detail-pages"

# generating-tech-stack-for-reverse-docsで調査書§2と実測値を突合したpage-dataを次へ保存する

# docs-inventory: docsの内容作成状況の一括判定
inventory_md="<md出力先>"
bash generation-engine/scripts/build-deliverable-inventory.sh <output_root> <html出力先> "$inventory_md" || exit 1

ここから先は納品先だけが実行する。納品する側は実行せず、上記の納品する側向け判定の
合否集計にも含めない。

```bash
# 実行主体: 納品先（納品する側は実行しない）
target_root="<対象repoルート>"
reverse_docs_root="<納品先が取得した本ツールのルート>"

# dev-flow-record: /dev-flow を対話実行し、Phase5承認後の記録を人手確認する（機械判定不可）

# dev-flow-validate: Phase5確定の完了記録を検査
bash "$reverse_docs_root/generation-engine/scripts/tests/check-dev-flow-completion.sh" "$target_root"
```

`build-portal.sh` は各生成器の実行を `INFO: generating ...` として記録する。入力となる種別
または文書が存在しない場合は生成を試みず、`SKIP: ...` として理由を記録する。`SKIP` は入力
不存在を表し、生成器の失敗は `ERROR: ...` と非0終了で区別する。

第5段は `/dev-flow` の Phase5 ゲートを人手で確定させる工程そのものは自動化していない。
確定後に残る完了記録の実在と中身は、納品先が `dev-flow-validate` で機械判定する。
