# 納品物置き場の再構成構想

> **この構想は採用されなかった。** 2026-08-17 に、ここで提案した `project-setup/` ではなく
> `delivery-payload/` と `generation-engine/` へ分ける形で再構成を実施した。以下は当時の検討の記録である。

2026-08-14 時点の構想である。本構想は実装しない。判断の根拠と実測値を残すことが目的である。

## 背景

このリポジトリは対象プロジェクトへ「AIエージェントが動く状態」を納品するセットアップキットを定義する。ところが納品先へ配られる資産と、私たちが使う生成器が `shared/` の中に混在しており、パスから納品物かどうかを判断できない。

`delivery-payload/templates/` を例にすると、`rules/tool-defined/` は納品される規約の本文である。`partials/` は生成器が使う共通シェルの断片であり、同じ階層に並んでいる。納品物の目録（`delivery-payload/references/納品物フォルダ体系.md`）は文書としてだけ存在し、実体と対応していない。実際、納品スキル3本と検査の道具の記載が目録に無いことを実測で確認した。

キットを名乗る以上、箱を開けたら中身と使い方が分かる状態でなければ成立しない。

## project-setup

ルート直下に `project-setup/` を新設し、対象プロジェクトへ配置されるものだけを集める。判定は「対象プロジェクトへ配置されるか」の1点とする。

```
<repo-root>/
├── project-setup/          対象プロジェクトへ配る一式（新設）
├── shared/                 私たちの道具（生成器・部品・検証用の見本）
└── docs/                   このリポジトリ自身の説明
```

`project-setup/` の内部構造は、全体ガイド `docs/guides/reverse-docs-overview.html` の §2「生成される成果物」が示す納品後の3層に合わせる。納品後の姿が `docs/`（定義）・`project-portal/`（人間向け）・`.claude/` ほか（派生アダプター）の3層であるため、配る元も同じ形にすれば対応が一目で分かる。

内部構造の詳細は本構想では確定しない。実測による仕分けが未完了のためである。確定に必要な調査の内容は後述する。

## 命名の判断

`project-setup` を選んだ理由を書く。検討した候補と不採用の理由も残す。

| 候補 | 判定 |
|---|---|
| `project-setup/` | 採用。このリポジトリの責務（対象プロジェクトをセットアップする）と名前が一致し、用途まで伝わる |
| `deliverables/` | 及第。既存の「納品物」という語彙の英語名だが、用途が伝わらない |
| `delivery/` | 及第。行為を指すため、物の集合という体とずれる |
| `payload/` | 不可。agent-toolkit が別の意味で使用中であり同名異義になる |
| `dist/` | 不可。不透明な略語であり、慣例ではビルド生成物を指すため誤解を招く |
| `kit/` | 不可。何の一式かが名前から復元できない |
| `package/` | 不可。npm の package と多義 |

## 実測で判明した事実

先行調査は、規約まわりの5資産だけを対象にした。2026-08-14時点で、範囲を `shared/` 全体へ広げて実測した。両方の事実を、根拠のパスとともに書く。

1. 規約の雛形 `rule-template.md` と `design-notes-template.md` には配布経路が無い。`scaffold-rule-definitions.sh` の `build_draft_rule_md()` と `build_design_notes()`（110〜192行）が内容を直書きしている。雛形ファイルは読み込まれない。使用箇所は自己テストの比較対象のみである。
2. 納品物の目録に納品スキル3本と検査の道具の記載が無い。`delivery-payload/references/納品物フォルダ体系.md` を対象に `delivered-skills`・`dev-flow`・`tooling` を検索して該当0件だった。
3. 移設で壊れやすいという記述は、移設の方法に依存する。範囲を広げた調査で `scaffold-rule-definitions.sh` を確認した。同スクリプトは `SCRIPT_DIR` 起点の相対パスで完結している。`shared/` を丸ごと動かす方法（後述の方法B）では、この箇所は破綻しない。配られる101件だけを動かす方法（後述の方法A）では、55〜60行の参照先を追従させる必要がある。
4. 公開同期は3箇所の同時更新が必要である。1箇所目は `~/github-public/agent-toolkit/scripts/sync-manifest.json` への `project-setup` の mapping 追加である。2箇所目は `.claude/rules/always/publish/complete/check-publish-sync-gate.sh` の比較対象リストである。3箇所目は同ディレクトリの `rule.md` 本文の比較対象の記述である。
5. ルート直下の許可リストは `shared` と `docs` の2件のみである。`.claude/rules/always/project-context/rule.md` の「ルート直下許可ディレクトリ」節へ `project-setup` の追記が必要になる。
6. 移設で落ちる自己テストが3本という記述は誤りである。範囲を広げた調査で、先行調査が挙げた3本を確認した。対象は次の3本である。

   - `scaffold-rule-definitions.sh --self-test`
   - `build-portal.sh` の test18（1595〜1596行）
   - `check-coverage.sh --self-test`（203〜204行）

   3本とも `SCRIPT_DIR` 起点の相対パスで完結しており、破綻を再現できなかった。落ちる検査の本数は、移設の方法が決まるまで確定できない。

7. 移設対象の総数は101件である。先行調査は規約まわりの5資産だけを対象にしており、`delivery-payload/templates/リバース検証/` の雛形36件は範囲外だった。2026-08-14時点の実測では、移設対象の総数は101件だった。内訳は次のとおりである。

   | 区分 | 件数 |
   |---|---|
   | `delivery-payload/templates/` | 95件（うち `リバース検証/` の雛形36件を含む） |
   | `delivery-payload/references/` | 3件（`unit-axes.json`・`portal-catalog.json`・`rule-taxonomy.json`） |
   | `generation-engine/scripts/`（`deploy_rule_scripts()` 経由で配られる分） | 3件 |
   | `generation-engine/samples/`・`samples-no-screen/`・`schemas/` | 0件 |

   配られないファイルは558件である。

8. 移設で追従が必要な参照は929箇所である。ファイル数は108件である。上位3件は次のとおりである。

   - `generation-engine/scripts/extract/build-matrix-data.sh`（75箇所）
   - `generation-engine/scripts/matrix/build-matrix-pages.sh`（60箇所）
   - `generation-engine/scripts/verification/run-layer-full-pipeline.sh`（56箇所）

9. `.claude/skills/` 配下のスキル群は、固定の3階層上向きの参照 `../../../shared/...` を216箇所・45ファイル持つ。これは、配られる101件への参照とは性質が異なる。生成エンジンそのものへの依存である。`shared/` だけを動かしてスキルを動かさない場合、この216箇所がすべて機能しなくなる。

## 着手前に必要な調査

先行調査は規約まわりの5資産のみを対象とした。2026-08-14時点で、範囲を `shared/` 全体へ広げた実測を完了した。判定は「そのファイルを読む生成器を特定し、その生成器の書き出し先を実装から確認する」方法で行った。名前や置き場からの推測はしていない。

完了した項目は次のとおりである。

- `delivery-payload/templates/`・`delivery-payload/references/`・`generation-engine/scripts/` について。納品先へ配られるかを判定した。`generation-engine/samples/`・`generation-engine/samples-no-screen/`・`generation-engine/schemas/` についても同じ判定をした（前節の7を参照する）。
- 移設で追従が必要な参照の全件と、`.claude/skills/` 配下の固定参照の全件を数えた（前節の8・9を参照する）。

未完了の項目は次のとおりである。

- 移設の方法の確定後に、落ちる自己テストの全件を数えること。

## 移設の方法を先に決める必要がある

移設には、少なくとも2つの方法がある。影響範囲が大きく異なる。

### 方法A: 配られる101件だけを動かす

`project-setup/` へ、配られる101件だけを動かす。生成器（`generation-engine/scripts/`）は元の場所に残る。

追従が必要な参照は、生成器から雛形への929箇所である。`.claude/skills/` からの216箇所は、影響を受けない。

### 方法B: `shared/` を丸ごと動かす

`shared/` を丸ごと `project-setup/` の下へ動かす。

配られる側と配られない側が、混在したまま移る。`.claude/skills/` からの216箇所が、すべて壊れる。

### 判定の基準は名前に出ない

方法Aは、判定の基準（配られるか）が名前に出る。ただし、区分の中に配られる側と配られない側が混在している。区分ごとに、ファイル単位で仕分ける必要がある。

たとえば `delivery-payload/templates/rules/` は29件である。27件が配られ、2件が配られない。

どちらの方法を採るかは、本構想では決めない。決めるには、配られない側の置き場をどうするかの判断が要る。

## 実施の順序

1. 移設の方法（方法Aまたは方法B）を決め、`project-setup/` の内部構造を確定する。
2. ルート直下の許可リストへ `project-setup` を追記する。
3. ファイルを移設する。
4. 参照を追従させる。方法Aの場合は929箇所、方法Bの場合はこれに216箇所を加えた件数が対象になる。
5. 移設の方法確定後に判明する自己テストを、全項目 PASS にする。
6. 公開同期の3箇所を同時に更新する。
7. 納品物の目録を実体から生成する形へ変える。手書きの目録は実体とずれるためである。
