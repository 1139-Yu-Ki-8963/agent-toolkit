## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書 |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書（本書） |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## §1 テスト観点

**この節の位置づけ: 仕様**

§1は正常・異常・境界を含む全観点の一覧です。
§5と§6は、§1のうち異常と境界の観点を列ごとに詳しく述べる部分集合です。
§5と§6では新しい観点キーを作らず、§1と同じ観点キーを使います。
実行する全ケースは§2だけに記載し、§1の全観点へ1件以上のケースを対応させます。
実行するテストの件数は§2のデータ行数だけで数えます。

観点は機能設計書の業務フロー・業務ルール・エラーと業務メッセージの各章から起こす。

| キー | 観点 | 由来する機能設計書の章 |
|---|---|---|
| 共通文書-層化サンプリング完了後書き起こし | 層化サンプリングが完了してから共通文書の書き起こしへ進むこと | §3.1 |
| 共通文書-機械ゲート不合格時のPhase3差し戻し | 機械ゲート不合格時にPhase 3へ差し戻り上限5回で収束を試みること | §3.2、§8.1 |
| 共通文書-追記モードの分岐 | `mode=append`でNG帰着(c)の指摘文書だけを追記し全ゲートを再実行すること | §3.2 |
| 要件定義-一覧マニフェストなし時のfallback | 対象種別の一覧マニフェストが無い場合に該当なし記録で代替すること | §3.2 |
| 要件定義-個別基本設計書・未生成時の空欄記録 | 個別基本設計書が未生成のユニットの列を空欄のまま要確認事項一覧へ回すこと | §3.2、§4.1 |
| 出力先共有-commonRoot経由の連携 | 共通文書と要件定義文書が同じcommonRoot配下へ出力され共存すること | §6.2 |
| 要件定義-業務の意図の要確認事項一覧への集約 | 業務の意図を必ず要確認事項一覧へ回すこと | §4.1 |

## §4 期待結果

**この節の位置づけ: 仕様**

| ケースのキー | 期待する結果 | 確認の方法 |
|---|---|---|
| case-common-sampling-order | サンプル記録.mdに全層の選定コマンドと選定ファイル一覧が記録される | `test -f サンプル記録.md` とファイル内の層数を数える |
| case-common-gate-retry | Phase 3へ差し戻り、上限5回以内に`check-common-docs.sh`が`exit 0`を返す | 再実行ログの回数と終了コードを確認する |
| case-common-append-mode | 指摘文書だけが更新され、全ゲートが再実行される | 差分の対象ファイルと機械ゲートの実行ログを確認する |
| case-req-manifest-absent | `<label>一覧（該当なし）.md`が代替として扱われ、当該文書はスキップ対象と記録される | 生成された成果物一覧を確認する |
| case-req-basic-design-absent | 該当列が空欄のまま残り、要確認事項一覧に「個別基本設計書が未生成」の行が追加される | 出力ファイルの該当列と要確認事項一覧を確認する |
| case-shared-output-root | commonRoot配下に両構成要素の出力ファイルが共存する | `ls <output_dir>/<commonRoot>/` で7＋5ファイルの実在を確認する |
| case-req-intent-to-open-items | §2の観測列を移した後、要確認事項一覧の行数がユニット数以上になる | 出力ファイルの要確認事項一覧の行数を数える |

## §5 異常系

**この節の位置づけ: 仕様**

| 観点のキー | 発生させる条件 | 期待する振る舞い | 由来する機能設計書の章 |
|---|---|---|---|
| 共通文書-機械ゲート不合格時のPhase3差し戻し | `check-common-docs.sh`が対象コード位置の混入を検出する | Phase 3へ差し戻り上限5回で再試行し、収束しなければ`status=中断`とする | §8.1 |
| 共通文書-追記モードの分岐 | Phase 7判定がNG帰着(c)を返す | `mode=append`の別起動で指摘文書だけを追記し全ゲートを再実行する | §3.2 |
| 要件定義-一覧マニフェストなし時のfallback | 対象種別の一覧マニフェストが実在しない | `<label>一覧（該当なし）.md`の実在を確認し「該当なし」と判定する | §3.2 |

## §6 境界値

**この節の位置づけ: 仕様**

| 観点のキー | 対象の項目 | 境界の値 | 境界の直前と直後の扱い |
|---|---|---|---|
| 要件定義-個別基本設計書・未生成時の空欄記録 | 個別基本設計書の実在 | 実在する／実在しない | 実在すれば該当列を記入し`status=traced`の対象に含める。実在しなければ列を空欄のまま残し`status=draft`のまま維持する |

## §7 網羅基準

**この節の位置づけ: 仕様**

| 観点 | 基準 |
|---|---|
| 条件の網羅 | §3業務フローの分岐（追記モード・一覧マニフェストなし・個別基本設計書・未生成）をすべて1件以上のケースで確認する。 |
| 分岐の網羅 | 共通文書のPhase 1〜5、要件定義のPhase 1〜4のいずれの分岐も1件以上のケースで確認する。 |
| 境界の網羅 | 個別基本設計書の実在／不在という唯一の境界を確認する。 |

## §8 前提条件と終了条件

**この節の位置づけ: 仕様**

| 区分 | 内容 |
|---|---|
| 実行の前提条件 | アーキテクチャ調査書が確定済みであること（共通文書）。一覧マニフェストまたは該当なし記録が判定可能な状態にあること（要件定義）。 |
| 終了の条件 | 共通文書は`status`が`採録v0確定`／`追記完了`／`中断`のいずれかに確定していること。要件定義は対象文書ごとに`status`が`draft`／`traced`に確定していること。 |
