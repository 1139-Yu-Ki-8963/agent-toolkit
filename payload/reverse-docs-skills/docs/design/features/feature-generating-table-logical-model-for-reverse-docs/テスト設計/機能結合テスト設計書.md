## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書 |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書（本書） |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## §1 テスト観点

**この節の位置づけ: 仕様**

観点は機能設計書の業務フロー・業務ルール・エラーと業務メッセージの各章から起こす。

| キー | 観点 | 由来する機能設計書の章 |
|---|---|---|
| 正常執筆完了 | 4引数が実在するとき、Phase1〜5が完走し論理データモデル等が生成される | §3.1 正常系フロー |
| 記述区分の要確認振り分け | 判断基準と業務背景に当たる記述が本文へ書かれず要確認事項一覧へ移る | §3.2 分岐と例外フロー |
| 業務語彙違反差し戻し | 実装用語・内部識別子が検出されたときPhase3へ差し戻される | §3.2 分岐と例外フロー、§4.1 業務判断ポイント |
| 識別子不確定エラー | unitId・unitKeyが両方空のとき生成せずstatus=ERRORになる | §8.1 業務エラー一覧 |
| 検査未収束エラー | Phase5の差し戻しが上限3回に達しても収束しないとき、status=ERRORになる | §8.1 業務エラー一覧 |
| status遷移 | 記入完了に伴いstatusがdraftからauthoredへ更新される | §4.2 状態と遷移の制約 |

## §3 入力条件

**この節の位置づけ: 仕様**

| ケースのキー | 入力の項目 | 値 |
|---|---|---|
| 正常執筆完了 | table_manifest_path・source_dir・output_dir・template_root | いずれも実在するパス |
| 記述区分の要確認振り分け | 原本コードの記述 | 保存期間の根拠のような判断基準を含む記述 |

| status遷移 | 対象ユニットのfrontmatter | status=draftの初期状態 |

## §4 期待結果

**この節の位置づけ: 仕様**

| ケースのキー | 期待する結果 | 確認の方法 |
|---|---|---|
| 正常執筆完了 | 論理データモデル・テーブル結合/単体テスト設計書が生成される | `scaffold-design-unit.sh --verify table basic/test`の終了コードが0であることを確認する |
| 記述区分の要確認振り分け | 判断基準を伴う記述が本文になく要確認事項一覧に記録される | 要確認事項一覧の件数が0件でないことを確認する |
| 業務語彙違反差し戻し | 検査1が不合格になりPhase3で書き直される | grep検査の検出件数が0件になるまで差し戻されることを確認する |
| 識別子不確定エラー | 当該ユニットが生成されずstatus=ERRORになる | 返却のhintに識別子不確定の旨が記録されることを確認する |
| 検査未収束エラー | 3回目の差し戻し後もstatus=ERRORのままである | 返却のstatusを確認する |
| status遷移 | frontmatterのstatusがauthoredになる | 生成ファイルのstatus欄を確認する |
