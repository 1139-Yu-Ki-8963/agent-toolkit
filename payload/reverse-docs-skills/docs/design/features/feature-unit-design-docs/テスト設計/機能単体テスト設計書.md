本書は関数・メソッド単位の内部処理を検証します。観点と具体的なケースを分けず、1文書で管理します。対応する設計書は `機能設計書.md` です。

## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書（本書） |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書 |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## テスト対象

対象は関数・メソッド単位の内部処理とする。

## テストの粒度と自動化の方針

反復可能なケースは自動化し、実装後のテスト参照をケースに記録する。単位配下へ結合テスト文書を生成しない。

## 本書が扱わない範囲

複数の画面・機能・APIにまたがる結合テストはプロジェクト全体の `docs/test-cases/結合テスト仕様書.md` が担う。操作の流れそのものは画面固有の操作シナリオ仕様書.mdが担い、それ以外の種別では生成しない。

### 根拠

以後、`.claude/skills/generating-feature-design-for-reverse-docs/SKILL.md` を（対象: feature-skill）と表記する。feature-skill のPhase 1〜5は、このスキル自身のPhase/Step手順（orchestration）を定義するものです。関数・メソッド単位の内部実装ではない。構成要素13スキルも同様に、対象アプリケーションの画面・接続窓口・テーブル等とは異なり、SKILL.md自体がPhase/Step手順の定義であって、独自の関数・メソッド単位の詳細設計書を持たない。

13スキルが共有する内部処理（機能設計書§7.1参照）は、`generation-engine/scripts/`配下のシェルスクリプトです。内訳は、`scaffold-design-unit.sh`・`scaffold-screen.sh`・`check-fact-coverage.sh`の3本です。加えて `delivery-payload/templates/rules/checkers/check-unit-test-design-doc-sections.sh` もある。これらは対象アプリケーションの構成要素ではなく、このツール自身の生成エンジンです。そのため `docs/design/`配下に個別の詳細設計書を持ちません。`.claude/rules/scoped/portal/page-conventions/rule.md`の「設計判断」節が各スクリプトの存在理由を記録する形式です。機能・関数単位の詳細設計書ではありません。関数単位の検証は、これら共有スクリプトが将来`docs/design/`配下の設計単位として書き起こされた段階で、本書へ追記する。
