## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書（本書） |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書 |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## テスト対象

以後、`delivery-payload/templates/delivered-skills/` を（対象: skills-dir）と表記する。対象は skills-dir 配下の `resolving-confirmation-items/scripts/apply-confirmation-answers.mjs` にある関数です。関数は `validateLedger`・`findHeadingRange`・`findTable`・`applyAnswers`・`assertConsistency` です。加えて `generation-engine/scripts/check-confirmation-ledger.mjs` の `validateLedgerShape` も対象とする。`build-confirmation-survey-data.sh` は bash の決定的な導出処理です。関数・メソッド単位の詳細設計を持ちません。design-unit-layout.json の feature.phases.detail は空のため、対象から除く。同スクリプトの外部の振る舞いは機能結合テスト設計書が担う。

## テストの粒度と自動化の方針

反復可能なケースは自動化し、実装後のテスト参照をケースに記録する。単位配下へ結合テスト文書を生成しない。本書のケースの一部は既に自動化済みです。自動化の担当は2つです。1つは `apply-confirmation-answers.mjs --self-test` です。もう1つは `check-confirmation-ledger.mjs`（node標準のテストランナー経由）です。

## 本書が扱わない範囲

複数の画面・機能・APIにまたがる結合テストはプロジェクト全体の `docs/test-cases/結合テスト仕様書.md` が担う。`build-confirmation-survey-data.sh` の外部の振る舞いは機能結合テスト設計書が担う。

## §4 期待結果

**この節の位置づけ: 仕様**

期待結果は観測可能な値・状態・表示で記載する。ledger-shape-okは例外を投げず正常終了する。ledger-shape-missing-fieldからledger-shape-check-status-invalidまでの各ケースは`Error`を投げる。投げるメッセージは、次の9種類のいずれかです。「8項目だけを持つ必要があります」「回答が空です」「未回答状態ですが回答または回答日を持っています」「反映先の節が見つかりません」「反映先のセルが見つかりません」です。「台帳でキーが重複」「回答済みのまま未反映」「反映済みの本文セルが回答と不一致」「status が許可値ではありません」です。heading-range-foundは`{ start, end }`を返し実際の見出し位置と一致する。table-cell-foundは`{ rowIndex, columnIndex, cells }`を返す。apply-write-answered-onlyは戻り値のMarkdownで回答済み2件のセルが書き換わり、items中の該当2件のstatusが「反映済み」に変わる。

## §5 異常系

**この節の位置づけ: 仕様**

| 観点のキー | 条件 | 期待結果 |
|---|---|---|
| ledger-shape | items要素が8項目の完全一致を満たさない | `validateLedger`が例外を投げる |
| ledger-status-consistency | 状態と回答・回答日の有無が矛盾する | `validateLedger`が例外を投げる |
| heading-range | target.sectionと一致する見出しが本文に無い | `findHeadingRange`が例外を投げる |
| table-cell | 見出し範囲内にtarget.rowKey・target.columnと一致する行/列が無い | `findTable`が例外を投げる |
| consistency-duplicate | 台帳内でkeyが重複する | `assertConsistency`が例外を投げる |
| consistency-unreflected | statusが回答済みのまま本文へ未反映の行が残る | `assertConsistency`が例外を投げる |
| consistency-mismatch | 反映済みの本文セルの値が回答と一致しない、または特定できない | `assertConsistency`が例外を投げる |
| ledger-shape-check | statusが許可値5種のいずれでもない | `validateLedgerShape`が例外を投げる |

## §6 境界値

**この節の位置づけ: 仕様**

| 観点のキー | 境界 | 期待結果 |
|---|---|---|
| ledger-shape | items要素が持つ項目数が8項目（7項目・9項目との境界） | 8項目ちょうどなら合格、1項目でも過不足があれば「8項目だけを持つ必要があります」で不合格とする |
| heading-range | 見出しレベル（`#`の数）が対象見出しと同じか、それ以下のレベルの見出しが後続に現れる位置 | 同じか浅いレベルの見出しが現れた時点で範囲を打ち切り、深いレベルの見出しは範囲内に含める |

## §7 網羅基準

**この節の位置づけ: 仕様**

設計書に定義された分岐・状態・制約をすべて観点へ対応付ける。apply-confirmation-answers.mjsは5関数を持つ。関数は validateLedger・findHeadingRange・findTable・applyAnswers・assertConsistency です。これらが持つ判定条件を、§2のケースがすべて1件以上カバーする。check-confirmation-ledger.mjsの1関数（validateLedgerShape）が持つ判定条件も、§2のケースがすべて1件以上カバーする。
