## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書 |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書（本書） |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## テスト対象

| 対象 | 確認する内容 | 根拠となる機能設計書の章 |
|---|---|---|
| screen-list・api-list・table-list・batch-list・report-list・external-list（6種別ループ） | 対象種別のみを対話並列・headless逐次で起動し、各構成要素がstatus=DONE（一覧HTML確定）またはstatus=NONE（該当なし文書確定）で完了すること | §3.1、§9.3 |

## §1 テスト観点

**この節の位置づけ: 仕様**

§1は正常・異常・境界を含む全観点の一覧です。
§5と§6は、§1のうち異常と境界の観点を列ごとに詳しく述べる部分集合です。
§5と§6では新しい観点キーを作らず、§1と同じ観点キーを使います。
実行する全ケースは§2だけに記載し、§1の全観点へ1件以上のケースを対応させます。
実行するテストの件数は§2のデータ行数だけで数えます。

観点は機能設計書の業務フロー・業務ルール・エラーと業務メッセージの各章から起こす。

| キー | 観点 | 由来する機能設計書の章 |
|---|---|---|
| 6種別ループ-対象種別のみ起動 | 承認済みexcluded-kinds.jsonのpresentKindsに含まれる種別だけが起動され、対話モードは並列、headlessは逐次で実行されること | §3.1、§4.1、§9.3 |
| 該当なしと検出失敗の区別 | アーキテクチャ調査書が不在を判定済みの種別はstatus=NONE、実在を認めているのに検出0件が続く種別はstatus=ERRORで停止すること | §3.2、§4.1、§4.2、§8.1 |
| feature-list起動条件 | raw画面定義の実在を条件にfeature-listが起動し、未確定なら見送られて画面一覧の定義確立後に再実行されること | §3.1、§3.2、§4.1、§4.2 |
| message-list起動条件 | メッセージ定義書.mdの実在を条件にmessage-listが起動し、不在ならstatus=STOPPEDでメッセージ一覧を生成しないこと | §3.1、§3.2、§4.1、§4.2、§8.1 |
| 整合検証不合格での差し戻し | validate-manifest.sh／validate-message-manifest.shが1項目でも不合格ならHTML生成へ進まず抽出フェーズへ差し戻され、修正ループが3回以内であること | §3.2、§8.1、§9.1 |
| 固定と可変の分離の徹底 | 抽出（検出戦略・境界判定）は種別ごとに可変な判断とし、整合検証とHTML生成は決定的スクリプト（build-unit-list.sh・validate-manifest.sh等）に固定されること | §4.1、§10.1 |
| 種別横断の一巡完了 | 全対象種別がDONEまたはNONEで確定した後に呼び出し元が次工程（横断ビュー・ポータルの製造等）へ進むこと | §3.1、§3.3 |

## §2 テストケース一覧

## §3 入力条件

**この節の位置づけ: 仕様**

| ケースのキー | 入力の項目 | 値 |
|---|---|---|
| case-loop-present-kinds-only | 承認済みexcluded-kinds.json | presentKindsに一部種別のみを含む状態 |
| case-none-vs-error | アーキテクチャ調査書の実在判定と、対象種別の原本コード | 一方は実在なし、もう一方は実在ありなのに検出0件のパターンを1件ずつ含む |
| case-feature-list-gated-by-screen-manifest | `<output_dir>/<manifestsRoot>/screen-manifest.json` | 未確定の状態と確定済みの状態の2パターン |
| case-message-list-gated-by-doc | `<output_dir>/<commonRoot>/メッセージ定義書.md` | 不在の状態と実在する状態の2パターン |
| case-validation-failure-rollback | 検出戦略が確定したraw manifest | validate-manifest.shが不合格を返すよう意図的にスキーマ不整合にした値 |
| case-fixed-vs-variable-boundary | 検出戦略の宣言（Phase 1）と、build-unit-list.sh／validate-manifest.shの呼び出し | 抽出パスは種別ごとのカスタム判断、検証・生成は共通スクリプトの呼び出し |
| case-full-loop-completion | 対象種別全件のPhase 1からPhase 4までの実行結果 | 全件がDONEまたはNONEに確定した状態 |

## §4 期待結果

**この節の位置づけ: 仕様**

| ケースのキー | 期待する結果 | 確認の方法 |
|---|---|---|
| case-loop-present-kinds-only | excluded-kinds.jsonに記載の無い種別は起動されず、presentKindsの種別だけが起動される | 起動されたスキルの一覧とpresentKindsを突合する |
| case-none-vs-error | 実在なしの種別は`<種別>一覧（該当なし）.md`を生成しstatus=NONEを返し、検出失敗の種別は停止してstatus=ERRORを返す | 各スキルの返却status値と生成物の有無を確認する |
| case-feature-list-gated-by-screen-manifest | screen-manifest.json未確定時はfeature-listが起動されず、確定後に再実行すると起動される | feature-listの呼び出しの有無を確認する |
| case-message-list-gated-by-doc | メッセージ定義書.md不在時はmessage-listがstatus=STOPPEDを返し、実在時はstatus=DONEで一覧HTMLを生成する | message-listの返却status値と生成物の有無を確認する |
| case-validation-failure-rollback | 不合格を検知しHTML生成が実行されず、抽出フェーズへ差し戻されて修正ループが3回以内で収束する | validate-manifest.shの終了コードと差し戻し回数を確認する |
| case-fixed-vs-variable-boundary | 抽出戦略の宣言内容が種別ごとに異なる一方、検証・生成スクリプトの呼び出し方は全種別で同一である | 各構成要素のPhase 1宣言内容とPhase 3・Phase 4のスクリプト呼び出しを比較する |
| case-full-loop-completion | 全対象種別のstatusがDONEまたはNONEに確定し、呼び出し元が次工程へ進む旨を確認できる | 全構成要素の返却status値を集計する |

## §5 異常系

**この節の位置づけ: 仕様**

| 観点のキー | 発生させる条件 | 期待する振る舞い | 由来する機能設計書の章 |
|---|---|---|---|
| 該当なしと検出失敗の区別 | アーキテクチャ調査書が実在を認めているのに検出0件が続く | 停止し、headless=falseならAskUserQuestion、headless=trueなら`progress.jsonl`へ記録してstatus=ERRORを返す | §3.2、§8.1 |
| message-list起動条件 | メッセージ定義書.mdが存在しない状態でmessage-listを起動する | status=STOPPEDを返し、メッセージ一覧を生成しない | §3.2、§4.2、§8.1 |

## §6 境界値

**この節の位置づけ: 仕様**

| 観点のキー | 対象の項目 | 境界の値 | 境界の直前と直後の扱い |
|---|---|---|---|
| 該当なしと検出失敗の区別 | 検出したユニットの件数 | 0件／1件以上 | 0件かつ調査書が不在を判定済みならNONE。0件かつ調査書が実在を認めていればERROR。1件以上ならDONEへ進む |
| 整合検証不合格での差し戻し | 修正ループの回数 | 3回以内／3回超過 | 3回以内に合格すればHTML生成へ進む。3回を超えて合格しない場合の扱いは各構成要素SKILL.mdの完了条件が定める上限に従う |
