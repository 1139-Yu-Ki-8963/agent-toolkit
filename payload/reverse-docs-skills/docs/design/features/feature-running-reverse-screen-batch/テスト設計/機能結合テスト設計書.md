## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書 |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書（本書） |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## テスト対象

| 対象 | 確認する内容 | 根拠となる機能設計書の章 |
|---|---|---|
| Phase 1〜5の一連の流れ | 引数検証→単発ドライラン→無人ループ起動→監視→完了報告が意図した順序で完走すること | §3 業務フロー |

## §1 テスト観点

**この節の位置づけ: 仕様**

観点は機能設計書の業務フロー・業務ルール・エラーと業務メッセージの各章から起こす。

| キー | 観点 | 由来する機能設計書の章 |
|---|---|---|
| 正常一括完了 | 引数が有効なとき、Phase1〜5が完走し全画面が検証完了する | §3.1 正常系フロー |
| docs-only終端 | verification_mode=docs-onlyのとき、前半のみでSTATIC_COMPLETEとなり動的工程を起動しない | §3.2 分岐と例外フロー |
| limit待機再開 | 出力にlimit文言を検知したとき、待機後に再開し失敗カウントに数えない | §3.2 分岐と例外フロー |
| 開通競合スキップ | CONFLICT-SKIPPEDを受けたとき、失敗とは別区分でconflict-skipリストへ記録される | §3.2 分岐と例外フロー |
| 時限到達ソフト停止 | deadline超過時、新規着手を停止するが実行中の呼び出しは中断しない | §3.2 分岐と例外フロー、§9.1 件数と量の制限 |
| 引数不正即終了 | 必須引数が欠落または参照先パスが不在のとき、エラーメッセージを返して即終了する | §8.1 業務エラー一覧 |

## §4 期待結果

**この節の位置づけ: 仕様**

| ケースのキー | 期待する結果 | 確認の方法 |
|---|---|---|
| 正常一括完了 | 全画面が検証完了しfailed/conflict-skip分を除いて残ゼロになる | 完了報告の残件数を確認する |
| docs-only終端 | STATIC_COMPLETEが確定し動的工程が起動されない | 実行記録に後半未実行の記載があることを確認する |
| limit待機再開 | wait_seconds秒後に同一画面が再試行される | ログのタイムスタンプ差を確認する |
| 開通競合スキップ | 当該画面がconflict-skipリストへ記録され次画面へ進む | conflict-skip-screens-<lane_id>.txtの内容を確認する |
| 時限到達ソフト停止 | 新規着手が停止し完了報告に締切時刻と仕掛り画面が記載される | 完了報告の記載内容を確認する |
| 引数不正即終了 | エラーメッセージを返して即終了する | 返却のエラーメッセージを確認する |

## §7 網羅基準

**この節の位置づけ: 仕様**

| 観点 | 基準 |
|---|---|
| 条件の網羅 | docs-only・single-pass・iterativeの3つのverification_modeを1件以上のケースで確認する |
| 分岐の網羅 | 成功・limit待機・競合スキップ・失敗退避の4分岐を1件以上のケースで確認する |
