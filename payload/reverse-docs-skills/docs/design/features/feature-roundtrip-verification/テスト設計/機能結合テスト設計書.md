## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書 |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書（本書） |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## テスト対象

| 対象 | 確認する内容 | 根拠となる機能設計書の章 |
|---|---|---|
| unlock → setup → file verify → baseline sync → implement → compare → judge の依存順の連鎖 | 5構成要素が正しい順序で呼び出され、前段の出力（env_block・compare_result等）が後段へ正しく渡ること | 機能設計書 §3.1・§6.1 |
| 画面数によるバッチ委譲判定 | 対象画面が4件以上のときrunning-reverse-screen-batchへ委譲され、3件以下のとき逐次仲介されること | 機能設計書 §3.1・§4.1 |
| 画面レジストリ・基準タグを介した状態共有 | 複数の構成要素が画面レジストリ・基準タグ・worktreeを介して状態を正しく共有すること | 機能設計書 §6.2 |

機能設計書で確定した範囲だけを記入する。対象外の構成要素は「本書が扱わない範囲」に記録する。

## テストの粒度と自動化の方針

| 項目 | 方針 |
|---|---|
| テストの粒度 | 1ケースで、Phase 単位の1つの分岐または1つの受け渡しを確認する。 |

## §1 テスト観点

**この節の位置づけ: 仕様**

§1は正常・異常・境界を含む全観点の一覧です。
§5と§6は、§1のうち異常と境界の観点を列ごとに詳しく述べる部分集合です。
§5と§6では新しい観点キーを作らず、§1と同じ観点キーを使います。
実行する全ケースは§2だけに記載し、§1の全観点へ1件以上のケースを対応させます。
実行するテストの件数は§2のデータ行数だけで数えます。

観点は機能設計書の業務フロー・業務ルール・エラーと業務メッセージの各章から起こす。

| キー | 観点 | 由来する機能設計書の章 |
|---|---|---|
| unlock-setup-verify連鎖 | unlocking-reverse-target-screens → syncing-reverse-env(setup) → rebuilding-screen-unit-from-docs の順に、開通結果とenv_blockが正しく受け渡される | 機能設計書 §3.1・§6.1 |
| baseline-implement-compare連鎖 | syncing-reverse-env(baseline sync) → rebuilding-code-from-docs(implement) → syncing-reverse-env(compare) の順に、基準タグとcompare_requestが正しく受け渡される | 機能設計書 §3.1・§6.1 |
| judge後の基準タグ更新 | rebuilding-code-from-docs(judge)がPASSした場合、承認を求めずsyncing-reverse-env(mode=sync)で基準タグが本番更新される | 機能設計書 §3.1・§3.2 |
| 画面数によるバッチ委譲分岐 | 対象画面が4件以上かどうかで、running-reverse-screen-batchへの委譲と逐次仲介が正しく分岐する | 機能設計書 §3.1・§4.1 |
| 開通競合とNG帰着の伝播 | unlocking-reverse-target-screensのCONFLICT-SKIPPED、rebuilding-code-from-docsのNG帰着3系統が、それぞれ機能全体の停止・差し戻しへ正しく伝播する | 機能設計書 §3.2・§8.1 |
