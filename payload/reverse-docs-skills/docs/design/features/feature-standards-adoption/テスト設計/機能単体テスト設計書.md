本書は関数・メソッド単位の内部処理を検証します。観点と具体的なケースを分けず、1文書で管理します。対応する設計書は `機能設計書.md` です。

## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書（本書） |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書 |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## テスト対象

対象は次の2つです。参照先の起点は `docs/rules/agent-operations/ai-config-asset-management/`（以後、rules-dir と表記する）です。1つは rules-dir の `validate-rule-definitions.sh` にある `validate_one_rule` です。もう1つは rules-dir の `check-rule-drift.sh` にある `cmd_check` です。build-rule-proposal.shとbuild-derived-rules.shは、それぞれHTML生成・派生一括生成という決定的な変換処理であり、本機能の詳細設計を持たない。design-unit-layout.json の feature.phases.detail は空のため、対象から除く。これらの外部の振る舞いは機能結合テスト設計書が担う。

## テストの粒度と自動化の方針

反復可能なケースは自動化し、実装後のテスト参照をケースに記録する。単位配下へ結合テスト文書を生成しない。`validate-rule-definitions.sh --self-test`・`check-rule-drift.sh --self-test` が本書のケースの一部を既に自動化済みです。

## 本書が扱わない範囲

複数の画面・機能・APIにまたがる結合テストはプロジェクト全体の `docs/test-cases/結合テスト仕様書.md` が担う。build-rule-proposal.sh・build-derived-rules.shの外部の振る舞いは機能結合テスト設計書が担う。

## §1 テスト観点

**この節の位置づけ: 仕様**

§1は正常・異常・境界を含む全観点の一覧です。
§5と§6は、§1のうち異常と境界の観点を列ごとに詳しく述べる部分集合です。
§5と§6では新しい観点キーを作らず、§1と同じ観点キーを使います。
実行する全ケースは§2だけに記載し、§1の全観点へ1件以上のケースを対応させます。
実行するテストの件数は§2のデータ行数だけで数えます。

| キー | 観点 | 由来する基本設計書の章 | 由来する詳細設計書の章 |
|---|---|---|---|
| frontmatter-parse | 先頭行が`---`でないfront matterを認識できないと判定する | §8.1 業務エラー一覧 | 該当なし |
| key-duplicate | front matterの鍵が重複していると判定する | §5.1 業務対象の定義 | 該当なし |
| key-missing | 必須14鍵のいずれかが欠落していると判定する | §5.1 業務対象の定義 | 該当なし |
| key-extra | 必須14鍵にない余分な鍵があると判定する | §5.1 業務対象の定義 | 該当なし |
| drift-build-fail | 定義からの一時再生成（build-derived-rules.sh --apply）自体が失敗したら判定不能として扱う | §8.1 業務エラー一覧 | 該当なし |
| drift-modified | 生成物と現物の内容が一致しないファイルをMODIFIEDとして検出する | §8.1 業務エラー一覧 | 該当なし |
| drift-deleted | 定義からは生成されるはずだが現物に無いファイルをDELETEDとして検出する | §8.1 業務エラー一覧 | 該当なし |
| drift-added | 現物にはあるが定義からの生成物に無いファイルをADDEDとして検出する | §8.1 業務エラー一覧 | 該当なし |

## §4 期待結果

**この節の位置づけ: 仕様**

期待結果は観測可能な値・状態・表示で記載する。frontmatter-parse-badは`add_failure`が「front-matter形式」区分で記録され以後の検査をせずreturnする。key-duplicate-hitは「front-matter鍵-重複」区分で記録される。key-missing-hitは「front-matter鍵-欠落」区分で記録される。key-extra-hitは余分な鍵として不合格が記録される。drift-build-fail-caseは標準エラーへ`ERROR: build-derived-rules.sh --apply が失敗した`が出力され終了コード2を返す。drift-modified-caseは標準出力へ`MODIFIED: <相対パス>`が出力され終了コード1を返す。drift-deleted-caseは`DELETED: <相対パス>`を出力し終了コード1を返す。drift-added-caseは`ADDED: <相対パス>`を出力し終了コード1を返す。drift-clean-caseは`CLEAN: 定義からの再生成と一致（ずれなし）`を出力し終了コード0を返す。

## §5 異常系

**この節の位置づけ: 仕様**

| 観点のキー | 条件 | 期待結果 |
|---|---|---|
| frontmatter-parse | rule.mdの先頭行が`---`でない | `validate_one_rule`が不合格を記録し以後の検査を打ち切る |
| key-duplicate | front matterに同じ鍵が複数回現れる | `validate_one_rule`が不合格を記録する |
| key-missing | 必須14鍵のいずれかが無い | `validate_one_rule`が不合格を記録する |
| drift-build-fail | 一時ディレクトリへの再生成自体が失敗する | `cmd_check`が終了コード2で判定不能として終わる |
| drift-modified | 生成物と現物の内容がバイト単位で一致しない | `cmd_check`がMODIFIEDとして検出する |
| drift-deleted | 生成されるはずのファイルが現物に無い | `cmd_check`がDELETEDとして検出する |
| drift-added | 定義に対応しないファイルが現物にある | `cmd_check`がADDEDとして検出する |

## §6 境界値

**この節の位置づけ: 仕様**

| 観点のキー | 境界 | 期待結果 |
|---|---|---|
| key-missing | front matterが持つ必須鍵の充足数が14鍵（13鍵との境界） | 14鍵すべて揃えば合格、1鍵でも欠ければ不合格として記録する |
| drift-modified | 生成物と現物のdiff一致がバイト単位の完全一致（1バイトでも異なる境界） | 完全一致なら合格、1バイトでも異なればMODIFIEDとして検出する |

## §7 網羅基準

**この節の位置づけ: 仕様**

設計書に定義された分岐・状態・制約をすべて観点へ対応付ける。`validate_one_rule`は4つの個別検査（frontmatter-parse・key-duplicate・key-missing・key-extra）を持つ。`cmd_check`は5つの判定（drift-build-fail・drift-modified・drift-deleted・drift-added・drift-clean）を持つ。この合計9観点を、§2のケースがすべて1件以上カバーする。

**この節の位置づけ: 仕様**
