## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書 |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書（本書） |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## §1 テスト観点

**この節の位置づけ: 仕様**

§1は正常・異常・境界を含む全観点の一覧です。
§5と§6は、§1のうち異常と境界の観点を列ごとに詳しく述べる部分集合です。
§5と§6では新しい観点キーを作らず、§1と同じ観点キーを使います。
実行する全ケースは§2だけに記載し、§1の全観点へ1件以上のケースを対応させます。
実行するテストの件数は§2のデータ行数だけで数えます。

観点は機能設計書の業務フロー・業務ルール・エラーと業務メッセージの各章から起こす。

| キー | 観点 | 由来する機能設計書の章 |
|---|---|---|
| output-path-outside | output_pathがtarget_repo_pathの外側なら規約提案HTMLを生成する | §3.2 分岐と例外フロー |
| output-path-inside | output_pathがtarget_repo_pathの内側なら生成せず停止する | §3.2 分岐と例外フロー |
| adopt-zero | decisionが全てadopt以外なら正常終了し書き込みを行わない | §3.2 分岐と例外フロー |
| adopt-write | decisionがadoptの要素をstatus: draftで新規書き込みする | §4.2 状態と遷移の制約 |
| protect-approved | 既存rule.mdがorigin: proposalかつstatus: approvedなら上書きしない | §3.2 分岐と例外フロー |
| protect-manual | 既存rule.mdがorigin: manualなら上書きしない | §3.2 分岐と例外フロー |
| line-number-reject | sources・projectRule.根拠に対象コード行番号が混入した要素は書き込まない | §8.1 業務エラー一覧 |
| mode-required | modeが3値のいずれでもなければ停止する | §8.1 業務エラー一覧 |
| draft-excluded | statusがdraftの規約はbuild-derived-rules.shの生成対象から除外される | §4.2 状態と遷移の制約 |
| drift-detected | check-rule-drift.shがMODIFIED/DELETED/ADDEDを検知する | §8.1 業務エラー一覧 |

## §3 入力条件

**この節の位置づけ: 仕様**

| ケースのキー | 入力の項目 | 値 |
|---|---|---|
| output-path-outside | target_repo_path・output_path | output_pathがtarget_repo_pathの外側の絶対パス |

| mode-required | syncing-derived-artifactsの引数 | modeを省略 |
| draft-excluded | docs/rules/の規約定義群 | statusがdraftの規約1件を含む |

## §4 期待結果

**この節の位置づけ: 仕様**

| ケースのキー | 期待する結果 | 確認の方法 |
|---|---|---|
| output-path-outside | 規約提案HTMLが出力先に生成される | 出力先ファイルの実在を確認する |
| output-path-inside | HTMLが生成されず、外側のパスへ変更するよう報告される | 出力先にファイルが無いこと、報告メッセージを確認する |
| adopt-zero | 採用0件・不採用の内訳が報告され、docs/rules/が変更されない | 実行結果とdocs/rules/の差分が無いことを確認する |
| adopt-write | docs/rules/<parent>/<key>/rule.mdがstatus: draftで新規作成される | 生成されたfront matterのstatus値を確認する |
| protect-approved | rule.mdが変更されず、差分が報告される（projectRuleを持つ場合はその節だけ更新される） | rule.mdの内容が変更前と一致することを確認する |
| protect-manual | rule.mdが変更されず、差分が報告される | 同上 |
| line-number-reject | 該当要素が書き込まれず、取り込み前後どちらの混入かが切り分けて報告される | 実行結果と生成されなかったファイルを確認する |
| mode-required | 「指定必須である」旨を返して停止し、書き込みが行われない | 終了コードと出力メッセージを確認する |
| draft-excluded | 生成された派生ファイルにdraftの規約が含まれない。除外件数が報告される | 生成物と`非承認(draft)除外: N件`の出力を確認する |
| drift-detected | check-rule-drift.shの出力にMODIFIEDとして該当ファイルが列挙される | 出力のMODIFIED一覧を確認する |

## §6 境界値

**この節の位置づけ: 仕様**

| 観点のキー | 対象の項目 | 境界の値 | 境界の直前と直後の扱い |
|---|---|---|---|
| adopt-zero | decisionがadoptの要素数 | 0件（1件との境界） | 0件なら正常終了し書き込みなし、1件以上なら書き込みを試みる |
| draft-excluded | 規約定義のstatus | draft（approvedとの境界） | draftなら生成対象から除外、approvedなら生成対象に含める |

## §7 網羅基準

**この節の位置づけ: 仕様**

| 観点 | 基準 |
|---|---|
| 条件の網羅 | §1の全観点キー（10件）に§2で1件以上のケースを対応させる |
