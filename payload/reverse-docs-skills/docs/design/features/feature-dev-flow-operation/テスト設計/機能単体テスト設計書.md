## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書（本書） |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書 |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## テスト対象

対象は `generation-engine/scripts/tests/check-dev-flow-completion.sh` が持つ2つの関数です。関数は `judge_record`・`run_check` です。本機能の他の構成要素（dev-flow SKILL.md の段階運転そのもの）は関数・メソッド単位に分解した詳細設計を持たない。design-unit-layout.json の feature.phases.detail は空のため、対象から除く。段階運転の外部の振る舞いは機能結合テスト設計書が担う。

## テストの粒度と自動化の方針

反復可能なケースは自動化し、実装後のテスト参照をケースに記録する。単位配下へ結合テスト文書を生成しない。`check-dev-flow-completion.sh --self-test` が本書のケースの一部を既に自動化済みです。

## 本書が扱わない範囲

複数の画面・機能・APIにまたがる結合テストはプロジェクト全体の `docs/test-cases/結合テスト仕様書.md` が担う。dev-flow SKILL.md の段階運転・承認ポイント・鮮度追従の外部の振る舞いは機能結合テスト設計書が担う。

## §1 テスト観点

**この節の位置づけ: 仕様**

§1は正常・異常・境界を含む全観点の一覧です。
§5と§6は、§1のうち異常と境界の観点を列ごとに詳しく述べる部分集合です。
§5と§6では新しい観点キーを作らず、§1と同じ観点キーを使います。
実行する全ケースは§2だけに記載し、§1の全観点へ1件以上のケースを対応させます。
実行するテストの件数は§2のデータ行数だけで数えます。

観点は `check-dev-flow-completion.sh` の `judge_record` 関数が持つ7つの個別検査と、`run_check` 関数が持つファイル単位の判定から起こす。

| キー | 観点 | 由来する基本設計書の章 | 由来する詳細設計書の章 |
|---|---|---|---|
| heading-format | 見出し行の先頭がISO8601形式（`### `に続けて年月日と時分秒を書く形式）であるかを判定する | §8.1 業務エラー一覧 | 該当なし |
| request-field | 要求欄が空でなく、プレースホルダ（山括弧で囲んだ形式）でもないかを判定する | §8.1 業務エラー一覧 | 該当なし |
| commit-field | コミット欄が40桁の16進文字列であるかを判定する | §8.1 業務エラー一覧 | 該当なし |
| portal-field | 入口のページ欄が「更新: 40桁16進」または「影響なし: 理由」の形式であるかを判定する | §8.1 業務エラー一覧 | 該当なし |
| impl-body | 実装概要の本文が空でないかを判定する | §8.1 業務エラー一覧 | 該当なし |
| review-body | 規約レビュー結果の本文が空でないかを判定する | §8.1 業務エラー一覧 | 該当なし |
| verify-rows | 動作確認結果の表が存在し、全行の結果列が"pass"であるかを判定する | §8.1 業務エラー一覧 | 該当なし |
| file-missing | 記録ファイル自体が存在しない場合に不合格とする | §8.1 業務エラー一覧 | 該当なし |
| record-aggregate | 複数の記録ブロックを走査し、1件でも不合格があれば全体を不合格として集計する | §7.1 機能内の呼び出し一覧 | 該当なし |

## §3 入力条件

**この節の位置づけ: 仕様**

| キー | データ | 用途 |
|---|---|---|
| self-test-ok-record | `judge_record` の説明コメントに示す完全な記録ブロック（見出し・要求・コミット・入口のページ・実装概要・動作確認結果・規約レビュー結果を全て仕様どおりに満たすもの） | 陽性の基準ケース |
| self-test-missing-file | `docs/scope-and-progress/開発フロー完了記録.md` を作らないプロジェクト | ファイル不在の判定 |
| self-test-verify-fail | 動作確認結果の表に1行以上 `fail` を含む記録 | 動作確認不合格の判定 |
| heading-format-bad | `T`区切りを欠く見出し行 | 見出し形式違反の判定 |
| request-field-empty | 要求欄のセルを空にした行 | 要求欄未記入の判定 |
| request-field-placeholder | 要求欄のセルを山括弧で囲んだ行 | 要求欄プレースホルダ残存の判定 |
| commit-field-invalid-chars | コミット欄の末尾1桁を16進以外の文字にした値 | コミット欄形式違反の判定 |
| portal-field-empty | 入口のページ欄のセルを空にした行 | 入口のページ欄未記入の判定 |
| impl-body-empty | 実装概要の見出しの直後に本文行を置かない記録 | 実装概要空の判定 |
| review-body-empty | 規約レビュー結果の見出しの直後に本文行を置かない記録 | 規約レビュー結果空の判定 |
| verify-rows-absent | 動作確認結果の見出しの直後に表の見出し行だけを置き、データ行を置かない記録 | 動作確認結果表無しの判定 |
| record-aggregate-mixed | self-test-ok-record と同等の記録1件 + heading-format-bad 相当の記録1件を1ファイルへ連結したもの | 複数記録の集計判定 |

## §4 期待結果

**この節の位置づけ: 仕様**

期待結果は観測可能な値・状態・表示で記載する。self-test-ok-recordは終了コード0と合格ラベルを返す。self-test-missing-fileは終了コード1と「記録ファイルが見つからない」旨を返す。self-test-verify-failは終了コード1と「pass 以外の結果を含む」旨を返す。heading-format-bad以下verify-rows-absentまでの各ケースは、対応する記録だけが不合格になり終了コード1を返し、対応するエラー文言を出力する。record-aggregate-mixedは終了コード1と「1/2 PASS, 1/2 FAIL」の集計表示を返す。

## §5 異常系

**この節の位置づけ: 仕様**

| 観点のキー | 条件 | 期待結果 |
|---|---|---|
| heading-format | 見出しがISO8601形式でない | `judge_record` が不合格を返し、理由を標準エラーへ出力する |
| request-field | 要求欄が空またはプレースホルダのまま | `judge_record` が不合格を返す |
| commit-field | コミット欄が40桁16進の形式に一致しない | `judge_record` が不合格を返し、実際の値を出力する |
| portal-field | 入口のページ欄が「更新: 16進」「影響なし: 理由」いずれの形式にも一致しない | `judge_record` が不合格を返す |
| impl-body | 実装概要の本文が空 | `judge_record` が不合格を返す |
| review-body | 規約レビュー結果の本文が空 | `judge_record` が不合格を返す |
| verify-rows | 動作確認結果の表が無い、または1行でも"pass"以外を含む | `judge_record` が不合格を返し、"pass"以外の行を列挙する |
| file-missing | 記録ファイルが存在しない | `run_check` が不合格を返し、以後の走査を行わない |

## §6 境界値

**この節の位置づけ: 仕様**

| 観点のキー | 境界 | 期待結果 |
|---|---|---|
| commit-field | コミット欄の16進文字数が40桁（39桁・41桁との境界） | 40桁ちょうどなら合格、39桁以下または41桁以上なら不合格として検出する |
| verify-rows | 動作確認結果の表の"pass"以外の行数が0件（1件との境界） | 0件なら合格、1件以上あれば不合格として検出する |
| record-aggregate | ファイル内の記録ブロック数が1件（0件・複数件との境界） | 0件（見出しが1つも無い）なら記録が1件も無いとして不合格、1件以上ならブロックごとに判定して集計する |

## §7 網羅基準

**この節の位置づけ: 仕様**

設計書に定義された分岐・状態・制約をすべて観点へ対応付ける。`judge_record` は7つの個別検査を持つ。検査は heading-format・request-field・commit-field・portal-field の4つです。加えて impl-body・review-body・verify-rows の3つです。`run_check` は2つの判定（file-missing・record-aggregate）を持つ。この合計9観点を、§2のケースがすべて1件以上カバーする。
