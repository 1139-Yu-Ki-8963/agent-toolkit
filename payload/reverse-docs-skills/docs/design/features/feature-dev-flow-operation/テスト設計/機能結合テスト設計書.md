## 本書が検証するもの

結合は2段に分けて定義します。1つの設計単位の中で構成要素が結合した状態を内部結合、複数の設計単位をまたぐ連携を外部結合と呼びます。単位ごとの文書は内部結合までを担い、プロジェクト全体の文書が外部結合を担います。

| 段 | 検証する状態 | 対応する設計書 | 文書 |
|---|---|---|---|
| 単体 | 1つの関数・メソッドの入出力 | 機能設計書 | 機能単体テスト設計書 |
| 内部結合 | 1つの機能の中で関数・メソッドが結合した状態（外部の振る舞い） | 機能設計書 | 機能結合テスト設計書（本書） |
| 外部結合 | 複数の画面・機能・APIをまたぐ連携 | 複数の設計書 | docs/test-cases/結合テスト仕様書.md |

## §1 テスト観点

**この節の位置づけ: 仕様**

§1は正常・異常・境界を含む全観点の一覧です。
§5と§6は、§1のうち異常と境界の観点を列ごとに詳しく述べる部分集合です。
§5と§6では新しい観点キーを作らず、§1と同じ観点キーを使います。
実行する全ケースは§2だけに記載し、§1の全観点へ1件以上のケースを対応させます。
実行するテストの件数は§2のデータ行数だけで数えます。

観点は機能設計書の業務フロー・業務ルール・エラーと業務メッセージの各章から起こす。

| キー | 観点 | 由来する機能設計書の章 |
|---|---|---|
| gate-confirm | 承認ポイントで「確定する」を選ぶと次の段階へ進む | §3.1 正常系フロー |
| gate-rewrite | 承認ポイントで「自由記述」を選ぶと同じ段階へ差し戻る | §3.2 分岐と例外フロー |
| reviewer-absent | レビュアー未配置時に自分で代替判定せず、その旨を明示する | §3.2 分岐と例外フロー、§4.4 権限別の可否 |
| freshness-stale | 表示コミット鮮度が「差分あり」のとき対象設計書を更新しsource_refを追従させる | §3.2 分岐と例外フロー |
| freshness-unknown | 表示コミット鮮度が判定不能のとき統合せず再実行する | §3.2 分岐と例外フロー、§8.1 業務エラー一覧 |
| portal-entry-stale | 入口のページに差分があるとき依存関係の宣言に基づき再生成する | §3.2 分岐と例外フロー |
| verification-fail | 動作確認観点一覧のケースが不合格のとき完了記録を確定しない | §3.2 分岐と例外フロー、§8.1 業務エラー一覧 |
| completion-record-format | 完了記録の見出し・コミット・本文が形式要件を満たさないとき不合格になる | §8.1 業務エラー一覧 |

## §3 入力条件

**この節の位置づけ: 仕様**

| ケースのキー | 入力の項目 | 値 |
|---|---|---|
| gate-confirm | 承認ポイントでの選択 | 確定する |
| gate-rewrite | 承認ポイントでの選択 | 自由記述（修正指示あり） |
| reviewer-absent | `.claude/agents/rule-reviewer.md` の実在 | 存在しない |
| freshness-stale | 対象実装パスとHEADの差分 | 1件以上の変更あり |
| freshness-unknown | source_refの解決結果 | 全長40桁のコミットとして解決不能 |
| portal-entry-stale | 入口のページの鮮度検査結果 | `[STALE]` |
| verification-fail | 動作確認観点一覧のケース結果 | 1件以上 pass 以外 |
| completion-record-commit-boundary | コミット欄の値 | 40桁の16進文字列（例: 全て `a`〜`f`・`0`〜`9` で構成される40文字） |
| completion-record-commit-invalid | コミット欄の値 | 39桁の16進文字列（1桁不足） |

## §4 期待結果

**この節の位置づけ: 仕様**

| ケースのキー | 期待する結果 | 確認の方法 |
|---|---|---|
| gate-confirm | 次の段階の提示物が示される | 承認ポイントの出力を目視で確認する |
| gate-rewrite | 同じ段階の承認ポイントが再度出る | 承認ポイントの出力を目視で確認する |
| reviewer-absent | 「規約レビュー: 実行せず（レビュアー未配置）」が承認ポイントへ明示される | 承認ポイントの出力を目視で確認する |
| freshness-stale | 対象設計単位の詳細設計書のsource_refがHEADの全長40桁コミットへ書き換わる | 更新後のfrontmatterを確認する |
| freshness-unknown | 統合せず原因（対応欠落・未コミット差分等）を提示する | 出力メッセージを確認する |
| portal-entry-stale | 依存関係の宣言が選んだ成果物が作り直される | 再生成後の成果物を確認する |
| verification-fail | 完了記録を追記せず、実装プラン策定段階との整合確認を促す | 完了記録ファイルに新しい節が追加されないことを確認する |
| completion-record-commit-boundary | `check-dev-flow-completion.sh` が終了コード0を返す | `check-dev-flow-completion.sh <対象パス>` を実行する |
| completion-record-commit-invalid | `check-dev-flow-completion.sh` が終了コード1を返す | `check-dev-flow-completion.sh <対象パス>` を実行する |

## §5 異常系

**この節の位置づけ: 仕様**

| 観点のキー | 発生させる条件 | 期待する振る舞い | 由来する機能設計書の章 |
|---|---|---|---|
| reviewer-absent | `.claude/agents/rule-reviewer.md` を配置しない状態で承認ポイントへ到達する | 規約レビューの手順を飛ばし、自分で代替判定しない | §3.2 分岐と例外フロー |
| freshness-unknown | source_refが全長40桁のコミットとして解決できない状態にする | 統合せず、原因を解消してから鮮度判定を再実行する | §3.2 分岐と例外フロー、§8.1 業務エラー一覧 |
| verification-fail | 動作確認観点一覧のいずれかのケースを不合格にする | 完了記録を確定せず、実装プラン策定段階との整合を確認してから再確認する | §3.2 分岐と例外フロー、§8.1 業務エラー一覧 |
| completion-record-commit-invalid | 完了記録のコミット欄を39桁の16進文字列にする | `check-dev-flow-completion.sh` が不合格として検出する | §8.1 業務エラー一覧 |

## §6 境界値

**この節の位置づけ: 仕様**

| 観点のキー | 対象の項目 | 境界の値 | 境界の直前と直後の扱い |
|---|---|---|---|
| freshness-stale | 対象実装パスの差分件数 | 1件（0件との境界） | 0件なら`[FRESH]`として鮮度追従を行わず、1件以上なら`[STALE]`として全設計単位を更新する |
| completion-record-format | コミット欄の16進文字数 | 40桁（39桁との境界） | 40桁ちょうどなら合格、39桁以下または41桁以上なら不合格として検出する |
