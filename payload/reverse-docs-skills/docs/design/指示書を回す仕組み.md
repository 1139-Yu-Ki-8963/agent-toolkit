# 指示書を回す仕組み

## 1. この文書は何か

画像から課題を書き起こし、指示書として回し、片付けるまでの一連の流れを 1 枚で説明する。
仕組みは 7 つの部品に分かれ、別々の場所に置かれている。
この文書は各部品の所在と、部品どうしがどう繋がるかだけを示す。
個々の部品の詳細な仕様は、それぞれの正本の文書が持つ。
この文書からはその正本を参照する。

## 2. 流れ

始まりは画像である。
課題を写した画像を渡すと、その内容を書き起こす。
書き起こした内容のうち改善課題と判定したものは、`docs/tasks/指摘改善一覧.md` の「やること」節へ、見出しキー付きの項目として追加する。
このファイル 1 つが、画像由来の課題が集まる唯一の器である。
資産ごとに新しい指示書を作ることはしない。

指示書が指摘改善一覧へ増えると、次はそれを片付ける番になる。
担当する側のセッションへ `docs/session-prompts/作業者のプロンプト.md` のプロンプトを貼って起動すると、そのセッションは `docs/tasks/` 直下にある指示書を自分で拾う。
どの指示書のどの項目をやるかを、人が指定する必要はない。
1 つの指示書につき、1 つの項目だけを選んで満たし、コミットしてから、その指示書の「対応の記録」へ結果を書く。
これを 1 周として繰り返す。

複数の担当セッションへ作業を配りたい場合は、`docs/session-prompts/進行担当のプロンプト.md` のプロンプトを貼った進行役のセッションを別に立てる。
進行役は各担当へ項目を割り振り、届いた報告を自分で確かめてから台帳へ記録する。

指示書の項目が片付いたかどうかは、記録の状態欄の文字列だけでは判定しない。
`docs/scripts/judge-task-done.sh` が、対応の記録に書かれた「確かめる手段」のコマンドを実際に実行し、コミットが main の祖先になっているか、公開が済んでいるかまで含めて判定する。
すべての条件を満たした指示書だけが `docs/tasks/done/` へ移り、片付いたものとして扱われる。

## 3. 置き場

やることと、その記録の置き場は次の 3 つに限られる。

| 置き場 | 何を置くか | 片付けの対象か | 現在の件数 |
|---|---|---|---|
| `docs/tasks/` 直下 | 指示書。やることの唯一の入口 | 対象。ここが空になることを目指す | 6 |
| `docs/tasks/work-records/` | 作業に付随して積み上がる記録。検査・検証ループ・進行の管理が読み書きする | 対象外。消してはならない | 5 |
| `docs/tasks/done/` | 片付いた指示書の退避先 | 対象外。判定を通ったものだけが入る | 31 |

「`docs/tasks/` を空にする」とは、直下の件数が 0 件になることを指す。
`work-records/` と `done/` の件数はこの目標に数えない。
`work-records/` には直した内容の履歴が積み上がっており、消すと何をいつ直したかを追えなくなる。
`done/` には片付いた指示書が退避してあり、再び判定する対象ではない。

直下 6 件のうち 1 件は `指摘改善一覧.md` であり、画像由来の課題 56 件を見出しキーごとの項目として抱えている。

## 4. 部品と所在

| 部品 | 所在 | 何をするか |
|---|---|---|
| 課題の集約 | `docs/tasks/指摘改善一覧.md` | 画像由来の課題が集まる唯一の器 |
| 作業者のプロンプト | `docs/session-prompts/作業者のプロンプト.md` | 担当セッションが直下の指示書を自分で拾い 1 項目ずつ片付ける |
| 進行担当のプロンプト | `docs/session-prompts/進行担当のプロンプト.md` | 複数の担当セッションへ項目を配る |
| 形の規約 | `.claude/rules/always/tasks/instruction-format/rule.md` | 指示書の形（必須の節・冒頭の行・状態の語）を定める |
| 形の検査 | 同じフォルダの `check-instruction-format.sh` | 規約への適合を機械で判定する |
| 片付き判定 | `docs/scripts/judge-task-done.sh` | 3 条件と実測で `done/` へ移せるかを判定する |
| 迂回の防止 | `docs/scripts/check-task-done-move.sh` | コミット直前に判定を通らない移動を止める |

## 5. 指示書の形

指示書は冒頭に `**状態**` `**優先度**` `**前提**` の 3 行を置き、必須の 8 節を並びも含めて固定の順で持つ。
規約の全文は写さない。
正本は `.claude/rules/always/tasks/instruction-format/rule.md` である。

末尾には「対応の記録」の節を置き、その中の「判定の充足状況」の表は「判定・確かめる手段・状態・コミット・確かめた内容」の 5 列で書く。
「確かめる手段」の欄には、判定を実際に満たすかどうかを判定できるコマンドだけを書き、説明文は混ぜない。
「状態」の欄は担当者が直接書き込むものではない。
`judge-task-done.sh` を `--write` 付きで実行すると、各行の「確かめる手段」を実際に走らせた結果に応じて判定器がこの欄を書き換える。
人が「完了」と自分で書けないことが、この形の要点である。

## 6. 判断で止まらない

担当者がユーザーへ質問して手を止めることを、`作業者のプロンプト.md` と `進行担当のプロンプト.md` の両方が禁じている。
指示書は「決めていないこと」の節に、判断が要る事項ごとの既定を表で持つ。
担当者は判断に出会うと、まずこの節に事項があるかを見る。
あれば既定に従って進み、無ければ判断の材料が多いほうを自分で選んで進む。
選んだ内容と理由は「対応の記録」の「判断の記録」へ書く。
ユーザーはこの記録を後からまとめて読み、必要なら覆す。
既定を選ぶと明らかに壊れる場合だけ、その判定を「対象外」にして次へ進む。

## 7. 3 つの検査が何を止めるか

`check-instruction-format.sh --self-test` は合格 17 件・不合格 0 件、`judge-task-done.sh --self-test` は合格 9 件・不合格 0 件、`check-task-done-move.sh --self-test` は合格 6 件・不合格 0 件で通る。

`check-instruction-format.sh` は、必須の 8 節や冒頭の 3 行、状態の語が規約から外れた指示書を検出する。
引き受けた側が形式のばらつきで迷う事態を防ぐ。
現時点では hook による強制は無く、手動で実行して確かめる検査である。

`judge-task-done.sh` は、記録の状態欄に「完了」と書いてあるだけでは通さない。
「確かめる手段」のコマンドを実際に実行し、コミットが main の祖先か、公開が済んでいるかまで確かめてから「移せる」を出す。
状態欄の文字列だけで済ませる自己申告を止める。

`check-task-done-move.sh` は、`git commit` の直前に staged の変更を見て、`judge-task-done.sh` が「移せる」と認めていない指示書を `docs/tasks/done/` へ入れる移動を止める。
過去に、判定器がどの条件も満たさないと示した状態のまま 7 件が判定器を経由せず `done/` へ移された実例があり、その再発を防ぐために置かれた。

## 8. いまの状態

`judge-task-done.sh` を引数なしで実行すると、次が出る。

```
公開の状態: 未反映（不一致: .claude/rules/scoped/portal/page-conventions/rule.md delivery-payload generation-engine ）

移せる:
（0件）

移せない:
- 指摘改善一覧.md: 記録なし
- 未着手の指示.md: 公開が未反映
- 片付き判定に実測の段階を足す指示書.md: 目視の行がある
- 自己テストの所要時間が規約の件数に追いつかれる問題を片付ける指示書.md: 記録なし
- 規約の定義と生成物の分離を自分のリポジトリへ適用する指示書.md: 確かめる手段の列が無い
```

「移せる」が 0 件なのは、直下 6 件のどれも 3 条件をすべて満たしていないからである。
公開の状態が「未反映」なのは、payload の一部（`page-conventions/rule.md`・`delivery-payload`・`generation-engine`）が現在の main と一致していないためであり、この不一致は指示書ごとではなくリポジトリ全体で 1 回だけ判定される。
`指摘改善一覧.md` と 1 件は「対応の記録」の節そのものを持たないため「記録なし」になる。
`片付き判定に実測の段階を足す指示書.md` は判定の 1 行が「目視」と書かれており、機械では確かめられないため止まる。
`規約の定義と生成物の分離を自分のリポジトリへ適用する指示書.md` は判定の表が旧い 4 列のままで、「確かめる手段」の列が無いため止まる。

## 9. まだ無いもの

### 段階 3（元の指摘との照合）

2026-08-19 時点で実装済みである。ただし実装までに向きを 3 度直している。

当初は反映対応台帳（`docs/tasks/work-records/改善反映台帳.md`）を起点に、そのキーが指示書に現れないものを欠落として報告する向きだった。**これは誤りである。** 台帳は反映が済んだ記録であり、そこに載るキーに指示書が無いのは正常な終わりの状態である。この向きでは片付いた 44 件を欠落として報告し続け、何度直しても数字が減らない。

指示書が主張するキーを起点に、台帳へ検証方法と結果を伴う行があるかを見る向きへ改めた。あわせて次の 2 つを直した。

- 台帳の書き方の揺れ（`（原文未取得、原番号 1-76）` のように語が挟まる形）を取りこぼしていた
- 本文から `1-NN` の形をすべて拾っていたため、`Stage 1-3` のような工程の番号を指摘のキーと取り違えていた。見出しの形（`### 1-NN.`）と `原番号 1-NN` だけに絞った

2026-08-19 時点の実測は、指示書が主張するキーが 55 件、裏付けの無いキーが 14 件である。

**残っている限界**: `docs/tasks/done/` の指示書は、元の指摘のキーを機械で読める形で 1 件も持たない。そのため段階 3 が照合できるのは、開いている指摘（`docs/tasks/指摘改善一覧.md` の見出し）だけである。片付いたと主張する指示書がどの指摘を覆ったのかは、いまも辿れない。この限界は `docs/tasks/done/指摘の追跡を機械で読める形にする指示書.md` が扱う。
