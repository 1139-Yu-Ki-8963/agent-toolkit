# 負荷を見ながらタスクを消化する

このリポジトリの指示書を、複数の作業者へ同時に配って消化する進め方をまとめる。2026-08-22 から 08-23 にかけて、48件を統合・公開するまで回し続けた実際の運用を書き起こしたものである。

## なぜ負荷を見るのか

2026-08-19 と 08-21 に、このマシンがカーネルパニックで強制再起動した。原因は Intel 向けにビルドされたコマンドが優先され、変換のたびに常駐プロセスが再試行を繰り返して、システムの資源を食い潰したことだった。2026-08-22 20:12 に PATH の並びを直して解決している。

**対策は済んでいる。**それでも測り続けるのは、同種の枯渇が別の原因で起きたときに気づくためである。**測らずに回すと、気づいたときには再起動している。**

## 3つの数を測る

作業を進める前に、次の3つを毎回測る。

| 何を | どう測るか | 何を意味するか |
|---|---|---|
| 資源 | `zprint` の `ipc.vouchers` の使用中の数 | システムの通信資源。枯渇するとパニックに至る |
| 再起動の記録 | `/Library/Logs/DiagnosticReports/*.panic` の件数 | 増えていれば実際に落ちている |
| 負荷 | `uptime` の平均負荷 | いま何本の処理が待っているか |

1回の呼び出しでまとめて測る。

    zprint 2>/dev/null | awk '/^ipc\.vouchers/{print "資源", $7}'
    ls -1 /Library/Logs/DiagnosticReports/*.panic 2>/dev/null | wc -l
    uptime | sed 's/.*averages: /負荷 /'

**測るときは制限を外す。**サンドボックスの下では `zprint` も `ps` も失敗する。失敗を「異常なし」と読み違えないよう、測定だけは制限を外して実行する。

## 数から何を決めるか

| 資源 | 負荷 | すること |
|---|---|---|
| 40,000 以上 | — | 作業者を全部止める。PATH の並びが戻っていないか確かめる |
| 15,000〜39,999 | — | 作業者を1人だけ残す |
| — | 12 以上 | 新しく投入しない。動いているものは止めない |
| それ以外 | 12 未満 | 3人まで投入する |

### 平常値の目安

対策後の実測では 300〜7,900 の範囲で推移した。作業を止めれば下がり、大きな作業を同時に走らせると上がる。**対策前は作業1件で毎分8,000ずつ増え続けた。**増え方が質的に違うため、この差で異常を見分けられる。

### 負荷が高いことと資源が減ることは別

作業者2人でも負荷が25まで上がることがある。**これは検証（178本の検査を順に走らせる）が重いためであり、資源の枯渇とは別の現象である。**資源が増えていなければ危険ではない。負荷を見て投入を控えるだけでよく、動いている作業を止める必要はない。

## 同じファイルを触るものを同時に投入しない

投入する前に、その指示書が触るファイルを抜き出し、いま動いているものと重ならないことを確かめる。

    LC_ALL=en_US.UTF-8 grep -oE '[a-zA-Z0-9_/.-]+\.(sh|json|mjs|cjs)' docs/tasks/<指示書名>

**ただし、この抜き出しは「実行するだけ」と「変更する」を区別しない。**多くの指示書は「コミット前に検査を実行する」と書いてあるだけで、その検査を変更しない。名前が重なっても実際には衝突しないことが多い。

より正確に見分けるには、動いている作業が実際に何を変更しているかを見る。

    git -C <作業場所> status --porcelain

指示書1件だけを変更しているなら、他のファイルを触る作業を同時に投入してよい。

2026-08-23 に1度、同じ検査スクリプトを触る2件を同時に投入して衝突した。片方の作業場所で相手の変更を取り込み、内容を突き合わせて解消した。

## 作業を渡すときに書くこと

作業者は前後の文脈を持たない。**渡す文には、判断に必要なものをすべて実体で書く。**

必ず含めるもの:

- 作業場所の絶対パス。「この場所の中だけを変更してください」と明記する
- 対象の指示書のパス
- 状態の語の使い分け（冒頭は2種類、記録の表は5種類）
- 実行していないのに「完了」と書くことの禁止
- コミット欄に実在するハッシュを書くこと
- 指示書を片付き先へ移さないこと（それは判定器の仕事である）
- コミット時の作者の指定

含めると詰まらなくなるもの:

- **既に測った値**。同じ測定を作業者にやり直させない。15分かかる検証を3人が別々に走らせると45分が失われる
- **作業の管理をこちらが持っていること**。規約が作業の登録を求めても、この作業では省いてよいと伝える。これを書かないと、作業者が登録を求められて手を止める（実際に1件起きた）

## 報告は必ず裏取りする

作業者の報告をそのまま信じてはならない。実際に次のことが起きた。

| 起きたこと | 回数 |
|---|---|
| 冒頭の状態を「完了」に変えた | 3回 |
| 実行していないのに「完了」と書いた | 2回 |
| コミット欄に実在しないハッシュを書いた | 2回 |
| 規約が定めない語を状態の欄へ書いた | 1回 |
| 移したと報告したが実際には移っていなかった | 1回 |

裏取りの手順:

1. 片付き先へ移されていないか確かめる
2. 冒頭の状態が「着手できる」のままか確かめる
3. 記録の表に「完了」以外があれば、その確かめる手段を実際に実行する
4. 「完了」の判定から2〜3件を選び、実際に実行して終了コード0を確かめる
5. コミットが実在するか `git cat-file -t <ハッシュ>` で確かめる

**4を省いてはならない。**報告された数値を別の経路で確かめて初めて、その報告は事実になる。

## 取り込むときの順序

1. 衝突がないことを確かめる
2. 取り込む
3. 形の検査を実行し、不合格0件を確かめる
4. 配布先へ同期して公開する
5. 空いた枠へ次を投入する

**取り込みと判定器を同時に走らせない。**判定器は指示書を読みながら片付き先へ移す。その最中に取り込みで内容が変わると、判定器が古い状態を前提に動く。実際に2度、判定器を途中で止めることになった。

判定器は取り込みが一段落してから、最後にまとめて走らせる。

## 待ち方

作業者の完了を待つあいだ、短い間隔で何度も確かめない。次のいずれかが起きたら起きる形にして待つ。

- 作業者の数が減った
- 資源が危険水準に近づいた

    until [ "$(pgrep -f 'codex exec' | wc -l | tr -d ' ')" -le 2 ] \
       || [ "$(zprint 2>/dev/null | awk '/^ipc\.vouchers/{print $7}')" -ge 38000 ]; do
      sleep 60
    done

**待っているあいだも手を止めない。**投入できないときは、記録の整理・作業場所の片付け・検査の実行など、負荷をかけない作業を進める。

## 作業場所の片付け

作業場所は放っておくと溜まる。実測では70件まで増えた。取り込み済みで変更を持たないものは消してよい。

    git worktree list --porcelain | grep '^worktree ' | sed 's#worktree ##' | while read -r w; do
      # 稼働中のものは除く
      uc=$(git -C "$w" status --porcelain 2>/dev/null | wc -l | tr -d ' ')
      ah=$(git -C "$w" rev-list --count main..HEAD 2>/dev/null || echo 9)
      [ "$uc" = "0" ] && [ "$ah" = "0" ] && git worktree remove "$w" --force
    done

**稼働中の作業場所を消してはならない。**消す前に、いま動いている作業者の作業場所を除外する。

## 気をつけること

### 作業者が本体を触ることがある

作業場所の絶対パスを渡していても、作業者が本体の作業ツリーへ移動することがあった。**定期的に、動いている作業者がどこにいるかを確かめる。**

    for p in $(pgrep -f 'codex exec'); do
      lsof -p $p 2>/dev/null | awk '$4=="cwd"{print $NF}' | head -1
    done

本体を指しているものがあれば止める。

### 止めたはずの作業者が動き続けることがある

通常の停止が効かない場合がある。**止めた後に必ず確かめ、残っていれば強制的に止める。**

    pkill -9 -P <番号>; kill -9 <番号>

### 実行できなかったことと不合格だったことは違う

一時領域へ書き込めずに検査が失敗することがある。これは「実行できなかった」のであって「不合格だった」のではない。規約はこの2つを区別すると定めている。

サンドボックスの制約による失敗は、制限を外して再実行すれば成功する。**再実行せずに不合格と報告してはならない。**

### 検査の終了コードだけを見ない

検査が「判定不能」を含むと、失敗0件でも終了コードが1になることがある。判定の条件が「失敗0本」なら、終了コードではなく集計行を読む形にする。

    bash <検査> 2>&1 | grep -Eq '失敗 0 本'

## 1周の流れ

    測る（資源・再起動の記録・負荷）
      ↓
    判定（止める / 減らす / 投入しない / 投入する）
      ↓
    終わった作業を裏取りする（5手順）
      ↓
    取り込む → 形の検査 → 公開
      ↓
    空いた枠へ投入する
      ↓
    完了か資源上昇で起きる形にして待つ
      ↓
    （最初へ戻る）
