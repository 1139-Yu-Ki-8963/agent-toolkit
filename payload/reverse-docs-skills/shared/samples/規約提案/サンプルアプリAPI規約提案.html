openapi.yaml未記載のエンドポイントが実装上2件存在する

routes/ の実装は38件だが、うち POST /recipes/:id/duplicate と GET /admin/reports の2件が openapi.yaml に未記載。ドキュメント漏れか廃止予定かの判断材料はコード上になく、現場での棚卸しを推奨する。

画像アップロードの署名付きURL発行に所有者チェックがない

POST /uploads/sign は認証済みであれば任意の recipe_id を指定して署名付きURLを取得できる（uploads.service.ts:32-58）。他人のレシピへの画像添付が可能かは後続処理の検証に依存し、静的解析のみでは断定できない。実挙動の確認を推奨する。

service層のユニットテストが決済・通報まわりで薄い

契約テストは38エンドポイント全カバーだが、service層カバレッジは31%。billing.service.ts は8%、report.service.ts は0%であり、業務ルールが最も集中する領域が最も薄い。

01

AIエージェント運用

agent-operations

AIエージェント行動規約

提案あり
  • .github/workflows/ai-review.yml:14-22 は全PR上で claude-review ジョブを実行し、レビュー結果をPRコメントへ投稿する。呼び出し先の scripts/ai/run-review.sh:9-15 には、AIエージェントが変更してよい範囲・禁止操作の明示的な記述がない。

規約提案文(案)

AIエージェントによるレビュー・修正提案は、PRコメントへの提案投稿に限定する。mainブランチへの直接pushやマージ操作は行わない旨を、本規約として明文化する。

出典: .github/workflows/ai-review.yml:14-22

破壊的操作の安全規約

提案あり
  • scripts/ai/run-review.sh:31-40 は rm -rf・git push --force・git reset --hard を含むコマンド文字列を実行前に検査し、該当した場合は実行を中断する処理が既に実装されている。この挙動を明文化した規約は見当たらない。

規約提案文(案)

破壊的コマンド（rm -rf・git push --force・git reset --hard）の実行前チェックは、scripts/ai/run-review.sh に実装済みの挙動を追認し、正式な安全規約として明文化する。

出典: scripts/ai/run-review.sh:31-40

セッション管理規約

対象外

調査範囲内に、AIエージェントの対話単位（開始・終了・引き継ぎ）を扱うコードや設定は存在しなかった。CI上のワンショット実行のみが確認され、セッションという概念自体が本サンプルアプリの開発体制に存在しない。

AI設定資産の管理規約

提案あり
  • .github/workflows/ai-review.yml と scripts/ai/ 配下のAI関連設定ファイルは3件存在するが、直近のコミット履歴では、レビューを経ずに単独コミットで変更されたものが5件確認された（未確認: コミット権限自体の制限有無）。

規約提案文(案)

scripts/ai/ および .github/workflows/ai-review.yml の変更はコードレビューを必須とし、単独コミットでのマージを禁止する。

出典: scripts/ai/run-review.sh:1-8

定型運用の規約

対象外

定型的な運用手順（日次バッチの再実行手順・障害時のロールバック手順等）を記述したドキュメントやスクリプトは、調査範囲内に見つからなかった。

02

開発プロセス

development-process

開発フロー規約

提案あり
  • .github/workflows/ci.yml:1-40 には pull_request トリガーのジョブが定義され、test → lint → build の順で実行される。一方、mainブランチへのマージ条件としてCI全通過を強制する設定（branch protection）はコード上からは確認できない（GitHub側の設定でありコード調査範囲外）。

規約提案文(案)

mainブランチへのマージは CI（test → lint → build）の全通過を必須条件とし、.github/workflows/ci.yml の実行結果をレビュー承認の前提とする。

出典: .github/workflows/ci.yml:1-40

ツールとコマンド実行の規約

提案あり
  • package.json:12-18 の scripts には dev・test・lint・build の4コマンドが定義されている。一方、DBマイグレーション実行手順は migrations/README.md:3 に文章で書かれているのみで、package.json には対応するコマンドが登録されていない。

規約提案文(案)

DBマイグレーション実行コマンド（npm run migrate）を package.json の scripts に登録し、手順書と実行コマンドを一致させる。

出典: package.json:12-18、migrations/README.md:3

開発環境規約

提案あり

ドキュメント記載

  • config/env.example:1-20 には環境変数22件が列挙されている。

実装参照

  • src/api/sample_app/config.ts:5-30 が実際に読み込む環境変数は26件あり、うち4件（RECIPE_IMAGE_BUCKET・REPORT_WEBHOOK_URL・SESSION_SECRET_ROTATE_AT・ADMIN_ALLOWLIST）が env.example に未記載。

規約提案文(案)

config.ts が参照する環境変数はすべて config/env.example に記載し、両者の差分をCIで検知する。

出典: src/api/sample_app/config.ts:5-30、config/env.example:1-20

Git運用規約

提案あり
  • 直近50件のコミット履歴のうち18件が「fix」「update」「wip」のみの単語で、変更内容の説明を伴わない。ブランチ命名も feature/* と feat-* が混在（それぞれ6件・4件）している。

規約提案文(案)

コミットメッセージは変更内容を要約した文を必須とし、ブランチ命名は feature/<slug> 形式に統一する。

出典: git log（直近50件のコミット履歴。リポジトリ内ファイルではなく履歴調査）

リリースとデリバリーの規約

→共通規約を参照

リリース手順・デリバリー手順は本サンプルアプリ固有ではなく、組織共通規約に既に定義されている領域であり、コード調査からは組織共通規約との重複以外の固有事項が見つからなかった。

コード規約

code-standards

コーディング規約

提案あり
  • src/api/sample_app/routes/recipes.controller.ts は420行あり、他コントローラの平均140行と比べて突出している。同ファイルには6つのハンドラが定義され、うち updateRecipe ハンドラ単体で95行を占める。

規約提案文(案)

1コントローラファイルは200行を目安とし、超過する場合はハンドラ単位でのサービス層への分割を必須とする。

出典: src/api/sample_app/routes/recipes.controller.ts:1-420

命名規約

提案あり
  • src/api/sample_app/services/ 配下14ファイルのうち11ファイルは <domain>.service.ts 形式だが、3ファイル（recipeHelper.ts・imgUtil.ts・mailer.ts）がこの命名から外れている。

規約提案文(案)

service層のファイル名は <domain>.service.ts 形式に統一する。

出典: src/api/sample_app/services/recipeHelper.ts、imgUtil.ts、mailer.ts

ディレクトリ構成規約

提案あり
  • src/api/sample_app/ 直下は routes / services / repositories / models の4層構成である。一方 uploads.service.ts のみ services/ ではなく routes/uploads/ 配下に配置されており、層構成から逸脱している唯一の例外である。
routes/HTTPハンドラ。recipes.controller.ts 等
services/業務ロジック。recipe.service.ts 等（uploads.service.ts のみ routes/uploads/ 配下に例外配置）
repositories/DBアクセス。recipe.repository.ts 等
models/型定義。recipe.model.ts 等

図2: routes / services / repositories / models の層構造

規約提案文(案)

routes / services / repositories / models の4層構成を正とし、層をまたぐ配置（routes/uploads/uploads.service.ts 等）を禁止する。

出典: src/api/sample_app/routes/uploads/uploads.service.ts

コンポーネント設計規約

対象外

06

非機能要件

non-functional-requirements

セキュリティ要件

提案あり
  • 横断的所見のとおり uploads.service.ts:32-58 の POST /uploads/sign は、認証済みであれば任意の recipe_id を指定して署名付きURLを取得できる。所有者チェックの呼び出しは確認できない。

規約提案文(案)

署名付きURL発行APIは、対象リソースIDに対する所有者チェック（または権限チェック）の呼び出しを必須とする。

出典: src/api/sample_app/routes/uploads/uploads.service.ts:32-58

性能要件

提案あり(範囲限定)
  • routes/recipes.controller.ts:210-240 の listRecipes ハンドラは、検索条件を都度SELECT *で全件取得したうえでアプリ側でfilterしている（repositories/recipe.repository.ts:88-102）。ページネーションのLIMITは適用されているが、WHERE句への条件反映はない。負荷試験の実測データは調査範囲になく、性能劣化そのものは未確認。

規約提案文(案)

検索条件はSQLのWHERE句へ反映し、アプリ側での全件filterを禁止する。ただし本提案は listRecipes 系エンドポイントに限定し、他エンドポイントへの一般化は別途検証を要する。

出典: src/api/sample_app/repositories/recipe.repository.ts:88-102

可用性要件

対象外

冗長構成・フェイルオーバーに関する設定（インフラ定義）は調査範囲（config/・.github/workflows/）に含まれておらず、コードからは判断できない。

拡張性要件

対象外

将来の機能追加を見据えた拡張ポイント（プラグイン機構等）は現状のコードに存在せず、評価対象がない。

監視要件

提案あり
  • services/billing.service.ts と report.service.ts にはログ出力（logger.info / logger.error）が1箇所も無い（該当箇所のgrep結果0件）。他のserviceファイルの平均は6.4箇所。

規約提案文(案)

決済（billing）・通報（report）など業務影響が大きいserviceは、主要処理の開始・終了・異常系にログ出力を必須とする。

出典: src/api/sample_app/services/billing.service.ts、report.service.ts

07

業務ドメイン規約

business-domain

用語定義

提案あり
  • models/ 配下で「レシピ」を指す識別子が recipe・dish・menuItem の3種類混在している（grep集計: recipe 42件・dish 6件・menuItem 3件）。

規約提案文(案)

業務用語「レシピ」に対応する識別子は recipe に統一し、dish・menuItem を廃止する。

出典: src/api/sample_app/models/（grep集計）

業務規則

提案あり(範囲限定)
  • services/recipe.service.ts:120-145 の公開レシピ判定は status === 'published' のみで判定しており、billing.service.ts 側の有料会員限定フラグ（isPremiumOnly）との整合チェックが recipe.service.ts には存在しない（未確認: 実際に有料限定レシピが無料公開される事象が起きるか）。

規約提案文(案)

公開判定ロジックは status と isPremiumOnly の両方を参照する単一関数に集約する。ただし本提案は公開判定処理に限定し、他の会員種別ロジックへの拡張は別途調査を要する。

出典: src/api/sample_app/services/recipe.service.ts:120-145

状態遷移の制約

提案あり
  • レシピの状態は draft → in_review → published → archived の4状態が models/recipe.model.ts:8 の型定義から確認できる。一方、状態遷移を検証する関数は services/recipe.service.ts に存在せず、updateRecipe ハンドラ（recipes.controller.ts:180-195）がリクエストのstatusフィールドをそのままDBへ書き込んでいる。
draft→ in_review→ published→ archived

図3: レシピの状態遷移（許可された遷移のみを想定）

規約提案文(案)

レシピの状態遷移は許可された遷移（draft→in_review・in_review→published・published→archived等）のみを許容する検証関数を設け、コントローラでの直接書き込みを禁止する。

出典: src/api/sample_app/routes/recipes.controller.ts:180-195、src/api/sample_app/models/recipe.model.ts:8

計算規則

対象外

価格計算・割引計算等のロジックは billing.service.ts に存在するが、カバレッジ8%（横断的所見のとおり）で実装の意図が読み取れる形のコメントがなく、規約提案の根拠となる観測事実を確保できなかった。
