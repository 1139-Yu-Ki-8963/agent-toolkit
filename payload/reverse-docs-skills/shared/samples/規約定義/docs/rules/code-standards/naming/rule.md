# 命名規約

## 概要

この規約は、コード内で使う識別子の命名パターンを定める。対象は関数名とデータベースのカラム名とReactコンポーネント名の3種である。サンプルアプリの実装から観測した命名の慣習をもとに定めた。`globs` はAIツールへ本規約を注入する適用範囲であり、`check-naming.sh` 自体は呼び出し時に渡されたファイルを検査する。マイグレーションファイルへ検査を及ぼす場合は、呼び出し側の対象パス指定に `db/migrations/**/*.sql` を含める。

## 規則

| 規則 | 内容 | 根拠 |
|---|---|---|
| 関数名はキャメルケース | `function` 宣言による関数名は、先頭を小文字にしたキャメルケースで書く | サンプルアプリの `src/utils/` と `src/api/` 配下で、この形式が大多数を占めていた |
| DBカラム名はスネークケース | マイグレーションファイル内のカラム名は、英小文字と数字とアンダースコアだけで書く | サンプルアプリの `db/migrations/` 配下のテーブル定義が、すべてこの形式で統一されていた |
| Reactコンポーネント名はパスカルケース | `.tsx` ファイルで `export` する関数名は、先頭を大文字にしたパスカルケースで書く | サンプルアプリの `src/components/` 配下のエクスポート済み関数が、すべてこの形式だった |

## 違反時の手順

1. `check-naming.sh` が報告したファイルと行番号を確認する
2. 該当する識別子を規則に沿った形式へ書き直す
3. 呼び出し元がある場合は、リネームに合わせて呼び出し元も修正する
4. advisory のため commit は止まらないが、次回のレビューで指摘対象になる

## 設計判断

この節は `.sh` 同梱に伴うアーキテクチャ決定記録であり、設計文書3節が規定するrule.mdの本文構造（概要・規則・違反時の手順）には含まれない。

**必要性**: `check-naming` は関数名・DBカラム名・コンポーネント名という3種の命名規則を、ファイル拡張子ごとに正規表現で判定する。判定条件が3種×2階層（キャメルケース／パスカルケース／スネークケースの切替）に分岐するため、Bashツールでの都度実行では同じ分岐を毎回組み立て直すことになりトークンを浪費する。CIやCLIから繰り返し呼ぶ想定のため、スクリプト化が必要である。

**代替案を採用しなかった理由**:
- Bash ツール直叩き: 拡張子判定・export判定・3種のケース判定という複数段の分岐を、対話のたびに手動再現するのは非現実的
- 既存 Makefile ターゲット拡張: このサンプルアプリは Makefile を持たない想定であり、新規導入は本チェック専用の依存を増やすだけになる
- package.json scripts 追加: 同様に、シェルロジック自体は package.json に埋め込めず `.sh` を別途持つ必要がある

**保守責任者**: 人手（ユーザー）。命名規則の対象を拡張する場合は本スクリプトと `rule.md` の「## 規則」表を同時に更新する。

**廃棄条件**: 命名規約自体が廃止された時、またはリンタ機能を持つ静的解析ツール（ESLintの命名規則プラグイン等）へ全面移行した時。

この設計判断は、回帰テスト `check-naming.test.sh` にも同様に適用する。合格例と違反例を固定サンプルとして持ち、`check-naming.sh` の検査ロジックを変更するたびに退行がないかを確認する用途である。
