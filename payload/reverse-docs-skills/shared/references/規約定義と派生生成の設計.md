# 規約定義と派生生成の設計

本ファイルは reverse-docs-skills が対象リポジトリへ納品する「規約の定義」と、そこから各 AI ツール向けに生成する「派生物」の設計を定める文書である。定義から派生への一方向生成だけを扱い、派生物から定義を逆生成する経路は扱わない。この文書は設計であり、対応する取り込みスキルと生成スクリプトは未実装である。

## 1. 全体像

規約の一生は提案・取り込み・適用の 3 段で構成する。

| 段 | 入力 | 出力 | 担当 |
|---|---|---|---|
| 提案 | 対象リポジトリのコード | 規約提案 HTML（リポジトリ外へ出力） | リバース工程 |
| 取り込み | 判定結果 JSON | `docs/rules/<親>/<子>/` の一式 | `importing-rule-proposals`（納品スキル） |
| 適用 | `docs/rules/` | `.claude/`・`.cursor/`・`.codex/`・`AGENTS.md`・`project-portal/規約/` | `syncing-derived-artifacts`（納品スキル） |

定義は `docs/rules/` だけである。`.claude/`・`.cursor/`・`.codex/`・`AGENTS.md`・`project-portal/規約/` はすべて `docs/rules/` から生成する派生物であり、直接編集の対象にしない。

## 2. docs/rules の構造

親カテゴリを 7 個、子カテゴリを 27 個の 2 階層で構成する。親フォルダは直下に宣言ファイルを持ち、1 つの子カテゴリは以下のフォルダを持つ。

```
docs/rules/<親>/
├── parent.yml               親カテゴリの宣言。必須
└── <子>/
    ├── rule.md                  規約本文（front matter 付き）。必須
    ├── check-<子>.sh            linter。checkable: true のとき必須
    ├── check-<子>.test.sh       linter の回帰テスト。linter があるとき必須
    └── design-notes.md          検査できない理由。checkable: false のとき必須
```

`parent.yml` は 2 鍵だけを持つ。

| 鍵 | 型 | 必須 | 用途 |
|---|---|---|---|
| `key` | 文字列 | 必須 | 親カテゴリの英語キー。フォルダ名と一致させる |
| `title` | 文字列 | 必須 | 日本語表示名。AGENTS.md とポータルの親見出しに使う |

取り込みスキルが `parent.yml` を新規作成する場合、`title` は判定結果 JSON の `chapter` から章番号を取り除いた部分を使う。取り除く対象は先頭の数字、`第<数字>章`、`<数字>.<数字>` と、それに続く区切り記号である。

規約本文と検査スクリプトを同じフォルダに置く。規約を直すときに検査も直す動機が働く配置であり、両者が離れていると片方だけが古くなる。

規約フォルダの linter は `check-<子>.sh` とする。前置詞は検査することを表し、hook として登録したときの強さ（advisory または block）とは別の軸である。強さは `enforcement` 鍵が持つ。`agent-home` の hook 命名規則は hook 自体のファイル名を対象とするもので、規約フォルダの linter には適用しない。

検証と生成のスクリプトは、納品先では `docs/rules-tooling/` に配る。`docs/rules/` の隣に置く理由は 2 つある。定義と道具を同じ `docs/` の下に収めることで、定義を配れば道具も付いてくる形にできる。もう 1 つは、`docs/rules/` の中に置くと、規約の階層を走査する処理がスクリプト自身を規約として拾ってしまうためである。

## 3. rule.md の形式

front matter の鍵は以下のとおり定める。

| 鍵 | 型 | 必須 | 値域 | 用途 |
|---|---|---|---|---|
| `key` | 文字列 | 必須 | ケバブケース | 子カテゴリの英語キー。フォルダ名と一致させる |
| `title` | 文字列 | 必須 | 日本語 | 表示名。ポータルと AGENTS.md が使う |
| `parent` | 文字列 | 必須 | ケバブケース | 親カテゴリの英語キー |
| `summary` | 文字列 | 必須 | 1 文 | 規約の要約。Cursor の description になる |
| `scope` | 列挙 | 必須 | `always` / `scoped` | 常時注入か条件付きか |
| `globs` | 配列 | `scope: scoped` のとき必須 | glob パターン | 適用対象のパス |
| `enforcement` | 列挙 | 必須 | `advisory` / `none` | 検査の強さ |
| `checkable` | 真偽 | 必須 | true / false | 機械検査が可能か |
| `checker` | 文字列 | `checkable: true` のとき必須 | ファイル名 | linter のファイル名 |
| `uncheckableReason` | 文字列 | `checkable: false` のとき必須 | 1 文以上 | 検査できない理由 |
| `formatter` | 列挙 | 必須 | `prettier` / `biome` / `editorconfig` / `none` | 矯正設定の写し先 |
| `status` | 列挙 | 必須 | `draft` / `approved` | 派生生成の対象か |
| `origin` | 列挙 | 必須 | `template` / `proposal` / `manual` | 出自。ずれ検知で上書き可否の判断に使う |

`# <title>` の下に次の節を置く。

| 節 | 条件 |
|---|---|
| `## 概要` | 必須 |
| `## 規則` | 必須。表で書く |
| `## 違反時の手順` | `enforcement` が `advisory` のとき必須。`none` のときは置かない |
| `## 設計判断` | `checkable: true` のとき必須。linter の必要性・代替案を採らなかった理由・保守責任者・廃棄条件の 4 項目を書く |

`enforcement` が `none` の規約は、機械が検知しない取り決めである。違反したときに何をするかは規約本文が述べる範囲であり、手順の節を設けない。

`origin` は 3 値のいずれかを持つ。`template`（空雛形のまま未記入のもの）・`proposal`（規約提案から取り込んだもの）・`manual`（現場が直接書いたもの）と区別する。

## 4. 判定結果 JSON の形式

規約提案 HTML が出力し、取り込みスキルが読む形式である。スキーマは以下のとおり。

```json
{
  "proposalId": "string",
  "generatedAt": "ISO8601",
  "total": 0,
  "judged": 0,
  "decisions": [
    {
      "parent": "string（ケバブケース）",
      "key": "string（ケバブケース）",
      "chapter": "string",
      "title": "string（日本語）",
      "decision": "adopt | hold | reject | pending",
      "proposedRule": "string",
      "scope": "always | scoped",
      "globs": ["string"],
      "enforcement": "advisory | none",
      "checkable": true,
      "checkMethod": "string",
      "sources": ["string"]
    }
  ]
}
```

書き込み先の特定には表示名ではなく `parent` と `key` を使う。日本語の表示名を後から変えても、`parent` と `key` が変わらない限り対応が壊れない。

`checkMethod` は `checkable: true` のとき、何をどう検査するかを自然文で持つ。取り込みスキルはこの記述を元に linter を生成する。

## 5. 変換規則

front matter の各鍵が、どの派生物のどこへ写るかを以下の表で定める。

| 鍵 | `.claude/rules/` | `.cursor/rules/*.mdc` | `AGENTS.md` | `project-portal/規約/` |
|---|---|---|---|---|
| `scope` | 配置先が `always/` か `scoped/` かを決める | `alwaysApply` の真偽 | 使わない | 使わない |
| `globs` | rule の paths に写す | `globs` にそのまま写す | 使わない | 使わない |
| `summary` | 使わない | `description` に写す | 索引の説明文 | カードの説明文 |
| `title` | 使わない | 使わない | 索引の表示名 | ページ見出し |
| `parent` + `key` | 配置パスを組む | ファイル名 `<parent>-<key>.mdc` を組む | 参照パスを組む | 分類とページ名を組む |
| 本文 | そのまま複製 | front matter の下にそのまま複製 | 複製しない（参照パスのみ） | HTML へレンダリング |
| `parent.yml` の `title` | 使わない | 使わない | 親見出しに使う | `規約/` の分類名に使う |

Cursor は素の `.md` を無視し、`.mdc` 拡張子と front matter を必須とする。この仕様が上表の変換根拠である。

`AGENTS.md` には規約本文を複製しない。Codex は `AGENTS.md` を各階層で探索して連結する仕様のため、参照パスだけで規約本文へ到達できる。本文を複製すると、同じ内容を持つ 2 つ目の実体が生まれ、片側だけを編集して他方が古くなる穴が増える。

`status: draft` の規約は派生生成の対象外とする。

## 6. linter の配線

linter のスクリプト実体は `docs/rules/<親>/<子>/check-<子>.sh` の 1 つだけとする。`.claude/`・`.cursor/`・`.codex/` の 3 ツールとも同じファイルを呼ぶ。各ツールへ生成するのは呼び出しの登録だけである。

| 変換先 | 生成するもの |
|---|---|
| `.claude/` | `settings.json` の hooks に呼び出しを登録 |
| `.cursor/` | hooks の該当イベントへ呼び出しを登録 |
| `.codex/` | `config.toml` の hooks へ呼び出しを登録 |

スクリプトは複製しない。複製すると片側だけが更新される穴が生まれるためである。

Cursor には `beforeShellExecution` 等の hook 機構があり、Codex は信頼されたプロジェクトでリポジトリ内の hooks を読む。この 2 点が配線可能であることの根拠である。

派生物のずれ検知は、丸ごと生成されるファイルだけを台帳の対象とする。対象は `.claude/rules/` 配下の `rule.md` と `.cursor/rules/*.mdc` である。`AGENTS.md` と各ツールの hooks 登録ファイルは、既存の内容の一部だけを差し替える方式のため対象外とする。ファイル全体のハッシュが人の手による他の編集でも変わり、規約由来のずれと区別できないためである。

判定にはファイルの内容から求めた SHA-256 を使う。更新時刻は使わない。git の操作や別のツールでも時刻は動くためである。

## 7. フォーマッタの合成

linter と違い 1 対 1 にならない。Prettier、Biome、`.editorconfig` のいずれも、プロジェクトに 1 つしか設定ファイルを置けないためである。

`formatter` 鍵は写し先の種類だけを宣言する。矯正する値そのもの（インデント幅・引用符・行長）は front matter が持たない。値は規約本文が日本語で述べ、設定ファイルへの反映は人が行う。

生成スクリプトが検出できる矛盾は 1 種類だけである。`none` を除く `formatter` 指定に 2 種類以上の値が混在する場合（規約 A が `prettier`、規約 B が `biome`）を矛盾とし、生成を止めて報告する。同じ種類を指す規約が複数あることは矛盾ではない。

値の水準の矛盾を機械的に検出するには、front matter が矯正値そのものを持つ必要がある。これは本設計の対象外とし、10 節に記す。

## 8. 決定事項と根拠

以下の 2 点を決定事項として定める。

1. **`enforcement` は `advisory` と `none` の 2 値とし、`block` は初期対象外とする**。根拠：提案から自動生成された検査がいきなり作業を止めると、誤検知のたびに現場が規約そのものを不信に感じる。まず `advisory` で運用し、実績が出てから現場の判断で手作業により `block` へ昇格させる。昇格を提案から自動で行うことはしない
2. **取り込み直後の `status` は `draft` とする**。根拠：取り込みスキルの誤書き込みを 1 段止めるためである。`draft` の規約は派生生成の対象外であり、人が `approved` に変えたものだけが各ツールへ写る

## 9. 整合の検査

生成スクリプトは実行時に以下を検査する。

| 検査キー | 内容 | 不合格時 |
|---|---|---|
| 鍵-対応整合 | `checkable: true` なら `checker` が実在し、`false` なら `uncheckableReason` が非空 | 生成を止める |
| 検査-テスト同伴 | `checker` があるなら `check-<子>.test.sh` も実在する | 生成を止める |
| 適用範囲-必須 | `scope: scoped` なら `globs` が非空 | 生成を止める |
| 階層-一致 | `parent` と `key` がフォルダ名と一致する | 生成を止める |
| 矯正-矛盾なし | 複数規約の `formatter` 指定に矛盾がない | 生成を止めて矛盾を報告 |
| 派生-未承認除外 | `status: draft` の規約が派生物に含まれていない | 生成を止める |
| 親宣言-実在 | 各親フォルダに `parent.yml` が実在し、`key` がフォルダ名と一致する | 生成を止める |

## 10. 触れない範囲

この設計は以下を扱わない。

- hook スクリプトの中身の自動生成。`checkMethod` の自然文から linter を書き起こす作業は取り込みスキルの責務であり、本設計は形式だけを定める
- 既存の規約提案 HTML の意匠
- `docs/screens/` と `docs/common/` の形式
- フォーマッタの矯正値そのものの合成。インデント幅・引用符・行長といった値を front matter が持たないため、値の水準での矛盾検出と自動合成は行わない。値は規約本文が述べ、設定ファイルへの反映は人が行う
