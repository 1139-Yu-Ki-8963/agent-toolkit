# 案件フォルダ設計

この文書は、AI 支援案件でコンサルタントが持つ案件フォルダについて、構成を決めた理由と、道具箱の業務フローとの対応を書いた設計書です。新しい案件は、道具箱の `templates/案件雛形/` を `clients/<案件名>/`(道具箱の git の管理外)へ複製し、`clients/<案件名>/` で `git init` して始めます。この文書と雛形は、案件の名前を `<案件名>` のような置き換え用の名前で書きます。

## 構成と決まりの置き場

- **フォルダの構成と、フォルダとファイルの役割**: 雛形の `README.md` の「構成」と「フォルダとファイルの役割」に書いてあります。
- **AI がものを置くフォルダと名前**: 雛形の `.claude/rules/case-folder-placement/case-folder-placement-rule.md` が決めます。
- **AI がポータルの `data.js` を直すときと直し方**: 雛形の `.claude/rules/portal-operation/portal-operation-rule.md` が決めます。

## 構成を決めた理由

**課題ごとのフォルダ**
- 決めたこと: `作業/`、`成果物/`、`納品/` は、課題のフォルダの中に置きます。課題のフォルダは、依頼のフォルダの中に置きます。
- 理由: 1 つの課題の作業の途中のものから納品したものの写しまでが 1 つのフォルダにまとまり、依頼が増えても、コンサルタントは雛形の `依頼内容/依頼名/` を 1 つ複製するだけで済みます。
- 根拠: Thomson Reuters の Engagement Manager は、新しい案件のフォルダを雛形から複製して作ります(https://www.thomsonreuters.com/en-us/help/engagement-manager/user-guide/work-with-advanceflow-folders)。Imperial College London の手引きは、フォルダの名前が中身を表すように求めています(https://www.imperial.ac.uk/research-and-innovation/support-for-staff/scholarly-communication/research-data-management/organising-and-describing-data/naming-files-and-folders/)。

**ルートの `参照資料/`**
- 決めたこと: 先方から受け取った原本は、依頼や課題で分けずに、ルートの `参照資料/` に置きます。
- 理由: 1 つの原本を 2 つ以上の課題で使っても、置き場が 1 つに決まります。
- 根拠: Cookiecutter Data Science は、元のデータを変えないものとして扱います(https://cookiecutter-data-science.drivendata.org/opinions/)。

**`案件管理/` の 3 つのフォルダ**
- 決めたこと: 依頼のフォルダの外に、`議事録/`、`依頼にまたがる送付物/`、`社内向け/` を置きます。
- 理由: 会議の文書の置き場の理由は、規約の規則「会議の文書の置き場」に書いてあります。2 つ以上の依頼にまたがる送付物の写しは、1 つの依頼の `納品/` に置くと、ほかの依頼から見つけられないので、依頼のフォルダの外に置きます。社内の書類は、先方に見せるものと混ざらないように、`社内向け/` に分けます。道具箱の業務管理ポータルも、会議の一覧を課題の一覧とは別に持ちます(`../13_業務管理ポータル設計/02_データモデル設計.md`)。
- 根拠: CivicActions の手引きは、社内のフォルダと先方に見せるフォルダを分けています(https://guidebook.civicactions.com/en/latest/06-project-management/project-folder/)。

**ルートの `portal/`**
- 決めたこと: 道具箱の業務管理ポータルの画面 `index.html` と、案件 1 件の仮の値だけを持つ `data.js` を、雛形の `portal/` に置きます。
- 理由: 業務管理ポータルの運用設計(`../13_業務管理ポータル設計/03_運用設計.md`)は、実案件のポータルを `clients/<案件名>/portal/` に置くと決めています。コンサルタントは、雛形を複製し、`data.js` の `<案件名>` と `<期間と定例の曜日>` を書き換えれば、ポータルも用意できます。道具箱の `portal/data.js` は公開するデモのデータなので、雛形の `data.js` は、画面を出すのに要る案件 1 件の仮の値だけを持ちます。雛形の `index.html` は、道具箱の `portal/index.html` の renderProjToast が返す文から、括弧の中の「このデモの実データはA社案件のみ収録」を除いたものです。
- 根拠: Thomson Reuters の Engagement Manager は、新しい案件のフォルダを雛形から複製して作ります(https://www.thomsonreuters.com/en-us/help/engagement-manager/user-guide/work-with-advanceflow-folders)。

**名前の日付**
- 決めたこと: 先方へ見せた版と渡した版の写しを入れるフォルダの名前と、会議の文書のファイルの名前は、`YYYYMMDD` の日付で始めます。日付の決め方は、規約の規則「名前に入れる日付の決め方」に書いてあります。
- 理由: いつの時点のものかが名前で分かり、フォルダの中が日付の順に並びます。
- 根拠: Cornell 大学の手引きは、名前の日付を `YYYYMMDD` の形で書くように求めています(https://data.research.cornell.edu/data-management/storing-and-managing/file-management/)。

## 業務の流れとファイルの対応

道具箱の 7 フェーズ(`../01_コンサル業務フロー/コンサル業務フロー.md`)のどのフェーズでも、コンサルタントと AI は、会議の文書を `案件管理/議事録/` に、先方から受け取った資料を `参照資料/` に置きます。AI は、会議の文書と受け取った資料を置いたあとに、`portal/data.js` を、雛形の `.claude/rules/portal-operation/portal-operation-rule.md` に従って直します。フェーズごとの置き場は次のとおりです。

**1. 課題の受付と事例照合、2. 現場ヒアリング、3. 業務の棚卸し、4. AI化レベル判定**
- 置き場: このフェーズの出力(課題受付簿、確認依頼リスト、課題サマリー、業務棚卸し表)は、依頼のフォルダができる前に作ります。AI は、規約の規則「置き場か名前が決まらないものの扱い」に従い、置き場をユーザーに尋ねてから置きます。

**5. 施策設計・WBS化**
- 置き場: コンサルタントは、先方から依頼を受けたら雛形の `依頼内容/依頼名/` を複製して依頼の名前に変え、依頼を課題に分けたら雛形の `依頼内容/依頼名/課題名/` を複製して課題の名前に変えます。見積と提案書の下書きは `案件管理/社内向け/` に置きます。

**6. 実行・稼働管理**
- 置き場: コンサルタントと AI は、課題ごとに、作業の途中のものを `作業/` に、確定版を `成果物/` に置きます。先方へ見せた版の写しは `成果物/提示済み/YYYYMMDD/` に、渡したものの写しは `納品/YYYYMMDD_名前/` に置きます。2 つ以上の依頼にまたがる完了報告の写しは、`案件管理/依頼にまたがる送付物/YYYYMMDD_名前/` に置きます。

**7. 効果測定・定着化**
- 置き場: コンサルタントと AI は、測定した課題の `作業/` に測定の途中のものを、`成果物/` に測定の結果を置きます。
