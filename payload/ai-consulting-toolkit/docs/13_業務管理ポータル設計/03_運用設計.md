# 業務管理ポータル 運用設計

## 1. 運用の全体像

AIが議事録・メール・チャットから情報を取り込み、`data.js`を更新する。人は確認と判断だけを行う。

書き込みの主体は常にAIであり、手動の追加・編集ボタンは置かない。人が担う操作は、資料の確認済/差戻しの変更と、判断・仮説の記入に限る。

## 2. データ更新フロー

データ更新は`consult-portal-update`スキルが担う。スキルは議事録・メール・チャットなどの素材を読み取り、対象エンティティの該当フィールドを更新する。

すべての更新に出典(いつ・どこから)を必須で付与する。出典の実装先は次のとおりである。

| 更新対象 | 出典の実装先 |
|---|---|
| issue.notes | 各エントリの3番目の要素(src) |
| doc | fromフィールドと受領日 |
| meeting | 会議そのものが出典になる |

出典のない更新は行わない。

## 3. 人の確認操作の位置づけ

資料の確認済/差戻しへの変更(doc.status)は、人が行う専用の軽い操作とする。

判断・仮説(issue.notesのtype=j)、リスク(type=r)、論点(type=q)の記入も人が行い、記名(srcフィールドに記入者名と日付)を必須とする。事実(type=f)はAIが集約し、出典を付ける。

将来これらの操作を拡張する場合も、専用の軽い操作に留め、汎用の追加・編集用インターフェースは設けない。

## 4. 更新検証手順

更新後は、次の順で検証する。

1. `scripts/verify-portal-data.sh`を実行し、4系統を検査する。
   - 構文検査: `data.js`がJavaScriptとして読み込めるかを確認する。
   - 必須フィールド検査: 各エンティティの必須項目が揃っているかを確認する。
   - 状態値検査: 各フィールドの値が定義済みの取りうる値かどうかを確認する。
   - 参照整合検査: 参照キーが対応する配列に実在するかを確認する。
2. 検証を通過したら、ブラウザで画面を開き、描画を目視で確認する。

## 5. 版管理

版管理はgit commitに委ねる。専用の版管理機構は持たない。

`data.js`を更新するたびにcommitし、commitメッセージには更新元(議事録の日付等)を記載する。完全な履歴はgitのログで追跡する。

## 6. 保守時の禁止事項

- 手動の追加・編集ボタンを実装しない。
- スキーマ(`02_データモデル設計.md`参照)に定義のないフィールドを追加しない。
- 出典のない更新をしない。
- レイアウト不変条件(`01_画面設計.md`参照)を変更しない。
- 「ボール」等の口語表現を使わない。「当社の対応タスク」「先方(A社)の対応タスク」「要対応」「申請中」「差戻し」等、プロトタイプの語彙に合わせる。

## 公開デモと実案件運用の分離

リポジトリ内の`portal/`は公開payload(agent-toolkit)へ同期される。したがって`portal/data.js`はモックデータ固定のデモとして扱い、実案件データを書き込まない。

実案件の運用手順は次のとおり。

1. `clients/<案件名>/portal/`へ`portal/index.html`と`portal/data.js`を複製する
2. 以後の更新は複製先のdata.jsに対してconsult-portal-updateスキルで行う
3. 検証は`verify-portal-data.sh <複製先のdata.jsのパス>`で行う(スクリプトは引数のパスを検査する)
4. `clients/`はgit管理外のため、顧客情報がリポジトリと公開先に載ることはない
