# hook の書き方の規約

## この規約について

この規約は、Claude Code の settings.json に登録する hook と、その hook が呼ぶスクリプトの書き方の規約です。この規約は、hook の登録の形、スクリプトと README と点検の依頼の文の置き場と名前と中身、スクリプトの入出力、ほかの仕組みが追加する登録の扱い、雛形が持つものを決めます。スクリプトの骨格は雛形 hook-script-template が、README の形は雛形 hook-readme-template が持ちます。

## この規約が満たすこと

- 規則は、settings.json の hook の登録と、`hooks/` の下のスクリプトと README と点検の依頼の文と、雛形と完成例を見れば合否が決まる文で書き、判定の仕方を持つ。
- 規則は、登録を見れば、どのスクリプトがいつ動くかが 1 つに決まる形を決める。
- 規則は、1 つの発火点で動く検査の結果が、AI に 1 つの出力で渡る形を決める。
- 複数の選択肢から 1 つを採用する規則は、採用した理由と採用しなかった理由を持つ。
- 文は、文章の書き方の規約に従う。

## 適用する場面

settings.json に hook を登録するとき。`hooks/` の下のスクリプトと README と点検の依頼の文を書くとき、直すとき、消すとき。雛形 hook-script-template と hook-readme-template を書くとき、直すとき。ほかの仕組みが settings.json に追加した登録を扱うとき。

## 前提とする規約

なし

## 目次

「守ること」の節は、語の定義、登録、名前とフォルダ、スクリプトと README と点検の依頼の文の中身、入出力、ほかの仕組みが追加する登録、雛形が持つもの、この規約を直すときの順に並ぶ。

1. この規約で使う語の定義
2. 登録
3. 名前とフォルダ
4. スクリプトと README と点検の依頼の文の中身
5. 入出力
6. ほかの仕組みが追加する登録
7. 雛形が持つもの
8. この規約を直すとき

## 守ること

### この規約で使う語の定義

この規約と、hook の登録とスクリプトと README と点検の依頼の文を読むとき、書くとき。

規則 1: 語は、次の定義の意味で使う
- 判定の仕方: 機械的
- この規約と、登録とスクリプトと README と点検の依頼の文の中では、次の表の語を、表の意味で使う。1 つのものは、1 つの語で呼ぶ。

| 用語 | 意味 |
|---|---|
| settings.json | Claude Code の設定ファイル。`hooks` の項目に、hook の書き込みを持つ |
| 登録 | settings.json の `hooks` の中の、hook 1 つ分の書き込み。いつ動かすか(発火点)、どのツールのときか(matcher)、何を動かすか(`type` と `command`)、何秒まで待つか(`timeout`)を持つ |
| 発火点 | 登録をいつ動かすかを表す名前(`PostToolUse` はツールが動いたあと、`Stop` は AI が回答を終えたとき)。settings.json では、`hooks` の中の見出しの名前 |
| matcher | 登録を動かすツールの名前の条件(`Edit\|Write` は Edit か Write のとき)。settings.json では、発火点の下の `matcher` の値 |
| スクリプト | 登録の `command` が呼ぶ、`hooks/` の直下の JavaScript のファイル 1 本。hook が動くときに Claude Code が実行する |
| スクリプトの名前 | スクリプトのファイル名から拡張子 `.js` を除いたもの |
| 検査 | スクリプトの中の、1 つのことを確かめる関数 |
| 点検の依頼の文 | 検査が AI に渡す、文の意味の点検を頼む文を持つ `.md` のファイル 1 本 |
| テスト | スクリプトのフォルダの中の、検査ごとの確かめを持つ node のテストのファイル 1 本。名前は `<スクリプトの名前>.test.js` |
| まとめた文章 | スクリプトが、検査の結果の全件を 1 つにまとめて AI に渡す文章 |
| `hookSpecificOutput.additionalContext` | Claude Code が AI の文脈に足す文を受け取る、標準出力の JSON の鍵 |

次の見本は、settings.json の `hooks` の書き方である。この見本は、発火点 `PostToolUse`、matcher `Edit|Write` の登録を 1 つ持つ。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "node <プロジェクトのパス>/hooks/post-tool-use-write-file.js", "timeout": 60 }
        ]
      }
    ]
  }
}
```

### 登録

settings.json の `hooks` に登録を追加する、直す、消すとき。

規則 1: 登録が持つ type と command の値
- 判定の仕方: 機械的
- 登録の `type` は、Claude Code が登録をどう動かすかを選ぶ値で、コマンドを実行する `command` とする。
- 登録の `command` は、`node <スクリプトのパス>` の 1 つのコマンドとする。パスは、`/` か `~` で始まる文字列とする。
- 採用した理由: `type` が `command` の登録は、`command` の文字列をそのまま実行するので、登録を読めば、動くスクリプトが 1 つに決まる。
- 採用した理由: 検査の中身の変更は、スクリプトの中だけで済む。
- 採用した理由: 登録の `command` は、`node` とパスの 2 語だけなので、macOS、Linux、Windows の 3 つの OS で同じように動く。
- 採用しなかった理由: 検査の本体を `command` に書く形は、settings.json を読む人に JSON の文字列の中のコードを読ませ、検査を追加する人に settings.json を書き換えさせる。
- 採用しなかった理由: `type` が `prompt` か `agent` の登録は、Claude Code が AI に文を渡して判定させる形で、検査の順と結果のまとめが AI の側に移り、機械的な検査を持てない。

規則 2: 発火点と matcher ごとに、スクリプトを 1 本とする
- 判定の仕方: 機械的
- 1 つの発火点と 1 つの matcher(matcher を持たない発火点では、1 つの発火点)は、この規約に従う登録を 1 つだけ持つ。
- 1 つのスクリプトを `command` で呼ぶ登録は、1 つとする。
- 採用した理由: Claude Code は、同じ発火点の登録を並列に動かし、結果を別々に AI に渡す。スクリプトを 1 本にすると、検査の順と、結果を 1 つにまとめる場所が、スクリプトの中に決まる。
- 採用しなかった理由: 検査ごとに登録を分ける形は、結果を別々に AI に届け、各登録のスクリプトに同じファイルを読み直させる。

規則 3: 登録が持つ timeout
- 判定の仕方: 機械的
- 登録の `timeout` の値は、秒で 60 以下とする。
- 採用した理由: hook が止まったとき、Claude Code は、hook が動くたびに timeout の秒数を待ってから次に進む。60 秒は、外部のコマンドの起動を含む検査が終わる長さで、待ちに気づける長さである。
- 採用しなかった理由: 既定の値 600 秒は、検査が止まったときの待ちが長い。

### 名前とフォルダ

`hooks/` の下のスクリプトと README と点検の依頼の文を置くとき、名前を付けるとき。

規則 1: hooks/ の中のどこに置くか
- 判定の仕方: 機械的
- `hooks/` は、スクリプトと README と点検の依頼の文とテストを持つ。hook と、hook 以外の仕組みの両方が呼ぶコマンドは、`hooks/` の外に置く。スクリプトは、そのコマンドをパスで呼ぶ。
- スクリプトと README と点検の依頼の文とテストは、次の形で置く。

```text
hooks/
├── <スクリプトの名前>.js
└── <スクリプトの名前>/
    ├── README.md
    ├── <点検の依頼の文のファイル名>
    ├── <スクリプトの名前>.test.js
    └── <2 本以上のスクリプトが require で読み込む部品のファイル名>.js
```

- 2 本以上のスクリプトが `require` で読み込む部品は、その部品を読み込むスクリプトのうち、名前の辞書順で最初のスクリプトのフォルダに置く。

- 採用した理由: スクリプトが `hooks/` の直下に並ぶので、`hooks/` の一覧がそのまま登録の一覧になる。
- 採用しなかった理由: スクリプトもフォルダの中に置く形は、登録の `command` のパスが 1 段深くなり、`hooks/` の一覧にスクリプトが並ばない。

規則 2: スクリプトの名前
- 判定の仕方: AI の推論
- スクリプトの名前は、`<発火点の部分>-<matcher の部分>` の形とし、英小文字、数字、ハイフンで書く。
- 発火点の部分は、発火点の鍵を英小文字にして語の境をハイフンでつないだもの(`post-tool-use`)とする。
- matcher の部分は、matcher が指すツールを日常の語にしたもの(`Edit|Write` → `write-file`)とする。matcher を持たない発火点では、名前は発火点の部分だけ(`stop`)とする。

### スクリプトと README と点検の依頼の文の中身

スクリプトと README と点検の依頼の文を書くとき。

規則 1: スクリプトを動かすものは node
- 判定の仕方: 機械的
- スクリプトは、node で動く JavaScript とする。
- 採用した理由: node は、macOS、Linux、Windows の 3 つの OS で同じコマンド名で動く。
- 採用しなかった理由: sh は、PowerShell から起動される Windows の hook では動かない。

規則 2: スクリプト、README、点検の依頼の文が持つもの
- 判定の仕方: 機械的
- スクリプトは、雛形 hook-script-template の本文のとおりに書く。
- README は、雛形 hook-readme-template の本文のとおりに、日本語で書く。
- スクリプトの先頭の注釈は、README のパスの 1 行とする。
- 点検の依頼の文は、日本語で書き、README の検査の表の「根拠の規約と規則の観点」の値と同じ根拠を持つ。
- テストは、README の検査の表のすべての行について、列「テスト」の名前を持つテストを持つ。テストは、見本の標準入力をスクリプトに流し、終了コードと出力を比べる。
- 採用した理由: 読む人は、README で中身を知る。注釈が README のパスだけを持つので、中身は README の 1 か所にある。
- 採用しなかった理由: 注釈だけに書く形は、読む人がスクリプトを開くことになり、書く項目が揃わない。

規則 3: 検査が確かめることと、AI に点検を頼むこと
- 判定の仕方: AI の推論
- 検査は、ファイルの有無、文字列の一致、外部のコマンドの終了コードのように、機械的に決まることを確かめる。
- 文の意味で決まることは、検査が点検の依頼の文で AI に点検を頼む。

### 入出力

スクリプトの入力と出力を書くとき。

規則 1: 標準入力が持つ鍵
- 判定の仕方: 機械的
- スクリプトは、Claude Code が標準入力に渡す JSON の全文を読む。この JSON は、次の表の鍵を持つ。

| 鍵 | 持つもの | 持つ発火点 |
|---|---|---|
| `hook_event_name` | 発火点の名前 | すべて |
| `session_id` | セッションの ID | すべて |
| `transcript_path` | 親の会話の記録のファイルのパス。サブエージェントの中のツールのときも、親の会話の記録を指す | すべて |
| `agent_id` | サブエージェントの ID。サブエージェントの中のツールのときだけ持つ | すべて |
| `tool_name` | ツールの名前 | PreToolUse、PostToolUse |
| `tool_input.file_path` | Edit か Write が変えるファイルのパス | PreToolUse、PostToolUse |
| `tool_input.notebook_path` | NotebookEdit が変えるファイルのパス | PreToolUse、PostToolUse |
| `stop_hook_active` | Stop の hook が同じ回答で既に 1 回動いたか(true か false) | Stop |

- 発火点が PostToolUse のときは、スクリプトは、ファイルの全文を `tool_input.file_path` のパスから読む。
- 採用した理由: ファイルの全文をパスから読むと、Edit と Write のどちらの編集でも、検査は同じ全文を見る。
- 採用しなかった理由: `tool_input` の `new_string` や `content` から中身を得る形は、Edit では変えた部分だけになり、検査がファイルの全文を見られない。

規則 2: 検査の結果の形
- 判定の仕方: 機械的
- 検査は、次の 3 つを持つ結果を 0 件以上返す。
  - `kind`: `violation`(機械的に決まった違反)か `prompt`(AI への点検の依頼)
  - `source`: 検査の名前
  - `text`: AI に渡す文
- スクリプトは、結果の全件を、`kind` ごとの見出しの行(「違反」「点検の依頼」)と、`source` の行と、`text` の行で、まとめた文章にする。

規則 3: 終了コードと出力先
- 判定の仕方: 機械的
- スクリプトは、次の表の場合のうち合う 1 つの行の終了コードと出力先と出力の形で終える。

| 発火点 | 場合 | 終了コード | 出力先 | 出力の形 |
|---|---|---|---|---|
| すべて | 標準入力が JSON として読めない | 0 | なし | なし |
| すべて | `hook_event_name` が登録の発火点と違う | 0 | なし | なし |
| すべて | 結果が 0 件 | 0 | なし | なし |
| Stop 以外 | 結果に `violation` が 1 件以上ある | 2 | 標準エラー | まとめた文章 |
| Stop 以外 | 結果が `prompt` だけ | 0 | 標準出力 | `hookSpecificOutput.additionalContext` の値にまとめた文章を入れた JSON |
| Stop | `stop_hook_active` が true | 0 | なし | なし |
| Stop | 結果が 1 件以上ある | 2 | 標準エラー | まとめた文章 |

- 採用した理由: Claude Code は、終了コード 2 の標準エラーを AI に誤りとして渡し、終了コード 0 の `hookSpecificOutput.additionalContext` を文脈として渡す。スクリプトは、違反を直す対象として誤りの形で渡し、点検の依頼を文脈の形で渡す。
- 採用した理由: hook は同じ編集で 1 回だけ動き、終了コード 2 で終えるときは標準エラーの文章だけが AI に届く。見出しの行「点検の依頼」が、誤りと点検の依頼を AI に見分けさせる。
- 採用した理由: PreToolUse では、終了コード 2 で終えると、Claude Code はツールの呼び出しを止め、標準エラーの文を止めた理由として AI に渡す。
- 採用した理由: Stop では、終了コード 2 の標準エラーだけが AI に続きの回答を出させる。`stop_hook_active` が true のときに終了コード 0 で終える行が、hook を 1 回の回答につき 1 回だけ動かす。
- 採用しなかった理由: すべてを終了コード 0 で渡す形は、違反が文脈に埋もれて直されない。
- 採用しなかった理由: すべてを終了コード 2 で渡す形は、点検の依頼が誤りとして扱われ、AI が直す対象のない誤りを探す。
- 採用しなかった理由: 終了コード 0 の JSON の `decision: "block"` と `reason` で違反を渡す形は、`reason` が 1 つの文字列で、`hookSpecificOutput.additionalContext` と並べて持てるかが公式の文書に書かれていない。

### ほかの仕組みが追加する登録

スキルや外部のアプリが settings.json に追加した登録を扱うとき。

規則 1: この規約が当てはまる登録の範囲
- 判定の仕方: 機械的
- この規約は、`command` が `hooks/` の直下のスクリプトを呼ぶ登録に当てはまる。
- ほかの登録は、この規約の外とし、追加した仕組みが書いた形のままとする。
- 採用した理由: この規約の外の登録は、それを追加した仕組みが保守する。
- 採用しなかった理由: スクリプトに取り込む形は、追加した仕組みが登録を書き直すたびに、取り込みをやり直す。

規則 2: スクリプトの検査が確かめることと、スキルが追加する登録の検査が確かめることの違い
- 判定の仕方: AI の推論
- スクリプトの検査は、スキルが追加する登録の検査と別のことを確かめる。
- 採用した理由: Claude Code は、`command` の文字列が同じ登録だけを 1 回にまとめる。スクリプトの検査とスキルの登録の検査が別のことを確かめると、どの検査も、同じファイルに 1 回ずつ動く。
- 採用しなかった理由: スキルの雛形の登録をスクリプトを呼ぶ形に直すと、スキルとリファレンスとテスト計画書の直しが要る。

### 雛形が持つもの

雛形 hook-script-template と hook-readme-template を書くとき、直すとき。

規則 1: 雛形が持つもの
- 判定の仕方: 機械的
- 雛形は、使う場面と、省ける部分と、雛形の本文を持つ。
- 雛形 hook-script-template の本文は、スクリプトの骨格の JavaScript を持ち、書く人が入れる部分を注釈で示す。
- 雛形 hook-readme-template の本文は、README に書く項目を、表の列の名前か項目の名前で持ち、書く人が入れる値を山かっこで示す。

規則 2: 雛形の完成例が持つもの
- 判定の仕方: 機械的
- 雛形の完成例は、雛形の本文のとおりに書いたスクリプトか README の全文を、雛形ごとに 1 本持つ。

### この規約を直すとき

この規約に規則を追加する、直す、消すとき。

規則 1: 節の順と、新しい節を置く位置
- 判定の仕方: 機械的
- 「守ること」の節は、目次の順に並ぶ。
- 新しい節は、この規約を直すときの節の前に置く。
