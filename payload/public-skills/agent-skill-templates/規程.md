# スキル運用規程

正本は設計書 `docs/design/skills/スキル運用規程.md` にある。雛形の組 `templates/agent-skill/規程.md` と、各スキルの `references/規程.md` はその写しで、正本を直したときは同じ作業の中で写しも直す。

この環境で作成、更新するすべてのスキルに共通する決まり。3 つの原則と、20 の規則からなる。規則を指すときは「規則 7」のように番号で呼ぶ。

## 読み方

- 規則は、原則を具体化したものである。規則に書いていない場面では、原則に照らして判断する。
- 規則に合うかどうかは、別のセッションで reviewing-agent-skills を使って 1 回照らす。指摘を直したあとは、実際に使って、困った箇所を直す。
- この規程に書くのは、できあがった `SKILL.md` について言う文である。線引きは規約 `writing-placement`(文の置き場の判定)に従う。
- 複数のスキルが共有する資料(規程、雛形、手引き、記入例)は、正本を雛形の組 `templates/agent-skill/` に置き、各スキルは `references/` にあるその写しを読む。
- 数の上限を超えるときは、分けるか、削るか、作らない。
- 規程と照らすときは、規則が対象とする行為や構造(繰り返し、委任、スクリプト、ファイルの出力など)が対象のスキルに 1 つもなければ「該当なし」とし、あって条件を満たすなら「合格」とする。その不在を「なし」と書くことを求める規則(規則 3 の「なし」、規則 18 と 19 の一覧)は、合格か違反かを決める。1 つの記述漏れが複数の規則に反するときは、反するすべての規則に計上する。

## 原則

1. **確定**: スキルを読んだ AI が、次に何をするかを一意に決められる。1 文に 1 つの動作を、対象、方法、終わりの条件とともに書く。
2. **閉じている**: スキルが読むもの、書くもの、表示するものは、`SKILL.md` に列挙したものだけである。
3. **小さい**: 1 つのスキルは 1 つの場面の 1 つの作業だけを扱い、数の上限の中に収める。

## 規則

### スキルの定義

1. スキルは、特定の場面で繰り返し必要になる、1 つの作業の手順であり、ユーザーがその場面で呼んで実行させるものである。常に守らせたいことと、条件付きであってもユーザーが呼ばずに守られることを期待する方針(「〜のときは必ず〜する」)は、規約(`.claude/rules` に置く規則の文書)にする。1 回しか行わない作業は、その場で依頼する。見分ける問いは「その場面が来たとき、ユーザーはこれを呼ぶか、呼ばずに守られることを期待するか」である。
2. 1 つのスキルは、1 つの場面と 1 つの目的だけを扱う。

### 構成

3. `SKILL.md` は、全体像(目的、開始時の入力、最終出力、流れ)、前提ツール、使用するスクリプト、使用するリファレンス、phase と step の節を、この順に持つ。フロントマターの description は、何をするスキルか、発動する場面、発動しない場面の 3 文とする。開始時の入力、前提ツール、使用するスクリプト、使用するリファレンスが 0 件のときは、表の代わりに「なし」と書く。本文は 200 行以内とする。前提ツールに挙げるのは、step が実行するコマンドのうち OS に標準で入っておらず、かつ使う場面の外にあるもの(コミットの直前に使うスキルの git は、使う場面の中にあるので挙げない)とする。前提ツールがあるときは、探す、不足を見る、インストールの意思を確認する、インストールする、の 4 step の phase を先頭に置く。
4. 流れは phase と step に分ける。phase は 5 個まで、1 つの phase の step は 5 個まで(ちょうど 5 個は収まる側)。番号は 1 から始まる整数とし、「step 2-1」の形で呼ぶ。
5. すべての step に、種別、入力、出力、手順を書く。分岐の step では条件と 2 つの行き先が、ユーザー確認の step では質問と選択肢の表が、手順に当たる。種別は「固定の手順」か「AI による推論」のどちらかとする。数える、列挙する、形式を検証する、変換する、のように毎回同じ結果になる作業は固定の手順とし、結果の意味づけ、進む道の選択、失敗したときの対処は AI による推論とする。
6. 固定の手順の step には、使う機能の名前と渡す値を書く。AI による推論の step には、判断の観点と合格の基準を書く。境目が割れやすいときは、合格の側と不合格の側の例を 1 つずつ書く。

### 確定

7. 手順の 1 文は、1 つの動作と、その対象、方法、終わりの条件を含む。「確認する」「調査する」「整理する」「適切に」「必要に応じて」「など」は、対象と方法を添えたときだけ使える。
8. 対象の範囲(どのフォルダか、どの種類のファイルか、直下だけか全階層か、除外するもの)を書く。対象が複数件になり得る step には、対象が存在しないとき、結果が 0 件のとき、想定より多いときの動作を書く。起こり得ないときは、その理由を書く。
9. 文面や手順の中で実行のたびに変わる値は `<ツールの名前>` のように山かっこで書き、その値がその step のどの入力から来るかをたどれるようにする。複数になり得る値は、件数と区切り方を書く。
10. 機能は、次の 7 つの名前で書く。機能がないときは、表の代わりの動作をとる。

| 機能の名前 | 意味 | ないときの代わりの動作 |
|---|---|---|
| 選択の画面 | 選択肢を提示し、ユーザーが選ぶまで止まる | チャットに番号付きで選択肢を表示し、回答を待つ |
| ファイルを読む | 指定したパスの中身を読む | 中止する |
| ファイルを書く | 指定したパスに書き込む | 中止する |
| ファイル名の検索 | 名前の規則に合うファイルを探す | コマンドの実行で代用する |
| 内容の検索 | ファイルの中身から文字列を探す | コマンドの実行で代用する |
| コマンドの実行 | シェルのコマンドを実行する | 中止する |
| サブエージェントの起動 | 別の文脈で作業をさせる | 検証や照合の委任なら中止する。それ以外は親が順番に実行する |

### 閉じている

11. 開始時の入力は、項目ごとに、種類(ユーザーの発言、既存のファイル、コマンドの結果)、必須か任意か、受け取り方、読み取れないときの動作(聞き取る、既定の値を使う、AI が案を作る、中止する、のどれかと、それを行う step)を書く。ユーザーに聞くのは、依頼から読み取れず、機械的にも決まらない項目だけとする。入力を確定する質問は、本作業の最初の phase の 1 つの step にまとめる。
12. step の入力は、開始時の入力、先行する step が出力した受け渡し値、先行する step が作った最終出力の 3 種類だけとする。出力は、最終出力と受け渡し値の 2 種類だけとする。受け渡し値は、必ず後続の step の入力になる。
13. 完了した時点で、新しく作られたファイルと変更されたファイルは、全体像に列挙した最終出力と完全に一致する。実行の途中でだけ要るファイル(検証で実行者に書かせる成果物など)は、OS の一時フォルダの中に置き、完了と中止の前に消す。その置き場と消す step を `SKILL.md` に書く。
14. チャットへの表示は、次の 8 種類とし、step に書いた表示を行う。中止するときの表示は、中止の表示(理由、止まった step、ユーザーが次にすること)だけとする。ユーザーから質問を受けたときの回答は、いつでも行う。

| 種類 | いつ | 必ず含める内容 |
|---|---|---|
| 開始の表示 | 最初の step | スキルの名前、何をするか、最後に何を出力するか |
| phase の表示 | 各 phase の最初 | phase の番号と名前 |
| 前提ツールの表示 | ツールを探すとき、不足が分かったとき | ツールの名前、インストールが必要であること |
| ユーザー確認 | ユーザー確認の step | 質問の文と選択肢 |
| 聞き取り | 自由な回答を求めるとき | 質問の文と、答えの候補 3 つ(推奨を先頭に、理由を添える)。パスや ID のように固有の値しか答えようがない項目は、質問の文だけ |
| 中止の表示 | 中止するとき | 理由、止まった step、次にすること |
| 成果物の表示 | 最終出力をチャットに出すとき | 最終出力の名前と中身 |
| 完了の報告 | 最後の step | 最終出力の一覧とパス(パスがなければ「チャットに表示」、0 件なら「0 件」) |

### 流れ

15. 流れの書き方は、直列、分岐、繰り返し、やり直し、ユーザー確認、中止、委任の 7 つとする。直列以外の step は見出しにパターンの名前を書き、次の項目を書く。分岐は条件と 2 つの行き先(2 方向、1 段)。繰り返しは対象の一覧、範囲、終了の条件(1 段)。やり直しは戻り先、やり直す条件、終了の条件、進展がないときの動作。ユーザー確認は規則 17 の項目。中止は条件と表示の文面。委任は規則 20 の項目。見出しに書くパターンは、その step の主たるものとし、step の中に従属して置く中止とユーザー確認は、条件と文面(または質問と選択肢と行き先)をその step に書く。
16. 繰り返しとやり直しの終了の条件は、達成すべき状態で書く。やり直しには、進展がないとき(同じ問題が 2 回続けて残る、または問題の数が 2 回続けて減らない)の動作を書く。進展がないときは、残っている問題と原因を表示して、方法を変えて続けるか中止するかをユーザー確認で選ばせる。
17. ユーザー確認は、1 文の質問を選択の画面で提示し、2 個から 4 個の選択肢に、名前、選ぶと起こること、行き先の step を書く。選択肢にない回答のときの行き先を書く。推奨があれば先頭に置いて理由を添える。回答を得てから次へ進む。元に戻せない操作(インストール、上書き、削除)の前には、ユーザー確認を置く。

### 付属物

18. リファレンスは `references/` に置き、5 個まで、各 200 行以内、1 つの主題だけとする(スクリプトの説明書は、この件数と行数のどちらにも数えない)。毎回は使わない内容、1 つの step でだけ使う 10 行を超える内容、雛形や例や一覧のように見て使う資料は、リファレンスに置く。全体像、入出力の列挙、phase と step、各 step の種別と入出力、スクリプトとリファレンスの一覧は、`SKILL.md` に置く。リファレンスは、この実行の開始後に、使う step に到達したときに全文読む。
19. スクリプトは `scripts/` に置き、固定の手順だけを扱う。3 本まで、各 50 行以内(空行とコメント行を除いて数える)、引数 3 個まで、処理は 1 つ、終了コードは 0 を正常、1 を指摘あり、2 を呼び出しの誤りとする。1 本ごとに、空行とコメント行を除く 1 行ずつの処理と理由を書いた説明書を `references/scripts/` に、テストを `scripts/tests/` に置く。`SKILL.md` に書くスクリプトのパスは、`SKILL.md` があるフォルダからの相対とする。実行中に使うスクリプトとコマンドは、同梱したものと 1 行のコマンドだけとする。
20. サブエージェントへの委任は、独立した観点が複数あるとき、多くのファイルを読むがその中身が後で要らないとき、何も知らない実行者に検証させるとき、のどれかに限る。委任の step には、当てはまる条件、使うモデル、渡す入力(親が決めたパスの一覧)、返す出力の形、同時に起動する数を書く。返り値は受け渡し値とし、統合は親が行う。検証は、実行のたびに新しいサブエージェントで行う。委任は 1 つの phase に 1 つ、1 つのスキルに 3 つまで。
