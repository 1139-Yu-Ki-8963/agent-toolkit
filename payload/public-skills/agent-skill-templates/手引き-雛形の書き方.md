# 手引き: 雛形の書き方

スキルを作る側が、依頼を読み、構成の案を作り、雛形を埋めるときの手順と技法。ここに書くのは「どう書くか」であり、「合格か違反か」は規程が決める。読むのは作る側だけで、規程と照らす側(reviewing-agent-skills)は読まない。

## 仕分けの基準(この文書と規程と雛形の境目)

- 完成した `SKILL.md` を見て、合格か違反かを決められる文は、規程に書く。
- 何をどの順に、どう選んで書くかを教える文は、この手引きに書く。
- 節、項目、表の列、山かっこの名前といった骨格は、雛形に書く。雛形に注記を書かない。
- 完成した見本は、記入例に置く。

## 1. 依頼の読み取り

- 読み取るのは、文面に明示された内容だけとし、含意から推し量らない。読み取った値は要約せず、原文の語句を写す。
- 写すときは、項目の中核となる名詞句だけを写し、助詞と、依頼全体を覆う主動詞(「作って」「して」「したい」「書いて」など、スキルに何をさせるかではなく AI への依頼を表す動詞)は含めない。1 つの項目だけの文でも同じ。
- 1 つの語句が複数の項目の合図に当たるときは、目的を優先する。「毎回同じ結果になる作業」は、作業の説明に「毎回」または「スクリプト」を含む語があるときだけ読み取る。「毎回そうしてほしい」「常に」「必ず」のように、スキルを呼ぶ頻度や強制を表す語は、作業ではなく「使う場面」に写す(規則 1 の判定の根拠になる)。
- 合図の例: 「X をスキルにして」の X は目的。「〜で守らせたい」「〜のときに使う」は使う場面。「〜を受け取って」「〜を読んで」は開始時の入力。ツールの名前は前提とするツール。フォルダのパスは出力先のフォルダ。
- 明示されていない項目は「不明」とする。「ログを読む」とだけあっても、開始時の入力の指定とは決めない。

## 2. 聞き取り

- 必須の項目が「不明」のときだけ、1 回の発言にまとめて尋ねる。任意の項目と、読み取れた項目は尋ねない。
- 項目ごとに候補を 3 つ添え、推奨を先頭に置いて理由を書く。スキルの名前の候補は英小文字、数字、ハイフンだけで作る。依頼に手がかりのない項目の候補は、その目的のスキルの一般的な使われ方から作る。
- パスや ID のように固有の値しか答えようがない項目は、候補を添えない。

## 3. 構成の案の埋め方

- 埋める順序: 「phase と step の一覧」を先に下書きし、それを見て「前提ツール」「スクリプト」「リファレンス」「数の上限との照合」を埋め、残りを雛形の順に埋める。前提ツールは step が実行するコマンドから決まり、上限の数は一覧から数えるため。
- description は 3 文。何をするスキルか(目的から)、発動する場面(使う場面から)、発動しない場面(目的の近くにあって扱わない作業を 3 つ)。
- 日本語名は、何をするスキルかが分かる体言止めの短い名前。
- 任意の項目が「不明」なら AI が案を作り、「AI が案を作った点」に解釈を書く。案は依頼の目的を満たす最小の設計にとどめ、依頼にないツール、入力、step は、それなしでは最終出力を作れないときだけ足す。
- 種類が「コマンドの結果」の入力は、本作業の step の中でコマンドの実行の機能で読み取って受け渡し値にし、その step の入力に項目の名前を書く。
- 「毎回同じ結果になる作業」は、種別を固定の手順にした step として書く。
- 前提ツールに挙げるのは、step が実行するコマンドのうち OS に標準で入っていないもの(git、jq、gh、node、python3 など)。ls、grep、cat、wc、test、find と、インストールに使うコマンドは挙げない。使う場面がそのツールの操作の中にあるもの(コミットの直前に使うスキルの git など)も挙げない。1 つもなければ「なし」。
- 一覧の「内容」には、直列以外のパターンの step では、そのパターンが必ず書く項目(分岐の条件と 2 つの行き先、やり直しの戻り先と終了の条件、ユーザー確認の質問と選択肢、委任の条件とモデルと入出力の形と上限)も書く。「中止する条件」はその step で中止する場合をすべて書き、なければ「なし」。「判断の観点」は AI による推論の step にだけ書き、固定の手順は「なし」。
- 上限を超えるときは、step を減らすか、スクリプトを使わない形にして作り直す。作り直しても収まらないときだけ、スキルを分ける案を書いてユーザーに見せる。分けても収まらないときは中止する。

## 4. 雛形-SKILL.md の埋め方

- 山かっこの部分を構成の案の内容で埋め、山かっこの外の文はそのまま写す。全体像の「全体の決まり」は、書くことがなければ行ごと省く。開始時の入力が 0 件なら、表の代わりに「なし」と書く。フォルダのパスを山かっこに入れるときは、末尾の `/` を除いた形にそろえる(`<出力先のフォルダ>/SKILL.md` のように後ろに `/` を続けるため)。
- 前提ツールが「なし」のときは、phase「前提ツールの確認」の節と「流れ」の表の行を書かず、本作業の phase を phase 1 として番号を振る。step の番号、行き先、「流れ」の表は繰り上げた番号で書く。このとき、開始の表示は本作業の最初の step の「表示」の項目の先頭に置く。前提ツールがあるときは、インストールの方法を種類「分岐先の資料」のリファレンス `references/インストールの方法.md` に、「OS の見分け方」と OS ごとのコマンドの表の 2 節で書く。
- 本作業の phase と step は、構成の案の「phase と step の一覧」にある数だけ書く。聞き取りの step の型は、必須の入力を依頼から読み取れないことがあるスキルにだけ使う。聞き取りは流れのパターンではないので、見出しにかっこを付けない。
- 各 step の手順と表示の文面は、一覧の「内容」「中止する条件」「判断の観点」の 3 列から作る。案にない中止する条件と判断の観点を足さない。表示の文面と境目の例は、案になくても足してよい。
- 手順の 1 文は、動作、対象、方法、終わりの条件を含める。固定の手順なら使う機能の名前と渡す値を、AI による推論なら判断の観点と合格の基準を書く。境目が割れやすいときは、合格の側と不合格の側の例を 1 つずつ書く。
- 対象が複数件になり得る step(探す、数える、1 件ごとに行う)には、0 件のときと想定より多いときの動作を書く。起こり得ないときは、その理由を書く。常に 1 件の値を扱う step には書かなくてよい。
- 直列以外のパターンの step は、見出しに「step 2-3(繰り返し)」のようにパターンの名前を書き、規程の規則 15 が定める必ず書く項目を足す。step の中に従属して置く中止とユーザー確認は、見出しに書かず、条件と文面(または質問と選択肢と行き先)をその step に書く。
- 最終出力をチャットに出す step は、「表示」の項目に種類を「成果物の表示」と書く。
- 完了の確認の step 3-1 は、最終出力の表の「種類」の列に「ファイル」の行があるかどうかで、2 つの手順のどちらか 1 つを写す。ファイルのないスキルでは、step 3-1 の入力を、成果物の表示の名前(例: 最終出力「コミットの文面」)に書き換える。
- 使用するスクリプトの表が 0 件なら、表の代わりに「なし」と書く。使用するリファレンスの表も同じ。スクリプトの説明書は「使用するリファレンス」には書かず、「使用するスクリプト」の「説明書のパス」の列にだけ書く。
- スクリプトのパスは、`SKILL.md` があるフォルダからの相対で書く。

## 5. 付属のファイルの書き方

- リファレンスは、構成の案の一覧の 1 件と 1 対 1 で対応させ、その件の「種類」と「内容」の列に書いた内容を持たせる。
- スクリプトは、1 本ごとに説明書を `references/scripts/` に、テストを `scripts/tests/` に置く。テストは 1 行目にシェバンを持つ実行可能なファイルにする。テストが一時ファイルを作るときは、環境変数 `TMPDIR` の下(なければ `/tmp`)に作り、終了時に必ず消すコードを含める。OS 既定の一時領域への書き込みが拒まれる環境があるため。
- 説明書には、空行とコメント行を除く 1 行ずつの処理と理由を書く。
