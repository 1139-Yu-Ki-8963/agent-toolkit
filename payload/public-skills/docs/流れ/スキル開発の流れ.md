# スキル開発の流れ

この文書は、雛形と規約に沿ってスキルを作るときの、ウォーターフォールの流れと、各フェーズで使うスキルを示す。今のスキルは、雛形に沿った単純な作業を受け持つ。考えて決める作業は、新しいスキルとして流れの中に足す。流れ全体を統括するスキルは置かない。守るファイルの書き換えを決まったスキルの手順の中に限ることと、文書の変更のたびに照合を促すことは、hook が受け持つ。

## 全体図

フェーズごとに、使うスキルの名前を並べる。「未作成」は、スキルのフォルダがなく、要件定義書と設計書もないスキルを示す。

**1. 要件定義**
- defining-skill-requirements(未作成)

**2. 下書き**
- drafting-skill-with-template

**3. 静的検証**
- checking-skill-with-template(雛形と規約との照合) → fixing-skill
- checking-markdown-document-with-rules(文章の書き方の規約との照合。hook が促す) → fixing-markdown-document
- rewrite-pink-elephants(ピンクの象の除去)

**4. テスト設計**
- designing-skill-test-cases → designing-skill-test-scenarios

**5. テスト実行**
- testing-skill-with-template → fixing-skill(スキルの直し)、fixing-test-plan(テスト計画書の直し)

**6. 公開**
- publishing-skills-to-public-repo

**hook(自動で動く仕組み)**
- pre-tool-use-write-file: テスト計画書を持つスキルのファイルとテスト計画書の書き換えを、fixing-skill、revising-skill-writing-rule、fixing-test-plan、designing-skill-test-cases、designing-skill-test-scenarios の手順の外では止める
- post-tool-use-any-tool: どのツールの操作のあとでも、守るファイルの変化を、スキルの手順の跡と突き合わせる
- post-tool-use-write-file: `.md` を変えたら 3 の照合と直しを促し、規約を変えたらピンクの象を除く書き直しとユーザーの承認を促す

## 流れ全体

- 目的: ユーザーの依頼から、要件を満たし、規約に沿い、初めて読む実行者が動かせるスキルを作る。
- 最初の入力: ユーザーの依頼(スキルにしたい作業)
- 最終出力: 公開したスキルのフォルダ(SKILL.md、references、scripts)、要件定義書、テスト計画書、判定の記録
- 要件(終わりの条件):
  - 要件定義書の受け入れの基準を、すべて満たす
  - 規約と雛形に照らして、致命的な誤りと機械的な不一致が 0 件
  - 判定の記録で、実施したすべてのケースが合格
  - 要件定義と、下書きの構成の案の 2 か所で、ユーザーが承認している
  - 前のフェーズへ戻ったときは、戻り先と理由が記録されている

## 流れ

未作成のスキルを使うフェーズ(1)の目的、機能、要件は、この文書だけにある案である。要件定義書と設計書はなく、ユーザーの承認も得ていない。

### 1. 要件定義

- 目的: 何を作るかをユーザーと合意し、後のすべてのフェーズが判断に使う元を作る。
- 機能:
  - 依頼を読み、関係する規約と既にあるスキルを調べる
  - 足りない情報をユーザーに質問する
  - 案を出して、ユーザーの承認を得る
  - 要件定義書を書く
- 要件(終わりの条件):
  - 目的、使う場面、入力、最終出力、受け入れの基準が書かれている
  - 既にあるスキルと受け持ちが重ならない
  - ユーザーが承認している
- 入力: ユーザーの依頼
- 出力: 要件定義書
- 使うスキル: defining-skill-requirements(スキルの要件の定義。未作成。古い設計書「要件の質問による具体化」はあるが、今の流れに合わせた要件と責務は決まっていない)

### 2. 下書き

- 目的: 承認された設計を、雛形の形のファイルにする。
- 機能:
  - 雛形の本文を写し、設計の値で埋める
  - 全スキル共通の決まりを写す
  - スクリプトのテストを流す
- 要件(終わりの条件):
  - ファイルの中身が、設計と 1 対 1 で対応する
  - 設計にない判断を足していない
- 入力: 承認された構成の設計
- 出力: スキルのフォルダ
- 使うスキル: drafting-skill-with-template(スキルの作成)

### 3. 静的検証

- 目的: 動かす前に、規約と雛形との食い違いをなくす。
- 機能:
  - スキルを雛形と規約 skill-writing-rule に照らす
  - スキルと文書を規約 text-writing-rule に照らす
  - ピンクの象(やらないことを思い出させる文)を書き直す
  - 致命的な誤りと機械的な不一致だけを、決めた直し方で直す
- 要件(終わりの条件):
  - 雛形の照合の違反と、判定の仕方が「機械的」の規則の違反が 0 件
  - AI の推論で出た指摘は警告とし、残してよい
- 入力: スキルのフォルダ
- 出力: 照合を通ったスキル
- 使うスキル: checking-skill-with-template(雛形と規約 skill-writing-rule との照合)、fixing-skill(照合の指摘によるスキルの修正)、checking-markdown-document-with-rules(文章の書き方の規約との照合。hook が `.md` の変更のたびに促す)、fixing-markdown-document(その指摘による Markdown の文書の修正)、rewrite-pink-elephants(ピンクの象の除去)

### 4. テスト設計

- 目的: 規約とスキルの文から、実行できるテストケースとシナリオを作り、実施するシナリオをユーザーが決める。
- 機能:
  - 規約の件数の表のとおりに、スキルの要素ごとにテストケースと期待を作る
  - 前提の状態、依頼の文、回答、実行の回数が同じケースをシナリオにまとめ、実施する範囲の承認をユーザーから得る
  - 仕様の行ごとの網羅を数える
- 要件(終わりの条件):
  - 規約の件数の表の行ごとに、求める数のテストケースがある
  - 仕様の行のすべてが、テストケースを 1 件以上持つ
  - 実施するシナリオを、ユーザーが承認している
- 入力: スキルのフォルダ
- 出力: テスト計画書(テストケースの表と、シナリオテストの表)
- 使うスキル: designing-skill-test-cases(テストケースの設計)、designing-skill-test-scenarios(シナリオテストの表の作成)
- 決まっていないこと: 要件定義書の受け入れの基準から期待を作る手順は、要件定義書がまだないので、決まっていない

### 5. テスト実行

- 目的: 初めて読む実行者に動かして、スキルの文どおりに動くかを確かめる。
- 機能:
  - 静的なテスト(照合のスクリプト 1 本ごとのコマンド)を先に流し、全件合格ならシナリオを流す
  - 実行者のサブエージェントにスキルを実行させる
  - ケースごとに、合格、不合格、判定できないの 3 つで判定する
  - 不合格の原因を仕分け、スキルの誤りはスキルを、期待の誤りはテスト計画書を直して、もう一度テストする
- 要件(終わりの条件):
  - 判定の記録で、実施したすべてのケースが合格
- 入力: テスト計画書
- 出力: 判定の記録と実行の記録
- 使うスキル: testing-skill-with-template(テストの実行)、fixing-skill(判定の記録によるスキルの修正)、fixing-test-plan(判定の記録によるテスト計画書の修正)
- 決まっていないこと: 直してもう一度テストする回数の上限。実行者の出力の揺れ(見出しの空白、理由の語順、パスの先頭の `~`)を合否にどう扱うか

### 6. 公開

- 目的: 規約とスキルを、他のプロジェクトでそのまま使える形で配る。
- 機能:
  - 検査の状況の表の丸と「最後に変えたコミット」を今の値にする
  - 規約とスキルを公開リポジトリに写し、混入(ローカルのパス、ユーザー名、メールアドレス)を照合する
  - 配布リポジトリに写して、GitHub に push する
- 要件(終わりの条件):
  - 配布リポジトリの写しが公開リポジトリと一致し、push が終わっている
- 入力: 公開するスキルの名前の一覧
- 出力: 公開リポジトリと配布リポジトリのコミット
- 使うスキル: publishing-skills-to-public-repo(公開リポジトリへの書き出しと配布リポジトリへの反映)

## 規約と、各スキルが規約から受け取って使うもの

流れの中のスキルは、規約を読む動作を持たない。規約は、`paths` に当たるファイルを読んだときに文脈に自動で読み込まれ、スキルはその文脈の中の規則を使う。次の表は、規約ごとの置き場、読み込まれる条件、どのスキルが何を受け取って使うかを示す。

| 規約 | 置き場 | 読み込まれる条件 | 受け取って使うスキルと、使うもの |
|---|---|---|---|
| 文章の書き方の規約 | `rules/text-writing/` | 常に | すべてのスキル: 文と名前の書き方。3 checking-markdown-document-with-rules: 照らす規則の全件。3 fixing-markdown-document: 規則ごとの直し方 |
| スキルか規約か | `rules/skill-or-rule/` | 常に | 1 defining-skill-requirements(未作成): 依頼をスキルにするか規約にするかの見分け方 |
| スキル作成の規約 | `rules/skill-writing/skill-writing-rule/` | `skills/*/SKILL.md` か `references/` を読んだとき | 2 drafting-skill-with-template: phase と step の切り方、受け渡す値、中間成果物の定義、書き方の規則。3 checking-skill-with-template: 照らす規則の全件。3 fixing-skill: 直し方の規則。revising-skill-writing-rule(流れの外。規約を直すときに使う): 改訂の対象 |
| スキルの雛形(phase と step) | `rules/skill-writing/skill-template/` | 同上 | 2 drafting-skill-with-template: phase の欄、step の形、数の上限、写す本文。3 checking-skill-with-template: 照らす本文 |
| 雛形の完成例 | `rules/skill-writing/skill-template-completed-example/` | 同上 | 2 drafting-skill-with-template: 埋め方の見本。3 checking-skill-with-template: 比べる見本 |
| 規約の書き方の規約 | `rules/rule-writing/` | `rules/` の下を読んだとき | revising-skill-writing-rule(流れの外): 規約の改訂の手順と形 |
| スキルのテスト設計の規約 | `rules/skill-testing/` | `skills/tests/` の下か、テストのスキルの `SKILL.md` を読んだとき | 4 designing-skill-test-cases: 技法を当てるスキルの要素、要素 1 つごとのテストケースの数、着眼点の群、期待の出どころ、判定の仕方の決め方。4 designing-skill-test-scenarios: シナリオの操作(依頼の文、回答、選択肢、置くファイル、実行の回数)。5 testing-skill-with-template: 静的なテストと単体と結合の操作、判定の記録が持つもの。5 fixing-skill と fixing-test-plan: 判定の記録の形 |

- テストの方針は、規約 skill-test-design-rule が一律に決める(観点は着眼点の群、深さは要素 1 つごとのテストケースの数の表)。そのため、流れはテストの方針のフェーズを持たない。
- プログラム一般のテスト設計の規約(test-design-rule)は、作業用リポジトリにない。

## 足りないもの

### スキルはないが、古い設計書があるもの

- defining-skill-requirements(スキルの要件の定義。設計書「要件の質問による具体化」。今の流れに合わせた要件と責務は決まっていない)

### 規約がないもの

- 設計の規約: 要件定義書が持つもの
- プログラム一般のテスト設計の規約

### 決まっていない運用

- テストの直しとやり直しの回数の上限
- 実行者の出力の揺れを合否にどう扱うか
- 雛形の全スキル共通の決まりの「中止までの成果物: それまでに書いた最終出力のファイル」が、フォルダを含むか

### 流れから外したもの

- 受け入れの判断(judging-skill-acceptance)と、規約の改訂と振り返り(analyzing-skill-change-impact、collecting-skill-failures)のフェーズ: 流れに置かない。公開スキルの検査の状況の表の丸が受け入れの記録になり、規約の改訂は revising-skill-writing-rule を流れの外で使う

- orchestrating-skill-development(スキル開発の統括): 作らない。守るファイルの書き換えの制限と照合の催促は hook が受け持つ
- checking-skill-with-rules(スキルと規約の照合): 作らない。checking-skill-with-template が雛形と規約の両方との照合を持つ
- selecting-skill-template(雛形の選択)、designing-skill-structure(スキルの構成の設計)、reviewing-skill-design(スキルの設計のレビュー): 作らない(2026-10-22)。雛形は 1 つで選ぶものがなく、構成の案と承認は drafting-skill-with-template の phase 3 が受け持つ
