# スキル開発の流れ(いまあるスキルだけの版)

作成日: 2026-10-11。状態: 下書き。

この文書は、最終ゴールの文書 同じフォルダの `スキル開発の流れ.md`(11 フェーズ)に対して、2026-10-11 の時点にあるスキルだけでスキルを作るときの流れを書いた文書です。最終ゴールの文書は、あるべき流れと足りないスキルを示し、この文書は、足りないスキルがないまま今日どう回すか、どこを人が埋めるか、どの合否が何を意味するかを示します。フェーズの番号と名前は、最終ゴールの文書と同じにします。

## 流れ全体(現状)

- 最初の入力: ユーザーの依頼の文。使う場面、目的、最終出力、出力先のフォルダを含む(drafting-skill-with-template の開始時の入力の必須の 4 項目)。
- 最終出力: スキルのフォルダ、テストケース.md、テストシナリオ.md、結果のフォルダ、ケースごとの判定.md。
- 最終ゴールの終わりの条件のうち、現状で確かめられるもの:
  - 規約と雛形に照らして、致命的な誤りと機械的な不一致が 0 件(フェーズ 6)。
  - テストの不合格と判定できないが 0 件(フェーズ 9)。
- 最終ゴールの終わりの条件のうち、現状で確かめられないもの:
  - 要件定義書の受け入れの基準をすべて満たす。要件定義書がない。
  - テスト結果が「受け入れ: 可」。受け入れの判断をするスキルがなく、ユーザーが判定の記録を読んで決める。
  - 3 か所の承認のうち、要件定義の承認と受け入れの承認は、スキルの外でユーザーが行う。設計のレビューの承認は、drafting の step 3-2 の構成の案の承認がその代わりになる。
  - 前のフェーズへ戻ったときの戻り先と理由の記録。記録する場所がない。

## 段の間の受け渡し

| 渡す側 | 受け取る側 | 渡すもの | 渡し方 |
|---|---|---|---|
| ユーザー | drafting-skill-with-template | 使う場面、目的、最終出力、出力先のフォルダ | 依頼の文 |
| drafting-skill-with-template | checking-skill-with-template | スキルのフォルダ | ユーザーが依頼の文にパスを書く |
| checking-skill-with-template | fixing-skill | 指摘の一覧 | チャットの表示。同じ会話の中で続けて呼ぶ |
| fixing-skill | designing-skill-test-cases | 直したスキルのフォルダ | ユーザーが依頼の文にパスを書く |
| designing-skill-test-cases | designing-skill-test-scenarios | テストケース.md | ファイル。ユーザーが依頼の文にパスを書く |
| designing-skill-test-scenarios | testing-skill-with-template | テストシナリオ.md | ファイル。ユーザーが依頼の文にパスを書く |
| testing-skill-with-template | fixing-skill | 結果のフォルダ | フォルダ。ユーザーが依頼の文にパスを書く |
| fixing-skill | testing-skill-with-template | もう一度テストする依頼の文 | チャットの表示。ユーザーが写して依頼する |

段をつなぐのは、すべてユーザーの依頼の文です。統括のスキル(orchestrating-skill-development)がないため、依頼の文 1 回で全段は通りません。

## フェーズごとの現状

### 1. 要件定義

- 最終ゴールの出力: 要件定義書。
- 現状のスキル: なし。
- 現状の埋め方: ユーザーが依頼の文に、使う場面、目的、最終出力を書く。drafting の step 2-5 が足りない項目を 1 回聞く。
- 現状で欠けるもの: 入力、受け入れの基準、既にあるスキルとの重なりの確認。後のフェーズの判断の元がないので、フェーズ 7 から 10 は要件に対する判定ができない。

### 2. 雛形の選択

- 最終ゴールの出力: 選んだ雛形と理由。
- 現状のスキル: なし。
- 現状の埋め方: 雛形は「スキルの雛形(phase と step)」の 1 つだけなので、選択は起きない。
- 現状で欠けるもの: 雛形が増えたときの基準。

### 3. 構成の設計

- 最終ゴールの出力: 構成の設計。
- 現状のスキル: drafting-skill-with-template の step 3-1(構成の案を作る)。
- 現状の埋め方: drafting が依頼の文から構成の案を推論で作る。
- 現状で欠けるもの: 要件定義書がないため、「すべての要件がどれかの step にたどれる」ことを確かめられない。

### 4. 設計のレビュー

- 最終ゴールの出力: 承認された構成の設計。
- 現状のスキル: drafting-skill-with-template の step 3-2(構成の案の承認)。
- 現状の埋め方: ユーザーが構成の案を読んで承認する。批判的に読むのはユーザー。
- 現状で欠けるもの: 要件と step の突き合わせ、指摘の仕分け。

### 5. 下書き

- 最終ゴールの出力: スキルのフォルダ。
- 現状のスキル: drafting-skill-with-template の step 4-1 と 4-2。
- 現状で欠けるもの: なし。構成の案から雛形どおりに書く。

### 6. 静的検証

- 最終ゴールの出力: 照合を通ったスキル。
- 現状のスキル: drafting-skill-with-template の step 4-3 から 4-6(機械的な判定、検証者の照合、違反の修正)、checking-skill-with-template、fixing-skill。
- 現状の埋め方: drafting が作成の中で照合と修正を回す。既存のスキルを直したあとは、checking と fixing-skill を同じ会話で続けて呼ぶ。
- 現状で欠けるもの:
  - checking は規約と雛形の両方に照らす。最終ゴールでは雛形だけに照らす受け持ちで、規約との照合は checking-skill-with-rules(ない)が持つ。
  - drafting の step 4-3 から 4-6 と checking の step 3-4 から 3-7 は、同じ照合の手順を 2 か所に持つ。片方を直したらもう片方も直す必要がある。
  - 検証者のサブエージェントは、流すたびに違う指摘を出す。「致命的な誤りと機械的な不一致が 0 件」の判定は、機械的な判定のスクリプト 3 本と 4 つのコマンドの部分だけが毎回同じ結果になる。

### 7. テストの方針

- 最終ゴールの出力: テストの方針(何をどの深さで確かめるか)。
- 現状のスキル: なし。
- 現状の埋め方: designing-skill-test-cases の雛形の規則が、機能ごとの深さ(徹底か標準)を SKILL.md の語(上書き、削除、インストール、ファイルを書く step)から機械的に決める。「要件の文」は任意の入力で、既定は「なし」。
- 現状で欠けるもの: 受け入れの基準から観点を作ること。深さは要件ではなく SKILL.md の語で決まる。

### 8. テスト設計

- 最終ゴールの出力: テストケース、テストシナリオ。
- 現状のスキル: designing-skill-test-cases、designing-skill-test-scenarios。
- 現状の埋め方: cases が SKILL.md と全スキル共通の決まりから期待する結果を写し、scenarios がケースをシナリオにまとめて分岐の網羅を数える。
- 現状で欠けるもの: 期待する結果は要件定義書からではなく、対象の SKILL.md 自身から写す。したがってフェーズ 9 の合格は「SKILL.md に書いたとおりに動いた」を意味し、「要件を満たした」を意味しない。

### 9. テスト実行

- 最終ゴールの出力: テスト結果。
- 現状のスキル: testing-skill-with-template、fixing-skill。
- 現状の埋め方: testing が初めて読む実行者にシナリオを実行させて記録を残し、fixing が記録と期待を照合して合格、不合格、判定できないに分け、スキルの誤りだけを直す。
- 現状で欠けるもの:
  - 「受け入れ: 可」の形がない。ケースごとの判定.md の件数を人が読む。
  - 「直してもう一度テストするのは 2 回まで」の歯止めが、スキルにない。2026-10-10 から 11 の検証では、5 本の道具を 7 回まわした。

### 10. 受け入れの判断

- 最終ゴールの出力: ユーザーの承認か、戻るフェーズ。
- 現状のスキル: なし。
- 現状の埋め方: ユーザーが fixing-skill の修正の結果とケースごとの判定.md を読んで決める。
- 現状で欠けるもの: 受け入れの基準(フェーズ 1 の出力)と、戻るフェーズと理由の記録。

### 11. 保守

- 最終ゴールの出力: 変わる動きと合わせて直すものの一覧。
- 現状のスキル: revising-skill-writing-rule(規約の改訂だけ)。
- 現状の埋め方: 規約と雛形の変更は revising が行い、全スキルと完成例との照合までする。スキルの変更の影響の洗い出しと、失敗の振り返りは、人が行う。
- 現状で欠けるもの: analyzing-skill-change-impact、collecting-skill-failures。

## 現状の流れで「合格」が意味すること

- フェーズ 6 の合格は、「規約と雛形の機械的な判定を通り、検証者がその回に違反を見つけなかった」を意味する。検証者の指摘は回ごとに変わる。
- フェーズ 9 の合格は、「SKILL.md に書いた手順どおりに、初めて読む実行者が動いた」を意味する。要件を満たしたかは、要件定義書がないので判定できない。
- 両方に合格しても、最終ゴールの終わりの条件のうち、要件定義書に関わる 2 つ(受け入れの基準、受け入れ: 可)は満たしたと言えない。

## 2026-10-10 から 11 の検証で得たもののうち、この流れに残すもの

- 結果のフォルダと skills/tests の下のファイルから、ホームのフォルダの絶対パスとユーザー名を消す決まりとコマンド(testing の step 3-7、cases と scenarios と fixing の書く step)。
- 実行者の記録の形(通った step、表示の記録、手順から外れた点の 3 つの見出し)と、記録の形を機械的に確かめる決まり。
- 実行の回数が 2 のシナリオで、再現性と冪等性を同じ回の中で確かめる形。
- fixing の判定を、記録と期待の照合で行い、推論で決めない決まり。

## 最初に埋めるべき穴

- defining-skill-requirements(フェーズ 1)と、要件定義書と構成の設計が持つものを決める設計の規約。これがないと、フェーズ 3、4、7、8、10 の判定の元がない。
- 段をつなぐ決まり。checking の指摘の一覧と fixing の修正の結果がチャットの表示だけで、ファイルに残らない。統括のスキルを作るには、段の間をファイルで渡す形が要る。
