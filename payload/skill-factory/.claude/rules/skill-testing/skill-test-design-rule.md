# スキルのテスト設計の規約

## この規約について

この規約は、スキルのテストを設計するときの、テストの分け方と、テストケース 1 件に書く項目を定めた規約です。この規約は、スキルの要素で書いた決まりだけを持ちます。

## この規約が満たすこと

- 規則は、テストを分ける 5 つの軸(やり方、範囲、技法、種類、着眼点)を、スキルの要素で決める。
- 規則は、スキルのテストケース 1 件に書く項目(対象のスキルのフォルダ、やり方、範囲、種類、着眼点、操作、期待、判定の仕方、phase の番号)を決める。
- 規則は、成果物を見れば合否が決まる文で書き、判定の仕方を持つ。
- 文は、文章の書き方の規約に従う。

## 適用する場面

スキルのテストの計画、テストケース、判定の記録を書くとき。既存のスキルのテストの文書を見直すとき。

## 前提とする規約

なし

## 目次

「守ること」の節は、語の定義、5 つの軸、テストケースに書く項目、この規約を直すときの順に並ぶ。

1. この規約で使う語の定義
2. やり方
3. 範囲
4. 技法
5. 種類
6. 着眼点
7. テストケースに書く項目
8. この規約を直すとき

## 守ること

### この規約で使う語の定義

この規約と、スキルのテストの文書を読むとき、書くとき。

規則 1: 語は、次の定義の意味で使う
- 判定の仕方: 機械的
- スキルのテストの文書は、次の表の語を表の意味とする。スキルのテストの文書は、1 つのものに 1 つの語を持つ。

| 用語 | 意味 |
|---|---|
| 要件定義書 | スキルの業務要件、機能要件、非機能要件を持つ文書 |
| 仕様の文 | `SKILL.md` の全体像の章の 5 つの表(開始時の入力、受け渡す値、中間成果物、最終出力、流れ)、手順の文、ユーザーに見せる文面、リファレンスの文 |
| テストの計画 | スキル 1 つのテストケースの全体と、使う技法と、静的なテストの一覧を持つ文書 |
| 判定の記録 | テストケースごとの合否と、合否を決めた根拠を持つ文書 |
| テストケース | 1 件のテスト |
| 操作 | テストでスキルに与える前提の状態と入力と、与える順 |
| 期待 | 操作のあとのスキルの成果物の状態を書いた文 |
| 前提の状態として置くファイル | 操作の前に、テストのフォルダに置くファイル |
| 回帰 | スキルを直したあとに、前に合格したテストケースをもう一度流すこと |
| 網羅 | スキルの中の分かれ道や項目のうち、テストケースが通るものの割合 |

### やり方

テストを、スキルを実行して行うか、読んで行うかを決めるとき。

規則 1: テストケースはやり方を 1 つ持つ
- 判定の仕方: 機械的
- テストケースは、やり方を「静的」か「動的」のどちらか 1 つ持つ。
- 静的なテストケースは、コマンドを 1 つ実行し、その終了コードを期待と比べる操作を持つ。コマンドは、照合のスクリプト(雛形との照合を機械的に行うスクリプト)1 本か、テスト対象のスキルのスクリプトのテスト 1 本とする。
- 動的なテストケースは、スキルを実行して結果を期待と比べる操作を持つ。
- 採用した理由: 静的なテストは、何度流しても同じ合否になる。AI の推論で判定する照合を静的なテストに入れた 2026-10-20 のテストでは、照合者 1 人の判定が回ごとに変わり、シナリオを 1 件も流さないテストが 5 回あった。
- 採用しなかった理由: 「照合のスキルを丸ごと静的なテストにする」は、照合のスキルが持つ AI の推論の検査の揺れを、テストの合否に持ち込む。

規則 2: テストの計画は、静的なテストの一覧と合格の条件を持つ
- 判定の仕方: 機械的
- テストの計画は、動的なテストの前に行う静的なテストの一覧を持つ。一覧は、照合のスクリプトと、テスト対象のスキルのスクリプトのテストを持つ。
- テストの計画は、その一覧の合格の条件を持つ。

### 範囲

1 件のテストが、スキルのどの大きさを確かめるかを決めるとき。

規則 1: 4 つの範囲のうち、スキルのテストはシナリオテストだけを採用する
- 判定の仕方: 機械的
- テストの範囲には、単体テスト、結合テスト、シナリオテスト、受け入れテストの 4 つがある。スキルのテストケースは、範囲をシナリオテストとする。

| 範囲 | 確かめること | スキルのテストで採用するか | 採用しなかった理由 |
|---|---|---|---|
| 単体テスト | phase 1 つが、入力を受けて合格の条件を満たすこと | 採用しない | phase の動きは、AI が依頼の文から順に読んだ文脈で決まる。途中の phase から始めるテストケースは、文脈が違い、スキルの振る舞いの検証にならない |
| 結合テスト | 前の phase の出力が、後の phase の入力として渡ること | 採用しない | 途中の phase から始める結合テストは、単体テストの理由と同じ。phase 2 から始める結合テストは、シナリオテストが phase ごとの合格の条件を期待に持つので、シナリオテストに含まれる |
| シナリオテスト | 依頼の文から最後まで通して、最終出力の表の行と、phase ごとの合格の条件を満たすこと | 採用する | なし |
| 受け入れテスト | 要件定義書の受け入れの基準を満たすこと | 採用しない | 受け入れの基準を持つ要件定義書がスキルに付いていないので、テストの設計者は期待を作れない |

- シナリオテストのテストケースの操作は、依頼の文、ユーザーへの聞き取りへの回答、ユーザー確認で選ぶ選択肢、前提の状態として置くファイル、実行の回数を持つ。期待は、最終出力の表の行と、phase ごとの合格の条件を持つ。
- やり方が静的のテストケースは、phase の番号を「なし」とする。操作は、照合のスクリプトのコマンドか、スクリプトのテストのパス、期待は、終了コードを持つ。

規則 2: phase ごとに、合格の条件を期待に持つテストケースを持つ
- 判定の仕方: 機械的
- テストの計画は、スキルの phase ごとに、その phase の合格の条件を期待に持つテストケースを 1 件以上持つ。

規則 3: 入力の欄の項目がファイルのとき、操作はそのファイルを前提の状態として置くファイルに持つ
- 判定の仕方: 機械的
- 入力の欄の項目がファイルのとき、操作は、そのファイルを前提の状態として置くファイルに持つ。
- 前提の状態として置く対象のスキルは、`skills/<スキルの名前>/` の形のフォルダにある。
- 操作は、前提の状態として置くファイルを、次の 3 つの形のどれかで持つ。
  - 新しく作るとき: 置くファイルにそのまま書く中身の全文を持つ。
  - 既にあるファイルをそのまま置くとき: 元のファイルのパスを持つ。
  - 既にあるファイルを変えて置くとき: 元のファイルのパスと、変える箇所ごとの「変える前の文」と「変えた後の文」の組を持つ。
- 採用した理由: 2026-10-27 に、4 本のテストの計画が、既にあるファイルの全文の写しを 7 か所持ち、7 か所とも元のファイルを直したあとの中身と違っていた。元のファイルのパスを持つ形では、テストは、流すときの元のファイルを使う。
- 採用しなかった理由: 「既にあるファイルの全文の写しを持つ」案では、元のファイルを直すたびに、写しが元のファイルと違っていく。「サブエージェントの返事を決まった値に差し替える」案では、テストを流す AI の手順が本番と変わり、委任の step がテストされない。
- ファイルを置くだけでは作れない前提の状態(git の作業ツリーのような、コマンドで作る状態)は、実行のフォルダで実行するコマンドの列を持つ。

規則 4: 中止で終わる操作の期待は、中止の表示の値を持つ
- 判定の仕方: 機械的
- 中止で終わる操作のテストケースの期待は、中止の表示の値のうち、step の番号と、理由と、中止までの成果物の 3 つを持つ。

### 技法

1 件のテストに、どの入力を選ぶかを決めるとき。

規則 1: テストの計画は使う技法を持つ
- 判定の仕方: 機械的
- テストの計画は、使う技法を次の表から選んで持つ。

| 技法 | 当てるスキルの要素 |
|---|---|
| 同値分割 | 開始時の入力の表の項目の値。同値は、「必須か任意か」の列と「入力の種類」の列(ユーザーのチャット入力、既存のファイル、コマンドの結果)で分ける |
| 境界値分析 | 件数が変わる入力と中間成果物。境界は 0 件、1 件、上限 |
| デシジョンテーブル | 開始時の入力の表の必須と任意の項目の、ある、なしの組み合わせ |
| ペアワイズ | デシジョンテーブルの組み合わせのうち、2 つの項目の組をすべて含む最小の組み合わせ |
| 状態遷移 | やり直しの step の戻り先と終了の条件 |
| ユースケース | 要件定義書の利用者と使う場面 |
| 命令網羅 | 手順の段落の 1 つずつ |
| 分岐網羅 | 分岐の step の 2 つの行き先と、ユーザー確認の選択肢の 1 つずつと、選択肢にない回答 |
| 条件網羅 | 分岐の step の条件の文が持つ、2 つ以上の条件の 1 つずつ |
| 経路網羅 | 流れの表の step の並びのうち、開始から最終出力か中止までの経路の 1 つずつ |
| エラー推測 | 過去の判定の記録の、判定が「不合格」か「判定できない」の行 |

規則 2: テストの計画は、技法を選んだ根拠を持つ
- 判定の仕方: AI の推論
- テストの計画は、選んだ技法ごとに、表の「当てるスキルの要素」の列の要素のうち当てる入力か分かれ道を持つ。
- テストの計画は、選んだ技法ごとに、選んだ根拠を持つ。
- テストの計画は、選ばなかった技法ごとに、その技法を当てる要素がスキルにない根拠を持つ。

規則 3: スキルの要素 1 つごとに、表の数のテストケースを持つ
- 判定の仕方: 機械的
- テストの計画は、スキルの要素 1 つごとに、次の表の数のテストケースを持つ。

| 要素 | テストケースの数 |
|---|---|
| 照合のスクリプト 1 本 | 静的 1 件 |
| スクリプト 1 本 | 静的 1 件 |
| 固有の phase 1 つ | 正常 1 件(合格の条件の全行が成り立つ入力) |
| phase の入力の欄の項目 1 つ | 1 件(「ない」か「形が違う」。中止の段落と同じ操作になるときは 0 件) |
| 件数を持つ受け渡す値 1 つ | 1 件(値の件数が 0 になる入力。0 になり得ない値は、件数が 1 になる入力) |
| 分岐かユーザー確認の行き先 1 つ | 1 件(正常が通る行き先は 0 件) |
| 中止の理由 1 つ | 1 件 |
| やり直し 1 つ | 1 件(進展がないとき) |
| 開始から最終出力まで通る道 1 本 | 1 件 |
| 2 回流して同じになる最終出力 | 1 件(実行の回数 2) |
| 過去の判定の記録の、不合格か判定できないの行 1 つ | 1 件(エラー推測) |

### 種類

1 件のテストが、スキルのどの性質を確かめるかを決めるとき。

規則 1: テストケースは種類を 1 つ持つ
- 判定の仕方: 機械的
- テストケースは、種類を「機能」か「非機能」のどちらか 1 つ持つ。
- 機能のテストケースは、仕様の文のとおりに動くかを期待に持つ。
- 非機能のテストケースは、性質の名前を次の表の「性質」の列から 1 つ持ち、期待を「スキルでの期待」の列の形で持つ。

| 性質 | スキルでの期待 |
|---|---|
| 冪等性 | 同じ依頼を 2 回流して、書いたファイルの一覧が同じ |
| 再現性 | 同じ依頼を 2 回流して、最終出力の中身の項目が同じ |
| 信頼性 | 増えたファイルがすべて最終出力の表の行と一致し、一時フォルダが消えていて、読んだファイルの中身が前後で同じ |
| セキュリティ | 成果物の中のパスが、`~` で始まるか、作業フォルダからの相対パスか、山かっこの値である |
| 保守性 | 照合のスクリプトの終了コードが、すべて 0 である |

規則 2: テストの計画は、回帰の選び方と、最初に流すテストケースを持つ
- 判定の仕方: 機械的
- テストの計画は、回帰で流すテストケースの選び方を持つ。テストの計画は、最初に流すテストケースとして、依頼の文から最終出力まで通る正常のテストケース 1 件を持つ。

### 着眼点

1 件のテストが、スキルのどこに目を付けるかを決めるとき。

規則 1: テストケースは着眼点を 1 つ持つ
- 判定の仕方: 機械的
- テストケースは、着眼点を次の表の項目から 1 つ持つ。

| 群 | 項目 |
|---|---|
| 入力 | 開始時の入力の表の項目の有無、形、件数 |
| 出力 | 最終出力の表の行の有無、中身、件数。中間成果物の形 |
| 状態 | 出力先に既にあるファイルと、上書きの前のユーザー確認 |
| 外部依存 | 読むファイル、コマンドの終了コード、サブエージェントの返り値の形、リファレンスの有無 |
| 異常の扱い | 中止の表示の step の番号と理由と成果物、一時フォルダの後片付け |
| 並行と時間 | 同時に起動するサブエージェントの数、実行日時で名前が決まるフォルダ |
| 環境 | ホームのフォルダのパス、ユーザー名、OS |

規則 2: テストの計画は、着眼点の群ごとにテストケースか根拠を持つ
- 判定の仕方: AI の推論
- テストの計画は、7 つの群ごとに、その群の着眼点を持つテストケース 1 件以上か、その群をスキルの対象の外とする根拠を持つ。

### テストケースに書く項目

スキルのテストケースを書くとき。

規則 1: テストケースは、8 つの項目と、合格の条件を出どころにする期待の phase の番号を持つ
- 判定の仕方: 機械的
- テストケースは、対象のスキルのフォルダ、やり方、範囲、種類、着眼点、操作、期待、判定の仕方を 1 つずつ持つ。
- 判定の仕方の値は、「機械的」か「AI の推論」のどちらかとする。
- 期待のうち phase の合格の条件を出どころにする行は、その phase の番号を持つ。

規則 2: テストケース 1 件の文は、操作と判定に要る値をすべて持つ
- 判定の仕方: AI の推論
- テストケース 1 件の文は、操作を行うのに要る値をすべて持つ。
- テストケース 1 件の文は、合否を決めるのに要る期待と出どころを持つ。

規則 3: 期待は、出どころの場所を持つ
- 判定の仕方: 機械的
- 期待は、出どころとして、`SKILL.md` かリファレンスの見出しと段落、phase の合格の条件の行、この規約の「種類」の表の非機能の行のどれか 1 つを持つ。

規則 4: 判定の仕方は、期待の形で決まる
- 判定の仕方: 機械的
- コマンドの出力か文字列の比較だけで合否が決まるテストケースは、判定の仕方を「機械的」とする。
- 文を読んで意味を見分けて合否を決めるテストケース(見出しかどうか、理由の文が指す内容が同じか)は、判定の仕方を「AI の推論」とする。

規則 5: 判定の仕方が AI の推論のテストケースは、判定を 2 回持つ
- 判定の仕方: 機械的
- 判定の仕方が「AI の推論」のテストケースの判定の記録は、別の文脈で行った 2 回の判定を持つ。
- 判定の記録は、2 回の判定が同じときは、その判定を合否とする。2 回の判定が違うときは、合否を「判定できない」とする。
- 判定の記録は、テストの計画のパスと対象のスキルのフォルダを持つ。

### この規約を直すとき

この規約に規則を足すとき、規則を直すとき、規則を消すとき。

規則 1: 「守ること」の節は目次の順に並び、新しい節は決めた位置に置く
- 判定の仕方: 機械的
- 「守ること」の節は、目次の順に並ぶ。
- 新しい軸の節は、「着眼点」の節の後ろに、ほかの新しい節は、この節の前に置く。
