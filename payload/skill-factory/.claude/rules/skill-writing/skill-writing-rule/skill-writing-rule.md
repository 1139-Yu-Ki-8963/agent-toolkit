# スキルの書き方の規約

## この規約について

この規約は、雛形を選び、その形に沿ってスキルを書くための規約です。スキルを作った AI は、作ったスキルをこの規約の規則と照らして合否を確かめます。

## この規約が満たすこと

- 規則は、できあがったスキルが満たすことだけを書く。
- 規則は、どの雛形で作ったスキルにも同じく当てはまる。
- 雛形の本文、書き方の決まり、雛形の構造に依存する決まり、決まった値の一覧は、雛形が持つ。
- 新しい雛形が満たすことは、この規約が持つ。
- 規則は、成果物を見れば合否が決まる文で書き、判定の仕方を持つ。
- 規則は、観点で参照し、観点は、初めて読む人がそのまま意味を読める語で書く。
- 同じことは、1 か所に 1 回だけ書く。
- 文は、文章の書き方の規約に従う。
- 直す AI は、直す前の文と直した後の文をユーザーに見せて承認を得てから反映する。
- 用語を変えた AI は、規約、雛形、完成例、全スキルの写しを同じ変更で揃える。
- 直したあとは、規約の一式と全スキルが照合を通る。

## 適用する場面

`SKILL.md`、リファレンス、スクリプトを書くとき。既存の `SKILL.md`、リファレンス、スクリプトをこの規約と比べるとき。雛形と完成例を新しく作るとき、直すとき。

## 前提とする規約

なし

## 目次

「守ること」の節は、スキルが満たすこと、雛形が満たすこと、リファレンス、スクリプト、前提ツール、この規約自身の順に並ぶ。

1. この規約で使う語の定義
2. スキルの切り分け方
3. 入力と出力
4. 雛形が持つもの
5. スキルのフォルダが持つもの
6. リファレンス
7. スクリプト
8. 前提ツール
9. この規約を直すとき

## 守ること

### この規約で使う語の定義

この規約、雛形、完成例を読むとき、書くとき。

規則 1: 語は、次の定義の意味で使う
- 判定の仕方: 機械的
- この規約と、雛形、完成例は、次の表の語を、表の意味で使う。1 つのものの名前は、1 つとする。

| 用語 | 意味 |
|---|---|
| 雛形 | スキルの形と書き方を持つ文書 |
| 完成例 | 雛形の「雛形の本文」のとおりに書いた `SKILL.md` の全文 |
| スキル | 1 つの依頼を受け取り、最終出力を返す手順の全体。プログラムの 1 つのコマンドに当たる |
| 作るスキル | 依頼を受け取り、成果物を新しく書くか、既にある成果物に章を足すスキル。名前の最初の語は drafting か designing。成果物を書く以外の動作(数える、コミットする)を行うスキルの名前の最初の語は、その動作の英語の動名詞(counting、committing) |
| 照合のスキル | 文書を読み、指摘の一覧を出すスキル。名前の最初の語は checking |
| 修正のスキル | 指摘を受け取り、対象のファイルを直すスキル。名前の最初の語は fixing |
| テストのスキル | テスト計画書を読み、テストを流して判定の記録を書くスキル。名前の最初の語は testing |
| 改訂のスキル | 規則を足す、直す、消す依頼を受け取り、規約の一式を直すスキル。名前の最初の語は revising |
| phase | 入力を受け取り、終わりの状態の成果物を返す step のひとまとまり。入力、出力、合格の条件を持つ。プログラムの関数に当たる |
| 前の phase | その phase より番号の小さい phase |
| 合格の条件 | phase を終えたときに、その phase の出力が満たしている状態。数、有無、一致のどれかで書く。実行者は、phase の終わりに出力を合格の条件と比べ、検証者とテストの設計者と判定者は、合格の条件を判定の元にする。プログラムの関数の事後条件に当たる |
| 全体の決まり | 2 つ以上の step で同じく守る動作の決まり。1 文に 1 つの決まりを書き、決まりの文だけを持つ |
| step | 1 つの動作。種別と流れのパターンを 1 つずつ持ち、情報の欄に種別、入力、出力と、パターンごとの項目を持つ。プログラムの文に当たる |
| 種別 | step の動作の決まり方。毎回同じ結果になる「固定の手順」か、AI が結果を決める「AI による推論」 |
| 流れのパターン | step の進み方。直列、分岐、繰り返し、やり直し、ユーザー確認、委任の 6 つ。プログラムの順次、if、for、while、入力待ち、別のプロセスの呼び出しに当たる |
| 情報の欄 | step の見出し「── step <番号> の情報 ──」の下の箇条書き。種別、入力、出力と、パターンごとの項目を書く |
| 最終出力 | スキルが終わったときに残る成果物。ファイルか、チャットに表示した成果物 |
| 受け渡す値 | step の間と phase の間で渡す値。会話の中に持つ。プログラムの変数と、関数の引数と返り値に当たる |
| 中間成果物 | スキルの目的の外で、実行の途中に作るファイルとフォルダ。一時フォルダに置く |
| 前提ツール | スキルが実行するコマンドのうち、OS の標準の構成の外から入れるもの |
| 前提 | 前提ツールのうち、node、npm、git |
| スキルごとのツール | 前提ツールのうち、前提を除くもの |
| ツールのフォルダ | スキルごとのツールの置き場。`SKILL.md` があるフォルダ(シンボリックリンクのときは、そのリンク先のフォルダ)の直下の `.tools/` |
| セッションの環境の情報 | AI の実行環境が会話の開始時に示す情報。Platform(`darwin`、`linux`、`win32`)を持つ |
| ユーザーへの聞き取り | 自由な回答を求める質問 |
| ユーザー確認 | 選択肢を出し、ユーザーが選ぶまで止まる step |
| 委任 | step の動作をサブエージェント(別の文脈で動く AI)に行わせること |
| 中止 | スキルを途中で終えること。中止の表示だけを出す |

### スキルの切り分け方

スキルを何本に分けるか、1 本のスキルがどこまでを扱うかを決めるとき。

規則 1: 1 つのスキルが扱う場面と目的は 1 つ
- 判定の仕方: AI の推論
- 1 つのスキルは、依頼の語句にたどれる 1 つの場面と 1 つの目的だけを扱う。

規則 2: 作るスキルは、作るか足す成果物ごとに 1 つとする
- 判定の仕方: 機械的
- 作るスキルは、作るか足す成果物ごとに 1 つとする。
- 採用した理由: 成果物が 1 種類なら、書く手順と雛形は 1 種類で済む。
- 採用しなかった理由: 「依頼の場面ごとに 1 つ」では、同じ成果物を書く手順を 2 本のスキルが持つ。

規則 3: 照合のスキルは、突き合わせる相手で本数が決まる
- 判定の仕方: 機械的
- 規約と突き合わせる照合のスキルは 1 本とし、受け取った規約のパスの一覧の規約ごとに照合する。
- 雛形で作った文書の照合のスキルは、雛形の種類ごとに 1 本とし、雛形との機械的な突き合わせと、その文書に当たる規約との比較を 1 本で持つ。
- 採用した理由: 規約との照合の手順は文書の種類によらず同じで、雛形との突き合わせの手順は雛形ごとに違う。
- 採用しなかった理由: 「対象の文書の種類ごとに 1 つ」は、規約と突き合わせる同じ手順を文書の種類の数だけ持つ。

規則 4: 修正のスキルは、直す対象ごとに 1 つとする
- 判定の仕方: 機械的
- 修正のスキルは、直す対象のファイルの種類(スキル、テスト計画書、規約の一式、Markdown の文書)ごとに 1 つとする。
- 1 つの修正のスキルは、指摘の出どころ(例: 規約との照合、雛形との照合、テストの判定の記録、ユーザーの依頼)ごとの仕分けを、リファレンスの判定の基準の章で持つ。
- 採用した理由: 直す対象が 1 種類なら、直し方の手順も 1 種類で済む。
- 採用しなかった理由: 「比べる規約ごとに 1 つ」では、規約が増えるたびに修正のスキルが増える。「指摘の出どころごとに 1 つ」では、1 つの修正のスキルが 2 種類の対象を直す。

規則 5: 改訂のスキルは、直す規約の一式ごとに 1 つとする
- 判定の仕方: 機械的
- 改訂のスキルは、直す規約の一式ごとに 1 つとする。
- 採用した理由: 規約の一式ごとに、規約と雛形と完成例の整合の取り方は決まる。
- 採用しなかった理由: 「足す、直す、消すの依頼の種類ごとに 1 つ」では、同じ一式の整合の取り方を 3 本のスキルが持つ。

### 入力と出力

スキルが読むもの、書くもの、消すもの、チャットに表示するものと、想定外のときの動きと、ユーザーに聞く項目を書くとき。

規則 1: スキルがユーザーに聞く項目
- 判定の仕方: AI の推論
- スキルがユーザーに聞く項目は、開始時の入力のうち、依頼から読み取れず、機械的にも決まらない項目だけとする。

規則 2: スキルが作るものと変えるものは、最終出力の表にある
- 判定の仕方: 機械的
- スキルが作るファイルとフォルダは、最終出力の表の行と一致する。フォルダの行は、出力の種類「フォルダ」を持つ。
- 別のスキルを動かすための作業用のフォルダと、ツールのフォルダは、最終出力の表の行を、フォルダの行の 1 行とする。
- スキルが変えるファイルは、最終出力の表の行と一致する。

規則 3: ファイルを書くスキルが受け取る書く先
- 判定の仕方: 機械的
- 最終出力の表に出力の種類「ファイル」の行を持つスキルは、開始時の入力の表に、入力の種類「ユーザーのチャット入力」で、その書く先のパス(出力先のフォルダ、または書き換える対象のファイル)の行を持つ。

規則 4: 書く前に書く先を読む
- 判定の仕方: AI の推論
- スキルは、ファイルを書く前に、書く先にあるファイルの今の中身を読む。
- スキルは、読んだ中身と書く中身が違うファイルだけを書き、同じファイルについては、ユーザーへの完了の報告のそのファイルの行に「変更なし」を添える。

規則 5: スキルが消すファイルとフォルダ
- 判定の仕方: 機械的
- 中間成果物は、全体像の「中間成果物」の表にあり、表は置き場と、作る step と、消す step を持つ。
- スキルが消すのは、中間成果物(終わる前と中止する前)と、手順に「消す」と書いたファイルとフォルダだけとする。

規則 6: 受け渡す値は全体像の表にあり、出す step と使う step が表と一致する
- 判定の仕方: 機械的
- 受け渡す値は、全体像の「受け渡す値」の表にある。表の出す step は、使う step より前にある。
- 前の step へ戻る流れで戻ったときだけ使う受け渡す値は、出す step が使う step より後でもよく、表の中身の列に、前の step へ戻ったときだけ使う旨を持つ。

規則 7: スキルがチャットに表示する種類
- 判定の仕方: 機械的
- 作業の開始をユーザーに伝える宣言、中止の表示、ユーザーへの完了の報告は、チャットへの表示の書式に値を入れたものとする。手順は、書式に入れる値だけを持つ。
- スキルは、ユーザーからの質問に、いつでも回答する。

規則 8: 想定外のときは止まり、残したものを示す
- 判定の仕方: 機械的
- スキルは、手順に書いていないことが起きた step(コマンドの終了コードが 0 でない、読むはずのファイルがない、入力の形が手順の想定する形と違う)で中止する。
- スキルは、中止までに書いた最終出力のファイルを残す。中止の表示は、中止までの成果物のパスを持つ。

### 雛形が持つもの

雛形を新しく作るとき、または既存の雛形を直すとき。

規則 1: 雛形が持つ章
- 判定の仕方: 機械的
- 雛形は、適用する場面、省ける部分、決まった値の一覧、この雛形で作るスキルが守ること、書き方の決まり、全スキル共通の決まり、雛形の本文の 7 つの章を持つ。

規則 2: 雛形の決まった値の一覧が持つ値
- 判定の仕方: 機械的
- 雛形の「決まった値の一覧」の章の表は、選択肢、固定の名前、ツールの呼び方、置き場の値を持つ。

規則 3: 「この雛形で作るスキルが守ること」の章が持つ形
- 判定の仕方: 機械的
- 雛形の「この雛形で作るスキルが守ること」の章は、規約 rule-writing-rule の規則「「守ること」の書き方」、規則「規則ごとに、機械的に判定できるか、AI の推論で判定するかを書く」の形を持つ。

規則 4: 雛形が持つ完成例
- 判定の仕方: 機械的
- 雛形は、完成例を 1 本持つ。
- 完成例は、雛形の「この雛形で作るスキルが守ること」の規則をすべて満たす。

規則 5: 雛形と完成例の置き場
- 判定の仕方: 機械的
- 雛形は、`rules/skill-writing/<雛形の名前>/` に、完成例は、`rules/skill-writing/<雛形の名前>-completed-example/` にある。

規則 6: 雛形が持つ名前
- 判定の仕方: 機械的
- 雛形は、題名に、他の雛形と見分けられる名前を持つ。

### スキルのフォルダが持つもの

スキルのフォルダにファイルとフォルダを置くとき。

規則 1: スキルのフォルダが持つもの
- 判定の仕方: 機械的
- `scripts/` と `scripts/tests/` のファイルは、1 行目にシェバンを持つ実行可能なファイルとする。
- スキルのフォルダが持つ、名前が `.` 以外の文字で始まるファイルとフォルダは、次の図にあるファイルとフォルダだけとする。【】の行の下の部分は、その条件のときだけある。

```text
<スキルの名前>/
├── SKILL.md
├── references/
│   ├── 全スキル共通の決まり.md
│   └── <主題の名前>.md
【使用するスクリプトの表に 1 行以上あるときだけ】
└── scripts/
    ├── <スクリプトの名前>
    └── tests/
        └── <テストの名前>
```

規則 2: `.` で始まるフォルダを作る step が持つ手順
- 判定の仕方: 機械的
- スキルのフォルダの中に、名前が `.` で始まるフォルダを作る step は、そのフォルダの直下に `*` の 1 行だけを持つ `.gitignore` を書く手順を、そのフォルダに書くほかの手順より前に持つ。
- 採用した理由: フォルダ自身が持つ `.gitignore` は、リポジトリ直下の `.gitignore` を持たない PC と公開リポジトリでも同じように効く。採用しなかった理由: リポジトリ直下の `.gitignore` は、作者の作業用リポジトリだけで効く。

### リファレンス

スキルにリファレンスを設けるとき。

規則 1: リファレンスの主題の分け方
- 判定の仕方: 機械的
- `references/<主題の名前>.md` は、主題(雛形、判定の基準、委任の指示文、対応表、インストールの方法、スクリプトの説明書)ごとに「##」の章を持ち、章の見出しは主題の名前を持つ。1 つの章は、1 つの主題だけを扱う。

規則 2: SKILL.md からリファレンスに出す内容
- 判定の仕方: AI の推論
- 特定の step に到達したときだけ使う内容と、雛形、例、一覧のように見ながら使う資料の 2 つは、リファレンスにある。
- 2 つ以上の step で使う文面は、リファレンスにある。
- どの step でも使う決まり(ツールの呼び方、チャットへの表示の書式、中止の決まり)と、どのスキルでも同じ最終出力の確認とユーザーへの完了の報告の手順は、リファレンス `references/全スキル共通の決まり.md` にあり、step から呼び出される。中身は、雛形の「全スキル共通の決まり」の章と一字一句同じ。

規則 3: SKILL.md に残す内容
- 判定の仕方: 機械的
- 次の 4 つは、`SKILL.md` にある。
  - 全体像(開始時の入力と最終出力の表を含む)
  - step の並び
  - 各 step の種別、入力、出力
  - 使用するスクリプトと使用するリファレンスの表

規則 4: スキルがリファレンスを読む時点
- 判定の仕方: 機械的
- スキルは、実行のたびに、リファレンスの章を使う step に到達したときに、その章を全文読む。手順は、読む章を「リファレンス `<パス>` の「<章の名前>」の章」の形で指し、使用するリファレンスの表は、章ごとに 1 行を持ち、章を「なし(ファイル全体)」と書く行は、`references/全スキル共通の決まり.md` だけとする。
- スキルは、`references/全スキル共通の決まり.md` を最初の step で全文読む。

### スクリプト

スキルにスクリプトを設けるとき。

規則 1: スクリプト 1 本が扱う処理
- 判定の仕方: 機械的
- 1 本のスクリプトは、種別が「固定の手順」の step を 1 つだけ行う。

規則 2: スクリプト 1 本ごとに添える説明書とテスト
- 判定の仕方: 機械的
- スクリプト 1 本ごとに、説明書とテストがある。
- 説明書は、リファレンスの章(章の種類「スクリプトの説明書」)で、空行とコメント行を除く 1 行ごとに、その行の処理と理由を持つ。
- テストが一時ファイルを作るときは、環境変数 `TMPDIR` の下(なければ `/tmp`)に作り、終了時に消すコードを含む。

規則 3: SKILL.md に書くスクリプトのパス
- 判定の仕方: 機械的
- `SKILL.md` に書くスクリプトのパスは、`SKILL.md` があるフォルダからの相対パスとする。

規則 4: スキルが実行中に使えるスクリプトとコマンド
- 判定の仕方: 機械的
- スキルが実行中に使うものは、同梱したスクリプトと、1 行のコマンドだけとする。

### 前提ツール

スキルが前提ツールを使うとき。

規則 1: 前提ツールの表に挙げるコマンド
- 判定の仕方: AI の推論
- 前提ツールの表は、入っているかどうかがユーザーの環境で変わるツールだけを持つ。依頼の文か使う場面に名前があるツール(例: コミットの直前に使うスキルの git)は、その場面に必ずあるツールとし、表に挙げない。表に挙げるツールは、区分「前提」の行とする。

規則 2: 前提ツールの表の行と列
- 判定の仕方: 機械的
- 前提ツールの表は、前提ツールの 1 件ごとに 1 行を持つ。
- 前提ツールの表は、「区分」「版」「有無を見るファイル」の列を持つ。
- 区分の値は、「前提」か「スキルごとのツール」のどちらかとする。
- 区分が「前提」の行は、版と有無を見るファイルを「なし」とする。
- 区分が「スキルごとのツール」の行を 1 行以上持つ前提ツールの表は、区分が「前提」の行に node と npm を持つ。

規則 3: スキルが外部のネットワークから取得するときに使えるコマンド
- 判定の仕方: 機械的
- スキルの手順、リファレンス、スクリプトが外部のネットワークからファイルかパッケージを取得するコマンドは、OS や言語のパッケージマネージャ(Homebrew、snap、apt、npm、pip など)か、公式の配布元のリポジトリへの `git clone` だけとする。`localhost` と `127.0.0.1` への接続は、どのコマンドでも行える。
- npm のパッケージの install script が公式の配布元から本体を取る取得は、パッケージマネージャによる取得に含める。
- 前提のインストールのコマンドは、パッケージマネージャのものだけで書く。
- 前提のインストールのコマンドを実行する前のユーザー確認の文面は、管理者の権限を求めるコマンドの 1 件ごとに、そのコマンドが管理者の権限を求める旨を持つ。

規則 4: 実行系は node
- 判定の仕方: 機械的
- スキルの手順、スクリプト、スキルが書き出すファイルの中のコマンドは、前提ツールのコマンド、パッケージマネージャのコマンド、`node` で始まるコマンドのどれかとする。規則「前提ツールの表に挙げるコマンド」でその場面に必ずあるとしたツールは、前提ツールのコマンドに含める。
- 一時フォルダの作成と削除、標準入力の読み取りは、`node` で始まるコマンドで行う。
- コマンドを実行する step を持つスキルは、前提ツールの表に node の行を持つ。
- 採用した理由: node は、3 つの OS でコマンド名が同じで、hook(AI の実行環境が自動で実行するスクリプト)とスクリプトと step を 1 つの実行系で書ける。
- 採用しなかった理由: python3 は、Windows に標準で入らず、コマンド名が揺れる。bash と pwsh は、OS で有無が変わる。

規則 5: スキルごとのツールの置き場
- 判定の仕方: 機械的
- 区分が「スキルごとのツール」の行のインストールのコマンドは、`npm install --prefix "<ツールのフォルダ>" <パッケージの名前>@<版>` を持つ。
- スキルごとのツールのインストールのコマンドを実行する手順は、前提のインストールのコマンドを実行する手順より後にある。
- 区分が「スキルごとのツール」の行の「ツールの有無を確かめるコマンド」は、`node -e` で始まる 1 行とする。そのコマンドの終了コードは、`<ツールのフォルダ>/node_modules/<パッケージの名前>/<有無を見るファイル>` があり、かつ同じパッケージの `package.json` の `version` が「版」と一致するときだけ 0 とする。
- 採用した理由: 3 つの OS で同じ方法でツールを入れ、テストで「ない」状態を `.tools/` を置かないことで作れ、利用者の PATH とプロジェクトを変えない。
- 採用しなかった理由: 利用者の環境へのインストールは、利用者の PATH とプロジェクトを変える。
- スキルごとのツールの本体を呼ぶコマンドは、`node` で始まり、本体のパスを `<ツールのフォルダ>` から始まるパスで持つ。
- コマンドの中の `<ツールのフォルダ>` は、区切りを `/` とし、二重引用符で囲む。

規則 6: インストールの表の行
- 判定の仕方: 機械的
- リファレンスの「インストールの方法」の章の表は、前提ツールの 1 件ごとに 1 行以上を持つ。区分が「前提」の行は、macOS、Linux、Windows の 3 つの OS で実行するコマンドを持ち、3 つの OS で同じコマンドは、OS の列を「すべての OS」とした 1 行にある。区分が「スキルごとのツール」の行は、OS の列を「すべての OS」とした 1 行にある。
- 「インストールの方法」の章の表は、「先に書くファイル」の列を持つ。先に書くファイルがない行は、「なし」とする。
- 「インストールの方法」の章の「OS の見分け方」は、セッションの環境の情報の Platform の値(`darwin`、`linux`、`win32`)ごとの OS の対応の表を持つ。

### この規約を直すとき

この規約に規則を足すとき、規則を直すとき、規則を消すとき。雛形と完成例の固定の文言を変えるとき。規則を足す、直す、消すときの共通の決まり(置く節、番号の振り直し、参照の修正、承認)は、規約 rule-writing-rule の「この規約を直すとき」の節にある。

規則 1: 節の順と、新しい節を置く位置
- 判定の仕方: 機械的
- 「守ること」の節は、目次の順に並ぶ。
- 新しい節は、この順の中の当たる位置にある。

規則 2: 雛形と完成例の固定の文言の変更が従う規則
- 判定の仕方: 機械的
- 雛形と完成例の固定の文言(節の見出し、固定の step の名前、表の列の名前、表示の種類の名前、情報の項目の名前)の変更は、規約 rule-writing-rule の規則「規約を足す、直す、消す、分ける、まとめるときに守ること」と規則「用語を足す、変える、廃止したときに揃えるもの」に従う。

規則 3: 規約の一式を直す順
- 判定の仕方: 機械的
- 規約の一式の直しは、規約、雛形、完成例、ユーザーが選んだ見本の 1 スキルの変更を先に持ち、残りのスキルの変更をそのあとに持つ。
- 雛形の「全スキル共通の決まり」の章を変えた直しは、同じ変更の中で、`skills/` の下のすべてのスキルの `references/全スキル共通の決まり.md` を、雛形の章のコードブロックの中身で写し直したものを持つ。

規則 4: 規約の一式とスキルの中の規則への参照が満たすこと
- 判定の仕方: 機械的
- 規約の一式とスキルの中の規則への参照は、観点が参照先の規則の見出しと一致する。
