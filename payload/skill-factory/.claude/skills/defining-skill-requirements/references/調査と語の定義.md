# 調査と語の定義

## 調査の対象と読む範囲

この章は、判定の基準である。実行者は、ユーザーに問う前に、調べて分かることを調べる。この調査が書くファイルは、結果を残す聞き取りの記録だけである。この章の「書き込み」は、「確定した依頼」のユーザーの依頼の文を指す。

調査は、2 回に分ける。1 回目(step 4-2)は、パスなしで調べられる「パスなしで調べる対象」(表の行「既にあるスキル」「作れるか」「プロジェクトの決まり」)を、最初の問いの前に調べる。2 回目(step 5-1)は、残りの行を、最初の問いの答えで調査の対象が決まったあとに調べる。調査の対象のプロジェクトは、実行者が 1 回目の調査の前に決め(step 4-1)、最初の問いの答えで決め直す(step 4-6)。書き込みの、フォルダとして開けるパスを使い、プロジェクトの名前しかないか、パスがないときは最初の問いで項目 11-3 を問い、パスを聞く。実行者を起動したリポジトリ skill-factory は、ユーザーが指定したときだけ、調査の対象のプロジェクトにする。項目 11-3 が「すべて」のときは、書き込みのパスの親のフォルダと、`~/.claude/skills/` と `~/.claude/CLAUDE.md` を対象にする。書き込みにも答えにもパスがないときは、関係するコードと入力の実物を調べず、そのことを「分からないこと」に書く。項目 11-3 が「すべて」で、書き込みにも答えにもパスがないときは、読む範囲を、既にあるスキルと `~/.claude/CLAUDE.md` だけとし、行「作れるか」の規約は、この範囲と別に読む。

実行者は、秘密の情報を持つファイル(`.env` で始まるファイル、鍵のファイル、認証の情報のファイル)を読まず、値を聞き取りの記録に写さない。実行者が流す git のコマンドは、読むだけの `git log`、`git status`、`git show`、`git diff`、`git branch` に限る。ファイルを名前で探すツールかファイルの中身を検索するツールがないときに、全スキル共通の決まりのとおりにコマンドを実行するツールで代わりに探すコマンドは、この git のコマンドと別に扱う。

| 対象 | 調べること | 読む範囲の既定 | 決まる項目 |
|---|---|---|---|
| 既にあるスキル | 名前、description、重なる作業、同じ名前があるか | 対象のプロジェクトの `.claude/skills/`、`~/.claude/skills/`、`~/agent-home/skills/` の直下の `SKILL.md` と、skill-factory の `output/*/SKILL.md`。`output/*/tests/` は除く。この表の行は、skill-factory を対象にしない決まりの例外とする | 2、4-2 |
| 関係するコード | 書き込みの語に関わるファイル、関数、スクリプト、呼び出し元、前のスキル | 書き込みのパスのフォルダと、対象のプロジェクトを、テストのフォルダ(`tests/`、`test/`、`__tests__/`)を除いて、ファイル名と中身の語で検索する。読み方は「調査が読めないときの動き」の章のとおりとする | 16、8、22、17-1、4-1 |
| 入力の実物 | 形式、章立て、値の例、件数、大きさ | 書き込みか答えが指すファイルと、同じフォルダの同じ種類のファイル | 6-1、6-3、6-4、6-6、26 |
| 出力の置き場 | 同じ種類のファイルの場所、名前の付け方、見出しと並び、出力先に同じ名前のファイルがあるか、同じ種類の文書が 1 つのファイルか複数か、ファイルごとの名前 | 入力と同じフォルダと、対象のプロジェクトの README、`docs/`、`output/` の一覧 | 7-10、7-1、7-5、7-6、7-4、7-7、10 |
| 作れるか | 規約が限るネットワークと実行系に、作業が合うか | `<SKILL.md があるフォルダ>/../../rules/skill-writing/skill-writing-rule/skill-writing-rule.md`(規約 skill-writing-rule)の節「前提ツール」。step 4-2 と step 6-4 と step 7-4 で読む | 29、25 |
| プロジェクトの決まり | 規約、CLAUDE.md、README の決まり | 対象のプロジェクトの規約と CLAUDE.md | 12-1 |

手元に答えがない語の意味、形式の仕様、外部のサービスの決まりは、「分からないこと」に書いて続ける。

関係するコードと資料(項目 23)の値は、designing-skill-phases が、要件定義書の使うプロジェクト(項目 11-3)と聞き取りの記録の章「調査の結果」から決める。

## 深掘りの問いの作り方

この章は、判定の基準である。実行者は、調査の結果が次の条件に当たるときだけ、「問いの雛形」の章の形の問いを足す。足した問いの番号は、「深掘り <番号>」とする。実行者は、答えを列「反映する項目」に書く。

| 条件 | 足す問いの形 | 反映する項目 | 問う時点 |
|---|---|---|---|
| 書き込みと調べた事実が食い違う | 「<書き込みの語>と書かれていますが、<ファイル>は<事実>です。どちらに合わせますか。」 | その語の項目 | 最初の問い |
| 値の候補が 2 つ以上見つかった | 「<候補 1>と<候補 2>があります。どちらを使いますか。」 | その値の項目 | カテゴリーの問いの中 |
| 関係するコードがスキルの作業を既に行っている | 「<ファイル>が同じ作業をしています。使いますか、置き換えますか。」 | 2、8 | カテゴリーの問いの中 |
| 依頼の語で、項目 7-1、7-10 の問いと合格の 1 問で聞けない、語の定義の問いが残った | 「<語>は、<候補 1>と<候補 2>のどちらですか。」(候補は具体的な形で書く) | その語の項目 | カテゴリーの問いの中 |
| 作業が、消す、送る、外部へ公開する操作を含む | 「どの操作の前に確かめますか。確認は外せません。」 | 22 | カテゴリーの問いの中 |
| 項目 29 で作れない作業があり、作れる形が 2 つ以上ある | 「<作業>は、<できない理由>のためスキルの手順にできません。次のどの形で作りますか。やめることもできます。」 | 29、16、25 | 最初の問い |

列「問う時点」の「最初の問い」は step 4-3 で問いを作る条件とし、「カテゴリーの問いの中」は step 6-1(カテゴリー「渡すものと出すもの」)と step 7-1(残りのカテゴリー)で問いを作る条件とする。

## 調査が読めないときの動き

この章は、判定の基準である。

- 読むファイルが読めないときは、そのファイルを「分からないこと」に書いて続ける。
- 検索で当たった行を先に読んで関係するファイルを決め、関係するファイルをすべて読む。
- 関係するコードがないときは、「関係するコードはありません(調べた範囲: <範囲>)」を事実にする。
- 調査の候補が 0 件の問いは、「問いの雛形」の章の欄「選択肢の作り方」のとおりに、書き込みの語で作った「AI の案」か「その他」で答えてもらう。
- 対象のフォルダが git のリポジトリでないときは、git のコマンドで調べられなかったことを「分からないこと」に書いて続ける。
- 対象のフォルダが git のリポジトリで、git のコマンドの終了コードが 0 でないときは、コマンドを実行するツールで `git status --porcelain=v2 --branch` を実行してコミットの数を確かめる。終了コードが 0 で、標準出力が行 `# branch.oid (initial)` を持つときは、コミットが 0 件である。終了コードが 0 で、この行を持たないときは、コミットが 1 件以上である。終了コードが 0 でないときは、コミットの数を確かめられない。
- コミットが 0 件のリポジトリは、正しい入力である。実行者は、「コミットがありません(確かめたコマンド: `git status --porcelain=v2 --branch`)」を事実にし、`git log` と `git show` を流さずに、作業ツリーのファイルを調べて続ける。
- コマンドの失敗の原因がコミットが 0 件であることのほかにあるときは、実行者は、手順の中止の段落のとおりに中止する。

## 問いのあとの調査

この章は、判定の基準である。実行者は、項目 6-1、7-1 の答えか、最初の問いか事実確認の直しで初めて入力か出力かパスが分かったときは、次のカテゴリーの問いを作る前に、その入力の実物と、同じ種類のファイルを「調査の対象と読む範囲」の章の範囲で調べ、答えの語で既にあるスキルを比べ直す。実行者は、結果を聞き取りの記録の章「調査の結果」に、調べた範囲と実行した git のコマンドを章「調べた範囲」に足し、次の問いの知らせの行に「調べ直した結果: <事実>」の 1 文で出す。

## 語の定義を決める手順

この章は、判定の基準である。実行者は、ユーザーが定義を書かずに使った語(例: 基本設計書、要約、レビュー)の定義について、規約 thinking-rule の節「AI が依頼の語の定義を決めるとき」の規則を、次の手順で当てる。項目 7-1、7-10 の問いと、語の深掘りの問いは、この手順で作る。

実行者は、この章を読む step(3-1、5-1、5-2、6-1、6-4、7-1、7-4、8-1、9-2)で、`<SKILL.md があるフォルダ>/../../rules/thinking/thinking-rule.md`(規約 thinking-rule)を、ファイルを読むツールで全文読む。

読めないときは、中止する。
理由: <SKILL.md があるフォルダ>/../../rules/thinking/thinking-rule.md を読めない。
ユーザーが次にすること: 規約 thinking-rule のファイルがあるかを確かめてから、もう一度実行する。
中止までの成果物: <要件定義書の出力先のフォルダ>/聞き取りの記録.md があるときは、<要件定義書の出力先のフォルダ>/ と <要件定義書の出力先のフォルダ>/聞き取りの記録.md。なければ、なし

1. 規約 thinking-rule の規則「語の定義の分かれる点は、6 つの項目ごとに挙げる」の対象の語を、書き込みと答えと直しから挙げる。
2. 同じ規則で、語ごとに分かれる点を挙げる。
3. 規約 thinking-rule の規則「分かれる点は、具体的な候補にして、成果物が変わる点だけを問う」で、候補を作り、問うかどうかを決める。
4. 候補が 1 つに絞れた点の定義と出典を、下書きの章 1 に書く。
5. 成果物が変わる点に当たらない点の、先に見つかった候補を、出典か「AI の案」を添えて下書きの章 1 に書く。
6. 出すものの語の範囲と部分を項目 7-1、7-10 の問いに、できた状態を合格の 1 問に、ほかの項目と、読むものと主な動作の語を深掘りの問いにする。
7. 語、項目、ユーザーの答えか候補、出どころを、聞き取りの記録の章「語の定義」の表の行に書く。
8. 答えか直しで新しい語が出たときは、その語で手順 2 へ戻る。

手順の終わりは、規約 thinking-rule の規則「語の定義を決める作業を終える条件」のとおりとする。実行者は、手順の問いが残る限り、深掘りの問いを出す。

手順を行う時点は、次の表のとおりである。

| 時点 | 実行者がすること |
|---|---|
| 書き込みを読んだ直後(step 3-1) | 手順 1。2 通りに読める語を読みの候補にする |
| 調査の間(step 5-1) | 「出力の置き場」「入力の実物」「関係するコード」「プロジェクトの決まり」の順で、語の定義の出典を探す |
| 調査の直後(step 5-2) | 手順 2 と手順 3。問わない点を手順 7 で記録に書く |
| カテゴリー「渡すものと出すもの」の先頭(step 6-1) | 手順 6。出すものの語を項目 7-1、7-10 の 1 問にする |
| 読むもの(項目 6-1)か作業の順(項目 16)の問いの前(step 7-1) | 手順 6。読むものと主な動作の語を深掘りの問いにする。読むものの語の問いは項目 6-1 の前に、主な動作の語の問いは作業の順の問いの前に出す |
| 項目 6-1 の答えで語が初めて分かったあと(step 6-4、7-1) | 手順 6。その語の深掘りの問いを、次のカテゴリーの先頭に出す |
| 答えか直しを受けた直後(step 6-4、7-4、9-2) | 手順 7 と手順 8 |
| 下書きの作成(step 8-1) | 手順 4 と手順 5 の定義と、答えた出すものの語の定義を、下書きの章 1 に書く |
| 下書きの承認(step 9-1) | 答えた定義と問わなかった定義を下書きの章 1 に出し、照合者が 2 通りに読めるとした語を確かめる点に出す |

定義の問いを飛ばすときは、問いも知らせも出さず、下書きにだけ定義を出す。

## 語の定義の 6 つの項目の例

この章は、判定の基準である。項目の意味は、規約 thinking-rule の規則「語の定義の分かれる点は、6 つの項目ごとに挙げる」にある。次の表の例は、項目ごとに実行者が考える点か候補である。答えの置き場は、「範囲」「部分」「使い道」「境目」が項目 7-10、「何か」が項目 7-3、7-4、「できた状態」が合格の 1 問である。読むものと主な動作の語の答えと、問わずに決めた定義は、その語の項目(6-1、16)に置く。

| 項目 | 基本設計書 | 要約 | レビューする |
|---|---|---|---|
| 何か | 文書か、図を含む資料か | 文書か、チャットへの表示か | 読んで指摘することか、合否を決めることか |
| 範囲 | 1 つのファイルか、基本設計の作業で要るファイルの組か | 議事録 1 件ごとか、週ごとのまとめか | 1 つの変更か、プロジェクトの全体か |
| 部分 | システム構成、画面一覧、データ設計 | 決定事項、宿題 | 正しさ、読みやすさ、規約との一致 |
| 使い道 | 開発者が詳細設計を書く、発注者が承認する | 欠席した人が宿題を知る | 作者が直す、取り込むかを決める |
| できた状態 | 画面の名前がどのファイルでも同じ | 300 字以内 | 指摘が行番号を持つ |
| 境目 | 要件定義書、詳細設計書 | 議事録の全文の清書 | テストの実行、コードの修正 |

## 聞き取りの記録の形

この章は、雛形である。実行者は、聞き取りの記録を、次の形の Markdown の文書で `<要件定義書の出力先のフォルダ>/聞き取りの記録.md` に書く。行が 0 件の表は、見出しの行と区切りの行だけとする。章「項目の振り分け」の状態が「書かれていない」の行は、値と値の出どころと出どころの箇所を「なし」と書く。章「項目の振り分け」の状態が「AI が案を作る」の行の値は、step 5-2 で「案は下書きの作成で作る」と書き、step 8-1 で案の値に書き換える。step 8-1 が章「項目の振り分け」に足す行は、項目の番号を「<項目の番号>の<要件定義書の欄の名前>」(表の欄の値は、後ろに「(<表の行の番号> 行目)」を添える。例: 「16 の見て決めること(2 行目)」)、値を要件定義書に書く値の全文、値の出どころを、その値の要件定義書の章 6 の出どころの種類とする。足す行の状態は、値の出どころが「文章」なら「書かれている」、「調査と承認」か「決まった式」なら「AI が調べて決まる」、「案と承認」なら「AI が案を作る」とする。足す行の出どころの箇所は、値の出どころが「文章」なら書き込みの引用、ほかは値の元にした答えの番号か項目の番号とする。章「調査の結果」の既にあるスキルは、表「事実」に、スキル 1 本につき 1 行で name と description を書き、出典を `SKILL.md` のパスとする。

## インストールの方法

この章は、対応表である。step 1-5 で、不足している前提ツールをインストールするときに読む。

### OS の見分け方

セッションの環境の情報の Platform の値を、次の表で OS に対応させる。

| Platform の値 | OS |
|---|---|
| `darwin` | macOS |
| `linux` | Linux(WSL を含む) |
| `win32` | Windows |

### OS ごとのインストールのコマンド

パッケージマネージャだけを使い、一般ユーザーの権限で実行できるコマンドだけを書く。

| OS | ツール | インストールのコマンド | 先に書くファイル |
|---|---|---|---|
| macOS | node | `brew --version && brew install node` | なし |
| Linux | node | `brew --version && brew install node` | なし |
| Windows | node | `winget install OpenJS.NodeJS.LTS` | なし |
| macOS | git | `brew --version && brew install git` | なし |
| Linux | git | `brew --version && brew install git` | なし |
| Windows | git | `winget install Git.Git` | なし |
