セッションワークフロー管理
managing-session-workflow

毎ユーザーターンで目的・訂正・完了条件・公開条件を再評価し、共通 handoff で専門 Skill へ引き継ぐ進行管理スキル。

こんな人向け
セッション冒頭で「前回何をしていたか」「次に何をすべきか」を毎回自分で調べ直している人。
こんな場面で使う
SessionStart hook（suggest-session-workflow.sh）が advisory を注入した直後、または手動でセッション冒頭に状況把握と誘導を行いたい場面。
対応 OSmacOS（agent-home の各スキルと同じ実行環境を前提とする）

§1概要・設計思想

本スキルは毎ターンの発話を新規・追加・訂正・置換・質問へ分類し、purpose・Goal・completionCriteria・constraints・routing・handoff・tracking・final判定だけを担う。実装や調査自体は専門 Skill へ委任する。

役割分担
UserPromptSubmit hook は本 Skill 全文と現ターン checksum を供給するが、Skill 実行完了は記録しない。後続 Skill には必須7キーの共通 handoff を渡し、公開条件を含む実測証拠が揃うまで complete にしない。

§2出力

本スキルを実行すると、以下が生まれる。

状況要約
プロジェクト名・前回セッションの最終状態・未完了レビューの有無・未コミット変更の有無・並走 PR の有無・推奨する次のアクションを 5 行以内でまとめたユーザー向け報告。
後続ルーティング
ユーザーの要望と読み取った状態から、利用可能な専門スキルを優先して起動する。該当スキルが存在しない場合は標準 reviewer・実行担当・通常応答へ縮退し、同じ completionCriteria と証拠条件を渡す。
必読ファイルの提案
flow-values.yml の context_a（調査前提）/ context_b（計画前提）から、現在の Phase に必要なファイルの提案リスト。自動読み込みはせず、ユーザーが承認したものだけを Read する。
共通 handoff
goal・purpose・completionCriteria・constraints・userCorrections・inputs・publication を持つ、後続 Skill 用の正規化契約。訂正は original/normalized/target、actionable画像は2段階確認結果の scopeConfirmation を保持する。

§3Phase 1: 状態の読み取り（読み取り専用）

Step内容
Step 1-1: プロジェクト判定cwd からプロジェクトを判定する。flow-values.yml の有無と内容を確認する。
Step 1-2: フロー状態の確認skill-log（~/agent-home/sessions/.skill-log/ 配下の JSON Lines 形式ファイル）から直近セッションの履歴を取得する（mtime ソートで直近ファイルを特定）。git log から未完了フローの痕跡（未マージのブランチ、worktree の存在）を確認する。全情報源が不在の場合は「新規セッション」として扱う。
Step 1-3: 作業環境の確認git status で未コミット変更を確認する。gh pr list --state open で並走 PR を確認する（オフラインの場合はスキップ）。

完了条件: プロジェクト名・フロー状態・作業環境の 3 軸の情報が揃っている（または「新規セッション」と判定されている）。

§4Phase 2: 状況の報告

Step 2-1 で以下の情報を 5 行以内でユーザーに報告する。

  • プロジェクト名と前回セッションの最終状態
  • 未完了のレビュー・品質確認の有無
  • 未コミット変更の有無
  • 並走 PR の有無
  • 推奨する次のアクション

完了条件: ユーザーが現在の状況を把握している。

§5Phase 3: フロー判定と誘導

Step 3-1: フロー判定

ユーザーの要望と Phase 1 の状態から、適切なスキルを 1 つ特定する。

状況誘導先
前回の続きあり（skill-log + git log で検知）該当スキルの該当 Phase から再開
前回の続き + 新規要望が同時AskUserQuestion でどちらを優先するか確認
新機能追加 / バグ修正 / リファクタorchestrating-dev-flow
スキル / ルール / hook 作成managing-agent-configs
レビュー依頼managing-review-sets
計画の提示presenting-plan-with-artifacts
issue 作成 / 着手managing-github-issues
単純な質問 / 小規模修正フロー不要。直接対応（スキルを起動しない）
判断できないAskUserQuestion でユーザーに確認

Step 3-2: 先回り検知

フロー判定に関わらず、以下を検知して先回りで対応する。

  • 計画ファイル（plans/*.md）があるがレビュー未実行 → managing-review-sets を先に起動
  • 未コミット変更があるが前回のフローが完了している → コミット / PR 作成を提案
  • 並走 PR が存在する → 競合の可能性を報告

Step 3-3: スキル起動

判定結果に基づいて Skill() で該当スキルを起動する。「フロー不要」の場合はスキルを起動せず直接対応する。

完了条件: 適切なスキルが起動されている、または直接対応が開始されている。

§6Phase 4: コンテキスト提案

Step 4-1: flow-values.yml の context_a（調査前提: 地図と語彙）/ context_b（計画前提: 配置・命名・テスト等の規約）から、現在の Phase に必要なファイルを提案する。

コンテキスト消費の制御
提案のみ行い、自動読み込みはしない。ユーザーが承認したものだけ Read する。

完了条件: 必読ファイルの提案が提示されている。

§7起動方法

SessionStart hook（scripts/suggest-session-workflow.sh）が advisory を注入する。hook からは Skill() を呼べないため、Claude が注入を受けて Skill("managing-session-workflow") を自発的に呼ぶ。手動起動（/managing-session-workflow）も可能。

§8完了条件

Phase完了条件
Phase 1プロジェクト名・フロー状態・作業環境の情報が揃っている
Phase 2ユーザーに状況要約を 5 行以内で報告済み
Phase 3適切なスキルが起動されている
Phase 4必読ファイルの提案が提示されている
Goalユーザーが正しいフローに乗り、必要なコンテキストを把握した状態で作業を開始できる

§9サブエージェント委任・ループ設計・実行方式

サブエージェント委任仕様
Phase 1 の情報収集は軽量なため委任不要（メイン自身が Read / Bash で実行）。Phase 3 のスキル起動は Skill() で直接呼び出す。
ループ設計
本スキル自体にループはない（セッション開始時に 1 回実行して完了）。Phase 3 で起動した先のスキルがそれぞれ独自のループを持つ。
実行方式
main-session（Skill / TaskCreate / AskUserQuestion を使用）。
