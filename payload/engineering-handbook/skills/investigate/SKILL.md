# 調査

コードと変更履歴を読んで、質問に根拠付きで答える。成果物は説明か推奨であって、コードの変更ではない。

## いつ使うか

- 「この機能はどう動いているか」「データはどこを流れるか」を知りたいとき
- 「なぜこう作られているか」「いつから、誰の判断でこうなったか」を知りたいとき
- 「この処理はどのモジュールに置くべきか」のような、置き場所や責任範囲の判断
- 複数の選択肢から、どれを採るべきか判断材料がほしいとき

**使わないとき。** 調べた結果すぐに直す作業は、bug-fix、feature、refactor のどれかを使う。この skill の結論がそれらの最初の材料になる。

## 手順

### 1. 質問を言い直す

質問を自分の言葉で1〜2文に言い直して、最初に書く。対象(どのコード、どの機能)と、知りたいこと(仕組みか、経緯か、置き場所か、選択か)を分けて書く。対象があいまいなら、会話の文脈から一番ありそうな解釈を選んで明記し、そのまま進める。読み違いなら、ユーザーがそこで正せる。

### 2. 範囲を決める

- **狭い質問。** 1つの関数、1つのモジュールなら、直接読んで答える。
- **広い質問。** 複数のファイルやサービスにまたがるなら、2〜4つの観点に分ける(例: 入口と呼び出しの流れ、データの形と保存先、エラー時の扱い)。観点ごとにサブエージェントに読ませてもよい。その場合、手元には要約だけを残す。

迷ったら狭い方から始める。

### 3. 仕組みを読む(「どう動くか」)

- 入口(画面の操作、API、コマンド、ジョブ)から順に、実際の呼び出しをたどる。名前から推測しない。
- 主要なデータの型と、それがどこで作られ、どこで変わり、どこに保存されるかを書き出す。
- 分岐、エラー処理、非同期の境界、キャッシュのように、読み落としやすい箇所を拾う。
- 動かして確かめられるなら、確かめる。ログを出す、テストを1本走らせる、実際に呼んでみる。読んだだけの理解は「推測」として扱う。

### 4. 経緯を読む(「なぜこうなっているか」)

経緯の質問のときだけ行う。

```bash
git blame -L <開始行>,<終了行> <ファイル>      # その行を最後に触ったコミット
git log --follow --oneline -20 -- <ファイル>   # 改名をまたいだ変更履歴
git log -1 --format=%B <コミット>              # コミット本文と PR 番号
gh pr view <番号> --json title,body,comments,reviews   # PR の説明と議論
```

- コミット本文、PR の説明とレビュー、リンクされた Issue を読む。
- 見つからなかった情報源も「探したが無かった」と記録する。
- 記録から確かに言えることと、状況からの推測を分ける。「この PR で〜と説明されている」は事実、「おそらく〜のためだ」は推測。

### 5. まとめる

仕組みの質問は、次の見出しで書く。当てはまらない見出しは省く。

- **概要。** 2〜3文で全体像。
- **主要な概念。** 理解に必要な型、用語、責任の分担。
- **処理の流れ。** 入口から出口までの流れを、番号付きで。
- **どこにあるか。** 主要なファイルと関数のパス。
- **落とし穴。** 読み違えやすい点、変更するときに壊しやすい点。

選択の質問は、選択肢ごとの利点、欠点、影響範囲を表にし、最後に自分の推奨と理由を書く。

## 完了の条件

- 質問に正面から答えている。
- 主要な主張に、ファイルパス、コミット、PR、実行結果のどれかが付いている。
- 確かめていないことには「推測」「未確認」と書いてある。

## 止まって確認する場面

- 調べた結果、質問の前提が間違っていると分かったとき。証拠を示して、前提が違うと伝える。
- 答えるのに、本番環境や外部サービスへの書き込みが必要なとき。

## 報告に書くこと

1. 質問の言い直し
2. 答え(上の見出しの形、または選択肢の表と推奨)
3. 根拠の一覧(ファイル、コミット、PR、実行したコマンド)
4. 分からなかったことと、次に調べるなら何を見るか

「本当に大丈夫か」と聞かれたら、相手に合わせず本当の判断を書く。

## 使っている規約

- V-08 実物で動作を証明する: 読んだだけの理解は推測として扱う
- A-01 最初に、目的を自分の言葉で言い直す
- A-05 迎合しない
- A-08 コンテキストを節約する: 広い調査は観点ごとに分け、要約だけ残す
- A-10 主張には、根拠かラベルを付ける
- A-11 リンクや引用を捏造しない
