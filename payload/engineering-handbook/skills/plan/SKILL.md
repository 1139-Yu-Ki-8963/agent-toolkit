# 計画

大きな作業を、1つずつ確かめられる小さな PR の並びに分けて、計画書にする。この skill の責任は計画であって、コードではない。実装はしない。計画書は、実行する人がチェックボックスを1つずつ埋め、確認する人が証拠で検証できる形にする。

## いつ使うか

- 1つの PR では大きすぎる機能追加、移行、作り直し
- 複数人やエージェントで分担する作業
- どの順番で進めると安全か、整理が必要な作業

**使わないとき。** 変更が1〜2ファイルで、やり方が明らかなら計画は要らない。そう伝えて、feature や bug-fix に進む。

## 手順

### 1. 目的を言い直す

誰のために、何を変えるのか、完了したら何ができるようになるのかを、5行以内で書く。

### 2. 未決の論点を先に片付ける

方式や見た目で決まっていないことがあれば、計画を書く前に決める。実行して観察できる問いは、prototype のやり方で試作して決める(使い捨ての案を並べ、観察で選ぶ)。ユーザーに聞くのは、実験では決まらないプロダクトの判断だけにする。聞くときは選択肢と推奨を示す。

### 3. 既存のコードを把握する

影響するサブシステムを読み、次を書き出す。範囲が広いときは観点ごとにサブエージェントに読ませ、手元には要約だけを残す。

- 変更が入る主要なファイルと入口
- 既存の規約(命名、ディレクトリの分け方、テストの書き方)
- テスト、型チェック、リントの実行コマンド
- アプリを実際に動かして確かめる方法

### 4. PR に分ける

分け方の基準は次のとおり。

- **1つの PR は1つの変更で、それ自体の証拠を持つ。** 単独でマージしても壊れない単位にする。
- **土台を先に。** 後のすべての PR が楽になるもの(共有の型、テスト基盤、設定)を最初の PR にする。
- **削除を先に。** 不要なコードの削除は、作り替えより前の PR にする。
- **最終形に向けて進める。** 途中の互換性を保つための一時コードは作らない。一時的に壊れてよい箇所があるなら、計画書に明記する。
- **依存関係を書く。** どの PR がどの PR の後か、並行して進められるのはどれかを書く。
- **触るファイルの範囲を書く。** 並行して進める PR 同士が同じファイルを触らないようにする。

### 5. 計画書を書く

次の雛形をそのまま使い、全部の項目を埋める。保存先はユーザーの指定がなければ `docs/plans/<テーマ>.md`。

```markdown
# <テーマ> の計画

<5行以内: 何が、誰にとって変わるか。守るべきルール。PR の一覧と順番>

## 読み方

チェックボックス1つが作業1つ。各ボックスには、完了を示す証拠(ファイル、ログ、スクリーンショット、テスト結果、コミット)を書く。証拠がそろったときだけチェックする。

テストが通るだけでは検証にならない。PR は、自動テスト、実物での確認、(該当すれば)性能の各ボックスがすべて埋まったときだけ検証済みとする。

## 全体の順番

- [ ] PR1 と PR2 は独立していて、最初に着手できる
- [ ] PR3 は PR1 のマージ後
- [ ] 触る範囲: PR1 は `<パス>` のみ、PR2 は `<パス>` のみ

## <動詞で書いた作業名>(PR1)

**依存。** なし
**目的。** <1〜2文>
**変更。**
- [ ] <変更内容1>
- [ ] <変更内容2>

**検証(自動テスト)。**
- [ ] <実行するコマンド> が通る
- [ ] <追加する、または変更するテスト>

**検証(実物)。**
- [ ] <具体的なシナリオ> を実際の画面や API で実行し、<期待する結果> を確認する。証拠: <スクリーンショットやログの保存先>

**検証(性能)。** <該当しなければ「なし」と書く>
- [ ] <指標> を変更前と変更後で測り、<この値を超えたら不合格> を満たす

**リスク。** <壊しうるもの、気を付ける点>

## 付録 A: 決定事項

<試作や調査で決めたことと、その根拠>

## 付録 B: 未決事項とリスク
```

### 6. 自分で点検する

書き終えたら、次を確かめる。

- 全部の PR に、検証の項目(自動テスト、実物、性能)がある。実物の確認が「動作確認する」のような抽象的な書き方になっていない。
- 依存関係に循環がない。並行の PR 同士が同じファイルを触っていない。
- プレースホルダ(`<...>`)が残っていない。
- 「後で決める」が本文に残っていない。残るなら付録 B に移し、誰がいつ決めるかを書く。

### 7. 渡して止まる

計画書のパスと要約を報告して、止まる。実装は、ユーザーが明示的に「進めて」と言ってから始める。

## 完了の条件

- 計画書がファイルとして保存されている。
- 各 PR が単独でマージでき、それぞれに具体的な検証の項目がある。
- 依存関係と触る範囲が書いてある。

## 止まって確認する場面

- 計画を書き終えたとき(必ず止まる)。
- 実験では決まらないプロダクトの判断が残ったとき。

## 報告に書くこと

1. 目的の言い直し
2. 計画書のパス
3. PR の一覧(1行ずつ)と依存関係
4. 決定事項と、残った未決事項

## 使っている規約

- V-01 土台から考える: 後のすべてが楽になるものを最初の PR に
- V-02 新しい要件は、最初からあった前提で設計し直す
- V-04 足す前に削る: 削除の PR を先に
- V-06 移行は最終形に向けて進める
- V-08 実物で動作を証明する: テストだけでは検証にしない
- V-12 検証できる小さな単位で進める
- A-04 聞く前に、試して確かめられないか考える
- A-08 コンテキストを節約する
