# 試作

決めるべきことを1つ決めるために、使い捨ての試作を作って比べる。この skill の責任は「正しい判断」であって、コードではない。試作は捨てる前提で作る。

## いつ使うか

- レイアウト、操作、情報の密度など、見て触らないと決まらない UI の判断
- 動作、速度、タイミングのように、実行すれば観察できる方式の判断
- 「A と B どちらにしますか」とユーザーに聞きたくなったとき。答えが実行して観察できる事実なら、聞く前に試作で決める

**使わないとき。** 決めることがすでに決まっているなら試作は要らない。feature で本番の実装に進む。

## この skill だけの例外

他の作業と違い、ここではコードの品質を求めない。速さを優先し、テスト、抽象化、本番のフレームワークは使わない。厳しさは「安く、正しい判断にたどり着くこと」に向ける。ユーザーが頼んでいない案も出してよい。うまくいかない案はすぐ捨てて、次を試す。

## 手順

### 1. 決めることを1文で書く

例:「一覧画面はカード型と表型のどちらにするか」「保存は入力ごとか、まとめてか」。決めることが書けないなら、試作をする理由がない。

### 2. 方向が決まっていなければ、参考を集める

似た製品や既存の画面の例を集め、テーマ、配色、配置の傾向を短くまとめる。方向性をユーザーに選んでもらってから作る。方向が決まっていればこの手順は飛ばす。

### 3. 本番のコードと分けて作る

- 本番のソースとは別の作業用フォルダに作る(例: `scratch/prototype-<テーマ>/`)。本番のコードには触らない。
- **見た目の判断。** 素の HTML、CSS、JavaScript など、そのアイデアを表示できる一番軽い手段で作る。
- **動作やタイミングの判断。** その問いだけを確かめる最小のスクリプトを書く。

### 4. 案を並べて切り替えられるようにする

複数案を比べるときは、1つの画面にボタンやキー操作で案を切り替える仕組みを付け、各案にラベルを付ける。並べて比べられることが試作の価値になる。案は2〜3個。構造から違う案を出す。同じ案の細部違いを並べても判断材料にならない。

### 5. 実物で観察する

- **見た目の判断。** 各案のスクリーンショットを撮り、実際に操作してみる。
- **動作やタイミングの判断。** 時間を計測する、出力を表示する、描画を見る。

ここでは観察そのものがテストになる。

### 6. 決定と推奨を示す

案ごとの利点、欠点、観察した結果を並べ、自分の推奨を理由付きで書く。選ばれた方向は、feature で本番として作り直す。試作のコードをそのまま本番に持ち込まない。

## 完了の条件

- 決めること1つに対して、比べた案と観察の証拠(スクリーンショット、計測値、出力)がそろっている。
- 推奨が1つ、理由付きで書いてある。

## 止まって確認する場面

- 実験では決まらない、プロダクトの方向性や好みの判断が残ったとき。選択肢と推奨を示してユーザーに決めてもらう。

## 報告に書くこと

1. 決めること(1文)
2. 試した案と、それぞれの観察結果(スクリーンショット、計測値、出力)
3. 案ごとの利点と欠点
4. 推奨と理由
5. 試作の置き場所と、「これは使い捨て」であること

## 使っている規約

- V-03 前例がなければ、複数案を作って比べる
- V-07 使う人の体験を優先する
- V-08 実物で動作を証明する: ここでは観察がそのまま証拠になる
- A-04 聞く前に、試して確かめられないか考える
- A-10 主張には、根拠かラベルを付ける
