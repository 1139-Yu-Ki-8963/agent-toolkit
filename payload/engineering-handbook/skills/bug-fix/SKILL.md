# バグ修正

バグを、再現から PR まで直す。科学的に進める。出荷する行はすべて、実行時の証拠にたどれなければならない。「効くかもしれない」念のための変更は仮説であって、修正ではない。

## いつ使うか

- 期待と違う振る舞い、エラー、クラッシュ、データの不整合
- 「前は動いていたのに動かなくなった」という報告

**使わないとき。**
- 遅い、重い → performance
- 振る舞いは正しいが構造が悪い → refactor
- 原因を知りたいだけで直さない → investigate

## 手順

### 1. 報告を言い直す

最初に、報告された問題を自分の言葉で書く。期待する振る舞い、実際の振る舞い、起きる条件の3つに分ける。報告がスレッドやチャットで長いときは、ここで読み違いを潰す。

### 2. 自分で再現する

- ユーザーが問題に遭遇したのと同じ面(画面、API、CLI)で、自分で再現する。ユーザーに再現を頼まない。
- 頼むのは、その面にどうしても届かない具体的な理由があり、届くところまで自分で進めた後だけにする。
- そのままで再現しないときは、条件を絞る、引き金を人工的に作る、ログを足して起きるまで観察する。
- 再現できたら、その手順を何度でも実行できる形(コマンド、スクリプト、テスト)で残す。

再現できないまま修正に進まない。

### 3. 原因を二分探索で絞り込む

- 原因の候補(仮説)を複数挙げる。影響する箇所の処理の流れを読み、最近の変更履歴(`git log`、`git blame`)も材料にする。
- 一番多くの候補を一度に潰せる観察から行う。ログを足す、値を出力する、範囲を半分にする。推測で決めない。
- 「前は動いていた」なら `git bisect` で原因のコミットを特定する。
- 残った仮説の仕組みを、実行時の証拠で確かめてから次に進む。

**根本原因の見分け方。**
- 症状が出た場所ではなく、最初にシステムが間違った判断をした場所を探す。「なぜ」を繰り返し、答えが「前の何かの結果」ではなく「コードの間違った判断」になるまで遡る。
- その状態はありうるものか考える。ありうるなら、それを扱えなかったコードが原因だ。ありえないなら、それを作った場所が原因だ。ありえない状態にガード、リトライ、例外の握りつぶしを足すのは、バグを隠しているだけだ。
- 再起動後にだけ起きるなら、保存された状態(設定、キャッシュ、ロックファイル)を先に疑う。

**同じ前提の修正が2回失敗したら止まる。** 失敗した修正がすべて置いていた前提を1文で書き、その前提が間違っていたら結果が変わるはずの観察を、次の修正の前に行う。

### 4. 修正を決める

- 証拠が裏付ける最小の変更にする。証拠で否定された仮説のために入れた変更は、元に戻す。
- 同じ原因の箇所がほかにもないか探し、あればまとめて直す。
- 修正が関数の境界をまたぐなら、型とシグネチャを先に決めてから書く。

### 5. 失敗するテストを先に書く(安く書けるとき)

既存のテストの仕組みで安く書けるなら、修正の前に、バグを捕まえるテストを書く。

1. 修正前に実行し、意図した理由で失敗することを確かめる。別の理由で失敗するなら、テストを直す。
2. 修正する。
3. 同じテストが通ることを確かめる。

テストに大がかりな準備、壊れやすいモック、遅い E2E 環境、本番にしかない状態が要るなら、新しいテストは書かない。代わりに手順2の再現スクリプトを使う。悪いテストを足すより、テストを足さない方がよい。テストを、間違った実装に合わせて書き換えない。

### 6. 同じ方法で直ったことを確かめる

手順2と同じ面、同じ手順で再現を実行し、直ったことを確かめる。ユニットテストが通ることは分岐の振る舞いを示すだけで、バグが無いことの証明にはならない。「どちらとも言えない」結果や、違う面での確認は合格ではない。そう明記する。

### 7. コミットを整えて PR にする

- 失敗するテスト(または再現)のコミットを先に、修正をその上に積む。履歴だけで「赤から緑になった」ことが分かるようにする。
- PR の説明には、何が壊れていたか、根本原因、修正、確かめ方を書く。詳しい書き方は open-pr にある。

## 完了の条件

- 修正前の失敗と、修正後の成功を、同じ再現手順で示した証拠がある。
- 根本原因を1〜2文で説明できる。
- 証拠に裏付けられない変更が、差分に残っていない。

## 止まって確認する場面

- 再現に、本番データの変更やユーザーの手元の環境が必要なとき。理由を具体的に書いて頼む。
- 根本原因の修正が、仕様の変更や他チームの領域に及ぶとき。
- デプロイ、データの削除、共有ブランチへの force-push が必要になったとき。

## 報告に書くこと

1. 何が壊れていたか(期待と実際)
2. 根本原因(どこで、なぜ)
3. 修正の内容
4. 確かめた方法。修正前の失敗と修正後の成功の出力を、そのまま貼る
5. 同じ原因の箇所をほかに探した結果

## 使っている規約

- V-05 最小の変更にとどめる
- V-08 実物で動作を証明する
- V-09 根本原因を直す
- V-10 同じ前提で2回失敗したら、前提を疑う
- V-12 検証できる小さな単位で進める: 失敗するテストを先に
- A-01 最初に、目的を自分の言葉で言い直す
- A-10 主張には、根拠かラベルを付ける
