# リファクタ

構造を変え、振る舞いは変えない。この skill の責任は、外から見た約束(振る舞い)を守ることだ。新しい振る舞いの追加は feature、間違った振る舞いの修正は bug-fix で扱う。

## いつ使うか

- 読みにくい、変更しにくいコードを整理するとき
- モジュールの分け方、型、呼び出し関係を変えるとき
- 古い API を新しい API に置き換えるとき

**使わないとき。**
- 整理の途中で、足りない機能や本物のバグが見つかった → 切り出して、先に構造の変更だけを出荷する。機能は feature、バグは bug-fix で別に扱う
- 作り直しが設計そのものを変える → feature として扱う
- 大きく、多くのモジュールにまたがる → 先に plan で分ける

## 手順

### 1. 現在の振る舞いを固定する

構造に触る前に、今の振る舞いを捕まえるテストを用意する。

- 対象のサブシステムを読み、外から見た約束(入力に対する出力、副作用、エラー時の振る舞い)を書き出す。
- 既存のテストで約束が守られているか確かめる。足りなければ、現在の振る舞いをそのまま記録するテスト(特性テスト)、スナップショット、新旧の出力を比べる仕組みを書く。
- 型チェックとリントは振る舞いの固定にならない。

テストが無い領域で、固定せずに構造を動かさない。

### 2. 足りない構造に名前を付ける

コードに欠けている構造を言葉にする。例: 「散らばった真偽値の組み合わせは、実は3つの状態を持つ状態遷移だ」「この if の連鎖は、種類ごとの処理を引く表だ」。形がすでに明確で局所的なら、地味なコードはそのままにする。作り替えは、分岐や不正な状態を減らすものでなければならない。間接層を足すだけの作り替えはしない。

### 3. 目標の形を決める

「今ゼロから作るなら、モジュールの分け方、型、呼び出し関係はどうなるか」を書く。目標が関数の境界をまたぐなら、型とシグネチャだけの骨組みを2案書いて比べ、小さく単純な公開インターフェースの方を選ぶ。

### 4. 足す前に削る

新しい形を作る前に、削る。

- 使われていないコードを消す。
- 呼び出し元が1つしかない薄いラッパーをたたむ。
- 仕様が求めていない、念のための検証を消す。
- どこからも参照されていない定義やファイルを消す。

目標の形にたどり着く最小の変更だけを出荷する。「効くかもしれない」整理は元に戻す。

### 5. 小さな手順で動かす

- 1手ごとに、手順1のテストが通ることを確かめてから次へ進む。
- API を作り替えるときは、全ての呼び出し元を移してから、古い API を同じ作業の中で消す。互換のための中継コードや、新旧2つの経路を残さない。
- 名前の変更は、実際のファイルで全部の使用箇所を確かめる。文字列、ドキュメント、コメントの中の参照は検索から漏れやすい。
- 機械的な編集が多いなら、手でやらずに一括置換のスクリプトを書く。最初の1件を手でやって、スクリプトの結果と比べる。

### 6. 振る舞いが変わっていないことを証明する

「コンパイルが通った」は証明ではない。

- 手順1のテストを全部通す。
- 大きな作り替えなら、新旧の出力を比べるスクリプト、記録した基準を新しいコードで再生する仕組み、実際の面での動作確認のどれかで、同じ振る舞いを示す。

### 7. 残す価値があるか確かめる

成功の基準は、読む人の負担が減ったかどうかだ。読む人が一度に追う必要のある概念、分岐、ファイルの数が、どこかで減っていなければ、変更を元に戻す。

### 8. コミットを整えて PR にする

コミットは「削除 → 作り替え → 後片付け」の順に並べる。各コミットでテストが通るようにする。PR の説明には、変わった構造、固定に使ったテスト、振る舞いが同じことの証拠、読みやすさがどう変わったかを書く。詳しい書き方は open-pr にある。

## 完了の条件

- 構造を動かす前に、振る舞いを固定するテストがあった。
- そのテストが、全てのコミットで通っている。
- 新しい振る舞いが差分に混ざっていない。
- 読む人の負担がどこで減ったかを説明できる。

## 止まって確認する場面

- 公開 API や外部に見える振る舞いを変えざるをえないと分かったとき。それはリファクタではないので、feature として扱うか確認する。
- 固定のテストを書くのに、本番の状態や大がかりな環境が必要なとき。

## 報告に書くこと

1. 変わった構造(前と後)
2. 振る舞いの固定に使ったテスト
3. 振る舞いが同じことの証拠(実行したコマンドと結果)
4. 読みやすさの変化(何が減ったか)
5. 出荷したものと、元に戻したもの

## 使っている規約

- V-01 土台から考える
- V-02 新しい要件は、最初からあった前提で設計し直す
- V-04 足す前に削る
- V-05 最小の変更にとどめる
- V-06 移行は最終形に向けて進める: 互換の中継コードを残さない
- V-08 実物で動作を証明する
- V-12 検証できる小さな単位で進める
- A-06 手作業より、道具を作る: 機械的な編集はスクリプトで
