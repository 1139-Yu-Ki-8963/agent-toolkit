# PR 作成

終わった作業を、レビューする人が1分で判断できる PR にする。PR の説明は、差分を持っているレビュー担当への1分の説明であって、作業日誌ではない。

## いつ使うか

- 実装が終わり、確認も済んだ作業を PR にするとき
- 大きな作業を、複数の PR の積み重ね(スタック)にするとき

**使わないとき。** PR を開いた後のレビュー対応、CI の失敗、コンフリクトは pr-followup で扱う。

## 前提の確認

PR を開く前に、作業そのものが終わっているか確かめる。

- 実物で動作を確かめた証拠がある(テストが通るだけではない)。
- 型チェック、リント、テストがローカルで通っている。

足りなければ、PR を開く前にそこへ戻る。

## 手順

### 1. 差分を掃除する

差分全体を読み、次を取り除く。

- 作業中に入れたデバッグ用の出力、一時ファイル、コメントアウトしたコード
- 頼まれていない変更(関係のない整形、ついでの修正)。必要なら別の PR に切り出す
- コードを見れば分かることを説明しているコメント、「手順1」「フェーズ2」のような作業手順のコメント。残すのは、コードからは分からない「なぜ」だけ
- 不要な抽象化、念のための検証、使われていない引数

### 2. コミットを並べ直す

- コミットを小さく、単独で成り立つ単位にする。各コミットが将来の PR になりうる大きさにする。
- 話の順番に並べる。
  - バグ修正: 失敗するテスト → 修正
  - リファクタ: 削除 → 作り替え → 後片付け
  - 性能改善: 計測の仕組み → 改善
  - 機能追加: 土台(型、設定) → 本体 → 後片付け
- 直前のコミットに属する修正は、そのコミットにまとめる(amend や fixup)。分けられるものは新しいコミットにする。
- コミット本文で、件名を繰り返さない。

### 3. PR の大きさを決める

大きな PR 1つより、狭い PR 5つを選ぶ。分けるときは積み重ね(スタック)にする。

- 一番下の PR は main(trunk)に向ける。
- 上の PR は、すぐ下の PR のブランチに向ける。

```bash
gh pr create --base main            # 一番下
gh pr create --base <下のブランチ>    # その上
```

独立した作業だけ、main から別にブランチを切る。スタックで作業する前に、main に rebase しておく。

### 4. タイトルを書く

Conventional Commits の形にする。末尾に句点を付けない。

```
<種類>(<範囲>): <要約>
```

- 種類: `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`perf` など
- 範囲: 変更した領域(例: `auth`、`export`)
- 要約: 短く、命令形で。変更の中心になる名前があれば入れる
- 例: `fix(export): リトライ時に行が重複する問題を修正`

チームに別の規約があれば、そちらに従う。

### 5. 説明を書く

次の見出しを、この順で使う。書くことがない見出しは省く。短い文で書き、識別子(関数名、パス)は変更の中心になるものだけにする。全体で40行程度に収める。

```markdown
## なぜ
<問題と方針を1〜3文。コミットの経緯や「main を元に」のような前置きは書かない>

## 変更内容
- <1〜3項目。名前を変えたなら、変更前と変更後の両方を書く>

## 範囲
- <何を含み、何を意図的に含めなかったか(後続の作業、既知の課題)を1〜3項目。この見出しは必ず書く>

## トレードオフ
<レビュー担当が聞きそうな、採らなかった案と理由。本当に選択肢がなかったなら省く>

## 影響範囲
<誰に、何に影響するか。なぜ安全か、どこが危ないかを1〜2文>

## 確認方法
- <実際に実行した手順と結果を1〜3項目>
- <性能なら主要な数字を1つ、単位付きで「変更前 → 変更後」>
```

見出しの後に、主張を裏付けるスクリーンショットや動画を添える。詳しい計測結果、長い確認記録は、別のファイルにしてリンクする。

### 6. PR を開く

```bash
gh pr create --base <向け先> --title "<タイトル>" --body-file <説明のファイル>
gh pr view <番号>     # 状態を確かめてから報告する
```

- チームの慣習がなければ、ドラフトではなく、レビュー可能な状態で開く。
- 説明の本文はファイルに書いて `--body-file` で渡す。シェルのコマンドに本文を直接埋め込まない。

### 7. URL を報告して作業に戻る

PR を開いても、レビュー対応を待って止まらない。URL を報告し、スタックの残りがあれば作り続ける。レビュー対応は、ユーザーに頼まれたら pr-followup で行う。

## 完了の条件

- 差分に、デバッグ用のコード、関係のない変更、不要なコメントが残っていない。
- コミットが単独で成り立ち、話の順に並んでいる。
- 説明に、なぜ、範囲、確認方法が書いてある。
- `gh pr view` で状態を確かめた。

## 止まって確認する場面

- 共有ブランチへの force-push が必要なとき。
- PR の向け先(main か、リリースブランチか)がチームの運用で決まっていて、分からないとき。

## 報告に書くこと

1. PR の URL(スタックなら下から順に)
2. タイトルと、説明の「なぜ」の1文
3. 確認方法の要約

## 使っている規約

- V-05 最小の変更にとどめる: 関係のない変更は混ぜない
- V-12 検証できる小さな単位で進める: コミットと PR を話の順に
- A-02 元に戻せる作業は、確認せずに進める: PR を開いても止まらない
- A-03 元に戻せない操作の前は、必ず止まる
- A-10 主張には、根拠かラベルを付ける
- A-11 リンクや引用を捏造しない
- A-12 誰に何が変わるかを先に書く
