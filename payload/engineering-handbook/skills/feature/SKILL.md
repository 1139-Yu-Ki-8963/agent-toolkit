# 機能追加

新しい振る舞いを、設計から PR まで作る。この skill の責任は設計であって、行数ではない。形を決めてから書き、実物で確かめてから渡す。

## いつ使うか

- 新しい画面、API、コマンド、設定項目を追加するとき
- 既存の機能に、新しい要件を組み込むとき

**使わないとき。**
- 間違った振る舞いを直す → bug-fix
- 振る舞いを変えずに構造を変える → refactor
- 方式が決まっていない → 先に prototype で決める
- 複数の PR にまたがる → 先に plan で分ける

## 手順

### 1. 目的と最小の変更を言い直す

最初に、ユーザーの目的、解こうとしている問題、それを満たす最小の変更を自分の言葉で書く。返事は待たずに次へ進む。

### 2. 影響する範囲を読む

変更が入るサブシステムを、入口から実際の呼び出しをたどって読む。主要なデータの型と、それが作られ、変わり、保存される場所を書き出す。似た既存の機能があれば、その作り方と規約を確認する。

### 3. データの形を先に決める

ロジックを書く前に、型、データ構造、関数のシグネチャ、モジュールの境界を決める。

- **ドメインを構造で表す。** 散らばった真偽値の組み合わせより状態遷移(状態を1つの型で表す)を、条件分岐の連鎖より表や登録の仕組みを、同じ形の前提を繰り返すより型付きのモデルを選ぶ。
- **不正な状態を作れない型にする。** ありえない組み合わせは、型の段階で表現できなくする。
- **外部からの入力は境界で1回だけ検証する。** API の入力、設定、DB の行は、受け取った場所で型付きのモデルに変換し、内側では型を信用する。
- **新しい要件は、最初からあった前提で設計する。** 既存の設計に継ぎ足すのではなく、「最初からこの要件があったら何を作ったか」を考える。
- **関数の境界をまたぐ変更なら、設計を2案出す。** 構造から違う2案を、型とシグネチャだけの骨組み(中身は未実装)で書き、比べる。小さく単純な公開インターフェースの後ろに、より多くの複雑さを隠せる方を選ぶ。

### 4. 作業の分け方を書く

ToDo リストに次の4項目を書く。当てはまらない項目も消さずに「該当なし: 理由」と書く。

- **先にやること。** 他の作業の前提になるもの(共有の型、設定、テストの土台)。
- **並行できる作業。** 触るファイルや層が重ならない作業。
- **共有する状態。** 複数の処理が同じ状態を書き換えるか。書き換えるなら、まず状態を分けられないか考える。
- **一番小さく安全な分け方。** 1人(1エージェント)でやるのが最善なら、その理由。

### 5. 小さな単位で実装する

- 問題を解く最小の変更をする。頼まれていない機能、起きるかもしれない例外のための分岐は足さない。
- 単位ごとに、型チェック、テスト、動作確認を通してから次に進む。
- 共有の部品を直したら、それを使っている全ての箇所に反映し、それぞれ確かめる。
- コメントは、コードを見ても分からない「なぜ」だけを書く。手順の説明は書かない。
- 実装をサブエージェントに任せる場合は、ファイルの範囲、決めたデータの形、完了の条件を具体的に渡し、戻ってきた差分は自分で読む。

### 6. 実物で確かめる

テストが通るだけで終わらせない。ユーザーが使うのと同じ面(画面、API、CLI)で、新しい振る舞いを実際に動かして確かめる。画面ならブラウザで操作してスクリーンショットを撮る。API なら実際にリクエストを送って応答を確認する。結果が「どちらとも言えない」なら、合格ではないと明記する。

### 7. 設計に異論が出そうなら、壊しにかかる

設計の判断が割れそうなときは、PR の前に自分で反例を探す。「この変更を壊すには」という観点で、境界値、同時実行、エラー時、既存機能との組み合わせを、実際に実行して試す。実行で示せた問題だけを直す対象にする。

### 8. コミットを整えて PR にする

- コミットを、小さく、話の順番が分かる並びに整える(土台 → 本体 → 後片付け)。各コミットが単独で成り立つようにする。
- PR の説明には、なぜ必要か、何を変えたか、範囲外にしたこと、影響範囲、どう確かめたか、を書く。詳しい書き方は open-pr にある。

## 完了の条件

- 新しい振る舞いを、実物で動かした証拠がある。
- 型チェック、リント、既存のテストが通っている。
- 差分に、頼まれていない変更が混ざっていない。

## 止まって確認する場面

- 調べた結果、頼まれた変更では目的を満たせないと分かったとき。証拠を示して止まる。
- 機能の方向性や仕様の解釈で、実験では決まらない判断が必要になったとき。選択肢と推奨を示す。
- デプロイ、データの削除、共有ブランチへの force-push が必要になったとき。

## 報告に書くこと

1. 目的の言い直し
2. 作ったもの。使う人に何が変わるかを先に書く
3. 選んだ設計と理由。比べた案があれば表で
4. 作業の分け方(手順4の4項目)
5. 確かめた方法と結果(コマンド、スクリーンショット、応答)
6. 残った判断事項

## 使っている規約

- V-01 土台から考える: データの形を先に決める
- V-02 新しい要件は、最初からあった前提で設計し直す
- V-03 前例がなければ、複数案を作って比べる
- V-05 最小の変更にとどめる
- V-07 使う人の体験を優先する
- V-08 実物で動作を証明する
- V-12 検証できる小さな単位で進める
- A-01 最初に、目的を自分の言葉で言い直す
- A-09 サブエージェントの成果は、自分で確かめる
- A-12 誰に何が変わるかを先に書く
