# 性能改善

性能の問題を、計測を軸に直す。この skill の責任は「数字の説明」だ。すべての修正を計測に結び付ける。コードを読んで推測するだけで、計測の代わりにしない。

## いつ使うか

- 画面の表示、API の応答、バッチ処理、ビルドが遅い
- メモリや CPU の使用量が多い
- 性能の改善や劣化を数字で報告する前

**使わないとき。** 遅さの原因が明らかな不具合(無限ループ、誤った条件)なら、bug-fix で扱う。

## 手順

### 1. 主張と判断の基準を先に書く

測る前に、出荷するときの主張を、その言葉のまま書く。例: 「60,000 行のデータで、エクスポートの p50 が 30% 速くなる」。あわせて、どんな結果なら判断が変わるか(この差がなければやめる、など)を書く。

### 2. 測る準備をする

- 計測スクリプトを読み、何を計り、何を計っていないかを確かめる。
- マシンが他の処理で忙しくないか確かめる(`uptime`、`top` など)。止められないなら、比べる側を交互に実行して、同じ雑音を受けるようにし、そのことを報告に書く。
- 本番と同じ条件で測る。リリースビルド、本番と同じ設定と環境変数、同じバージョン、現実的なデータ量と同時実行数。片方だけが既定の設定のままなら、実装ではなく設定を比べていることになる。

### 3. 基準値を測る

変更前の数字を測る。比べる側を交互に(A、B、A、B…)最低5回ずつ実行し、中央値と範囲を記録する。実行ごとのばらつきが、狙う効果より大きければ、まず計測を安定させる。

### 4. 上限を決めている要因を特定する

「なぜ2倍速くないのか」に答える。

- 報告しない別の実行でプロファイルを取る(プロファイラ自体が処理を遅くするため)。CPU 使用率、言語のプロファイラ、I/O 待ち、システムコールの数を見て、重い箇所をソースに対応付ける。
- 負荷をかける側が先に限界になっていないか確かめる。そうなら、負荷をかける側を測っている。
- コードを読んだ推測は、特定ではない。

### 5. 安い打ち手から順に試す

次の順で考え、前の段階で目標に届いたら止める。

1. やらない。誰も結果を使っていない処理をやめる
2. やるが、二度やらない(キャッシュ、結果の再利用)
3. 回数を減らす
4. 後でやる(遅延実行)
5. 見えないときにやる(先読み、バックグラウンド)
6. 並行してやる
7. 安くやる(アルゴリズムやデータ構造の改善)

1回に1つずつ試し、試すたびに測ってから次に進む。効かなかった変更は元に戻す。修正が関数の境界をまたぐなら、型とシグネチャを先に決めてから書く。

### 6. 変更後の数字を検証する

変更後を、手順3と同じ方法で測る。そのうえで、数字そのものを疑う。

1. **限界を超えていないか。** 帯域、コア数、処理全体に占める割合から計算する。全体の10%しかない処理を消しても、全体は最大で約11%しか速くならない。限界を超えた結果は、キャッシュ、空振り、バグを測っている。
2. **エラーは出ていないか。** 失敗やエラー応答の数を数え、出力が正しいことを確かめる。拒否は速く、タイムアウトは遅い。
3. **再現するか。** 差が実行ごとのばらつきより小さければ、「測定できる差はない」とする。
4. **全体に効いているか。** 部分的な改善なら、使う人が待つ処理全体の時間も測り、その中での割合を示す。
5. **本当に実行されたか。** 計測の区間で、処理が実際に行われたことを確かめる。誰も待っていない非同期処理、使われずに捨てられる結果は、起きていない仕事の数字を作る。

結果は、新旧の出力を機械的に比べられる形(JSON、CSV)で保存し、差分を取る。

### 7. PR にまとめる

PR の説明には主要な数字を1つだけ、単位付きで「変更前 → 変更後」の形で書く。実行回数、範囲、上限の要因、プロファイルは、別のファイルにまとめてリンクする。詳しい書き方は open-pr にある。

## 完了の条件

- 変更前と変更後の数字が、同じ条件、同じ方法で測られている。
- 数字に、実行回数、範囲、上限の要因が添えてある。
- 手順6の5つの確認を通っている。

## 判定の書き方

結論を最初に書く: 速くなった、遅くなった、測定できる差はない、判定できない。次のどれかに当てはまるときは「判定できない」とし、何が足りないかを書く。

- 上限の要因を特定できていない
- 片方が本番と同じ条件で動いていない
- エラーの数と、処理が実行されたことを確かめられていない

## 止まって確認する場面

- 改善のために、仕様(表示の内容、データの鮮度、精度)を変える必要があるとき。
- 本番環境での計測や、本番の設定の変更が必要なとき。

## 報告に書くこと

1. 判定(速くなった、など)
2. 変更前の数字、変更後の数字、差(例: 「p50 41 ms → 33 ms、各7回の中央値、変更後の範囲 32〜35 ms、1コアでの JSON 解析が上限」)
3. 上限の要因と、その根拠(プロファイル)
4. 試して効かなかった打ち手
5. 計測結果の保存先

## 使っている規約

- V-08 実物で動作を証明する
- V-09 根本原因を直す
- V-11 数字の理由を説明する
- V-12 検証できる小さな単位で進める: 1回に1つずつ試す
- A-10 主張には、根拠かラベルを付ける
