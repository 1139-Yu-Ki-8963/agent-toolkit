# ベテランエンジニアの振る舞い規約

ベテランエンジニアが無意識にやっている判断を、言葉にしたもの。人間もエージェントも、どの作業でもこの規約に従う。

- コードの書き方はコーディング規約で扱う。ここでは「何をどこまで作るか」と「正しいとどう示すか」を扱う。
- 各項目は ID で参照する。skill から引用するときは「(V-09 根本原因を直す)」のように書く。
- 出典は pstack(cursor/plugins)の原則スキル。日本語に訳し、要点に絞った。

---

## 設計するとき

### V-01 土台から考える

**いつ。** ロジックを書く前。

- データの形を先に決める。主要な型を定め、どこからどう読み書きされるかを洗い出してから処理を書く。
- 後のすべての作業が楽になるもの(CI、リンター、テスト基盤、共有の型)を先に整える。
- 共通化するのは構造であって、似た行ではない。似た処理が3つあっても、早すぎる抽象化よりはましだ。
- 複数の処理が同じ状態を触るなら、「同時に書き換えられたらどうなるか」を先に考える。答えが「何も起きない」でなければ分離する。

**なぜ。** データの形を間違えると、後から直すコストが一番大きい。

### V-02 新しい要件は、最初からあった前提で設計し直す

**いつ。** 既存の設計に新しい要件を組み込むとき。

- 既存の設計に継ぎ足さない。「この要件が最初からあったら、何を作ったか」を考える。
- 影響するファイルを全部読み、型、ドキュメント、例まで変更を行き渡らせる。
- 設計は全体で考え、届けるのは少しずつにする。

**なぜ。** 継ぎ足しを重ねた設計は、誰にも説明できない形になる。

### V-03 前例がなければ、複数案を作って比べる

**いつ。** コードベースに前例のない UI の操作や、アーキテクチャの判断をするとき。

- 2〜3案を実際に動く形で作り、並べて比べてから決める。
- 使い心地のように、理屈では決まらないプロダクトの判断にも使う。

**なぜ。** 説明を読んで選ぶより、動くものを触って選ぶ方が判断を誤らない。

### V-04 足す前に削る

**いつ。** 機能追加、リファクタ、作り直しの順番を決めるとき。

- 不要なコードを先に消してから、新しいものを作る。
- 実際の使われ方に合わせて作る。起きるかもしれない例外のための検証や分岐は足さない。
- 中身のない参照や空のファイルは、残さず消す。
- 作業前より、少し単純で、同じかそれ以上のことができる状態にして終える。

**なぜ。** 複雑なものの上に足すと、複雑さが掛け算で増える。

### V-05 最小の変更にとどめる

**いつ。** 差分の大きさを決めるとき。抽象化やレイヤーを足したくなったとき。

- 問題を解く最小の変更をする。見栄えのよい定型コードより、行数が少ない方を選ぶ。
- 同じ判断を複数の場所に書かない。1か所にまとめ、結果を渡す。

**なぜ。** 差分が小さいほど、レビューしやすく、壊れにくい。

### V-06 移行は最終形に向けて進める

**いつ。** 段階を区切った作り直しや移行をするとき。

- 途中の状態を完璧に保つことより、最終形の正しさを優先する。
- 計画されていて、範囲が決まっていて、元に戻せる一時的な破損は許容する。どこで壊れてよいかは先に宣言する。
- 移行の完了時には、静的チェックと実行時の確認を全部通す。

**なぜ。** 途中の互換性を保つための一時コードは、そのまま長く残る負債になる。

### V-07 使う人の体験を優先する

**いつ。** 実装の楽さと、使う人の満足がぶつかったとき。

- 使う人を優先する。機能も設定項目も、一つずつ存在理由を説明できるようにする。
- 少なく、よく作る。粗い10機能より、磨いた3機能。
- 細部(遷移、余白、反応、エラー時の表示)まで仕上げる。
- 「使う人」は成果物を受け取る人全員を指す。画面ならエンドユーザー、ライブラリなら使う同僚、そして次にこのコードを保守するエンジニアも含む。

**なぜ。** 作る側の都合は、使う人には関係がない。

## 正しさを示すとき

### V-08 実物で動作を証明する

**いつ。** 作業を終えて「できた」と言う前。

- 実物を直接確かめる。「コンパイルが通った」「テストが通った」「たぶん動く」は証明ではない。
- キャッシュや派生した値ではなく、実際の値を読む。
- 確認が失敗したら、システムより先に確認方法を疑う。
- できるだけ、同じ確認を何度でも再実行できるスクリプトにする。結果はレビューする人が見られる形で残す。

**なぜ。** 確かめていない成果物は、正しいかどうか分からない。間違いの上に積むと、後で何倍も高くつく。

### V-09 根本原因を直す

**いつ。** デバッグするとき。

- まず再現する。
- 「なぜ」を繰り返し、最初にシステムが間違った判断をした場所まで遡って、そこを直す。症状が出た場所ではない。
- 推測しない。詰まったらログや計測を足し、実際のエラーと状態を読む。
- その状態がありうるものか考える。ありうるなら、それを扱えなかったコードが原因だ。ありえないなら、それを作り出した場所を探す。ありえない状態にガードを足すのは、バグを隠しているだけだ。
- 同じ原因の箇所を全部探して、まとめて直す。
- 再起動後にだけ起きる問題は、まず保存された状態(設定、キャッシュ、ロックファイル)を疑う。

**なぜ。** 症状だけ直すと証拠が消え、同じ原因が別の場所で再発する。

### V-10 同じ前提で2回失敗したら、前提を疑う

**いつ。** 同じ前提に立った修正が、2回以上同じところで失敗したとき。

- 失敗した修正すべてが置いていた前提を、1文で書き出す。
- その前提が間違っていたら結果が変わるはずの観察を、次の修正の前に行う。
- 証拠が前提を否定したら、原因は別にある。失敗に共通していて、前提で説明できないものを探す。

**止まる条件。** 前提を書き出して確かめるまで、次の修正を始めない。

**なぜ。** 失敗した修正は、それぞれが前提への反証になっている。3回目を同じ前提で打つのは無駄だ。

### V-11 数字の理由を説明する

**いつ。** 性能や評価の数字を測るとき。測った数字を報告したり、判断に使ったりする前。

- 測る前に、どんな結果なら判断が変わるかを書く。実行ごとのばらつきが効果より大きければ、そこで止める。
- 「なぜ2倍ではないのか」に答える。何が上限を決めているか(CPU、ロック、ディスク、ネットワーク、負荷をかける側)を、プロファイルや計測で特定する。コードを読んだ推測は特定ではない。
- その数字が別の何かを測っていないか確かめる。エラー、処理されなかった仕事、キャッシュ、実行されなかったコード、片方だけ調整していない比較、ノイズを順に潰す。
- 数字には、実行回数、ばらつき、上限の要因を添える。

**なぜ。** 説明できない数字は、何を測ったか分かっていない数字だ。

### V-12 検証できる小さな単位で進める

**いつ。** 複数のステップがある作業。一括置換、移行、似た修正の繰り返し。

- 作業を小さな単位に分け、各単位を確認できる状態で終える。確認が通るまで次に進まない。
- コミットと PR は、作業の正しさを示す順番に並べる。基本形は「失敗するテストを先に、修正をその上に」。他にも「削除を先に、作り替えを後に」「計測を先に、改善を後に」がある。
- 各コミットが単独で成り立ち、並びが一つの論証として読めるようにする。

**なぜ。** 壊れた単位ですぐ気付けば原因の特定は安い。まとめて気付くと、壊れた土台の上にさらに積んでしまっている。
