# 形式検証の skill を作る

テストは、誰かが書こうと考えた場合だけを確かめる。形式検証は、述べた範囲のすべての場合を確かめる。述べた範囲とは、モデルの中のすべての手順の順番、上限までのすべての入力、またはすべての入力である。この skill は、リポジトリの中で形式検証がいちばん効く所を見つけ、その所の性質を 1 つ検証し、次のエージェントが変更をその性質に照らして確かめられる、プロジェクトの中の skill を残す。残す skill は、変更の途中で初めて読み、これまでの作業を一度も見ていないエージェントに向けて書く。ユーザーは、検証の言語を学ばずに、結果を信じて動けなければならない。

## 対象をコードから選ぶ

答えはコードから出し、ユーザーには、コードを見ても分からないことだけを聞く。ユーザーが場所かバグを挙げたときは、そこから始める。

よい対象は、コードが守る約束のうち、破れると利用者が害を受け、破れる場合にテストがめったに届かないものである。検証しやすい対象ではなく、リポジトリの中でいちばん強い対象を選ぶ。

## 問いが道具を決める

問いにいちばん安く答える道具を選ぶ。道具は、モデル検査器、証明支援系、SMT を使う検証器、またはほかの道具である。

- 出来事が悪い順番で起こりうるかの問いには、多くの場合、設計の小さなモデルに対するモデル検査器が合う。言語を問わず、その既定は TLA+ である。
- コードそのものが、すべての入力で正しく振る舞うかの問い(メモリ安全、オーバーフロー、データ構造の不変条件など)には、多くの場合、コードの上で動く検証器が合う。
- その言語で動く検証器がないときは、そう言い、手で書いた関数のモデルではなく、本物のコードを、生成した入力でテストする。
- 上限では足りず、どの大きさでも成り立たなければならない性質には、証明が要ることがある。

リポジトリの開発者が入れて動かせる道具を選び、その道具を選んだ理由をユーザーに伝える。

## よい検証が満たすこと

- **コードに忠実である。** モデルか証明のすべての部分が、レビューする人が開けるコードを指す。検証が分けられない 1 つの手順として扱うものは、コードでも分けられない 1 つの手順である。名前は、このリポジトリの名前を使う。
- **失敗できる。** 一度も失敗するのを見ていない検査は、何も証明しない。性質ごとに、その性質が守るコードを壊した版(検査を外す、手順の順を入れ替えるなど)で、検査が失敗するのを見せる。
- **見つけたものは、見つけたものとして扱う。** 今のコードが性質を破るときは、コードの言葉で書いた反例とともに報告する。通るまで性質やモデルを弱めない。ユーザーが頼まない限り、製品のコードを変えない。
- **範囲に正直である。** 何を、どの上限と仮定の下で検証したかと、何を外したかを言う。合格が覆うのは、モデルか上限の中だけで、システムの全体ではない。
- **道具なしで読める。** 性質と害を、それぞれ平易な 1 文で述べる。反例は、コードの言葉で書いた短い手順の並びとして伝える。
- **安く回し直せる。** コマンドが 1 つで、道具の版が再現でき、関わる変更のたびに次のエージェントが回すほど短い時間で終わる。
- **コードと歩調を合わせる。** 検査ごとに、覆うファイルと関数と、検証がそれらを表していると最後に確かめたコミットを記録する。そのコミットのあとに覆うコードが変わったら、次のエージェントは、検証を見直す必要があると分かる。

## 検証の skill を作る

プロジェクトの中の skill を、場所の名前と使う場面を書いた frontmatter とともに書く。frontmatter がないと、skill は読み込まれない。次のエージェントは、その skill だけを読んで、次の 4 つができなければならない。

- 変更が、検証したコードに触れるかを見分ける。
- 検査を走らせる。
- 本物のバグと、モデルの誤りを見分ける。
- 意図した変更のときに、検証を直す。

覆う範囲の記録と同期のコミットを、skill に書く。同期のコミットは、新しいコミットでも検証がコードを表していると確かめてから進めるように、次のエージェントに書く。このリポジトリの本物のコマンド、パス、名前を使い、仮の値を残さない。

検査が TLA+ のモデルのときは、検査器が見つけた不変条件の破れを、初期状態からの最短の手順の並びとして、コードの言葉で読むように書く。道具の出力をそのまま渡さない。

## 渡す前に、動くことを示す

作った skill に、次のエージェントと同じように 1 回従う。そのとき、本物のコードの性質を壊す一時の変更を入れる。skill は、その破れを捕まえなければならない。そのあと、一時の変更を外し、検査が元の状態(合格か、報告する見つけたものだけでの失敗)に戻ったことを確かめる。一度も走らせていない検証の skill は、下書きである。skill が破れを見逃すか、手順が動かないときは、一時の変更ではなく、skill か検証を直す。

## 渡す

ユーザーに、次のことを伝える。

- 何を検証したか
- どの道具を使い、なぜその道具か
- 上限
- 検査が見つけたもの(平易な言葉で)
- 走らせ方
- 覆わないもの

近い対象を見つけたときだけ、2 つ目の対象を勧める。検査をし直さずに入った変更のあとで検証をコードに合わせ直すときは、`/maintain-formal-verification-skill` を使うように伝える。
