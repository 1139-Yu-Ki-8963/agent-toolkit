# E2E テストの実行の基準と指示文

このファイルは、インストールの方法と、テストケースの行の仕分けと結果の 5 列の書き方の判定の基準と、planner、generator、healer への委任の指示文と、スクリプトの説明書を持つ。

## インストールの方法

この章は、対応表である。

OS の見分け方は、セッションの環境の情報の Platform の値 `darwin` を macOS、`linux` を Linux(WSL を含む)、`win32` を Windows に対応させる。OS ごとのインストールのコマンドは、macOS と Linux の node が `brew --version && brew install node`、Windows の node が `winget install OpenJS.NodeJS.LTS` で、macOS と Linux は一般ユーザーの権限で実行でき、Windows の winget は管理者の権限を求め、先に書くファイルは「なし」とする。

### OS の見分け方

実行者は、セッションの環境の情報の Platform の値を、次の表で OS に対応させる。

| Platform の値 | OS |
|---|---|
| `darwin` | macOS |
| `linux` | Linux(WSL を含む) |
| `win32` | Windows |

### OS ごとのインストールのコマンド

次の表のコマンドは、パッケージマネージャのコマンドである。macOS と Linux のコマンドは一般ユーザーの権限で実行でき、Windows の winget は管理者の権限を求める。

| OS | ツール | インストールのコマンド | 先に書くファイル |
|---|---|---|---|
| macOS | node | `brew --version && brew install node` | なし |
| Linux | node | `brew --version && brew install node` | なし |
| Windows | node | `winget install OpenJS.NodeJS.LTS` | なし |

## テストケースの行の仕分けの判定の基準

この章は、判定の基準である。

実行者は、テストケースの表の 1 行ごとに、次の 3 つを順に見て、最初に当たった理由でその行を未実施にする行に入れ、どれにも当たらない行をコードにする行に入れる。1 つ目は、列「前提」の始める所が API で、画面を通らない行で、理由を「API だけのテストケースは、このスキルの範囲の外」とする。2 つ目は、列「前提」か列「入力」が、節「仮に決めた点」の列「確かめる相手」が「テストを行う人」の仮の番号を持つ行で、理由を「テストを行う人が決める仮の点(<仮の番号の一覧>)が残る」とする。3 つ目は、列「前提」の要るテストデータが「なし」でなく、その値がテストケースの md にも seed のテストにも書かれていない行で、理由を「テストデータ(<要るテストデータ>)がない」とする。確かめる相手が「テストを行う人」でない仮の点(画面のパス、ボタンの文言)は、planner がアプリから決めるので、未実施の理由にしない。期待結果の「画面の外: <見る所>」は確かめず、未実施の理由にしない。

## 計画の委任の指示文

この章は、委任の指示文である。

実行者は、空欄 `<planner の定義のファイルのパス>`、`<コードにする行の ID の一覧>`、`<アプリの URL>`、`<seed のテストのパス>`、`<計画の md のパス>`、`<テストケースの md の全文>` に値を書き込み、ほかの文はそのまま写す。

````text
この指示文の担当は、Playwright の planner です。
最初に、<planner の定義のファイルのパス> を全文読み、その定義の手順とツールに従ってください。
次のテストケースの md を要件の文書とし、ID が <コードにする行の ID の一覧> の行だけを計画にしてください。
アプリの URL は <アプリの URL>、seed のテストは <seed のテストのパス> です。
計画の md は <計画の md のパス> に 1 つだけ書き、ほかのファイルを書き換えず、消さないでください。
計画の中の 1 つのテストの名前は、「<ID> 」で始めてください。
テストケースの md の仮に決めた点のうち、画面のパスやボタンの文言のようにアプリを探れば分かる値は、アプリから決めてください。
期待結果の「画面の外: <見る所>」は、計画に入れないでください。

テストケースの md:
<テストケースの md の全文>

返す書式:
計画を書けたときは、1 行目に「計画を書いた: <計画の md のパス>」を、続けて見出し「| ID | アプリから決めた値 |」と区切りの行「|---|---|」と、ID ごとに 1 行の表を返してください。
決めた値がない ID は、「なし」と書いてください。
計画を書けないときは、「中止: <理由>」の 1 行だけを返してください。
````

## コードの委任の指示文

この章は、委任の指示文である。

実行者は、空欄 `<generator の定義のファイルのパス>`、`<計画の md のパス>`、`<テストのファイルのパスの一覧(1 行に 1 件、ID とパス)>`、`<seed のテストのパス>`、`<アプリの URL>` に値を書き込み、ほかの文はそのまま写す。

````text
この指示文の担当は、Playwright の generator です。
最初に、<generator の定義のファイルのパス> を全文読み、その定義の手順とツールに従ってください。
<計画の md のパス> の計画から、Playwright のテストを書いてください。
1 つの ID のテストは、次の一覧のその ID のパスの 1 つのファイルに書き、テストの名前を「<ID> 」で始めてください。
<テストのファイルのパスの一覧(1 行に 1 件、ID とパス)>
seed のテスト <seed のテストのパス> を見本にしてください。アプリの URL は <アプリの URL> です。
一覧のパスのほかのファイルを書き換えず、消さないでください。

返す書式:
見出し「| ID | 書いたか |」と区切りの行「|---|---|」に続けて、ID ごとに 1 行の表を返してください。
列「書いたか」の値は、「書いた」か「書けなかった(<理由>)」と書いてください。
1 件も書けないときは、「中止: <理由>」の 1 行だけを返してください。
````

## 修復の委任の指示文

この章は、委任の指示文である。

実行者は、空欄 `<healer の定義のファイルのパス>`、`<失敗したテストの一覧(1 行に 1 件、テストのファイルのパスとテストの名前)>`、`<実行日時のフォルダのパス>` に値を書き込み、ほかの文はそのまま写す。

````text
この指示文の担当は、Playwright の healer です。
最初に、<healer の定義のファイルのパス> を全文読み、その定義の手順とツールに従ってください。
次の失敗したテストを、1 件ずつ直して流し直してください。
<失敗したテストの一覧(1 行に 1 件、テストのファイルのパスとテストの名前)>
失敗したときの報告とトレースは、<実行日時のフォルダのパス> にあります。
直すのは一覧のテストのファイルだけとし、ほかのファイルを書き換えず、消さないでください。
機能が壊れていると判断したテストは、skip の形にしてください。

返す書式:
見出し「| テストのファイルのパス | 直した結果 |」と区切りの行「|---|---|」に続けて、テストごとに 1 行の表を返してください。
列「直した結果」の値は、「直した」「skip にした」「直せなかった」のどれかと書いてください。
作業ができないときは、「中止: <理由>」の 1 行だけを返してください。
````

## サブエージェントが返す書式

この章は、委任の指示文である。

planner は、1 行目の「計画を書いた: <計画の md のパス>」と、列「ID」「アプリから決めた値」の表を返す。generator は、列「ID」「書いたか」の表を返し、列「書いたか」の値は「書いた」か「書けなかった(<理由>)」とする。healer は、列「テストのファイルのパス」「直した結果」の表を返し、列「直した結果」の値は「直した」「skip にした」「直せなかった」のどれかとする。3 つのどれも、作業ができないときは、「中止: <理由>」の 1 行だけを返し、この 1 行を中止する返り値とする。

## 結果の 5 列の書き方

この章は、判定の基準である。

実行者は、テストケースの表の 1 行ごとに結果の 5 列を次のとおりに書き、ほかの 8 列のセルと、表のほかの節を読んだ中身のまま残す。列「結果(合格、不合格、未実施)」は、使った結果の状態が expected か flaky の行を「合格」、unexpected の行と、healer が skip にした行を「不合格」、未実施にする行と、generator がコードを書けなかった行を「未実施」とする。列「実際の結果」は、合格の行に「期待結果のとおり」と planner がアプリから決めた値を、不合格の行に「コードの誤りか不具合かは未確認」(healer が skip にした行は「機能が壊れている(healer の判定)」)を、未実施の行に未実施の理由を書き、期待結果に「画面の外:」を持つ行には「画面の外は未確認」を足す。列「実施日」は、使った結果の実行日時の日付を YYYY-MM-DD の形で書く。列「実施者」は「AI(Playwright)」とする。列「証跡と不具合の番号」は、実行した行に `e2e-results/<実行日時>/report/index.html` と `e2e-results/<実行日時>/trace/` を書き、未実施の行に「なし」を書き、不具合の番号を書かない。行「- テスト環境:」は、「- テスト環境: <アプリの URL>、<ブラウザの名前>」とし、ブラウザの名前は使った結果のプロジェクトの名前(例: chromium)とする。セルの中の縦棒は `\|` と書く。

## run-playwright-tests.js の説明書

この章は、スクリプトの説明書である。

### 呼び方と終了コード

- 呼び方: `node "<SKILL.md があるフォルダ>/scripts/run-playwright-tests.js" "<出力先のフォルダ>" "<実行日時>" "<テストのファイルのパス>" ...`
- 標準出力: テストごとに「<テストのファイルのパス>(タブ)<プロジェクトの名前>(タブ)<状態>(タブ)<テストの名前>」の 1 行。状態は expected、unexpected、flaky、skipped のどれか
- 終了コード: 0 はすべての状態が expected か flaky、1 はほかの状態を含むか、cli.js がないか、`results.json` ができない(cli.js がないときと `results.json` ができないときは、標準エラーに「失敗: <起きたこと>」の行)、2 は呼び出しの誤り(引数が足りないか、実行日時のフォルダが既にある。標準エラーに「失敗: <起きたこと>」の行)
- テスト: `scripts/tests/run-playwright-tests.test.js`(一時フォルダに偽の `cli.js` を置いて流し、終了コードと標準出力を確かめ、終わるときに一時フォルダを消す)

### 1 行ごとの処理と理由

| 行の中身 | 処理 | 理由 |
|---|---|---|
| `#!/usr/bin/env node` | node でこのファイルを実行する | 規約のスクリプトはシェバンを持つ実行可能なファイルとするため |
| `const fs = require('fs');` | ファイルを扱う部品を読み込む | フォルダの有無を見て、作り、`results.json` を読むため |
| `const path = require('path');` | パスを組み立てる部品を読み込む | OS ごとの区切りの違いを部品に任せるため |
| `const { spawnSync } = require('child_process');` | 別のプロセスを起動する関数を読み込む | 組み立てた文字列をシェルに渡さず、引数の配列で Playwright を起動するため |
| `function fail(message, code) {` | 失敗を伝える関数を始める | 「失敗:」の行と終了コードの伝え方を 1 か所にまとめるため |
| `process.stderr.write('失敗: ' + message + '\n');` | 標準エラーに「失敗:」の行を書く | 呼んだ step が中止の理由に写すため |
| `process.exit(code);` | 呼んだ箇所が渡した終了コードで終わる | 呼び出しの誤りを 2 で、流せなかったことを 1 で、決まった終了コードのとおりに伝えるため |
| `}` | 関数を閉じる | 構文のため |
| `const [projectDir, runName, ...testFiles] = process.argv.slice(2);` | 引数から出力先のフォルダ、実行日時、テストのファイルのパスを取り出す | 呼び方の並びのとおりに受け取るため |
| `if (!projectDir \|\| !runName \|\| testFiles.length === 0) fail(..., 2);` | 引数が足りないときに、終了コード 2 の失敗にする | 流すテストのないまま Playwright を起動しないため |
| `const root = path.resolve(projectDir);` | 出力先のフォルダを絶対パスにする | 起動するプロセスの作業フォルダと出力のパスをそろえるため |
| `const cli = path.join(root, 'node_modules', '@playwright', 'test', 'cli.js');` | 出力先のフォルダの Playwright の cli.js のパスを作る | npx を通さず、どの OS でも node で Playwright を起動するため |
| `if (!fs.existsSync(cli)) fail(cli + ' がない', 1);` | cli.js がないときに、終了コード 1 の失敗にする | Playwright が入っていないプロジェクトで流さないため |
| `const runDir = path.join(root, 'e2e-results', runName);` | 実行日時のフォルダのパスを作る | 報告とトレースを実行ごとのフォルダに置き、Playwright が実行を始めるたびに空にする既定の出力のフォルダ(test-results/)の外に残すため |
| `if (fs.existsSync(runDir)) fail(runDir + ' が既にある', 2);` | 実行日時のフォルダが既にあるときに、終了コード 2 の失敗にする | 前の実行の報告とトレースを上書きせず、消さないため |
| `fs.mkdirSync(runDir, { recursive: true });` | 実行日時のフォルダを作る | 報告とトレースと `results.json` の置き場を先に作るため |
| `const jsonFile = path.join(runDir, 'results.json');` | `results.json` のパスを作る | JSON の報告の置き場を決めるため |
| `const env = Object.assign({}, process.env, {` | 今の環境変数を写して足す値を始める | 利用者の環境変数を残したまま、報告の場所だけを足すため |
| `PLAYWRIGHT_HTML_OUTPUT_DIR: path.join(runDir, 'report'),` | HTML の報告の置き場を実行日時のフォルダの `report/` にする | 既定の `playwright-report/` を上書きしないため |
| `PLAYWRIGHT_HTML_OPEN: 'never',` | HTML の報告をブラウザで開かないようにする | 実行が報告を開いたまま止まらないようにするため |
| `PLAYWRIGHT_JSON_OUTPUT_FILE: jsonFile,` | JSON の報告の置き場を `results.json` にする | テストごとの状態を読むため |
| `});` | 足す値を閉じる | 構文のため |
| `const args = [cli, 'test', ...testFiles, '--trace=on', '--output=' + path.join(runDir, 'trace'), '--reporter=html,json'];` | Playwright に渡す引数を並べる | 流すテストのファイルだけを流し、トレースを必ず残し、トレースを実行日時のフォルダの `trace/` に置き、HTML と JSON の報告を書くため |
| `spawnSync(process.execPath, args, { cwd: root, env, stdio: ['ignore', 2, 2] });` | node で Playwright を起動し、終わるまで待つ | Playwright の出力を標準エラーに回し、標準出力をテストごとの行だけにするため |
| `if (!fs.existsSync(jsonFile)) fail(jsonFile + ' ができない', 1);` | `results.json` がないときに、終了コード 1 の失敗にする | Playwright が結果を書けなかったことを伝えるため |
| `const report = JSON.parse(fs.readFileSync(jsonFile, 'utf8'));` | `results.json` を読んで値にする | テストごとの状態を取り出すため |
| `const lines = [];` | 標準出力に書く行の入れ物を作る | テストごとの行を集めるため |
| `function walk(suite) {` | 入れ子のテストの集まりをたどる関数を始める | JSON の報告はファイルと describe ごとに入れ子になるため |
| `for (const spec of suite.specs \|\| []) {` | 集まりの中のテストの定義を 1 つずつ見る | テストの名前とファイルを取るため |
| `for (const test of spec.tests \|\| []) {` | 定義の中のプロジェクトごとの実行を 1 つずつ見る | ブラウザごとの状態を取るため |
| `lines.push([spec.file, test.projectName, test.status, spec.title].join('\t'));` | ファイル、プロジェクトの名前、状態、テストの名前をタブで区切った 1 行を足す | 呼んだ step が行ごとに読めるようにするため |
| `}` | 内側の繰り返しを閉じる | 構文のため |
| `}` | 外側の繰り返しを閉じる | 構文のため |
| `for (const child of suite.suites \|\| []) walk(child);` | 子の集まりを同じ関数でたどる | 入れ子の深さによらずすべてのテストを集めるため |
| `}` | 関数を閉じる | 構文のため |
| `for (const suite of report.suites \|\| []) walk(suite);` | 一番上の集まりから順にたどる | 報告のすべてのテストを集めるため |
| `process.stdout.write(lines.join('\n') + (lines.length ? '\n' : ''));` | 集めた行を標準出力に書く | 呼んだ step が実行の結果として読むため |
| `const allPassed = lines.every((line) => ['expected', 'flaky'].includes(line.split('\t')[2]));` | すべての状態が expected か flaky かを見る | 終了コードを決めるため |
| `process.exit(allPassed ? 0 : 1);` | すべて通れば 0、ほかの状態があれば 1 で終わる | 決まった終了コードで、失敗を含むかを伝えるため |
