# 影響範囲

変更がほかのどこかで壊すものを、出す前に見つける。「X の影響範囲」「これで何が壊れうるか」のような依頼や、まだ信じきれない小さな差分をレビューするときに使う。

呼び出し元を並べることは、この仕事ではない。それは、エージェントが grep で一瞬で出せる。この仕事は、grep に出ない壊れ方を見つけることである。

## 自分の書いた説明を信じない

もっともらしく聞こえる影響範囲の説明には、価値がない。正しくても誤りでも、同じように説得力があるからである。そのため、説明を渡すのではなく、全体が頼っている 1 つか 2 つの事実を見つけ、コードを走らせて証明する。

### どこまで確かか

変更の安全が頼る事実ごとに、次の段階のうち、安く届く所まで進め、どこで止まったかを言う。

1. 自分がそう言った。それだけでは価値がない。
2. その行を指した。本物の `file:line`、またはライブラリそのもののソースである。
3. 悪い場合が起こりえないことを示した。失敗を一歩ずつたどり、そこに届かないことを示した。
4. 走らせた。本物のコードを呼び、自分が誤っていれば大きな音で失敗するスクリプトかテストである。
5. 動いているアプリで再現した。

段階 4 は、多くの場合、アプリが使うのと同じライブラリを読み込み、心配している関数そのものを呼ぶ、小さなスクリプト 1 本である。

## 手順

1. 変更を読む。差分と、変更が足し、変え、消すシンボルと、変更が今は違うことをする点を読む。差分が書いていない部分も含める。プルリクエストとそのコミットを取ってくる。
2. 変更が安全である理由の 1 つの事実を見つける。危なく見える変更の多くは、1 つの事実のおかげで安全である。たとえば、「この呼び出しは、すでに使われていないキャッシュの項目を捨てるだけで、ほかに何もしない」である。その事実を見つける。それが成り立てば、危ない場合の多くが一度に晴れる。時間は、ありうることの長い一覧ではなく、ここに使う。
3. grep が止まる所を見る。呼び出すライブラリのソースを読み、固定した版と、手元の当て布(パッチ)を確かめる。いつ何が走るかを考える(マイクロタスク、アンマウントと後始末、Solid と React の違いなど)。シンボルの検索が見落とすものをたどる。API が返す JSON、DB の列、通信の形式、同じバイトを読むほかの言語、機能のフラグ、3 段先の下流のコードである。
4. 危険ごとに正直に書く。危険ごとに、起こる本当の見込みと、起きたときの本当の損失を付ける。確かめた危険は残し、確かめて晴れたものは別に並べる。本物の `file:line` を引く。何も見つからない検索も、1 つの答えである。呼び出し元や API を作り話にしない。
5. 1 つの事実を証明する。本物のコードを走らせるスクリプトかテストを書き、走らせ、起きたことを貼る。
6. 大きな変更か広い変更では、互いの結果を知らない 2 つ以上のサブエージェントに同じ問いを出し、答えをまとめる。判定者が違えば、見つける本物のバグも違う。

## 渡すもの

- **何をするか。** 何が変わったか。分かりにくい部分を含める。
- **安全である理由の 1 つの事実。** その事実を述べ、どの段階まで届いたかを言い、証明を見せる。証明できなかったときは、「証明していない」と書く。
- **危険。** 危険ごとに、どう壊れるか、`file:line`、見込みと損失の大きさ、確かめ方を書く。大事な危険には、証明を貼る。
- **晴れたもの。** 何を確かめ、なぜ問題ないか。
- **マージの前に。** 本物のバグを捕まえる、いちばん安いテストか再現。自分が書いたスクリプトを含める。

本物のコードを引き、公開される所に出す前に、私的な情報を取り除く。

**返答:** 上の説明。安全である理由の 1 つの事実は、証明したか、「証明していない」と書いたかのどちらかとする。
