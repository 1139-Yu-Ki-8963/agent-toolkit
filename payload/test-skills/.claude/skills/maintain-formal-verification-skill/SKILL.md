# 形式検証の skill を保つ

形式の検査は、それが表すものの性質を証明する。コードが変わり、検証が変わらないと、検査は、もうないコードを表したまま合格し続けることがある。この合格は、証明に見えるので、いちばん危ない。この skill は、`/create-formal-verification-skill` が作った検証の skill か、名前の付いたコードに対してモデル検査器、証明器、コードの上で動く検証器を走らせる、プロジェクトの中の skill を保つための手順である。プロジェクトの中の skill は、エージェントがその skill を使いながら行う変更を扱う。この skill は、その skill を通らなかった変更を扱う。その変更とは、マージ、skill を使わずに行った編集、多くのコミットにわたって積もったずれである。

## 結果

検査ごとに、次の結果を 1 つ付け、どれかを言う。

- **同期済み**: 最後の同期のあとの変更は、検査が表すものを変えず、検査は合格する。
- **更新済み**: コードが変わり、検証が今は新しいコードを表し、検査は合格する。
- **バグ**: 検証は今のコードを表し、コードが性質を破る。これはコードについての見つけたものであり、ずれではない。
- **止まった**: 検査をコードに合わせ直せなかったか、走らせられなかった。理由を正確に言う。

1 つの検査が、更新済みとバグの両方になることがある。更新で検証が再びコードを表し、そのうえで性質がそのコードで破れる場合である。

## 直してよい範囲

直すのは、検証だけである。検証とは、モデル、ハーネス、性質のファイル、検証の skill そのものである。ユーザーが頼まない限り、作業の間に製品のコードを直さない。今のコードで性質が破れるときは、通すために性質やモデルを弱めず、失敗を報告する。

## 手順

1. **検査を見つける。** 検証の skill には決まった名前がないので、働きで見つける。働きとは、名前の付いたコードに対して、モデル検査器、証明器、またはほかの検証器を走らせるプロジェクトの skill であることである。見つけたものを 1 つずつ読む。ユーザーが名前を挙げたときは、その 1 つを読む。検査ごとに、次のものを集める。

   - 性質
   - 覆うコード
   - 上限と仮定
   - 走らせるコマンド
   - 検証がコードを表していると最後に確かめたコミット

   検証の skill がないときは、止まり、`/create-formal-verification-skill` を示す。skill が同期のコミットを記録していないときは、検証のファイルを最後に変えたコミットを使い、そうしたことを言う。

2. **そのまま走らせる。** 何かを変える前に、検査ごとに 1 回走らせ、結果を記録する。ここでの合格は、コードが正しいことを示さない。古い表し方がまだ成り立つことを示すだけである。ここでの失敗は、ずれかバグのどちらかである。どちらかは、手順 5 まで決めない。

3. **覆うコードへの変更を、すべて読む。** 同期のコミットから今のコミットまでの、覆うファイルの差分を取り、コミットのメッセージを 1 つずつ読む。動いたコードも探す。名前が変わった関数、分かれた関数、ほかのファイルに移った関数は、まだ覆うコードである。検査が守る状態に触れる新しいコード(同じ欄に書く新しい関数など)も探す。変更ごとに、次のどれかを決める。
   - **影響なし。** 変更は、検証が表すものを何も変えない(書式、コメント、検証が覆わない経路など)。この判断は、コミットのメッセージではなく、モデルかハーネスに照らして行う。
   - **検証が、もうコードを表していない。** 分けられない 1 つの動作だった手順が 2 つになった、分岐が足されたか消された、検査が動いた、新しい経路が守る状態に届く、値の範囲が変わった、のどれかである。モデルかハーネスを変える必要がある。
   - **約束が、意図して変わった。** 変更がコードの約束を変え、変更の中の証拠(ドキュメントのコメント、テスト、変更履歴、コミットのメッセージ)が、それを意図したことだと言う。性質を変える必要があり、その証拠を引く。
   - **約束が、破れたかもしれない。** コードが変わり、約束が変わったと言う証拠がない。このあとに続く失敗は、バグの候補として扱う。

4. **結果からではなく、コードから直す。** 変わった部分のそれぞれが、レビューする人が開けるコードを再び指すように、モデルかハーネスを変える。コードの分けられない 1 つの手順は、検証でも 1 つの手順に保つ。直しは、回し直す前にコードから書き、検査が通る形に合わせない。性質は、約束が意図して変わったときだけ変え、古い文、新しい文、証拠を書き残す。変更で上限が誤りにならない限り、上限は保つ。上限を減らすときは、報告にそう書く。

5. **回し直し、結果ごとに判断する。**
   - **合格のとき:** 検査は、失敗する力をなくした表し方の上で合格しているかもしれない。性質が守るとおりに新しいコードを壊し(新しい検査を外す、新しい手順の順を入れ替えるなど)、検査がそれを捕まえることを確かめる。そのあと、壊した変更を外す。
   - **失敗のとき:** 反例を、本物のコードに対して、手順ごとにたどり直す。ある手順がコードで起こりえないなら、検証が誤っている。検証を直し、何が誤っていたかを言う。すべての手順が起こりうるなら、バグである。そのバグを入れたコミットを挙げ、反例をコードの言葉で書いた手順の並びとして伝え、害を 1 文で述べる。本物のコードに対する安いテストか再現でバグを示せるなら、証拠として報告に足す。それを製品のコードにコミットはしない。

6. **検証の skill を直す。** 検査ごとに覆うコード、コマンド、上限、仮定、同期のコミットを直す。同期のコミットは、確かめたコミットにする。止まった検査の同期のコミットは動かさず、報告にそう書く。そのあと、次のエージェントと同じように検証の skill に 1 回従い、手順がまだ動くことを確かめる。

## 報告

検査ごとに、ユーザーに次のことを伝える。

- 結果と、読んだコミット
- 検証の何を、なぜ変えたか。変更ごとに短い理由(コードの形が変わった、または、約束が意図して変わった(証拠を付けて))
- 回し直しの結果と、直した検査がまだ失敗できることを示すために使った壊し方
- バグごとに、平易な言葉で、コードの言葉で書いた反例の手順、害、そのバグを入れたコミット
- 検証がまだ覆わないもの。覆うべきなのに覆っていない新しいコードを含む

どの失敗が検証のずれで、どの失敗がコードのバグかを、はっきり言う。直す前に合格し、直したあとに失敗する検査については、前の合格が古い表し方の上のものだったと言う。

検証の直しは、製品の修正とは分けて、それだけの変更にする。
